# Проверить архив без ввода команды

Оставьте исходный ZIP-файл без изменений. Распакуйте весь архив и дважды щелкните по
`VERIFY.cmd` в Windows. В качестве альтернативы перетащите исходный ZIP-файл на `VERIFY.cmd`.
В macOS/Linux запустите `sh VERIFY.sh` из терминала.

Если ровно один из ближайших ZIP-файлов имеет тот же манифест, что и извлечённая копия,
программа проверки отображает его путь и запрашивает подтверждение. В противном случае она запрашивает
путь к исходному ZIP-файлу. Обнаружение не является проверкой: полные проверки всё равно выполняются.
Перемещение или переименование ZIP-архива не приводит к потере его действительности. Распакованные файлы
не являются объектом проверки. Проверка печати только по HTML-файлу не заменяет
проверку ZIP-архива.

Программа-запуска запрашивает отпечаток ключа подписи, полученный **отдельно** из
источника, которому доверяет получатель. Допускаются пробелы, двоеточия и шестнадцатеричные символы в верхнем регистре.
Если отпечаток не ввести, подпись останется неподтверждённой. Ключ,
указанный внутри архива, никогда не принимается автоматически в качестве доверенного отпечатка.
Ввод отпечатка обрабатывается на языке Python и никогда не оценивается оболочкой.

Существующий верификатор отображает цветной результат проверки целостности с пояснениями
и записывает изображение в формате UTF-8 `verify-result-<UTC>-<random>.txt` рядом с исходным ZIP-файлом. Если
в этот каталог запрещен запись, он пытается записать изображение `~/TgWitness-verifications/`. Результаты
не перезаписывают предыдущие транскрипты и не становятся частью подписанного архива.
В транскрипте фиксируются путь к архиву и его SHA-256, путь к верификатору и его SHA-256,
локальное время начала и окончания, предупреждения о доверии, проверки и статус завершения. Транскрипт не подписывается.
Хеш архива проверяется повторно после верификации для обнаружения изменений, произошедших во время
выполнения. Верификатор, предоставленный злонамеренным отправителем, всё равно может вводить в заблуждение: при необходимости независимой верификации следует
независимо получить код и среду выполнения.

Статус завершения 0 означает, что запрошенные проверки целостности прошли успешно. Информацию о привязке подписавшего,
охвате и проверке временной метки см. в соответствующих разделах отчета.
Статус 1 означает, что проверка завершилась неудачно; 2 означает, что
рабочий процесс не был завершен (например, отсутствие среды выполнения, отмена, недопустимые
входные данные или невозможность сохранить стенограмму). Отсутствие отпечатка приводит к
желтому результату проверки. Привязанный ключ может дать зелёный результат проверки **целостности**, хотя
ограничения по охвату или независимому времени остаются видимыми.

<a id="runtime-and-language"></a>
## Среда выполнения и язык

Программа запуска Windows сначала пробует запустить встроенный интерпретатор в `python/`
, затем в
`verifier/python/`
, а затем — совместимую установленную версию Python. Путь к Python должен
содержать Python 3.11+ и `cryptography`
. Программа не устанавливает зависимости и не
загружает среду выполнения. Функция обнаружения отключает автоматическую установку лаунчера Python и
переключатели среды «dry-run». Python запускается в режиме `-I -B -X utf8`
: модули из папки evidence-folder
и пакеты пользовательского сайта исключаются из импорта, байт-код не
записывается, а ввод/вывод осуществляется в кодировке UTF-8. См. официальную
[документацию по изолированному режиму](https://docs.python.org/3/using/cmdline.html#cmdoption-I)
и [настройки лаунчера Windows](https://docs.python.org/3/using/windows.html#configuration)
.

Автономный пакет для Windows содержит тот же файл `verify.py`, программы запуска,
встроенную официальную среду выполнения Python, а также закреплённые криптографические зависимости и
их лицензии. Он не включает панель и не запускает сервер. Используйте его собственный файл
`VERIFY.cmd` с любым поддерживаемым исходным ZIP-файлом или скопируйте его каталог `python/`
рядом с программой запуска из пакета. Получите дистрибутив и проверьте его контрольную сумму
через надёжный канал, отдельный от самого загрузочного файла. В сборке используется
существующая закреплённая среда выполнения Python из репозитория и файл `deploy/constraints.txt`.

Сборка на Windows с использованием Python 3.12. На хосте сборки не требуется никаких предварительно установленных
зависимостей приложений: генерация запускающего файла выполняется внутри только что скомпилированной встроенной среды выполнения.

```powershell
python tools/build_verifier.py
```

Здесь собирается `dist/TgWitness-verifier-<version>-windows-<arch>-all.zip` и
дополнительный файл SHA-256. `VERIFY.cmd` содержит список всех названий языков и принимает номер
или код языка. Кнопка «Enter» выбирает обнаруженный язык системы. `--language de`,
например, собирается с фиксированным значением по умолчанию; каждая сборка по-прежнему содержит все
языки. Локализованные инструкции также находятся в `languages/START_HERE-<code>.txt`.
Сборка проверяет общедоступный фиктивный демонстрационный архив со встроенной средой выполнения;
`--validation-archive PATH` выбирает другой сохраненный архив. Она запускает реальный запускающий файл bat
для проверки чистых и подделанных ZIP-архивов, а затем запускает его на всех языках
при отсутствии системного Python в PATH. Сборка не публикует релиз. Публикация на
GitHub Releases или get.destroy.tools по-прежнему является отдельной операцией выпуска.

Инструкции запуска, подсказки, метки проверок, пояснения, сводки об ошибках
и сохраненные стенограммы поддерживаются на всех 25 языках панели: английском, русском,
украинском, испанском, португальском, турецком, арабском, персидском, урду, хинди,
индонезийский, вьетнамский, упрощённый китайский, французский, немецкий, итальянский, узбекский,
корейский, традиционный китайский, малайский, польский, японский, тайский, иврит и бенгальский.
Генерируемые запускающие программы архивов используют язык отчёта; коды неизвестных языков
отклоняются, а не заменяются запускающей программой на английском языке без уведомления. Автономная
программа проверки принимает любой код панели с `--lang`, включая региональные псевдонимы,
такие как `pt-BR` и `zh-TW`. `--choose-language --interactive` открывает меню.
Имена файлов, хэши, исходные записи и исходная техническая диагностика сохраняются
дословно; их перевод изменил бы доказательства или затруднил бы обнаружение ошибки.
Подробные описания опций командной строки остаются технической документацией на английском языке.
Новый графический интерфейс не требуется. Среда выполнения Windows не является средой выполнения macOS/Linux;
`VERIFY.sh` требует уже установленного совместимого `python3` и зависимостей.

Каталог исходных текстов для чтения — это `tgwitness/verifier_languages.json`.
Существующие переводы панелей содержат устоявшуюся терминологию в области доказательств; сообщения
рабочего процесса получателя переводятся в этом каталоге. Сжатая копия встроена
в `verify.py`, поэтому она работает без файла каталога, установки приложения,
сетевого сервиса перевода или импорта из каталога доказательств. После редактирования
переводов запускается `python tools/sync_verifier_languages.py`; `--check` проверяет,
синхронизирована ли встроенная копия. Проверки каталога требуют точного набора языков
панелей, полных ключей и неизменённых заполнителей. Объяснения для языков CJK, индийских и с направлением письма справа налево
сохраняют полные абзацы Unicode, а не вставляют разрывы строк
внутри формирующих последовательностей; конечный рендеринг по-прежнему зависит от используемых шрифтов.

<a id="extra-verification-inputs"></a>
## Дополнительные данные для проверки

По умолчанию при двойном щелчке файл ZIP проверяется локально. При этом не предполагается доверие к
центрам сертификации временных меток и не происходит автоматическое доверие к контрольной точке внутри того же самого ZIP-архива.
Опытные пользователи могут передать независимо сохраненные входные данные тому же самому коду:

```text
python -I verify.py archive.zip --interactive --lang en --checkpoint retained.json
python -I verify.py archive.zip --pretty --explain --fingerprint TRUSTED_SHA256
python -I verify.py archive.zip --pretty --explain --fingerprint TRUSTED_SHA256 --tsa-ca trusted-root.pem
python -I verify.py archive.zip --pretty --explain --witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness
```

Для встроенной среды выполнения Windows используйте `python/python.exe` вместо `python`.
Для проверки по RFC 3161 требуется доверенный корневой сертификат центра сертификации (`--tsa-ca`); OpenSSL
не требуется. Аутентификация Bitcoin с помощью OpenTimestamps остаётся отдельной проверкой.
Максимальный размер распакованного ZIP-архива по умолчанию составляет 4 GiB; `--max-gib` явно изменяет
это значение. `--jobs N` задаёт, сколько процессов будет одновременно проверять большой архив; `auto`,
по умолчанию, использует по одному процессу на каждый процессор (до 16), а `--jobs 1` — проверку в одном процессе. `--json` сохраняет машинно-читаемый формат, в том числе когда `--explain`
указан. `--plain --explain` предоставляет читаемые пояснения без цвета.

В интерактивном режиме также сохраняются элементы `--strict`, `--require-tier`, `--check-bitcoin`,
`--bitcoin-source` и параметры запечатанного подтверждения. При строгих или невыполненных требованиях к надежности возвращается
статус 2; при аутентифицированном новом формате возвращается статус 3 с элементом `--strict`. Элементы
`--check-drand`, `--check-bitcoin` и соответствующие требуемые уровни могут использовать
сетевые службы. `--check-bitcoin` берет заголовки блоков из двух публичных эксплореров
и требует, чтобы они совпадали; `--bitcoin-source URL` вместо этого использует API Esplora вашего собственного
узла (повторите это, чтобы потребовать совпадения нескольких источников). Для проверки аттестации требуется установленный TgWitness
— верификатор запечатанных данных — и `gh`; автономный архив не предоставляет этих инструментов.

`VERIFY.cmd`, `VERIFY.sh` и `START_HERE.txt` генерируются перед подписанием
манифеста для целей экспорта в целях доказательств, чата, передачи, учёта, раскрытия информации и свидетельских показаний.
Они хешируются и подписываются как обычные элементы архива. Зашифрованные транспортные
обертки необходимо сначала открыть, чтобы получить исходный подписанный ZIP-файл. Более ранние ZIP-файлы
остаются проверяемыми без повторной упаковки; используйте отдельно полученную программу проверки.

Устаревшая программа проверки, ограничивающая список элементов раскрытия фиксированным набором, может отклонить
новые ZIP-архивы с этими программами запуска. Используйте обновленную программу проверки из
независимого надежного источника. Не удаляйте файлы из подписанного ZIP-архива, чтобы
устаревшая программа проверки приняла его.
