Trusted Live CPU Ubuntu 및 WARP · 5년 11월 2026일#

유지된 통합 실행은 RunPod CPU 호스트 내부의 QEMU에서 CPU 전용 Ubuntu 24.04.5 게스트(4 vCPU, 8 GiB)를 사용했습니다. 수집기에는 14e642a5가, 검증에는 02072461가 사용되었습니다. 최종 수정 사항은 PR #114에 755f78f6로 병합되었으며, 해당 트리는 테스트된 PR 헤드와 일치했습니다. 이는 TEE가 아니었습니다.

  • 실제 WARP 커넥터는 정상으로 보고되었으며, 프록시된 HTTPS에서는 WARP 및 게이트웨이가 활성화된 것으로 보고되었습니다. 세 개의 프로브가 동일한 출구 주소를 감지했으나, 이는 고정 IP를 보장하는 것은 아닙니다.
  • WARP 연결을 끊자 프록시를 거친 요청이 실패했습니다. 게이트웨이 서비스에 대한 직접 HTTPS 접속은 거부되었습니다. 레코더 네임스페이스에서는 직접 IPv4/IPv6, 외부 DNS 및 Docker의 내장 UDP 리졸버가 차단되었습니다.
  • 범위가 지정된 읽기 전용 제공자 토큰은 health/connections를 읽을 수 있었으나 커넥터 등록 토큰은 읽을 수 없었습니다. 서명된 제공자 관측 결과에는 명시적으로 사용할 수 없는 샘플이 포함되어 있었습니다. 위트니스는 운영자의 호스트에서 실행되었으므로, 이는 독립적인 제3자 보관 방식이 아닌 기록 및 보존 방식을 보여줍니다.
  • 공식 데스크톱 버전이 인증되지 않은 환영 화면에 도달했습니다. 캡처 과정에서 보안이 적용된 키보드 입력이 거부되었습니다. 세 개의 H.264 디스플레이 세그먼트가 디코딩되었으며 해당 시계 오버레이가 검사되었습니다. 18개 이벤트로 구성된 프리플라이트 아카이브는 고정된 레코더 키 및 보존된 체크포인트와 대조하여 검증되었습니다.
  • 최종 캡처 테스트는 Windows 및 Linux CI 환경에서 실제 Chromium/FFmpeg을 사용하여 114개 사례를 통과했습니다. 5개의 앵커 테스트와 종속성 권고 사항 점검도 모두 통과했습니다.

초기 2 vCPU/4 GiB 구성이 동시 이미지 빌드 부하로 인해 타임아웃이 발생하여 가드 기능을 통해 중단되었으며, 이는 성공으로 간주되지 않습니다. 수동 테스트 계정 로그인, 네이티브 채팅 내보내기, 실제 하이브리드 비교 및 텔레그램 측 로그아웃은 여전히 진행 중입니다. 제공된 텔레톤 세션은 가져오지 않았습니다. 첨부 파일, 자동 OCR, 로컬 drand BLS 검증 및 Trusted Live TDX 인증은 검증 기준을 충족하지 못했습니다.

배포 1–2 · 제공자별 차이점 및 회귀 테스트

처음 두 번의 배포에서 시뮬레이션된 Phala Cloud와 5가지 차이점이 발견되었습니다. tools/check_phala.py는 이제 각 차이점을 재현하며, 수정 사항이 없으면 실패합니다:

Phala Cloud에서 수정 전 수정
compose_file.name가 필요합니다 HTTP 422, 아무것도 생성되지 않음 Docker Compose 구성에는 CVM 이름이 포함됩니다.
빈 값이 지정되지 않은 경우, Phala는 측정 대상 app-compose에 자체 사전 실행 스크립트를 추가합니다(v0.0.20: Docker 로그인, docker compose pull, 루트 비밀번호, user_config의 SSH 키). tdx_compose 오류: 게시된 Docker Compose 구성 외부의 코드 app-compose가 pre_launch_script를 ""로 설정하면, Phala는 이를 제외합니다
image가 없으면 Phala는 SSH 액세스가 활성화된 개발용 빌드인 dstack-dev-0.5.12를 선택합니다. server_state가 실패합니다. 이 이미지에서는 하드웨어 인증 기록만 통과했으며, 제공자 기록과 tdx_os에만 해당 내용이 표시됩니다. 배포 시 Phala의 현재 릴리스인 dstack-0.5.12의 프로덕션 빌드를 요청합니다.
dstack 게이트웨이가 꺼져 있는 상태에서는 CVM 세부 정보에 instance_id가 표시되지 않습니다. 배포가 30분 동안 대기한 후 실패합니다 인스턴스 ID는 CVM 상태에서 읽어옵니다.
재시작, 중지 및 시작은 CVM 작업이며, 애플리케이션 수정 사항이 아닙니다. provider_actions에는 재시작 내역이 표시되지 않았습니다. 읽기 작업도 수행됩니다.
배포3 · 인증, 접근 확인 및 재시작 증거
  • CVM은 SSH 액세스를 비활성화한 상태에서 dstack-0.5.12를 실행했습니다. 수집기는 생성 후 약 1.5분 후에 서명된 주소를 게시했습니다. 이후 배포는 tdx_binding, tdx_quote(Intel TCB UpToDate, 하드웨어 증명 기록 v4, FMSPC 20a06f000000, 디버그 모드 아님, 마이그레이션 불가, Intel에서 가져온 암호화 검증 데이터 지원), tdx_compose_hash, tdx_compose(바이트 단위) 및 tdx_identity(KMS 키)를 통과했습니다.

후속 수정 사항 · 서명된 주소 탐지 및 OS 측정
  • 주소 키가 없으면, verify는 주소 주제에 대한 가장 최근의 올바른 형식의 게시물을 따랐는데, 이는 게시된 Docker Compose 구성에 인쇄되어 있습니다. 한 건의 위조된 게시물이 이를 존재하지 않는 호스트로 보냈고, statement는 실패했습니다: 위조자는 수집자로 위장할 수는 없었지만, 제3자 검증을 최대 12시간 동안 위조된 미래 타임스탬프를 사용하여 차단할 수 있었습니다. 이제 수집기는 자신의 키로 서명된 주소 게시물도 올리며, verify는 수집기가 직접 작성한 게시물만 수용하며, 게시물은 ntfy.sh의 수신 시간 순으로 정렬됩니다. tools/check_cloud_wizard.py는 위조된 게시물을 재실행합니다. CVM은 이를 포함하는 커밋에서만 이 코드를 실행하므로, 이번 실행의 수집기는 아직 자신의 주소에 서명하지 않았고 verify가 이를 알렸습니다.
  • tdx_os는 dstack-mr 없이는 실행할 수 없었습니다. 해당 도구의 현재 버전에는 문서에 나온 measure --json 대신 measure-os가 있습니다. 검증기는 이제 공개된 이미지와 ACPI 테이블을 포함한 VM 구성으로부터 MRTD 및 RTMR0-2를 직접 계산합니다.
배포 4 · 전체 16개 검사, 보고서 봉인 및 재시작 검증
  • Deploy는 게시된 dstack-0.5.12를 한 번 다운로드하여 CVM이 보고한 OS 이미지 해시와 대조한 결과, tdx_os가 통과되었습니다: MRTD, RTMR0, RTMR1 및 RTMR2 값이 QEMU 8.2.2, 1 vCPU 및 2 GiB 조건에서 계산된 값과 일치했습니다. 동일한 계산에서 4 GiB, 2 vCPU, QEMU 9.2.1 또는 두 번째 네트워크 카드를 지정했을 때는 다른 RTMR0 값이 산출되었으며, 커널, 펌웨어 또는 명령줄이 변경된 경우 및 개발용 이미지의 경우에는 테스트에 실패했습니다.
  • verify는 퀵 터널의 커넥터를 포함하여 16가지 검사 항목을 모두 통과했으므로, 결과는 PASS였습니다. 이 시스템은 HTML 및 PDF 인증서를 생성했으며, 벨기에 정부의 타임스탬프 기관인 TSU 202301(벨기에 신뢰 목록에 등재된 상태)에서 발급한 적격 eIDAS 타임스탬프, FreeTSA 타임스탬프 및 검증자의 서명으로 디지털 봉인했습니다. check-report는 이 모든 항목과 PDF의 서명을 확인했습니다.
  • 재시작 후, verify --evidence는 두 번의 시작을 확인했으며, 각 시작 시 CVM 내에서 생성된 하드웨어 인증이 동반되었고, 각각 게시된 dstack-0.5.12에서 부팅되었습니다. 재시작과 새로운 부팅 모두 REVIEW 상태였습니다.

배포5 · 수집자가 서명한 디스커버리 및 위조 게시물 거부

libarchive로 열 수 있는 비밀번호로 보호된 내보내기 파일 · 2026년 10월 29일#

내보내기 암호화 코드(WinZip AES-256, 7-Zip 및 WinRAR이 읽을 수 있는 형식)로 생성된 아카이브를 Windows tar(bsdtar 3.6.2, libarchive)로 열었습니다. 올바른 암호를 입력했을 때 추출된 파일의 SHA-256 해시값은 원본과 일치했으며, 잘못된 암호를 입력했을 때는 "Incorrect passphrase"라는 오류 메시지가 표시되었습니다. 7-Zip과 WinRAR 자체는 실행되지 않았습니다.

200개의 채팅에서 생성된 1,000,000개의 합성 메시지(러시아어 어형, 우크라이나어, 영어, 중국어, 일본어, 링크 및 핸들 포함)로 구성된 결정론적 서명된 저널이 71초 만에 색인화되었으며, 1.50 GiB 크기의 저널 외에도 색인 파일로 58 MiB가 추가로 사용되었습니다. 최적 일치 검색은 9~190 ms(중앙값)가 소요되었으며, 이는 이전의 부분 문자열 검색에 소요되던 2.4~3.2초와 대비됩니다. 전체 결과, 하드웨어 및 제한 사항: 전체 텍스트 검색. tools/test_fulltext.py 또한 현재 검증기를 사용하여 전체 텍스트 검색 (tools/fixtures/evidence-before-fulltext.zip)를 현재 검증기로 검증하고, 현재 아카이브를 해당 아카이브 자체의 verify.py.

나머지 자격 요건#

보관된 실시간 저널은 실제 수집 내역, 수정 내역, 삭제 알림, 첨부 파일, 재확인 및 속도 제한 처리를 기록합니다. 단, 이 기록은 전송 내역의 완전한 추적이나 역할별 가시성, 반응 주체, 장기간의 FloodWait, 계정 차단 및 네트워크/프로세스 중단 복구와 관련된 통제된 매트릭스를 보장하지는 않습니다. QR 토큰 발급은 완료된 모바일 QR 확인과는 별개로 처리됩니다.

Docker/Compose 및 설치 검사는 CI에 기록되며, 실제 Phala 배포 및 외부 타임스탬프 검증은 위에서 설명되어 있습니다. 이는 지속적인 고부하, 완전한 라이브 플랫폼/역할 매트릭스, 독립적인 보안 검토, 장기 보관 검증 또는 포렌식 인증을 보장하지는 않습니다. 저장된 MTProto 상태 및 캐치업 기능이 구현되었으나, 원자적 무손실 라이브 리플레이는 아직 구현되지 않았습니다. 최신 백필(backfill) 기능은 메시지와 커서를 원자적으로 커밋하고 사용 가능한 최근 작업(Recent Actions)을 보존하지만, 그 합성 커버리지는 라이브 검증과는 별개입니다. 제어된 검증 매트릭스에 대해서는 라이브 승인(live acceptance)을 참조하십시오.

공개 감사 디렉토리에는 서명된 보고서와 집계된 측정값만 포함되어 있습니다. 상세한 운영 기록, 원본 캡처 자료 및 계정 자료는 비공개로 유지됩니다. docs/assets/에 있는 애플리케이션 스크린샷은 가상의 데모 데이터를 사용합니다.
