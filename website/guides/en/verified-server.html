One command, six steps

You run python -m tgwitness.cloud deploy, or the Server 24/7 wizard in the panel runs it for you. Your computer talks to two APIs, Cloudflare's and the provider's, and nothing else. The server builds itself from a single commit and never accepts a connection.

Who can reach a cloud server

A cloud server is a QEMU process on the provider's physical host. Its memory, disk, network and clock all belong to that host. There are two ways in: the control plane you and your API token use, and the hosts themselves.

✓ What stays fixed even then

  • Checkpoints already published to independent witnesses cannot be rewritten.
  • RFC 3161 and OpenTimestamps fix when each checkpoint existed; the host clock cannot move them.
  • Telegram still holds the messages. Another capture of the same chat contradicts a forgery.

! The realistic risk

  • Manipulation at the moment of collection by someone with host access, not silent rewriting afterwards.
  • Host access to every server on that host is a capability the provider guards closely; spending it covertly on one evidence server is a state-level decision.
  • Answer it with two providers in different jurisdictions, or with the next assurance level.

How verify reads the provider log

The verifier asks the provider with a read-only key what happened to the server. Every action is sorted: creation and the start that belongs to it pass, any path into the server fails, power actions and anything nobody foresaw go to review. An unknown action never passes silently.

What Cloudflare records

Cloudflare is a second witness that the provider does not control. The tunnel record shows where the connector runs. With Gateway DNS, Cloudflare also logs every name the server looks up, and the provider firewall keeps DNS from going anywhere else.

What the Hetzner Cloud log records

Actions on the server and on its firewall, with time and status. Read with a Read token of the same project.

What the log does not show

  • Who performed an action: Hetzner's log does not name the user.
  • The contents of earlier firewall rules: the log shows that they changed, not what they were.
  • Anything done on the physical host, below the API.

Cloudflare on Hetzner Cloud

Cloudflare is a second witness that Hetzner Cloud does not control.

  • TunnelThe panel is reached only through a Cloudflare tunnel. Its ingress forwards the panel hostname to the panel alone.
  • Connector checkCloudflare lists every connector with its address. verify checks that the connector runs from the server's address and reports any other.
  • Quick tunnelWorks without a domain, but no Cloudflare account keeps a record of it, so the report is at best INCOMPLETE.
  • Gateway DNSAvailable. The Hetzner firewall lets DNS leave only to Cloudflare Gateway over TLS, so Cloudflare logs every name the server looks up. Free Zero Trust plan; the log lasts 24 hours there, and evidence mode copies it into the journal.
  • drandEvidence mode can add rounds from drand.cloudflare.com: records after a round are newer than it.

What the Amazon EC2 log records

CloudTrail management events with the user who made each call. Read with credentials allowed only ec2:DescribeInstances, ec2:DescribeSecurityGroups and cloudtrail:LookupEvents.

What the log does not show

  • AWS staff and the underlying host.
  • Anything older than 90 days, unless you keep a CloudTrail trail.
  • Not a gap in the log but a risk: ec2:Describe* would return the user data with both tokens, so the verifier gets only the three actions above.

What the Vultr log records

Account activity log with method, path, username and address, for 30 days, longer with an audit-log subscription. Read with a user that has read access and the activity_logs permission.

What the log does not show

  • Opening the web console: it is not identified as such in the activity log.
  • Anything older than 30 days, unless an audit-log subscription keeps it.
  • Not a gap in the log but a risk: any key that can read the instance receives its console address and its user data, so assume the verifier's key can read both tokens.
