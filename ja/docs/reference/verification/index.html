Phala Cloud へのライブデプロイ · 2026年11月4日#

--provider phala --quick-tunnelは、実際のPhala Cloud（tdx.small、リージョン US-WEST-1）に対して実行され、空のワークスペースのPhala Cloud APIキー、実際のntfy.sh、GitHub、およびIntel PCSが使用されました。 CVMにはコミットdf7d860c（v0.8.1）がインストールされました。デプロイ、検証、および破棄は、以下の修正を加えてコマンド ラインから実行されました。7台のCVMの合計費用は約1.9米セントでした。

最初の2回のデプロイでは、シミュレートされたPhala Cloudとの間に5つの相違点が検出されました。 tools/check_phala.pyは現在、それぞれを再現しており、修正を施さないと失敗します：

Phala Cloud にて 修正前 修正
compose_file.name が必要です HTTP 422、何も作成されませんでした Docker Compose の構成には、CVM 名が含まれています
空の値が指定されない限り、Phalaは測定対象のapp-composeに独自のpre-launchスクリプトを追加します（v0.0.20：Dockerログイン、docker compose pull、rootパスワード、user_configからのSSHキー） tdx_compose が失敗します：公開された Docker Compose 構成の範囲外のコードが含まれています app-compose は pre_launch_script を "" に設定していますが、Phala はこの設定を省略しています
imageが指定されていない場合、PhalaはSSHアクセスが有効な開発ビルドであるdstack-dev-0.5.12を選択します server_state は失敗しました。このイメージでは、ハードウェア認証レコードのみが合格しました。プロバイダーレコードと tdx_os のみがそれを示しています。 デプロイでは、Phalaの現在のリリースであるdstack-0.5.12のプロダクションビルドが求められます。
dstackゲートウェイがオフの状態では、CVMの詳細にinstance_idが表示されることはありません。 デプロイは30分待機した後、失敗します インスタンスIDはCVMの状態から読み取られます
再起動、停止、起動はCVMの操作であり、アプリケーションの更新ではありません。 provider_actionsには再起動の記録はありませんでした これらの操作には読み取り操作も含まれます

3回目のデプロイ：

  • CVMは、SSHアクセスを無効にした状態でdstack-0.5.12を実行しました。コレクターは、作成から約 1.5分後に署名付きアドレスを投稿しました。その後、デプロイはtdx_binding、tdx_quote（Intel TCB UpToDate、ハードウェアアテステーションレコードv4、FMSPC 20a06f000000、デバッグモードではない、移行不可、Intelから取得した暗号検証データを サポート）、tdx_compose_hash、tdx_compose（バイト単位）、およびtdx_identity（KMSキー）を順次通過しました。
  • trycloudflare.com のアドレスにあるパネルは、トークンがない場合や誤ったトークンを指定した場合は 401 を返し、 パネル用トークンを指定した場合は 200 を返しました。
  • verify について、--source は GitHub のコミットアーカイブに設定され、フィンガープリントは 個別に合格しました：サーバー、server_state、ファイアウォール（ゲートウェイなし、パブリックエンドポイントなし）、プロバイダーログ、 明細書、フィンガープリント、ソースハッシュ、ブート、および 5 つの tdx_* チェックが合格しました。 Cloudflare および tdx_os は利用できなかったため、結果は「INCOMPLETE」となりました。
  • PhalaのAPIで二度再起動しました。毎回、CVMは二分以内に復旧し、コレクターの鍵は同じまま、新しい署名付きアドレスが発行され、以前のアドレスは530を返しました。verifyは新たな起動と両方の再起動をREVIEWとして報告しました。--evidenceではジャーナルの署名と三回の起動を確認し、それぞれに同じCVM内で生成されたIntel TDXのハードウェア認証記録が付いていました。
  • destroy コマンドは、その CVM のみを削除しました。その後、ワークスペースは空になり、パネルのアドレスは 応答しなくなりました。
  • パネルのウィザードで料金を確認すると、tdx.smallは時間あたり0.058ドルと表示されました。無効なキーを入力すると、「APIキーが受け入れられませんでした」という簡潔なメッセージが表示されました。

さらに2つの発見があり、その後修正されました：

  • アドレスキーがない場合、verifyは、アドレスに関するトピックで最も新しい、形式が正しい投稿に従いました。 この投稿は、公開されたDocker Compose構成に印刷されています。ある偽造された投稿により、存在しないホストへ送信され、 statementは失敗しました。偽造者はコレクターになりすますことはできませんでしたが、 第三者による検証を、偽造された将来の日時スタンプを用いて最大12時間までブロックすることができました。現在、コレクターは 自身の鍵で署名されたアドレスも投稿しており、verifyは、 コレクターが投稿したそのような投稿のみを受け入れ、投稿はntfy.shの受信時刻順に並べ替えられます。 tools/check_cloud_wizard.pyは、偽造された投稿を再実行します。CVMは これを、それを含むコミットからのみ実行するため、今回の実行におけるコレクターはまだ自身のアドレスに署名しておらず、 verifyはその旨を報告しました。
  • tdx_osはdstack-mrなしでは実行できませんでした。このツールの現行バージョンには、文書に記載されたmeasure --jsonではなくmeasure-osが含まれています。検証ツールは現在、公開されたイメージとACPIテーブルを含むVMの構成から、MRTDとRTMR0-2を直接計算します。

4回目のデプロイでは、以下の内容を含みます：

  • デプロイでは、公開された dstack-0.5.12 を一度ダウンロードし、CVM が 報告した OS イメージのハッシュと照合しました。その結果、tdx_os は合格しました：MRTD、RTMR0、RTMR1、および RTMR2 は、QEMU 8.2.2、1 vCPU、2 GiBの環境で計算された値と一致しました。同じ計算でも、4 GiB、2 vCPU、 QEMU 9.2.1、または2枚目のネットワークカードが指定された場合は異なるRTMR0値となり、カーネル、ファームウェア、またはコマンドラインが変更された場合や 開発用イメージでは失敗しました。
  • verifyは、クイックトンネルのコネクタを含め、16項目のチェックをすべて通過したため、結果は 「PASS」となりました。 HTMLおよびPDF形式の証明書が作成され、署名とタイムスタンプによってデジタル封印されました。タイムスタンプには、 ベルギー政府のタイムスタンプ機関TSU 202301（ベルギーの信頼リストに 登録済み）によるeIDAS認定タイムスタンプ、FreeTSAタイムスタンプ、および検証者の署名が使用されました。check-reportはこれらすべて およびPDFの署名を確認しました。
  • 再起動後、verify --evidence は 2 回の起動を確認しました。それぞれ、CVM 内で生成されたハードウェア認証を伴い、それぞれ 公開された dstack-0.5.12 から起動されました。再起動と新しい起動は、いずれも REVIEW でした。
  • destroy では、ワークスペースは空の状態になりました。

5回目のデプロイでは、コミット 53a0f7e9 からのコレクターを実行しました。これには上記のすべてが含まれています：

  • コレクターは、オペレーターの HMAC 投稿の隣に、自身の鍵で署名されたアドレスを投稿しました。 その後、このトピックに 2 件の偽造投稿が追加されました。1 件は HMAC が 0 に設定されており、もう 1 件は別の Ed25519 鍵で署名されたもので、いずれも 2096 年の時刻を主張していました。 verifyは、 コレクターの鍵で署名されたアドレスを取得し、16のチェックすべてに合格しました。このシールには、再びベルギーの認定タイムスタンプ、 FreeTSAのタイムスタンプ、および検証者の署名が記載されており、check-reportがこれらを確認しました。
  • 再起動後、コレクターは署名付きの新しいアドレスを投稿しました：verifyは即座にそれを検出しました。 オペレーターのは現在のアドレスを特定し、はHMAC投稿から27秒後に検出しましたが、両者とも 偽造された投稿を無視しました。verify --evidenceは、dstack-0.5.12から起動した2つのインスタンスを確認しました。
  • デプロイ処理は、PhalaがCVMに請求するディスク料金込みの金額を表示しました。時間あたり0.06078ドルです。

パネルウィザードは Phala Cloud に対して 2 回実行されました。1 回はジョブ API を通じて、もう 1 回は 実際の Chromium を使用したブラウザを通じてです。価格の確認、Advanced でのコミットによる作成、6 つの 認証チェックすべてに合格し、サーバーリストには請求価格（月額 44.37 米ドル）が表示され、 Find 現在のアドレス、測定済みのDocker Compose構成のダウンロード、および削除が行われました。ブラウザではページエラーは発生しませんでした。 その後、ワークスペースは毎回空の状態になりました。

対象外：Phala上のCloudflareドメイン、CVM上のTelegramアカウント、およびdstack-0.6.1 イメージ。ウィザードでの作成前の価格はPhalaのコンピューティング料金のみとなります。これは、APIがディスク 料金を既存のCVMに対してのみ指定しているためです。サーバー一覧には、作成後の請求価格が表示されます。

残りの資格要件#

保存されたライブジャーナルには、実際の収集状況、編集、削除通知、添付ファイル、 再確認、およびレート制限の処理が記録されます。 ただし、配信の網羅性や、 役割ごとの可視性、反応主体、長期にわたるFloodWait、アカウントの停止、および ネットワーク／プロセスの中断からの復旧に関する管理マトリックスについては、記録の対象外となります。QRトークンの発行は、完了した モバイルQR確認とは区別されます。

Dockerによるビルド／実行、Linux／macOSへのインストール、持続的な高負荷への対応、独立したセキュリティ レビュー、真に独立したTSA対応、証明書の失効／アーカイブの検証、および フォレンジック認証については、本ドキュメントに記載された認定範囲外となります。保存されたMTProtoの状態 およびキャッチアップ機能は実装されていますが、アトミックかつ耐久性のあるリプレイ機能については、まだ確立されていません。 管理ログの 収集、追加のリアクターリスト、および優先度の高いショートポーリングは、引き続き別個の機能として扱われます。 管理された認定マトリックスについては、ライブ受入テストをご参照ください。

ローカルに保存された詳細な記録やスクリーンショットは、test-results/ ディレクトリに格納されています（Gitでは無視されています）。 docs/assets/ ディレクトリ内の公開用スクリーンショットには、架空のデモデータのみが含まれています。
