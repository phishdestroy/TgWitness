## A8 — P2: source packages omit all website translation dictionaries

**Files:** [source selection](../../tools/build_source.py#L17),
[website translation loading](../../tools/site_i18n.py#L193), and
[site build](../../tools/build_site.py#L239).

`website` allows HTML, CSS, JS and Python files, but not JSON. JSON selection also
requires the `tgwitness` directory and its explicit package-resource allowlist.
Consequently, none of the twelve `website/i18n/*.json` dictionaries enters a source
ZIP. Staging them without correcting the allowlist would cause the publication
checker to reject them as non-public paths.

The site loader treats a missing dictionary as an empty one. Building from public
source therefore succeeds and creates language URLs whose content falls back to
English. This differs from a build in the complete working directory. A successful
source check or site-build exit code alone is insufficient to catch the omission.

**Reproduction:** copy precisely the public allowlist, build the source ZIP and
site, and inspect the Spanish dictionary/page. Then add only the twelve known
translation files to that diagnostic copy and rebuild. The initial artifact has
zero Spanish strings; the complete-input build has **337 Spanish strings** and
different localized HTML. Both builds exit successfully. The original ZIP remains
unchanged for inspection.

**Fix and acceptance criteria:**

1. Add the twelve known website dictionary paths to an explicit source-resource
   allowlist. Do not allow arbitrary JSON throughout the repository.
2. Build the site from an extracted source ZIP in a regression test. Assert that
   the expected dictionaries and non-English search entries survive packaging.
   Keep intentional development fallback separate from release completeness checks.
3. Validate required resource closure: every declared site input must either be
   included in public source or be an explicitly documented generated dependency.
4. Add `tools/site_i18n.py` to the Pages workflow's push and pull-request path
   filters. The helper is currently absent from both lists, so an ordinary change
   limited to that file does not match either filter. This conclusion follows
   from the current workflow and GitHub's documented
   [path-filter rules](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore);
   no remote workflow was triggered as part of this review.

## A9 — P2: derived profile counts treat repeat observations as new messages

**Files:** [reply accumulation](../../tgwitness/dossier.py#L294),
[cross-chat sender counts](../../tgwitness/store.py#L538), and
[UI labels](../../tgwitness/static/app.js#L2158).

The main activity counter deduplicates message IDs. Reply relationships instead
append a record for every matching observation and use the number of records as
the number of replies. Cross-chat activity uses SQL `count(*)` over message events.
Snapshots and edited versions therefore inflate these counts even when no new
message was sent. The UI labels them as replies and saved messages.

**Reproduction:** create one message from Alice and one reply from Bob. Bob's reply
count starts at one. Save a snapshot and an edited version of that same reply; the
reply count becomes **three** while Bob's distinct-message activity remains **one**.
In another chat, one message followed by its snapshot is displayed as **two saved
messages**. The test uses only synthetic identities and text.

**Impact:** a derived profile exaggerates interaction frequency and cross-chat
activity. Signed source records remain intact. Integrity verification checks
signatures and referenced records; it does not independently recompute these
derived metrics, so a valid signature does not correct the counting error.
The recheck also signed this incorrect profile and verified it against a signed
evidence ZIP: both integrity and cited-record verification passed.

**Fix and acceptance criteria:** count stable message identities within each chat,
and count a reply relationship once per replying message. Preserve all associated
observation sequences as references without letting the reference count determine
the metric. Add regressions covering a new message, repeated snapshots, recovered
observations, edits and a genuinely different second reply. Do not rewrite earlier
journal records to repair a derived view.

## A10 — P3: reference-page GitHub links lead back to the same page

**Files:** [link rewriting](../../tools/build_site.py#L291) and
[reference footer](../../tools/build_site.py#L460).

The footer initially points to the document's GitHub source URL. The general
rewriter then recognizes that URL as a rendered reference document and rewrites
it to the same local page, leaving the label "Edit this page on GitHub" intact.
Every one of the **221 reference pages** (17 documents in 13 language paths)
contains this source link with `href="./"` in the generated output.

**Impact:** the advertised contribution/source navigation does not work. The link
resolves successfully, so ordinary missing-link checks do not detect the incorrect
destination. This is a lower-priority navigation defect, not a confidentiality or
evidence-integrity issue.

**Fix:** exempt explicit source/edit links from document-link rewriting, or generate
a GitHub edit URL that the ordinary reference-link converter does not rewrite.
Assert the expected destination for this control in a site regression test; merely
asserting that its target returns a page is insufficient.

## A11 — P3: translated README disclosure blocks close before their content

**Examples:** [Spanish README](../es/README.md#L46) and
[Ukrainian README](../uk/README.md#L46).

During the recheck, translated Markdown documents were being updated independently.
The final input snapshot at **18:13:24 UTC** captures this defect in eight README
files: Arabic, Spanish, Persian, Hindi, Portuguese, Turkish, Ukrainian and Urdu.
Each contains two instances of this structure:

```html
<details>
<summary>Translated heading</summary></details>

Content intended to be collapsible.

</details>
```

The first closing tag leaves the disclosure with only its summary. Its intended
content is outside the element, and the later closing tag is unmatched. The two
controls therefore cannot collapse the feature list or screenshot section.
Ordinary destination/link checks do not catch this HTML structure defect.

**Fix:** preserve HTML structure while translating text. Keep each closing
`</details>` after the complete associated content, and check the rendered DOM for
non-summary children inside each disclosure. Review the other translated README
files as their updates arrive. This finding is based on the frozen local files;
GitHub's hosted renderer was not contacted.
