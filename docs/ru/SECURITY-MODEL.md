# Безопасность и обработка данных

На этой странице описаны вопросы доступа, хранения и защиты сети в локальной рабочей области или на сервере. Что касается сбора данных на GitHub Runner или в конфиденциальной виртуальной машине Intel TDX, ознакомьтесь с [режимами верификации](EVIDENCE.md#verification-scope), которые предусматривают дополнительные проверки среды сбора. Подключения к аккаунтам, уведомления, временные метки, внешние копии и свидетели имеют собственные настройки маршрутизации.

| Область | Вкратце |
| --- | --- |
| Доступ | Ключ администратора плюс доступ с ограниченной областью действия к аккаунтам/чатам, семь прав доступа и сеансы, которые можно отозвать; по умолчанию — localhost |
| Секретные данные в состоянии покоя | Сеанс, пара API, ключ подписи и настройки прокси шифруются с помощью Fernet |
| Сообщения и медиафайлы | Файлы в рабочей области защищены с помощью шифрования диска или тома, а также файловых прав доступа хоста |
| Целостность | Цепочка хешей SHA-256 и подпись Ed25519 на каждой записи |
| Внешнее время | Квитанции по стандарту RFC 3161 и OpenTimestamps, записи свидетелей с датой от Telegram и подтверждение GitHub; в качестве вспомогательных проверок используются сохраненные контрольные точки, записи свидетелей и измерения Intel TDX. Верификатор сообщает, каким условиям доказательности они соответствуют |

Информацию о сообщениях об уязвимостях см. в [политике безопасности](../../.github/SECURITY.md).

<a id="access-model"></a>
## Модель доступа

Токен главной панели предоставляет полный контроль. Другие пользователи могут получить собственный [ограниченный доступ](ACCESS.md): выбранные рабочие области и чаты, разрешения, срок действия, ограничения по IP-адресам, лимиты входа в систему и отзывные сеансы. Пользователь с доступом, ограниченным чатом, не может выполнять операции на уровне всего рабочего пространства, даже если соответствующий пункт разрешений отмечен. Каждая рабочая область имеет собственный журнал, хранилище и ключ подписи в рамках одного процесса; разделение между пользователями на хосте осуществляется посредством аккаунтов операционной системы.

По умолчанию панель прослушивает порт localhost. При входе через браузер токен доступа обменивается на учетные данные сеанса; браузер отправляет их в виде токена «bearer». Они хранятся в sessionStorage, а не в файле cookie аутентификации. Блокировка или выход из системы очищают сеанс браузера. Закрытие браузера или завершение сеанса не останавливают сбор данных.

Выданные токены и учетные данные сеанса хранятся в виде хешей в зашифрованном хранилище. Отзыв токена приводит к завершению связанных сеансов; изменения прав доступа влияют на последующие запросы. Загруженные файлы не подлежат отзыву. Администратор также может ограничивать собственные сеансы браузера, однако скрипты, напрямую использующие токен главной панели, сохраняют полный доступ и обходят эти ограничения сеанса браузера.

Число неудачных попыток аутентификации ограничивается по адресу клиента. При ограничениях по IP-адресу используется адрес, видимый приложению; прежде чем полагаться на это, проверьте поведение обратного прокси-сервера. Учетные данные свидетеля остаются отдельными учетными данными для проверки работоспособности и контроля состояния, доступными только для чтения.

<a id="demo-access"></a>
### Доступ к демо-версии

`/api/demo-access` — это намеренно неаутентифицированный начальный механизм для явно запущенной, изолированной синтетической демонстрационной версии. Он предоставляет отдельные права, действующие в течение срока жизни процесса, но никогда не предоставляет реальный токен панели или переопределение TGWITNESS_TOKEN. Для выдачи и использования требуются узел обратной связи и хост, отсутствие перенаправленных заголовков и отсутствие междоменных запросов. Дополнительные рабочие области или авторизованный сеанс отключают этот путь. Рабочие области в режиме реального времени никогда не выдают данную возможность. Демо-версия не может связывать аккаунты или изменять настройки сбора данных.

<a id="panel-content-and-exports"></a>
## Содержимое панели и экспорт данных

Панель не использует внешних шрифтов, аналитики, ресурсов CDN или встроенных удалённых медиафайлов. Текст из Telegram вставляется в виде текста, а не HTML. Загруженные вложения предоставляются в виде двоичных вложений. Экспорт в формате JSONL сохраняет исходные строки; HTML кодирует их; ячейки CSV, которые могут превратиться в формулы, снабжаются префиксом в виде апострофа.

Экспортные файлы исключают секретные данные аутентификации и подписи, но намеренно содержат собранные исходные метаданные, идентификаторы и, возможно, личный или конфиденциальный контент. В необработанных исходных метаданных могут встречаться хеши доступа Telegram и ссылки на файлы.

<a id="secrets-at-rest"></a>
## Секретные данные в состоянии покоя

Учетные данные API Telegram, ключ сеанса и ключ подписи шифруются с помощью Fernet. Для локальных сообщений и медиафайлов шифрование обеспечивается диском или томом хоста; рабочая область хранит обычные файлы. При экспорте может использоваться ZIP-архив с шифрованием AES-256, защищённый паролем, а для внешних копий применяется шифрование AES-256-GCM.

По умолчанию ключ хранилища находится в каталоге защищённых данных. Для его отдельного хранения используйте приведённый ниже файл внешнего мастер-ключа. В системе Unix для новых файлов с закрытыми ключами используется режим доступа 0600, а для новых каталогов данных — 0700; в Windows необходимо настроить список прав доступа (ACL) к каталогу для аккаунта службы и авторизованных администраторов. Существующие права доступа к каталогам сохраняются.

<a id="external-master-key"></a>
### Внешний мастер-ключ

Для нового каталога данных параметр TGWITNESS_VAULT_KEY_FILE может предоставлять внешний случайный мастер-ключ. С помощью алгоритма HKDF-SHA256 и отдельного случайного солевого значения для каждой рабочей области генерируется уникальный ключ Fernet. Файл vault.external.json необходимо сохранить для восстановления. Отсутствие или неверность мастер-ключей приводит к сбою с закрытием. Существующие локальные хранилища не переносятся автоматически. На панели отображается выбранный режим хранения ключей. Шифрование диска защищает локальные сообщения и медиафайлы в любом из режимов; подробности настройки см. в разделе [Подключение и защита данных](CONNECTION-SECURITY.md).

<a id="proxies-and-network-routes"></a>
## Прокси-серверы и сетевые маршруты

Настройки прокси шифруются в хранилище. Пароли и секретные данные MTProxy не возвращаются API и не записываются в отчёты о доказательствах. Каждая рабочая область выбирает свой маршрут Telegram и [режим IP](CONNECTION-SECURITY.md#ip-modes).

**Настройка Скрыть адрес** блокирует прямой резервный доступ к Telegram и требует использования прокси для внешних HTTP-запросов. Явно выбранный режим резервного доступа разрешает прямой доступ к Telegram после задержки; режим «туннель/VPN» разрешает прямые маршруты. Выбор режима «туннель» не приводит к установке или верификации VPN. Эти настройки не контролируют весь трафик устройства, браузеры, менеджеры пакетов или разрешение DNS на локальном прокси-хосте.

MTProxy передаёт только трафик Telegram. Внешние запросы могут использовать отдельный SOCKS5/HTTP-прокси, маршрут SOCKS5/HTTP рабочей области или разрешённый прямой маршрут; их также можно отключить. Независимый свидетель имеет собственные настройки транспорта. Обычная аутентификация SOCKS5/HTTP CONNECT не шифруется самими этими протоколами прокси. Поддельные секретные ключи TLS для MTProxy по-прежнему не поддерживаются.

<a id="sign-in-and-session-imports"></a>
## Вход в систему и импорт сеансов

Преобразованные файлы .tgwitness-сеанс содержат секрет авторизации в виде открытого текста до тех пор, пока они не будут загружены и сохранены в хранилище. Автономный интерфейс командной строки (CLI) поддерживает проверенные схемы Telethon. Функция импорта через панель управления дополнительно поддерживает входные данные в форматах Pyrogram SQLite, современного ZIP-архива TData для одного аккаунта и документированного JSON. Этот процесс проходит аутентификацию, ограничен четырьмя файлами / 8 МиБ и обрабатывает загрузки в памяти без извлечения архивов или сохранения исходных файлов. Нормализованные учетные данные возвращаются только запрашивающему аутентифицированному браузеру; они сохраняются в зашифрованном хранилище после успешной авторизации в Telegram. Обеспечьте защиту исходных и преобразованных файлов и предотвратите клонирование авторизационных данных параллельными клиентами.

При обработке TData верификатор проверяет контрольные суммы контейнеров, хеши локального дешифрования и длины структур. Предоставленный локальный пароль для Desktop используется временно и не сохраняется. Ограниченный парсер поддерживает форматы Desktop, которые он проверяет на валидность, и отклоняет остальные. Изображения QR-кодов генерируются локально, содержат краткосрочные токены входа в Telegram и никогда не отправляются во внешний сервис рендеринга. Блокировка устройства, переключение рабочей области, новый вход в систему и изменение маршрута отменяют ожидающие попытки сканирования QR-кода. Перезагрузка или закрытие вкладки может привести к тому, что попытка останется в ожидании до истечения срока действия. Успешный вход с помощью QR-кода по-прежнему требует привязки аккаунта. Размер обычных тел запросов API по-прежнему ограничен 16 КиБ; маршрут импорта с аутентификацией принимает до 12 МиБ закодированного JSON, при этом отдельно применяется ограничение на размер декодированного файла.

Коды входа и облачные пароли двухэтапной аутентификации Telegram не сохраняются. Состояние номера телефона и хеша кода хранится в памяти во время авторизации. Сеансы Telegram предоставляют доступ к аккаунту; никогда не загружайте каталог данных, сеанс, токен, ключ хранилища или частный ключ подписи на GitHub.

<a id="logs-and-transport"></a>
## Журналы и транспорт

Стандартный ответ API на проверку заменяется таким образом, чтобы он не повторял значения учетных данных. Регистрация доступа приложений отключена. Не настраивайте обратный прокси на регистрацию заголовков авторизации или тел запросов. Панель прослушивает порт на localhost; удалённый доступ осуществляется через предоставленный SSH-туннель, Cloudflare Tunnel или Caddy HTTPS, поэтому токены и секретные данные для входа передаются по протоколам SSH или TLS.

<a id="integrity-and-external-time"></a>
## Целостность и внешнее время

Проверки целостности сравнивают подписи записей, цепочку хешей, вложения и манифест экспорта с ключом сборщика. Допустимая подпись свидетельствует о том, что байты не изменились с момента их подписания. Каждая рабочая область создаёт свой ключ подписи при первом запуске и отображает его отпечаток в панели управления и в каждом экспорте. Оператор передаёт отпечаток получателю по отдельному каналу, а параметр ``--fingerprint`` фиксирует ключ.

Изменение, добавление или удаление записи нарушает хеш-цепочку или подпись, и верификатор сообщает об этом. Внешние временные метки и свидетель также фиксируют журнал за пределами рабочей области. Триггеры SQLite в таблице журнала лишь предотвращают случайное перезаписывание или удаление записи приложением. Файл ``TGWITNESS_VAULT_KEY_FILE`` хранит ключ хранилища отдельно от копии каталога данных.

Квитанции по стандарту RFC 3161 и OpenTimestamps, а также сообщения-свидетели, даты которых верификатор считывает из Telegram, привязывают префикс журнала, который они охватывают, к времени, установленному третьей стороной. Раунд drand, записанный в журнал, показывает, что записи, следующие за ним, были созданы не раньше, чем был опубликован этот раунд. Проверенное подтверждение GitHub также содержит подтверждённое время своей подписи, что привязывает весь архив к внешнему времени. Контрольная точка подписывается ключом сборщика и привязывает записи, предшествующие ей, с момента получения её получателем через другой канал. Свидетель подтверждает, что второй ключ сохранил вершину журнала; запись о контроле ключей хранителя показывает, кто владеет этим ключом. Обе эти проверки являются вспомогательными; минимальным требованием является время, установленное третьей стороной. [Захват GitHub Actions](SEALED-ACTIONS.md) или [развертывание Intel TDX](PHALA.md#confidential-vm-on-phala-cloud-intel-tdx) добавляют информацию о происхождении рабочего процесса или аппаратные измерения среды сбора данных.

В каждом ответе на запрос о проверке перечисляются условия доказательств с указанием способа проверки каждого из них, сгруппированные по их роли в минимальном наборе:

| Роль | Условие |
| --- | --- |
| Обязательно | Целостность; ключ подписанта закреплён с помощью команды `--fingerprint`; внешнее время, охватывающее последнюю запись (квитанция RFC 3161 проверена с помощью команды `--tsa-ca`, квитанция OpenTimestamps подтверждена с помощью команды `--check-bitcoin`, сообщение свидетеля прочитано с t.me с помощью команды `--channel`, печать Bitcoin свидетеля или проверенное подтверждение GitHub) |
| Дополнительные, не входящие в минимальный набор | Свидетель со своим собственным ключом; сохраненная контрольная точка; заверенный цикл сбора |

**Минимальные** требования **к доказательству** включают выполнение всех трёх обязательных условий, охватывающих последнюю экспортированную запись; проверенный заверенный цикл сбора данных добавляет профиль `attested`. В последней строке указывается результат, а в ответе перечисляются параметры, которые позволили бы выполнить недостающие условия. Без параметра `--fingerprint` последняя строка начинается со слова `EVIDENCE: minimum not met · missing: confirmed signer key`. Если проверенные временные метки охватывают только более ранние записи, в ответе указывается запись, до которой соблюдаются минимальные требования. Параметры `--require evidence` или `--require attested` завершают работу с кодом 2, если профиль не достигнут для всего экспорта, а запрос на проверку в командной строке, который не может быть выполнен, отмечается как невыполненный с тем же кодом. Каждый отчёт содержит те же условия с указанием их состояния в данной копии и команды, которая их проверяет. Уровни достоверности и параметр `--strict` по-прежнему доступны; [формат доказательств](EVIDENCE.md#verification-scope) перечисляет проверки для каждого режима сбора данных.

<a id="if-you-suspect-a-problem"></a>
## Если вы подозреваете наличие проблемы

Сохраните исходный каталог данных и используйте отдельную копию для анализа. Сообщите о затронутой версии, операции и шагах, позволяющих воспроизвести проблему, через [политику безопасности](../../.github/SECURITY.md), не раскрывая данные аккаунта и учетные данные.
