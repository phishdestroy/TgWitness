# Экспорт распределённых чатов

При повторной проверке отсутствующих номеров пропуски учитываются как интервалы, без выделения каждого отсутствующего номера в памяти. По умолчанию выборка остаётся ограниченной; явная полная повторная проверка считывает последовательные партии и может быть отменена. Непроверенные номера остаются видимыми в результате и не рассматриваются как доказательство удаления.

Откройте чат и выберите **Экспорт чата**. Выберите рабочие области аккаунтов, которые уже имеют доступ к источнику; участвовать может аккаунт, находящийся только в режиме наблюдения. Каждый аккаунт сохраняет своё настроенное соединение. Данная функция не изменяет WARP и не выбирает IP-адрес выхода.

На **странице Главная → Экспорт чата по ссылке** введите публичное имя пользователя или ссылку для приглашения, чтобы просмотреть доступные данные чата и подходящие аккаунты; для каждого исключённого аккаунта указывается причина. Проверка временно резервирует неактивного читателя; она не приводит к вступлению в чат или запуску экспорта. Оценки времени охватывают один аккаунт, выбранные аккаунты, а также — в случае каналов и супергрупп — десять аккаунтов; они учитывают измеренные или стандартные показатели просмотра и не включают вложения и ожидания в Telegram. Запустите экспорт явно.

<a id="history-acquisition"></a>
## Получение истории

В диалоговом окне экспорта поле **Загрузить выбранные вложения с учетом ограничений на сбор данных данного аккаунта** по умолчанию отмечено, если рабочая область загружает медиафайлы, и не отмечено — в противном случае; при необходимости измените это значение для отдельного экспорта. Если это поле не отмечено, при распределенном сборе данных также пропускается загрузка фотографии профиля из чата. Идентификатор доступной фотографии и другие метаданные профиля остаются в экспорте. Для извлечения фотографий требуется как включение данного параметра, так и соответствующие настройки медиафайлов/аватаров в рабочей области. Повторная проверка идентификаторов сообщений (Message-ID) использует общие ограничения по скорости доступа к аккаунтам, применимые к чтению истории; любое ожидание, запрашиваемое сервером, по-прежнему распространяется на всех вызывающих пользователей.

**Обычный сеанс** сохраняет существующий путь получения данных. **Сеанс Telegram Takeout** представляет собой опциональный путь для публичных каналов и супергрупп. Он открывает сеанс экспорта для каждого участвующего аккаунта, использует последний диапазон разбиения Telegram для этой области, доступной только публично, и считывает историю без дополнительной задержки итератора Telethon. Собственная функция Telegram FloodWait по-прежнему применяется в полном объёме. Takeout использует ту же ограниченную полосу запросов к истории, что и обычное чтение; смена транспортного протокола не создаёт дополнительных слотов и не обходит общие ограничения на интервалы между запросами.

Начальные границы источника и даты измеряются с помощью обычных запросов и фиксируются в подписанном плане. Takeout считывает эти запланированные диапазоны. Для получения профилей, журналов администратора, дополнительного контекста и вложений по-прежнему используются обычные запросы; архив определяет эту область. Флаги Takeout запрашивают выбранный тип чата без контактов или экспорта файлов. Личные чаты и закрытые группы остаются доступными через обычный путь или [экспорт аккаунтов](ACCOUNT-EXPORT.md).

Если Telegram требует одобрения экспорта, задание приостанавливается и отображается возвращённый срок. Одобрите запрос в Telegram или дождитесь, а затем явно возобновите задание. Автоматического перехода на работу со стандартной скоростью не происходит. Функции «Приостановить»/«Отменить» сохраняют личный идентификатор Takeout для задания, которое можно возобновить; они не выходят из аккаунта и не отзывают авторизацию. При возобновлении происходит проверка аккаунта, идентификатора и диапазона разделения. Идентификатор с истекшим сроком действия приостанавливает задание; последующее возобновление создает новое поколение. Измененный диапазон разделения требует нового экспорта, а не смешивания несовместимых страниц.

Идентификаторы Takeout хранятся в зашифрованном хранилище. Квитанции фрагментов идентифицируют канал передачи и поколение без использования идентификатора. Подписанный архив фиксирует время открытия, повторного использования и закрытия поколения, а также любые ошибки финализации. Финализация истории происходит после выбора и выполнения сетевых операций, но до упаковки; при повторной попытке упаковки можно повторно использовать подписанные фрагменты. Старые планы сохраняют исходные размеры каналов передачи и фрагментов.

<a id="exclusive-account-ownership"></a>
## Исключительное право владения аккаунтом

Одной учетной записью одновременно выполняется один цикл просмотра истории или один экспорт, наряду с наблюдением в режиме реального времени. Элементы управления паузой являются независимыми. Бронирования приобретаются до отправки запросов в Telegram и освобождаются по завершении, в случае сбоя или при приостановке. История считывает до трёх чатов одновременно с одним курсором на каждый чат. Запросы к истории и запросы на файлы имеют отдельные ограничения по три активных запроса каждый; интервал между запросами остаётся общим для каждого аккаунта. Другие RPC-запросы поочерёдно обрабатываются в отдельных каналах для оперативных обновлений, работы оператора, фоновых проверок и экспорта. Медленный ответ освобождает другие каналы для продолжения работы; темп обработки по-прежнему распределяется на один аккаунт. Отдельные аккаунты работают одновременно. Сохраненные сроки FloodWait проверяются повторно перед отправкой запросов из очереди, в том числе после перезапуска. Повторные попытки экспорта приостанавливают данный экспорт; сохраненный срок для затронутого метода Telegram по-прежнему применяется к другим вызывающим сторонам, использующим его.

<a id="selection"></a>
## Выбор

- Вся доступная история: скользящий период 7/30 дней, предыдущий календарный месяц или пользовательские границы. Даты в пользовательском интерфейсе используют часовой пояс браузера и при запуске фиксируются в виде границ в формате UTC `[from, until)`.
- Включаются сообщения, отправленные ровно в момент **От**, включая несколько сообщений, пришедших в течение одной секунды. Telegram может возвращать само сообщение со смещением даты, поэтому при сборе данных происходит считывание чуть раньше нижней границы, а точный период применяется локально. Граница **До** остаётся исключительной.
- Определение языка сообщений в автономном режиме с помощью Lingua. Для коротких, неоднозначных и многоязычных сообщений предусмотрена отдельная опция включения/исключения. К оцененным выбранным сообщениям прилагаются версия детектора, принятые решения и показатели достоверности.
- При выборе **Сообщения, являющиеся ответами** отбираются прямые ответы. **При** выборе **Сообщения, на которые поступил ответ** отбираются исходные сообщения, на которые было проведено наблюдение за прямым входящим ответом. Взаимосвязи устанавливаются до фильтрации по языку/тексту, поэтому ответ на русском языке может соответствовать критериям отбора исходного сообщения на английском языке. Простое размещение сообщения в теме форума не считается прямым ответом.
- Поиск ответов возможен в пределах выбранного периода или с момента начала сбора данных. В последнем случае может потребоваться сканирование более поздней истории.
- Ограниченный контекст «родительского сообщения/ответа» с отдельным ограничением на количество сообщений. Контекст может выходить за пределы фильтров и помечается как `selection.role=context`. Для отсутствующих родительских сообщений сохраняется причина; связанные обсуждения за пределами выбранного источника не просматриваются. Контекст расширяется на всю собранную историю и извлекает отсутствующие родительские сообщения из того же источника; он не обнаруживает все ответы, выходящие за пределы просканированного периода.
- Буквальная текстовая фраза; фильтрация по идентификатору отправителя через API. Дополнительные вложения извлекаются после выбора в соответствии с политикой сбора данных ведущего аккаунта, независимо от того, какой аккаунт их просматривает. Изменённое сообщение не заменяется автоматически во время извлечения вложений.

<a id="chunking-and-continuation"></a>
## Разделение на фрагменты и продолжение

Для супергруппы/канала в ходе предварительной проверки источник определяется отдельно для каждого аккаунта, а видимые границы по дате и идентификатору фиксируются. Общая очередь распределяет непересекающиеся фрагменты между подходящими аккаунтами. Как обычный сбор данных, так и сбор через Takeout начинаются с 2 000 числовых идентификаторов на фрагмент и могут быть расширены до максимум 100 000 идентификаторов с использованием оценки количества доступной полной истории, предоставленной аккаунтом с наибольшей плотностью данных. Это сокращает количество пустых запросов в редких историях; при этом из подписанного плана не исключаются никакие идентификаторы и не изменяется темп RPC-запросов. Подсчёты представляют собой оценку для планирования, а не подсчёт за выбранный период или результат удаления. Диапазон идентификаторов не является количеством сообщений. Обычные группы и личные чаты используют один аккаунт, поскольку идентификаторы не могут объединяться между аккаунтами одинаковым образом.

В каталоге `distributed-exports/<job-id>/` хранятся подписанный неизменяемый план, подписанные квитанции о получении фрагментов, полученные фрагменты в формате JSONL, восстанавливаемые индексы SQLite и итоговый ZIP-архив. В новых планах внутри каждого фрагмента используются контрольные точки `tgwitness-distributed-pages-v2`; планы, запущенные ранее, сохраняют `tgwitness-distributed-pages-v1`. Перед контрольной точкой в буфере накапливается не более 100 декодированных сообщений; при целевом значении 4 MiB также сбрасываются более мелкие партии (размер отдельной записи может достигать 64 MiB). Речь идёт о локальных партиях записей, а не о необработанных ответах RPC Telegram. Каждая квитанция связывает хеш плана, чат, ключ аккаунта/подписи, диапазон идентификаторов, курсоры «до» и «после», интервал в байтах, хеш данных, время локального получения, генерацию транспорта и хеш предыдущей квитанции.

Данные сбрасываются и синхронизируются до того, как соответствующая квитанция будет атомарно записана и синхронизирована. Только после этого продвигается постоянный курсор. Приостановка сбрасывает незавершённую запись перед освобождением аккаунта. Возобновление проверяет каждую сохраненную контрольную точку перед подключением, игнорирует неподписанные конечные байты и обрезает этот хвост перед продолжением с последнего зафиксированного курсора. Может потребоваться повторное чтение до 99 сообщений из буфера или текущей неподписанной записи. Зафиксированные страницы сохраняются без изменений. В схеме v1 частично приобретённый диапазон остаётся привязанным к исходному аккаунту. В схеме v2, когда Telegram просит аккаунт подождать 15 секунд или более, либо если аккаунт читает заметно медленнее, чем аккаунт, у которого больше нет задач, диапазон освобождается на уровне последней подписанной страницы, и другой подходящий аккаунт продолжает работу с этого курсора. Первая подписанная страница указывает в поле ``handover_from`` аккаунт, у которого был получен диапазон; страницы, подписанные ранее, сохраняют свой аккаунт. Смена аккаунта без указания этого поля отклоняется верификатором, поэтому ни один аккаунт не может незаметно завершить диапазон другого. Архив относит каждое сообщение к тому аккаунту, который подписал его страницу. Пустые терминальные квитанции указывают на исчерпание итератора для данного наблюдателя, а не на его полное отсутствие. Истекший Takeout может возобновиться в новом поколении, что фиксируется отдельно в последующих квитанциях.

После завершения диапазона квитанция его фрагмента привязывает конечную головку контрольной точки. При возобновлении выполняется проверка подписей, хешей, диапазонов, порядка, идентичности учетной записи и сохраненного прогресса перед повторным использованием. Старые планы без параметра ``checkpoint_format`` сохраняют исходный путь восстановления всего фрагмента; они не подвергаются автоматической миграции. Приостановленные задания можно возобновить из **сохраненных экспортов** в диалоговом окне экспорта. Несколько заданий могут выполняться одновременно, если они используют отдельные аккаунты. Каждое задание сохраняет свои собственные рабочие процессы, контрольные точки и временные параметры; аккаунт, зарезервированный одним заданием, не может присоединиться к другому, пока не будет освобожден.

Проверьте **приостановленный или завершившийся сбоем** рабочий каталог нового формата без приложения, индекса SQLite или хранилища:

```bash
python tgwitness/verify.py /path/to/distributed-exports/JOB_ID --fingerprint RETAINED_FINGERPRINT --json
```

Эта проверка в режиме «только для чтения» отображает зафиксированные сообщения/страницы, завершённые диапазоны и неподписанные конечные байты. Независимо зафиксируйте начальный отпечаток. Как и в случае с любой локальной цепочкой квитанций, удаление её конца и всего соответствующего локального прогресса невозможно обнаружить без отдельно сохраненной начальной части квитанции. Верификатор анализирует зафиксированные записи о получении данных. При сравнении собранного состояния обращайте внимание на их интервалы и охват.

Промежуточные фрагменты включают сообщения, необходимые для оценки фильтров, в том числе отклоненные сообщения. Фильтры ограничивают окончательный архив. Приостановленное, отмененное или завершившееся с ошибкой задание сохраняет эти фрагменты и квитанции контрольных точек для восстановления. Экспорт, завершившийся сбоем по причине, отличной от отклоненного запроса или настройки, также записывается в журнал процесса вместе с трассировкой в рамках логгера `tgwitness.export`; на панели отображается только текст ошибки. После успешной проверки архива и завершения задания приложение удаляет фрагменты, квитанции, медиафайлы и индексы. В каталоге задания сохраняются файл ``export.zip``, подписанный план ``job.json`` и файл ``status.json``; для завершённых заданий используйте верификатор ZIP-архивов. Перед созданием новых фрагментов и каждой контрольной точки проверяется наличие настроенного резерва свободного места.

Более широкие диапазоны по-прежнему сокращают количество запросов при работе с разреженными историческими данными. Новые контрольные точки ограничивают повторное чтение прерванных диапазонов независимо от этой ширины. Проверка перекрытия между аккаунтами остаётся отдельной задачей на будущее. Более частая подпись и синхронизация увеличивают нагрузку на локальный ввод-вывод; создание контрольных точек улучшает восстановление, но не скорость успешного непрерывного чтения по сети.

Планы, созданные до исправления, связанного с «inclusive-start», сохраняют свои исходные диапазоны подписанных идентификаторов при возобновлении. Запустите новый экспорт с фильтрацией по дате, чтобы восстановить любые сообщения, исключённые в поле **From** более старым планом.

<a id="result-and-limits"></a>
## Результаты и ограничения

<a id="performance-measurements"></a>
### Измерение производительности

Панель экспорта и API состояния отображают время, прошедшее с момента **текущего запуска или возобновления**, с использованием монотонного таймера. Подготовка включает установку соединения, проверку границ, верификацию сохраненных фрагментов и метаданные чата. Измерение скорости сбора данных учитывает совокупную работу всех параллельных процессов, включая ожидание ответа от Telegram, запись фрагментов и выпуск квитанций. Выбор и извлечение вложений, а затем упаковка и проверка имеют отдельные таймеры. Приостановка или завершение останавливают измерения; возобновление запускает новое измерение и исключает ранее зафиксированные сообщения из числителя пропускной способности.

Пропускная способность процесса сбора определяется как количество вновь зафиксированных сообщений, деленное на общее время сбора. Данные о новых заданиях обновляются при фиксации страниц, включая прогресс в незавершённом диапазоне; данные о старых заданиях обновляются при фиксации блоков. Это среднее значение, а не мгновенная скорость сети. Оно не включает отбор, вложения или создание ZIP-архивов и PDF-файлов. Статус задания с подписью сохраняет эти показатели; при успешном выполнении они также записываются в поле ``chat_export.completed``. Задания, созданные до появления этой функции, не имеют записей о производительности до момента возобновления. Количество оставшихся сообщений неизвестно, поэтому панель не рассчитывает предполагаемое время завершения (ETA) на основе числовых диапазонов идентификаторов. Сравнивайте запуски с одинаковым фиксированным охватом, настройками вложений и доступом к аккаунтам; прирост производительности при использовании большего количества аккаунтов зависит от диапазонов идентификаторов чатов и ограничений Telegram.

Поиск больших списков имеет иной набор запросов, чем сбор истории. Ознакомьтесь со [сравнением исходных данных экспортера и ограничениями,](EXPORT-LIMITS.md) прежде чем экстраполировать результаты тестирования небольшого объёма истории на тысячи новых источников.

[Тестирование в режиме реального времени с 50 источниками,](../EXPORT-BENCHMARK-2026-11-06.md) проведённое 06.11.2026, дало 48 проверенных архивов, содержащих 3 598 381 запись. Одно задание в обычном режиме с восемью аккаунтами собрало 768 007 записей истории за 1 117,082 секунды; полное выполнение задания заняло 1 574,920 секунды. Повторные проверки добавили записи, которые не были возвращены при первоначальном сборе истории. В ходе тестирования также были выявлены накладные расходы при работе с разреженными диапазонами, таймауты соединений и замедление последующих заданий по мере увеличения выученного темпа обработки. Объем тестирования и проводимые проверки описывают измеряемую конфигурацию.

В рамках ограниченного пилотного тестирования в режиме реального времени 06.11.2026 г. по UTC было проведено сравнение одного и двух аккаунтов в одних и тех же диапазонах, включающих примерно 4 000 идентификаторов, в двух общедоступных супергруппах. Сбор 3 313 сообщений занял 33,672 с и 16,969 с; сбор 3 691 сообщений — 37,750 с и 19,188 с. Все четыре ZIP-архива прошли проверку. Наборы идентификаторов совпадали между прогонами; различия в трёх заголовках reply-media ограничивались хешами доступа и ссылками на файлы. ### Архив

Файл ZIP использует существующий, поддающийся независимой проверке формат экспорта чата с подписанными частями для каждого аккаунта, выбранными сообщениями, метками контекста, настройками выбора и объёмом сбора данных. Авторитетным является файл ``chat.json``. В форматах HTML и PDF номера сообщений, пропущенных в результате выбора, отличаются от доказательств удаления. Приложение проверяет файл ZIP перед тем, как пометить его как готовый; после этого загрузки остаются доступными.

Манифест определяет формат контрольной точки и количество, используемое локально. Данные невыбранных контрольных точек и соответствующие квитанции не добавляются в отфильтрованный ZIP-файл. Проверка архива продолжается для проверки выбранных сообщений и их подписей аккаунтов; проверка локальных контрольных точек представляет собой отдельную проверку каталогов, описанную выше. Старые ZIP-файлы по-прежнему поддерживаются.

В разделе «Охват» перечислены доступные диапазоны, которые были фактически прочитаны. Аккаунты могут иметь разные права доступа; при распределённом или возобновлённом сборе данные каждого диапазона считываются в своё время. Информация об участниках, причинах удаления, блокировках и личностях модераторов предоставляется только из тех данных Telegram, в которых она указана.
