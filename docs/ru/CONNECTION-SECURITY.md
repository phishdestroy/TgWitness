# Подключение, прокси-серверы и защита данных

В данном документе описано поведение TgWitness 0.9.3 и его ограничения. Аутентификация,
доступ к источникам, сетевое соединение и полнота сбора данных представляют собой отдельные состояния.
Информацию о шагах входа в систему, форматах файлов и работе с несколькими аккаунтами см. в разделе
[аккаунты и форматы сеансов](../ACCOUNTS.md). Информацию о правилах обработки событий и поведении при перезапуске
см. в разделе [как работает сбор данных](../COLLECTION.md).

<a id="guided-connection-setup"></a>
## Настройка подключения с помощью мастера

В разделе **«Дополнительные инструменты» → «Учетная запись» → «Маршрут подключения»** администратор может выбрать **«Эта учетная запись»**, **«Группа аккаунтов»**
или **«Все аккаунты»**, а затем выбрать маршрут. В разделе **Проверить выбор** отображается список
затронутых учётных записей. Функция **Подготовить и проверить** позволяет протестировать предложенный маршрут без изменения
сохраненного. Функция **Применить проверенное подключение** подтверждает предварительный просмотр, приостанавливает мониторинг, если
необходимо, сохраняет маршрут и возобновляет уже запущенный мониторинг.
Сбор данных никогда не запускается в учетной записи, которая ранее находилась в неактивном состоянии. Загрузки из истории остаются
приостановленными и могут быть возобновлены отдельно. Перед переключением приостановите активные экспорты.

По умолчанию при изменении группы настройки аккаунтов сохраняются с их собственными маршрутами. Снимайте этот флажок
только в том случае, если в окне предварительного просмотра отображаются именно те изменения, которые вы планируете внести. Приложение сообщает о
результатах для каждого аккаунта; это не транзакция типа «всё или ничего» для всех баз данных. В случае
неудачного переключения для данного аккаунта восстанавливаются предыдущие настройки. Неудача при возобновлении
отображается явно. Срок действия предварительного просмотра истекает через десять минут, а изменения в настройках подключения
или членстве в группе требуют новой проверки.

Apply повторно использует успешный результат предварительной проверки в течение 90 секунд, если его маршрут,
режим и политика остаются неизменными. Управляемый туннель по-прежнему должен иметь тот же запущенный
процесс. Более старые результаты, измененные процессы туннелей и маршруты автоматического пула MTProxy
проверяются заново. Подписанная запись приложения сохраняет исходное время проверки
и фиксирует повторное использование, а также его возраст. Каждая предварительная проверка закрывает свой временный неавторизованный
клиент; коллектор подключается, используя собственную авторизованную сессию.

| Маршрут | Чем занимается TgWitness |
| --- | --- |
| Прямой | Подключения с хоста; VPN внешнего хоста не обнаруживается и не принудительно настраивается. |
| VPN | Один профиль WireGuard с полным туннелированием на каждую учетную запись, реализуемый локальным процессом SOCKS5 в пользовательском пространстве. Никаких хост-интерфейсов или драйверов не устанавливается. |
| Мой представитель | Учетные данные SOCKS5, HTTP CONNECT или MTProxy. URL-адрес может заполнить поля SOCKS5/HTTP. При выборе нескольких аккаунтов введенные данные прокси используются для всех них. |
| Публичный MTProto | Существующий пул назначает маршруты Telegram. Внешние запросы отключены до тех пор, пока в расширенных настройках не будет настроен отдельный подходящий прокси-сервер. |
| WARP | Отдельный локальный туннель для каждой выбранной учетной записи, при этом регистрация WARP и профиль WireGuard хранятся в хранилище этой учетной записи. |

При проверке текущего маршрута используется новое неавторизованное транспортное соединение Telegram, а не
сессия учетной записи. При этом открывается транспортное соединение по маршруту до
центра обработки данных учетной записи и выполняется один цикл обмена данными по протоколу MTProto без аутентификации
(`req_pq_multi`); при этом не создаётся ключ авторизации и не используется учётная запись.
Указанная задержка представляет собой время установления соединения плюс время обмена данными, и проверка
регистрирует обе части отдельно. Для маршрутов, поддерживающих HTTP, также запрашивается
HTTPS-трассировка Cloudflare по данному маршруту и отображаются указанные в ней IP-адрес выхода,
страна, состояние WARP и время проверки. Подготовка WARP завершается сбоем, если в трассировке
не указано, что WARP активен. Эти предварительные проверки сообщают о доступности маршрута и
наблюдаемом выходе. Просмотрите захваченные записи через результаты сбора и
верификации архива. Сам по себе запущенный локальный процесс не является успешной проверкой выхода.

Панель ведёт скользящее среднее по последним пяти проверкам. Маршрут считается **медленным**, если
среднее значение превышает 5 секунд или три проверки подряд превышают это значение, и
**недоступным** — после двух неудачных проверок подряд; `network.slow_route` и
`network.route_recovered` фиксируют эти изменения. Для медленного маршрута WARP функция **«Re-roll WARP»**
перезапускает туннель аккаунта через другие конечные точки Cloudflare WARP, сохраняет
самый быстрый и фиксирует `network.warp_rerolled` с указанием времени до и после;
**Новая идентификация WARP** регистрирует новое устройство WARP и сохраняет его только в том случае, если оно
работает быстрее. Адрес локального прокси, аккаунт Telegram и его сессия остаются
прежними; соединения с Telegram восстанавливаются через перезапущенный туннель. Медленный маршрут WARP
перенастраивается автоматически не чаще одного раза в 30 минут; если это
не помогает, дальнейшие перенастройки ожидают вмешательства оператора.

<a id="portable-warp-and-wireguard"></a>
### Портативные версии WARP и WireGuard

Это **неофициальная интеграция с WARP**, использующая
[wgcf 2.3.1](https://github.com/ViRb3/wgcf/releases/tag/v2.3.1) и
[wireproxy 1.1.3](https://github.com/windtf/wireproxy/releases/tag/v1.1.3).
Администратор явно подтверждает настройку перед первой загрузкой или регистрацией в WARP. Эти соединения для настройки устанавливаются напрямую с GitHub и Cloudflare и
раскрывают IP-адрес компьютера. Трафик обычных учётных записей сохраняет существующий маршрут до момента
запуска приложения. Cloudflare выбирает адрес выхода и страну; отдельные туннели
могут использовать один и тот же адрес выхода. Выбор страны, периодическая ротация IP-адресов и общесистемный
VPN-kill-switch не поддерживаются этой функцией.

Поддерживаемые версии вспомогательных программ: Linux и macOS (x86-64/ARM64), а также Windows (x86-64).
Артефакты проверяются по хэшам SHA-256, включенным в проверенный исходный код,
а исполняемые файлы из кэша проверяются повторно перед запуском. Ни один вспомогательный модуль не добавляется в
PATH, не устанавливается в качестве системной службы и не получает общедоступного прослушивателя. Все файлы находятся
в каталоге рабочей области `portable-routes/` и в зашифрованных записях хранилища.
Для прослушивателя SOCKS5 с обратной связью требуются независимо сгенерированные учетные данные.

Личные профили и учетные данные учетной записи WARP шифруются с помощью существующего
хранилища рабочей среды. Во время работы вспомогательной программе требуется конфигурационный файл в виде открытого текста, доступный только владельцу;
при нормальном завершении работы он удаляется. В результате сбоя хоста этот файл может остаться в
папке данных, доступной только владельцу. Это не обеспечивает шифрование диска и не защищает от действий
администратора. Супервизор закрывает туннель, если родительский канал панели
исчезает. Неудавшийся туннель никогда не включает прямой резервный вариант. Перезапуск панели
восстанавливает выбранный туннель; неудавшиеся запуски повторяются с ограниченной задержкой. **Остановить
туннель** также приостанавливает наблюдение и сохраняет состояние остановки. **Запустить туннель**
запускает туннель; возобновите наблюдение отдельно, когда будете готовы.

Загруженные профили WireGuard должны содержать один интерфейс и один узел-партнер, полные маршруты IPv4
и IPv6, а также не должны содержать хуков, включений, подстановок переменных среды или дополнительных
прослушивателей. Адреса публичных конечных точек определяются и фиксируются до запуска.
Для OpenVPN/IPsec и частных конечных точек используйте внешний VPN-шлюз или SOCKS5-шлюз.

<a id="authentication-methods"></a>
## Методы аутентификации

**Идентификатор API и хеш API служат для идентификации приложения; они не заменяют данные для входа в аккаунт.**
В TgWitness их использование не является обязательным. Порядок приоритета: пара, введенная в форму; затем пара из
импортированного JSON-файла аккаунта; затем пара, сохраненная в рабочей области; затем встроенный пул из 50
общедоступных пар, которые пробуются в случайном порядке с автоматической ротацией, когда Telegram отклоняет одну из них. Только
пара Telegram Desktop (2040) отправляется с соответствующим описанием клиента Telegram Desktop.
Ваша собственная пара из инструментов разработки API на [my.telegram.org](https://my.telegram.org)
может использоваться со всеми вашими аккаунтами; при этом каждый аккаунт по-прежнему имеет собственную авторизацию.

| Метод | Требования | Поддержка TgWitness |
| --- | --- | --- |
| Номер телефона, код, двухфакторная аутентификация (по желанию) | Доступ к учетной записи; пара API — необязательна | Вход в панель управления |
| HEX-код аутентификации + DC-идентификатор | Полная клавиатура на 512 символов и DC 1–5 | Вкладка «**Ключ авторизации**»; перед сохранением авторизации проверяется наличие идентификатора пользователя (опционально) |
| Телемарафон StringSession | Допустимая строка сеанса | Вход в панель управления |
| Telethon SQLite `.session` | Закрытый, согласованный текст | Прямой импорт схем через панель управления 7/8; дополнительная возможность автономного использования командной строки |
| Pyrogram SQLite `.session` | Закрытие рабочей сессии пользователя | Прямой импорт схем из панели 2/3 |
| Telegram Desktop TData ZIP | Одно из современных описаний; локальный пароль, если доступ защищен | Преобразование в памяти с проверкой контрольной суммы и дешифрования |
| JSON-файл учетной записи | Поддерживаемые поля API/сессия/ключ | Метаданные сами по себе заполняют учетные данные API; по-прежнему требуется вход с помощью сеанса/ключа или номера телефона/QR-кода |
| Вход с помощью QR-кода | Подтверждение из официального приложения Telegram | Локальное создание QR-кодов, управление сроком действия и повторные попытки, опциональная двухфакторная аутентификация (2FA) |
| TDLib / Pyrogram StringSession | Другие форматы, специфичные для библиотек | Не поддерживается |
| Токен бота | Бот со своей собственной моделью доступа и обновления | Не используется данным коллекционером |

Telegram выбирает способ доставки кода, в том числе решает, отправлять ли SMS. Хеш API не может восстановить
отмененную сессию или заменить забытый пароль двухфакторной аутентификации. TgWitness не сохраняет
коды входа или пароль двухфакторной аутентификации Telegram на диске.

Если речь идет о частном источнике, у аккаунта уже должен быть доступ. Имя пользователя группы
не требуется. Импорт через прокси или сессию не предоставляет ни членства, ни прав администратора.
Настройки чата определяют, видят ли участники историю, накопленную до их присоединения.

<a id="import-a-telethon-session-file"></a>
## Импорт файла сеанса Telethon

Telethon SQLite, Pyrogram SQLite и Telegram Desktop TData используют разные форматы.
Панель определяет и конвертирует поддерживаемые структуры; переименование файла не является
конвертацией. Выберите одну сессию и сопутствующий ей файл JSON в разделе **Файлы**, нажмите **Проверить файлы**, а затем **Подключить аккаунт**. Допускается до четырёх совпадающих файлов и
общий объём до 8 МиБ. Подробности о TData/JSON см. в разделе [ограничения формата](../ACCOUNTS.md).
Восстановление пароля невозможно. Вход с помощью телефона/двухфакторной аутентификации или QR-кода создаёт отдельную авторизацию.

Дополнительный путь командной строки, предназначенный исключительно для Telethon, по-прежнему доступен:

1. Остановите работу клиента, использующего исходную сессию, и создайте согласованную копию.
   Конвертер отклоняет файлы с незавершенным журналом WAL. Закройте исходный
   клиент надлежащим образом, вместо того чтобы удалять эти файлы с целью обойти проверку.
2. В среде TgWitness выполните следующую команду:

```sh
python -m tgwitness.sessions account.session --out account.tgwitness-session
```

3. В разделе **«Добавить аккаунт» → «Файлы»** загрузите результат или
   вставьте его строку и нажмите «Далее».
4. Проверьте отображаемый цифровой идентификатор аккаунта, выберите источники и начните наблюдение.

**Преобразованный файл представляет собой незашифрованный секретный ключ доступа к учетной записи.** Храните его в защищённом
месте и ни в коем случае не заносите в репозиторий и не отправляйте его стороннему сервису конвертации. TgWitness
сохраняет авторизованную сессию в своём зашифрованном хранилище. Копирование сессии не
приводит к созданию отдельной авторизации: не запускайте одновременно несколько клиентов с клонированными ключами авторизации
и не предполагайте независимую доставку обновлений.

При преобразовании передается авторизация, а не исходные сообщения, кэш сущностей или
устойчивый курсор обновления. Это не решает проблему восстановления обновлений после перезапуска процессов.

<a id="mtproto-telethon-and-proxies"></a>
## MTProto, Telethon и прокси-серверы

MTProto — это протокол Telegram. Telethon — это клиентская библиотека на Python, которую использует TgWitness.
MTProxy — это транспортный прокси Telegram; SOCKS5 и HTTP CONNECT обеспечивают общие
туннели. Ни один из них не заменяет аутентификацию учетной записи.

Сохраните маршрут для каждой рабочей области в разделе **Дополнительные инструменты → Учётная запись → Настройки → Настройки подключения → Изменить маршрут подключения** перед
входом в систему. Для новых рабочих областей по умолчанию установлено значение **Автоматический MTProxy · общедоступные списки** с параметром **Скрыть адрес**.
Существующие рабочие области, в которых явно использовался режим «Прямой», сохраняют режим, допускающий его использование.

Файлы читаются по отдельным соединениям, отличным от того, по которому читаются сообщения, как это делается в официальных
приложениях. В собственном дата-центре аккаунта ключ авторизации аккаунта используется повторно в
новой сессии MTProto; для другого дата-центра создаётся один ключ, который авторизуется во время
подключения аккаунта и хранится только в памяти. Каждое файловое соединение использует тот же маршрут,
что и аккаунт. Их количество на один центр обработки данных ограничено параметром **Параметры → Производительность →
Количество файловых соединений на один центр обработки данных Telegram**; при значении 0 файлы читаются только через основное
соединение аккаунта. Одновременно может быть установлено не более пяти соединений с Telegram для всех аккаунтов
в рамках одной инсталляции.

<a id="ip-modes"></a>
## Режимы IP

Маршрут определяет тип подключения. Режим IP, **Защита IP** в разделе «Учетная запись» панели управления,
определяет, когда адрес сервера может быть раскрыт. Эти настройки не
обеспечивают установку VPN и не маршрутизируют весь трафик компьютера.

| Режим | Telegram | Внешние запросы |
| --- | --- | --- |
| Скрыть адрес (`hide`) | Используйте прокси; если ни один не работает, подождите. Прямого резервного варианта нет. | Требовать использование SOCKS5/HTTP; отклонять запросы без соответствующего прокси-сервера. |
| Прямой доступ — в крайнем случае (`fallback`) | Автоматический MTProxy может использовать Direct по истечении заданной задержки, а затем вернуться к работе через прокси. | Предпочтительно использовать настроенный внешний прокси-сервер или маршрут SOCKS5/HTTP учетной записи; в противном случае допускается использование прямого подключения. |
| Сервер, расположенный за туннелем или VPN (`tunnel`) | Допускаются прямые маршруты и немедленное переключение на резервный пул. | Прямой доступ разрешается, если не настроено ни одно соответствующее прокси-сервер. |

Режим «туннель» или «VPN» предполагает, что вы управляете этой сетью отдельно. Без работающего
туннеля конечные пользователи могут увидеть собственный адрес сервера. Выбирайте режим в соответствии
с вашей фактической сетевой конфигурацией, а не по названию опции.

<a id="choose-a-route"></a>
### Выберите маршрут

| Маршрут | Настройки | Граница |
| --- | --- | --- |
| Автоматический MTProxy | Встроенные списки или каталог операторов | Обеспечивает работоспособность маршрута Telegram; выбор прямого резервного варианта зависит от режима IP |
| Прямой | Режим «Туннель» или «VPN» | Telethon использует сетевой маршрут хоста |
| SOCKS5 | Хост, порт, опционально — имя пользователя/пароль | python-socks, поддержка удалённого DNS-адреса |
| HTTP CONNECT | Хост, порт, опционально — имя пользователя/пароль | Обычный HTTP CONNECT; TLS для самого прокси не реализован |
| MTProxy | Хост, порт, секретный ключ | Экспериментальный формат передачи данных Telethon: 32 шестнадцатеричных цифры или `dd` + 32 шестнадцатеричных цифры |

Поддельные секретные данные TLS `ee` отклоняются. Функция нормализации в Telethon 1.45 может удалять префикс
и домен, но это не реализует функцию «Поддельный TLS». Вставьте `tg://proxy?server=…&port=…&secret=…`
или `https://t.me/proxy?server=…&port=…&secret=…` и выберите **Заполнить поля из ссылки**.
Это проверяет и заполняет поля без подключения или сохранения; проверьте и сохраните
маршрут отдельно. Поля для ручного ввода остаются доступными. См. [Прокси-ссылки Telegram](https://core.telegram.org/api/links#proxy-links).

<a id="public-proxies-supplied-by-your-installation"></a>
### Общедоступные прокси-серверы, предоставляемые вашей установкой

Встроенный список объединяет семь источников:
[SoliSpirit/mtproto](https://github.com/SoliSpirit/mtproto)
,
[zakky8/mtproto-proxy-pro](https://github.com/zakky8/mtproto-proxy-pro)
,
[kort0881/telegram-proxy-collector](https://github.com/kort0881/telegram-proxy-collector)
,
[3yed-61/MTP-Collector](https://github.com/3yed-61/MTP-Collector)
,
[Therealwh/MTPproxyLIST](https://github.com/Therealwh/MTPproxyLIST)
,
[KhodeJav/telegram-proxy-collector](https://github.com/KhodeJav/telegram-proxy-collector)
и [tgmtproxy/telegram-mtproto-proxy-list](https://github.com/tgmtproxy/telegram-mtproto-proxy-list)
.
Включённый в пакет снэпшот содержит данные об конечных точках, информацию об источниках и даты загрузки.
Списки являются исходными данными; приведенные ниже проверки подключения определяют, какие прокси будут использоваться.

**Автоматический MTProxy** проверяет подключение к транспортному каналу Telegram, поддерживает рабочий прокси-сервер
и переключается на другой в случае сбоя. Рабочие пространства предпочитают использовать разные прокси-серверы, если доступно достаточное
количество рабочих записей; прокси-серверы могут использовать общий выходной адрес. Неработающие прокси
отдыхают перед повторной попыткой. Если ни один не работает, режим IP определяет, должна ли коллекция
ждать или может использовать прямое соединение. Смена прокси не меняет учётную запись
и не удаляет её журнал. Выбор маршрутов и изменения записываются в подписанный журнал.

Пока активны автоматические маршруты, списки обновляются ежечасно, а проверки транспорта выполняются
по умолчанию каждые десять минут. Эти интервалы можно настроить. **Обновление общедоступных списков**
запускает процесс обновления; простой просмотр списка не приводит к изменению сохраненного ручного маршрута.

**Трафик Telegram и HTTPS-запросы используют разные маршруты.** При загрузке списков используется
отдельное HTTPS-соединение и заданный маршрут внешних запросов. Элемент
`TGWITNESS_PROXY_FEED_PROXY` явно переопределяет этот маршрут с помощью HTTP/SOCKS5-прокси;
оба варианта сборщика Compose перенаправляют его. Фоновый пул следует за основной рабочей областью.
Поставщикам фидов не отправляются данные о сеансах Telegram, учетные данные API, токен панели или токен бота.
Названия поставщиков, даты создания снимков и маршрут загрузки отображаются в разделе **Откуда взят список**.

MTProxy передаёт исключительно трафик Telegram. HTTP-операции рабочего пространства, такие как временные метки,
уведомления, внесайтовые копии и проверки источников, используют отдельный SOCKS5/HTTP-прокси, если
он настроен, а затем — маршрут SOCKS5/HTTP учетной записи. При отсутствии того или другого «Скрыть адрес» отклоняет
запрос; остальные режимы разрешают «Прямой». Внешние запросы можно отключить. Явно
настроенный прокси для загрузки фидов остаётся отдельным переопределением оператора.
Независимый сервис свидетелей использует свой собственный маршрут.

Для частных сервисов, управляемых оператором, существующий параметр серверной среды
`TGWITNESS_ALLOW_PRIVATE_DESTINATIONS=1` разрешает частные адреса назначения и сохраняет
разрешение имен хостов на стороне прокси. Его невозможно включить через панель управления. Режим «только публичные»
отклоняет адреса назначения `.onion` перед отправкой запроса в публичный резолвер; для onion-сервисов Tor
требуется явная настройка частных адресов назначения и подходящий прокси.
Данное поведение DNS применимо к внешним HTTP-операциям, а не к транспортному протоколу Telegram.
Cloudflare описывает [конечную точку JSON DNS ](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json/).

Чтобы заменить общедоступный список собственным каталогом операторов, настройте приведенное ниже переопределение.
Оно полностью отключает внешние подписки, в том числе и в том случае, если массив `proxies` пуст.

Скопируйте [пустой каталог ](../../deploy/proxies.config.example)
в `proxy-config/proxies.json`
и добавьте свои развернутые общедоступные конечные точки:

```json
{"format": "tgwitness-proxy-catalog-v1", "proxies": [
  {"id": "project-eu", "label": "Project EU",
   "link": "tg://proxy?server=REPLACE_HOST&port=443&secret=REPLACE_SECRET"}
]}
```

Приведенные в примере значения необходимо заменить. Допускается до 32 уникальных записей. В
списке с аутентификацией отображаются метки/хосты/порты без общих секретных ключей; при выборе одной из
записей её учетные данные сохраняются в хранилище рабочей среды. Доступность не проверяется до тех пор, пока не будет
проведено явное тестирование транспорта. В случае некорректного формата каталога допускается ручная настройка.

Запуск в нативной среде: укажите путь к локальному файлу JSON в элементе `TGWITNESS_PROXY_CATALOG`. Docker:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.proxies.yaml up -d --build
```

Накладные монтируемые диски `proxy-config` доступны только для чтения; файлы должны быть доступны для чтения пользователю контейнера с UID 10001.
Этот каталог исключен из Git, контекста сборки Docker и архивов исходного кода. В этом
каталоге настраиваются аккаунты для сбора данных; [бот-свидетель ](../WITNESS.md) использует собственный
маршрут HTTP/SOCKS5, а не MTProxy.

Прямой переход на резервный маршрут регулируется описанным выше режимом IP. Перед
изменением маршрута следует приостановить наблюдение. При сохранении старые клиенты отключаются, а незавершенный вход отменяется;
новый клиент использует сохраненный маршрут. Связь между учетной записью и журналом/сессией сохраняется.
Настройки заменяют предыдущий маршрут: при их редактировании необходимо повторно ввести учетные данные прокси.

Учетные данные зашифрованы в `network.enc`. API не возвращает имя пользователя,
пароль или секретный ключ. Подписанные записи содержат тип маршрута и информацию о наличии
учетных данных, за исключением конечной точки и секретных ключей. Оператор может увидеть конечную точку
в панели управления. Поля с секретными ключами очищаются после сохранения, блокировки или переключения рабочих пространств.

Функция **«Проверить соединение с Telegram»**, доступная также до входа в систему, открывает и закрывает временное
неавторизованное соединение с Telegram через данный маршрут. Она не обращается к сайту проверки IP-адресов.
Успешное выполнение этой операции подтверждает наличие транспортного соединения, но не означает доступ к группам, полную
доставку сообщений или анонимность.

Прокси применяется к соединениям клиента Telegram, включая загрузку медиафайлов из Telegram DC.
Для браузера, pip, SSH и запускаемых вручную инструментов TSA предусмотрены отдельные маршруты.
Имя хоста прокси может разрешаться локально. `rdns` влияет на имена хостов назначения;
Telegram часто предоставляет числовые IP-адреса DC.

Протоколы SOCKS5 и обычный HTTP CONNECT сами по себе не шифруют учетные данные прокси-сервера или
туннель «клиент-прокси». MTProto отдельно защищает трафик Telegram. Используйте
соответствующий безопасный канал для подключения к прокси в ненадежной сети. Закрытые группы
— это облачные чаты, защищенные протоколом MTProto при передаче данных; секретные чаты с сквозным шифрованием представляют собой отдельный тип чата
, который создается с помощью модуля [«Секретный чат»](../PSEUDO-SECRET.md).

<a id="encryption-and-signatures"></a>
## Шифрование и подписи

| Слой | Реализовано | Ответственность оператора |
| --- | --- | --- |
| Трафик Telegram | Телемарафон MTProto | Доверие к платформе, маршрут и доступность |
| Веб-панель | Токен на предъявителя, значение по умолчанию для loopback, ограничения на количество запросов | HTTPS или SSH-туннель для удаленного доступа |
| Секреты | Fernet для учетных данных API, сеанса, учетных данных прокси и закрытого ключа подписи | Обеспечьте защиту ключа дешифрования и работающего хоста |
| Ключ хранилища | Локальный ключ или внешний мастер-ключ для новой установки | Раздельное хранение данных и резервное копирование ключей |
| Сообщения и вложения | Хранение приложений в виде открытого текста | Зашифрованный диск/том |
| ZIP/JSONL/CSV/HTML | Проверка целостности, отсутствие шифрования содержимого | Защита экспортированных копий и передач |
| Происхождение и время | Подписанный журнал, квитанция о приеме, инструменты RFC 3161 | Доверенный ключ, независимые контрольные точки/TSA и процедура хранения |

**Защита хранилища** в разделе «Аккаунт» отображает эти состояния. Токен панели — это
секретный ключ доступа, а не пароль для шифрования. Он предоставляет права администратора;
[выданные токены](../ACCESS.md) могут быть привязаны к аккаунтам и чатам. Рабочие пространства используют
общий хост-процесс и не являются изолированными арендаторами.

BitLocker, LUKS, FileVault или управляемый зашифрованный том могут обеспечить защиту хранилища в рамках
соответствующих моделей угроз. Администратор разблокированного работающего компьютера
по-прежнему может читать данные. При планировании хранения данных следует учитывать файлы WAL/SHM SQLite, мультимедиа, временные экспорты, файлы подкачки, резервные копии
и загрузки из браузера. Том Docker не шифруется только
потому, что он является томом.

<a id="external-master-key"></a>
## Внешний мастер-ключ

При **новой** установке поместите главный ключ вне каталога данных.
Это не приведёт к автоматическому переносу существующего хранилища с локальными ключами. Подготовьте каталог ключей,
доступ к которому будет иметь только учетная запись службы, а затем выполните:

```sh
python -m tgwitness.security create-master-key /private/keys/tgwitness-master.key
export TGWITNESS_VAULT_KEY_FILE=/private/keys/tgwitness-master.key
python -m tgwitness --data-dir /private/observations/new-case
```

PowerShell с использованием установленной среды проекта:

```powershell
python -m tgwitness.security create-master-key E:\PrivateKeys\tgwitness-master.key
$env:TGWITNESS_VAULT_KEY_FILE = 'E:\PrivateKeys\tgwitness-master.key'
python -m tgwitness --data-dir E:\PrivateData\new-case
```

В Docker подключите файл в режиме «только для чтения» вне `/data`, например, в
`/run/secrets/tgwitness-master.key`, и задайте эту дорожку в переменной среды.
UID сервиса должен иметь права на чтение этого файла. Передавайте дорожку, а не байты ключа, через
файлы среды/конфигурации.

Каждому рабочему пространству присваивается случайный открытый соль и собственный ключ Fernet, полученный с помощью
алгоритма HKDF-SHA256. В элементе `vault.external.json` хранятся метаданные о выводе ключа, а не сам мастер-ключ.
Отсутствие или неверность ключа приводит к сбою запуска, при этом ключ не заменяется автоматически. Для восстановления следует сохранить как
метаданные о соли, так и мастер-ключ.

Все рабочие пространства производятся от одного и того же главного ключа; его компрометация затрагивает всю
систему. Запущенный процесс может расшифровывать секретные данные. Это не HSM и не
KDF на основе пароля. Произвольные пароли, введенные пользователем, не принимаются вместо случайного ключа.

Сохраняйте существующий ключ для действующих установок до тех пор, пока не будет
осуществлен и проверен плановый переход. Удаление `vault.key` или замена главного ключа может привести к потере
доступа к сессионным ключам и ключам подписи. Храните зашифрованные резервные копии и ключи отдельно и
проверяйте возможность восстановления в изолированном экземпляре.
