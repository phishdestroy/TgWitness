# Telegram · ソース履歴を読み込む

Canonical page: https://phishdestroy.github.io/TgWitness/ja/docs/reference/history/

有効化されたソースから過去のメッセージを読み込み、一時停止や再開を行い、署名付きの進捗レポートを検証します。

[TgWitness](https://github.com/phishdestroy/TgWitness/blob/main/README.md) / [ドキュメント](https://github.com/phishdestroy/TgWitness/blob/main/docs/README.md) · [コレクション](https://github.com/phishdestroy/TgWitness/blob/main/docs/COLLECTION-MODES.md)

![コレクション](https://phishdestroy.github.io/TgWitness/assets/chapter-collect.svg)

「**ソース**」で、有効になっているチャットを確認し、監視を一時停止して、「標準API」または 「テイクアウトエクスポート」を選択し、次に**「全履歴を読み込む**」を選択してください。この実行により、ソースのリストが確定され、利用可能な過去のメッセージが 「チャット」および署名付き監視ログに読み込まれます。メディアについては、既存の添付ファイル 設定と永続的なダウンロードキューが使用されます。これは、チャットごとの署名付き JSON/HTMLエクスポートとは別物です。

アカウント全体のデータを収集するには、**「Whole account**」を選択し、監視を開始して ソースリストを読み込み、履歴の取得を開始する前にそのリストを確認してください。ダイアログリストの制限は 引き続き適用されます（デフォルトは1,000件、[Parameters]で調整可能）。実行が成功したからといって、 すべてのアカウントのダイアログがリストアップされたことを証明するものではありません。後で発見された、または有効化されたチャットについては、再度実行する必要があります。 履歴の取得を開始する前に監視を一時停止してください。1回の取得で所有できるアカウントは1つだけです。

1～5つのアタッチメント処理ワーカーを選択し、利用可能な「最近のアクション」を保持するかどうか、 および以前に保存されたバージョンを比較するかどうかを指定します。「テイクアウト」には、Telegramでの承認や、 サーバーで指定された待機時間が必要になる場合があります。これらのオプションは、再開後も固定されたままとなります。転送、再試行、信頼に関する詳細については、[「バックフィル動作」および 「証拠契約」](https://github.com/phishdestroy/TgWitness/blob/main/docs/BACKFILL.md)を参照してください。

## 一時停止、再開、および部分的な結果

- **「履歴の一時停止」**を選択すると読み取りが停止します。**「履歴の再開」を選択すると**、各ソースの最後にコミットされた メッセージから再開されます。アプリを再起動した場合も、再開されるまで実行は一時停止されたままとなります。 再開するには、同じ未使用の Telegram アカウントが必要です。
- メッセージの観測、添付ファイルの処理、カーソルのコミットが1つのトランザクションで行われます。 再開された実行では、すでにコミット済みの観測は繰り返されません。ライブキャプチャや 別途明示的に開始された実行では、同じメッセージを独立して観測することができます。
- 各ソース（Takeout 内の各 Telegram スプリット範囲）は、最初の読み取り時にメッセージ ID の上限を固定します。それより新しいメッセージは、 ライブ観測に属し、そのソースの残りの履歴ページには属しません。
- アクセスできないソースや、取得中に無効化されたソースは、 「失敗」または「スキップ」として表示されたままになります。その他のソースは処理が継続されますが、全体的な結果は不完全となります。
- FloodWait の遅延は、保存されたアカウントのバックオフ設定に従います。一時的な障害が発生した場合は最大 5回まで再試行します。リソースの枯渇やディスク容量不足の場合は、カーソルの位置を維持したまま一時停止します。
- **「この履歴の実行を終了」を選択すると**、保存された観測結果は保持されます。これによって観測結果が削除されたり、 標準APIの添付ファイル処理ジョブがキャンセルされたりすることはありません。「Takeoutを終了」を選択すると、残りのTakeout ファイルはスキップ済みとしてマークされます。一時停止を選択した場合は、それらの処理を再開可能です。新しい実行を開始すると、有効化されたソースが再度読み込まれます。

履歴の完了とは、履歴の読み取りのみを指します。添付ファイルは、処理待ちの状態のままとなる場合、 処理に失敗する場合、または設定されたポリシーによって除外される場合があります。ジャーナル および添付ファイルキュー内のメディア受信確認状況を確認してください。バイトデータが保持された完了済みの受信確認のみが、 保存された添付ファイルとみなされます。履歴操作は明示的なスナップショット要求であり、 将来のライブイベントのカテゴリを選択するスイッチとは別個のものです。

## 転送と検証

**署名済みの進捗レポート**を保存した後、**「証拠のエクスポート」**機能を使用して、 ジャーナルと保存された添付ファイルをダウンロードしてください。後に行われる証拠のエクスポートには追加の記録が含まれる場合がありますが、 レポートのカウンターは、作成時点のジャーナルプレフィックスに紐付けられています。 このバージョンの信頼できるチェックアウトから検証ツールを実行してください：

```
python tgwitness/verify.py tgwitness-history-report.json --evidence evidence.zip --fingerprint TRUSTED_FINGERPRINT
```

期待される署名鍵のフィンガープリントは個別に保持してください。検証ツールは、 レポートの署名、証拠アーカイブ、レポートのチェックポイント、ソースプラン、アカウント、 および保存済み／利用不可のメッセージ数をチェックします。新しい実行では、ソースの進行状況や オプションも署名付きカーソルイベントに紐付けられます。`--evidence` オプションを指定しない場合、 署名付きレポートとその内部の一貫性のみがチェックされます。従来の進行状況フィールドおよび添付ファイルの 要約は、引き続き署名付きコレクターステートメントとして扱われます。証拠検証ツールは、アーカイブされたメディアのバイトデータをチェックします。

利用可能な履歴への署名や完了処理を行っても、Telegram からの発信元、アトミックな スナップショット、または履歴の完全性が証明されるわけではありません。メッセージは閲覧中に変更される可能性があります。削除された メッセージや、「最近の操作」に表示されない中間的な編集、およびシークレットチャットは、 復元されません。署名鍵を管理する オペレーターは、外部へのコミットメントが存在する前にジャーナルを捏造する可能性があります。 文書化された 改ざん検出特性については、別途保持されたチェックポイントまたは独立した証人を使用してください。

取得カーソルはローカルワークスペースの状態を表します。証拠用ZIPファイルを復元しただけでは、 保留中の取得ジョブやTelegramセッションは復元されません。元のジョブを継続する必要がある場合は、 ワークスペースのバックアップを保管しておいてください。
