# รูปแบบหลักฐาน

Canonical page: https://phishdestroy.github.io/TgWitness/th/docs/reference/evidence/

เนื้อหาของไฟล์ ZIP ที่ลงนาม, ประเภทบันทึก, ใบยืนยันการดำเนินการ, โปรไฟล์ผู้ใช้, สำเนาที่เก็บไว้นอกระบบ และการตรวจสอบแบบออฟไลน์

TgWitness เก็บรักษาข้อมูลการสังเกต Telegram ที่ผู้ใช้งานสามารถเห็นได้ในบัญชีไว้ในสมุดบันทึกที่ลงนาม ผู้รับสามารถตรวจสอบบันทึก ไฟล์แนบ และรายงานที่เก็บไว้ โดยใช้ กุญแจผู้เก็บรวบรวมที่เชื่อถือได้ จากนั้นเปรียบเทียบสมุดบันทึกกับจุดตรวจสอบที่เก็บรักษาไว้อย่างอิสระ หน้านี้อธิบายรูปแบบ การตรวจสอบ และข้อมูลที่จำเป็นต้องเก็บรักษาไว้สำหรับการส่งต่อ

## อะไรคือ "ลงนาม"

| เนื้อหา | การป้องกัน | สิ่งที่ควรเก็บไว้ |
| --- | --- | --- |
| ทุกบันทึกในสมุดบันทึก รวมถึงเหตุการณ์การดำเนินงาน | โซ่ SHA-256 และลายเซ็น Ed25519 สำหรับแต่ละเหตุการณ์ | `events.jsonl` ดั้งเดิม, ลายนิ้วมือกุญแจที่เชื่อถือได้, และจุดตรวจสอบที่เก็บรักษาไว้ |
| เนื้อหาในไฟล์ ZIP ของหลักฐาน | `manifest.sig` ลงนามในไฟล์ manifest แบบมาตรฐาน ซึ่งระบุค่าแฮชของไฟล์เนื้อหา | ไฟล์ ZIP ฉบับสมบูรณ์ รวมถึงไฟล์ manifest และลายเซ็น |
| ไฟล์แนบที่เก็บรักษาไว้ | SHA-256 และจำนวนไบต์ในเหตุการณ์`media.saved`ที่ลงนาม; ค่าแฮชไฟล์ในไฟล์ ZIP manifest ที่ลงนาม | ข้อมูลต้นฉบับภายในไฟล์ ZIP ที่ได้รับการตรวจสอบแล้ว |
| จุดตรวจสอบ | ลายเซ็น Ed25519 ที่ครอบคลุมความยาวของบันทึก, ค่าแฮชส่วนหัว, กุญแจสาธารณะ และเวลาสร้าง | สำเนาอิสระที่เก็บไว้ก่อนการเปลี่ยนแปลงที่มีข้อโต้แย้ง |
| ใบเสร็จรับเงิน | บันทึกที่ลงนามของเวอร์ชันเครื่องมือเก็บข้อมูล, ค่าแฮชของไฟล์ต้นฉบับ และการตั้งค่าเริ่มต้น ซึ่งยังรวมอยู่ใน `process.started` | ใบรับ，บันทึกที่เกี่ยวข้อง และหลักฐานสภาพแวดล้อมสำหรับโหมดการตรวจสอบที่เลือก |
| รายงานที่อ่านได้: `report.html` และส่วนประกอบของมัน, `report.json`, `report.pdf`, `chat.pdf` | มีตราประทับ Ed25519 สำหรับแต่ละไฟล์ที่ครอบคลุมเนื้อหาของไฟล์นั้น; PDF ยังมาพร้อมกับลายเซ็นมาตรฐาน PDF (ดูรายงาน [Readable](https://phishdestroy.github.io/TgWitness/th/docs/reference/evidence/#readable-reports)) | ไฟล์ที่รับมาและลายนิ้วมือของกุญแจที่เชื่อถือได้; ไฟล์ ZIP ที่เอกสารนี้อธิบาย |
| CSV แบบสแตนด์อโลน | ไม่มีลายเซ็นเข้ารหัสแบบสแตนด์อโลน; การใช้แฮชของเหตุการณ์เพียงอย่างเดียวไม่เพียงพอ | ใช้สำเนาที่อยู่ในไฟล์ ZIP ที่ได้รับการตรวจสอบแล้วเพื่อตรวจสอบความสมบูรณ์ |
| ภาพหน้าจอ, เอกสารพิมพ์ หรือไฟล์ PDF ที่สร้างขึ้นจากเบราว์เซอร์ | ไม่มีลายเซ็นของ TgWitness บนเวอร์ชันที่ดัดแปลง | เก็บรักษาแพ็กเกจต้นฉบับที่ได้รับการตรวจสอบแล้ว และบันทึกวิธีการสร้างเวอร์ชันที่ดัดแปลง |

Collector จะตรวจสอบลายเซ็นของบันทึกก่อนที่จะสร้างทุกรูปแบบการส่งออก รายงาน HTML และ PDF ที่อ่านได้จะมีตราประทับของตัวเอง; ไฟล์ CSV แบบสแตนด์อโลนจะถูกตรวจสอบเป็นส่วนหนึ่งของ ZIP ที่ลงนาม เก็บ ZIP ไว้เพื่อรักษาไบต์ของไฟล์แนบและ manifest และใช้จุดตรวจสอบแยกต่างหากเพื่อตรวจสอบบันทึกกับขอบเขตก่อนหน้า

## การส่งต่อคดี

1. บันทึกหมายเลขอ้างอิงคดี ผู้ดำเนินการ ID บัญชี Telegram แบบตัวเลข แหล่งข้อมูลที่เลือก นโยบายการเก็บรวบรวม และช่วงเวลาการเก็บรวบรวมไว้ในบันทึกคดีของคุณ TgWitness เก็บรักษาข้อมูลการสังเกตการณ์ และสนับสนุนการบันทึกและเก็บรวบรวมข้อมูลที่เชื่อมโยงกับแหล่งข้อมูลใน [Case Board](https://phishdestroy.github.io/TgWitness/th/docs/reference/case-board/) เก็บบันทึกการโอนย้ายและการดูแลรักษาไว้พร้อมกับ เอกสารคดีของคุณ ตรวจสอบการตั้งค่าการเก็บรวบรวมที่ตั้งใจไว้กับ [ขั้นตอนการรับข้อมูลแบบเรียลไทม์](https://github.com/phishdestroy/TgWitness/blob/main/docs/internal/LIVE_ACCEPTANCE.md)
2. เก็บลายนิ้วมือกุญแจสาธารณะของพื้นที่ทำงานไว้อย่างอิสระก่อนที่จะพึ่งพา ข้อมูลที่ส่งออกจากระบบนั้น บันทึกจุดตรวจสอบที่ลงนามไว้ภายนอกตัวเก็บข้อมูลระหว่างการเก็บข้อมูล บันทึกการหยุดชะงักและข้อจำกัดของขอบเขตการมองเห็นของบัญชี
3. ส่งออกไฟล์ **ZIP ที่มีลายเซ็น**และเก็บใบเสร็จการรันที่มีลายเซ็นไว้ ใช้จุดตรวจสอบ (checkpoint) ที่ หรือก่อนขอบเขตของบันทึกที่ส่งออก จุดตรวจสอบที่ตั้งไว้ภายหลังสามารถปฏิเสธ การส่งออกก่อนหน้านี้ได้อย่างถูกต้อง เนื่องจากมีความยาวไม่เพียงพอ การส่งออกจะรวมบันทึกพื้นที่ทำงานทั้งหมด โดยไม่คำนึงถึงตัวกรองของแผงควบคุม; ตรวจสอบเนื้อหาให้ละเอียดก่อนที่จะแบ่งปัน
4. ให้ผู้รับตรวจสอบไฟล์ ZIP ด้วยเวอร์ิไฟเออร์ที่เชื่อถือได้และ ลายนิ้วมือ/จุดตรวจสอบที่จัดหาอย่างอิสระ จากระบบที่เชื่อถือได้ซึ่ง มีสภาพแวดล้อม Python ที่กำลังทำงานอยู่:

   ```
   python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --checkpoint retained-checkpoint.json
   ```

   รายงานผลลัพธ์ที่สำเร็จจะแสดง `key_pinned: true` และ `checkpoint_checked: true` เมื่อมีการป้อนข้อมูลทั้งสองและได้รับการยอมรับแล้ว ให้เก็บรักษาผลการตรวจสอบไว้

   ```
   For a handover requiring the final exported record to be witnessed, use
   `--witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness`.
   This refuses an export with an unwitnessed tail. See the
   [witness handover procedure](WITNESS.md#require-a-witnessed-export-boundary).
   ```

   1. บันทึก SHA-256 ของไฟล์เก็บถาวร ขอบเขตการส่งออก วันที่ส่ง ผู้ส่ง และ ผู้รับไว้ในบันทึกการเก็บรักษาของคุณ รักษาแพ็กเกจต้นฉบับให้สมบูรณ์และทำงาน จากสำเนาเท่านั้น แบ่งปันไฟล์หลักฐานแทนที่จะแบ่งปันไดเรกทอรีข้อมูลส่วนตัวของแอปพลิเคชัน ซึ่งยังเก็บข้อมูลเซสชันบัญชีและข้อมูลลับสำหรับการลงนามด้วย สำหรับการส่งต่อ สามารถนำไฟล์ที่ส่งออกใส่ใน ZIP ที่ได้รับการป้องกันด้วยรหัสผ่าน AES-256 ได้ รหัสผ่าน นี้ใช้เพื่อรักษาความลับเท่านั้น และไม่ถูกเก็บไว้; ผู้รับจะทำการแตกไฟล์ และตรวจสอบไฟล์ส่งออกที่ลงนามภายใน ซึ่งไม่มีการเปลี่ยนแปลงใดๆ
   2. หากจำเป็นต้องกำหนดเวลาอย่างอิสระ ให้ปฏิบัติตาม [ขั้นตอนตาม RFC 3161](https://phishdestroy.github.io/TgWitness/th/docs/reference/timestamp/) และเก็บรักษาคำขอ จุดตรวจสอบ ข้อมูล CA ที่เชื่อถือได้ และคำตอบจากหน่วยงานที่มีอำนาจที่ได้รับการยืนยัน การเตรียมคำขอเพียงอย่างเดียว ไม่สามารถได้รับเวลาประทับได้

การตรวจสอบที่สำเร็จจะยืนยันความสมบูรณ์ของข้อมูลเมื่อเทียบกับ กุญแจผู้เก็บข้อมูลที่เชื่อถือได้และขอบเขตที่เก็บรักษาไว้ ดู[ขอบเขตการตรวจสอบ](https://phishdestroy.github.io/TgWitness/th/docs/reference/evidence/#verification-scope)เพื่อทราบ สมมติฐานความเชื่อถือและ[ผลการตรวจสอบ](https://phishdestroy.github.io/TgWitness/th/docs/reference/verification/)สำหรับการตรวจสอบที่ดำเนินการ

## ส่วนสรุปการส่งมอบ

ไฟล์ ZIP ที่ลงนามจะบรรจุบันทึกพื้นที่ทำงานทั้งหมด เมื่อศาล ทนายความ หรือศูนย์รับเรื่องร้องเรียนต้องการ เพียงบางส่วนของการสนทนา ช่วงระยะเวลา หรือบุคคลเฉพาะบางราย การเลือก "**Exports → Handover extract**" จะสร้างสำเนาที่ถูกลดขนาด (`tgwitness-handover-v1`) ตามกฎการเปิดเผยข้อมูลที่เลือกไว้ ผู้ดำเนินการจะระบุวัตถุประสงค์และเลือกการสนทนา ช่วงระยะเวลา (UTC) (ตามความจำเป็น) ผู้ที่เกี่ยวข้อง กับข้อมูลที่สกัด รวมถึงการจัดการกับผู้อื่นๆ (แสดงไว้, แทนที่ด้วยชื่อปลอม P01, P02… หรือไม่รวม ไว้), ข้อความใดจะคงอยู่, ไฟล์แนบและรูปโปรไฟล์ใดจะถูกรวมไว้, และว่า หมายเลขโทรศัพท์และที่อยู่อีเมลในข้อความจะถูกปิดบังหรือไม่ วัตถุประสงค์และกฎเหล่านี้จะปรากฏใน manifest ที่ลงนามและในรายงาน; บันทึกกิจกรรมจะบันทึก`handover.exported` พร้อมข้อมูลการเข้าถึงของ ผู้เตรียมไฟล์และค่า SHA-256 ของไฟล์ ไม่ใช่เนื้อหาของไฟล์

`verify.py` ตรวจสอบข้อมูลที่สกัดออกมาด้วยสองวิธี บันทึกที่แสดงว่าไม่มีการเปลี่ยนแปลงจะได้รับการตรวจสอบอย่างครบถ้วน: เนื้อหาเทียบกับค่าแฮช ลายเซ็น Ed25519 และลิงก์ไปยังบันทึกก่อนหน้าที่มีอยู่ บันทึก ที่ถูกลดขนาดจะเก็บค่าแฮชและลายเซ็นต้นฉบับไว้ ดังนั้นลายเซ็นจึงยังคงผ่านการตรวจสอบได้ แต่ สนามที่ถูกระงับไม่สามารถคำนวณใหม่ได้จากข้อมูลนั้น; บันทึกจะระบุสิ่งที่ถูกระงับและรายงาน จะหมายเหตุไว้ ไฟล์ manifest จะระบุความยาวของบันทึกและส่วนหัว พร้อมลายเซ็นของผู้เก็บข้อมูลบน ส่วนหัวนั้น และนับจำนวนบันทึกที่ถูกตัดออก; `coverage.json` อธิบายการสนทนาที่เลือกไว้ ชื่อภายใน ชื่อไฟล์จะไม่ถูกตรวจพบ ตรวจสอบไฟล์สุดท้ายก่อนแบ่งปัน: ข้อความอิสระ ชื่อไฟล์ และ ไฟล์แนบที่เลือกไว้ ยังสามารถระบุตัวบุคคลได้ เก็บ ZIP ที่ลงนามไว้อย่างครบถ้วน: ไฟล์ที่สกัดออกมาถือเป็นการเปิดเผยข้อมูล ไม่ใช่การแทนที่

## รายงานที่อ่านได้

หลักฐานที่ลงนาม, การส่งต่อ และไฟล์ ZIP ของการสนทนา ประกอบด้วยรายงาน HTML และ JSON ที่อ่านได้ รวมถึง ไฟล์ PDF เมื่อมีฟอนต์ที่จำเป็น ในภาษาของรายงานที่เลือกไว้ รายงานแต่ละ ฉบับถูกล็อกด้วยกุญแจ Ed25519 ของพื้นที่ทำงาน และสามารถตรวจสอบได้แยกกัน: `python -m tgwitness.verify FILE --fingerprint KEY [--evidence ZIP]`.

- `report.html` / `chat.html`: คำประกาศการปิดผนึก (`tgwitness-report-seal-v1`) ปิดไฟล์และ ลงนามใน SHA-256 ของทุกไบต์ที่อยู่ก่อนหน้านั้น บันทึกและบทสนทนาที่ยาวจะถูกแบ่งออกเป็นส่วนๆ ที่มี ขนาดที่สามารถกำหนดได้ (การตั้งค่าการรายงาน, 500 ถึง 100,000 รายการ; ค่าเริ่มต้นคือ 5,000): `records/records-0001.html` หรือ `messages/messages-0001.html` โดยแต่ละส่วนถูกลงนามด้วยหมายเลข ช่วง และจำนวนรวม และถูกระบุพร้อมกับ SHA-256 ของมันใน manifest ที่ถูกลงนาม การส่งสัญญาณชีพของ collector จะแสดงเป็นบรรทัดเดียว เว้นแต่การตั้งค่า Report จะกำหนดให้แสดงทีละรายการ
- `report.json` (`tgwitness-report-json-v1`, keys `format`, `report`, `seal`): ลายเซ็นนี้ลงนามใน SHA-256 ของ JSON แบบมาตรฐานของ `report` ดังนั้นข้อมูลจึงสามารถอ่านได้โดยระบบตัวอักษรและสคริปต์ และสามารถเลือกข้อมูลเพื่อคุ้มครองข้อมูลจากข้อมูลเหล่านั้นได้ ในขณะที่ไฟล์ที่ลงนามยังคงครบถ้วน
- `report.pdf` / `chat.pdf`: เอกสารอย่างเป็นทางการสำหรับการพิมพ์และจัดเก็บ, ลงนามสองครั้งบน ไบต์เดียวกัน, ไฟล์ทั้งหมดยกเว้นค่าลายเซ็น (`/ByteRange`). ลายเซ็นมาตรฐาน PDF (`adbe.pkcs7.detached`, CMS พร้อม SHA-256 และ ECDSA P-256) ใช้เอกสารลงนามที่ออกเอง ที่เก็บไว้ในคลังพื้นที่ทำงาน; หมายเลขซีเรียลของหัวข้อคือลายนิ้วมือกุญแจ Ed25519 ตราประทับ Ed25519 เคลื่อนที่ภายใน CMS ในฐานะแอตทริบิวต์ที่ยังไม่ได้ลงนาม `2.25.240684792623320047764573196045913242332` และระบุชื่อใบรับรอง SHA-256 ด้วย `"content": "pdf-byte-range"` ดังนั้นกุญแจ Ed25519 จึงรับรองความถูกต้องของใบรับรอง เครื่องอ่านPDF จะแสดง ว่าไฟล์มีการเปลี่ยนแปลงหลังการลงนามหรือไม่ และจะระบุผู้ลงนามว่าเป็น "ไม่ทราบ" จนกว่าใบรับรองจะ ได้รับการเชื่อถือ; ให้เปรียบเทียบลายนิ้วมือEd25519 แทน PDF ภาษาจีน ญี่ปุ่น และเกาหลีจำเป็นต้องมีฟอนต์ บนเซิร์ฟเวอร์ (หรือใน`TGWITNESS_FONT_DIR`); หากไม่มี ZIP จะนำรายงานHTML และJSON มาด้วยเท่านั้น

ในช่องหรือกลุ่มใหญ่ Telegram จะจัดลำดับข้อความ 1, 2, 3… ตามลำดับ การส่งออกบทสนทนาจะแสดง หมายเลขแรกและหมายเลขสุดท้าย จำนวนข้อความที่มีอยู่ และทุกช่วงของหมายเลขที่ขาดหายไปใน `message-ids.json` , รายการเนื้อหา (manifest) และส่วนหัว (header) ของ `chat.json` พร้อมทั้งทำเครื่องหมายช่องว่างแต่ละจุดที่ปรากฏใน บันทึกการสนทนา `verify.py` นับหมายเลขต่อจาก `chat.json` หมายเลขที่ขาดหายไปคือข้อความที่ Telegram ไม่ได้ส่งกลับมา (ถูกลบก่อนการส่งออก หรือไม่ปรากฏต่อบัญชี); ในแชทส่วนตัวและ กลุ่มพื้นฐาน หมายเลขจะถูกใช้ร่วมกันในทุกแชทของบัญชี และช่องว่างจะไม่ถูกนับ

หลังจากอ่านประวัติแล้ว กระบวนการส่งออกจะขอข้อมูลจาก Telegram สำหรับทุกหมายเลขที่ยังขาดอีกครั้ง โดยระบุตามหมายเลข (`channels.getMessages`, สูงสุด 10,000 หมายเลข) ผลลัพธ์จะอยู่ใน `message-ids.json` และในรายงาน คำตอบที่ว่างจะบันทึกว่าหมายเลขดังกล่าวไม่สามารถติดต่อได้กับบัญชีนี้ ณ เวลาตรวจสอบซ้ำ； โดยไม่ระบุสาเหตุ．ข้อความที่ส่งกลับมาในการตรวจสอบซ้ำจะถูกเพิ่มเข้าไปในไฟล์ส่งออก และถูกทำเครื่องหมาย `found_on_recheck`．

ทุกรายงานจะเริ่มต้นด้วย **โดยสรุป**: หนึ่งย่อหน้า ตามด้วยสิ่งที่ข้อมูลแสดงและสิ่งที่มันไม่แสดง (ผู้อยู่เบื้องหลังบัญชี, ความครบถ้วนของการส่งข้อมูล, การลบข้อมูลก่อนการสังเกต, เวลาตามนาฬิกา โดยไม่มีตราประทับเวลา). ตราประทับของหน้าเว็บจะเปลี่ยนเป็นสีเหลืองอำพันเมื่อเบราว์เซอร์ตรวจสอบลายเซ็นของตราประทับ ไม่ใช่ของหน้าเว็บ: เบราว์เซอร์ไม่ส่งข้อมูลไบต์ของหน้าเว็บนั้นเอง มันจะเปลี่ยนเป็นสีเขียวเฉพาะเมื่อ ผู้อ่านนำไฟล์ไปตรวจสอบที่ส่วนท้ายของหน้า และทุกไบต์ตรงกัน และเฉพาะเมื่อ หน้าที่แสดงคือไฟล์นั้นเอง; มิฉะนั้นมันจะเปลี่ยนเป็นสีแดง

รายงานแต่ละฉบับระบุชื่อโปรแกรมอย่างแม่นยำ: git commit เมื่อตัวเก็บข้อมูลทำงานจาก checkout หรือ เมื่อตัวติดตั้งตั้งค่า `TGWITNESS_COMMIT` และ SHA-256 ของไฟล์ต้นฉบับ (`source_tree_sha256`, JSON แบบมาตรฐานของ path → SHA-256 ของทุกไฟล์ `.py`, `.js`, `.css`, `.html` และ `.svg` ใน แพ็กเกจ), ซึ่งการ checkout ของ commit ดังกล่าวจะสร้างซ้ำได้ เว้นแต่ไฟล์จะถูกเปลี่ยนแปลง Telegram ถูกตั้งชื่อตามไลบรารี ชั้น API และศูนย์ข้อมูล เมื่อการสังเกตการณ์เริ่มขึ้น และเมื่อการส่งออกแชท เริ่มและสิ้นสุด ผู้เก็บข้อมูลจะขอเวลาจาก Telegram (`updates.getState`, วินาทีเต็ม ) และบันทึกเวลาของ Telegram ลบด้วยนาฬิกาของผู้เก็บข้อมูล พร้อมกับความไม่แน่นอนจาก การส่งข้อมูลไป-กลับ; รายงานจะแสดงการวัดค่าเหล่านี้ภายใต้ส่วน Chain of custody การส่งออกแชทยังบันทึก เวลาที่อ่านประวัติด้วย นอกเหนือจากวันที่ของข้อความ

### คู่มือการดูรายงานและเก็บถาวรแบบออฟไลน์

โปรดแตกไฟล์ ZIP ทั้งหมดก่อนเปิด `chat.html` หรือ `report.html` โปรแกรมดูนี้ให้ฟังก์ชันการค้นหา, ตัวกรอง, ผู้เข้าร่วม, ตัวชี้วัด, รายละเอียดบันทึก และการเลือก JSON/CSV โดยไม่ต้องใช้เซิร์ฟเวอร์ โปรดเก็บ `viewer/` และ `media/` ไว้ข้างรายงาน การเลือกเป็นข้อมูลที่สร้างขึ้นจากต้นฉบับ: ใช้ `verify.py SELECTION.json
--evidence ARCHIVE.zip` เพื่อเปรียบเทียบกับไฟล์เก็บถาวรที่ลงนามแล้ว โปรแกรมตรวจสอบจะตรวจสอบ ID รายงาน, กุญแจลงนาม, ขอบเขตไฟล์เก็บถาวร และทุกรายการที่เลือก; รายการที่แก้ไขแล้ว, ขาดหายไป หรือซ้ำกันจะไม่ผ่านการตรวจสอบ หมายเหตุการเลือกและเวลาสร้างยังคงเป็นข้อมูลเมตาที่ไม่ได้รับการลงนาม

ช่องว่างระหว่างหมายเลขข้อความจะแสดงขึ้นเฉพาะในฟีดการสนทนาที่เรียงตามลำดับขึ้นและไม่ผ่านการกรองเท่านั้น การซ่อน หมวดหมู่หรือการไม่สามารถโหลดข้อมูลส่วนหนึ่งได้ ไม่ควรทำให้แถวที่ถูกข้ามไปกลายเป็นหลักฐานว่าข้อความนั้น หายไป การเน้นผลการค้นหาทำงานบนข้อความธรรมดา ก่อนการเข้ารหัสHTML โดยรักษาเครื่องหมายแท็กไว้ตามเดิม

เบราว์เซอร์จะตรวจสอบลายเซ็นของไฟล์แมนิเฟสต์, ID และกุญแจของรายงาน, รวมถึงค่าแฮชของไฟล์ทั้งหมดที่ระบุไว้ มัน จะปฏิเสธโครงสร้าง ZIP ที่ไม่ชัดเจนหรือผิดรูปแบบ, ชื่อที่ซ้ำกัน และเส้นทางที่ไม่ปลอดภัย, พร้อมทั้งจำกัดขนาดไฟล์ สูงสุดที่ 256 MiB และขนาดเนื้อหาทั้งหมดที่ประกาศไว้สูงสุดที่ 4 GiB สำหรับไฟล์อาร์ไคฟ์ที่มีขนาดใหญ่กว่า ให้ใช้ตัวตรวจสอบแบบสแตนด์อโลน การตรวจสอบของเบราว์เซอร์นี้เสริมการตรวจสอบของเครื่องมือตรวจสอบเกี่ยวกับโซ่บันทึก (journal chains) และความหมายของข้อมูล

`README.txt` ประกอบด้วยคู่มือเริ่มต้น รายการไฟล์ที่จัดเรียงให้ตรงกัน คำแนะนำการตรวจสอบ และ หมายเหตุเกี่ยวกับรูปแบบข้อมูลในภาษาของรายงาน ตามด้วยคู่มือภาษาอังกฤษฉบับสมบูรณ์ `SHA256SUMS` ครอบคลุม ไฟล์ที่ระบุไว้ภายในไฟล์นี้ โดยไม่รวมไฟล์นี้เอง `manifest.json` และ `manifest.sig`; รายการไฟล์ที่ลงนาม ยังครอบคลุม `SHA256SUMS` ด้วย ให้เก็บ ZIP ต้นฉบับไว้โดยไม่เปลี่ยนแปลง และบันทึกไฟล์ทำงานไว้ภายนอก โฟลเดอร์ที่แตกไฟล์ออกมา รายงาน PDF มีเครื่องหมายบุ๊กมาร์กสำหรับแต่ละส่วน และข้อมูลระบุกรณี/รายงานในหน้าถัดไป

### การสนทนา ณ เวลาส่งออก

การส่งออกแชทบันทึกข้อมูลที่ Telegram ระบุเกี่ยวกับแชทเมื่อเริ่มการส่งออก: ป้ายกำกับของ Telegram เอง (`scam`, `fake`, `restricted` พร้อมเหตุผล, `verified`), ชื่อผู้ใช้, คำอธิบาย, จำนวน สมาชิกและผู้ดูแลระบบ, การสนทนาที่เชื่อมโยง, การป้องกันเนื้อหา, ว่าสมาชิกใหม่สามารถเห็นข้อความก่อนหน้า ได้หรือไม่ และข้อความใดในบัญชีนี้ที่เริ่มแสดงประวัติ (`available_min_id`), วันที่ ของข้อความที่ 1 เมื่อเป็นวันที่สร้างห้องสนทนา และ SHA-256 ของรูปภาพห้องสนทนา (เก็บไว้ใน `media/`) ระบบบันทึกตำแหน่งของบัญชีผู้ส่งออกในห้องสนทนา: บทบาท, วันที่เข้าร่วม, ผู้เชิญ และสำหรับ ผู้ดูแลระบบ, สิทธิ์ของมัน หากคำขอ Telegram ถูกปฏิเสธ จะระบุชื่อคำขอที่ถูกปฏิเสธแทน

เมื่อบัญชีที่ส่งออกเป็นแอดมิน การส่งออกจะอ่านบันทึกแอดมินของแชท (Telegram เก็บไว้ประมาณ 48 ชั่วโมง) เข้าสู่ `admin-log.json`: การลบและการแก้ไขพร้อมเนื้อหาและบัญชีที่ดำเนินการ นี่คือบันทึกเดียวของการลบที่ระบุชื่อผู้ลบ

### ตัวชี้วัด

รายการรายงานและไฟล์เก็บถาวรมีชื่อเป็น `indicators.csv` , `indicators.stix.json` (STIX 2.1 ) และ `indicators.misp.json` (เหตุการณ์ MISP ), ซึ่งทีมรับมือการละเมิดสามารถดำเนินการได้จากข้อความที่บันทึกไว้: ลิงก์และโดเมน (รวมถึงที่ซ่อนอยู่หลังข้อความ ในปุ่ม และในตัวอย่างลิงก์), ที่อยู่สกุลเงินดิจิทัล Telegram ชื่อผู้ใช้และลิงก์เชิญ, หมายเลขโทรศัพท์, ที่อยู่อีเมล และรูปภาพที่บันทึกไว้ ที่อยู่ Bitcoin, Litecoin, Dogecoin และ TRON จะถูกแสดงเฉพาะเมื่อ checksum base58 ของมันถูกต้อง, ที่อยู่ segwit เมื่อ checksum bech32 หรือ bech32m ของมันถูกต้อง และที่อยู่ TON เมื่อ CRC ของมันถูกต้อง; ที่อยู่ EVM และ Solana ถูกทำเครื่องหมายว่าไม่ได้รับการตรวจสอบ รูปภาพมีรหัส SHA-256 และค่าแฮชเชิงการรับรู้ (dHash, 64 บิต) ที่สำเนาที่ถูกบีบอัดใหม่หรือปรับขนาดใหม่จะคงค่าไว้เกือบไม่เปลี่ยนแปลง รายงานจะเขียน ตัวชี้วัดเพื่อไม่ให้เปิดโดยไม่ได้ตั้งใจ (`hxxps[://]example[.]com` ); ไฟล์จะคง ค่าไว้ตามเดิม ทุกตัวชี้วัดถูกทำเครื่องหมายว่าไม่ทราบและไม่ใช้สำหรับการตรวจจับอัตโนมัติ (STIX `indicator_types: unknown` , MISP `to_ids: false` , การแจกจ่ายไปยังองค์กรของตนเอง): การ ปรากฏในรายการหมายความว่าข้อความนั้นมีตัวชี้วัดดังกล่าวอยู่ ไม่ใช่ว่ามันเป็นอันตราย ลิงก์ที่มีข้อความแสดง ที่อยู่ต่างจากที่อยู่จริงเมื่อเปิดจะถูกทำเครื่องหมายในรายงาน

รายงานPDF จบลงด้วยคำประกาศของผู้ตรวจสอบที่ต้องลงลายมือชื่อด้วยตนเอง, รายการตรวจสอบสำหรับผู้รับรองเอกสารหรือ ผู้เชี่ยวชาญของศาล, และรหัส QR (ซึ่งปรากฏบนหน้าแรกด้วย) ที่มีรหัสประจำรายงาน, ลายนิ้วมือของกุญแจ และ SHA-256 ของข้อมูลที่เชื่อถือได้ เพื่อให้การพิมพ์ออกมาสามารถติดตามกลับไปยังคลังข้อมูลต้นฉบับได้

## การกำหนดรูปแบบมาตรฐานของเหตุการณ์

ข้อมูลแฮชที่ป้อนเข้าประกอบด้วยสนามต่อไปนี้เท่านั้น:

```
seq, observed_at, source_at, kind, chat_id, message_id, actor_id, payload, previous_hash
```

จัดเรียงเป็นลำดับโดยใช้ JSON ที่เข้ากันได้กับ Python ด้วย UTF-8, คีย์วัตถุที่เรียงลำดับ, ไม่มีการหลบหลีก ASCII ไม่มีช่องว่างที่ไม่สำคัญ และไม่มี NaN/infinity:

```
json.dumps(value, ensure_ascii=False, sort_keys=True,
           separators=(",", ":"), allow_nan=False).encode("utf-8")
```

SHA-256 ของไบต์เหล่านั้นจะกลายเป็นแฮชของเหตุการณ์ ลายเซ็นคือ Ed25519 ที่คำนวณจาก 32 ไบต์แฮชดิบ จากนั้นเข้ารหัสด้วย base64 ค่า previous_hash แรกคือ 64 ตัวศูนย์ หมายเลขลำดับเริ่มต้นที่ 1 และเพิ่มขึ้นทีละ 1 ทุกเหตุการณ์ รวมถึงเหตุการณ์ ปฏิบัติการ ใช้โซ่เดียวกัน ไม่มีการระงับการส่งซ้ำ: การสังเกต ซ้ำเป็นใบรับที่แยกกัน ไม่ใช่การอ้างว่าเป็นการกระทำของ Telegram ที่แยกกัน

ข้อมูลวันที่ Telegram แบบดิบเป็นสตริง ISO; สนามข้อมูลแบบไบนารีจะกลายเป็นอ็อบเจกต์ที่ประกอบด้วย bytes_base64 ข้อความข้อความ, เอนทิตี, ตัวอธิบายสื่อ, เมตาดาต้าการตอบกลับ, ปฏิกิริยา, และปฏิบัติการของบริการจะถูกเก็บรักษาไว้ในเมตาดาต้าข้อความแบบดิบเมื่อมีข้อมูลดังกล่าว

observed_at คือเวลา UTC ตามนาฬิกาของระบบเก็บข้อมูล source_at คือวันที่จาก Telegram เมื่อมีข้อมูล การแจ้งเตือนการลบไม่ระบุเวลาลบที่แม่นยำ ดังนั้น source_at จึงยังคงเป็นค่าว่าง ลำดับการรับข้อมูลจากระบบขนส่งไม่จำเป็นต้องเป็นลำดับเหตุการณ์ จากแหล่งข้อมูล ภาพถ่ายประวัติใช้วันที่จากแหล่งข้อมูลที่เก่ากว่า แต่ใช้เวลาการสังเกตการณ์ปัจจุบัน

## ความหมายของตัวแสดง

message.new actor_id คือผู้ส่งข้อความ message.edited ไม่มี ผู้แก้ไขที่คาดการณ์ได้ payload.sender_id บันทึกผู้ส่งของข้อความที่สังเกตได้ การลบ actor_id ยังคงเป็น null ข้อความจากบริการสมาชิกจะเก็บรักษาผู้ส่งและประเภทการดำเนินการ ไว้ โดยไม่แปลงการลบทุกครั้งเป็นการออกจากกลุ่มโดยสมัครใจ การอัปเดตผู้เข้าร่วมแบบดิบ จะเก็บรักษา actor_id ตามที่ระบุไว้ ภาพถ่ายปฏิกิริยาจะไม่สร้างผู้ดำเนินการเปลี่ยนแปลงขึ้นมา

การแจ้งเตือนการลบสำหรับแชทส่วนตัวและกลุ่มทั่วไปมีเพียง ID ของข้อความเท่านั้น แชทเหล่านั้นใช้ลำดับ ID เดียวกันสำหรับทั้งบัญชี ดังนั้น ID หนึ่งจึงระบุข้อความเดียวของ บัญชีนี้ เมื่อข้อความที่มี ID ดังกล่าวถูกบันทึกไว้ในสมุดบันทึกนี้ก่อนหน้านี้แล้ว การลบข้อความจะถูกบันทึกในแชทนั้นเป็น message.deleted โดยใช้ payload.chat_resolution เป็นชื่อของเมธอด ID ที่ไม่เคยถูกบันทึกไว้จะถูกเก็บไว้เป็น deletion.unscoped โดยไม่มี chat_id; ไม่มีการคาดเดาใดๆ ช่อง (Channels) และกลุ่มใหญ่ (supergroups) นับข้อความตามแต่ละแชท และ ไม่เคยถูกจับคู่ด้วยวิธีนี้ เมื่อข้อความที่ถูกลบถูกส่งโดยบัญชีที่ถูกสังเกต payload.deleted_message_was_outgoing จะมีค่าเป็น true; แต่ผู้ลบข้อความยังไม่ถูกระบุ

## เนื้อหาที่ครอบคลุม: ความต่อเนื่อง ช่องว่าง และ ID ที่ไม่ถูกตรวจพบ

ทุกไฟล์ ZIP ที่ลงนามจะมีรหัส `coverage.json` รายงาน HTML จะเปิดด้วยบทสรุปเดียวกัน และ `verify.py` จะคำนวณใหม่จาก `events.jsonl` แทนที่จะเชื่อถือไฟล์ดังกล่าว:

- **ถูกสังเกตอย่างต่อเนื่องจาก X ถึง Y** ช่วงหนึ่งเริ่มต้นด้วย `observation.started` และ สิ้นสุดเมื่อมีการหยุดชั่วคราว การหยุด การสูญเสียการเชื่อมต่อ Telegram การออกจากระบบ การเริ่มกระบวนการโดยไม่ มีการหยุดอย่างเป็นระเบียบ หรือไม่มีบันทึกใดๆ เป็นเวลามากกว่าสามนาทีระหว่างการสังเกต (สัญญาณชีพถูกบันทึกทุกนาที ดังนั้นความเงียบหมายความว่ากระบวนการหยุดลง แช่แข็ง หรือ คอมพิวเตอร์เข้าสู่โหมดสลีป) เมื่อช่วงเวลาสัญญาณชีพถูกปรับเปลี่ยนใน**ส่วนพารามิเตอร์** แต่ละสัญญาณชีพ จะบันทึกการเปลี่ยนแปลงนี้ และช่วงเวลาความเงียบที่อนุญาตจะกลายเป็นสามช่วงเวลา โดยไม่เคยน้อยกว่าสามนาที
- **ช่องว่าง**จะแสดงช่วงเวลาที่ขาดหายไปพร้อมเหตุผล ช่องว่างที่ยังคงเปิดอยู่ ณ บันทึกสุดท้าย จะถูกทำเครื่องหมายว่า `not_resumed_by_last_record`
- **ID ข้อความที่ไม่ได้สังเกตเห็น** สำหรับช่องและกลุ่มซูเปอร์ ซึ่งนับจำนวนข้อความต่อ การสนทนา ID ที่ขาดหายไประหว่างข้อความที่สังเกตเห็นจะถูกรายการเป็นช่วง (range) และถูกรายงานว่า *“ไม่ได้สังเกตเห็น*” — ซึ่งอาจหมายถึงถูกลบ ไม่เคยส่งถึงผู้รับ หรืออยู่นอกประวัติที่บันทึกไว้ — แต่ไม่เคยถูกรายงานว่า “ถูกลบ” การสนทนาส่วนตัวและกลุ่มทั่วไปใช้ลำดับหมายเลขเดียวกันสำหรับบัญชีทั้งหมด ดังนั้นช่องว่างภายใน การสนทนาประเภทนี้จึงไม่มีความหมายและไม่ถูกรายการไว้ที่นั่น
- การแจ้งเตือนช่องว่างระดับแชท (เช่น Telegram ที่ขอการกู้คืนความแตกต่างใน ช่องหนึ่ง) จะถูกนับเป็นบันทึก; สิ่งเหล่านี้ไม่ขัดขวางการครอบคลุมโดยรวม

### หมายเลขข้อความที่ขาด (`gap_summary`)

**ดูตัวอย่าง.** `coverage.json` → `gap_summary` วัดหมายเลขที่ Telegram กำหนดและ ตัวเก็บข้อมูลนี้ไม่เคยเห็น Telegram กำหนดหมายเลขให้ข้อความครั้งเดียวต่อช่องหรือกลุ่มซูเปอร์ และครั้งเดียวต่อ บัญชีในแชทส่วนตัว บอท และกลุ่มทั่วไป หมายเลขระหว่างข้อความที่สังเกตได้ สองข้อความนั้นอาจถูกสังเกตได้หรือขาดหายไป ช่วงที่ต่อเนื่องกันเป็นคำยืนยันเชิงบวกว่า ทุกข้อความที่มีหมายเลขในช่วงนั้นถูกสังเกตได้ ช่องว่างไม่ระบุผู้กระทำหรือเหตุผลใดๆ

| Field | ความหมาย |
| --- | --- |
| `status` | `on`, หรือ `off` เมื่อปิดใน **Parameters → Gap analysis** |
| `parameters` | พารามิเตอร์ที่สร้างผลลัพธ์ดังกล่าว เพื่อให้สามารถทำซ้ำได้ |
| `chats[]` | บันทึกหนึ่งรายการต่อช่องหรือกลุ่มใหญ่ โดยแต่ละรายการมีหมายเลขเฉพาะตัว |
| `account` | ลำดับการสนทนาส่วนตัว บอท และกลุ่มทั่วไปในบัญชีทั้งหมด |
| `status` (ตามลำดับ) | `applicable`, หรือ `not_applicable` ด้วย `reason` |
| `observed_from`, `observed_to`, `span` | หมายเลขแรกและหมายเลขสุดท้ายที่สังเกตได้ รวมถึงขนาดของช่วง |
| `observed`, `observed_without_content` | ตัวเลขที่สังเกตได้; ตัวเลขที่ทราบได้เฉพาะจากบันทึกการลบหรือการตรวจสอบซ้ำ |
| `missing`, `density`, `gap_ranges`, `largest_gap` | ตัวเลขที่ยังไม่เคยถูกสังเกต, สัดส่วนของช่วงค่า, จำนวนรอบการรัน, รอบการรันที่ยาวที่สุด |
| `clusters[]` | ช่องว่างที่ระบุไว้: `low`, `high`, `missing`, และตัวเลขที่สังเกตได้ใกล้เคียง `after` / `before` พร้อมเวลาการสังเกต |
| `service_estimate` | เฉพาะเมื่อเปิดใช้งาน: จำนวนหมายเลขที่ขาดหายไปซึ่งจะเป็นข้อความบริการตามสัดส่วนที่สังเกตได้ ไม่เคยถูกหักออก `missing` |

ความถูกต้องถูกกำหนดจากบันทึก ไม่เคยถูกสมมติไว้:

- **ช่องและกลุ่มใหญ่**จะถูกวัดตามแต่ละการสนทนา รวมถึงในการส่งออกการสนทนาที่เลือกไว้ การวัดผลจะขึ้นอยู่กับบันทึกที่ผู้ส่งเลือก `not_applicable`.
- **ลำดับการส่งข้อความของบัญชีทั้งหมด**จะถูกวัดเฉพาะจากข้อความแรกถึงข้อความสุดท้ายที่ ได้รับมาในขณะที่การเก็บข้อมูลทั้งบัญชีกำลังเปิดอยู่ และรวมถึงการสนทนาส่วนตัว, บอท, กลุ่ม ทั่วไป และข้อความของบัญชีเอง โดยไม่มีการสนทนาใดถูกยกเว้น (`scope.changed`). ตัวเลขที่ระบุโดย `deletion.unscoped` นับเป็นข้อความที่สังเกตได้โดยไม่รวมเนื้อหา การส่งออกหรือ การโอนย้ายการสนทนาที่เลือกไว้ไม่สามารถวัดค่านี้ได้ หากการเก็บข้อมูลทั้งบัญชีถูกปิด และเปิดใหม่ จะมีหมายเหตุระบุว่าตัวเลขที่ใช้ในช่วงเวลานั้นจะปรากฏเป็นช่องว่าง
- ข้อความบริการเป็นบันทึกในสมุดบันทึกที่มีหมายเลขเฉพาะตัว ดังนั้นจึงปิดช่องว่าง ได้ด้วยตัวเอง; การประมาณค่าที่เป็นตัวเลือกเป็นเพียงข้อมูลบริบทเท่านั้น

`verify.py` คำนวณใหม่ `gap_summary` จาก `events.jsonl` จากพารามิเตอร์ใน `coverage.json` member (ค่าเริ่มต้นสำหรับอาร์ไคฟ์เก่า) และ พิมพ์บรรทัดระดับบัญชีในสรุปการครอบคลุมของมัน อาร์ไคฟ์ของ `get_capture_status`(MCP และบรรทัดคำสั่ง) จะคืนค่าการวัดที่เหมือนกันสำหรับแชทที่การเข้าถึงอาจอ่านได้; ส่วนลำดับข้อมูลระดับบัญชีจะคืนค่าเฉพาะสำหรับการเข้าถึงที่ครอบคลุมพื้นที่ทำงานทั้งหมดเท่านั้น

การสังเกตซ้ำของข้อความบริการหนึ่งครั้งจะนับเป็นหนึ่งครั้ง และการประมาณค่าบริการบัญชี ใช้เฉพาะตัวเลขภายในช่วงที่วัดได้เท่านั้น ขอบเขตที่นำไปใช้ต้องรักษา ข้อความของบัญชีเองไว้อย่างชัดเจน ก่อนที่จะเปิดใช้งานการวัดระดับบัญชีทั้งหมด; บันทึกเก่า ที่ไม่มีข้อมูลดังกล่าวไม่สามารถยืนยันเงื่อนไขนี้ได้ การหยุดการสังเกตไม่ ขยายช่วงที่วัดได้ และการเริ่มใหม่จะได้รับการบันทึก การค้นหาในคลังข้อมูลแบบเรียลไทม์มี งบประมาณเวลา ซึ่งรวมถึงการสแกนฐานข้อมูล และจะหมายเหตุการวัดที่ยังไม่เสร็จสิ้นว่าเป็นแบบไม่สมบูรณ์

Telegram บันทึกลำดับ [ID](https://core.telegram.org/api/updates#message-id-sequences) [ข้อความที่แยกกัน](https://core.telegram.org/api/updates#message-id-sequences) ตัวเลขเหล่านี้อธิบายข้อมูลการสังเกตการณ์เท่านั้น; ไม่ระบุตัวผู้ลบข้อความหรือชี้แจง เหตุผลที่ตัวเลขบางตัวขาดหายไป

เมื่อ Telegram หยุดรับบัญชีแล้ว บันทึก `coverage.gap` ที่สิ้นสุดการสังเกตการณ์ จะนำ `cause` (`account_banned`, `account_frozen`, `account_deleted`, `session_duplicated`, `session_revoked`, `session_expired`, `session_ended` หรือ `not_authorized`) และข้อผิดพลาด Telegram; `verify.py` ระบุสาเหตุที่จุดสิ้นสุดของช่วงเวลา

การครอบคลุมรวมถึงช่วงเวลาการบันทึกการสังเกตการณ์ การหยุดชะงัก และผลลัพธ์ของข้อความ ให้ประเมินร่วมกับแชทที่เลือก ช่วงเวลา และนโยบายการแนบไฟล์; การทำงานต่อเนื่อง เพียงอย่างเดียวไม่สามารถยืนยันการส่งข้อมูลอัปเดตของ Telegram ได้อย่างครบถ้วน

## ผู้ผลิต

ไฟล์ ZIP ของรายการหลักฐานที่ลงนาม, ไฟล์ส่งออกการสนทนา, บันทึกพยาน และคำชี้แจงของ ไฟล์โปรไฟล์บุคคล มีข้อมูล`producer` : ซอฟต์แวร์, เวอร์ชัน, โครงการ (PhishDestroy), หน้าหลัก และคลังแหล่งที่มา รายงาน HTML แสดงบรรทัดเดียวกัน และ`verify.py` พิมพ์ข้อมูลนี้เป็นส่วนหนึ่งของสิ่งที่ได้รับการตรวจสอบ ไฟล์ที่เก็บไว้ก่อนที่ช่องข้อมูลนี้จะถูกสร้างขึ้น ได้รับการตรวจสอบว่า เป็นไปตามเดิม และถูกรายงานว่าไม่ระบุชื่อผู้ผลิต

แต่ละบันทึก`observation.started` ยังระบุชื่อไคลเอนต์Telegram ที่ทำการสังเกตการณ์: `api_id` ของมัน (ไม่เคยเป็นแฮช), ไม่ว่าจะเป็นคู่สาธารณะที่ติดตั้งมาพร้อมระบบหรือแอปพลิเคชันของผู้ดำเนินการเอง, คำอธิบายไคลเอนต์ที่ส่งมาในคำขอเชื่อมต่อของTelegram และประเภทของเส้นทางเชื่อมต่อ พร้อมโหมด IP (ไม่มีที่อยู่พร็อกซีหรือข้อมูลลับ) รายงานและ`custody.json` ระบุทุก ไคลเอนต์และเส้นทางที่ต่างกัน พร้อมทั้งเวลาที่บันทึกไว้ รวมถึงช่วงเวลาที่พร็อกซีที่ไม่ได้ระบุในรายการไม่ตอบรับ และTelegram ตรวจพบที่อยู่ของเซิร์ฟเวอร์ บันทึกที่บันทึกไว้ก่อนนี้ระบุไว้เช่นนั้น

## โปรไฟล์บุคคล

ไฟล์โปรไฟล์ (`tgwitness-dossier-v1`, JSON) จะถูกสร้างขึ้นตามคำขอจากข้อมูลบันทึกที่มีอยู่แล้ว ในสมุดบันทึกสำหรับแชทหนึ่งแชทเท่านั้น; ไม่มีการดึงข้อมูลใดจาก Telegram และเนื้อหาของโปรไฟล์จะไม่ถูก บันทึกไว้ในสมุดบันทึก (การเปิดและปิดโปรไฟล์จะถูกบันทึกเป็น `dossier.changed`) สำหรับทุกบุคคลที่มีข้อความที่บันทึกไว้ ระบบจะแสดงประวัติชื่อและชื่อผู้ใช้, สัญลักษณ์ของ Telegram (บอท, หลอกลวง, ปลอม, พรีเมียม, ได้รับการยืนยัน, ถูกจำกัด, ถูกลบ) ตามที่ปรากฏ ณ เวลาบันทึก, รูปโปรไฟล์ ID รูปภาพโปรไฟล์, SHA-256 และแฮชเชิงรับรู้ (pHash, ที่เข้ากันได้กับ`imagehash.phash`) ของ อวาตาร์จากแคชอวาตาร์ท้องถิ่นที่มีอวาตาร์คล้ายกัน, กิจกรรม (ข้อความแรกและข้อความสุดท้าย, จำนวนข้อความ, การแชร์ที่แก้ไขและลบ, ข้อความตามชั่วโมง UTC), ใครตอบใคร, การสนทนาอื่น ๆ ในบันทึกนี้ที่บุคคลดังกล่าวได้เขียนและกล่าวถึงกระเป๋าเงิน (BTC, EVM, TRON, TON, LTC, DOGE, XMR, SOL; ที่อยู่ Base58Check ได้รับการตรวจสอบความถูกต้องด้วย checksum), หมายเลขโทรศัพท์, ชื่อผู้ใช้ และ ลิงก์ รวมถึงลิงก์ที่ซ่อนอยู่หลังข้อความ

ทุกข้อเท็จจริงจะระบุบันทึกในสมุดบันทึก (`seq`) ที่มันมาจาก และ `record_hashes` เก็บ ค่าแฮชของบันทึกแต่ละรายการที่ถูกอ้างอิงไว้ ข้อความนี้ได้รับการลงนามด้วยกุญแจพื้นที่ทำงาน:

```
python verify.py tgwitness-dossier-CHAT.json --fingerprint TRUSTED_SHA256 --evidence tgwitness-evidence.zip
```

ตรวจสอบลายเซ็น, ตรวจสอบการส่งออกหลักฐานเอง (ลายเซ็น, ห่วงโซ่แฮช และไฟล์) และว่าทุกบันทึกที่อ้างอิงอยู่ยังคงไม่เปลี่ยนแปลงในไฟล์ส่งออกนั้นของพื้นที่ทำงานเดียวกัน แฮชของอวาตาร์ถูกระบุว่าเป็นข้อมูลจากแคชท้องถิ่น (ไม่ใช่บันทึกในสมุดบันทึก) การกล่าวถึงเป็นการจับคู่รูปแบบ — เป็นข้อมูลนำทางเพื่อตรวจสอบ ไม่ใช่ข้อเท็จจริงที่ได้รับการยืนยัน โปรไฟล์ถูกเปิดใช้งานตามแต่ละแชท สามารถส่งออกเป็นไฟล์ ZIP ที่เข้ารหัสด้วย AES-256 พร้อมรหัสผ่าน และ ถูกลบเมื่อปิดใช้งานหรือเมื่อแชทถูกลบออกจากแหล่งข้อมูล

## พยานอิสระ

สมุดบันทึกพยาน (`tgwitness-witness-v1`) และโพสต์ในช่องของมันถูกตรวจสอบเทียบกับ การส่งออกหลักฐานด้วย `verify.py --witness … --channel …`; [ดูพยานอิสระ](https://phishdestroy.github.io/TgWitness/th/docs/reference/witness/)

## Manifest และจุดตรวจสอบ

manifest.json ประกอบด้วยรูปแบบ เวลาส่งออก กุญแจสาธารณะ ลายนิ้วมือ ความยาวของบันทึก แฮชส่วนหัว ขอบเขต ผู้ผลิต ข้อจำกัด และ SHA-256 ของสมาชิกเนื้อหาทุกตัว ยกเว้น `manifest.json` และ `manifest.sig` เอง manifest.sig คือลายเซ็น Ed25519 ที่เข้ารหัสด้วย base64 บนไฟล์ manifest JSON แบบมาตรฐาน ตัวตรวจสอบจะปฏิเสธองค์ประกอบที่ไม่คาดคิด/ขาดหายไป ชื่อที่ซ้ำกัน ไฟล์ที่เสียหาย ลำดับ/โซ่ที่ขาดหาย ลายเซ็นที่ไม่ถูกต้อง และความไม่ตรงกันกับจุดตรวจสอบที่ให้มา ตัวตรวจสอบจะไม่ดึงเส้นทางของไฟล์เก็บถาวรออกมาเลย และจำกัดขนาดรวมที่ประกาศไว้ (ไม่รวมการบีบอัด) ไว้ที่ 4 GiB; `--max-gib N` อนุญาตให้สร้างไฟล์เก็บถาวรที่มีขนาดใหญ่ขึ้นได้ โดยเพิ่มขีดจำกัดของ **Parameters**

ดำเนินการตรวจสอบจากเวอร์ชัน TgWitness ที่ติดตั้งไว้ หรือจากเวอร์ชันที่ได้รับการตรวจสอบแล้ว สำเนาที่รวมอยู่ในไฟล์อาร์ไคฟ์รองรับการใช้งานแบบพกพา; โปรดตรวจสอบสำเนานั้นกับ การติดตั้งที่คุณเชื่อถือได้ ก่อนที่จะดำเนินการ

จุดตรวจสอบ (checkpoint) จะลงนามในข้อความที่ประกอบด้วยกุญแจสาธารณะ ความยาวของบันทึก ค่าแฮชส่วนหัว และเวลาสร้าง ผู้ตรวจสอบสามารถตรวจสอบได้ว่าไฟล์เก็บถาวรที่สร้างขึ้นภายหลังมี คำนำหน้าเดียวกัน ให้เก็บจุดตรวจสอบไว้ภายนอกตัวเก็บข้อมูล (collector) เพื่อให้การตรวจสอบในภายหลังสามารถเปรียบเทียบ ไฟล์เก็บถาวรกับข้อมูลอ้างอิงที่เก็บไว้แยกต่างหาก

## ขอบเขตการตรวจสอบ

การตรวจสอบจะตรวจสอบไฟล์เก็บถาวรและโหมดการเก็บข้อมูลที่ใช้ในการสร้างไฟล์ดังกล่าว ให้เลือก โหมดที่มีขอบเขตความเชื่อถือตรงกับกรณีนั้น แล้วเก็บข้อมูลการตรวจสอบของโหมดนั้นไว้

| โหมดการเก็บข้อมูล | สิ่งที่ผู้ตรวจสอบจะตรวจสอบ | ข้อมูลป้อนเข้าสำหรับการตรวจสอบและขอบเขตความเชื่อถือ |
| --- | --- | --- |
| พื้นที่ทำงานท้องถิ่น | บันทึกลายเซ็น, ห่วงโซ่แฮช, รายการเนื้อหา (manifest) และไบต์ของไฟล์แนบ | ลายนิ้วมือของตัวเก็บข้อมูลที่เก็บไว้อย่างอิสระ；ผู้ดูแลระบบโฮสต์ควบคุมกุญแจลงนามท้องถิ่น |
| พื้นที่ทำงานท้องถิ่นที่มีพยานอิสระ | การตรวจสอบไฟล์เก็บถาวร รวมถึงการตรวจสอบความสอดคล้องกับคำนำหน้าของบันทึกก่อนหน้านี้ที่ผู้เป็นพยานเก็บรักษาไว้ | กุญแจพยานและบันทึกที่เชื่อถือได้แยกกัน；จุดตรวจสอบจะผูกกับคำนำหน้าที่ได้รับการสังเกตแล้ว |
| [การบันทึกด้วย GitHub Actions](https://github.com/phishdestroy/TgWitness/blob/main/docs/SEALED-ACTIONS.md) | การรับรองบน GitHub สำหรับข้อมูลสรุปของไฟล์เก็บถาวร, กระบวนการทำงานที่ได้รับการอนุมัติและคำสั่ง commit ของผู้รวบรวมข้อมูล, เครื่องรันเนอร์ที่โฮสต์เอง, ที่มาของเซสชัน/คีย์ใหม่ และความสมบูรณ์ของไฟล์เก็บถาวรภายใน | นโยบายผู้ตรวจสอบที่เชื่อถือได้, ที่เก็บข้อมูลของผู้เรียก และชุดการรับรองจาก GitHub; การเก็บข้อมูลดำเนินการภายใต้เวิร์กโฟลว์ที่ถูกตรึง |
| [การปรับใช้บนคลาวด์](https://phishdestroy.github.io/TgWitness/th/docs/reference/high-assurance/) | บันทึกวงจรชีวิตและสิทธิ์การเข้าถึงของผู้ให้บริการ, สถานะของไฟร์วอลล์และ Cloudflare, รวมถึงบันทึกการทำงานที่ลงนามของผู้รวบรวมข้อมูล | การสอบถามแบบอ่านอย่างเดียวไปยังผู้ให้บริการและ Cloudflare；ความพร้อมใช้งานของการตรวจสอบแต่ละรายการขึ้นอยู่กับผู้ให้บริการ |
| [Intel TDX VM ลับ](https://phishdestroy.github.io/TgWitness/th/docs/reference/high-assurance/#confidential-vm-on-phala-cloud-intel-tdx) | ระบุลายเซ็นและสถานะแพลตฟอร์ม，เชื่อมโยงกับคำสั่ง collector，การเขียนข้อความ และการวัดผลระบบปฏิบัติการ | Intel trust chain และค่าการปรับใช้ที่คาดการณ์ไว้；เก็บรักษาผลการตรวจสอบ TDX ทุกครั้งที่จำเป็น |

ในการเก็บข้อมูลแบบปิดผนึก (sealed acquisition) ผู้เก็บข้อมูลที่ได้รับการอนุมัติจะรับข้อมูลผ่านการเชื่อมต่อ Telegram ที่ได้รับการยืนยันตัวตน ภายในสภาพแวดล้อมที่ได้รับการตรวจสอบแล้ว การรับรอง (attestation) จะผูกไฟล์เก็บถาวรไว้กับ การดำเนินการนั้น ดังนั้นการตรวจสอบจึงครอบคลุมทั้งขั้นตอนการเก็บข้อมูลและความสมบูรณ์ของไฟล์ในภายหลัง สิ่งนี้ขึ้นอยู่กับโค้ดที่ได้รับการอนุมัติและห่วงโซ่ความเชื่อถือของแพลตฟอร์มที่ระบุไว้ข้างต้น การตรวจสอบการจับภาพบน GitHub จำเป็นต้องมีเซสชันที่สร้างขึ้นภายในกระบวนการทำงาน และจะปฏิเสธ การจับภาพจากเซสชันที่นำเข้ามา

ใบยืนยันการรันบันทึกเวอร์ชันของตัวเก็บข้อมูล ค่าแฮชของไฟล์ และการตั้งค่าเริ่มต้น GitHub ข้อมูลที่มา (provenance) และการวัดค่า TDX ให้ข้อมูลการตรวจสอบสภาพแวดล้อม ส่วน [บันทึกการตรวจสอบ](https://phishdestroy.github.io/TgWitness/th/docs/reference/verification/)ความถูกต้องระบุการตั้งค่าที่ได้รับการทดสอบ

TgWitness ลงนามในข้อมูลการสังเกตที่เก็บรวบรวมได้；Telegram และผู้เขียนข้อความไม่ได้ออก ลายเซ็นเหล่านี้．ในพื้นที่ทำงานท้องถิ่น，ข้อมูลที่สร้างขึ้นก่อนจุดตรวจสอบอิสระ ครั้งแรกยังคงขึ้นอยู่กับผู้เก็บรวบรวมข้อมูลและผู้ถือกุญแจของมัน．บันทึกการครอบคลุมอธิบาย ขอบเขตที่เลือกและผลลัพธ์การเก็บรวบรวมข้อมูล ส่วนเวลาประทับจากภายนอกที่ได้รับการตรวจสอบจะกำหนด ขอบเขตของคลังข้อมูลหรือบันทึกที่ถูกบันทึกไว้ในเวลา

## ไฟล์แนบ

ไฟล์ถูกระบุด้วย SHA-256 ในโฟลเดอร์ media/ เหตุการณ์ media.saved เชื่อมโยงค่าแฮชและ ความยาวไบต์กับเหตุการณ์ข้อความเฉพาะ ชื่อไฟล์ดิบเป็นข้อมูลเมตา ไม่เคยเป็น เส้นทางในเครื่อง ไบต์ของสื่อถูกดาวน์โหลดแบบไม่พร้อมกัน ดังนั้นการลบข้อความทันทีอาจทำให้ การบันทึกไม่สำเร็จ การปิดการเก็บข้อมูล ไฟล์ที่มีขนาดใหญ่เกินกำหนด/ขนาดไม่ทราบ ความล้มเหลวในการดาวน์โหลด และการดาวน์โหลดที่ถูกขัดจังหวะ จะปรากฏเป็นผลลัพธ์ การเกิดข้อผิดพลาดของกระบวนการอาจทิ้ง ไฟล์บางส่วนที่ไม่มีอ้างอิงไว้; ไฟล์เหล่านี้จะไม่ถูกรวมอยู่ในการส่งออก

เครื่องมือส่งออก ZIP ตรวจสอบสื่อที่เก็บไว้ตามชื่อของสื่อนั้น JSONL, CSV และ HTML การส่งออกจะตรวจสอบลายเซ็นของเหตุการณ์ แต่ไม่ส่งข้อมูลไบต์ของสื่อ รายงานที่สร้างขึ้น เป็นเพียงเพื่อความสะดวกเท่านั้น; events.jsonl เป็นรูปแบบการแสดงเหตุการณ์ที่ถือเป็นมาตรฐาน

การส่งออกแชทแบบเต็มจะบันทึกไฟล์แนบตามการตั้งค่าไฟล์แนบในพื้นที่ทำงานลงใน media/ โดยตั้งชื่อเป็น SHA-256 แต่ละบันทึกข้อความใน chat.json จะระบุชื่อไฟล์ (`file`, `file_sha256`) หรือเหตุผลที่ไฟล์นั้นขาดหายไป (`file_status`) พร้อมทั้งข้อมูลที่ผู้อ่านเห็น รอบข้อความ: ลิงก์ที่อยู่หลังข้อความ, แหล่งที่มาของการส่งต่อ, ปุ่มบอท, ลายเซ็น, จำนวนการดู และ ตัวจับเวลาการลบอัตโนมัติ `verify.py` ตรวจสอบว่าทุกไฟล์ที่ระบุชื่ออยู่ใน manifest ที่ลงนาม ภายใต้แฮชนั้น

## ใบรับการเก็บรวบรวมและประมวลผลที่คงทน (0.2)

งานสื่อและเหตุการณ์การส่งข้อความถูกบันทึกในธุรกรรมเดียว งานนี้จะเก็บ ตัวระบุข้อความ TL ต้นฉบับ; การสังเกตที่ลงนามจะผูก SHA-256, บัญชี, และนโยบายขนาดไว้ การกู้คืนจะตรวจสอบการผูกนั้นก่อนดาวน์โหลด มันจะไม่เคยดึง ข้อความปัจจุบันมา และจะแทนที่ไฟล์แนบที่ใหม่กว่าอย่างเงียบๆ งานที่ถูกขัดจังหวะ จะได้รับการลองใหม่ ในขณะที่ความล้มเหลวถาวรยังคงเป็นผลลัพธ์ที่ชัดเจน

แต่ละพื้นที่ทำงานมีบันทึกและตัวตนสำหรับการลงนามเป็นของตัวเอง เหตุการณ์ process.started ประกอบด้วย ID การรัน, นาฬิกาท้องถิ่น, เวอร์ชันของส่วนที่พึ่งพา, ค่าแฮชของไฟล์ต้นฉบับ, บัญชี/ขอบเขตเริ่มต้น, และการตั้งค่าการบันทึก Heartbeats ประกอบด้วย ID การรัน, เวลาแบบโมโนโทนิก, และสถานะคิว ใบยืนยันการรันยังสามารถดาวน์โหลดเป็นเอกสารที่ลงนามแยกต่างหากได้ เพื่อการตรวจสอบ สภาพแวดล้อมการรัน ให้ใช้ร่วมกับใบรับรองจาก GitHub หรือการตรวจสอบ TDX ที่อธิบายไว้ ในส่วน "[ขอบเขตการตรวจสอบ](https://phishdestroy.github.io/TgWitness/th/docs/reference/evidence/#verification-scope)"

จุดตรวจสอบอัตโนมัติจะถูกเก็บไว้อย่างท้องถิ่นเมื่อเริ่มต้นระบบ ทุกห้านาทีระหว่าง การสังเกตการณ์ (**พารามิเตอร์ → Signed checkpoint every**) และเมื่อหยุดระบบอย่างเป็นระเบียบ การตรวจสอบเมื่อเริ่มต้นระบบและการส่งออกจะเปรียบเทียบบันทึก กับจุดตรวจสอบท้องถิ่นล่าสุดที่เก็บไว้ สิ่งนี้สามารถตรวจพบการย้อนกลับของฐานข้อมูล เมื่อจุดตรวจสอบยังคงอยู่ การเก็บรักษาอย่างอิสระทำให้การอ้างอิงนี้สามารถใช้งานได้นอก พื้นที่ทำงาน; และเวลาประทับภายนอกที่ได้รับการตรวจสอบแล้วยังช่วยยึดจุดอ้างอิงนี้ให้คงที่ตามเวลาอีกด้วย．

หลังจากรีสตาร์ท ระบบจะกลับมาดำเนินการต่อจากตำแหน่งการอัปเดต Telegram ที่บันทึกไว้ (`catch_up_from` ใน `observation.started`) และจะขอรับการอัปเดตที่พลาดไป การตรวจสอบซ้ำเป็นระยะจะบันทึก `message.recovered` สำหรับข้อความที่พลาดไป และ `message.missing_on_recheck` เมื่อ Telegram ไม่ ส่งข้อความที่บันทึกไว้กลับมาอีกต่อไป; กรณีหลังนี้ไม่ใช่การแจ้งเตือนการลบ และไม่ระบุชื่อผู้ลบหรือเวลา

### คัดลอกและกู้คืนข้อมูลจากภายนอก (S3)

สำเนาที่จัดเก็บนอกไซต์ (Exports, ปิดตามค่าเริ่มต้น) จะอัปโหลดส่วนต่าง ๆ ของบันทึก, ไฟล์ที่เก็บรักษาไว้, จุดตรวจสอบ พร้อมด้วยเวลาประทับ และไฟล์แชทที่ส่งออกเสร็จสมบูรณ์ไปยังพื้นที่จัดเก็บที่เข้ากันได้กับ S3, ซึ่งถูกเข้ารหัสด้วย AES-256-GCM ก่อนการอัปโหลด โดยใช้กุญแจที่เก็บไว้ใน vault ของพื้นที่ทำงาน; การเก็บรักษาด้วย Object Lock จะถูกนำไปใช้ เมื่อ bucket รองรับคุณสมบัตินี้ หากไม่มีกุญแจที่ดาวน์โหลดมา สำเนาดังกล่าวจะไม่สามารถอ่านได้ การกู้คืนและตรวจสอบ ด้วย `python -m tgwitness.replica restore --key-file KEY.json --out DIR`

การกู้คืนต้องการไดเรกทอรีธรรมดาที่ว่างเปล่า ไฟล์ที่ดาวน์โหลดและวัตถุที่ถูกถอดรหัสจะเก็บไว้ใน พื้นที่จัดเก็บชั่วคราวส่วนตัวจนกว่าบันทึกทั้งหมดและจุดตรวจสอบทุกจุดที่เก็บไว้จะผ่านการตรวจสอบ วัตถุ ที่มีเส้นทางไม่ปลอดภัย ช่วงเซกเมนต์ไม่สอดคล้องกัน หรือบันทึกที่สั้นกว่าจุดตรวจสอบจะถูกปฏิเสธ; หาก การตรวจสอบล้มเหลว จะไม่มีการเผยแพร่ไฟล์ที่กู้คืนได้ การตรวจสอบการเก็บรักษาจะเปรียบเทียบโหมด Object Lock และวันที่ที่ส่งกลับมา กับกำหนดเวลาที่ส่งไปเมื่ออัปโหลด (มีความคลาดเคลื่อนในการปัดเศษ 1 วินาที) กำหนดเวลาที่หมดอายุ ไม่ถูกต้อง หรือถูกตัดสั้น จะไม่นับว่าผ่านการตรวจสอบ สถานะจะรายงานวัตถุตัวอย่าง ที่การเก็บรักษาถูกอ่านกลับสำหรับการอัปโหลดครั้งนั้น

สื่อท้องถิ่นที่ขาดหายหรือเสียหายจะถูกรายงานเป็นข้อผิดพลาดของรอบการอัปโหลด และรักษาตัวชี้สื่อไว้ก่อน จุดนั้น เพื่อให้ไฟล์ได้รับการลองอัปโหลดอีกครั้งในรอบถัดไป; ไฟล์ จุดตรวจสอบ และการส่งออกหลังจากนั้นยังคง ถูกคัดลอกต่อไป การตรวจสอบการกู้คืน จะเปรียบเทียบการอ้างอิงสื่อที่เก็บรักษาไว้ทั้งหมดกับแฮชที่ถอดรหัสแล้วและขนาดที่บันทึกไว้ ส่วนบันทึก ที่ทับซ้อนกันและเหมือนกันจากการอัปโหลดที่ถูกขัดจังหวะจะถูกกำจัดข้อมูลซ้ำ; ส่วนทับซ้อนที่ขัดแย้งกันจะถูกปฏิเสธ จุดตรวจสอบที่สร้างขึ้นระหว่างการอัปโหลดจะถูกเลื่อนออกไปจนกว่าบันทึกในบันทึกที่ครอบคลุมจะถูก คัดลอกเสร็จสิ้น ดังนั้นรอบการอัปโหลดที่เสร็จสมบูรณ์จะไม่เผยแพร่จุดตรวจสอบก่อนบันทึกที่เกี่ยวข้อง

### ภาพถ่ายหน้าจอการส่งออกแบบสตรีมมิ่ง

การส่งออกแบบสตรีมมิ่งใช้สแนปช็อตการอ่าน SQLite ที่เสถียร ส่วนหัวของสแนปช็อตอาจเก่ากว่า บันทึกสดปัจจุบันเมื่อการดาวน์โหลดเสร็จสิ้น จุดตรวจสอบที่สร้างขึ้นหลังจาก สแนปช็อตนั้นสามารถรายงานได้อย่างถูกต้องว่าไฟล์เก็บถาวรสั้นกว่า; ให้เปรียบเทียบกับจุดตรวจสอบ ที่หรือก่อนส่วนนำที่ถูกส่งออก ไม่ใช่จุดตรวจสอบที่สร้างขึ้นภายหลังแบบสุ่ม

## การเตรียมการตาม RFC 3161 และการตรวจสอบการตอบกลับ (0.2)

โหมดหลักฐาน (ปิดตามค่าเริ่มต้น) จะส่งเพียง SHA-256 ของจุดตรวจสอบที่ลงนามแต่ละจุดไปยัง หน่วยงาน RFC 3161 และปฏิทิน OpenTimestamps ที่ระบุไว้ ผ่านเส้นทางพื้นที่ทำงาน (workspace route) และไม่เคยผ่าน MTProxy คำตอบถูกเก็บไว้ใน `checkpoints/anchors/`, ส่งออก และตรวจสอบโดย `verify.py` (`--tsa-ca` ตรวจสอบ ลายเซ็น TSA; ยืนยันหลักฐาน OpenTimestamps ด้วย `ots upgrade` และ `ots verify`).

แผงควบคุมจะเตรียมอาร์ไคฟ์คำขอที่ประกอบด้วยข้อมูล byte ของไฟล์ checkpoint.json แบบมาตรฐาน, ลายนิ้วมือข้อความ SHA-256 และ nonce แบบสุ่มในไฟล์ timestamp.tsq, ค่า checksum และคำแนะนำ ไม่มีการส่งคำขอผ่านเครือข่าย การเตรียมข้อมูลนี้ไม่ใช่การประทับเวลาที่เชื่อถือได้

`python -m tgwitness.anchor verify` เรียก OpenSSL ts สองครั้ง: ครั้งหนึ่งกับ byte ของจุดตรวจสอบ และครั้งหนึ่งกับคำขอเดิม จำเป็นต้องระบุไฟล์ CA ที่เชื่อถือได้อย่างชัดเจน; ใบรับรองที่รวมมาจะไม่ได้รับการเชื่อถือโดยอัตโนมัติ การตรวจสอบคำขอเป็นตัวเลือกที่ CLI ดังนั้นให้เก็บและระบุ --request เพื่อตรวจสอบ nonce ผลลัพธ์จะระบุว่า ได้ตรวจสอบแล้วหรือไม่ ลายเซ็นจุดตรวจสอบของตัวเก็บข้อมูลและบันทึกหลักฐานยังคงต้องได้รับการตรวจสอบ แยกกันด้วยลายนิ้วมือของตัวเก็บข้อมูลที่เชื่อถือได้

การตรวจสอบความถูกต้องจะตรวจสอบลายเซ็นของคำตอบ, ไบต์ของจุดตรวจสอบ และหากมี คำขอเดิมภายใต้ความเชื่อถือของ CA ที่กำหนด การตรวจสอบการเพิกถอนและการตรวจสอบความถูกต้องของการเก็บรักษา ระยะยาวหลังจากใบรับรองหมดอายุอยู่นอกขอบเขตของตัวตรวจสอบปัจจุบัน ดู[ขั้นตอนและ](https://phishdestroy.github.io/TgWitness/th/docs/reference/timestamp/)[ผลการตรวจสอบความ](https://phishdestroy.github.io/TgWitness/th/docs/reference/verification/)ถูกต้อง

## ข้อมูลเสริมในโหมดหลักฐาน: อุปกรณ์ drand และTelegram

สามารถบันทึกข้อมูลเพิ่มเติมได้อีกสองรายการในรอบการประมวลผลเดียวกันกับเวลาประทับเวลา ทั้งสองรายการนี้ถูกปิดไว้ตามค่าเริ่มต้นและ จะมีผลเฉพาะเมื่อโหมดหลักฐานเปิดอยู่: Extras → Evidence & backups → **More witnesses · optional**, หรือ `"drand": true` และ `"devices": true` ใน `POST /api/evidence`. การล้มเหลวของหนึ่งในนั้นจะไม่หยุด อีกอันหรือการประทับเวลา; แผงควบคุมจะแสดงผลลัพธ์ล่าสุดของแต่ละส่วนใต้แบบฟอร์ม

**drand** (`beacon.drand` ). ในแต่ละรอบ ระบบจะบันทึกรอบล่าสุดของ drand quicknet ซึ่งเป็น ความสุ่มสาธารณะของ League of Entropy (รอบทุก 3 วินาที) ลงในบันทึก: `chain` , `round` , `randomness` , `signature` , `round_time` และ `relay` ที่ตอบกลับ รอบที่ได้รับการยืนยัน และไม่สามารถคาดการณ์ได้จะให้จุดอ้างอิงเวลาต่ำสุดสำหรับข้อมูลที่เชื่อมโยงด้วยแฮชในรอบถัดไป เวลาที่ได้รับการตรวจสอบแล้วบนจุดตรวจสอบในภายหลังจะให้จุดอ้างอิงเวลาสูงสุด การตรวจสอบเหล่านี้ กำหนดขอบเขตของข้อมูลที่เชื่อมโยงกัน; การครอบคลุมการเก็บรวบรวมข้อมูลจะได้รับการประเมินแยกต่างหาก ผู้เก็บรวบรวมข้อมูลจะสอบถาม `drand.cloudflare.com` ก่อน แล้วจึงสอบถามรีเลย์ของ Protocol Labs ผ่านเส้นทางพื้นที่ทำงาน โดยส่งคำขอหนึ่งครั้งต่อรอบ

`verify.py` ตรวจสอบว่าความสุ่มแต่ละครั้งคือ SHA-256 ของลายเซ็นของมัน และว่ารอบ เวลาถูกต้อง และรายงานจำนวนรอบ ช่วงที่ยาวนานที่สุดที่ไม่มีรอบ และว่านาฬิกาของผู้เก็บข้อมูล ล่าช้ากว่า drand ไปเท่าใด มันไม่ตรวจสอบลายเซ็น BLS`--check-drand` เปรียบเทียบรอบกับรีเลย์ของ Cloudflare และรีเลย์ของ Protocol Labs ทั้งทั้งหมดหรือตัวอย่างสุ่ม 100 รายการในบันทึกยาว; รอบที่แตกต่างจะผ่านการตรวจสอบไม่สำเร็จ

**Telegram** (`account.devices`). ในแต่ละรอบจะอ่านเซสชันของบัญชีด้วย `account.getAuthorizations`, รายการ Telegram ที่แสดงใน Settings → Devices และบันทึกไว้: บันทึกอย่างครบถ้วนเมื่อมีการเปลี่ยนแปลงตั้งแต่รอบการตรวจสอบครั้งก่อน พร้อมด้วยแฮชเซสชัน `added` และ `removed` หากไม่มีการเปลี่ยนแปลง จะบันทึกเพียงจำนวนเซสชันและ SHA-256 เท่านั้น รุ่นอุปกรณ์ แพลตฟอร์ม แอป และเวอร์ชัน วันที่สร้างและกิจกรรมครั้งสุดท้าย ประเทศและภูมิภาคจะถูกเก็บรักษาไว้ ส่วนที่อยู่ IP จะไม่ถูกเก็บรักษา เนื่องจาก หลักฐานที่ส่งออกจะอยู่นอกเหนือการควบคุมของคุณ เซสชันของตัวเก็บข้อมูลเองจะทำงานตลอดเวลา ดังนั้น เพียงกิจกรรมของเซสชันอื่นเท่านั้นที่นับเป็นการเปลี่ยนแปลง`verify.py` รายงานความถี่ที่รายการ ถูกบันทึก รวมถึงเซสชันใหม่และเซสชันที่สิ้นสุดแต่ละครั้ง มันจะอ่านรายการนี้เฉพาะเมื่อการสังเกตการณ์กำลังทำงานอยู่เท่านั้น

สิ่งที่พวกเขาไม่แสดง: drand พิสูจน์ได้เพียงลำดับของบันทึกเทียบกับเวลาสาธารณะเท่านั้น, และรายชื่ออุปกรณ์คือคำแถลงของTelegram ผ่านผู้รวบรวมข้อมูล ซึ่งได้รับการลงนามโดยผู้รวบรวมข้อมูล เช่นเดียวกับบันทึกอื่น ๆ ทุกบันทึก

**Cloudflare Gateway log** (`cloudflare.gateway_dns`). สำหรับเซิร์ฟเวอร์ที่ทำการแก้ไขผ่าน Cloudflare Gateway ([Gateway DNS](https://phishdestroy.github.io/TgWitness/th/docs/reference/high-assurance/#cloudflare-as-an-outside-witness)) ในแต่ละ รอบการคัดลอกจะคัดลอกข้อมูลที่ Gateway ได้บันทึกไว้ตั้งแต่การคัดลอกครั้งก่อน: หนึ่งบันทึกต่อช่วงเวลาสูงสุดสาม ชั่วโมง โดยใช้ `from`, `until`, `location_id`, `address` ของเซิร์ฟเวอร์ (หากมีการตั้งค่า) และ `queries` เป็น `[at, name, type, rcode, decision, colo]` แม้ในกรณีที่ไม่มีข้อมูลใดๆ ตั้งค่าไว้ภายใต้ **Cloudflare Gateway log**: บัญชี, สถานที่, ที่อยู่ (ไม่บังคับ) และโทเค็นอ่านอย่างเดียว (Account Analytics Read; Zero Trust PII Read เพื่อเก็บที่อยู่หนึ่งแห่งของตำแหน่งที่แชร์ร่วมกัน). แผงควบคุมจะตรวจสอบ ข้อมูลเหล่านี้ด้วยคำขอหนึ่งครั้งก่อนการบันทึก; โทเค็นจะยังคงถูกเข้ารหัสและไม่เคยถูกบันทึกลงในบันทึก `verify.py` แสดงรายการหน้าต่าง ชื่อที่ถูกค้นหามากที่สุด และช่วงเวลาที่ไม่มีสำเนาครอบคลุม; บันทึก ที่มีจำนวนไม่ตรงกับคำขอจะล้มเหลว หน้าต่างที่เก็บการค้นหา มากกว่าหนึ่งหน้าภายในหนึ่งวินาทีจะเก็บหน้านั้นไว้และแจ้งว่าส่วนที่เหลือขาดหายไป สำเนาดังกล่าวคือ คำตอบของ Cloudflare ผ่านตัวรวบรวมข้อมูล (collector) ซึ่งได้รับการลงนามโดยตัวรวบรวมข้อมูลนั้นเอง; ภายใน 24 ชั่วโมง ผู้ใดก็ตามที่มี โทเค็นอ่านอย่างเดียวสามารถเปรียบเทียบกับ Cloudflare ได้
