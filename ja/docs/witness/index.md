## 2つのホスト、2つの署名鍵

Telegramセッションコレクターの署名鍵

読み取り専用チェックポイントのエンドポイント

← 署名付きの回答をリクエスト →

HOST B / WITNESS**検証＋保存**

固定されたコレクターのフィンガープリント 個別のWitness署名鍵

独自のジャーナル + ボットトークン

Witness → Telegram Bot API →**あなたのチャンネル · 署名付き TGW1 投稿**

Witnessは自身で検証を行います。コレクターへのアクセスは読み取り専用です。ボットによる公開には、Witnessの接続とトークンが使用されます。Witnessにはアカウントセッションは付与されません。

03 / チェックポイントの決定事項参考となる回答例

最終承認日**120件の記録**`head 9c7d…`

次の回答**128件の記録**`head a4f2…`

承認済み：カウントが増加し、署名が検証され、鍵が一致しました。Witnessはこの新しい境界を保持します。

すべての回答例は、有効な署名と固定鍵が存在することを前提としています。ここでのハッシュ値は、説明のための省略形です。ハッシュ値の合計数が大きいという事実だけでは、古いプレフィックス全体が変更されていないことを証明することはできません。チェックポイントが保持されているエクスポートデータと比較してください。

## ボットとチャンネルの準備

BotFather でボットを作り、チャンネルへの投稿を許可します。証人は別の場所で動かしてください。別のホスト、できれば別の人が管理するホストの方が、コレクターの隣で動く 2 つ目のプロセスよりずっと価値があります。

## 「Extras」の3つの手順

1. **読み取り専用アクセス。****追加情報 → 独立した証人**でトークンを作り、ファイルを保存します。読むのはチェックポイントと稼働状態だけです。
2. **チャンネルと間隔。**Telegram チャンネルまたは Discord の webhook と、証人から届くコレクターのアドレス。設定ファイルを保存します。
3. **起動。**`witness.json`、`witness-token.txt`、`bot-token.txt` を証人のホストにまとめて置き、次を実行します：

```
python -m tgwitness.witness run --config witness.json --check-config
python -m tgwitness.witness run --config witness.json
```

チャンネルに最初の署名付き投稿が出るのを待ち、証人のフィンガープリントを安全な場所に保存します。

Discord を使う場合は、webhook の URL を `discord-webhook.txt` として保存します。1 つの証人は 1 か所に投稿します。長い確認結果は Discord ではファイルとして届きます。

## 公開頻度を選択してください

確認のたびに投稿すると、外部に安定した記録が残ります：5 分ごとなら、ワークスペースあたり 1 日約 288 件の投稿です。詳細設定では、変化や問題があったときだけ投稿したり、プロキシや独自の Bot API を使ったりできます。

**このボットは実際には何を証明するのでしょうか？**

コレクターに署名付きチェックポイントを要求し、想定した鍵で確認して、見逃した応答や拒否された応答も含めて自分の署名付きジャーナルに記録します。

確認するのはジャーナルの状態で、Telegram 自体を見ているわけではありません。そのためには、管理された配信テストを行ってください。

## 後で証拠を確認してください

証人のジャーナル、投稿、フィンガープリントを保管してください。コレクターのエクスポートとの[照合方法](https://phishdestroy.github.io/TgWitness/ja/docs/reference/witness/#verify)。
