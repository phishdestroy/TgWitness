証拠の形式

署名付きZIPファイルの内容、記録の種類、処理の受領確認、ユーザープロフィール、オフサイトコピー、およびオフライン検証について。

TgWitnessは、アカウント上で確認可能なTelegramの観測データを、署名付きジャーナルとして保存します。 受信者は、信頼できる コレクターキーを用いて、保存された記録、添付ファイル、およびレポートの整合性を検証し、その後、ジャーナルを独立して保持されているチェックポイントと比較することができます。 このページでは、引き渡しに必要なフォーマット、検証手順、および保存すべき資料について説明します。

署名とは#

資料 保護 保存すべき内容
運用上のイベントを含む、ジャーナルへのすべての記録 イベントごとにSHA-256チェーンとEd25519署名を付与します オリジナルのevents.jsonl（信頼できる鍵のフィンガープリント）および保持されたチェックポイント
証拠ZIPファイルの内容 manifest.sigは、コンテンツファイルのハッシュを一覧にした正規のマニフェストに署名します。 マニフェストおよび署名を含む完全なZIPファイル
保存された添付ファイル 署名付きmedia.savedイベント内のSHA-256およびバイト数；署名付きZIPマニフェスト内のファイルハッシュ 検証済みのZIPファイル内の元のバイトデータ
チェックポイント ジャーナルの長さ、先頭ハッシュ、公開鍵、および作成時刻に対するEd25519署名 変更の是非が争われた際に備えて保持された独立したコピー
実行記録 個別に署名されたコレクターの測定値。これらは、署名付きprocess.startedイベントにも含まれています。 受信記録および関連するジャーナル。測定値は自己申告によるものです。
読みやすいレポート：report.htmlおよびその構成要素、report.json、report.pdf、chat.pdf ファイルごとにその内容に対してEd25519のシールが適用されます。PDFには、標準のPDF署名も付いています（参照。読み取り可能なレポート：）。 受信したファイルと信頼済み鍵のフィンガープリント、およびそれらが指すZIPファイル
スタンドアロン版 CSV 独立した暗号署名はありません。イベントのハッシュだけでは不十分です。 完全性チェックのためには、検証済みのZIPファイル内の正確なコピーをご使用ください。
ブラウザによって生成されたスクリーンショット、印刷物、またはPDF 派生作品にはTgWitnessの署名が含まれていません 検証済みの元のパッケージを保管し、派生版がどのように作成されたかを文書化してください。

コレクターは、あらゆるエクスポート形式を生成する前に、ジャーナルの署名を検証します。 読みやすい HTML および PDF レポートには独自のシールが付与されており、スタンドアロンの CSV ファイルは、 署名付き ZIP ファイルの一部としてチェックされます。添付ファイルのバイトデータとマニフェストを保持するために ZIP 形式を維持し、 以前の境界線に対してジャーナルを検証するための別のチェックポイントを設けてください。

調査の引き継ぎ#

  1. ケース参照番号、担当者、Telegramの数値アカウントID、選択された ソース、収集ポリシー、および収集期間をケースノートに記録してください。TgWitnessは 観察結果を保存し、 Case Boardにおけるソースにリンクされたメモや収集データをサポートします。移管および保管記録は、ケース 資料とともに保管してください。 実際の受入手順を用いて、意図した収集設定を確認してください。
  2. エクスポート機能に依存する前に、ワークスペースの公開鍵フィンガープリントを独自に保持してください。 収集中は、署名済みのチェックポイントをコレクターの外部に保存してください。 中断やアカウントの可視性の制限についても記録してください。
  3. 署名付きZIPファイルをエクスポートし、署名付き実行レシートを保管してください。エクスポート対象のジャーナルの境界点、 またはその手前の地点でチェックポイントを使用してください。それより後のチェックポイントでは、 それ以前のエクスポートが「短すぎる」として正しく拒否される場合があります。エクスポートには、パネルフィルターの設定にかかわらず、 ワークスペースのジャーナル全体が含まれます。共有する前に内容を必ず確認してください。

  4. 受信者には、信頼できる検証ツールのコピーと、 別途提供されたフィンガープリント／チェックポイントを用いて、ZIPファイルの検証を行っていただきます。信頼できるチェックアウト環境から、 Python環境を起動した状態で：

    python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --checkpoint retained-checkpoint.json

    両方の入力が提供され、受け入れられた場合、出力レポートとして「key_pinned: true 」および「checkpoint_checked: true 」が正常に生成されます。検証結果は保持されます。

    For a handover requiring the final exported record to be witnessed, use
`--witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness`.
This refuses an export with an unwitnessed tail. See the
[witness handover procedure](WITNESS.md#require-a-witnessed-export-boundary).
    1. アーカイブのSHA-256、エクスポート境界、転送日時、送信者、および 受信者を保管記録に記録してください。元のパッケージはそのままの状態で保管し、 作業はコピーで行ってください。アカウントのセッションや署名用秘密鍵も含まれる アプリケーションのプライベートデータディレクトリではなく、証拠ファイルを共有してください。 転送の際は、エクスポートデータをパスワードで保護されたAES-256 ZIPファイルに格納することができます。 パスワードは機密性を保護するのみであり、保存されることはありません。受信者は アーカイブを解凍し、内部にある署名付きエクスポートデータが変更されていないことを検証します。
    2. 独立したタイムアンカーが必要な場合は、 RFC 3161の手順に従い、リクエスト、チェックポイント、信頼できる CA情報、および検証済みの認証局の応答を保持してください。リクエストを準備するだけでは、 タイムスタンプは取得されません。

検証が成功すると、信頼されたコレクター キーおよび保持された境界に対する完全性が確立されます。実施されたチェックに関する 信頼の前提条件および検証結果については、検証範囲を参照してください。

引き継ぎ要約#

署名付きZIPファイルには、ワークスペースのログ全体が含まれています。裁判所、弁護士、または虐待相談窓口が 一部のチャット、特定の期間、または特定の参加者だけが必要な場合、「エクスポート」→「引き渡し用抽出」により、選択された開示ルールに従って最小限の コピー（tgwitness-handover-v1）が作成されます。 オペレーターは目的を明記し、チャット、任意の期間（UTC）、 抽出対象となる人物、その他の人物への対応（表示、仮名 P01、 P02…、あるいは除外）の扱い、どのメッセージ本文を残すか、どの添付ファイルやプロフィール写真を含めるか、そして 本文中の電話番号やメールアドレスをマスキングするかどうかを指定します。 目的およびこれらのルールは、 署名付きマニフェストおよびレポートに記載されます。ジャーナルには、handover.exportedが、 それを作成したアクセス情報とファイルのSHA-256（内容そのものではありません）とともに記録されます。

verify.pyは、抽出データを2つの方法で検証します。「変更なし」と表示された記録は完全に検証済みであり、その コンテンツはハッシュ値、Ed25519署名、および含まれる先行記録へのリンクと照合されます。 A 最小化されたレコードは元のハッシュと署名を保持しているため、署名の検証は可能ですが、 非表示にされたフィールドはそこから再計算することはできません。レコードには非表示にされた項目が明記され、レポート にはその旨が示されます。マニフェストにはジャーナルの長さと先頭部分が記載され、その 先頭部分にはコレクターの署名が付与されており、除外されたレコードの数がカウントされます。 coverage.jsonは、選択されたチャットを記述します。ファイル 名に含まれる名前は検出されません。共有する前に最終的なファイルを確認してください。自由形式のテキスト、ファイル名、および選択された 添付ファイルから、依然として個人を特定できる可能性があります。署名済みのZIPファイル全体を保管してください。抽出ファイルは情報開示であり、代替物ではありません。

読みやすいレポート#

署名付き証拠、引き渡しデータ、およびチャットの ZIP ファイルには、読み取り可能な HTML および JSON 形式のレポートに加え、 必要なフォントが利用可能な場合は、選択されたレポート言語の PDF も含まれます。各 レポートはワークスペースの Ed25519 鍵で封印されており、個別に検証が可能です： python -m tgwitness.verify FILE --fingerprint KEY [--evidence ZIP]。

  • report.html / chat.html：シールステートメント（tgwitness-report-seal-v1）はファイルを閉じ、 それ以前のすべてのバイトのSHA-256に署名します。長いジャーナルやチャットは、 設定可能なサイズ（レポート設定、500～100,000レコード、デフォルトは5,000）の 部分に分割されます： records/records-0001.htmlまたはmessages/messages-0001.htmlは、それぞれその番号、範囲、 および合計が記載され、署名付きマニフェストにはSHA-256と共にリストされます。コレクターのハートビートの一連の記録は、 レポート設定で個別に表示するように指定されていない限り、1行として表示されます。
  • report.json（tgwitness-report-json-v1、キー format、report、seal）：このシールは、report の正規な JSON である SHA-256 に署名するため、事実関係を各システムのシステムやスクリプトで読み取ることができ、 署名付きファイルの完全性を保ったまま、データ保護のための選択を行うことが可能になります。
  • report.pdf / chat.pdf：印刷およびファイリング用の正式な文書であり、同一の バイト列に対して2回署名されており、署名値（/ByteRange）を除くファイル全体が対象となる。標準のPDF署名 （adbe.pkcs7.detached、CMS、SHA-256、およびECDSA P-256）は、ワークスペースの保管庫に保持されている自己発行の文書署名用 証明書を使用しており、そのサブジェクトのシリアル番号はEd25519キーの フィンガープリントである。Ed25519シールは、CMS内部に未署名の属性 2.25.240684792623320047764573196045913242332として格納され、証明書のSHA-256を "content": "pdf-byte-range"で指定するため、Ed25519キーが証明書を保証する。 PDFリーダーは、 署名後にファイルが変更されたかどうかを表示し、証明書が 信頼されるまでは署名者を「不明」とみなします。その場合は、代わりにEd25519フィンガープリントを比較してください。中国語、日本語、韓国語のPDFには、 サーバー上（またはTGWITNESS_FONT_DIR内）にフォントが必要です。フォントがない場合、ZIPファイルにはHTMLおよびJSONレポートのみが 含まれます。

チャンネルまたはスーパーグループ内では、Telegram がメッセージ1、2、3…を順に番号付けします。チャットのエクスポートには、 最初と最後の番号、存在するメッセージの数、および欠落している番号の連続範囲が message-ids.json 、マニフェスト、chat.json ヘッダーに一覧表示され、トランスクリプト内の 各欠落箇所がマークされます。 verify.py は、chat.json から番号を再カウントします。欠落した番号とは、Telegram が返さなかったメッセージ（エクスポート前に削除されたもの、またはそのアカウントからは表示されないもの）を指します。プライベートチャットや 基本グループでは、番号はアカウントのすべてのチャットで共有されるため、欠落はカウントされません。

履歴を読み込んだ後、エクスポート処理は、存在しない番号について、番号ごとに （channels.getMessages から 10,000 番まで）再度 Telegram に問い合わせを行います。結果は message-ids.json およびレポートに記載されます。 空の応答は、Telegramが当該アカウントにおいてその番号のメッセージを保有していないことを意味します。ただし、 そのメッセージが削除されたのか、それとも当該アカウントには最初から表示されていなかったのかについては明記されていません。Telegramというメッセージが返された場合、 そのメッセージは読み取り時に見落とされていたものであり、found_on_recheckとしてマークされ、エクスポートに追加されます。

すべてのレポートは「」で始まります。概要「」：1段落の後、資料が示す内容と示さない内容 （アカウントの背後にいる人物、配信の完全性、監視前の削除、タイムスタンプのない 時刻情報）。 ページ固有のシールスタンプは、ブラウザがページ自体ではなくシールの 署名を検証した際に琥珀色に変わります。ブラウザはページに独自のバイト列を付与することはありません。 それが緑色に変わるのは、 読者がページ末尾の検証欄にファイルをドロップし、すべてのバイトが一致した場合、かつ 表示されているページがそのファイルである場合に限られる。そうでない場合は赤色になる。

各レポートでは、プログラム名を正確に明記してください。具体的には、コレクターがチェックアウトから実行された際のgitコミット、または インストーラーが設定した TGWITNESS_COMMIT、およびそのソースファイルのSHA-256（source_tree_sha256、 パス → すべてのSHA-256値の正規化されたJSON .py, .js, .css, .html および .svg ファイルのSHA-256）を明記する。これらは、ファイルが変更されていない限り、そのコミットをチェックアウトすることで再現可能である。Telegram クライアントは、そのライブラリ、APIレイヤー、およびデータセンターとともに指定される。観測の開始時、およびチャットの エクスポートの開始・終了時、コレクターはTelegramに時刻（updates.getState、整数 秒）をTelegramに問い合わせ、Telegramの時刻からコレクターの時計の時刻を差し引いた値を、 往復通信による誤差を含めて記録します。レポートでは、これらの測定値が「Chain of custody」の下に表示されます。チャットのエクスポートでは、メッセージの日付とは別に、 履歴を読み込んだ時刻も記録されます。

オフラインレポートビューアおよびアーカイブガイド#

chat.htmlまたはreport.htmlを開く前に、ZIPファイルを完全に解凍してください。ビューアでは、サーバーを介さずに検索、 フィルタ、参加者、インジケーター、記録の詳細、およびJSON/CSVの選択が可能です。 viewer/とmedia/はレポートの隣に保管してください。選択内容は派生データです。verify.py SELECTION.json --evidence ARCHIVE.zipを使用して、署名付きアーカイブと比較してください。 検証ツールは、レポート ID、署名キー、アーカイブの境界、および選択されたすべての項目をチェックします。編集済み、 欠落、または重複している項目は失敗となります。選択に関する注記および作成時刻は、署名されていないメタデータとして残ります。

メッセージ番号の欠番は、フィルタリングされていない完全な昇順のチャットフィードにおいてのみ表示されます。 カテゴリを非表示にしたり、データチャンクの読み込みに失敗したりしても、省略された行がメッセージの欠落の 証拠となってはなりません。検索ハイライトは、HTMLによるエスケープ処理前のプレーンテキストに対して行われ、リテラルなマークアップは保持されます。

ブラウザは、マニフェストの署名、レポートIDおよびキー、ならびにリストされているすべてのファイルハッシュをチェックします。また、 不明確または形式不備のZIP構造、重複するファイル名、安全でないパスを拒否し、ファイルサイズは 256 MiB、宣言された総容量は4 GiBを上限とします。これより大きなアーカイブについては、スタンドアロンの検証ツールを使用してください。 このブラウザによるチェックは、ジャーナルチェーンやデータセマンティクスに関する検証ツールのチェックを補完するものです。

README.txtには、スタートガイド、ファイル一覧（言語対応済み）、検証手順、およびデータ 形式に関する注記がレポートの言語で記載されており、その後に完全な英語版ガイドが続きます。 SHA256SUMSは、 それ自体、manifest.json、およびmanifest.sigを除く、そこに記載されたファイルを網羅しています。署名付きマニフェストは SHA256SUMSも対象としています。元のZIPファイルは変更せず、作業用ファイルは 解凍したフォルダの外に保存してください。PDFのレポートには、セクションごとのブックマークと、後半のページにケース/レポートの識別情報が含まれています。

エクスポート時のチャット内容#

チャットのエクスポートには、エクスポート開始時点でTelegramがそのチャットについて記録した内容が含まれます：Telegram自身の ラベル（scam、fake、理由付きのrestricted、verified）、ユーザー名、説明、メンバー 数および管理者数、関連するディスカッション、コンテンツ保護、新規メンバーが過去の メッセージを閲覧できるかどうか、およびこのアカウントがどのメッセージから履歴を閲覧できるか（available_min_id）、 チャットが作成された場合の メッセージ1の日付、およびチャットの写真に関するSHA-256（media/に保存）。 また、エクスポート元アカウントのチャット内での位置情報（役割、参加日、招待者、および 管理者の場合はその権限）も記録されます。Telegramが拒否したリクエストについては、代わりにその名称が記載されます。

エクスポートを行うアカウントが管理者である場合、エクスポート処理ではチャットの管理者ログ（Telegramには約 48時間分が保存される）がadmin-log.jsonに読み込まれます。これには、削除や編集の内容、および操作を行ったアカウントが含まれます。 削除を行った人物の名前が記載されているのは、この削除記録のみです。

指標#

レポート一覧およびアーカイブには、indicators.csv 、indicators.stix.json （STIX 2.1 ） およびindicators.misp.json （MISP イベント）として、記録されたメッセージ内で不正利用対応窓口が対応可能な項目が記載されています： リンクおよびドメイン（テキストの背後に隠されているもの、ボタン内、リンクのプレビュー内を含む）、仮想通貨 アドレス、Telegram のユーザー名および招待リンク、電話番号、メールアドレス、保存された画像。 ビットコイン、ライトコイン、ドージコイン、TRONのアドレスは、base58チェックサムが有効な場合にのみリストされ、 segwitアドレスはbech32またはbech32mチェックサムが有効な場合、TONアドレスはCRCが 有効な場合にリストされます。EVMおよびSolanaアドレスは「未確認」としてマークされます。 画像にはSHA-256 と知覚的 ハッシュ（dHash、64ビット）が含まれており、再圧縮またはリサイズされたコピーでもほぼ変化しません。レポートは、 誤って開かれないようにインジケーターを記述します（hxxps[://]example[.]com ）。ファイルは 元の値を保持します。 すべてのインジケーターは「不明」かつ「自動検出対象外」としてマークされます（STIX 、 indicator_types: unknown 、MISP 、to_ids: false 、自社組織への配布）：リストに 掲載されていることは、そのメッセージに含まれていたことを示すものであり、悪意があることを示すものではありません。テキストに表示されているアドレスと 実際に開くアドレスが異なるリンクは、レポート内でマークされます。

PDFレポートの末尾には、検査官が手書きで署名する宣言文、公証人または 裁判所鑑定人向けのチェックリスト、およびレポートID、鍵のフィンガープリント、 そして権威あるデータのSHA-256が記載されたQRコード（1ページ目にも記載）が含まれており、これにより印刷物を元のアーカイブに遡って確認できるようになっています。

イベントの正規化#

ハッシュの入力は、正確に以下のフィールドで構成されています：

seq, observed_at, source_at, kind, chat_id, message_id, actor_id, payload, previous_hash

UTF-8 形式の Python 互換 JSON を使用してシリアライズし、オブジェクトのキーはソート済み、ASCII エスケープなし、無意味な空白なし、NaN/無限大なしとします：

json.dumps(value, ensure_ascii=False, sort_keys=True,
           separators=(",", ":"), allow_nan=False).encode("utf-8")

これらのバイトのSHA-256ハッシュがイベントハッシュとなります。署名は、 32バイトの生のハッシュ値に対してEd25519を適用し、その後Base64エンコードされたものです。最初のprevious_hashは64個のゼロで構成されます。 シーケンス番号は1から始まり、1ずつ増加します。運用上の イベントを含むすべてのイベントは、1つのチェーンを共有します。重複配信の抑制機能はありません。つまり、繰り返して 観測されたものは、個別の受信記録であり、個別のTelegramアクションの主張ではありません。

Telegramの生データの日付はISO文字列であり、バイナリフィールドは bytes_base64を含むオブジェクトとなります。メッセージ本文、エンティティ、メディア記述子、返信メタデータ、リアクション、 およびサービスアクションは、提供された場合、生メッセージのメタデータとして保持されます。

observed_at は、コレクターの UTC ウォールクロックです。source_at は、利用可能な場合に提供される Telegram の日付です。 削除通知には正確な削除時刻が含まれていないため、 source_at は null のままとなります。受信順序は、必ずしもソースイベントの 順序とは限りません。履歴のスナップショットでは、古いソース日付が使用されますが、観測時刻は現在の時刻となります。

アクターのセマンティクス#

message.new の actor_id はメッセージの送信者です。message.edited には推定された 編集者は含まれません。payload.sender_id には、観測されたメッセージの送信者が記録されます。 削除 actor_id は null のままとなります。メンバーシップサービスのメッセージは、送信者とアクション タイプを保持しますが、すべての削除を「自発的な退会」として扱ったりはしません。生の参加者 更新情報では、提供されたままの actor_id が保持されます。リアクションのスナップショットでは、変更を行ったアクターを架空のものとして生成することはありません。

プライベートチャットおよび通常のグループにおける削除通知には、メッセージIDのみが含まれます。 これらのチャットはアカウント全体で共通のIDシーケンスを共有しているため、1つのIDは このアカウントの単一のメッセージを識別します。 そのIDを持つメッセージが以前にこのジャーナルに保存されていた場合、 削除は当該チャット内で「message.deleted」として記録され、メソッド名を 「payload.chat_resolution」として指定されます。保存されたことのないIDは、「deletion.unscoped」として、 chat_idなしで保持されます。推測による処理は一切行われません。 チャンネルやスーパーグループでは、チャットごとにメッセージが番号付けされており、 この方法では照合されることはありません。削除されたメッセージが監視対象のアカウントによって送信された場合、 payload.deleted_message_was_outgoing は true となりますが、削除者は依然として指定されません。

対象範囲：連続性、欠落、および検出されなかったID#

署名付きZIPファイルにはすべてcoverage.jsonが含まれており、HTMLレポートは同じ要約で始まります。また、 verify.pyはファイルをそのまま信頼するのではなく、events.jsonlから要約を再計算します：

  • XからYまで継続的に監視されます。1つの期間はobservation.startedで始まり、 一時停止、停止、Telegram接続の切断、ログアウト、正常な停止を伴わないプロセスの起動、 または監視中に3分以上記録がない場合に終了します （ハートビートは1分ごとに記録されるため、記録がない状態は、プロセスが停止した、フリーズした、または コンピュータがスリープ状態になったことを意味します）。「パラメータ」でハートビート間隔が変更された場合、各ハートビートが その変更を記録し、許容される無記録時間は3つの間隔分となり、3分を下回ることはありません。
  • 「ギャップ」には、各期間間の時間と理由が記載されています。最後の 記録時点で未解決のギャップは、not_resumed_by_last_record とマークされます。
  • メッセージIDは観測されませんでした。チャットごとにメッセージ数をカウントするチャンネルやスーパーグループについては、 観測されたIDの間に欠落しているIDは範囲として記載されています。これらは 「観測されなかった（削除された、配信されなかった、または保存された履歴の範囲外）」として報告され、決して 「削除された」とは記載されません。 プライベートチャットや通常のグループはアカウント全体で共通の連番を使用しているため、そこでの 欠落は意味を持たず、一覧には記載されません。
  • チャット単位のデータ欠落通知（例えば、Telegramが特定の チャンネルにおいてデータ差分の復元を要求する場合など）は「メモ」としてカウントされ、全体的な記録範囲を中断することはありません。

Telegramがアカウントの受け入れを停止すると、監視を終了するcoverage.gapレコードには cause（account_banned、account_frozen、account_deleted、session_duplicated、 session_revoked、session_expired、session_ended、またはnot_authorized）とTelegram エラーが含まれます。verify.pyは、その期間が終了する原因を指定します。

「カバー範囲」では、このコレクターが何を記録したかを説明しています。これは、Telegramが 連続した期間中にすべての更新を配信したことを証明するものではありません。

プロデューサー#

証拠用ZIPファイル、チャットエクスポート、ウィットネス・ジャーナル、および人物プロファイルファイルの 署名付きマニフェストには、producer （ソフトウェア、バージョン、プロジェクト（PhishDestroy）、 ホームページ、ソースリポジトリ）が含まれています。HTMLレポートにも同様の行が表示され、verify.py は検証結果の一部としてこれを表示します。 このフィールドが存在する以前に作成されたアーカイブは、 従来通り検証され、作成者が特定されていないものとして報告されます。

各observation.startedレコードには、観測を行ったTelegramクライアントの名称も記載されています。具体的には、そのapi_id （ハッシュ値は記載されません）、それが組み込みの公開ペアであるかオペレーター独自のアプリケーションであるか、 Telegramの接続リクエストで送信されたクライアントの説明、およびIPモードを含む接続 ルートの種類（プロキシアドレスやシークレットは含まれません）です。 レポートおよびcustody.jsonには、 記録された日時とともに、すべての異なるクライアントとルート、リストにないプロキシが応答しなかった時刻、 およびTelegramがサーバーのアドレスを検知した時刻が記載されています。これ以前に記録されたジャーナルにはその旨が記載されています。

人物プロフィール#

プロファイルファイル（tgwitness-dossier-v1、JSON）は、リクエストに応じて、 1つのチャットに関するジャーナルにすでに記録されているデータに基づいて生成されます。Telegramからデータを取得することはなく、プロファイルの内容が ジャーナルに書き込まれることもありません（プロファイルのオン／オフの切り替えはdossier.changedとして記録されます）。 メッセージが保存されているすべてのユーザーについて、名前とユーザー名の履歴、保存時点でのTelegramのフラグ （ボット、詐欺、偽アカウント、プレミアム、認証済み、制限付き、削除済み）、プロフィール 写真ID、ローカルのアバターキャッシュ内の類似アバターからのアバターのSHA-256および知覚ハッシュ（pHash、imagehash.phashと互換性あり）、 アクティビティ（最初のメッセージと最後のメッセージ、 メッセージ数、編集・削除されたシェア、UTC時間ごとのメッセージ）、誰が誰に返信したか、その人物が書き込みを行った 、その人物が書き込みを行った他のチャット、および言及されたウォレット（BTC、EVM、TRON、TON、LTC、 DOGE、XMR、SOL；Base58Checkアドレスはチェックサム検証済み）、電話番号、ユーザー名、 リンク（テキスト内に隠されたリンクを含む）などが含まれます。

各事実には、その出典となるジャーナル記録（seq）が記載されており、record_hashesには 参照された各記録のハッシュ値が格納されています。この記述は、ワークスペースキーを用いて署名されています：

python verify.py tgwitness-dossier-CHAT.json --fingerprint TRUSTED_SHA256 --evidence tgwitness-evidence.zip

署名を検証し、証拠エクスポート自体（署名、ハッシュチェーン、ファイル）を検証するとともに、 参照されているすべてのレコードが、同じワークスペースのそのエクスポート内に変更されずに存在することを確認します。アバターのハッシュは、ローカルキャッシュに由来するものとしてラベル付けされます （ジャーナルレコードではありません）。メンションはパターン一致であり、確認すべき手がかりであり、検証済みの事実ではありません。 プロファイルはチャットごとに有効化され、パスワード付きのAES-256 ZIPとしてエクスポート可能で、 無効化された場合、またはチャットがソースから削除された場合に削除されます。

独立した証人#

ウィットネス・ジャーナル（tgwitness-witness-v1）およびそのチャンネルへの投稿は、 verify.py --witness … --channel … による証拠エクスポートと照合されます。独立したウィットネスについては、こちらをご覧ください。

マニフェストとチェックポイント#

manifest.json には、フォーマット、エクスポート日時、公開鍵、フィンガープリント、ジャーナルの 長さ、先頭ハッシュ、スコープ、プロデューサー、制限事項、および manifest.json と manifest.sig 自体を除く すべてのコンテンツメンバーの SHA-256 ハッシュが含まれています。 manifest.sig は、正規化されたマニフェスト JSON に対する Base64 エンコードされた Ed25519 署名です。 検証ツールは、予期しないメンバーや欠落したメンバー、重複する名前、破損したファイル、 シーケンスやチェーンの破損、無効な署名、および提供されたチェックポイントとの不一致を拒否します。 アーカイブのパスを抽出することはありません。宣言された総非圧縮サイズは 4 GiB に制限されています。 「--max-gib N」では、Parameters の制限値を引き上げることで、より大きなアーカイブを作成することが可能です。

検証コードは、信頼できるチェックアウトまたは審査済みの独立したコピーから入手してください。信頼できないアーカイブ内の検証プログラムは、 そのアーカイブの作成者によって提供された実行可能ファイルです。 その存在は移植性の利便性を目的としたものであり、独立した信頼の根拠ではありません。

チェックポイントは、公開鍵、ジャーナルの長さ、先頭 ハッシュ、および作成時刻を含むステートメントに署名します。検証者は、後のアーカイブに 同じプレフィックスが含まれていることを確認できます。係争の恐れのある変更が行われる前に、コレクターの外側にチェックポイントを保持しておいてください。 アーカイブとチェックポイントの両方を制御している攻撃者は、両方を置き換えてしまう可能性があります。

検証範囲#

署名はコレクターキーを識別し、保存された資料を保護します。その フィンガープリントを個別に固定することで、そのキーを想定されるコレクターに関連付けます。Telegramの 更新情報は収集の入力となります。TgWitnessは、それらの更新に関する観測結果に署名します。 これらの署名は、Telegramやメッセージの作成者によって発行された署名ではありません。

保持されたチェックポイントまたはウィットネスレコードは、以前のジャーナルプレフィックスの変更を検知します。 これには、コピーされたコレクターキーで署名された置換も含まれます。最初の独立したチェックポイント以前に 捏造されたレコードについては、ソースによる裏付けが必要です。コレクターキーの保有者は 新しい資料に署名することができます。署名キーへのアクセスは管理下に置き、参照情報は別途保持してください。

カバレッジ記録と管理されたテストを用いて、アカウントの可視性と配信状況を評価してください。 独立した時間アンカーとして、検証済みの外部タイムスタンプを使用してください。送信者 ID は Telegram アカウントを識別するものであり、調査を通じて個人と関連付けます。プログラムの受信確認と クラウドチェックは、コレクターが報告した測定値および展開構成を説明しています。 測定された動作とその範囲に関する検証結果をご確認ください。

添付ファイル#

ファイルは media/ ディレクトリ内で SHA-256 ハッシュによって識別されます。media.saved イベントは、ハッシュと バイト長を特定のメッセージイベントに関連付けます。生のファイル名はメタデータであり、決してローカル パスではありません。 メディアのバイトデータは非同期でダウンロードされるため、即時削除を行うと キャプチャできない場合があります。収集が無効化されている場合、サイズ超過またはサイズ不明のファイル、ダウンロードの失敗、 およびダウンロードの中断は、結果として表示されます。プロセスのクラッシュにより、 参照されていない部分的なファイルが残る場合がありますが、これらはエクスポートには含まれません。

ZIPエクスポート機能は、保存されたメディアをそのファイル名と照合して検証します。JSONL、CSV、およびHTML 形式でのエクスポートは、イベントの署名を検証しますが、メディアのバイナリデータは含まれません。派生レポートは 利便性を目的としたものであり、events.jsonlがイベントの正式な表現となります。

チャット全体のエクスポートでは、ワークスペースの添付ファイル設定に従って、添付ファイルが media/ ディレクトリ内に、SHA-256 という名前で保存されます。 chat.json内の各メッセージレコードには、ファイル名（file、 file_sha256）または欠落理由（file_status）が記載されており、読者がテキストの 周辺で確認した内容（テキスト内のリンク、転送元、ボットボタン、署名、閲覧回数、 自動削除タイマー）も併せて記録されます。verify.pyは、指定されたすべてのファイルが、そのハッシュに対応する署名付きマニフェスト内に 存在することを確認します。

永続的な収集と受領証の処理 (0.2)#

メディアジョブとそのメッセージイベントのコミットは、1つのトランザクションで行われます。 ジョブは 元のTLメッセージ記述子を保存します。署名付き観測データには、そのSHA-256、アカウント、 およびサイズポリシーが紐付けられます。復元時には、ダウンロード前にその紐付けが検証されます。現在のメッセージを取得することは決してなく、 新しい添付ファイルに静かに置き換えられます。中断されたジョブは 再試行されますが、恒久的な失敗は明示的な結果として残ります。

各ワークスペースには、独自のジャーナルと署名用IDが割り当てられています。「process.started」イベントには、 実行ID、ローカル時刻、依存関係のバージョン、ソースファイルのハッシュ、初期アカウント／スコープ、 およびキャプチャ設定が含まれます。ハートビートには、実行ID、単調時間、およびキューの状態が含まれます。 プロセス領収書は、個別に署名されたステートメントとしてダウンロードすることも可能です。 ファイルの測定値は自己申告によるものであり、信頼できるハードウェアによる証明ではありません。

自動チェックポイントは、起動時、監視中（[パラメータ] → [署名付きチェックポイントの生成間隔]）に5分ごとに、 および正常な停止時にローカルに保持されます。 起動時の検証およびエクスポートでは、ジャーナルを ローカルに保持されている最新のチェックポイントと照合します。これにより、チェックポイントが残存している場合にデータベースのロールバックを 検出できます。ただし、両方を管理しているオペレーターであれば、両方を上書きすることも可能です。 独立した保存期間の設定と、外部の信頼できるタイムスタンプは、引き続き別個の要件となります。

再起動後、保存されていたTelegramの更新位置（catch_up_fromから observation.started）が再開され、見逃された更新が要求されます。定期的な再確認により、見逃されたメッセージについては message.recoveredが記録され、Telegramが保存されたメッセージを 返さなくなった場合はmessage.missing_on_recheckが記録されます。後者は削除通知ではなく、削除者や時刻は記載されません。

オフサイトでのコピーおよび復元（S3）#

オフサイトコピー（エクスポート、デフォルトでは無効）では、ジャーナルのセグメント、保存されたファイル、チェックポイント およびそれらのタイムスタンプ、完了したチャットのエクスポートデータを、S3互換のストレージにアップロードします。これらは AES-256-GCMで暗号化された上でアップロードされます。バケットが対応している場合は、オブジェクトロックの保存期間が適用されます。 ダウンロードした鍵がなければ、コピーを読み取ることはできません。復元および検証は python -m tgwitness.replica restore --key-file KEY.json --out DIRで行ってください。

復元には、空の通常のディレクトリが必要です。ダウンロードされたデータおよび復号化されたオブジェクトは、 ジャーナル全体および保持されているすべてのチェックポイントが検証されるまで、非公開の一時ストレージに保管されます。安全でないオブジェクト パス、不整合なセグメント範囲、およびチェックポイントよりも短いジャーナルは拒否されます。検証に失敗した場合、 復元されたファイルは公開されません。 保持チェックでは、返されたオブジェクトロック モードと日付を、アップロード時に送信された期限と比較します（丸め誤差は1秒）。期限切れ、 無効、または短縮された期限は、検証済みとはみなされません。ステータスには、そのアップロードパスにおいて保持情報が読み取られた サンプリングされたオブジェクトが報告されます。

ローカルメディアの欠落や破損は、そのパスのエラーとして報告され、メディアカーソルは その位置に留まるため、次のパスでファイルの再試行が行われます。その後のファイル、チェックポイント、およびエクスポートは 引き続きコピーされます。復元時には、 保存されたすべてのメディア参照について、復号化されたハッシュおよび記録されたサイズとの照合が行われます。 中断されたアップロードによる同一の重複する ジャーナルセグメントは重複排除され、競合する重複部分は拒否されます。 アップロード中に作成されたチェックポイントは、それに対応するジャーナル記録が コピーされるまで保留されるため、完了したパスでは、ジャーナルより先にチェックポイントが公開されることはありません。

ストリーミングによるスナップショットのエクスポート#

ストリーミング形式でのエクスポートでは、安定したSQLiteの読み取りスナップショットが使用されます。ダウンロードが完了した時点で、その先頭部分は 現在のライブジャーナルよりも古い場合があります。そのスナップショット後に作成された チェックポイントでは、アーカイブのサイズが実際より小さいと正しく報告されることがあります。比較する際は、エクスポートされたプレフィックス時点またはそれ以前のチェックポイントと 比較し、恣意的に後日のチェックポイントと比較しないようにしてください。

RFC 3161 に基づく準備および応答の検証 (0.2)#

エビデンスモード（デフォルトではオフ）では、各署名付きチェックポイントのSHA-256のみを、リストされた RFC 3161認証機関およびOpenTimestampsカレンダーへ、ワークスペース経由で送信し、MTProxyを経由することは一切ありません。 応答はcheckpoints/anchors/に保存され、エクスポートされた後、verify.pyによって検証されます（--tsa-caは TSA署名を検証し、ots upgradeおよびots verifyでOpenTimestampsの証明を確認します）。

このパネルは、正規化された checkpoint.json バイトデータ、 SHA-256 メッセージインプリント、および timestamp.tsq 内のランダムなノンス、チェックサム、ならびに手順書を含むリクエストアーカイブを作成します。 ネットワークリクエストは行われません。この準備作業は、信頼できるタイムスタンプではありません。

python -m tgwitness.anchor verifyはOpenSSLのts関数を2回呼び出します。1回目はチェックポイント バイトに対して、2回目は元のリクエストに対してです。信頼できるCAファイルが明示的に必要となります。 同梱の証明書は自動的に信頼されるわけではありません。CLI ではリクエストの検証は オプションですので、ノンスを検証するには `--request` オプションを指定してください。結果には、 検証が行われたかどうかが表示されます。コレクターのチェックポイント署名およびジャーナルは、 信頼できるコレクターのフィンガープリントを用いて別途検証する必要があります。

検証では、応答の署名、チェックポイントバイト、および指定された場合、 指定されたCAの信頼下にある元のリクエストがチェックされます。証明書失効後の失効チェックおよび長期 アーカイブの妥当性検証は、現在の検証ツールの対象外です。 手順および検証結果をご確認ください。

タイムスタンプと同じパス上で、さらに2つの記録を実行できます。どちらもデフォルトではオフになっており、 証拠モードがオンの間のみ有効になります：[Extras] → [Evidence & backups] → [More witnesses] · オプション、 または "drand": true および "devices": true で POST /api/evidence。一方の処理が失敗しても、 もう一方やタイムスタンプの処理は停止しません。パネルには、フォームの下に各処理の最新の結果が表示されます。

drand (beacon.drand )。各パスでは、League of Entropyの公開 ランダム性であるdrand quicknetの最新ラウンド（3秒ごとに1ラウンド）がジャーナルに書き込まれます：chain 、 round 、randomness 、signature 、round_time 、および応答したrelay 。検証済みの 予測不可能なラウンドは、後続のハッシュリンクされたデータに対する下限の時間基準を提供します。 後続のチェックポイントにおける検証済みのタイムスタンプは、時間的な上限の基準を提供します。これらのチェックにより リンクされたデータが範囲内に収められますが、収集範囲の網羅性は別途評価されます。コレクターは、まず drand.cloudflare.com に問い合わせ、次にワークスペース経由で Protocol Labs のリレーに問い合わせを行います。1パスにつき1回のリクエストが行われます。

verify.py は、各ランダム値がその署名のSHA-256 であることと、ラウンド 時間が正しいことを確認し、ラウンド数、ラウンドがない最長の期間、およびコレクターのクロックがdrandより どれだけ遅れていたかを報告します。 BLS署名の検証は行いません。--check-drand は、CloudflareリレーおよびProtocol Labsリレーとのラウンドを比較します。比較対象は、すべてのラウンド、あるいは長いジャーナルから無作為に 抽出した100件のサンプルです。差異があるラウンドは検証に失敗します。
