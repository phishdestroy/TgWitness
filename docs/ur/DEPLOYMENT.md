# تعیناتی اور آپریشنز

## انسٹالیشن کا انتخاب کریں

پورٹیبل پیکیج کے لیے GitHub Releases سے `TgWitness-<version>-windows-amd64-portable.zip` نکالیں۔
دوسرے طریقوں کے لیے سورس ZIP ڈاؤن لوڈ کر کے نکالیں یا ریپوزیٹری کلون کریں، پھر پروجیکٹ
ڈائریکٹری سے درج ذیل چلائیں:

| انسٹالیشن | شروع کرنا | کیا پس منظر میں چلتی ہے؟ |
| --- | --- | --- |
| Windows پورٹیبل پیکیج | `TgWitness.cmd` | نہیں؛ ونڈو کھلی رکھیں۔ |
| نیٹو Windows | `Start.cmd` | نہیں؛ پس منظر میں چلانے کے لیے اختیاری لاگ آن ٹاسک استعمال کریں۔ |
| نیٹو Linux/macOS | `sh start.sh` | نہیں؛ پس منظر میں چلانے کے لیے systemd/launchd استعمال کریں۔ |
| کسی بھی معاون ہوسٹ پر Docker | `docker compose up -d --build --wait` | ہاں، جب تک Docker ڈیمن چل رہا ہو۔ |
| Windows پر Docker ہیلپر | `scripts\Docker.cmd` | ہاں؛ ہیلپر ویب سرور کے صحت مند ہونے کا انتظار کرتا ہے۔ |
| Linux/macOS پر Docker ہیلپر | `sh scripts/docker-start.sh` | ہاں؛ ہیلپر ویب سرور کے صحت مند ہونے کا انتظار کرتا ہے۔ |

ایسے کلاؤڈ سرور کے لیے جسے کوئی تیسرا فریق جانچ سکے — جو فراہم کنندہ کے API کے ذریعے بنایا گیا ہو،
SSH کے بغیر ہو اور جس تک صرف Cloudflare Tunnel کے ذریعے پہنچا جا سکے —
[اعلیٰ یقین دہانی والی تعیناتی](../HIGH-ASSURANCE.md) دیکھیں۔

نیٹو اسٹارٹ اپ ایک نجی `.venv` بناتا ہے اور پن کی گئی ڈیپنڈنسیز انسٹال کرتا ہے۔
Docker انہیں ہوسٹ کے Python کے بغیر امیج کے اندر بلڈ کرتا ہے۔ پہلی بار سیٹ اپ کے لیے انٹرنیٹ
تک رسائی درکار ہے۔ اگر Python 3.11+ نہ ملے تو `Start.cmd` موجودہ Windows صارف کے لیے Python 3.12
انسٹال کرنے سے پہلے پوچھتا ہے (winget کے ذریعے، ورنہ Python Software Foundation کے دستخط کی جانچ
کے بعد python.org انسٹالر سے)؛ یہ کبھی ایڈمنسٹریٹر کے اختیارات نہیں مانگتا۔
Docker اور آپریٹنگ سسٹم کی سروسز پیشگی شرائط رہتی ہیں۔

نیٹو اور پورٹیبل انسٹالیشنز اپنے فولڈر کے اندر `data/live` استعمال کرتی ہیں۔ Docker `/data` پر
`tgwitness-data` نامی والیوم استعمال کرتا ہے۔ جب تک آپ جان بوجھ کر پوری ڈیٹا ڈائریکٹری منتقل
نہ کریں، یہ الگ الگ انسٹالیشنز رہتی ہیں۔ یہ توقع نہ رکھیں کہ نیا Docker کنٹینر نیٹو اکاؤنٹس
خود بخود ڈھونڈ لے گا۔

## انسٹالیشن کی ضروریات

نیٹو انسٹالیشن کے لیے `venv` اور `ensurepip` کے ساتھ Python 3.11 یا نیا ورژن، پہلی بار ڈیپنڈنسیز
انسٹال کرنے کے لیے انٹرنیٹ تک رسائی، اور `.venv` کے لیے ایسی پروجیکٹ ڈائریکٹری درکار ہے جس میں
لکھا جا سکے۔ ساتھ آنے والے پینل کو Node.js یا فرنٹ اینڈ بلڈ کی ضرورت نہیں۔ لانچر اپنے عام OS
اکاؤنٹ سے چلائیں؛ TgWitness کو ایڈمنسٹریٹر/root اختیارات درکار نہیں۔

- **Windows:** `Start.cmd` پہلے `py -3`، پھر `python`، پھر فی صارف اور Program Files کے طے شدہ
  انسٹالیشن فولڈرز جانچتا ہے، اور ورژن 3.11 یا نیا مانگتا ہے۔ اگر کچھ بھی کام نہ کرے تو یہ اوپر
  بیان کردہ خودکار فی صارف انسٹالیشن کی پیشکش کرتا ہے۔ `py -3 start.py` بھی کام کرتا ہے۔
  پورٹیبل پیکیج کو Python کی بالکل ضرورت نہیں۔
- **Linux:** `start.sh` باری باری `python3.13`، `python3.12`، `python3.11`، `python3` اور `python` آزماتا ہے،
  اور اگر کوئی بھی شرط پوری نہ کرے تو apt، dnf، pacman، zypper، apk یا Homebrew کے لیے انسٹال
  کمانڈ دکھاتا ہے۔ Debian/Ubuntu انسٹالیشنز کو منتخب انٹرپریٹر سے مطابقت رکھنے والا
  `python3-venv` پیکیج درکار ہو سکتا ہے۔ ڈسٹری بیوشن کا پرانا طے شدہ Python بدلنا یا اس کے ساتھ
  Python 3.11+ شامل کرنا ضروری ہے۔
- **macOS:** Python 3.11+ کی کوئی موجودہ ڈسٹری بیوشن انسٹال کریں؛ یہ فرض نہ کریں کہ OS کے ساتھ
  آنے والا انٹرپریٹر یہ شرط پوری کرتا ہے۔ پروجیکٹ ڈائریکٹری سے `python3 start.py` استعمال کریں۔
- **Docker:** Compose v2.20 یا نئے ورژن کے ساتھ Docker Engine/Desktop استعمال کریں۔ Windows پر
  Docker Desktop کا Linux کنٹینرز استعمال کرنا ضروری ہے۔ کنٹینر اپنی Python ڈیپنڈنسیز خود
  انسٹال کرتا ہے؛ ہوسٹ پر الگ Python انسٹالیشن کی ضرورت نہیں۔

## مقامی کمپیوٹر

Windows پر `Start.cmd` اور Linux/macOS پر `sh start.sh` استعمال کریں۔ `scripts\Setup.cmd` یا
`sh start.sh --setup-only` ماحول تیار کرتا ہے۔ لانچر پہلی بار استعمال پر ڈیپنڈنسیز انسٹال کرتا
ہے؛ بعد کے لانچ وہی ماحول دوبارہ استعمال کرتے ہیں۔ سیٹ اپ اور Telegram سے جمع آوری کے لیے
انٹرنیٹ تک رسائی درکار ہے، لیکن موجودہ ریکارڈز دیکھنا اور ایکسپورٹس بنانا آف لائن بھی ہو جاتا ہے۔

سیٹ اپ کے بعد `python start.py --check` چلائیں تاکہ جمع کنندہ شروع کیے بغیر مقامی ڈیپنڈنسیز،
Ed25519، اسٹوریج، کلید کی ترتیب اور سننے والا پتہ جانچا جا سکے۔ ساختی آؤٹ پٹ کے لیے `--json`
استعمال کریں۔ مطلوبہ `--data-dir`، `--host` اور `--port` دیں۔ یہ جانچ نہ پیکیجز انسٹال کرتی
ہے، نہ جرنل بناتی ہے اور نہ Telegram سے جڑتی ہے؛ یہ سالمیت یا کوریج کی باضابطہ توثیق نہیں ہے۔
اسٹارٹ اپ موجودہ جرنلز کی تصدیق الگ سے کرتا ہے۔ `python start.py --help` بھی کچھ انسٹال نہیں کرتا۔

start.py استعمال کرنے کے بعد معاون کمانڈز Windows پر `.venv\Scripts\python.exe` یا Linux/macOS
پر `.venv/bin/python` سے چلائیں، یا پہلے وہ ماحول فعال کریں۔ نیچے دی گئی `python -m ...` مثالیں
فرض کرتی ہیں کہ ماحول فعال ہے۔

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

ماحولیاتی متغیرات: TGWITNESS_DATA، TGWITNESS_HOST، TGWITNESS_PORT، TGWITNESS_TOKEN۔
TGWITNESS_VAULT_KEY_FILE نئی انسٹالیشن کے لیے بیرونی کلید کا موڈ منتخب کرتا ہے؛ دیکھیں [بیرونی ماسٹر کلید](../SECURITY-MODEL.md#external-master-key)۔
اگر TGWITNESS_TOKEN دیا جائے تو اس میں کم از کم 24 حروف ہونے چاہییں؛ کرپٹوگرافک طور پر بے ترتیب
قدر استعمال کریں۔ اس کے بغیر ایپ panel-token.txt میں 256 بٹ کا بے ترتیب ٹوکن بناتی ہے۔
ماحولیاتی متغیر سے دی گئی قدر اس فائل کو دوبارہ نہیں لکھتی۔ اسناد تبدیل کرنے کے لیے ری اسٹارٹ کریں۔

ایک ڈیٹا ڈائریکٹری کا مالک صرف ایک ہی پروسیس ہو سکتا ہے۔ کراس پلیٹ فارم OS فائل لاک غلطی سے
بیک وقت لکھنے والے پروسیسز کو روکتا ہے۔ ایک ہی Uvicorn ورکر استعمال کریں۔ پینل کسی بھی تعداد
میں ورک اسپیسز کا انتظام کر سکتا ہے؛ اضافی ورک اسپیسز کی ڈائریکٹریز profiles/<id>/ کے تحت ہوتی ہیں۔
الگ سروس انسٹینسز کے لیے الگ ڈائریکٹریز اور پورٹس استعمال کریں۔ SQLite WAL فائلیں مقامی مستقل
اسٹوریج پر ہونی چاہییں، نیٹ ورک فائل سسٹم پر نہیں۔ ایک والیوم کو کئی ریپلیکاز میں شیئر نہ کریں۔

## Windows پورٹیبل پیکیج

ہر GitHub Release کے ساتھ `TgWitness-<version>-windows-amd64-portable.zip` اور اس کی
`.sha256` فائل ہوتی ہے۔ اس میں python.org کا سرکاری ایمبیڈ ایبل Python 3.12 رن ٹائم (جس کا چیک سم
`tools/build_portable.py` میں پن ہے)، TgWitness اور اس کی پن کی گئی ڈیپنڈنسیز، اور تین لانچرز
شامل ہیں:

| فائل | مقصد |
| --- | --- |
| `TgWitness.cmd` | پینل شروع کرتا ہے؛ اضافی اختیارات آگے منتقل کیے جاتے ہیں، مثلاً `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | `data\demo` میں مصنوعی ڈیمو شروع کرتا ہے |
| `TgWitness-Check.cmd` | شروع کیے بغیر تیاری کی جانچ چلاتا ہے |

پن کی گئی روسی مورفولوجی لغت اور PDF کلر پروفائلز آف لائن استعمال کے لیے پیکیج میں شامل ہیں۔
پیکیجنگ ڈیپنڈنسیز کی `data` ڈائریکٹریز میں صرف ان کے معلوم فائل راستوں کی اجازت دیتی ہے؛
ان ڈائریکٹریز میں کوئی غیر متوقع فائل ہو تو بلڈ ناکام ہو جاتا ہے۔

پورا آرکائیو کسی ایسے فولڈر میں نکالیں جس میں لکھا جا سکے، جیسے `Documents\TgWitness`؛ اسے ZIP
کے اندر سے یا Program Files سے نہ چلائیں۔ رن ٹائم ایک الگ تھلگ ماڈیول پاتھ استعمال کرتا ہے،
اس لیے دوسری Python انسٹالیشنز اور `PYTHONPATH` اس پر اثر انداز نہیں ہوتے۔ ڈیٹا پیکیج کے `data`
فولڈر میں رہتا ہے۔ اپ ڈیٹ کرنے کے لیے TgWitness بند کریں، نیا ورژن نئے فولڈر میں نکالیں
اور `data` فولڈر اس میں کاپی کریں۔

Python 3.12 کے ساتھ 64 بٹ Windows پر اسے خود بلڈ کریں:

~~~sh
python tools/build_portable.py
~~~

## کنٹینر

```sh
docker compose up -d --build --wait
```

یہ /data کے لیے ایک نامزد مستقل والیوم بناتا ہے۔
ویب پورٹ 127.0.0.1:8787 پر میپ ہوتا ہے۔ پروسیس UID 10001 کے طور پر چلتا ہے، ہٹائی گئی
capabilities، صرف پڑھنے کے قابل روٹ فائل سسٹم، اور قابلِ تحریر /data اور /tmp کے ساتھ۔
`--wait` واپس آنے سے پہلے ویب سرور کی صحت جانچتا ہے؛ Telegram اتھارائزیشن اور ڈیلیوری کی صورتحال
پینل میں نظر آتی ہے۔ فراہم کردہ ہیلپرز بلڈ کے بعد تیاری کے لیے 180 سیکنڈ کا ٹائم آؤٹ استعمال کرتے
ہیں۔ ابتدائی ڈیپنڈنسیز کی ڈاؤن لوڈ اس سے زیادہ وقت لے سکتی ہے۔

دونوں بنیادی Compose فائلیں پروجیکٹ کا نام `tgwitness` استعمال کرتی ہیں، اس لیے نئی ریلیز کسی
دوسری ڈائریکٹری میں نکالنے سے خاموشی سے نیا ڈیٹا والیوم منتخب نہیں ہوتا۔ اس پروجیکٹ کے لیے صرف
ایک تعیناتی فعال رکھیں۔ آزاد انسٹالیشنز کے لیے منفرد `docker compose -p NAME ...` اور مختلف ہوسٹ
پورٹ استعمال کریں، اور اپ ڈیٹس کے دوران دونوں برقرار رکھیں۔ اگر کوئی پرانی تعیناتی مختلف پروجیکٹ
نام استعمال کرتی ہے تو `-p` کے ساتھ اس کا اصل نام استعمال کرتے رہیں؛ `docker compose ls` موجودہ
پروجیکٹس کی فہرست دکھاتا ہے۔

`deploy/env.example` کو `.env` میں کاپی کریں اور کوئی دوسرا لوپ بیک پورٹ استعمال کرنے کے لیے
`TGWITNESS_PORT` بدلیں۔ مثال کے طور پر `TGWITNESS_PORT=8788` پینل کو
`http://127.0.0.1:8788` پر دستیاب کرتا ہے؛ کنٹینر اب بھی 8787 پر سنتا ہے۔ `.env` کو Git نظر انداز کرتا ہے۔

ابتدائی ٹوکن حاصل کریں:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

مفید کمانڈز:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` کریش یا Docker ڈیمن کے ری اسٹارٹ کے بعد جمع کنندہ کو دوبارہ شروع کرتا ہے۔
Linux سرور پر اپنی ڈسٹری بیوشن کے سروس مینیجر سے بوٹ کے وقت Docker فعال کریں، عام طور پر
`sudo systemctl enable --now docker`۔ Windows/macOS پر Docker Desktop کی سائن ان پر خود شروع
ہونے والی ترتیب فعال کریں۔ ڈیسک ٹاپ سے سائن آؤٹ، سلیپ یا رکا ہوا Docker ڈیمن جمع آوری میں خلل
ڈال سکتا ہے۔ جو کنٹینر واضح طور پر روکا گیا ہو وہ تب تک رکا رہتا ہے جب تک آپ اسے دوبارہ شروع نہ کریں۔

مثالی کنفیگریشن میں /tmp والیوم 512 MiB تک محدود ہے۔ ایکسپورٹ کی تیاری اس کے بجائے مستقل /data
پر ہر ورک اسپیس کی `temporary-exports/` استعمال کرتی ہے۔ وہاں بیک وقت چلنے والے ایکسپورٹس،
جرنل/WAL کے بڑھنے، میڈیا اور بیک اپس کے لیے جگہ مخصوص رکھیں۔
لانچر رن ٹائم ڈیپنڈنسیز کے توثیق شدہ ورژنز پن کرنے کے لیے deploy/constraints.txt استعمال کرتا ہے۔
Docker اور اعلیٰ یقین دہانی والے سرورز deploy/requirements.lock اور deploy/build.lock سے
pip --require-hashes کے ساتھ انسٹال کرتے ہیں: ہر پیکیج فائل کا کمٹ میں درج SHA-256 سے مطابقت رکھنا
ضروری ہے، اس لیے PyPI یا کسی مرر پر بدلی گئی فائل مسترد ہو جاتی ہے۔ Python بیس امیج اور آپریٹنگ
سسٹم کے پیکیجز کو اب بھی ریلیز کی آزادانہ توثیق درکار ہے۔

جب تک آپ جرنل اور کلیدیں تلف کرنے کا ارادہ نہ رکھتے ہوں، docker compose down -v استعمال نہ کریں۔
کنٹینر کی صحت ویب سرور کی دستیابی بتاتی ہے، Telegram سے کامیاب کیپچر نہیں۔
پینل میں جمع کنندہ کی حالت، ہارٹ بیٹ، خرابیاں اور کوریج ایونٹس دیکھیں۔

### آزاد گواہ کا پروفائل

اختیاری `witness` سروس ایک [آزاد گواہ](../WITNESS.md) کو اس کے اپنے کنٹینر میں چلاتی ہے؛ اس کی
اپنی کلید اور جرنل `witness-data` والیوم میں ہوتے ہیں، اور جمع کنندہ تک رسائی کے لیے اس کے پاس صرف
پڑھنے والا گواہ ٹوکن ہوتا ہے۔ ٹوکن پینل میں **مزید اوزار → اضافی سہولیات → آزاد شاہد** کے تحت بنائیں،
اسے بوٹ ٹوکن اور چینل کے ساتھ `.env` میں شامل کریں، پھر پروفائل شروع کریں:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

سروس Compose نیٹ ورک کے اندر جمع کنندہ تک `http://tgwitness:8787` پر پہنچتی ہے
(`TGWITNESS_WITNESS_COLLECTOR` اسے بدل دیتا ہے، مثلاً کسی دوسری ورک اسپیس کے لیے
`/profiles/<workspace ID>`)۔ اگر گواہ کسی الگ سرور پر ہو اور اسے کوئی اور چلائے، تو وہاں
`deploy/compose/compose.witness.yaml` استعمال کریں اور `TGWITNESS_WITNESS_COLLECTOR` کو جمع کنندہ
کے HTTPS پتے پر سیٹ کریں؛ اس فائل میں صرف گواہ شامل ہے۔

## شائع شدہ امیج انسٹال کریں

`deploy/env.example` کو `.env` میں کاپی کریں۔ `TGWITNESS_IMAGE` کو شائع شدہ ورژن پر سیٹ کریں اور
ریپوزیٹری کا راستہ **چھوٹے انگریزی حروف** میں لکھیں، مثلاً:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.9.3
TGWITNESS_PORT=8787
```

`compose.yaml` کے بجائے اس فائل کو اکیلے چلائیں:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

ہوسٹ پر سورس بلڈ، Python یا کمپائلر کی ضرورت نہیں۔ ریلیز ورک فلو Linux AMD64 اور ARM64
کنٹینرز کو ہدف بناتا ہے، بشمول Docker Desktop کی Linux VM۔
ورک فلو کے خلاصے سے ورژن ٹیگ یا `ghcr.io/owner/repository@sha256:...` استعمال کریں۔
نہ کوئی بدلتا ہوا `latest` ٹیگ ترتیب دیا گیا ہے اور نہ بغیر نگرانی کے ایپلیکیشن اپ گریڈ۔
پروجیکٹ کا نام ایک ہو تو امیج اور سورس والی صورتیں ایک ہی ڈیٹا والیوم استعمال کرتی ہیں۔

## سرور پر خودکار HTTPS

ایسا سرور استعمال کریں جس پر Docker ہو، ایک ڈومین جو آپ کے کنٹرول میں ہو، اور مستقل مقامی اسٹوریج۔
ڈومین کے A/AAAA ریکارڈز سرور کی طرف کریں؛ AAAA صرف تب شائع کریں جب IPv6 کے ذریعے سرور تک پہنچا
جا سکے۔ سرٹیفکیٹ کے اجرا کے لیے آنے والے TCP 80 اور 443 اور جانے والے DNS/HTTPS کی اجازت دیں۔
یہ پورٹس پہلے سے کسی دوسری سروس کے استعمال میں نہیں ہونے چاہییں۔

`deploy/env.example` کو `.env` میں کاپی کریں اور اسکیم یا پاتھ کے بغیر ہوسٹ نیم سیٹ کریں:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

HTTPS اوورلے کے ساتھ سورس بلڈ شروع کریں:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

شائع شدہ امیج کے لیے اس کے بجائے پہلی فائل کے طور پر `deploy/compose/compose.image.yaml` استعمال
کریں۔ بعد کی اسٹیٹس، لاگز، اپ ڈیٹ اور اسٹاپ کمانڈز کے لیے بھی دونوں `-f` آرگیومنٹس برقرار رکھیں۔

Caddy سرٹیفکیٹ حاصل کرتا اور اس کی تجدید کرتا ہے، HTTP کو HTTPS پر ری ڈائریکٹ کرتا ہے، اور
درخواستیں نجی Compose نیٹ ورک پر جمع کنندہ کو بھیجتا ہے۔ سرٹیفکیٹ کی حالت کا اپنا مستقل والیوم ہے۔
جمع کنندہ کا براہِ راست ہوسٹ پورٹ صرف لوپ بیک تک محدود رہتا ہے۔
فراہم کردہ Caddy کنفیگریشن رسائی کی لاگنگ فعال نہیں کرتی۔

`https://watch.your-domain.org` کھولیں اور پینل ٹوکن درج کریں۔ Compose کی تیاری صرف کنٹینرز سے
متعلق ہے؛ سرٹیفکیٹ کا اجرا اور باہر سے رسائی DNS اور فائر وال پر منحصر ہے۔ اگر HTTPS تیار نہ ہو
تو DNS، فائر وال کے قواعد اور درج ذیل کا معائنہ کریں:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

فراہم کردہ Caddy امیج اپنے `2-alpine` ٹیگ کی پیروی کرتی ہے۔ pull کرنے سے وہ امیج تازہ ہو جاتی ہے؛
اگر آپ کو انفراسٹرکچر کے مقررہ ورژنز چاہییں تو اپنی تعیناتی میں جانچا ہوا ڈائجسٹ پن کریں۔

## اپ ڈیٹس اور بیک اپس

اپ ڈیٹس کے دوران Compose پروجیکٹ کا نام اور ڈیٹا والیوم برقرار رکھیں۔ پہلے جمع کنندہ روکیں
اور مکمل بیک اپ بنائیں۔ طے شدہ سورس پر مبنی تعیناتی کے لیے:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

ہر بار ریپوزیٹری سے باہر نئی بیک اپ منزل استعمال کریں اور اسے اکاؤنٹ تک رسائی دینے والے مواد
کی طرح محفوظ رکھیں۔ مثال کا راستہ صرف وضاحت کے لیے ہے؛ اپنی نجی بیک اپ جگہ استعمال کریں۔
پوری ڈائریکٹری کاپی کریں، بشمول پوشیدہ فائلیں، تمام ورک اسپیسز، کلیدیں، جرنلز اور میڈیا۔
اگر بیرونی والٹ ماسٹر کلید ترتیب دی گئی ہو تو اس کا بیک اپ الگ سے لیں۔
ثبوت کی ZIP ایپلیکیشن کا ایسا بیک اپ نہیں جس سے بحالی ہو سکے۔ HTTPS کے لیے، اگر Caddy کے
سرٹیفکیٹ/اکاؤنٹ کی حالت برقرار رکھنی ہو تو اس کے والیومز بھی محفوظ کریں۔

سورس تعیناتی کے لیے نئی ریلیز کی فائلیں حاصل کریں اور چلائیں:

```sh
docker compose up -d --build --wait
```

امیج تعیناتی کے لیے `TGWITNESS_IMAGE` کو مطلوبہ ورژن پر بدلیں، پھر چلائیں:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

اوپر کی stop/copy کمانڈز کے لیے بھی اپنی انسٹالیشن کی Compose فائل (یا فائلیں) استعمال کریں۔
`.env`، اپنی مرضی کی کنفیگریشن اور وہی پروجیکٹ نام برقرار رکھیں۔ `down` نامزد والیومز باقی رکھتا ہے؛
**`down -v` انہیں حذف کر دیتا ہے**۔ `.venv` کو مختلف آپریٹنگ سسٹمز یا Python ورژنز کے درمیان
کاپی نہ کریں۔ نیٹو اپ ڈیٹ کے لیے TgWitness روکیں، اس کی پوری ڈیٹا ڈائریکٹری کا بیک اپ لیں،
سورس فائلیں بدلیں اور لانچ سے پہلے `python start.py --setup-only` چلائیں۔

اپ ڈیٹ کے بعد پینل تک رسائی، اکاؤنٹ کی شناخت، مشاہدے کی حالت اور کوریج چیک کریں۔ ری اسٹارٹ
کے بعد TgWitness محفوظ کی گئی Telegram اپ ڈیٹ پوزیشن سے دوبارہ شروع کرتا ہے اور اپ ڈیٹ کے دوران
چھوٹ جانے والی اپ ڈیٹس طلب کرتا ہے۔ اگر کوئی آئندہ ورژن اسٹوریج فارمیٹس بدلے تو رول بیک کے لیے
اپ ڈیٹ سے پہلے کا بیک اپ درکار ہو سکتا ہے۔

## ریموٹ سرور

سروس کو لوپ بیک پر رکھیں اور SSH ٹنل استعمال کریں، یا HTTPS کو ریورس پراکسی پر ٹرمینیٹ کریں۔
بنیادی Compose فائل صرف مقامی رسائی کے لیے ہے؛ اختیاری `deploy/compose/compose.https.yaml` اوورلے
ترتیب دیے گئے ڈومین کے لیے Caddy فراہم کرتا ہے۔ bearer ٹوکن کو URLs اور پراکسی لاگز سے باہر رکھیں۔
ریورس پراکسی کو درخواست کا سائز اور کنیکشن کی شرح محدود کرنی چاہیے۔ سادہ HTTP کو انٹرنیٹ پر نہ کھولیں۔

systemd، Windows لاگ آن ٹاسک، macOS یوزر ایجنٹ اور Caddy کی مثالیں
[deploy/](../../deploy/README.md) میں دی گئی ہیں۔ انسٹالیشن سے پہلے ان کے راستے جانچیں اور اپنے
مطابق ڈھالیں۔ یہ فراہم کردہ ٹیمپلیٹس ہیں، مقامی طور پر چلا کر کی گئی پلیٹ فارم کی توثیق نہیں۔
عام لانچر کوئی بیک گراؤنڈ سروس یا ٹاسک رجسٹر نہیں کرتا۔

Windows پر بغیر ونڈو کے `pythonw.exe` لانچ میں اسٹارٹ اپ/سرور کی تشخیصی معلومات ڈیٹا ڈائریکٹری
کے تحت `logs/server.log` میں محفوظ ہوتی ہیں (فی فائل 5 MiB، روٹیشن کی دو بیک اپ فائلیں)۔
کنسول سے لانچ میں لاگنگ کنسول میں ہی رہتی ہے۔ HTTP رسائی کی لاگنگ دونوں موڈز میں بند ہے۔
لاگز کو ڈیٹا ڈائریکٹری کی طرح ہی محفوظ رکھیں اور شیئر کرنے سے پہلے ان کا جائزہ لیں۔

## ری اسٹارٹ اور خلا

آخری بار طلب کی گئی مشاہدے کی حالت محفوظ رہتی ہے۔ اگر مشاہدہ فعال تھا تو اسٹارٹ اپ دوبارہ
جڑنے اور منتخب ماخذوں کو بحال کرنے کی کوشش کرتا ہے۔ دستی طور پر روکنے سے یہ ارادہ ختم ہو جاتا
ہے۔ ناکام ری اسٹارٹ ریکارڈ ہوتا ہے اور پینل میں دکھایا جاتا ہے۔

TgWitness اکاؤنٹ اور ہر چینل کے لیے Telegram کی اپ ڈیٹ پوزیشن (pts، qts، seq اور date) ورک اسپیس
کے والٹ میں محفوظ کرتا ہے اور اگلی بار شروع ہونے پر اسے بحال کرتا ہے۔ پھر کلائنٹ وہ اپ ڈیٹس طلب
کرتا ہے جو پروسیس بند رہنے کے دوران چھوٹ گئیں، اور وقتاً فوقتاً ہونے والی دوبارہ جانچ چھوٹے ہوئے
پیغامات بحال کرتی ہے اور اُن محفوظ پیغامات کو ریکارڈ کرتی ہے جو Telegram اب واپس نہیں کرتا۔
شروع ہونے پر ڈائیلاگز دوبارہ لوڈ ہوتے ہیں۔ ہر اسٹارٹ اپ پچھلے جرنل ہیڈ، آف لائن حد اور اُس
اپ ڈیٹ پوزیشن کو ریکارڈ کرتا ہے جہاں سے کام دوبارہ شروع ہوا۔
مانیٹر ہر 10 سیکنڈ میں کنیکٹیویٹی جانچتا ہے اور ہر منٹ ایک ہارٹ بیٹ شامل کرتا ہے
(**مزید اوزار → پیرامیٹرز → سرگرمی کا ریکارڈ ہر**)۔
کنیکشن ٹوٹنے اور خاموشی کے ادوار کو ان کی وجہ کے ساتھ کوریج کے خلا کے طور پر ریکارڈ کیا جاتا ہے۔
ہسٹری اسنیپ شاٹس لائیو ریکارڈز کے ساتھ الگ موجودہ ہسٹری مشاہدات کے طور پر محفوظ ہوتے ہیں۔

میڈیا کی قطار ہر ورک اسپیس کے SQLite ڈیٹا بیس میں محفوظ ہوتی ہے۔ پیغام اور اس کا کام ایک ہی
ایٹمی کمٹ میں محفوظ ہوتے ہیں۔ جو کام چلتے ہوئے منقطع ہو گئے ہوں، وہ اسٹارٹ پر دوبارہ کوشش کے لیے
بحال کیے جاتے ہیں۔ ہر ڈاؤن لوڈ کا بنیادی ٹائم آؤٹ 120 سیکنڈ ہے، جس میں فائل کے سائز کے حساب سے
256 KiB/s کی رفتار پر درکار وقت جمع ہوتا ہے، اور ہر اٹیچمنٹ کی قسم کے لیے 1–2,000 MiB کی حد ہے؛
ٹائم آؤٹ، رفتار اور دوبارہ کوششیں **مزید اوزار → پیرامیٹرز** میں ہیں۔ جمع کنندہ
اُن فائلوں کو چھوڑ دیتا ہے جن کا سائز معلوم نہ ہو۔ روکنے پر قطار میں موجود کام برقرار رہتا ہے۔
دوبارہ کوشش اصل مشاہدہ شدہ فائل ڈسکرپٹر استعمال کرتی ہے، بعد میں ترمیم ہونے والے پیغام کا تازہ
ترین ورژن کبھی نہیں۔ عارضی ناکامیوں کے لیے دوبارہ کوششوں کی تعداد محدود ہے؛ میڈیا کے FloodWait
وقفے ری اسٹارٹ کے بعد بھی برقرار رہتے ہیں۔ میڈیا کی بحالی Telegram اپ ڈیٹس کی بحالی سے الگ ہے
اور غائب ہو چکی فائلیں دوبارہ نہیں بنا سکتی۔

## بیک اپ، بحالی اور گنجائش

**پوری ڈیٹا ڈائریکٹری** کاپی کرنے سے پہلے پروسیس روک دیں، بشمول vault.key، signing.enc،
credentials.enc، SQLite ڈیٹا بیس/WAL فائلیں، میڈیا، ٹوکن، چیک پوائنٹس اور profiles/ کی تمام
ذیلی ڈائریکٹریز۔ مکمل کاپی اُس وقت بحال کریں جب منزل والی سروس بند ہو۔ والٹ کلیدیں موجود نہ ہوں
یا سائننگ کلید میل نہ کھائے تو اسٹارٹ اپ ناکام ہو جاتا ہے؛ رسائی زبردستی حاصل کرنے کے لیے کلیدیں
دوبارہ نہ بنائیں۔

خفیہ معلومات والے بیک اپس کو انکرپٹڈ اور رسائی کے کنٹرول میں رکھیں۔ ثبوت کی ZIP فائلیں جائزے کے
لیے قابلِ منتقلی مواد ہیں، ایپلیکیشن بیک اپ یا Telegram سیشن بیک اپ نہیں۔
مدتِ محفوظگی پوری ہونے پر خودکار حذف کا کوئی نظام نہیں۔ تمام پیغامات، خام میٹا ڈیٹا، میڈیا،
عارضی ایکسپورٹس اور بیک اپس کے لیے ڈسک کی جگہ کی منصوبہ بندی کریں۔

اسٹارٹ اپ کی تصدیق اور ایکسپورٹ پورا جرنل لوڈ کرنے کے بجائے ریکارڈز کو اسٹریم کرتے ہیں۔
ایکسپورٹ ایک ریڈ اسنیپ شاٹ پن کرتا ہے جبکہ WAL میں نئی تحریر جاری رہ سکتی ہے؛ طویل ایکسپورٹس
WAL صفحات کو روکے رکھ سکتے ہیں، اس لیے ڈسک کی گنجائش پھر بھی اہم ہے۔ آزاد ویریفائر کی طے شدہ حد
سے مطابقت کے لیے ZIPs غیر کمپریسڈ حالت میں 4 GiB تک محدود ہیں؛
**مزید اوزار → پیرامیٹرز → سب سے بڑا دستخط شدہ ZIP** یہ حد بڑھاتا ہے، اور ایسے آرکائیوز کی تصدیق
`verify.py --max-gib N` سے کی جاتی ہے۔ دوسرے فارمیٹس پر ایونٹس کی تعداد کی کوئی حد نہیں۔
معاون براؤزر جواب کے حصے صارف کی منتخب کردہ فائل میں اسٹریم کرتے ہیں۔ دوسرے براؤزر زیادہ سے زیادہ
128 MiB بفر کرتے ہیں اور بڑی منتقلیوں کے لیے اتھینٹیکیٹڈ CLI کی طرف بھیجتے ہیں:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

دوسری ورک اسپیس کے لیے **ایکسپورٹس → ورک اسپیس آئی ڈی** سے `--profile ID`،
`--format zip|jsonl|csv|html`، ریموٹ سرور کے لیے `--url https://your-server`، یا 5 GiB کی
ٹرانسفر حد بدلنے کے لیے `--max-mib` استعمال کریں۔ سادہ HTTP کی اجازت صرف لوپ بیک کے لیے ہے۔
ٹوکنز ہیڈرز میں بھیجے جاتے ہیں، ری ڈائریکٹس مسترد کیے جاتے ہیں، موجودہ فائلیں اوور رائٹ نہیں
ہوتیں، اور نامکمل ڈاؤن لوڈز مکمل فائلوں کے طور پر شائع نہیں کیے جاتے۔
اگر TGWITNESS_TOKEN بنائے گئے ٹوکن کی جگہ لیتا ہے تو اسی فعال قدر پر مشتمل الگ سے محفوظ کی گئی
فائل استعمال کریں: یہ متبادل قدر panel-token.txt کو دوبارہ نہیں لکھتی۔
کمانڈ کا SHA-256 صرف منتقلی کا چیک سم ہے؛ دستخط شدہ ZIP کی تصدیق آزادانہ طور پر کریں۔

پینل قطار میں موجود/ناکام میڈیا، سب سے پرانا زیرِ التوا میڈیا، خالی ڈسک، Telegram درخواستوں کے
وقفے اور وہ ماخذ دکھاتا ہے جن تک رسائی کی تصدیق نہیں ہوئی۔ یہ تشخیصی معلومات ترسیل کی مکمل
اینڈ ٹو اینڈ نگرانی نہیں ہیں۔ ورک اسپیسز ایک ہی پروسیس شیئر کرتی ہیں؛ بہت زیادہ سرگرم اکاؤنٹ
پھر بھی دوسروں کو متاثر کر سکتا ہے۔ الگ ورکر پروسیسز، مدتِ محفوظگی/روٹیشن، پائیدار اپ ڈیٹ بحالی
اور تعیناتی کی مکمل توثیق ابھی باقی ہیں۔ پینل تک محدود دائرے والی رسائی
[رسائی اور اجازتیں](../ACCESS.md) میں بیان کی گئی ہے؛ آزاد چیک پوائنٹس کا احاطہ
[گواہ کی رہنما](../WITNESS.md) میں ہے۔
