# Безопасность и обработка данных

На этой странице описаны вопросы доступа, хранения и защиты сети в локальной рабочей среде или на сервере.
Что касается сбора данных на GitHub Runner или в конфиденциальной виртуальной машине Intel TDX, см.
[режимы верификации](../EVIDENCE.md#verification-scope), которые предусматривают дополнительные проверки среды сбора данных.
Для подключений аккаунтов, уведомлений, временных меток, внесайтовых копий и свидетелей предусмотрены собственные настройки маршрутизации.

| Площадь | Короче говоря |
| --- | --- |
| Доступ | Ключ администратора плюс доступ к аккаунтам и чатам с ограниченной областью действия, семь прав доступа и сеансы с возможностью отзыва; по умолчанию — localhost |
| Секреты в покое | Сессия, пара API, ключ подписи и настройки прокси шифруются с помощью алгоритма Fernet |
| Сообщения и мультимедиа | Файлы в рабочей области, защищенные с помощью шифрования диска или тома, а также с помощью прав доступа к файлам на хост-компьютере |
| Честность | Цепочка хэшей SHA-256 и подпись Ed25519 для каждой записи |
| Внешнее время | RFC 3161 и квитанции OpenTimestamps, записи свидетелей с датой от Telegram и подтверждение GitHub; сохраненные контрольные точки, записи свидетелей и измерения Intel TDX служат в качестве подтверждающих данных. Верификатор сообщает, каким условиям в отношении доказательств они соответствуют |

Информацию о сообщениях об уязвимостях см. в [политике безопасности](../../.github/SECURITY.md).

<a id="access-model"></a>
## Модель доступа

Токен главной панели предоставляет полный контроль. Другие пользователи могут получить собственный
[ограниченный доступ](../ACCESS.md): выбранные рабочие пространства и чаты, права доступа, срок действия,
ограничения по IP-адресам, ограничения на вход и отзывные сессии. Пользователь с доступом, ограниченным чатом,
не может выполнять операции, затрагивающие всё рабочее пространство, даже если соответствующее право отмечено.
Каждая рабочая область имеет собственный журнал, хранилище и ключ подписи в рамках одного процесса;
разделение пользователей на хосте осуществляется с помощью учётных записей операционной системы.

По умолчанию панель прослушивает соединения на localhost. При входе через браузер токен доступа
обменивается на сессионные учетные данные; браузер отправляет их в виде токена «bearer». Они хранятся
в sessionStorage, а не в файле cookie аутентификации. Блокировка или выход из системы очищает
сессию браузера. Закрытие браузера или завершение сессии не останавливает сбор данных.

Выданные токены и учетные данные сеанса хранятся в виде хэшей в зашифрованном хранилище.
Отзыв токена приводит к завершению связанных с ним сеансов; изменения прав доступа влияют на последующие
запросы. Загруженные файлы невозможно отозвать. Администратор также может ограничить свои
собственные сеансы браузера, однако скрипты, напрямую использующие токен главной панели, сохраняют
полный доступ и обходят эти ограничения сеансов браузера.

На количество неудачных попыток аутентификации накладывается ограничение по адресу клиента. При ограничении по IP-адресу используется
адрес, видимый приложению; прежде чем полагаться на это, проверьте поведение обратного прокси-сервера.
Учетные данные «Witness» остаются отдельными учетными данными для проверки работоспособности и контрольных точек, доступными только для чтения.

<a id="demo-access"></a>
### Доступ к демо-версии

`/api/demo-access` — это намеренно неавторизованный начальный механизм для явно
запущенной, изолированной синтетической демонстрации. Он выдаёт отдельную способность, действующую в течение срока жизни процесса,
но никогда не выдаёт реальный токен панели или переопределение TGWITNESS_TOKEN. Для выдачи и использования требуются
узел обратной связи и хост, отсутствие перенаправленных заголовков и отсутствие междоменных запросов. Дополнительные
рабочие пространства или авторизованная сессия отключают этот путь. Активные рабочие пространства никогда не выдают
эту возможность. Демо-версия не может связывать аккаунты или изменять настройки сбора данных.

<a id="panel-content-and-exports"></a>
## Содержимое панели и экспорт данных

Панель не использует внешних шрифтов, аналитических инструментов, ресурсов CDN или встроенных удаленных медиафайлов.
Текст из Telegram вставляется в виде текста, а не HTML. Загруженные вложения
предоставляются в виде двоичных вложений. При экспорте в формат JSONL исходные строки сохраняются без изменений; в HTML они
подвергаются экранированию; ячейки CSV, которые могут содержать формулы, снабжаются префиксом в виде апострофа.

Экспортные данные не включают секретные ключи аутентификации и подписи, но намеренно содержат
собранные метаданные исходного кода, идентификаторы и, возможно, личную или конфиденциальную информацию.
В необработанных метаданных исходного кода могут встречаться хэши доступа Telegram и ссылки на файлы.

<a id="secrets-at-rest"></a>
## Тайны в покое

Учетные данные API Telegram, сессия и ключ подписи шифруются с помощью алгоритма Fernet.
Для локальных сообщений и мультимедиа шифрование обеспечивается диском или томом хоста;
в рабочей области хранятся обычные файлы. При экспорте может использоваться ZIP-архив с шифрованием AES-256, защищённый паролем,
а для удалённых копий применяется алгоритм AES-256-GCM.

По умолчанию ключ хранилища находится в каталоге защищенных данных. Для его отдельного хранения используйте внешний файл мастер-ключа,
указанный ниже. В Unix новые файлы закрытых ключей используют режим доступа 0600, а новые каталоги данных —
0700; в Windows установите список контроля доступа (ACL) каталога для учётной записи службы и
авторизованных администраторов. Существующие права доступа к каталогу сохраняются.

<a id="external-master-key"></a>
### Внешний мастер-ключ

Для нового каталога данных переменная TGWITNESS_VAULT_KEY_FILE может предоставлять внешний случайный
главный ключ. С помощью алгоритма HKDF-SHA256 и отдельного случайного солевого значения выводится отдельный ключ Fernet
для каждой рабочей области. Файл vault.external.json необходимо сохранить для восстановления. Отсутствие или
неверность мастер-ключей приводит к сбою с закрытием. Существующие локальные хранилища не мигрируются автоматически.
На панели отображается выбранный режим хранения ключей. Шифрование диска защищает локальные
сообщения и медиафайлы в любом режиме; подробности настройки см. в разделе
[защита соединения и данных](../CONNECTION-SECURITY.md).

<a id="proxies-and-network-routes"></a>
## Прокси-серверы и сетевые маршруты

Настройки прокси зашифрованы в хранилище. Пароли и секретные данные MTProxy
не возвращаются API и не записываются в протоколы. Каждая рабочая область выбирает
свой маршрут Telegram и [режим IP](../CONNECTION-SECURITY.md#ip-modes).

**«Скрыть адрес»** блокирует прямой доступ к Telegram в режиме резервного доступа и требует использования прокси для внешних
HTTP-запросов. Явно выбранный режим резервного доступа разрешает прямой доступ к Telegram
после некоторой задержки; режим «туннель/VPN» разрешает прямые маршруты. Выбор режима «туннель»
не приводит к установке или проверке VPN. Эти настройки не контролируют весь трафик
компьютера, браузеры, менеджеры пакетов или разрешение DNS локального прокси-хоста.

MTProxy передаёт только трафик Telegram. Для внешних запросов можно использовать отдельный
прокси SOCKS5/HTTP, маршрут SOCKS5/HTTP рабочей среды или разрешённый прямой маршрут;
их также можно отключить. Независимый свидетель имеет собственные настройки транспорта.
Обычная аутентификация SOCKS5/HTTP CONNECT не шифруется самими этими
прокси-протоколами. Поддельные секретные ключи TLS для MTProxy по-прежнему не поддерживаются.

<a id="sign-in-and-session-imports"></a>
## Импорт данных входа в систему и сеансов

Преобразованные файлы .tgwitness-session содержат секретный ключ авторизации в виде открытого текста до тех пор, пока
они не будут загружены и сохранены в хранилище. Автономный интерфейс командной строки поддерживает проверенные схемы Telethon.
Функция импорта в панели управления дополнительно поддерживает Pyrogram SQLite, современный формат TData ZIP для одной учетной записи,
а также задокументированные входы в формате JSON. Она проходит аутентификацию, ограничена четырьмя файлами / 8 MiB,
и обрабатывает загрузки в памяти без извлечения архива или сохранения исходных файлов.
Нормализованные учетные данные возвращаются только запрашивающему авторизованному браузеру;
они сохраняются в зашифрованном хранилище после успешной авторизации в Telegram.
Защищайте исходные и преобразованные файлы и не допускайте одновременного клонирования авторизации несколькими клиентами.

При обработке данных проверяются контрольные суммы контейнеров, хэши локального дешифрования и длины структур.
Указанный локальный пароль Desktop используется временно и не сохраняется.
Ограниченный парсер поддерживает форматы Desktop, которые он проверяет, и отклоняет остальные.
Изображения QR-кодов генерируются локально, содержат краткосрочные токены входа в Telegram и
никогда не отправляются во внешний сервис рендеринга. Блокировка, переключение рабочего пространства, новый вход
и изменения маршрута отменяют ожидающие попытки сканирования QR-кода. Перезагрузка или закрытие вкладки может привести к тому, что
попытка останется в ожидании до истечения срока действия. Успешный вход с помощью QR-кода по-прежнему требует привязки учетной записи.
Размер обычных тел запросов API по-прежнему ограничен 16 КиБ; маршрут импорта с аутентификацией принимает
до 12 МиБ закодированного JSON, при этом отдельно применяется ограничение на размер декодированного файла.

Коды входа и пароли для двухэтапной аутентификации в Telegram не сохраняются. Состояние номера телефона/хеша кода
хранится в памяти на время авторизации. Сессии в Telegram предоставляют доступ к учетной записи; ни в коем случае
не загружайте на GitHub каталог данных, сессию, токен, ключ хранилища или закрытый ключ подписи.

<a id="logs-and-transport"></a>
## Лесоматериалы и транспорт

Ответ по проверке API по умолчанию заменяется, чтобы в нём не отображались
значения учетных данных. Регистрация доступа приложений отключена. Не настраивайте обратный прокси-сервер
на регистрацию заголовков авторизации или тел запросов. Панель прослушивает порт на localhost;
удаленный доступ осуществляется через предоставленный SSH-туннель, Cloudflare Tunnel или Caddy HTTPS,
поэтому токены и секретные данные для входа передаются внутри SSH или TLS.

<a id="integrity-and-external-time"></a>
## Целостность и внешнее время

В ходе проверки подписи записей, цепочка хешей, вложения и манифест экспорта
сравниваются с ключом сборщика. Действительная подпись свидетельствует о том, что байты не изменились с момента
их подписания. Каждая рабочая область создаёт свой ключ подписи при первом запуске и отображает его
отпечаток на панели и в каждом экспорте. Оператор передаёт отпечаток
получателю по отдельному каналу, а `--fingerprint` фиксирует ключ.

Изменение, вставка или удаление записи приводит к разрыву хеш-цепочки или подписи, и
проверяющая сторона фиксирует это. Внешние временные метки и «свидетель» также фиксируют журнал за пределами
рабочей области. Триггеры SQLite на таблице журнала лишь предотвращают
случайную перезапись или удаление записи приложением. `TGWITNESS_VAULT_KEY_FILE` обеспечивает, чтобы ключ хранилища
не попадал в копию каталога данных.

RFC 3161, квитанции OpenTimestamps и сообщения свидетелей, даты которых верификатор извлекает
из Telegram, привязывают префикс журнала, который они охватывают, к времени, установленному третьей стороной.
Раунд drand, записанный в журнал, показывает, что записи, следующие за ним, были созданы не
ранее публикации этого раунда.
Проверенное подтверждение GitHub также содержит проверенное время своей подписи, что
привязывает весь архив к внешнему времени.
Контрольная точка подписывается ключом сборщика и привязывает записи, предшествующие ей, с
момента получения её получателем через другой канал. Свидетельство показывает, что второй
ключ хранил начало журнала; запись о контроле ключей хранителя показывает, кто владеет этим
ключом. Оба являются вспомогательными проверками; минимум — это время, установленное третьей стороной.
[GitHub Actions capture](../SEALED-ACTIONS.md)
или
[развертывание Intel TDX](../PHALA.md#confidential-vm-on-phala-cloud-intel-tdx)
добавляют информацию о происхождении рабочего процесса или аппаратные измерения среды сбора данных.

В каждом ответе по проверке перечислены условия доказательств с указанием способа проверки каждого из них,
сгруппированные по их роли в минимальном наборе:

| Роль | Состояние |
| --- | --- |
| Обязательно | Целостность; ключ подписавшего закреплён с помощью `--fingerprint`; внешнее время, охватывающее последнюю запись (подтверждение получения по RFC 3161 проверено с помощью `--tsa-ca`, подтверждение получения от OpenTimestamps подтверждено с помощью `--check-bitcoin`, сообщение свидетеля прочитано на t.me с помощью `--channel`, печать свидетеля в Bitcoin или проверенное подтверждение на GitHub) |
| Дополнительные, не входящие в минимальный набор | Свидетель с собственным ключом; сохраненная контрольная точка; заверенный цикл сбора данных |

**Минимальным требованием для подтверждения** является выполнение всех трёх обязательных условий в отношении последней экспортированной
записи; проверенный и заверенный цикл сбора данных добавляет профиль `attested`.
В последней строке указывается результат, а в ответе перечисляются варианты, которые удовлетворяют
невыполненным условиям. Без `--fingerprint` последняя строка начинается с
`EVIDENCE: minimum not met · missing: confirmed signer key`.
Когда проверенные временные метки охватывают только более ранние записи, в ответе указывается запись, до
которой выполняется минимальное условие. `--require evidence` или `--require attested` завершаются с кодом 2, когда
профиль не достигается для всего экспорта, а проверка, запрошенная в командной
строке, которую невозможно выполнить, отмечается как невыполненная с тем же кодом. Каждый отчёт
содержит те же условия с указанием их состояния в данной копии и команды, которая их
проверяет. Уровни достоверности и `--strict` остаются доступными; в
[формате доказательств](../EVIDENCE.md#verification-scope) перечислены проверки для каждого режима сбора данных.

<a id="if-you-suspect-a-problem"></a>
## Если вы подозреваете, что возникла проблема

Сохраните исходный каталог с данными и используйте для анализа отдельную копию.
Сообщите о затронутой версии, операции и шагах, позволяющих воспроизвести проблему, через
[политику безопасности](../../.github/SECURITY.md), не раскрывая данные учетной записи и учетные данные.
