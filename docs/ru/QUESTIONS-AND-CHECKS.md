# Вопросы и проверки

[Независимая проверка](TRUST.md) · [Что подтверждает запись](FOR-THE-RECORD.md) · [Запись проверки](VERIFICATION.md)

Каждый приведённый ниже ответ указывает, что подтверждает запись, и содержит команду или файл для её проверки. Проверки не зависят от доверия к оператору, собравшему архив, или к PhishDestroy.

Достоверные входные данные поступают из источника, отличного от проверяемого файла: отпечаток сборщика от отправителя, корневой сертификат органа, выдающего временные метки, от самого этого органа, а также коммит из вашей собственной проверки. Запустите верификатор из установки или коммита, которым вы доверяете; копия внутри архива предназначена исключительно для удобства ([манифест и контрольные точки](EVIDENCE.md#manifest-and-checkpoints)). Верификатор представляет собой один файл, [`tgwitness/verify.py`](../../tgwitness/verify.py), скомпилированный из каталога [`tgwitness/verifier/`](../../tgwitness/verifier/README.md); скрипт `python tools/build_standalone_verifier.py --check` выявляет расхождения между этими двумя версиями. Проверки журнала и подписей находятся в каталогах `common`, `chain` и `journal` (общим объёмом 22 КБ); примерно треть файла `verify.py` составляют сжатые данные перевода из каталога `languages`. Для работы требуется Python 3.11+ и модуль `cryptography`.

## Команды, используемые на этой странице

**Архив доказательств. Команда** `--require evidence` завершает работу с кодом 2, если не соблюдены все условия: целостность данных, наличие закреплённого ключа сборщика и время от стороннего источника, охватывающее последнюю запись. Добавьте параметр `--explain`, чтобы получить понятное описание того, что проверяет каждая проверка.

```sh
python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_SHA256 --tsa-ca TSA-ROOT.pem --check-bitcoin --require evidence
```

Чтобы прочитать сообщения свидетелей из Telegram, добавьте `--witness witness.zip --witness-fingerprint WITNESS_SHA256 --channel https://t.me/s/WITNESS_CHANNEL`. Опция `--require-tier TIER` завершает работу с кодом 2, если [уровень гарантии](FOR-THE-RECORD.md#1-what-each-step-establishes) ниже указанного.

**ZIP-архив исходного кода релиза** ([архив исходного кода релиза](TRUST.md#release-source-archive)). `COMMIT` — это полный SHA, который вы проверили:

```sh
gh attestation verify "TgWitness-${VERSION}.zip" --repo phishdestroy/TgWitness \
  --signer-workflow phishdestroy/TgWitness/.github/workflows/provenance.yml \
  --signer-digest "$COMMIT" --source-digest "$COMMIT" \
  --source-ref "refs/tags/v${VERSION}" --deny-self-hosted-runners
```

**Снимок GitHub Actions** ([запечатанное доказательство](TRUST.md#sealed-evidence)). `WORKFLOW_SHA` — это `workflow_sha`, указанный в файле `tgwitness/sealed_policy.json` для установки, которой Вы доверяете:

```sh
gh attestation verify evidence.zip --bundle attestation.jsonl --repo OWNER/TgWitness \
  --signer-workflow phishdestroy/TgWitness/.github/workflows/sealed-collector.yml \
  --signer-digest WORKFLOW_SHA --deny-self-hosted-runners
python -m tgwitness.sealed_verify evidence.zip --bundle attestation.jsonl --repo OWNER/TgWitness
```

**Скрипт установщика перед запуском** ([проверьте перед запуском](INSTALLATION.md#verify-before-running)):

```sh
curl -fSLO https://get.destroy.tools/install.sh && curl -fSLO https://get.destroy.tools/install.sh.sig &&
curl -fSLO https://get.destroy.tools/release-signing.pub &&
test "$(openssl dgst -sha256 release-signing.pub | awk '{print $NF}')" = \
  '039d98a658ccda14253e45a00335b4a68d840976d8ec18b8d4355cc7c458447d' &&
openssl dgst -sha256 -verify release-signing.pub -signature install.sh.sig install.sh && bash install.sh
```

<a id="how-a-record-is-tied-to-telegram"></a>
## Как запись привязывается к Telegram

- Сборщик подписывает каждую запись в момент её поступления через аутентифицированное соединение аккаунта с Telegram. Журнал фиксирует это соединение и источник записи ([откуда поступают сообщения](EVIDENCE.md#where-the-messages-come-from)).
- Telegram доставляет сообщения каждому клиенту, включая официальные приложения, в рамках сеанса MTProto. Его ключ авторизации согласовывается с закреплённым серверным ключом Telegram, и каждое обновление расшифровывается и проходит проверку целостности (`msg_key`) с использованием этого ключа. Прокси-сервер или ретранслятор на пути не может читать, вставлять или изменять обновление.
- Соединение устанавливается с опубликованными сетевыми диапазонами Telegram. **Дополнительные инструменты → Карта системы** показывает для каждого подключённого аккаунта, находится ли его конечная точка в пуле Telegram (`TELEGRAM_NETWORKS` в файле [`tgwitness/topology.py`](../../tgwitness/topology.py)).
- Перехваченные кадры MTProto можно расшифровать с помощью собственного ключа сеанса и сопоставить с записями журнала по идентификатору сообщения и SHA-256 полезной нагрузки ([`tgwitness/forensics/`](../../tgwitness/forensics)).
- Каждая запись содержит идентификаторы и даты сервера, присвоенные Telegram: чат, сообщение и отправитель. Другой аккаунт в том же чате получает те же идентификаторы, а опция `--compare` позволяет сравнивать два экспорта друг с другом ([сравнивая экспорты чатов](EVIDENCE.md#comparing-chat-exports)).
- [Запрос-свидетель](ACCOUNTS.md#witness-probe) со второго аккаунта показывает, что сеанс получал обновления в режиме реального времени; второй клиент, использующий тот же ключ, отображается как пропущенные ответы. Верификатор сообщает: «Запросы-свидетели: отправлено N, отвечено в режиме реального времени N».
- GitHub Actions фиксирует, а Intel TDX привязывает сеанс, созданный в ходе выполнения, и ключ подписи к заверенному выполнению (`key_origin: created`; [область проверки](EVIDENCE.md#verification-scope)).

**Что сообщает верификатор.** Действительная подпись свидетельствует о том, что байты не изменились с момента подписания; оператор передаёт отпечаток ключа получателю по отдельному каналу. Без параметра `--fingerprint` последняя строка начинается со слова `EVIDENCE: minimum not met · missing: confirmed signer key`. С параметром `--fingerprint`: `self_attested` (подписи, цепочка хешей, манифест и хеши файлов). При наличии стороннего временного отметка, охватывающего последнюю запись: `EVIDENCE: minimum met`. При проверенном заверенном запуске: profile `attested` (`evidence_conditions` в [`tgwitness/verifier/witness.py`](../../tgwitness/verifier/witness.py)).

<a id="how-records-are-fixed-against-later-change"></a>
## Как записи защищаются от последующих изменений

- Каждое наблюдение подписывается при поступлении и вставляется в хеш-цепочку ([то, что подписывается](EVIDENCE.md#what-is-signed)). В режиме «Доказательства» временные метки по умолчанию ставятся на подписанные контрольные точки каждые 10 минут в трёх TSA: одна из них — квалифицированная TSA бельгийского правительства, соответствующая требованиям eIDAS (`DEFAULT_TSA` в `tgwitness/anchoring.py`), а также в OpenTimestamps.
- Изменение, вставка или удаление записи нарушает целостность хеш-цепочки или подписи, и верификатор отклоняет архив. Метка фиксирует начало цепочки, которую она охватывает, на момент времени, подтверждённый сторонней организацией, поэтому охваченная ею запись не может быть заменена впоследствии без появления несоответствия. Записи, следующие за последней меткой, обозначаются следующим образом: `EVIDENCE: minimum met up to record N of M · later records need a binding` (EVIDENCE: минимальное требование выполнено до записи N из M · последующие записи требуют привязки).
- Триггеры SQLite в таблице журнала лишь предотвращают случайное перезаписывание или удаление записи приложением; обнаружение нарушений опирается на цепочку, подписи, метки и свидетелей.
- При включенном drand каждый проход также записывает общедоступный раунд drand, о котором никто не знал до наступления его времени. Этот раунд устанавливает самое раннее время, а следующая метка — самое позднее, поэтому контрольную точку невозможно подготовить заранее; опция `--check-drand` сравнивает раунды с общедоступными ретрансляциями ([drand](EVIDENCE.md#optional-records-in-evidence-mode-drand-and-telegram-devices)).
- Время наблюдений, идущее в обратную сторону, фиксируется как регрессия хронологии (`tgwitness/verifier/journal.py`).
- Запись должна совпадать с тем, что Telegram доставил всем остальным участникам чата. Независимый экспорт того же чата показывает любые расхождения ([сравнение экспортов чата](EVIDENCE.md#comparing-chat-exports)): ``python -m tgwitness.verify first.zip --compare second.zip --fingerprint FIRST_SHA256 --compare-fingerprint SECOND_SHA256``.
- Свидетель с собственным ключом сохраняет префиксы более ранних журналов, а сообщения свидетеля, считываемые в режиме реального времени с t.me, содержат даты, установленные Telegram ([свидетель](WITNESS.md)).
- GitHub Actions и Intel TDX освобождают оператора от необходимости сбора данных: сеанс создаётся внутри заверенного цикла выполнения (импортированный сеанс не попадает в профиль `attested`), а заверение привязывает архив к утверждённому сборщику ([область проверки](EVIDENCE.md#verification-scope)).

**Что сообщает верификатор.** Записи, охватываемые каждой меткой, и интервал между записью и следующей меткой. В режиме «Доказательства» этот интервал представляет собой график простановки меток.

<a id="checkpoints-and-witnesses"></a>
## Контрольные точки и свидетели

- Контрольная точка подписывается ключом сборщика. Она привязывается с момента получения её получателем по другому каналу, до передачи архива ([манифеста и контрольных точек](EVIDENCE.md#manifest-and-checkpoints)).
- Свидетель работает как отдельный процесс со своим собственным ключом на хосте сборщика или на компьютере другого оператора ([свидетеля](WITNESS.md)). Верификатор проверяет, отличается ли ключ свидетеля от ключа сборщика; «Кто владеет этим ключом, указывается в записи о контроле ключей хранителя, хранящейся вместе с его отпечатком» (`CONDITION_SCOPE` в файле [`tgwitness/verifier/witness.py`](../../tgwitness/verifier/witness.py)).
- Оба добавляют независимые копии вершины журнала сверх минимального объёма, необходимого для подтверждения, которым является время, зафиксированное третьей стороной.
- Для параметра `--channel` данные о датах, установленных Telegram, предоставляются при чтении страницы в режиме реального времени по адресу `https://t.me/s/…` или `https://telegram.me/s/…`. Отредактированные сообщения игнорируются, а экспорт из Telegram Desktop или сохраненная страница считаются предоставленными метаданными.

**Результат.** Контрольная точка привязывается с момента её получения получателем. Свидетель на компьютере другого оператора не зависит от сборщика; сохраните запись о хранителе и контроле ключей вместе с её отпечатком ([свидетелем](WITNESS.md)).

<a id="signed-on-receipt-compared-with-a-stamped-desktop-export"></a>
## Подписывается при получении квитанции, сравнивается с экспортом из Telegram Desktop, снабженным временной меткой

Квалифицированная временная метка на экспорте из Telegram Desktop фиксирует файлы с момента простановки метки. TgWitness фиксирует каждую запись с момента её поступления.

- Telegram Desktop сохраняет экспорт в виде файлов HTML или JSON без подписи. Их можно редактировать до простановки отметки, а квалифицированная временная отметка затем подтверждает, что отредактированные файлы существовали в тот момент. В разделе [Export Clinic](https://phishdestroy.github.io/TgWitness/docs/export-clinic/) показан диалог рядом с намеренно измененными файлами экспорта из Telegram Desktop.
- TgWitness подписывает каждое наблюдение по мере его поступления и вставляет его в цепочку хешей ([то, что подписывается](EVIDENCE.md#what-is-signed)). Проставка отметки времени подписанных контрольных точек в соответствии с RFC 3161 и OpenTimestamps включена по умолчанию в каждой конфигурации; **доказательства по делу** также фиксируют раунды drand. Файлы `.tsr` и `.ots`, расположенные в папке `anchors/`, позволяют любому пользователю проверить их.
- TgWitness может использовать квалифицированный центр сертификации времени (TSA). В соответствии с процедурой RFC 3161 контрольная точка отправляется в любой TSA, а ответ проверяется с помощью команды ``python -m tgwitness.anchor verify --checkpoint checkpoint.json --request timestamp.tsq --response timestamp.tsr --ca trusted-tsa-root.pem`` ([процедура](TIMESTAMP.md#procedure)). Сертификат аттестации Intel TDX заверен квалифицированным центром сертификации времени правительства Бельгии, корневой сертификат которого закреплён в файле ``tgwitness/tsa_roots.py`` ([сертификат аттестации](PHALA.md#attestation-certificate)).

- В режиме «Evidence» каждая контрольная точка отправляется в квалифицированный TSA правительства Бельгии, а также в freetsa.org и Sectigo (`DEFAULT_TSA` в файле `tgwitness/anchoring.py`). При установке параметра `--tsa-ca` на корневой сертификат данного поставщика программа `verify.py` идентифицирует отметку как квалифицированную временную отметку eIDAS и указывает организацию, поставившую временную отметку, из доверенного списка ЕС (`qualified_timestamp` в файле `tgwitness/verifier/timestamps.py`). В соответствии со статьёй 41(2) Регламента (ЕС) № 910/2014 такая отметка дает основание предполагать, что указанное время является точным, а связанные данные не повреждены, в любой стране-члене ЕС.

**Отличие.** TgWitness подписывает каждую запись при получении и проставляет отметки на контрольных точках по расписанию, поэтому байты с отметкой времени соответствуют полученным байтам. Экспорт в формат Desktop защищён только с момента проставления отметки времени; до этого он может быть отредактирован.

<a id="court-package-and-jurisdictions"></a>
## Судебный пакет и юрисдикции

- Сертификация судебного пакета «заполняется заранее в форме сертификата по Правилу 902(13)/(14)» ([документы для суда](INVESTIGATION-MODE.md#documents-for-court)). Его уведомление начинается словами «В соответствии с Федеральными правилами доказывания США» и заканчивается словами «Перед подписанием адаптируйте данный шаблон к применимым правилам» (`NOTICE` в файле [`tgwitness/court.py`](../../tgwitness/court.py)).
- [Руководство по юрисдикциям](JURISDICTION_GUIDANCE.md) в Report Studio охватывает 31 юрисдикцию: правовые основания, задачи по подготовке, правовые источники, меры безопасности при сборе данных и дополнительное резюме на местном языке. Описательные отчёты содержат терминологию по юрисдикциям на 25 языках ([шаблоны и юрисдикции](NARRATIVE.md#templates-and-jurisdictions)).
- Проверка архива везде одинакова: проверки подписей, соответствия стандарту RFC 3161, биткойнов и заверения носят технический характер. Квалифицированная временная метка eIDAS обеспечивает презумпцию, предусмотренную статьёй 41(2) Регламента (ЕС) № 910/2014, в каждом государстве-члене ЕС.

**Результат.** Декларант использует шаблон в его исходном виде для федеральных судов США и адаптирует его к применимым правилам в других странах.

<a id="deleted-messages-and-data-protection"></a>
## Удалённые сообщения и защита данных

- TgWitness «регистрирует контент, доставленный на подключённый аккаунт Telegram» ([README](../../README.md)): сообщения, которые получает собственное приложение Telegram данного аккаунта, и ничего, кроме них. При поступлении уведомления об удалении система оперативного наблюдения регистрирует это уведомление и по замыслу сохраняет текст.
- Программное обеспечение не использует телеметрию и не предоставляет хостинговых услуг ([README](../../README.md)), поэтому оно не хранит чьи-либо данные от своего имени. Как и в случае со скриншотом или экспортом из Telegram Desktop, обязанности по защите данных ложатся на того, кто собирает и использует данную запись. В руководстве по проекту перечислены законные интересы, на которые обычно ссылаются (GDPR, ст. 6(1)(f), преамбура 47 и 49; ст. 9(2)(f) в отношении судебных исков), а также исключение из правила удаления «для предъявления или защиты судебных исков (ст. 17(3)(e))» ([ответственность и защита данных](PROJECT-GUIDE.md#responsibility-and-data-protection-gdpr)).
- Удаление одной записи приводит к разрыву хеш-цепочки, о чём сообщает верификатор. Хранение данных планируется на уровне рабочей области, и удаление рабочей области приводит к удалению всех её записей. Внешние копии, защищённые с помощью S3 Object Lock, не могут быть удалены до истечения срока их хранения (тот же раздел).
- Профили пользователей по умолчанию отключены и включаются для каждого чата отдельно. Экспорт данных позволяет удовлетворять запросы на доступ в соответствии со ст. 15 (тот же раздел).

**Вывод.** GDPR регулирует деятельность физических лиц и организаций, обрабатывающих данные, а не программное обеспечение. Удалённое сообщение сохраняется в записи в том виде, в каком оно присутствует в любой копии, сохраненной до удаления; в руководстве перечислены правовые основания, используемые для предъявления юридических претензий.

<a id="a-public-mtproxy-relays-encrypted-traffic-only"></a>
## Публичный MTProxy ретранслирует исключительно зашифрованный трафик

- Новые рабочие области по умолчанию настроены на **Автоматический MTProxy · публичные списки** с параметром **Скрыть адрес** ([MTProto, Telethon и прокси](CONNECTION-SECURITY.md#mtproto-telethon-and-proxies)). Эти списки берутся из открытых источников, указанных в разделе [Публичные прокси](CONNECTION-SECURITY.md#public-proxies-supplied-by-your-installation).
- MTProxy передаёт исключительно трафик Telegram. Этот трафик шифруется с помощью ключа сеанса, согласованного с закреплённым серверным ключом Telegram ([откуда поступают сообщения](EVIDENCE.md#where-the-messages-come-from)), поэтому прокси ретранслирует его, не читая ни сообщений, ни ключей. Как сетевой ретранслятор, он по-прежнему получает адрес подключения, а также информацию о времени и объёме трафика.
- «Ни сеансы Telegram, ни учетные данные API, ни токены панели или ботов не передаются поставщикам каналов» ([общедоступные прокси](CONNECTION-SECURITY.md#public-proxies-supplied-by-your-installation)).
- Оператор самостоятельно выбирает остальные исходящие сервисы. Сервисы временных меток получают хеши контрольных точек, а не сами сообщения ([процедура](TIMESTAMP.md#procedure)). ИИ по умолчанию отключен во всех рабочих областях и перед каждым запросом отображает данные, которые он собирается отправить ([анализ](ANALYSIS.md)). Уведомления не содержат текста сообщений, если не включена функция отображения выдержек ([руководство по проекту](PROJECT-GUIDE.md#responsibility-and-data-protection-gdpr)). **Дополнительные инструменты → На карте системы** перечислены соединения, которые пытается установить процесс ([карта системы](SYSTEM-MAP.md)).
- Настройка каталога операторов с параметром `TGWITNESS_PROXY_CATALOG` «полностью отключает внешние подписки»; другой альтернативой является использование собственного маршрута SOCKS5 или HTTP ([безопасность соединения](CONNECTION-SECURITY.md)).

**Результат.** Публичный прокси видит метаданные соединения: то, что сервер подключается к Telegram, когда и в каком объёме, как и любой другой прокси или VPN. Он не может читать или изменять сообщения, а также может прервать соединение. Если метаданные имеют значение, используйте каталог операторов или собственный маршрут.

<a id="built-in-api-pairs-identify-a-client-not-an-account"></a>
## Встроенные пары API идентифицируют клиента, а не аккаунт

В [специальном руководстве по аккаунтам](https://phishdestroy.github.io/TgWitness/docs/dedicated-account/#api) объясняется выбор и приводятся ссылки на документацию Telegram по каждому пункту.

- **Пара определяет приложение.** Идентификатор API и хеш API идентифицируют приложение для Telegram и не предоставляют доступа к данным аккаунта. При входе в систему используется собственная авторизация аккаунта: код входа и пароль двухфакторной аутентификации (2FA) либо сеанс, в котором данный аккаунт уже авторизован.
- **Общая пара не предоставляет совместного доступа.** При входе в систему создаётся ключ авторизации посредством обмена по алгоритму Диффи–Хеллмана; этот ключ никогда не передаётся, а другие программы с той же парой имеют свои собственные ключи. Трафик шифруется с помощью этого ключа, а не с помощью хеша API. В Telegram отсутствует метод, позволяющий получить список аккаунтов, сеансов или сообщений по идентификатору API.
- **Встроенные пары являются общедоступными.** Пары официальных приложений Telegram (Desktop 2040, Android 6, Telegram X 21724, iOS 10840, macOS 2834, Web 2496), а также остальные пары из пула опубликованы в открытом исходном коде клиентов Telegram и библиотек, таких как opentele, opentele2 и Grampo.
- Файл [`tgwitness/api_pool.py`](../../tgwitness/api_pool.py) содержит 50 общедоступных пар. При новом входе в систему сначала проверяется пара Telegram Desktop (2040), затем — до семи других пар в случайном порядке (`login_order`); если Telegram отклоняет какую-либо пару, проверяется следующая. Только пара Telegram Desktop (2040) отправляется с соответствующим описанием клиента Telegram Desktop ([методы аутентификации](CONNECTION-SECURITY.md#authentication-methods)). Отсутствующие поля устройства берутся из встроенных каталогов opentele2 ([API ID и хеш](ACCOUNTS.md#before-you-start-api-id-and-api-hash)).
- **Ваша собственная пара.** Введите её в полях **API ID + хеш**, и TgWitness будет использовать её вместо пула. Встроенная пара регистрируется для судебных целей аналогичным образом (следующий пункт). По опыту проекта новая личная пара с сайта my.telegram.org приводит к выходу из системы большинства аккаунтов, поэтому используйте её только в том случае, если дело требует использования вашего собственного приложения: создайте её с помощью специального аккаунта и введите до начала сбора данных ([API ID и хеш](ACCOUNTS.md#before-you-start-api-id-and-api-hash)).
- Каждая запись `observation.started` содержит `api_id` (никогда не хеш), независимо от того, является ли пара встроенной или принадлежит оператору, а также описание клиента и тип маршрута. Отчёты и файл `custody.json` перечисляют их ([производитель](EVIDENCE.md#producer)), поэтому получатель может увидеть, какой клиент осуществлял наблюдение.

**Результат.** Пара, с помощью которой выполнен вход в систему, не влияет на то, что получает аккаунт, и эта информация указывается в записи. Telegram самостоятельно определяет ограничения независимо от того, какой профиль клиента используется ([аккаунты](ACCOUNTS.md#before-you-start-api-id-and-api-hash)), поэтому в данном руководстве рекомендуется использовать отдельный аккаунт.

<a id="verifying-the-installer"></a>
## Проверка установщика

- Однострочный установщик — это стандартный способ установки инструментов для разработчиков: Claude Code (`curl -fsSL https://claude.ai/install.sh | bash`), rustup (`curl … https://sh.rustup.rs | sh`), Homebrew и скрипт Docker с сайта `get.docker.com` используют тот же шаблон. TgWitness дополняет его приведёнными ниже проверками.
- [Команды проверки сначала](INSTALLATION.md#verify-before-running) загружают скрипт, его отдельную подпись и открытый ключ, проверяют хеш ключа по алгоритму SHA-256, проверяют подпись с помощью OpenSSL и только после этого запускают скрипт. Ожидаемый хеш ключа — это SHA-256 файла [`deploy/installer/release-signing.pub`](../../deploy/installer/release-signing.pub): `git show origin/main:deploy/installer/release-signing.pub | sha256sum`.
- Установщик проверяет хеш SHA-256 и подпись RSA пакета приложения и файла фиксации зависимостей перед установкой, причём «как Bash, так и PowerShell останавливаются в случае сбоя любой из обязательных проверок» (тот же раздел).
- [Файл installer.yml](../../.github/workflows/installer.yml) выполняет сборку на основе конкретной ревизии ветки `main` и проверяет работоспособность результата в системах Linux и Windows. Он ожидает, пока файлы `checks.yml` и `security-audit.yml` будут привязаны к тому же коммиту, публикует сборку только в том случае, если ветка `main` не сменила ревизию, а затем проверяет общедоступные загрузки. В [манифесте](https://get.destroy.tools/manifest.json) фиксируются версия, коммит, идентификатор выпуска и SHA-256 каждого артефакта.
- Альтернативными вариантами являются GitHub Releases с заверенным ZIP-архивом исходного кода ([архив исходного кода выпуска](TRUST.md#release-source-archive)), установка из исходного кода и [Docker](DEPLOYMENT.md).

**Результат.** Чтобы проверить скрипт перед его запуском, используйте команды verify-first; в любом случае установщик проверяет подписи пакета и блокировки. Происхождение исходного кода подтверждается для [ZIP](TRUST.md#release-source-archive)-архива [с исходным кодом выпуска](TRUST.md#release-source-archive).

<a id="tests-and-continuous-integration"></a>
## Тестирование и непрерывная интеграция

- Набор регрессионных тестов состоит из 126 тестовых модулей, содержащих около 950 тестовых функций. Он запускается в частной среде валидации с использованием синтетических аккаунтов и имитированного транспортного протокола Telegram. Тестовые файлы исключены из Git и из архивов исходного кода ([`.gitignore`](../../.gitignore), [`tools/build_source.py`](../../tools/build_source.py)). Реальные запуски регистрируются отдельно в [журнале валидации](VERIFICATION.md).
- [Проверки](../../.github/workflows/checks.yml): lint, аудит закреплённых зависимостей, согласованность автономного верификатора, установка пакетов wheel и готовность к работе с пустой рабочей областью. Полный запуск платформы охватывает Linux, Windows и macOS с Python 3.11–3.13.
- [Проверки PR](../../.github/workflows/pr-check.yml) повторяют проверку lint, аудит зависимостей и проверку готовности установленных пакетов, а также создают публичный сайт.
- [Верификатор установщика](../../.github/workflows/installer-acceptance.yml) проверяет подписанные артефакты установщика и ревизию исходного кода, после чего устанавливает и проверяет файл wheel.
- [Проверки с запечатанными образами](../../.github/workflows/sealed-checks.yml) создают образ запечатанного сборщика на основе его закреплённой версии и импортируют его без подключения к сети.
- [Аудит безопасности](../../.github/workflows/security-audit.yml) запускает pip-audit для зафиксированных файлов блокировки, CodeQL для Python, JavaScript и рабочих процессов, а также Trivy для образов контейнеров.
- [Фузинг](../../.github/workflows/fuzz.yml) проверяет архив верификатора и синтаксический анализ JSON.

**Результат.** Общедоступные рабочие процессы и их журналы выполнения показывают, что именно проверяла система непрерывной интеграции (CI) для каждого коммита. Сам набор регрессионных тестов не публикуется.
