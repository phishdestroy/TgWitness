หลักฐานและความเชื่อถือ

สิ่งที่การส่งออก วิดีโอ ไฟล์เก็บถาวรเว็บ และบันทึกที่ลงนามสามารถยืนยันได้ รวมถึงวิธีที่อุปกรณ์เก็บรวบรวมส่งผลต่อความน่าเชื่อถือของข้อมูลเหล่านั้น

การส่งออก ภาพหน้าจอ หรือการบันทึกอาจเป็นหลักฐานที่มีประโยชน์ ความน่าเชื่อถือของมันขึ้นอยู่กับ วิธีการที่มันถูกเก็บรวบรวม รักษา และยืนยันความถูกต้องของแฮชหรือลายเซ็นที่ถูกต้อง จะตรวจสอบเนื้อหาที่บันทึกไว้ แต่ไม่ได้ยืนยันอย่างอิสระว่าอุปกรณ์ที่เก็บรวบรวม ได้รับเนื้อหาต้นฉบับที่ถูกต้องตามความเป็นจริงขอบเขตนี้ยังใช้กับ TgWitness ด้วย

คู่มือนี้แยกการตรวจสอบทางเทคนิคออกจากประเมินทางกฎหมาย เอกสาร ผลิตภัณฑ์และข้อกำหนดทางกฎหมายด้านล่างได้รับการตรวจสอบเมื่อวันที่ 1 พฤศจิกายน 2026; การเปรียบเทียบ Hunchly อธิบายเอกสารที่เผยแพร่แล้ว ไม่ใช่การตรวจสอบผลิตภัณฑ์ใหม่

เมื่อความเชื่อถือเข้ามาเกี่ยวข้องในการบันทึก#

แบบจำลองภัยคุกคามในที่นี้สมมติว่าผู้โจมตีหรือผู้ดำเนินการสามารถเปลี่ยนแปลงสภาพแวดล้อมการเก็บรวบรวม ก่อนที่หลักฐานจะถูกบันทึกอย่างถาวร นี่เป็นการวิเคราะห์แบบมีเงื่อนไข ไม่ใช่ การอ้างว่าอุปกรณ์หรือผลิตภัณฑ์ใด ๆ ได้ถูกบุกรุกแล้ว

ไคลเอนต์อย่างเป็นทางการและการเชื่อมต่อที่เข้ารหัสช่วยปกป้องการใช้งานปกติ แต่ ไม่ทำให้ระบบปฏิบัติการ เบราว์เซอร์ หรือหน้าจอแสดงผลโดยรอบ น่าเชื่อถือได้ด้วยตัวเอง หากเนื้อหาถูกแทนที่หลังการถอดรหัสแต่ก่อนการบันทึก ผู้ส่งออกสามารถบันทึกเนื้อหาได้อย่างถูกต้อง และผู้ลงนามสามารถลงนามได้อย่างถูกต้อง ทั้งสอง กระบวนการนี้ไม่จำเป็นต้องใช้อัลกอริทึมแฮชที่เสียหายหรือลายเซ็นปลอม

วิดีโอที่ถ่ายด้วยอุปกรณ์เดียวกันสามารถบันทึกการแสดงผลที่ถูกแทนที่ได้ กล้องแยกต่างหากสามารถยืนยันสิ่งที่หน้าจอแสดงได้ แต่หน้าจอเพียงอย่างเดียว ไม่สามารถยืนยันความถูกต้องของข้อมูลที่ Telegram ให้มาได้ เช่นเดียวกัน HTML, JSON, ภาพหน้าจอ และบันทึกเบราว์เซอร์ที่ตรงกันจากสภาพแวดล้อมที่ควบคุมได้หนึ่งแห่งอาจมี ข้อผิดพลาดเดียวกัน ความสอดคล้องกันนี้เป็นบริบทที่มีประโยชน์ แต่ไม่ใช่ การยืนยันที่อิสระโดยอัตโนมัติ

สิ่งที่แต่ละรูปแบบของหลักฐานช่วยเสริม#

เนื้อหา การมีส่วนร่วมที่มีประโยชน์ คำถามที่เหลือ
การส่งออก Telegram Desktop การสนทนาที่อ่านได้หรืออ่านได้ด้วยเครื่อง และสื่อที่เลือกไว้ ใครเป็นผู้ควบคุมไฟล์ลูกค้าและไฟล์ส่งออก และข้อมูลใดที่มีอยู่หรือถูกยกเว้น?
ภาพหน้าจอหรือการบันทึกหน้าจอ บริบทที่มองเห็นได้ ลำดับการดำเนินการ และการนำเสนอ การนำเสนอนี้สะท้อนแหล่งข้อมูลต้นฉบับอย่างถูกต้องหรือไม่ และสิ่งที่เกิดขึ้นนอกเหนือจากการบันทึกนั้นเป็นอย่างไร?
คลังเว็บท้องถิ่น รวมถึง MHTML เนื้อหาหน้าเว็บและทรัพยากรที่เกี่ยวข้องเพื่อตรวจสอบในภายหลัง เบราว์เซอร์ได้ส่งข้อมูลอะไรไปยังโปรแกรมเก็บข้อมูล และใครเป็นผู้ควบคุมเบราว์เซอร์นั้น?
ไฟล์เก็บข้อมูลที่ลงนามโดยผู้เก็บรวบรวม การเปลี่ยนแปลงในไบต์ที่ลงนามสามารถตรวจพบได้เมื่อเทียบกับกุญแจที่เชื่อถือได้และอ้างอิงที่เก็บไว้ ใครเป็นผู้ควบคุมกุญแจการลงนามและข้อมูลก่อนการลงนาม?
จุดตรวจสอบที่เก็บรักษาอย่างอิสระ หรือเวลาที่ได้รับการยืนยัน แฮชหรือจุดตรวจสอบที่เก็บไว้เพื่อเปรียบเทียบกับข้อมูลที่ส่งมาในภายหลัง ไบต์และขอบเขตใดที่ได้รับการครอบคลุม และฝ่ายอิสระนั้นยืนยันอะไรจริงๆ?

Telegram บันทึกการส่งออกผ่าน Desktop เป็นสำเนา HTML/JSON แบบออฟไลน์ และ Takeout API เป็นวิธีการดึงข้อมูลบัญชีที่เลือกไว้ คำอธิบายเหล่านี้ไม่ได้ให้ ลายเซ็นของ Telegram บนไฟล์ที่ส่งออกสุดท้ายเพื่อให้ผู้รับสามารถตรวจสอบได้ ข้อสรุปของเราจำกัดอยู่เพียงกลไกการส่งออกที่บันทึกไว้เท่านั้น; นี่ไม่ใช่ การอ้างว่าหลักฐานของ Telegram ไม่มีมูลค่าทางกฎหมาย การส่งออกผ่าน Telegram Desktop, Takeout API.

การแยกแยะเดียวกันนี้ใช้กับคำขอในพื้นหลัง รายการแคช และบันทึกเครือข่าย ด้วย ซึ่งอาจเปิดเผยความไม่สอดคล้องกันและช่วยยืนยันการเก็บรวบรวมได้ ความ ซับซ้อนของข้อมูลเหล่านี้เพียงอย่างเดียวไม่สามารถยืนยันได้ว่าใครเป็นผู้สร้างขึ้น การเก็บรักษา ข้อมูลที่ดำเนินการอย่างอิสระหรือบันทึกบริการที่ได้รับมาแยกต่างหาก จะนำแหล่งข้อมูลที่ ต่างกันมาเปรียบเทียบ โดยอยู่ภายใต้ข้อจำกัดในการเก็บรวบรวมและการดูแลรักษาของแหล่งนั้นเอง

Hunchly แสดงขอบเขตเดียวกัน#

เอกสารของ Hunchly อธิบายการแฮช SHA-256 ของข้อมูล MHTML ที่จับภาพ, รูปภาพ และ ไฟล์แนบ พร้อมการตรวจสอบแฮชอย่างอิสระ นอกจากนี้ยังอธิบายว่าทำไมไฟล์ที่ถูกแก้ไข ซึ่งมาพร้อมกับแฮชที่คำนวณใหม่จึงสามารถผ่านการเปรียบเทียบนั้นได้ และชี้ ไปยังลายเซ็นและการยืนยันแหล่งที่มาเป็นขั้นตอนตรวจสอบเพิ่มเติม Hunchly: การแฮชเนื้อหา รูปภาพ และไฟล์แนบ

คู่มือหลักฐาน (Evidence Guide) ที่เผยแพร่แล้ว เวอร์ชัน 1.0 วันที่ 17 ตุลาคม 2018 อธิบายถึง กุญแจ GPG และลายเซ็นที่สร้างขึ้นในเครื่องท้องถิ่นสำหรับการจับภาพ MHTML คู่มือนี้ระบุอย่างชัดเจน ว่าการเข้าถึงกุญแจส่วนตัวในเครื่องท้องถิ่นเป็นวิธีหนึ่งในการลงลายเซ็นบนเนื้อหาที่แก้ไขแล้วอีกครั้ง นี่คือ ข้อจำกัดความเชื่อถือที่บันทึกไว้ ไม่ใช่หลักฐานของช่องโหว่ปัจจุบันที่ยังไม่ถูกเปิดเผย คู่มือนี้ยังระบุว่า Chrome เป็นผู้ดำเนินการจับภาพ MHTML การอธิบาย Hunchly ว่า พึ่งพาเพียงชื่อเสียงของผู้สอบสวนเท่านั้น จะทำให้การควบคุมทางเทคนิคเหล่านี้ถูกละเว้น คู่มือหลักฐาน Hunchly, ส่วน 2–4.

การว่าข้อมูลที่เก็บรวบรวมด้วยผลิตภัณฑ์เฉพาะนั้นได้รับการยอมรับในคดีหรือไม่ ขึ้นอยู่กับคำตัดสินและสถานการณ์ที่เกี่ยวข้อง เราไม่อ้างสิทธิ์ใดๆ ที่นี่เกี่ยวกับ ความถี่ที่ศาลยอมรับ Hunchly หรือ TgWitness หรือเกี่ยวกับผลิตภัณฑ์ใดผลิตภัณฑ์หนึ่งที่มี การรับรองทั่วไปจากศาล

สิ่งที่ TgWitness เพิ่มเติม และขอบเขตการคุ้มครองของมันสิ้นสุดที่ใด#

TgWitness บันทึกการสังเกตการณ์ในสมุดบันทึกที่ลงนามและเชื่อมโยงกัน และจัดเตรียมไฟล์ส่งออก ที่ผู้รับสามารถตรวจสอบได้ จุดตรวจสอบที่เก็บรักษาไว้ ตราเวลา และ ผู้สังเกตการณ์ที่แยกต่างหาก ให้ผู้ตรวจสอบมีข้อมูลอ้างอิงนอกเหนือจากไฟล์ปัจจุบันของผู้เก็บรวบรวม สิ่งเหล่านี้ช่วยเปิดเผยการเปลี่ยนแปลงในบันทึกที่บันทึกไว้ก่อนหน้านี้ บันทึกการครอบคลุมและ ผลลัพธ์การเก็บรวบรวมที่ชัดเจน ช่วยอธิบายว่าข้อมูลใดถูกบันทึกและข้อมูลใดไม่ถูกบันทึก รูปแบบหลักฐานและการส่งต่อ ขอบเขตการเก็บรวบรวม

เวลาของการแทนที่ที่อาจเกิดขึ้นมีความสำคัญ:

  1. หลังการลงนาม โดยไม่มีสิทธิ์เข้าถึงกุญแจลงนาม:การเปลี่ยนแปลงบันทึกที่ลงนามแล้ว หรือไฟล์ที่ผูกกับ manifest จะทำให้การตรวจสอบล้มเหลวเมื่อใช้ผู้ตรวจสอบที่เชื่อถือได้และกุญแจ
  2. ด้วยกุญแจผู้เก็บรวบรวม หลังจากที่จุดตรวจสอบอิสระถูกเก็บรักษาไว้แล้ว: บันทึกการแทนที่สามารถมีลายเซ็นใหม่ที่ถูกต้องได้ แต่คำนำหน้าที่ถูกเปลี่ยนแปลงจะ ไม่สามารถเปรียบเทียบได้กับจุดตรวจสอบก่อนหน้านี้ จุดตรวจสอบที่เก็บรักษาไว้เฉพาะบน อุปกรณ์ที่ควบคุมเดียวกันสามารถถูกแทนที่ได้พร้อมกับบันทึกการแทนที่ ข้อมูลที่อยู่นอก ขอบเขตที่เก็บรักษาไว้จำเป็นต้องมีการครอบคลุมแยกต่างหาก
  3. ก่อนที่จุดตรวจสอบที่ครอบคลุมการสังเกตการณ์จะถูกเก็บรักษาอย่างอิสระ: ข้อมูลป้อนเข้าที่ผิดพลาดสามารถถูกลงนามและยึดตรึงได้สำเร็จ รวมถึงบันทึกใหม่ ที่ถูกเพิ่มเข้าไปหลังจากจุดตรวจสอบก่อนหน้า จุดตรวจสอบหรือเวลาประทับ ที่ได้ยังคงครอบคลุมบันทึกที่ผิดพลาดเหล่านั้น; มันไม่ได้ยืนยันความจริงของบันทึกเหล่านั้น

พยาน TgWitness จะรับจุดตรวจสอบที่ลงนามโดยผู้รวบรวมข้อมูล; มันไม่อ่าน การสนทนา Telegram ที่อยู่เบื้องหลังอย่างอิสระ กุญแจและบันทึกที่เก็บไว้ของมันต้อง ได้รับการเชื่อถืออย่างแยกต่างหาก เมื่อต้องให้พยานรับรองบันทึกทั้งหมดที่ส่งมา ให้ใช้ ขั้นตอนการส่งต่อ (handoff) ที่ต้องการขอบเขตการส่งออกสุดท้าย การตรวจสอบความสมบูรณ์แบบปกติยังสามารถรายงานส่วนท้ายที่ยังไม่ได้รับการรับรองจากพยานได้

การตอบกลับ RFC 3161 ที่ได้รับการตรวจสอบแล้วสามารถยืนยันได้ว่าจุดตรวจสอบ (checkpoint) มีอยู่ตาม เวลาที่หน่วยงานมีอำนาจระบุไว้ แต่ไม่สามารถยืนยันได้ว่าข้อความ Telegram ถูกส่งเมื่อใด หรือเนื้อหาของข้อความนั้นเป็นความจริงหรือไม่ การใช้คำขอที่เตรียมไว้หรือไฟล์ตอบกลับที่แนบมา เพียงอย่างเดียวไม่เพียงพอ เมื่อตรวจสอบการส่งออกด้วยtgwitness.verify การตรวจสอบ ลายเซ็น TSA ที่แนบมาจำเป็นต้องใช้ CA ที่ได้รับความเชื่อถืออย่างชัดเจนผ่าน--tsa-ca ใบเสร็จ OpenTimestamps จำเป็นต้องมีots verify ที่อิสระ พร้อมการอัปเกรดหลักฐานเมื่อ จำเป็น ขั้นตอนการประทับเวลา,RFC 3161.

ในการจับภาพใน GitHub Actions, รันเนอร์ที่โฮสต์ชั่วคราวจะรวบรวม ข้อความต่างๆ การรับรองจะผูกไฟล์เก็บถาวรกับเวิร์กโฟลว์ที่ได้รับการอนุมัติ โหมดนี้ ยังคงเชื่อถือ GitHub, ซอฟต์แวร์และส่วนประกอบที่ได้รับการอนุมัติ, ตัวช่วย/เบราว์เซอร์ และอุโมงค์ มันไม่ใช่ฮาร์ดแวร์ที่เป็นความลับ, ลายเซ็น Telegram หรือหลักฐาน ว่าไม่มีใครเข้าถึงโฮสต์ ใบเสร็จการรันที่ลงนามในเครื่องท้องถิ่นก็เป็นเพียงการวัดผล ที่รายงานด้วยตนเอง ไม่ใช่การรับรองฮาร์ดแวร์

น้ำหนักทางกฎหมายขึ้นอยู่กับพื้นฐาน#

มีสี่คำถามที่ควรแยกให้ชัดเจน: ว่าสิ่งนั้นเป็นตามที่กล่าวไว้หรือไม่, ว่าไบต์ที่ส่งมาตรงกับบันทึกที่เก็บไว้หรือไม่, ว่าเนื้อหาสนับสนุน ข้อเท็จจริงที่อ้างไว้หรือไม่, และว่ากฎระเบียบที่เกี่ยวข้องอนุญาตให้ใช้งานได้หรือไม่ การตรวจสอบ ทางเข้ารหัสจะครอบคลุมเพียงส่วนหนึ่งของพื้นฐานดังกล่าวเท่านั้น

ในกระบวนการพิจารณาคดีของรัฐบาลกลางสหรัฐฯ กฎข้อ 901 กำหนดวิธีการรับรองความถูกต้องของหลักฐาน รวมถึงคำให้การของพยานที่มีความรู้ และหลักฐานเกี่ยวกับกระบวนการหรือระบบ กฎ 902(13) และ 902(14) กำหนดวิธีการรับรองความถูกต้องสำหรับบันทึก และสำเนาอิเล็กทรอนิกส์บางประเภท พร้อมด้วยข้อกำหนดทางขั้นตอน หมายเหตุของคณะกรรมการ แยกการรับรองความถูกต้องออกจากประเด็นต่าง ๆ เช่น คำบอกเล่า ความเกี่ยวข้อง และการระบุแหล่งที่มา ลายเซ็น ซอฟต์แวร์เพียงอย่างเดียวไม่ถือเป็นการรับรองจากบุคคลที่มีคุณสมบัติตามที่ระบุไว้ในกฎดังกล่าว กฎหลักฐานของรัฐบาลกลาง 901, กฎหลักฐานของรัฐบาลกลาง 902.

ในกรณีที่พระราชบัญญัติหลักฐานของแคนาดามีผลบังคับใช้ มาตรา 31.1 กำหนดเรื่องการรับรองความถูกต้องของ เอกสารอิเล็กทรอนิกส์ มาตรา 31.2 เชื่อมโยงหลักการหลักฐานที่ดีที่สุดกับความสมบูรณ์ของระบบ หรือข้อสันนิษฐานที่ใช้ได้ มาตรา 31.3 กำหนดสถานการณ์สำหรับข้อสันนิษฐาน เกี่ยวกับความสมบูรณ์ของระบบ สิ่งเหล่านี้เป็นเงื่อนไขหลักฐานที่กำหนดไว้ ไม่ใช่ข้อสันนิษฐานทั่วไป ว่าผู้สอบสวนที่ได้รับใบอนุญาตหรือผลิตภัณฑ์เชิงพาณิชย์ใด ๆ จะไม่มีข้อผิดพลาด พระราชบัญญัติหลักฐานของแคนาดา มาตรา 31.1, 31.2, 31.3.

ตัวอย่างเหล่านี้ไม่กำหนดความยอมรับได้ในเขตอำนาจศาลอื่นหรือใน คดีเฉพาะใด ๆ การตรวจสอบทางเทคนิคควรถูกนำไปใช้อย่างสม่ำเสมอกับเอกสารที่สนับสนุน หรือคัดค้านข้อกล่าวหา คู่มือนี้ไม่อ้างว่าหลักฐานของฝ่ายอัยการ โดยทั่วไปจะได้รับการยอมรับได้ง่ายกว่าหลักฐานของฝ่ายจำเลย

เตรียมบันทึกที่บุคคลอื่นสามารถประเมินได้#

  • อธิบายบัญชี อุปกรณ์เก็บข้อมูล ผู้ดำเนินการ เวอร์ชันซอฟต์แวร์ สิทธิ์การเข้าถึง ขอบเขตที่เลือก และช่วงเวลาการเก็บข้อมูล บันทึกการหยุดชะงักและกรณีที่อาจ เกิดการละเมิด แทนที่จะถือว่าการตรวจสอบลายเซ็นที่สำเร็จเป็นการทดสอบว่าอุปกรณ์สะอาด
  • เก็บรักษาแพ็กเกจต้นฉบับและบันทึกการโอนย้าย ค่าแฮช และแหล่งที่มาของเวลา เก็บรักษาลายนิ้วมือของกุญแจและจุดตรวจสอบผ่านช่องทางที่เชื่อถือได้แยกต่างหาก ตรวจสอบความครอบคลุมของผู้เป็นพยานหรือเวลาประทับจริงก่อนที่จะอธิบายไว้ในรายงาน
  • หาหลักฐานยืนยันจากแหล่งอิสระที่เหมาะสมกับคำกล่าวอ้าง: บันทึกของผู้เข้าร่วม คนอื่น, การบันทึกข้อมูลจากแหล่งอิสระ หรือบันทึกบริการที่ได้รับมาอย่างถูกต้องตามกฎหมาย อธิบาย ความอิสระและข้อจำกัดของหลักฐานเหล่านั้น; ความสอดคล้องระหว่างสำเนาเพียงอย่างเดียวไม่เพียงพอ
  • รักษาบริบทที่เกี่ยวข้องไว้ ระบุไฟล์ที่ถูกตัดออก ประวัติที่ไม่สามารถเข้าถึงได้ และ ส่วนที่ถูกปิดบัง จัดเตรียมเอกสารเปิดเผยข้อมูลที่ถูกลดขนาดลง แยกต่างหากเมื่อจำเป็น และอธิบายการเปลี่ยนแปลงของเอกสารนั้นโดยไม่แสดงมันเป็นต้นฉบับเต็ม
  • ให้คำแนะนำการตรวจสอบแก่ผู้รับและข้อมูลที่จำเป็นสำหรับการตรวจสอบดังกล่าว ให้แน่ใจว่าคำสังเกต ผลการวิเคราะห์ทางเทคนิค และข้อสรุปของนักวิเคราะห์สามารถแยกแยะได้อย่างชัดเจน

สำหรับการส่งต่อแต่ละครั้ง ให้ระบุค่าแฮชของไฟล์เก็บถาวร กุญแจที่เชื่อถือได้ ผลลัพธ์การตรวจสอบ และขอบเขตที่ครอบคลุมจากภายนอกอย่างแม่นยำ อธิบายความแท้จริงของแหล่งที่มา การระบุ เจ้าของบัญชี ความครบถ้วน และข้อสรุปทางกฎหมายอย่างแยกกัน สิ่งนี้จะให้ผู้ตรวจสอบ คนต่อไปมีข้ออ้างเฉพาะเพื่อตรวจสอบ
