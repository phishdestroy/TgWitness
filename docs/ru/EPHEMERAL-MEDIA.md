# Самоуничтожающиеся медиафайлы в журнале API

Сборщик API сохраняет доступные фотографии, видео, голосовые сообщения и файлы с параметром ``ttl_seconds`` с помощью специального рабочего процесса с нулевым приоритетом. Он запускается независимо от обычных вложений и настройки «история сначала по сообщениям». Настройка по умолчанию **Включать самоуничтожающиеся медиафайлы из исключённых типов** обходит исключения по типу и продолжительности, сохраняя при этом настроенные ограничения по размеру файлов, резервы дискового пространства, последовательные запросы Telegram RPC и полные сроки ожидания FloodWait. Она не преобразует захват, состоящий только из метаданных или только из хешей, в загрузку файла. Отключите этот параметр, чтобы применять обычные правила по типам. Когда он отменяет действие какого-либо правила, подписанное сообщение фиксирует это в поле `media_capture.rule_override`: правило (`type_not_collected`, `duration_limit`) и ограничения, которые по-прежнему применяются.

При наблюдении за подписанным сообщением сохраняются исходный дескриптор медиафайла Telegram, TTL и доступность. Положительное значение TTL отличается от значения Telegram `0x7FFFFFFF` (просмотр один раз); значение `ttl_period` для чата фиксируется как настройка автоматического удаления данного чата. Сохраненный файл имеет адресацию по содержимому с помощью SHA-256, с указанием его размера и ссылки на наблюдение за подписанным сообщением.

- Значение `media.saved` с `ephemeral_media.outcome=saved` означает, что байты были сохранены.
- Отсутствие или пустота фотографии/документа с положительным значением TTL приводит к появлению записи `media.skipped` со значениями `outcome=unavailable` и `availability=unavailable_at_observation`. Это фиксирует маркер самоуничтожающихся медиафайлов, предоставленный Telegram, а не причину исчезновения файла или информацию о том, просматривал ли его кто-либо.
- Исключения, предусмотренные политикой, неизвестный или превышающий допустимый размер, ошибки загрузки и отмена сохраняют явный результат «not-saved» и предупреждение о том, что Telegram может больше не предложить данный медиафайл. Временные сбои сохраняют обычный результат повторной попытки.
- Периоды офлайн-режима остаются записями типа `coverage.gap`. Они не создают невиданных медиафайлов, их содержания или времени доставки.

При загрузке используется исходный дескриптор, полученный в ходе наблюдения, без повторной проверки исходного сообщения. Если Telegram отклоняет ссылку на файл с истекшим сроком действия, при обновлении должна быть идентифицирована та же вложения; отсутствующее или измененное вложение никогда не заменяется.

Границы запросов клиента API не допускают подтверждений прочтения истории сообщений, содержания сообщений, обсуждений, упоминаний, реакций и историй, включая обобщённые и пакетные запросы. Это не распространяется на другое устройство, на котором выполнен вход в систему, или на официальный веб-клиент/настольный клиент. Ни сохраненный файл, ни отсутствие уведомления о прочтении со стороны получателя ничего не говорят о том, просмотрел ли его получатель-человек. Отчёты явно сохраняют это различие.

Данный приоритетный рабочий процесс относится к режиму мониторинга в реальном времени и журналу отдельных чатов. При экспорте данных по всей учётной записи сохраняется отдельная настройка обработки вложений; сбор данных официальным клиентом по-прежнему ограничивается тем, что отображается в официальном пользовательском интерфейсе. Извлечение данных возможно до тех пор, пока Telegram продолжает обслуживать медиафайлы.

Telegram документирует независимое [подтверждение прочтения содержимого](https://core.telegram.org/method/messages.readMessageContents) и [подтверждение прочтения истории](https://core.telegram.org/method/messages.readHistory), а также дополнительные поля «медиафайлы» и «TTL» для [фотографий](https://core.telegram.org/constructor/messageMediaPhoto) и [документов](https://core.telegram.org/constructor/messageMediaDocument).
