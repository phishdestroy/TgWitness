# Развёртывание и эксплуатация

## Выбор способа установки

Для портативного пакета распакуйте `TgWitness-<version>-windows-amd64-portable.zip` из
GitHub Releases. Для остальных способов скачайте и распакуйте ZIP с исходным кодом или клонируйте
репозиторий, затем выполните из каталога проекта:

| Способ установки | Запуск | Работает в фоне? |
| --- | --- | --- |
| Портативный пакет для Windows | `TgWitness.cmd` | Нет; держите окно открытым. |
| Windows без Docker | `Start.cmd` | Нет; для работы в фоне используйте необязательную задачу, запускаемую при входе в систему. |
| Linux/macOS без Docker | `sh start.sh` | Нет; для работы в фоне используйте systemd/launchd. |
| Docker на любой поддерживаемой системе | `docker compose up -d --build --wait` | Да, пока работает демон Docker. |
| Вспомогательный скрипт Docker для Windows | `scripts\Docker.cmd` | Да; скрипт дожидается работоспособности веб-сервера. |
| Вспомогательный скрипт Docker для Linux/macOS | `sh scripts/docker-start.sh` | Да; скрипт дожидается работоспособности веб-сервера. |

Для облачного сервера, который должна иметь возможность проверить третья сторона, — созданного
через API провайдера, без SSH и доступного только через Cloudflare Tunnel, — см.
[развёртывание с повышенной доказуемостью](HIGH-ASSURANCE.md).

При запуске без Docker создаётся собственное окружение `.venv` и устанавливаются закреплённые
версии зависимостей. Docker собирает их внутри образа, Python на хосте не требуется. Для первой
настройки нужен доступ в интернет. Если Python 3.11+ не найден, `Start.cmd` спрашивает разрешения,
прежде чем установить Python 3.12 для текущего пользователя Windows (через winget, а если он
недоступен — установщиком с python.org после проверки его подписи Python Software Foundation);
права администратора он никогда не запрашивает. Docker и службы ОС по-прежнему должны быть
подготовлены заранее.

Установки без Docker и портативный пакет используют `data/live` внутри своей папки. Docker использует именованный том `tgwitness-data`,
смонтированный в `/data`. Это раздельные установки, пока вы намеренно не перенесёте весь
каталог данных. Новый контейнер Docker не обнаружит автоматически аккаунты установки
без Docker.

## Требования к установке

Для установки без Docker нужны Python 3.11 или новее с `venv` и `ensurepip`, доступ
в интернет для первой установки зависимостей и каталог проекта с правом записи для
`.venv`. Встроенной панели не нужны Node.js и сборка фронтенда. Запускайте скрипт запуска
из своей обычной учётной записи ОС; TgWitness не требует прав администратора или root.

- **Windows:** `Start.cmd` проверяет `py -3`, затем `python`, затем стандартные папки установки
  для пользователя и в Program Files; требуется версия 3.11 или новее. Если ни один вариант
  не подходит, он предлагает описанную выше автоматическую установку для пользователя. Можно также
  выполнить `py -3 start.py`. Портативному пакету Python вообще не нужен.
- **Linux:** `start.sh` пробует `python3.13`, `python3.12`, `python3.11`, `python3` и
  `python`, а если ни один не подходит, выводит команду установки для apt, dnf, pacman, zypper,
  apk или Homebrew. В Debian/Ubuntu может потребоваться пакет `python3-venv`, соответствующий
  выбранному интерпретатору. Если в дистрибутиве по умолчанию стоит более старый Python,
  его нужно заменить или дополнить Python 3.11+.
- **macOS:** установите актуальный дистрибутив Python 3.11+; не рассчитывайте, что интерпретатор
  из состава ОС соответствует требованию. Выполняйте `python3 start.py` из каталога проекта.
- **Docker:** используйте Docker Engine/Desktop с Compose v2.20 или новее. В Windows Docker Desktop
  должен работать с контейнерами Linux. Контейнер устанавливает собственные
  зависимости Python; отдельная установка Python на хосте не нужна.

## Локальный компьютер

Используйте `Start.cmd` в Windows или `sh start.sh` в Linux/macOS. `scripts\Setup.cmd` или
`sh start.sh --setup-only` подготавливает
окружение. Скрипт запуска устанавливает зависимости при первом использовании; последующие запуски
используют уже готовое окружение. Доступ в интернет нужен для настройки и сбора из Telegram,
а просмотр существующих записей и создание экспортов работают без сети.

После настройки выполните `python start.py --check`, чтобы проверить локальные зависимости, Ed25519,
хранилище, конфигурацию ключей и адрес прослушивания, не запуская коллектор.
Для структурированного вывода добавьте `--json`. Передайте те `--data-dir`, `--host` и
`--port`, которые собираетесь использовать. Проверка не устанавливает пакеты, не создаёт журнал
и не подключается к Telegram; она не подтверждает целостность или полноту охвата. Существующие
журналы отдельно проверяются при запуске. `python start.py --help` тоже ничего не устанавливает.

После start.py запускайте вспомогательные команды через `.venv\Scripts\python.exe` в
Windows или `.venv/bin/python` в Linux/macOS либо сначала активируйте это окружение.
Примеры `python -m ...` ниже предполагают, что окружение активно.

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

Переменные окружения: TGWITNESS_DATA, TGWITNESS_HOST, TGWITNESS_PORT, TGWITNESS_TOKEN.
TGWITNESS_VAULT_KEY_FILE включает режим внешнего ключа для новой установки; см. [Внешний мастер-ключ](../SECURITY-MODEL.md#external-master-key).
Если TGWITNESS_TOKEN задан, он должен содержать не менее 24 символов; используйте
криптографически случайное значение. Без него приложение генерирует случайный 256-битный
токен в panel-token.txt. Переопределение через переменную окружения не перезаписывает этот файл.
Для смены учётных данных перезапустите приложение.

Каталогом данных может владеть только один процесс. Кроссплатформенная блокировка файла
средствами ОС предотвращает случайную одновременную запись. Используйте один рабочий процесс
Uvicorn. Панель может управлять любым числом рабочих пространств; каталоги дополнительных
рабочих пространств находятся в profiles/<id>/.
Для отдельных экземпляров службы используйте отдельные каталоги и порты. Файлы SQLite WAL должны
находиться в локальном постоянном хранилище, а не в сетевой файловой системе. Не используйте
один том для нескольких реплик.

## Портативный пакет для Windows

К каждому релизу на GitHub приложены `TgWitness-<version>-windows-amd64-portable.zip` и его
`.sha256`. Пакет содержит официальную встраиваемую среду Python 3.12 с python.org
(контрольная сумма закреплена в `tools/build_portable.py`), TgWitness с закреплёнными
зависимостями и три файла запуска:

| Файл | Назначение |
| --- | --- |
| `TgWitness.cmd` | Запуск панели; дополнительные параметры передаются дальше, например `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | Запуск синтетического демо в `data\demo` |
| `TgWitness-Check.cmd` | Проверка готовности без запуска |

Закреплённый словарь русской морфологии и цветовые профили PDF входят в пакет для работы
без сети. При упаковке в каталогах `data` зависимостей допускаются только их известные пути;
неожиданные файлы в этих каталогах прерывают сборку с ошибкой.

Распакуйте весь архив в папку с правом записи, например `Documents\TgWitness`; не запускайте
его изнутри ZIP или из Program Files. Среда выполнения использует изолированный путь поиска
модулей, поэтому другие установки Python и `PYTHONPATH` на неё не влияют. Данные остаются
в папке `data` пакета. Для обновления остановите TgWitness, распакуйте новую версию в новую
папку и перенесите в неё папку `data`.

Чтобы собрать пакет самостоятельно, используйте 64-разрядную Windows с Python 3.12:

~~~sh
python tools/build_portable.py
~~~

## Контейнер

```sh
docker compose up -d --build --wait
```

Команда создаёт именованный постоянный том для /data.
Веб-порт привязан к 127.0.0.1:8787. Процесс работает с UID 10001 со сброшенными
capabilities, с корневой файловой системой только для чтения и доступными для записи /data и /tmp.
`--wait` дожидается работоспособности веб-сервера перед возвратом; состояние авторизации
в Telegram и доставки отображается в панели. Поставляемые вспомогательные скрипты после сборки
ждут готовности не более 180 секунд. Первоначальная загрузка зависимостей может занять больше времени.

Оба базовых файла Compose используют имя проекта `tgwitness`, поэтому распаковка нового выпуска
в другой каталог не приводит к незаметному выбору нового тома данных. Держите активным только
одно развёртывание этого проекта. Для независимых установок используйте уникальное
`docker compose -p NAME ...` и другой порт хоста и сохраняйте оба значения при обновлениях.
Для старого развёртывания с другим именем проекта продолжайте использовать его исходное
имя через `-p`; `docker compose ls` выводит существующие проекты.

Чтобы использовать другой порт на loopback-интерфейсе, скопируйте `deploy/env.example` в `.env`
и измените `TGWITNESS_PORT`. Например, при `TGWITNESS_PORT=8788` панель доступна по адресу
`http://127.0.0.1:8788`; контейнер по-прежнему слушает порт 8787. Файл `.env` игнорируется Git.

Получите начальный токен:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

Полезные команды:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` перезапускает коллектор после сбоя или перезапуска демона Docker.
На Linux-сервере включите автозапуск Docker при загрузке через менеджер служб дистрибутива,
обычно `sudo systemctl enable --now docker`. В Windows/macOS включите в Docker Desktop
запуск при входе в систему. Выход из системы на рабочем компьютере, спящий режим или
остановленный демон Docker могут прервать сбор. Явно остановленный контейнер остаётся
остановленным, пока вы его снова не запустите.

В примере конфигурации том /tmp ограничен 512 МиБ. Экспорты вместо него собираются
в каталоге `temporary-exports/` каждого рабочего пространства на постоянном томе /data.
Зарезервируйте там место для одновременных экспортов, роста журнала и WAL, медиафайлов
и резервных копий.
Скрипт запуска использует deploy/constraints.txt, чтобы закрепить проверенные версии зависимостей
среды выполнения. Docker и серверы с повышенной доказуемостью устанавливают пакеты
из deploy/requirements.lock и deploy/build.lock с pip --require-hashes: каждый файл пакета
должен совпадать с SHA-256, записанным в коммите, поэтому файл, подменённый на PyPI или зеркале,
отклоняется. Базовый образ Python и пакеты операционной системы по-прежнему требуют
отдельной проверки при каждом выпуске.

Не используйте docker compose down -v, если не собираетесь уничтожить журнал и ключи.
Состояние работоспособности контейнера отражает доступность веб-сервера, а не успешный сбор
из Telegram. Проверяйте в панели состояние коллектора, сигналы работоспособности, ошибки
и события охвата.

### Профиль независимого свидетеля

Необязательная служба `witness` запускает [независимого свидетеля](WITNESS.md) в отдельном
контейнере, с собственным ключом и журналом в томе `witness-data`; для коллектора у неё есть
только токен свидетеля с доступом на чтение. Создайте токен в панели в разделе
**Инструменты → Дополнительно → Независимый свидетель**, добавьте его вместе с токеном бота
и каналом в `.env`, затем запустите профиль:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

Служба обращается к коллектору внутри сети Compose по адресу `http://tgwitness:8787`
(его переопределяет `TGWITNESS_WITNESS_COLLECTOR`, например с `/profiles/<workspace ID>` для
другого рабочего пространства). Для свидетеля на отдельном сервере, которым управляет другое
лицо, используйте там `deploy/compose/compose.witness.yaml`, указав в `TGWITNESS_WITNESS_COLLECTOR`
HTTPS-адрес коллектора; этот файл содержит только свидетеля.

## Установка опубликованного образа

Скопируйте `deploy/env.example` в `.env`. Укажите в `TGWITNESS_IMAGE` опубликованную версию,
записав путь к репозиторию **строчными буквами**, например:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.9.2
TGWITNESS_PORT=8787
```

Запускайте этот файл отдельно, вместо `compose.yaml`:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

На хосте не нужны сборка из исходного кода, Python или компилятор. Рабочий процесс выпуска
собирает контейнеры для Linux AMD64 и ARM64, включая Linux-ВМ Docker Desktop.
Используйте тег версии или `ghcr.io/owner/repository@sha256:...` из сводки рабочего процесса.
Подвижный тег `latest` и автоматическое обновление приложения не настроены. Варианты
с образом и со сборкой из исходного кода используют один и тот же том данных, если у них
совпадает имя проекта.

## Автоматический HTTPS на сервере

Нужны сервер с Docker, домен под вашим управлением и постоянное локальное хранилище.
Направьте записи A/AAAA домена на сервер; публикуйте AAAA, только если сервер доступен
по IPv6. Разрешите входящие TCP 80 и 443 и исходящие DNS/HTTPS для выпуска сертификата.
Эти порты не должны быть заняты другими службами.

Скопируйте `deploy/env.example` в `.env` и укажите имя хоста без схемы и пути:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

Запустите сборку из исходного кода с HTTPS-оверлеем:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

Для опубликованного образа укажите первым файлом `deploy/compose/compose.image.yaml`.
Сохраняйте оба аргумента `-f` в последующих командах просмотра состояния, журналов, обновления
и остановки.

Caddy получает и продлевает сертификат, перенаправляет HTTP на HTTPS и передаёт
запросы коллектору в частной сети Compose. Состояние сертификата хранится в отдельном
постоянном томе. Прямой порт коллектора на хосте по-прежнему доступен только через loopback.
Поставляемая конфигурация Caddy не включает журнал доступа.

Откройте `https://watch.your-domain.org` и введите токен панели. Готовность в Compose
относится к контейнерам; выпуск сертификата и доступность извне зависят от DNS
и межсетевого экрана. Если HTTPS не работает, проверьте DNS, правила межсетевого экрана
и вывод команды:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

Поставляемый образ Caddy следует тегу `2-alpine`. Команда pull обновляет этот образ;
если нужны фиксированные версии инфраструктуры, закрепите в своём развёртывании проверенный дайджест.

## Обновления и резервные копии

При обновлениях сохраняйте имя проекта Compose и том данных. Сначала остановите
коллектор и сделайте полную резервную копию. Для развёртывания по умолчанию со сборкой
из исходного кода:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

Каждый раз используйте новое место для резервной копии за пределами репозитория и защищайте его
как материал, дающий доступ к аккаунтам. Путь в примере условный; используйте своё закрытое
место для резервных копий. Копируйте весь каталог, включая скрытые файлы, все рабочие пространства,
ключи, журналы и медиафайлы. Если настроен внешний мастер-ключ хранилища, сохраните его отдельно.
ZIP с доказательствами не является резервной копией, из которой можно восстановить приложение.
При использовании HTTPS сохраните также тома Caddy, если нужно сохранить состояние его сертификата
и учётной записи.

Для развёртывания из исходного кода получите файлы нового выпуска и выполните:

```sh
docker compose up -d --build --wait
```

Для развёртывания из образа укажите в `TGWITNESS_IMAGE` нужную версию и выполните:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

В приведённых выше командах остановки и копирования также используйте файлы Compose своей установки.
Сохраните `.env`, собственную конфигурацию и прежнее имя проекта. `down` сохраняет именованные
тома; **`down -v` удаляет их**. Не копируйте `.venv` между операционными системами
или версиями Python. Для обновления установки без Docker остановите TgWitness, сделайте резервную
копию всего каталога данных, замените файлы исходного кода и перед запуском выполните
`python start.py --setup-only`.

После обновления проверьте доступ к панели, подключённый аккаунт, состояние наблюдения и охват.
После перезапуска TgWitness продолжает с сохранённой позиции обновлений Telegram
и запрашивает обновления, пропущенные за время обновления. Если будущая версия изменит
форматы хранения, для отката может понадобиться резервная копия, сделанная до обновления.

## Удалённый сервер

Оставьте службу привязанной к loopback и используйте SSH-туннель либо завершайте HTTPS
на обратном прокси. Базовый файл Compose предназначен только для локального доступа; необязательный
оверлей `deploy/compose/compose.https.yaml` добавляет Caddy для настроенного домена.
Не допускайте попадания bearer-токена в URL и журналы прокси. Обратный прокси должен
ограничивать размер запросов и частоту подключений. Не открывайте доступ по обычному HTTP
из интернета.

Примеры для systemd, задачи Windows при входе в систему, пользовательского агента macOS и Caddy
находятся в [deploy/](../../deploy/README.md). Перед установкой проверьте и при необходимости
измените пути в них. Это поставляемые шаблоны, а не проверенные локальным запуском конфигурации
для каждой платформы. Обычный скрипт запуска не регистрирует фоновых служб или задач.

В Windows при запуске без окна через `pythonw.exe` диагностика запуска и сервера записывается
в `logs/server.log` в каталоге данных (5 МиБ на файл, две ротируемые резервные копии).
При запуске в консоли журнал выводится в консоль. Журнал HTTP-доступа отключён в обоих
режимах. Защищайте журналы вместе с каталогом данных и просматривайте их перед передачей.

## Перезапуск и пропуски

Последнее запрошенное состояние наблюдения сохраняется. Если наблюдение было включено,
при запуске приложение пытается переподключиться и возобновить работу с выбранными источниками.
Ручная пауза отменяет это намерение. Неудачный перезапуск записывается и отображается в панели.

TgWitness хранит позицию обновлений Telegram для аккаунта и для каждого канала
(pts, qts, seq и date) в хранилище рабочего пространства и восстанавливает её при следующем запуске.
Затем клиент запрашивает обновления, пропущенные, пока процесс был остановлен, а
периодическая перепроверка восстанавливает пропущенные сообщения и отмечает сохранённые,
которые Telegram больше не возвращает. Диалоги загружаются заново при запуске. При каждом запуске
записываются предыдущий заголовок журнала, граница периода простоя и позиция обновлений,
с которой продолжена работа.
Монитор проверяет связь каждые 10 секунд и раз в минуту добавляет сигнал работоспособности
(**Инструменты → Параметры → Отметка активности каждые**).
Разрывы связи и периоды тишины записываются как пропуски в охвате с указанием причины.
Снимки истории хранятся как отдельные наблюдения текущей истории рядом с записями, полученными
в реальном времени.

Очередь медиафайлов хранится в базе SQLite каждого рабочего пространства. Сообщение и его
задание фиксируются атомарно. Прерванные выполнявшиеся задания при запуске восстанавливаются
для повторной попытки. Для каждой загрузки действует базовый тайм-аут 120 секунд плюс время,
нужное для её размера при скорости 256 КиБ/с, и лимит от 1 до 2 000 МиБ для каждого типа
вложений; тайм-аут, скорость и повторы настраиваются в **Инструменты → Параметры**. Коллектор
пропускает файлы неизвестного размера. Пауза сохраняет задания в очереди. Повторная попытка
использует исходный наблюдавшийся дескриптор файла, а не последнюю версию сообщения,
отредактированного позже. Число повторов при временных сбоях ограничено; паузы FloodWait
для медиа сохраняются после перезапуска. Восстановление медиа не связано с восстановлением
обновлений Telegram и не может воссоздать исчезнувшие файлы.

## Резервное копирование, восстановление и ёмкость

Остановите процесс, прежде чем копировать **весь каталог данных**, включая vault.key,
signing.enc, credentials.enc, файлы базы SQLite и WAL, медиафайлы, токен, контрольные точки
и все подкаталоги profiles/. Восстанавливайте
полную копию при остановленной целевой службе. Отсутствие ключей хранилища или несовпадение
ключа подписи приводят к ошибке запуска; не создавайте ключи заново, чтобы принудительно
получить доступ.

Храните резервные копии с секретами в зашифрованном виде и с контролем доступа. ZIP с доказательствами —
переносимые материалы для проверки, а не резервные копии приложения или сессий Telegram.
Автоматического удаления по сроку хранения нет. Планируйте место на диске для всех сообщений,
исходных метаданных, медиафайлов, временных экспортов и резервных копий.

Проверка при запуске и экспорт обрабатывают записи потоком, не загружая весь журнал.
Экспорт фиксирует снимок для чтения, пока новые записи в WAL продолжаются; длительные экспорты
могут удерживать страницы WAL, поэтому объём диска по-прежнему важен. Размер ZIP ограничен
4 ГиБ в распакованном виде — это значение по умолчанию независимого верификатора; параметр
**Инструменты → Параметры → Самый большой подписанный ZIP-файл, распакованный**
повышает это ограничение, а такие архивы проверяются с `verify.py --max-gib N`. Для других
форматов ограничения по числу событий нет.
Поддерживаемые браузеры записывают части ответа потоком в выбранный пользователем файл.
Другие браузеры буферизуют не более 128 МиБ и для более крупных передач направляют к CLI
с аутентификацией:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

Используйте `--profile ID` из **Экспорт → Идентификатор рабочей области** для другого рабочего
пространства, `--format zip|jsonl|csv|html`, `--url https://your-server` для удалённого сервера
или `--max-mib`, чтобы изменить лимит передачи 5 ГиБ. Обычный HTTP допускается только для
loopback. Токены передаются в заголовках, перенаправления отклоняются, существующие файлы
не перезаписываются, а незавершённые загрузки не сохраняются как готовые файлы.
Если TGWITNESS_TOKEN переопределяет сгенерированный токен, используйте отдельно защищённый файл
с этим действующим значением: при переопределении panel-token.txt не перезаписывается.
SHA-256, который выводит команда, — лишь контрольная сумма передачи; подписанный ZIP проверяйте
отдельно.

Панель показывает медиафайлы в очереди и с ошибками, самый старый ожидающий файл, свободное
место на диске, паузы запросов к Telegram и источники с неподтверждённым доступом. Эта
диагностика не является полноценным сквозным контролем доставки. Рабочие пространства работают
в одном процессе, поэтому сильно нагруженный аккаунт всё же может влиять на остальные. Ещё предстоит сделать:
отдельные рабочие процессы, хранение и ротацию, надёжное восстановление обновлений и полную
проверку развёртывания. Ограниченный доступ к панели описан в разделе
[«Доступ и права»](../ACCESS.md); независимые контрольные точки — в
[руководстве по свидетелю](WITNESS.md).

Подробные процедуры: [подключение и безопасность](../CONNECTION-SECURITY.md) и
[режимы работы](../OPERATIONS.md).
