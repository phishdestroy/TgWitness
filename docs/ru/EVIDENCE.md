# Формат доказательств, версия 1

TgWitness сохраняет видимые для аккаунта записи Telegram в подписанном журнале.
Получатели могут проверить сохраненные записи, вложения и отчеты с помощью доверенного
ключа сборщика, проверить внешнее время от третьей стороны для последней записи и сравнить
журнал с контрольной точкой, сохраненной ранее.
На этой странице описаны форматы, проверки и материалы, которые необходимо сохранить для передачи.

Пользователи в Windows могут начать с запуска файла **VERIFY.cmd**: программа запросит исходный
архив ZIP и самостоятельно полученный отпечаток ключа, отобразит результат с пояснениями
и сохранит отдельный отчет о проверке. Информацию о настройке и ограничениях доверия см. в разделе [программы запуска проверки и
портативная среда выполнения](../VERIFICATION_LAUNCHER.md).

<a id="what-is-signed"></a>
## Что подписано

| Материал | Защита | Что следует сохранить |
| --- | --- | --- |
| Каждая запись в журнале, включая оперативные события | Цепочка SHA-256 и подпись Ed25519 для каждого события | Исходный файл `events.jsonl`, отпечаток ключа доверия и сохраненная контрольная точка |
| Содержимое ZIP-архива с доказательствами | `manifest.sig` подписывает канонический манифест, в котором перечислены хэши файлов содержимого | Полный ZIP-архив, включая манифест и подпись |
| Сохраненные вложения | SHA-256 и количество байтов в событии с подписью `media.saved`; хеш файла в манифесте ZIP с подписью | Исходные байты внутри проверенного ZIP-архива |
| Контрольный пункт | Подпись Ed25519, включающая длину журнала, хеш заголовка, открытый ключ и время создания | Независимая копия, сохраненная до внесения спорного изменения |
| Квитанция о выполнении заказа | Подписанная запись о версии сборщика, хеши исходных файлов и начальные настройки, также включенные в `process.started` | Приемная накладная, соответствующая проводка в журнале и данные об условиях эксплуатации для выбранного режима проверки |
| Наглядные отчеты: `report.html` и его части: `report.json`, `report.pdf`, `chat.pdf` | Каждый файл защищён печатью Ed25519, подтверждающей его содержимое; кроме того, PDF-файл содержит стандартную PDF-подпись (см. [Отчеты в удобочитаемом формате](#readable-reports)) | Полученный файл и отпечаток доверенного ключа; ZIP-архив, к которому он относится |
| Автономный файл CSV | Отсутствие автономной криптографической подписи; одних только хешей событий недостаточно | Для проверки целостности используйте точную копию, содержащуюся в проверенном ZIP-файле |
| Скриншоты, распечатки или PDF-файлы, созданные браузером | На производной отсутствует подпись TgWitness | Сохраните исходный проверенный пакет и задокументируйте процесс создания производного продукта |

Перед генерацией каждого экспортного формата коллектор проверяет подписи журнала.
Читаемые отчеты в форматах HTML и PDF имеют собственные печати; автономный файл CSV проверяется как
часть подписанного архива ZIP. Сохраните архив ZIP, чтобы сохранить байты вложения и манифест,
а также создайте отдельную контрольную точку для сверки журнала с более ранней границей.

<a id="formats-and-verification-paths"></a>
## Форматы и пути проверки

Режим сбора данных и формат вывода отвечают на разные вопросы. Режим
обеспечивает сбор данных и информацию об окружающей среде; каждый формат сохраняет или представляет
часть этой записи с учетом приведенных ниже проверок.

| Вывод | Проверка и использование |
| --- | --- |
| Архив с доказательствами в формате ZIP | Канонические события, подписанный манифест, отчет о проверке, записи о хранении, приложения и имеющиеся внешние квитанции; проверьте архив и выбранный режим его пополнения. |
| Контейнер ASiC-E | Архив ZIP с доказательствами в формате контейнера ETSI ASiC-E (EN 319 162-1), содержащий записи `mimetype` и `META-INF/ASiCManifest.xml`, подписанный с помощью CAdES собственным сертификатом рабочей среды на уровне B-B или B-T, если включена функция временной маркировки. Такие валидаторы, как EU DSS, проверяют формат и целостность и, поскольку сертификат выдан самостоятельно, сообщают об отсутствии опорного пункта доверия. EU DSS 6.3 с настройками по умолчанию отклоняет контейнер, содержащий более 1000 файлов («Обнаружено слишком много файлов»). `verify.py` проверяет манифест Ed25519 и каждый указанный в нём файл, значения SHA-256 в `META-INF/ASiCManifest.xml` и в добавленном `ASiCManifestNNN.xml` или `ASiCEvidenceRecordManifest.xml`, и выдает ошибку при проверке записи `META-INF/`, которую ни одна из них не охватывает. Он не проверяет подписи CAdES и сообщает об этом. |
| Отчеты в форматах HTML и JSON | Отдельно упакованные представления с указанием источников, которые также перечислены в манифесте ZIP-архива. Их зарегистрированные значения суммируют типы событий журнала. |
| Отчеты в формате PDF | Печать Ed25519 плюс базовая PDF-подпись PAdES для диапазона байтов: B-B или B-T с временной меткой подписи, если функция временной метки включена. Программа проверки TgWitness использует доверенный ключ Ed25519; отображение доверия к сертификату в программе просмотра представляет собой отдельную проверку. |
| CSV | Представление электронной таблицы, включенное в манифест ZIP. Экранирование формул обеспечивает безопасность использования электронной таблицы; исходный подписанный текст сохраняется в журнале. |
| JSONL | Заверенные записи о событиях, включая ссылки на вложения. Архив ZIP с доказательствами дополнительно содержит сохраненные байты вложений. |
| Экспорт чата и представления, совместимые с настольными версиями | Сбор исторических данных и доступных записей журналов администрирования с требуемым представлением и подписанным архивом. Сохраненные версии данных оперативного мониторинга представляют собой отдельный канал сбора данных. |
| Медиафайлы и записи, содержащие только хэш-коды | Сохраненные байты сверяются с их хэшем SHA-256 и ссылкой на сообщение. При сборе только хэшей сохраняются доступные метаданные хэша для последующего сравнения с байтами файла. |
| STIX/MISP и профили лиц | Извлеченные данные наблюдений с указанием источника, идентификаторы учетных записей и аналитические совпадения. Сигнатуры профилей и хэши записей можно сверить с исходными доказательствами; происхождение кэша аватаров маркируется отдельно. |
| Выдержка из протокола передачи | Подписанные правила раскрытия информации, неизменённые записи и помеченные сведением о сокращении записи, в которых сохранены исходные хэши/подписи. Для сравнения, требующего учета скрытых полей, используйте сохраненный оригинал. |
| Свидетельские показания и квитанции с указанием времени | Ранее в журнале фиксировались границы, непрерывность и отдельные подтвержденные временные отметки. Они сопровождают процедуры приемки и проверки архива. |
| Доставка с защитой паролем | Обеспечивает защиту вложенного пакета во время передачи. `.tgwpw` использует шифрование с аутентификацией по алгоритму AES-GCM, включая аутентифицированную заключительную запись; вложенный журнал сохраняет свои подписи и квитанции о получении. |

Распечатка или снимок экрана представляют собой отображение подписанного материала. Идентификатор отчета,
отпечаток ключа и QR-ссылка помогают найти исходный файл для проверки.
В декларациях о хранении фиксируются данные о назначенном эксперте и передаче материалов;
результаты проверки и квитанции о получении хранятся в качестве отдельных доказательств.

<a id="external-signatures"></a>
### Внешние подписи

Подпись также может быть получена с помощью ключа, который TgWitness никогда не хранит, например,
квалифицированной электронной подписи следователя или печати организации. В случае **экспорта** **внешняя
подпись** на подготовленном экспорте без пароля предоставляет байты для подписи: новый элемент
`META-INF/ASiCManifestNNN.xml`, содержащий список всех файлов с их SHA-256 для контейнера ASiC-E
, или элемент `manifest.json` экспорта для ZIP-архива. Подписывающий возвращает CMS (CAdES)
в виде `.p7s` — отдельно или со встроенным содержимым.

TgWitness проверяет, что подпись охватывает именно эти байты, и проводит верификацию с помощью
сертификата подписавшего лица (RSA PKCS#1 v1.5, RSASSA-PSS, ECDSA, Ed25519, Ed448). Цепочка
проверяется только по корневым сертификатам, предоставленным оператором; отзыв, списки доверенных
сертификатов и статус квалифицированности не проверяются. На панели отображается одно состояние для каждой подписи:
ожидание подписи, прикреплена и не проверена, проверена, алгоритм не поддерживается,
подпись недействительна, подписанные байты не совпадают или сертификат не входит в цепочку, ведущую к предоставленному
корневому сертификату. Изменение экспорта
после передачи байтов приводит к установке для всех его подписей состояния «подписанные байты не совпадают».

Функция **Скачать с подписями** добавляет подписи и их манифесты под тегом `META-INF`
в контейнер ASiC-E. В случае ZIP-архива она помещает неизменённый ZIP-архив, файлы `.p7s` и
`SIGNATURES.txt` во внешний ZIP-архив. Недопустимые подписи и подписи, наложенные на другие байты,
исключаются. Включается подпись с алгоритмом, который TgWitness не может проверить;
панель отображает её состояние, как и `SIGNATURES.txt` для ZIP-файла.

<a id="signed-chat-images"></a>
### Изображения из чата с подписями

**Скачать подписанный ZIP-файл** в предварительном просмотре изображения позволяет сохранить страницы в формате PNG: `pages.sig.json` и
`README.txt`. Каждая страница заканчивается номерами записей журнала, отображаемыми на ней, чатом,
временем рендеринга, отпечатком ключа рабочей области и командой, проверяющей его. Панель
отправляет только SHA-256 каждой страницы и номера записей; сервер подтверждает, что записи
относятся к данному чату, подписывает отчёт (`tgwitness-image-attestation-v1`) с помощью
ключа рабочей области и фиксирует подписание в журнале как `export.image_attested`.

```
python verify.py page-01.png page-02.png pages.sig.json
python verify.py page-*.png pages.sig.json --fingerprint TRUSTED_SHA256 --evidence evidence.zip
```

Верификатор проверяет подпись, сопоставляет каждый файл PNG с подписанной страницей и выводит
отпечаток ключа. `--fingerprint` сравнивает подписавшего с отпечатком, полученным от
отправителя независимым образом. `--evidence` считывает ZIP-архив с подписанными доказательствами из той же рабочей области и
требует, чтобы каждая запись изображений присутствовала с тем же хешем. Измененный пиксель,
измененное утверждение или другой ключ приводят к сбою проверки. Изображения показывают сохраненные записи в
собственном макете TgWitness; они не отображают то, что Telegram показывал кому-либо.

<a id="comparing-chat-exports"></a>
## Сравнение экспортированных данных чата

Проверьте и сравните два ZIP-файла с экспортом чата, подписанных с использованием отпечатков подписей,
сохраненных независимо друг от друга:

```sh
python -m tgwitness.verify first.zip --compare second.zip \
  --fingerprint FIRST_TRUSTED_KEY_SHA256 --compare-fingerprint SECOND_TRUSTED_KEY_SHA256
```

`--require` и `--require-tier` отклонены вместе с `--compare`; проверьте требуемый
профиль каждого архива с помощью соответствующей проверки.

Если в обоих архивах зафиксированы одинаковые числовые идентификаторы учетной записи и чата, записи сопоставляются
по идентификатору сообщения. **Без изменений** означает равенство полной сохраненной записи в формате JSON:
включая полный текст, автора, даты, адресата ответа, вложенные метаданные и неизвестные поля. Порядок ключей в объекте JSON не имеет значения; значение имеют отсутствующие поля, нулевые значения, типы значений
и порядок массивов. Предварительный просмотр длиной 300 символов предназначен только для отображения. В измененных записях
указываются отличающиеся элементы верхнего уровня `changed_fields`, включая изменения, невидимые в этом предварительном просмотре.
Дубликаты идентификаторов сообщений отбрасываются, а не перезаписывают друг друга при сопоставлении.

Разница может заключаться в изменении отображаемого имени, количества просмотров, аннотации коллекции или
других метаданных наблюдения. Изменения в Telegram отображаются как отдельные события редактирования, а проверка каждого
архива показывает, сохранен ли он в целостности. Непроанализированные записи остаются
в сравнении и сравниваются на основе их сохраненного представления.

В случае несовпадения или отсутствия идентификаторов учетной записи/чата инструмент находит возможные
соответствия, используя данные об отправителе, полный текст, хеш файла, тип медиафайла и пятисекундный
допуск по времени, и отмечает их как **Совпадение**, а не **Без изменений**. Непроанализированные
записи остаются без сопоставления. Различия в сопоставленных записях перечисляются в `changed`,
в том числе в режиме содержимого. С помощью `--json` и `matched` подсчитываются возможные пары, а
`unchanged` — пары, полные сохраненные записи которых совпадают. Существующий
вывод `changed_fields` и целочисленный `unchanged` остаются совместимыми с
предыдущими результатами сравнения. Формат архива и проверка подписи остаются без изменений.

<a id="investigation-handoff"></a>
## Передача дела на расследование

1. Зафиксируйте в заметках по делу номер дела, оператора, цифровой идентификатор аккаунта в Telegram, выбранные
   источники, политику сбора данных и период сбора. TgWitness
   сохраняет наблюдения и поддерживает привязанные к источникам заметки и сбор данных в
   [Панели дела](../CASE-BOARD.md). Храните записи о передаче и хранении вместе с материалами
   дела. Проверьте настройки сбора данных с помощью
   [процедуры приёма в режиме реального времени](../internal/LIVE_ACCEPTANCE.md).
2. Сохраните отпечаток открытого ключа рабочей области отдельно, прежде чем полагаться на
   её экспортированные данные. Оставьте включенным режим доказательств (по умолчанию), чтобы контрольные точки получали квитанции в соответствии с RFC 3161
   и OpenTimestamps. Сохраняйте подписанные контрольные точки вне сборщика во время
   сбора данных. Регистрируйте прерывания и ограничения видимости учетной записи.
3. Экспортируйте **подписанный ZIP-файл** и сохраните подписанную квитанцию запуска. Используйте контрольную точку, расположенную
   на границе экспортируемого журнала или перед ней. Более поздняя контрольная точка может правильно отклонить
   более ранний экспорт как слишком короткий. Экспорты включают полный журнал рабочей области,
   независимо от фильтров панели; проверьте материалы перед их передачей.
4. Попросите получателя проверить ZIP-архив с помощью доверенной копии программы проверки,
   независимо предоставленного отпечатка и корневого
   сертификата органа, выдающего временные метки, полученного отдельно. Из доверенной среды с активной средой Python
  :

   ```sh
   python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --tsa-ca TSA-ROOT.pem --checkpoint retained-checkpoint.json --require evidence
   ```

   Отпечаток и проверенная временная метка последней записи соответствуют минимальным требованиям к
   доказательству; в противном случае выводится `--require evidence` с кодом 2. Контрольная точка является
   вспомогательной проверкой, поскольку она подписана ключом сборщика. При успешном выполнении
   вывод сообщает `key_pinned: true` и `checkpoint_checked: true`, если оба входных данных
   предоставлены и приняты. Сохраните результат проверки.

    Для передачи, требующей подтверждения окончательной экспортированной записи, используйте
    `--witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness`.
    Это не допустит экспорта с неподтвержденной конечной частью. Добавьте
    `--channel https://t.me/s/WITNESS_CHANNEL`, чтобы использовать даты, установленные Telegram в
    сообщениях-свидетельствах, в качестве внешнего времени. См.
    [процедуру передачи с подтверждением](../WITNESS.md#require-a-witnessed-export-boundary).
5. Зафиксируйте SHA-256 архива, границу экспорта, дату передачи, отправителя и
   получателя в вашем протоколе хранения. Сохраняйте исходный пакет в неизменном виде и работайте
   с копиями. Делитесь файлами доказательств, а не каталогом личных данных приложения,
   который также содержит сессии учётных записей и секретные ключи подписи.
   Для передачи выберите ZIP-архив с защитой по паролю и шифрованием AES-256 или более надёжный контейнер `.tgwpw`
  . ZIP использует недорогую схему вычисления пароля WinZip; используйте длинную случайную
  парольную фразу. `.tgwpw` использует scrypt и AES-256-GCM и открывается с помощью автономной
   команды верификатора `unseal-password`. Пароль не сохраняется и защищает только
   конфиденциальность; получатель расшифровывает
   архив и проверяет подписанный экспорт внутри, который остаётся неизменённым.
6. Чтобы проставить временную метку на контрольной точке вне режима доказательств, следуйте
   [процедуре RFC 3161](../TIMESTAMP.md) и сохраните запрос, контрольную точку, информацию о доверенном
   ЦС и проверенный ответ центра сертификации. Сама по себе подготовка запроса
   не приводит к получению временной метки.

Для `.tgwpw` используйте независимо полученный верификатор и выберите новый выходной файл
с исходным расширением: `python verify.py unseal-password export.tgwpw --out evidence.zip`.
Команда запрашивает пароль; `--password-stdin` считывает одну строку для автоматизации.
Она никогда не перезаписывает существующий файл и публикует открытый текст только после того, как все записи
пройдут аутентификацию. После этого выполните обычную проверку подписи на расшифрованном файле.
Контейнер использует scrypt (`N=131072`, `r=8`, `p=1`, 16-байтовый соль; около 128 MiB ОЗУ)
и AES-256-GCM с записями размером 1 MiB и аутентифицированной конечной записью. Зашифрованная
запись метаданных хранит внутреннее имя файла, поэтому загруженные контейнеры можно переименовывать.

Успешная верификация подтверждает целостность относительно ключа доверенного сборщика
и сохраненной границы. См. [объем верификации](#verification-scope) для ознакомления с
допущениями о доверии и [результаты валидации](../VERIFICATION.md) для ознакомления с выполненными проверками.

<a id="handover-extract"></a>
## Выдержка из протокола передачи дел

Подписанный ZIP-файл содержит полный журнал рабочей области. Если суду, адвокату или службе по борьбе со злоупотреблениями требуются
только отдельные чаты, определенный период или конкретные участники, функция **Экспорт → Выдержка для передачи** формирует сокращенную
копию (`tgwitness-handover-v1`) в соответствии с выбранными правилами раскрытия информации.
Оператор указывает цель и выбирает чаты, опциональный период (UTC), участников, которых
касается выдержка, а также определяет, что происходит с остальными участниками (отображаются, заменяются псевдонимами P01, P02… или исключены
), какие тексты сообщений остаются, какие вложения и фотографии профилей включаются, а также будут ли
замаскированы номера телефонов и адреса электронной почты в текстах. Цель и эти правила указаны в
подписанном манифесте и в отчёте; в журнале регистрируется запись `handover.exported` с указанием доступа, который
её подготовил, и SHA-256 файла, а не его содержимого.

`verify.py` проверяет выдержку двумя способами. Запись, отображаемая как неизменённая, проверяется полностью: её
содержимое сравнивается с хешем, проверяется подпись Ed25519 и ссылка на включённую предшествующую запись. В
сокращённой записи сохраняются исходный хеш и подпись, поэтому подпись по-прежнему проходит проверку, но
утаенные поля не могут быть пересчитаны на её основе; в записи указывается, что именно было утаено, и в отчёте
это отмечается. Записи об обслуживании всего аккаунта (запуски и остановки, пробелы в охвате, уведомления о подключении, сети и хранилище,
изменения области действия и настроек) сохраняют только поля, указанные для их типа: списки чатов в них сокращаются до выбранных
чатов, а их итоги пересчитываются; при пропуске в результате проверки в реальном времени чата, не входящего в выборку, этот чат, его
номера сообщений и учётная запись свидетеля теряются; в выбранном чате для проверки учётная запись свидетеля заменяется его псевдонимом, если только
не отображаются все участники или он не является одним из выбранных лиц. Манифест указывает длину журнала и его заголовок с подписью сборщика над этим
заголовком, а также подсчитывает количество пропущенных записей; `coverage.json` описывает выбранные чаты. Новые выдержки также
содержат `proofs.jsonl`: для каждой включённой записи и для заголовка журнала — путь Меркла от
исходного хеша записи до корня журнала, указанного в подписанном манифесте. `verify.py` проверяет каждый
путь, чтобы убедиться, что каждая запись принадлежит одному и тому же журналу данной длины и с данным заголовком, без необходимости
проверки полного журнала; выдержка из 100 сообщений проверяется примерно за секунду независимо от размера журнала.
`--range=CHAT:FROM-TO` дополнительно подтверждает, что сообщения «ОТ» и «К» в чате присутствуют в выдержке,
и сообщает, сколько записей было проверено на их наличие. Если для некоторых чисел диапазона в
выдержке нет записей, также указывается их количество: они были исключены по правилам формирования выдержки, удалены или никогда не использовались,
и сама по себе выдержка не позволяет определить, что именно произошло. Имена в именах файлов
не распознаются. Проверьте окончательные файлы перед отправкой: свободный текст, имена файлов и выбранные
вложения по-прежнему могут идентифицировать людей. Сохраните полный подписанный ZIP-архив: выдержка является раскрытием информации, а не заменой.

<a id="readable-reports"></a>
## Удобные для чтения отчеты

ZIP-файлы с подписанными данными, результатами передачи и чатом содержат читаемые отчеты в форматах HTML и JSON, а также
PDF (при наличии необходимых шрифтов) на выбранном языке отчета. Каждый
отчет зашифрован ключом Ed25519 рабочей области и может быть проверен отдельно:
`python -m tgwitness.verify FILE --fingerprint KEY [--evidence ZIP]`.

- `report.html` / `chat.html`: операция запечатывания (`tgwitness-report-seal-v1`) закрывает файл и
  подписывает SHA-256 каждого предыдущего байта. Объемные журналы и чаты разбиваются на части
  настраиваемого размера (в настройках отчета — от 500 до 100 000 записей; по умолчанию — 5 000):
  `records/records-0001.html` или `messages/messages-0001.html`, каждая из которых запечатана с указанием номера, диапазона
  и общего количества, а также перечислена с SHA-256 в подписанном манифесте. Серии сигналов о работе коллектора
  отображаются одной строкой, если в настройках отчёта не указано их поочерёдное отображение.
- `report.json` (`tgwitness-report-json-v1`, ключи `format`, `report`, `seal`): печать подписывает
  SHA-256 канонического JSON-файла `report`, благодаря чему данные могут считываться судебными системами и скриптами,
  а также из них можно выбирать данные для защиты, при этом подписанный файл остаётся целым.
- `report.pdf` / `chat.pdf`: официальный документ для печати и архивирования, подписанный дважды на одни и те же
  байты — весь файл, за исключением значения подписи (`/ByteRange`). Стандартная подпись PDF
  — PAdES baseline (ETSI EN 319 142-1, `/SubFilter /ETSI.CAdES.detached`: CMS с SHA-256 и
  ECDSA P-256, signing-certificate-v2, без указания времени подписания CMS; заявленное время — `/M`) на уровне
  B-B или B-T с отметкой времени подписи по RFC 3161 в блоке CMS, если функция временной маркировки включена и
  центр временных отметок отвечает по маршруту на запросы вне Telegram. Используется
  самовыданный сертификат для подписи документов, хранящийся в хранилище рабочего пространства; его серийный номер субъекта
  номер является отпечатком ключа Ed25519. Печать Ed25519 передаётся внутри CMS в виде
  неподписанного атрибута `2.25.240684792623320047764573196045913242332` и указывает
  SHA-256 сертификата с помощью `"content": "pdf-byte-range"`, таким образом ключ Ed25519 гарантирует
  подлинность сертификата. Сертификат не является квалифицированным: программа просмотра PDF отображает подпись как действительную, а
  подписавшего — как неизвестного или недоверенного, пока сертификат не будет признан доверенным; вместо этого сравните отпечаток ключа Ed25519
  отпечаток. Для PDF-файлов на китайском, японском и корейском языках требуется шрифт
  на сервере (или в `TGWITNESS_FONT_DIR`); без него ZIP-архив содержит только отчеты в форматах HTML и JSON
 .
- `report.en.html`, `report.en.pdf` / `chat.en.html`, `chat.en.pdf`: английский оригинал
  того же отчёта, если язык отчёта не английский, заверенный и подписанный таким же образом и указанный
  под `report.original` в подписанном манифесте. Отчёт на выбранном языке открывается с
  рекомендацией подать английский оригинал вместе с заверенным или присяжным переводом; см.
  [Перевод отчётов для суда](../TRANSLATION.md).

В канале или супергруппе Telegram нумерует сообщения по порядку: 1, 2, 3… В экспорте чата перечислены
первый и последний номер, общее количество сообщений, а также все диапазоны отсутствующих номеров в
`message-ids.json`, манифесте и заголовке `chat.json`; кроме того, отмечены все пробелы в
транскрипте. `verify.py` перечисляет их, начиная с `chat.json`. Отсутствующий номер — это сообщение, которое Telegram
не вернул (удалено до экспорта или невидимое для аккаунта); в личных чатах и
обычных группах номера общие для всех чатов аккаунта, и пробелы не учитываются.

После считывания истории экспорт заново запрашивает у Telegram каждый отсутствующий номер по отдельности
(`channels.getMessages` — до 10 000 номеров, включая 1 000 номеров, расположенных ниже первого сообщения, которые равномерно распределяются по всем пробелам, если их больше). Результат находится в `message-ids.json` и отчете.
Пустой ответ фиксирует, что номер недоступен для данной учетной записи на момент повторной проверки;
причина не указывается. Сообщение, возвращённое при повторной проверке, добавляется в экспорт
и помечается как `found_on_recheck`.

Когда в рабочей области наблюдения обнаруживается, что сообщения чата были удалены, отсутствуют при повторной проверке или отредактированы, при
экспорте чата добавляется `journal-changes.jsonl`: эти записи журнала, каждая сохраненная версия и соответствующее уведомление,
каждая из которых сопровождается хешем и подписью Ed25519, полученными в журнале. `verify.py` пересчитывает хеш каждой
записи, сверяет её подпись с ключом экспорта и сравнивает количество записей с подписанным
манифестом; экспорт доказательств содержит полную цепочку хешей. В отчёте эти сообщения перечислены в разделе
**Удалённые сообщения и более ранние версии**.

Каждый отчет начинается с раздела **Кратко о материалах**: один абзац, затем — что показывают данные и что
включает в себя запись. Собственная печать страницы становится янтарного цвета, когда браузер проверяет
подпись печати, а не саму страницу: браузер не присваивает странице собственные байты. Он становится зелёным только тогда, когда
читатель перетаскивает файл в поле проверки внизу страницы и все байты совпадают, и только если
отображаемая страница является именно этим файлом; в противном случае он становится красным.

В каждом отчете точно указывается название программы: git-коммит, когда сборщик запускается из чек-аута или
установщик задаёт `TGWITNESS_COMMIT`, а также SHA-256 его исходных файлов (`source_tree_sha256`,
канонический JSON в формате «путь → SHA-256» для каждого файла `.py`, `.js`, `.css`, `.html` и `.svg` в
пакете), который воспроизводится при чек-ауте этого коммита, если файлы не были изменены. Клиент Telegram
имеет имя, состоящее из названия его библиотеки, уровня API и дата-центра. Когда начинается наблюдение, а также когда начинается и заканчивается экспорт чата,
коллектор запрашивает у Telegram время (`updates.getState`, целые
секунды) и фиксирует время Telegram за вычетом времени по часам коллектора с погрешностью, обусловленной
временем прохождения сигнала в обоих направлениях; эти измерения отображаются в отчётах в разделе «Цепочка хранения». При экспорте чата также фиксируется
момент чтения истории, помимо дат сообщений.

<a id="offline-report-viewer-and-archive-guide"></a>
### Руководство по автономному просмотру отчетов и архивированию

Перед открытием `chat.html` или `report.html` необходимо полностью распаковать ZIP-архив. Программа просмотра предоставляет функции поиска,
фильтров, просмотра участников, показателей, сведений о записях и выбора данных в форматах JSON/CSV без подключения к серверу. Держите
`viewer/` и `media/` рядом с отчетом. Выбранные элементы являются производными: используйте `verify.py SELECTION.json
--evidence ARCHIVE.zip` для их сравнения с подписанным архивом.
Программа проверки проверяет идентификатор отчёта, ключ подписи, границы архива и каждый выбранный элемент; отредактированные,
отсутствующие и дублирующиеся элементы не проходят проверку. Примечания к выбору и время создания остаются неподписанными метаданными.

Пробелы между номерами сообщений отображаются только в полной, неотфильтрованной ленте чата, отсортированной по возрастанию. Скрытие
категории или сбой при загрузке блока данных не должны приводить к тому, что пропущенная строка будет рассматриваться как признак отсутствия
сообщения. Подсветка результатов поиска осуществляется в простом тексте до HTML-эскейпинга с сохранением буквальной разметки.

Браузер проверяет подписи манифеста, идентификатор отчета и ключ, а также все указанные хэши файлов. Он
отклоняет неоднозначные или некорректно сформированные структуры ZIP, дубликаты имен и небезопасные пути, а также ограничивает размер файлов
256 MiB и общий объём содержимого — 4 GiB. Для архивов большего размера используйте автономный верификатор.
Эта проверка браузера дополняет проверки верификатора, касающиеся цепочек журналов и семантики данных.

`README.txt` содержит вводную инструкцию, сопоставленный перечень файлов, инструкции по проверке и примечания
по формату данных на языке отчета, а также полное руководство на английском языке. `SHA256SUMS` охватывает
перечисленные в нём файлы, за исключением самого себя, `manifest.json` и `manifest.sig`; подписанный манифест
также охватывает `SHA256SUMS`. Оставьте исходный ZIP-архив без изменений и сохраните рабочие файлы вне
разархивированной папки. Отчёты в формате PDF содержат закладки по разделам и идентификационные данные дела/отчёта на последующих страницах.

<a id="the-chat-at-export-time"></a>
### Чат во время экспорта

Экспорт чата фиксирует информацию, предоставленную Telegram о чате на момент начала экспорта: собственные
метки Telegram (`scam`, `fake`, `restricted` с указанием причин, `verified`), имена пользователей, описание, количество
участников и администраторов, связанное обсуждение, защиту контента, информацию о том, видят ли новые участники предыдущие
сообщения и с какого сообщения этот аккаунт имеет доступ к истории (`available_min_id`), дата
сообщения № 1, если это дата создания чата, и SHA-256 аватара чата (сохраненного в `media/`).
Здесь фиксируется место аккаунта, осуществляющего экспорт, в чате: роль, дата присоединения, кто его пригласил, а для
администратора — его права. Вместо этого указывается запрос, который Telegram отклоняет.

Если аккаунт, осуществляющий экспорт, является администратором, при экспорте в файл `admin-log.json` загружается журнал действий администратора чата (Telegram хранит его в течение примерно
48 часов): удаления и правки с указанием предоставленного контента,
аккаунта, совершившего действие, и даты исходного действия. Эти записи дополняют
сохраненные версии записей в LiveJournal и записи о получении уведомлений об удалении.

<a id="indicators"></a>
### Показатели

В списке отчетов и в архиве представлены в виде `indicators.csv`, `indicators.stix.json` (STIX 2.1)
и `indicators.misp.json` (событие MISP), на которые служба по борьбе со злоупотреблениями может реагировать в зарегистрированных сообщениях:
ссылки и домены (в том числе скрытые за текстом, в кнопках и в предварительном просмотре ссылок), адреса криптовалют,
имена пользователей Telegram и ссылки для приглашения, номера телефонов, адреса электронной почты и сохраненные изображения.
Адреса Bitcoin, Litecoin, Dogecoin и TRON указываются только в том случае, если их контрольная сумма base58 верна,
адреса segwit — если верна их контрольная сумма bech32 или bech32m, адреса TON — если верна их CRC,
а адреса XRP Ledger — если верна их контрольная сумма; адреса EVM и Solana помечаются
как непроверенные. Также отображаются хеши транзакций: 32-байтовый хеш с `0x` всегда, а
простая 64-символьная шестнадцатеричная строка — только в том случае, если тот же текст обозначает транзакцию (например,
`tx`, `hash`, `transaction`, название эксплорера). Простой хеш не указывает на цепочку, поскольку Bitcoin,
TRON, TON и другие используют хэши того же формата; это указано в записи, и цепочку необходимо определить с помощью
эксплорера. Ссылки на платежи (`bitcoin:`, `ethereum:`, `solana:`, `tron:`, `litecoin:`, `dogecoin:`,
`ton:`) перечисляются с указанием цепочки, адреса, суммы, контракта токена и метки, если эта информация
содержится в ссылке, а адрес длиной 20 символов или более в ссылке также указывается как кошелек, помеченный как взятый
из ссылки на платеж. Изображения содержат SHA-256 и перцептивный
хэш (dHash, 64 бита), который при повторном сжатии или изменении размера копий остаётся практически неизменным. В отчётах
индикаторы записываются так, чтобы они не открывались случайно (`hxxps[://]example[.]com`); файлы сохраняют
значения в том виде, в каком они были. Каждый индикатор помечается как «неизвестный» и не подлежит автоматическому обнаружению (STIX
`indicator_types: unknown`, MISP `to_ids: false`, распространение в собственной организации): его
наличие в списке означает, что он содержался в сообщении, а не то, что он является вредоносным. Ссылка, текст которой указывает на
адрес, отличный от того, который открывается, помечается в отчете.

Отчеты в формате PDF заканчиваются заявлением эксперта, которое необходимо подписать от руки, контрольным списком для нотариуса или
судебного эксперта, а также QR-кодом (также расположенным на первой странице), содержащим идентификатор отчета, отпечаток ключа и
хеш-код SHA-256 достоверных данных, благодаря чему распечатка позволяет отследить отчет в архиве.

<a id="event-canonicalization"></a>
## Канонизация событий

Входные данные хеша состоят именно из следующих полей:

~~~text
seq, observed_at, source_at, kind, chat_id, message_id, actor_id, payload, previous_hash
~~~

Сериализация с использованием JSON, совместимого с Python, с кодировкой UTF-8, отсортированными ключами объектов, без ASCII-эскейпинга, без незначительных пробелов и без значений NaN/бесконечности:

~~~python
json.dumps(value, ensure_ascii=False, sort_keys=True,
           separators=(",", ":"), allow_nan=False).encode("utf-8")
~~~

Хеш-сумма SHA-256 этих байтов становится хешем события. Подпись вычисляется по алгоритму Ed25519 над
32 исходными байтами хеша, а затем кодируется в Base64. Первый предыдущий хеш (previous_hash) состоит из 64 нулей.
Порядковые номера начинаются с 1 и увеличиваются на 1. Все события, включая операционные,
находятся в одной цепочке. Подавление дубликатов доставки отсутствует: повторные
наблюдения являются отдельными подтверждениями получения, а не утверждением о различных действиях Telegram.

Исходные даты Telegram представляют собой строки в формате ISO; двоичные поля преобразуются в объекты, содержащие
bytes_base64. Текст сообщения, сущности, дескрипторы мультимедиа, метаданные ответа, реакции
и действия сервиса сохраняются в исходных метаданных сообщения, если они предоставлены. Активное
сообщение также сохраняет обновление Telegram, которое его доставило, в `transport_update`; когда
это обновление содержит то же сообщение, что и `raw`, его поле `message` имеет значение
`{"same_as": "raw"}` вместо второй копии.

`observed_at` — время записи в формате UTC, зафиксированное коллектором; `source_at` — дата,
указанная в данном событии Telegram. Записи, созданные при обработке обновления в режиме реального времени, содержат
`payload.received_at` — время по UTC, когда обновление поступило в коллектор, и
`payload.processing_delay_ms`. При редактировании в режиме реального времени сохраняется указанная дата редактирования, в
снимках истории сохраняется дата сообщения с текущим временем наблюдения, а в обычном
уведомлении об удалении фиксируется время получения с нулевой датой источника. Записи в журнале администратора
сохраняют указанную дату действия отдельно. Порядок получения и порядок
событий источника представляют собой отдельные временные шкалы, при этом для сравнения доступны
данные наблюдений по времени и внешние подтверждения получения.

<a id="actor-semantics"></a>
## Семантика актеров

Атрибуция зависит от источника события. `message.new.actor_id` и
`message.edited.payload.sender_id` сохраняют данные об отправителе сообщения. Обычные
`message.deleted` уведомления содержат идентификаторы сообщений и имеют поле «исполнитель» с нулевым значением;
доступные записи журнала администратора содержат указанные в них данные о действии, исполнителе и дате.
Сообщения службы членства сохраняют отправителя и тип действия, необработанные обновления участников
сохраняют указанный `actor_id`, а моментальные снимки реакций сохраняют указанные
количества и видимые идентификаторы. Читайте эти записи вместе с сохраненными
версиями и [квитанциями о взаимодействии с панелью](../COLLECTION.md#own-actions).

Уведомления об удалении в личных чатах и обычных группах содержат только идентификаторы сообщений.
Эти чаты используют единую последовательность идентификаторов для всей учетной записи, поэтому каждый идентификатор однозначно идентифицирует одно сообщение
данной учетной записи. Если сообщение с этим идентификатором ранее сохранялось в этом журнале,
удаление фиксируется в данном чате как message.deleted с именем метода payload.chat_resolution.
Идентификаторы, которые никогда не сохранялись, хранятся в виде `deletion.unscoped`: это
фактическое уведомление об удалении, чат которого не был сопоставлен. Это отличается
от `message.missing_on_recheck`, которое фиксирует недоступный результат запроса, и
от пробела в сохраненных идентификаторах сообщений. Каналы и супергруппы нумеруют сообщения по чатам и
никогда не сопоставляются таким образом. Если удалённое сообщение было отправлено наблюдаемой учётной записью,
payload.deleted_message_was_outgoing принимает значение true; информация об удаляющем пользователе по-прежнему не предоставляется.

Уведомление без области действия сохраняет собственную метку, поскольку соответствующий чат может находиться за пределами
текущей области наблюдения или не иметь однозначного соответствия. Повторная проверка на отсутствие остается
отдельным наблюдением, отличным от уведомления об удалении, в подсчётах отчётов, фильтрах и
метках. Последующее восстановление сбрасывает текущее состояние «отсутствует», сохраняя при этом
ранее неудачную проверку в подписанной истории; уведомления об удалении остаются отдельным
типом события.

Несколько идентификаторов, относящихся к одному и тому же чату из одного уведомления, группируются как
`deletion.batch`, независимо от их количества, с указанием идентификаторов сообщений в том виде, в каком их отправил Telegram,
а также количества сообщений, отправленных этим аккаунтом. В уведомлении Telegram
перечислены сообщения; в журнале администратора чата указан действующий администратор, где аккаунт
может прочитать эту информацию. Ссылка (`message.deletion_attributed`) создаётся в зависимости от того, что поступило первым:
опрос, в котором запись в журнале администратора появилась до уведомления об удалении, сопоставляется при регистрации
уведомления.

<a id="coverage-continuity-gaps-and-unobserved-ids"></a>
## Охват: непрерывность, пробелы и ненаблюдаемые идентификаторы

Каждый подписанный ZIP-файл содержит `coverage.json`, HTML-отчет открывается с той же сводкой, а
`verify.py` пересчитывает её на основе `events.jsonl`, а не полагается на данные из файла:

- **Непрерывное наблюдение от X до Y.** Период начинается с `observation.started` и
  заканчивается при паузе, остановке, потере соединения с Telegram, выходе из системы, запуске процесса без
  упорядоченной остановки или прохождении более трёх минут без каких-либо записей во время наблюдения
  (сигналы о работе записываются каждую минуту, поэтому отсутствие записей означает, что процесс остановился, завис или
  компьютер перешёл в спящий режим). Когда интервал между сигналами о работе изменяется в **Дополнительные инструменты → Параметры**, каждый сигнал
  фиксирует это изменение, и допустимое время отсутствия записей становится равным трём интервалам, но никогда не меньше трёх минут.
- В списке **Пробелы** указано время между периодами с указанием причины. Пробел, остающийся открытым на момент последней
  записи, помечается значком `not_resumed_by_last_record`.
- **Идентификаторы сообщений, не зафиксированные.** Для каналов и супергрупп, в которых сообщения нумеруются по
  чату, пропущенные идентификаторы между зафиксированными указываются в виде диапазонов. Они отображаются как
  *не зафиксированные* — удалённые, никогда не доставленные или находящиеся за пределами сохраненной истории — но никогда как
  удалённые. Личные чаты и обычные группы используют общую для всей учётной записи нумерацию, поэтому пробелы внутри
  одного такого чата ничего не значат и там не перечисляются.
- Уведомления о пробелах на уровне чата (например, запрос Telegram на восстановление разницы в одном
  канале) учитываются как заметки; они не прерывают общий охват.
- **Записи сеансов.** Периоды, в течение которых счетчик обновлений Telegram увеличивался, хотя никаких обновлений
  в этот сеанс не поступало (`updates_diverted`), этот сеанс покинул список сеансов Telegram, хотя
  его соединение продолжало работать (`session_revoked_externally`), или ответ контрольного запроса
  поступил только из истории (`probe_ack_missed_live`), перечисляются отдельно. Верификатор
  также сообщает, откуда был получен сессионный ключ Telegram, какие другие сессии были авторизованы на момент
  начала наблюдения, какие сессии были добавлены во время наблюдения, уведомления о безопасности Telegram
  (777000), какие другие сессии были завершены из рабочей области, периоды, когда была активна только одна сессия, количество запросов к свидетелю
  и обновления по телефонным звонкам. См. [аккаунты](../ACCOUNTS.md#witness-probe). Пока
  включена функция [строгий выбор чатов](../COLLECTION.md#strict-chosen-chats) (`scope.strict` в `observation.started`),
  список сеансов (за исключением случаев, когда это единственный сеанс или когда включена функция **Устройства Telegram**), уведомления о безопасности и
  обновления о телефонных звонках не собираются, поэтому их отсутствие ничего не означает, а удаление сопоставляется с сеансом
  только в том случае, если она проходила в течение 10 минут до этого.

<a id="update-sequence-pts"></a>
### Последовательность обновлений (`pts`)

Telegram фиксирует обновления, связанные с сообщениями, с помощью `pts`: одна последовательность для аккаунта
(личные чаты и обычные группы вместе) и по одной для каждого канала или супергруппы. Коллектор
записывает каждую полученную им непрерывную последовательность в виде записи `coverage.sequence`
: первую и последнюю записи `pts`, количество обновлений каждого типа, а также информацию о том,
были ли они отправлены в режиме реального времени или возвращены с помощью `getDifference` или `getChannelDifference`. Разрыв представляет собой запись
`coverage.gap`, а `coverage.gap_closed` указывает на `pts`, с которой последовательность
снова становится целой.

Непрерывный отрезок показывает, что каждое обновление Telegram, пронумерованное в этой последовательности между
первым и последним `pts`, достигло клиента Telegram данного сборщика. Это ничего не говорит о
содержании, которое Telegram никогда не отправлял на эту учетную запись, о времени до первого зафиксированного
`pts` или об отрезках, которые сборщик не зафиксировал. Прыжок `pts`, который не
покрывается ни одной зафиксированной последовательностью или разницей, отображается как разрыв.

`GET /api/continuity` определяет для интервала (`since`, `until`, `chat_id`), является ли каждая
последовательность непрерывной, и перечисляет места разрыва с указанием причин. `verify.py` выводит те же
данные из записей архива в разделе **Непрерывность последовательности**.

<a id="missing-message-numbers-gap_summary"></a>
### Пропущенные номера сообщений (`gap_summary`)

Руководство для читателя по данному разделу, а также информацию о периодах наблюдений и пробелах см. в разделе [Охват и отсутствующие данные](../COVERAGE.md).

**Предварительный просмотр.** `coverage.json` → `gap_summary` измеряет номера, присвоенные Telegram, которые этот
коллектор никогда не видел. Telegram нумерует сообщения один раз на канал или супергруппу и один раз на
аккаунт во всех частных чатах, ботах и обычных группах. Номер, находящийся между двумя наблюдаемыми
сообщениями, либо наблюдается, либо отсутствует; непрерывный диапазон является утверждением о том, что
каждое сообщение, пронумерованное в нём, было наблюдаемо. Пробел не указывает ни на какого участника, ни на какую-либо причину.

| Поле | Значение |
| --- | --- |
| `status` | `on` или `off`, если эта функция отключена в разделе **«Дополнительные инструменты» → «Параметры» → «Анализ пробелов»** |
| `parameters` | Параметры, с помощью которых был получен данный результат, чтобы его можно было повторить |
| `chats[]` | По одной записи на каждый канал или супергруппу, каждая из которых пронумерована отдельно |
| `account` | Общая для всего аккаунта хронология личных чатов, ботов и обычных групп |
| `status` (за последовательность) | `applicable` или `not_applicable` с `reason` |
| `observed_from`, `observed_to`, `span` | Первое и последнее наблюдаемое число, а также размер интервала |
| `observed`, `observed_without_content` | Наблюдаемые значения; значения, известные только по записям о удалении или повторной проверке |
| `missing`, `density`, `gap_ranges`, `largest_gap` | Никогда не фиксировавшиеся значения, их доля в диапазоне, количество серий, самая длинная серия |
| `clusters[]` | Перечисленные пробелы: `low`, `high`, `missing`, а также соседние наблюдаемые числа `after` / `before` с указанием времени их наблюдения |
| `service_estimate` | Только при включенной функции: сколько отсутствующих номеров пришлось бы на служебные сообщения с учетом их наблюдаемой доли. Никогда не вычитается из `missing` |

Валидность выводится из журнала, она никогда не принимается за данность:

- **Каналы и супергруппы** учитываются по каждому чату, в том числе при экспорте выбранных чатов.
  Записи, выбранные отправителем, формируют статистику `not_applicable`.
- **Последовательность по всему аккаунту** измеряется только от первого до последнего сообщения,
  поступившего в период, когда сбор данных по всему аккаунту был включен, и включает приватные чаты, ботов, обычные
  группы и собственные сообщения аккаунта, при этом ни один такой чат не исключается (`scope.changed`).
  Цифры, указанные в `deletion.unscoped`, считаются наблюдаемыми без учета содержания. Экспорт или
  передача выбранных чатов не позволяют измерить этот показатель. Если сбор данных по всей учётной записи был
  отключён, а затем снова включён, в примечании указывается, что номера, использовавшиеся в промежуточный период, отображаются как пробелы.
- Сервисные сообщения представляют собой записи журнала со своими собственными номерами, поэтому они сами заполняют свои пробелы;
  дополнительная оценка служит лишь для контекста.

`verify.py`
пересчитывает `gap_summary`
на основе `events.jsonl`
с использованием параметров, указанных в элементе
`coverage.json`
со знаком (значения по умолчанию для старых архивов), и
выводит строку, относящуюся ко всей учетной записи, в сводке охвата. `get_capture_status`
архива (MCP и командная строка) возвращает те же показатели для чатов, которые может читать пользователь;
последовательность для всей учётной записи доступна только при охвате всего рабочего пространства.

Повторные наблюдения одного служебного сообщения учитываются один раз, а при расчете показателей обслуживания учетной записи
используются только значения, лежащие в пределах измеряемого диапазона. Применяемый объем должен явно сохранять
собственные сообщения учетной записи до включения измерения на уровне всей учетной записи; измерение
начинается с записей, содержащих эту информацию. Измеряемый диапазон охватывает текущее
наблюдение, и его возобновление фиксируется. Запрос к архиву в режиме реального времени имеет временной
лимит, включая сканирование базы данных, и помечает незавершенное измерение как частичное.

Telegram фиксирует [отдельные последовательности идентификаторов сообщений](https://core.telegram.org/api/updates#message-id-sequences).
Эти номера отражают наблюдаемые явления: уведомления об удалении, повторные проверки и записи в журнале администратора,
объясняющие, почему тот или иной номер отсутствует там, где его указывает Telegram.

Когда Telegram перестает принимать аккаунт, запись
`session_revoked` `coverage.gap``session_duplicated`, завершающая`verify.py` наблюдение`account_frozen``account_deleted``session_expired`,`session_ended`
содержит `cause` `not_authorized`(`account_banned`

Обхват включает в себя зафиксированные периоды наблюдения, перерывы и результаты сообщений.
Оцените его с учетом выбранных чатов, периода и политики в отношении вложений; повторно проверьте
результаты и зафиксированные пробелы, которые показывают, насколько полно отслеживались обновления учетной записи.

<a id="producer"></a>
## Продюсер

Подписанный манифест доказательств, включающий ZIP-архивы, экспортированные данные чатов, дневники свидетелей и описание
файлов профилей пользователей, содержит `producer`: программное обеспечение, версию, проект (PhishDestroy),
домашнюю страницу и репозиторий исходного кода. В отчете в формате HTML и в верификаторе отображается эта подписанная
запись о создателе. Хэши исходных файлов идентифицируют записанное дерево исходного кода для сравнения
с доверенной версией. Происхождение выполнения проверяется отдельно с помощью
[сертификата получения GitHub](../SEALED-ACTIONS.md) или
[измерений Intel TDX](../HIGH-ASSURANCE.md), если они включены. Архивы, созданные до
появления поля «производитель», по-прежнему поддерживаются и идентифицируются как устаревшие записи.

В каждой записи `observation.started` также указывается клиент Telegram, который осуществил наблюдение: его `api_id`
(никогда не хеш), будь то встроенная публичная пара или собственное приложение оператора,
описание клиента, отправленное в запросе на подключение Telegram, а также тип маршрута подключения
с указанием режима IP (без адреса прокси или секретного ключа). В отчете и списке `custody.json` перечислены все
уникальные клиенты и маршруты с указанием времени их регистрации, а также случаи, когда ни один из перечисленных прокси не ответил
и Telegram увидел адрес сервера. Об этом говорится в журналах, записанных до этого.

<a id="people-profiles"></a>
## Профили людей

Файл профиля (`tgwitness-dossier-v1`, JSON) формируется по запросу на основе записей, уже имеющихся в
журнале для одного чата; данные из Telegram не загружаются, а содержимое профиля никогда
не записывается в журнал (включение и выключение профилей фиксируется как `dossier.changed`).
Для каждого пользователя, у которого сохранено сообщение, указываются имя и история пользовательских имён, флаги Telegram
(бот, мошенничество, фейк, премиум, подтверждённый, ограниченный доступ, удалённый) на момент сохранения,
идентификаторы фотографий, SHA-256 и перцептивный хеш (pHash, совместимый с `imagehash.phash`)
аватара из локального кэша аватаров с похожими аватарами, активность (первое и последнее сообщение,
количество, отредактированные и удалённые публикации, сообщения по часам UTC), кто кому отвечает, другие чаты
в этом журнале, в которых этот человек писал, а также упомянутые кошельки (BTC, EVM, TRON, TON, LTC,
DOGE, XMR, SOL; адреса Base58Check проверяются по контрольной сумме), номера телефонов, имена пользователей и
ссылки, включая ссылки, скрытые за текстом.

В каждой записи указаны журнальные записи (`seq`), из которых она взята, а `record_hashes` содержит
хэш каждой упомянутой записи. Заявление подписано ключом рабочей области:

```sh
python verify.py tgwitness-dossier-CHAT.json --fingerprint TRUSTED_SHA256 --evidence tgwitness-evidence.zip
```

проверяет подпись, проверяет сам экспорт доказательств (подпись, цепочку хешей и файлы)
и наличие каждой упомянутой записи в неизменном виде в этом экспорте той же рабочей области. Хэши аватаров помечаются как полученные из локального кэша
(а не из записей журнала). Упоминания сопоставляются по шаблонам и приводят к проверке.
Профили включаются для каждого чата, могут экспортироваться в виде ZIP-архива с шифрованием AES-256 и паролем, и
удаляются при отключении или при удалении чата из источников.

<a id="independent-witness"></a>
## Независимый свидетель

Журнал свидетеля (`tgwitness-witness-v1`) и сообщения в его канале сверяются с
экспортом доказательств с `verify.py --witness … --channel …`; см. [независимый свидетель ](../WITNESS.md).
При наличии публичного адреса `https://t.me/s/…` или `https://telegram.me/s/…` верификатор считывает
дату каждого сообщения из Telegram, и самая ранняя такая дата сообщения в начале экспорта
является внешним временем для последней записи. Даты из любого другого источника являются предоставленными метаданными.

<a id="manifest-and-checkpoints"></a>
## Манифест и контрольные точки

Файл manifest.json содержит информацию о формате, времени экспорта, открытом ключе, отпечатке, длине журнала,
хеше головы, области действия, производителе, ограничениях, а также SHA-256 каждого элемента контента, кроме
самих `manifest.json` и `manifest.sig`.
Файл manifest.sig представляет собой подпись Ed25519 в кодировке base64, наложенную на канонический JSON-манифест.
Проверяющий отклоняет неожиданные/отсутствующие элементы, дубликаты имен, повреждённые файлы,
нарушенную последовательность/цепочку, недействительные подписи и несоответствие предоставленной контрольной точке.
Он никогда не извлекает пути к архивам. Он ограничивает общий заявленный размер в несжатом виде до 4 ГиБ;
элемент `--max-gib N` позволяет создавать архивы большего размера с помощью повышенного предела в разделе **Дополнительные инструменты → Параметры**.

Проверка большого архива осуществляется несколькими процессами одновременно: элементы архива хешируются параллельно,
а после первых 5 000 записей хеш содержимого и подпись каждой записи проверяются
рабочими процессами, в то время как главный процесс последовательно отслеживает цепочку, степень охвата и привязки
. `--jobs N` задаёт количество процессов; по умолчанию `auto` используется по одному процессу на каждый процессор,
не более 16, а `--jobs 1` выполняет всё в одном процессе. Результат одинаков в обоих случаях,
а изменение отклоняется с одинаковым сообщением. Хэши в позициях, указанных сохраненными
контрольными точками и анкерами временных меток, сохраняются в течение этого единственного прохода, поэтому каждый анкер
сравнивается без повторного чтения журнала. На компьютере с 32 потоками обработка архива объёмом 10,8 ГБ, содержащего
400 000 записей, заняла 58,9 с в одном процессе, 15,2 с при использовании 4 процессов и 8,4 с при использовании 16; один проход по
записям по порядку затем устанавливает предельное время.

Запустите проверку из установленной версии TgWitness или из проверенной версии кода.
Копия, входящая в состав архива, предназначена для переносимого использования; перед запуском сравните эту копию с вашей
доверенной установкой.

Контрольная точка подписывает заявление, содержащее открытый ключ, длину журнала, хеш
начальной части и время создания. Он также содержит самый новый раунд drand, который рабочая область
загрузила (`drand_anchor`
): сборщик запрашивает ретранслятор drand через
внешний маршрут рабочей области перед каждым периодическим контрольным пунктом, поэтому Hide IP, прокси и отключенный
внешний маршрут действуют, и сам контрольный пункт никогда не выходит во внешнюю сеть. Верификатор может проверить,
содержит ли более поздний архив тот же префикс. С помощью `--checkpoint`
и `--check-drand`
он подтверждает этот раунд у ретрансляторов drand и сообщает, что контрольная точка была подписана
не раньше времени данного раунда; раунд не изменяет уровень гарантии. Храните
контрольную точку вне коллектора, чтобы при последующей верификации архив сравнивался с
эталоном, хранящимся отдельно от него. Ключ коллектора подписывает его, поэтому он
связывает записи с ним только в том случае, если получатель получил его до архива через
другой канал; сам по себе он не соответствует минимальным требованиям к доказательству.

<a id="reading-a-verification-result"></a>
## Просмотр результатов проверки

Верификатор отдельно сообщает о целостности архива, привязке подписавшего и проверках достоверности.
Достоверная подпись свидетельствует о том, что байты не изменились с момента
подписи. Оператор передаёт отпечаток ключа получателю по отдельному
каналу. Без `--fingerprint` неповреждённый архив проходит проверки подписи и формата
с помощью `signer_pinned: false`, а последняя строка начинается с
`EVIDENCE: minimum not met · missing: confirmed signer key`.

Для автоматизированной политики локального архивирования, требующей закрепленного подписанта и минимального
объема доказательств:

```sh
python -m tgwitness.verify evidence.zip --strict --json --fingerprint TRUSTED_KEY_SHA256 --tsa-ca TSA-ROOT.pem --require evidence
```

Используйте отпечаток пальца, сохраненный через доверенный канал получателя. Доверенный
свидетель также может закрепить сборщика с помощью согласованного журнала с подтверждением; предоставьте
`--witness`, `--witness-fingerprint` и `--require-witness`. `--strict` завершает работу со
статусом 2 для незакрепленного подписанта; невыполненные `--require-tier` или `--require evidence` также
завершают работу со статусом 2. `--require evidence` требует `--fingerprint` и внешнее время от
третьей стороны, охватывающее последнюю запись.
Следует учитывать `signer_pinned`, `requirements_met` и результаты проверки достоверности, а не только
код завершения. [Запечатанное получение ](../TRUST.md#sealed-evidence) вместо этого использует свой
верификатор аттестации и утвержденную политику для аутентификации дайджеста получения.

<a id="verification-scope"></a>
## Объем проверки

В ходе проверки проверяется архив и режим сбора, использованный для его создания. Выберите
режим, граница доверия которого соответствует данному случаю, а затем сохраните его входные данные для проверки.

| Режим сбора данных | Что проверяет верификатор | Входные данные для проверки и граница доверия |
| --- | --- | --- |
| Локальное рабочее пространство | Запись подписей, цепочки хешей, манифеста и байтов вложений | Отпечаток коллектора, сохраненный получателем, и внешнее время от третьей стороны: подтвержденные квитанции в соответствии со стандартом RFC 3161 или OpenTimestamps, либо записи свидетелей, прочитанные на t.me. Сохраненные контрольные точки и записи свидетелей служат подтверждением проверки |
| Локальное рабочее пространство с независимым свидетелем | Проверка архива, а также соответствие более раннему префиксу журнала, сохраненному свидетелем | Отпечатки пальцев свидетеля и соответствующие записи; в журнале учета ключей ответственного лица указано, кто владеет ключом свидетеля. С помощью `--channel https://t.me/s/…` даты, установленные Telegram для постов, отображают внешнее время |
| [Снимок экрана GitHub Actions](../SEALED-ACTIONS.md) | Подтверждение GitHub: дайджест архива, утвержденный рабочий процесс и коммиты сборщика, размещенный раннер, новый источник сессии/ключа и целостность внутреннего архива | Политика доверенного верификатора, репозиторий вызывающих сторон и пакет аттестации GitHub; сбор данных выполняется в рамках закреплённого рабочего процесса |
| [Развертывание в облаке](../HIGH-ASSURANCE.md) | Данные о жизненном цикле провайдера и записи о доступе, состояние брандмауэра и Cloudflare, а также подписанная запись о выполнении сборщика | Запросы только для чтения к провайдеру и Cloudflare; доступность отдельных проверок зависит от провайдера |
| [Конфиденциальная виртуальная машина Intel TDX](../HIGH-ASSURANCE.md#confidential-vm-on-phala-cloud-intel-tdx) | Указание подписи и статуса платформы, привязка к оператору сборщика, составление и измерения ОС | Цепочка доверия Intel и показатели ожидаемого развертывания; сохранение результатов каждой необходимой проверки TDX |

При «запечатанном» сборе данных утвержденный сборщик получает данные через аутентифицированное
соединение Telegram внутри проверенной среды. Аттестация привязывает архив к
данному запуску, поэтому проверка охватывает как сам процесс сбора, так и последующую целостность файлов.
Это основано на утвержденном коде и цепочке доверия платформы, перечисленных выше.
Проверка сбора данных GitHub требует сеанса, созданного в рамках данного запуска, и отклоняет
сбор данных из импортированных сеансов.

В отчёте о запуске фиксируются версия сборщика, хэши файлов и настройки запуска. Проверка среды осуществляется с помощью данных о происхождении из GitHub
и результатов измерений TDX;
[запись валидации](../VERIFICATION.md) содержит информацию о протестированных конфигурациях.

<a id="where-the-messages-come-from"></a>
### Откуда поступают сообщения

Telegram доставляет сообщения каждому клиенту, включая официальные приложения, в рамках
сеанса MTProto. Ключ авторизации сеанса согласовывается с
закреплённым серверным ключом Telegram, и каждое обновление поступает в зашифрованном виде с проверкой целостности с использованием
этого ключа. Коллектор получает сообщения через аутентифицированную
сессию учётной записи и подписывает каждую запись в журнале по мере её поступления, указывая идентификаторы чата,
сообщения и отправителя, а также дату, установленную Telegram для каждого сообщения. В развёртываниях GitHub
Actions capture и Intel TDX аттестация также связывает эту сессию и
ключ подписи с утверждённым запуском коллектора.

Журнал фиксирует источник ключа авторизации. При входе в систему с помощью телефона или QR-кода,
а также при автономном входе из файла сеанса записывается `account.authorized` с
`key_origin: "created"`; при получении импортированного ключа `.session`, TData или JSON записывается
`imported`. Импортированный ключ также существует независимо от источника его получения. Сертифицированные развертывания
не принимают импортированные ключи.

Происхождение записи Telegram основывается на аутентифицированном подключении учетной записи,
записях о подключении и захвате в журнале, захваченных кадрах MTProto, сопоставленных с записями
журнала ([`tgwitness/forensics/`](../../tgwitness/forensics/)), дате Telegram каждого
сообщения и, в случае заверенного захвата, проверенной среде выполнения. Архивные подписи
сохраняют эту запись для последующей проверки. Сохраненные контрольные точки фиксируют пределы предыдущих журналов,
записи об охвате показывают результаты сбора, а проверенные внешние временные метки
определяют момент фиксации байтов во времени.

В случае локальной рабочей среды получатель предоставляет входные данные от доверенного сборщика или свидетеля.
При запечатанном сборе данных доверенная политика и аттестация связывают дайджест архива с
утвержденным запуском сборщика. Это разные пути проверки; сообщите о
проведенных проверках для выбранного пути.

<a id="attachments"></a>
## Вложения

Файлы идентифицируются по хешу SHA-256 в каталоге media/. Событие media.saved связывает хеш и
длину в байтах с конкретным событием сообщения. Исходные имена файлов являются метаданными, а не локальными
путями. Байты мультимедиа загружаются асинхронно, поэтому немедленное удаление может помешать
их захвату. В качестве результатов отображаются отключённый сбор данных, файлы большого размера или с неизвестным размером, сбои при загрузке
и прерванные загрузки. Сбой процесса может привести к появлению
неиспользованных неполных файлов; они не включаются в экспортируемые данные.

Экспортер ZIP сверяет сохраненные медиафайлы с их именами. Экспорт в форматах JSONL, CSV и HTML
проверяет сигнатуры событий, но не передает байты медиафайлов. Производные отчеты
предназначены для удобства; файл events.jsonl является авторитетным представлением событий.

При полном экспорте чата вложения сохраняются в соответствии с настройками вложений рабочей среды в папке
media/, при этом имена файлов формируются на основе SHA-256. Каждая запись сообщения в файле chat.json содержит название файла (`file`,
`file_sha256`) или причину его отсутствия (`file_status`), а также информацию о том, что видел читатель
вокруг текста: ссылки за текстом, источник пересылки, кнопки ботов, подпись, просмотры и
таймер автоматического удаления. `verify.py` проверяет, что каждый указанный файл находится в подписанном манифесте
под этим хешем.

<a id="durable-collection-and-process-receipts-02"></a>
## Хранение и обработка квитанций (0.2)

Задание медиа и фиксация события сообщения выполняются в рамках одной транзакции. Задание сохраняет
исходный дескриптор сообщения TL; подписанное наблюдение связывает с ним SHA-256, учетную запись
и политику размера. Система восстановления проверяет эту привязку перед загрузкой. Она никогда не извлекает
текущее сообщение и незаметно заменяет его более новым вложением. Прерванные задания
повторяются, в то время как постоянный сбой остается явным результатом.

Каждая рабочая среда имеет собственный журнал и идентификатор для подписи. Событие `process.started` содержит
идентификатор запуска, данные локальных часов, версии зависимостей, хеши исходных файлов, исходные данные об учетной записи/области действия,
а также настройки записи. Сигналы пульсации содержат идентификатор запуска, монотонное время и состояние очереди.
Квитанцию о запуске также можно скачать в виде отдельно подписанного отчёта. Для проверки
среды выполнения сопоставьте её с аттестацией GitHub или проверками TDX, описанными
в разделе [Область проверки](#verification-scope).

Автоматические контрольные точки сохраняются локально при запуске, каждые пять минут в ходе
наблюдения (**Дополнительные инструменты → Параметры → Подписанная контрольная точка каждые**) и при упорядоченной остановке. При проверке при запуске и при экспорте журнал
сравнивается с последней сохраненной локальной контрольной точкой. Это позволяет обнаружить откат базы данных,
если контрольная точка сохранилась. Независимое хранение обеспечивает доступность этой ссылки за пределами
рабочей области; проверенная внешняя временная метка дополнительно фиксирует её во времени.

После перезапуска возобновляется сохранённая позиция обновлений Telegram (`catch_up_from` в
`observation.started`), и запрашиваются пропущенные обновления. Сохранённая позиция охватывает только
те обновления, обработка которых завершилась, поэтому обновления, которые ещё находились в очереди на момент разрыва соединения или
остановки процесса, запрашиваются заново. Периодическая повторная проверка фиксирует
`message.recovered` для пропущенных сообщений и `message.missing_on_recheck`, когда Telegram больше
не возвращает сохраненное сообщение; последнее не является уведомлением об удалении и не указывает ни удаляющего пользователя, ни время.

<a id="off-site-copy-and-restore-s3"></a>
### Копирование и восстановление данных за пределами площадки (S3)

Внешняя копия (**Настройки → Уведомления и внешняя копия → Внешняя копия**, или
**Дополнительные инструменты → Дополнительные функции → Доказательства и резервные копии**; по умолчанию отключено) загружает сегменты журнала, сохраненные файлы, контрольные точки
с их временными метками и готовые экспорты чатов в хранилище, совместимое с S3, зашифрованные с помощью
AES-256-GCM перед загрузкой с использованием ключа, хранящегося в хранилище рабочей области; применяется политика хранения Object Lock,
если корзина поддерживает эту функцию. Без загруженного ключа копию невозможно прочитать. Восстановление и проверка
с помощью `python -m tgwitness.replica restore --key-file KEY.json --out DIR`.

Для восстановления требуется пустой обычный каталог. Загруженные и расшифрованные объекты остаются в частном
временном хранилище до тех пор, пока не будет проверен весь журнал и каждая сохраненная контрольная точка. Небезопасные пути к объектам,
несогласованные диапазоны сегментов и журналы, длина которых меньше длины контрольной точки, отклоняются; в случае неудачной
проверки восстановленные файлы не публикуются. Проверки срока хранения сравнивают возвращённый режим блокировки объекта
и дату со сроком хранения, отправленным при загрузке (допуск на округление составляет одну секунду). Истекший,
недействительный или сокращённый срок хранения не считается проверенным. Статус сообщает о выборочном объекте,
срок хранения которого был считан обратно для данного прохода загрузки.

Отсутствие или повреждение локального носителя фиксируется как ошибка прохода, при этом курсор носителя останавливается перед
этим местом, чтобы файл был повторно скопирован в следующем проходе; файлы, контрольные точки и экспортированные данные, расположенные после него, по-прежнему
копируются. Процесс восстановления проверяет
все ссылки на сохраненные носители по расшифрованным хешам и записанным размерам. Идентичные перекрывающиеся
сегменты журнала из прерванных загрузок дедуплицируются; конфликтующие перекрытия отбрасываются.
Контрольные точки, созданные во время загрузки, откладываются до тех пор, пока не будут
скопированы охватываемые ими записи журнала, поэтому завершённый проход не публикует контрольную точку раньше, чем соответствующая ей запись в журнале.

<a id="streaming-export-snapshots"></a>
### Потоковая передача снимков экспорта

При потоковом экспорте используется стабильный снимка чтения базы данных SQLite. К моменту завершения загрузки его начало может оказаться более старым, чем
текущий активный журнал. Контрольная точка, созданная после этого
снимка, может правильно показать, что архив меньше по размеру; сравнивайте с контрольной точкой,
расположенной на уровне экспортируемого префикса или перед ним, а не с произвольной более поздней контрольной точкой.

<a id="rfc-3161-preparation-and-response-verification-02"></a>
## Подготовка запросов и проверка ответов в соответствии с RFC 3161 (0.2)

В режиме «Evidence» в указанные авторитетные центры по стандарту RFC 3161
и календари OpenTimestamps передается только хеш SHA-256 каждой подписанной контрольной точки по маршруту рабочей области и ни в коем случае не через MTProxy.
В каждой цели настройки по умолчанию включена функция временных меток; **Доказательства по делу** также фиксируют drand.
Ответы хранятся в `checkpoints/anchors/`, экспортируются в виде файлов `.tsr` и `.ots` в папке `anchors/`,
а также проверяются с помощью `verify.py` (`--tsa-ca` проверяет подпись TSA; подтверждение доказательств OpenTimestamps
осуществляется с помощью `ots upgrade` и `ots verify`).

Авторитетный сервер, работающий по стандарту RFC 3161, при двух неудачных попытках подряд выжидает перед следующей попыткой: один интервал, затем
два, четыре и так далее до шести часов или столько, сколько запрашивает его `Retry-After`, но не более одного дня. При проходе, в ходе которого
обнаруживаются только ожидающие авторитеты, запись не создается; в противном случае `anchor.completed` перечисляет их под
`deferred` с помощью `retry_at`. До тех пор, пока они не ответят снова, панель отображает временные метки как **Работает с ограничениями**.

Модуль формирует архив запроса, содержащий канонические байты файла checkpoint.json,
отпечаток сообщения по алгоритму SHA-256 и случайный нонс в файле timestamp.tsq, а также контрольные суммы и инструкции.
Сетевой запрос не отправляется; токеном, возвращаемым авторитетом в ответ на этот запрос, является временная метка.

`python -m tgwitness.anchor verify` проверяет ответ на соответствие байтам контрольной точки
и исходному запросу без использования OpenSSL. Требуется явное указание файла доверенного ЦС;
включённые сертификаты автоматически не считаются доверенными. Проверка запроса является опциональной в
командной строке, поэтому сохраните и укажите параметр --request для проверки нонса. Результат указывает, была ли
проведена проверка. Подпись контрольной точки коллектора и журнал по-прежнему необходимо проверять
отдельно с помощью доверенного отпечатка пальца коллектора.

В ходе проверки проверяется подпись ответа, байты контрольной точки и, при наличии,
исходный запрос в рамках указанного доверия к центру сертификации. Для временных меток, полученных в режиме подтверждения,
`verify.py` также проверяет сохраненные данные OCSP или CRL
([отзыв сертификата подписи](../TIMESTAMP.md#signing-certificate-revocation)).
См. [процедуру](../TIMESTAMP.md) и [результаты проверки](../VERIFICATION.md).

<a id="optional-records-in-evidence-mode-drand-and-telegram-devices"></a>
## Дополнительные записи в режиме сбора доказательств: устройства drand и Telegram

Еще две записи могут запускаться в тех же проходах, что и временные метки. Обе вступают в силу только при
включенном режиме сбора доказательств. **Доказательства по делу** включают drand; в противном случае оба запускаются изначально. Переключайте их
в разделе «Дополнительные инструменты» → «Дополнительные функции» → «Доказательства и резервные копии» → **«Дополнительные свидетели · опционально»**,
или `"drand": true` и `"devices": true` в `POST /api/evidence`. Сбой одного из них не останавливает
работу другого или временных меток; панель отображает последние результаты каждого из них под формой.

**drand** (`beacon.drand`
). При каждом проходе в журнал записывается новейший раунд drand quicknet — общедоступный
генератор случайных чисел Лиги Энтропии (один раунд каждые 3 секунды): `chain`
,
`round`
, `randomness`
, `signature`
, `round_time`
и `relay`
, на который был получен ответ. Проверенный
непредсказуемый раунд служит нижней временной отметкой для последующего материала, связанного хэшем.
Проверенная временная метка на более поздней контрольной точке служит верхней временной отметкой. Эти проверки
ограничивают связанный материал. Коллектор сначала запрашивает `drand.cloudflare.com`
, затем ретрансляторы Protocol Labs через маршрут рабочей области — по одному запросу за проход.

`verify.py`
проверяет, что каждое случайное число соответствует SHA-256 его подписи и что время раунда
верно, а также сообщает количество раундов, самый длинный отрезок без раунда и насколько
часы сборщика отставали от drand. `--check-drand`
сравнивает раунды с ретранслятором Cloudflare и ретранслятором Protocol Labs — либо со всеми из них, либо со случайной
выборкой из 100 записей в длинном журнале; раунд, который отличается, не проходит проверку.

**Устройства Telegram** (`account.devices`). При каждом проходе программа считывает сессии учетной записи с помощью
`account.getAuthorizations` — список, который Telegram отображает в разделе «Настройки» → «Устройства», — и записывает их:
в полном объеме, если с момента предыдущего прохода произошли изменения, с указанием хешей сессий `added` и `removed`;
в противном случае — только их количество и SHA-256. Сохраняются модель устройства, платформа, приложение и версия,
дата создания и последней активности, страна и регион; IP-адреса не сохраняются, поскольку
экспорт доказательств выходит из-под вашего контроля. Собственная сессия сборщика активна постоянно, поэтому
только активность других сессий считается изменением. `verify.py` сообщает, как часто список
записывался, а также о каждой новой и завершённой сессии. Он считывает список только во время работы наблюдения.

Что они показывают: drand упорядочивает записи в соответствии с общедоступным временем, а список устройств
представляет собой заявление Telegram, переданное через сборщик и подписанное им, как и каждая
другая запись.

**Журнал Cloudflare Gateway** (`cloudflare.gateway_dns`). Для сервера, который осуществляет разрешение через
Cloudflare Gateway ([Gateway DNS ](../HIGH-ASSURANCE.md#cloudflare-as-an-outside-witness)), при каждом
проходе копируются данные, зарегистрированные Gateway с момента предыдущего копирования: одна запись за интервал не более трех
часов с `from`, `until`, `location_id`, `address` сервера (если он установлен) и
`queries` в качестве `[at, name, type, rcode, decision, colo]`, в том числе и в случае их отсутствия. Укажите это в разделе
**Журнал Cloudflare Gateway**: учётная запись, местоположение, адрес (по желанию) и токен только для чтения (Account
Analytics Read; Zero Trust PII Read для сохранения одного адреса общего местоположения). Панель проверяет
их с помощью одного запроса перед сохранением; токен остается зашифрованным и никогда не попадает в журнал.
`verify.py` перечисляет окна, имена, по которым выполнялось наибольшее количество поисков, и любое время, не охваченное копией; запись,
число запросов которой не совпадает с количеством запросов, считается неудачной. Окно, содержащее более одной страницы
запросов за одну секунду, сохраняет эту страницу и указывает, что остальная часть отсутствует. Копия представляет собой
ответ Cloudflare, полученный через коллектор и подписанный им; в течение 24 часов любой, у кого есть
токен только для чтения, может сравнить её с данными Cloudflare.
