# Формат доказательств

Canonical page: https://phishdestroy.github.io/TgWitness/ru/docs/reference/evidence/

Содержимое подписанного ZIP-архива, типы записей, подтверждения обработки, профили пользователей, внешние копии и офлайн-проверка.

TgWitness сохраняет видимые в учетной записи данные Telegram в подписанном журнале. Получатели могут проверить сохраненные записи, вложения и отчеты с помощью доверенного ключа сборщика, а затем сравнить журнал с независимо сохраненной контрольной точкой. На этой странице описаны форматы, проверки и материалы, которые необходимо сохранить для передачи.

Recipients can start with **VERIFY.cmd** on Windows: it asks for the original ZIP and independently obtained key fingerprint, displays an explained result, and saves a separate verification transcript. See [verification launchers and the portable runtime](https://github.com/phishdestroy/TgWitness/blob/main/docs/VERIFICATION_LAUNCHER.md) for setup and trust limits.

## Что подлежит подписанию

| Материалы | Защита | Что следует сохранять |
| --- | --- | --- |
| Каждая запись в журнале, включая оперативные события | Цепочка SHA-256 и подпись Ed25519 для каждого события | Исходный `events.jsonl` — отпечаток доверенного ключа — и сохраненная контрольная точка |
| Содержимое ZIP-архива с доказательствами | `manifest.sig` подписывает канонический манифест, в котором перечислены хэши файлов с содержимым | Полный ZIP-архив, включая манифест и подпись |
| Сохраненные вложения | SHA-256 и количество байтов в подписанном событии `media.saved`; хеш файла в подписанном манифесте ZIP | Исходные байты внутри проверенного ZIP-архива |
| Checkpoint | Подпись Ed25519, охватывающая длину журнала, хеш заголовка, открытый ключ и время создания | Независимая копия, сохраненная до внесения спорного изменения |
| Квитанция об отправке | Signed record of the collector version, source-file hashes and start settings, also included in `process.started` | The receipt, associated journal and the environment evidence for the selected verification mode |
| Удобные для чтения отчеты: `report.html` и его части: `report.json`, `report.pdf`, `chat.pdf` | Печать Ed25519 на каждом файле, подтверждающая его содержание; файл PDF также содержит стандартную подпись PDF (см. [Readable reports](https://phishdestroy.github.io/TgWitness/ru/docs/reference/evidence/#readable-reports)) | Полученный файл и отпечаток доверенного ключа; ZIP-архив, описанный в документе |
| Автономный CSV | Отсутствие автономной криптографической подписи; одних только хешей событий недостаточно | Для проверки целостности используйте точную копию, содержащуюся в проверенном ZIP-файле |
| Скриншоты, распечатки или PDF-файлы, сгенерированные браузером | В производном материале не должно быть упоминания о TgWitness | Сохраните исходный проверенный пакет и задокументируйте процесс создания производного файла |

Коллектор проверяет подписи журнала перед генерацией каждого формата экспорта. Удобные для чтения отчеты в форматах HTML и PDF имеют собственные печати; автономный файл CSV проверяется как часть подписанного ZIP-архива. Сохраните ZIP-архив, чтобы сохранить байты вложений и манифест, а также отдельную контрольную точку для сверки журнала с более ранней границей.

## Comparing chat exports

Verify and compare two signed chat-export ZIPs with independently retained signer fingerprints:

```
python -m tgwitness.verify first.zip --compare second.zip \
  --fingerprint FIRST_TRUSTED_KEY_SHA256 --compare-fingerprint SECOND_TRUSTED_KEY_SHA256
```

When both archives record the same numeric account and chat IDs, records are paired by message ID. **Unchanged** means equality of the complete saved JSON record: full text, author, dates, reply target, nested metadata and unknown fields are all included. JSON object key order does not matter; absent fields, nulls, value types and array order do. The 300-character preview is only for display. Changed entries name the differing top-level `changed_fields`, including changes invisible in that preview. Duplicate message IDs are rejected instead of overwriting one another during matching.

A difference can be a changed display name, view count, collection annotation or other observation metadata. It does not by itself establish a Telegram edit, identify who made a change, or prove which contradictory archive is accurate. Unparsed records remain in the comparison; equality of their saved representation does not mean their Telegram payload was decoded.

For different or missing account/chat identities, the tool only finds possible correspondences using sender, complete text, file hash, media type and a five-second time tolerance. It reports **Matched**, not **Unchanged**. These candidates do not establish message identity or equality of all metadata. Unparsed records remain unmatched. Differences in paired records remain listed in `changed`, including in content mode; these differences do not prove edits of the same message. With `--json`, `matched` counts pairs and `unchanged` counts pairs whose complete saved records are equal. Neither count proves message identity in content mode. The existing `changed_fields` and integer `unchanged` output remain compatible with earlier comparison results. Archive format and signature verification are unchanged.

## Передача расследования

1. Запишите номер дела, имя оператора, цифровой идентификатор аккаунта Telegram, выбранные источники, политику сбора данных и период сбора в заметках по делу. TgWitness сохраняет наблюдения и поддерживает привязанные к источникам заметки и сбор данных в [Case Board](https://phishdestroy.github.io/TgWitness/ru/docs/reference/case-board/). Храните записи о передаче и хранении вместе с материалами по делу . Проверьте настройки сбора данных с помощью [процедуры приёма в режиме реального времени](https://github.com/phishdestroy/TgWitness/blob/main/docs/internal/LIVE_ACCEPTANCE.md).
2. Перед тем как полагаться на экспортированные данные, самостоятельно сохраните отпечаток открытого ключа рабочей среды. Во время сбора данных сохраняйте подписанные контрольные точки вне коллектора. Фиксируйте прерывания процесса и ограничения видимости учетной записи.
3. Экспортируйте **подписанный ZIP**-файл и сохраните подписанную квитанцию о запуске. Используйте контрольную точку, расположенную на границе экспортируемого журнала или перед ней. Более поздняя контрольная точка может правильно отклонить более ранний экспорт как слишком короткий. Экспорт включает полный журнал рабочей области, независимо от фильтров панели; ознакомьтесь с материалом перед его передачей.
4. Попросите получателя проверить ZIP-архив с помощью надёжной копии программы проверки и независимо предоставленного отпечатка/контрольной точки. Из надёжного репозитория с активной средой Python:

   ```
   python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --checkpoint retained-checkpoint.json
   ```

   При успешном выполнении выводятся отчеты `key_pinned: true` и `checkpoint_checked: true` , если оба входных значения предоставлены и приняты. Сохраните результат проверки.

   ```
   For a handover requiring the final exported record to be witnessed, use
   `--witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness`.
   This refuses an export with an unwitnessed tail. See the
   [witness handover procedure](WITNESS.md#require-a-witnessed-export-boundary).
   ```

   1. Зафиксируйте в вашем протоколе хранения SHA-256 архива, границы экспорта, дату передачи, отправителя и получателя. Сохраняйте исходный пакет в неизменном виде и работайте с копиями. Передавайте файлы с доказательствами, а не каталог личных данных приложения, который также содержит сеансы учетных записей и секретные ключи подписи. Для передачи экспортный файл можно поместить в ZIP-архив с защитой по паролю AES-256. Пароль обеспечивает лишь конфиденциальность и не сохраняется; получатель извлекает архив и проверяет содержащийся в нём подписанный экспортный файл, который остаётся неизменённым.
   2. Если требуется независимая привязка ко времени, следуйте [процедуре, изложенной в RFC 3161,](https://phishdestroy.github.io/TgWitness/ru/docs/reference/timestamp/) и сохраните запрос, контрольную точку, информацию о доверенном центре сертификации, а также проверенный ответ центра сертификации. Сам по себе запрос не обеспечивает получение временной метки.

Успешная верификация подтверждает целостность относительно доверенного ключа сборщика и сохраненных границ. См. [раздел «Объем верификации»](https://phishdestroy.github.io/TgWitness/ru/docs/reference/evidence/#verification-scope) для ознакомления с допущениями о доверии и [результатами проверки](https://phishdestroy.github.io/TgWitness/ru/docs/reference/verification/) выполненных тестов.

## Выдержка из протокола передачи дел

Подписанный ZIP-файл содержит полный журнал рабочей области. Если суду, адвокату или службе по борьбе со злоупотреблениями требуются только отдельные чаты, определенный период или конкретные участники, **функция «Экспорт → Выдача выдержки»** подготавливает сокращенную копию (`tgwitness-handover-v1`) в соответствии с выбранными правилами раскрытия информации. Оператор указывает цель и выбирает чаты, опциональный период (UTC), участников, к которым относится выдержка, а также определяет, что происходит с остальными участниками (отображаются, заменяются псевдонимами P01, P02… или исключены из отчета), какие тексты сообщений сохраняются, какие вложения и фотографии профилей включаются, а также маскируются ли номера телефонов и адреса электронной почты в текстах. Цель и эти правила указаны в подписанном манифесте и в отчёте; в журнале регистрируется запись «`handover.exported`» с указанием доступа, который её подготовил, и SHA-256 файла, а не его содержимого.

Скрипт `verify.py` проверяет выдержку двумя способами. Запись, отображаемая как неизменённая, проверяется полностью: её содержимое сверяется с хешем, подписью Ed25519 и ссылкой на включённую предыдущую запись. В сокращённой записи сохраняются исходный хеш и подпись, поэтому подпись по-прежнему проходит проверку, но утаенные поля не могут быть пересчитаны на её основе; в записи указывается, что именно было утаено, а в отчёте это отмечается. В манифесте указывается длина журнала и его начало с подписью сборщика над этим началом, а также подсчитывается количество пропущенных записей; файл `coverage.json` описывает выбранные чаты. Имена, содержащиеся в именах файлов, не обнаруживаются. Перед публикацией проверьте окончательные файлы: свободный текст, имена файлов и выбранные вложения по-прежнему могут идентифицировать людей. Сохраните полный подписанный ZIP-архив: извлеченная часть является раскрытием информации, а не заменой.

## Удобные для чтения отчеты

Подписанные доказательства, передаваемые материалы и ZIP-архивы чатов содержат читаемые отчеты в форматах HTML и JSON, а также PDF (при наличии необходимых шрифтов) на выбранном языке отчета. Каждый отчет запечатан ключом Ed25519 рабочей среды и может быть проверен отдельно: ` `python -m tgwitness.verify FILE --fingerprint KEY [--evidence ZIP]``.

- `report.html` / `chat.html`: оператор запечатывания (`tgwitness-report-seal-v1`) закрывает файл и подписывает SHA-256 каждого предыдущего байта. Длинные журналы и чаты разбиваются на части настраиваемого размера (настройки отчёта, от 500 до 100 000 записей; по умолчанию — 5 000): `records/records-0001.html` или `messages/messages-0001.html`, каждая из которых запечатана своим номером, диапазоном и общим количеством, и указана вместе со своим файлом SHA-256 в подписанном манифесте. Серии сигналов о работоспособности коллектора отображаются одной строкой, если в настройках отчёта не указано их поочерёдное отображение.
- `report.json` (`tgwitness-report-json-v1`, ключи `format`, `report`, `seal`): печать подписывает SHA-256 канонического JSON из `report`, благодаря чему факты могут быть прочитаны системами обработки дел и скриптами, а также на их основе может быть сделан выбор для защиты данных, при этом подписанный файл остаётся целым.
- `report.pdf` / `chat.pdf`: официальный документ для печати и архивирования, подписанный дважды на одних и тех же байтах, весь файл за исключением значения подписи (`/ByteRange`). Стандартная подпись PDF (`adbe.pkcs7.detached`, CMS с SHA-256 и ECDSA P-256) использует самоподписанный сертификат для подписи документов , хранящийся в хранилище рабочей области; его серийный номер субъекта является отпечатком ключа Ed25519 . Печать Ed25519 передаётся внутри CMS в качестве неподписанного атрибута `2.25.240684792623320047764573196045913242332` и указывает на сертификат SHA-256 с помощью `"content": "pdf-byte-range"`, таким образом ключ Ed25519 подтверждает подлинность сертификата. Считыватель PDF показывает, изменился ли файл после подписания, и считает подписавшего неизвестным, пока сертификат не будет признан доверенным; вместо этого сравните отпечаток Ed25519. Для PDF-файлов на китайском, японском и корейском языках требуется шрифт на сервере (или в `TGWITNESS_FONT_DIR`); в отсутствие такового ZIP-архив содержит только отчёты HTML и JSON .

В канале или супергруппе Telegram нумерует сообщения 1, 2, 3… по порядку. Экспорт чата содержит список первого и последнего номера, количество присутствующих сообщений и каждый диапазон отсутствующих номеров в `message-ids.json` , манифесте и заголовке `chat.json` , а также отмечает каждый пробел там, где он встречается в транскрипте. `verify.py` перечисляет их, начиная с `chat.json` . Отсутствующий номер — это сообщение, которое Telegram не вернул (удалено до экспорта или невидимо для аккаунта); в личных чатах и обычных группах номера используются во всех чатах аккаунта, и пропуски не учитываются.

After reading the history, the export asks Telegram for every absent number again, by number (`channels.getMessages`, up to 10,000 numbers). The result is in `message-ids.json` and the report. An empty answer records that the number is unavailable to this account at recheck time; it leaves the cause unspecified. A message returned on recheck is added to the export and marked `found_on_recheck`.

Каждый отчёт начинается с **. Кратко**: один абзац, затем — что показывает материал и чего он не показывает (кто стоит за аккаунтом, полнота передачи данных, удаления перед наблюдением, время без временной метки). Собственная печать страницы становится янтарной, когда браузер проверил подпись печати, а не саму страницу: браузер не присваивает странице свои собственные байты. Он становится зелёным только тогда, когда читатель перетаскивает файл в поле проверки в конце страницы и все байты совпадают, и только если отображаемая страница является именно этим файлом; в противном случае он становится красным.

В каждом отчёте точно указывается название программы: коммит в Git, когда сборщик запускается из чек-аута или установщик устанавливает `TGWITNESS_COMMIT`, а также SHA-256 исходных файлов (`source_tree_sha256`, канонический JSON пути → SHA-256 каждого файла `.py`, `.js`, `.css`, `.html` и `.svg` в пакете), которые воспроизводятся при чек-ауте этого коммита, если файлы не были изменены. Клиент Telegram называется по имени своей библиотеки, уровня API и центра обработки данных. Когда начинается наблюдение, а также когда начинается и заканчивается экспорт чата, коллектор запрашивает у Telegram его время (`updates.getState`, целые секунды) и записывает время Telegram за вычетом времени по часам коллектора с погрешностью, обусловленной временем прохождения сигнала в обоих направлениях; эти измерения отображаются в отчетах в разделе «Цепочка контроля». При экспорте чата также фиксируется момент считывания истории, помимо дат сообщений.

### Руководство по автономному просмотру отчетов и архивированию

Перед открытием файлов `chat.html` или `report.html` необходимо полностью распаковать ZIP-архив. Программа просмотра предоставляет функции поиска, фильтров, просмотра участников, индикаторов, сведений о записях, а также выборку файлов JSON и CSV без подключения к серверу. Сохраните файлы `viewer/` и `media/` рядом с отчётом. Выбранные элементы являются производными: используйте файл `verify.py SELECTION.json
--evidence ARCHIVE.zip` для их сравнения с подписанным архивом. Программа проверки проверяет идентификатор отчёта, ключ подписи, границы архива и каждый выбранный элемент; отредактированные, отсутствующие и дублирующиеся элементы не проходят проверку. Примечания к выбору и время создания остаются неподписанными метаданными.

Пробелы в номерах сообщений отображаются только для полной, нефильтрованной ленты чата в порядке возрастания. Скрытие категории или сбой при загрузке блока данных не должны превращать пропущенную строку в доказательство отсутствия сообщения. Подсветка результатов поиска осуществляется в виде простого текста до экранирования HTML, с сохранением буквальной разметки.

Браузер проверяет подписи манифеста, идентификатор отчёта и ключ, а также все указанные хэши файлов. Он отклоняет неоднозначные или некорректно сформированные ZIP-структуры, дубликаты имён и небезопасные пути, а также ограничивает размер файлов 256 MiB и объявлённый общий объём содержимого 4 GiB. Для архивов большего размера используйте автономный верификатор. Эта проверка браузером дополняет проверки верификатора, касающиеся цепочек журналов и семантики данных.

Файл `README.txt` содержит руководство по началу работы, согласованный перечень файлов, инструкции по проверке и примечания по формату данных на языке отчёта, за которыми следует полное руководство на английском языке. `SHA256SUMS` охватывает перечисленные в нём файлы, за исключением самого этого файла, `manifest.json` и `manifest.sig`; подписанный манифест также охватывает `SHA256SUMS`. Оставьте исходный ZIP-архив без изменений и сохраняйте рабочие файлы вне распакованной папки. Отчёты PDF содержат закладки разделов и идентификаторы дел/отчётов на последующих страницах.

### Чат на момент экспорта

Экспорт чата фиксирует информацию, указанную Telegram о чате на момент начала экспорта: собственные метки Telegram (`scam`, `fake`, `restricted` с обоснованиями, `verified`), имена пользователей, описание, количество участников и администраторов, связанное обсуждение, защиту контента, информацию о том, видят ли новые участники предыдущие сообщения и с какого сообщения этот аккаунт видит историю (`available_min_id`), дату сообщения № 1, если это дата создания чата, и SHA-256 — фотографию чата (сохраненную в `media/`). Здесь фиксируется место аккаунта, осуществляющего экспорт, в чате: роль, дата присоединения, кто его пригласил, а для администратора — его права. Вместо этого указывается запрос, отклоненный Telegram.

Если аккаунт, осуществляющий экспорт, является администратором, при экспорте в файл `admin-log.json` записывается журнал администратора чата (Telegram хранится около 48 часов): удаления и правки с указанием содержания и аккаунта, который их совершил. Именно в этой записи об удалении указывается, кто его совершил.

### Показатели

Список отчетов и архив содержат такие записи, как `indicators.csv` , `indicators.stix.json` (STIX 2.1 ) и `indicators.misp.json` (событие MISP ), на основании которых служба по борьбе со злоупотреблениями может принимать меры в отношении записанных сообщений: ссылки и домены (в том числе скрытые за текстом, в кнопках и в предварительном просмотре ссылок), адреса криптовалют, имена пользователей и ссылки для приглашения (Telegram ), номера телефонов, адреса электронной почты и сохраненные изображения. Адреса Bitcoin, Litecoin, Dogecoin и TRON указываются только в том случае, если их контрольная сумма base58 верна, адреса segwit — если верна их контрольная сумма bech32 или bech32m, а адреса TON — если верна их CRC; адреса EVM и Solana помечаются как непроверенные. Изображения содержат SHA-256 и перцептивный хэш (dHash, 64 бита), который при повторном сжатии или изменении размера копий остаётся практически неизменным. Отчёты записывают индикаторы таким образом, чтобы они не открывались случайно (`hxxps[://]example[.]com` ); файлы сохраняют значения в том виде, в каком они были. Каждый индикатор помечается как неизвестный и не подлежащий автоматическому обнаружению (STIX , `indicator_types: unknown` , MISP , `to_ids: false` , рассылка собственной организации): наличие в списке означает, что он содержался в сообщении, а не то, что он является вредоносным. Ссылка, текст которой указывает на адрес, отличный от того, на который она ведет, помечается в отчете.

Отчёты формата PDF заканчиваются заявлением эксперта, которое необходимо подписать от руки, контрольным списком для нотариуса или судебного эксперта, а также QR-кодом (также расположенным на первой странице) с идентификатором отчёта, отпечатком ключа и SHA-256 авторитетных данных, чтобы распечатка позволяла отследить их происхождение из архива.

## Канонизация событий

Входные данные хеша состоят именно из следующих полей:

```
seq, observed_at, source_at, kind, chat_id, message_id, actor_id, payload, previous_hash
```

Сериализация должна осуществляться с использованием JSON, совместимого с Python, в кодировке UTF-8, с отсортированными ключами объектов, без ASCII-эскейпинга, без незначительных пробелов и без значений NaN/бесконечности:

```
json.dumps(value, ensure_ascii=False, sort_keys=True,
           separators=(",", ":"), allow_nan=False).encode("utf-8")
```

Хеш события формируется на основе SHA-256 этих байтов. Подпись создается с помощью алгоритма Ed25519 над 32 исходными байтами хеша, а затем кодируется в Base64. Первый предыдущий хеш (previous_hash) состоит из 64 нулей. Порядковые номера начинаются с 1 и увеличиваются на 1. Все события, включая операционные, составляют одну цепочку. Подавление дубликатов доставки отсутствует: повторные наблюдения представляют собой отдельные подтверждения получения, а не утверждение о различных действиях в Telegram.

Исходные даты Telegram представляют собой строки в формате ISO; двоичные поля преобразуются в объекты, содержащие bytes_base64. Текст сообщения, сущности, дескрипторы мультимедиа, метаданные ответов, реакции и действия сервиса сохраняются в исходных метаданных сообщения, если они были предоставлены.

observed_at — это системное время сбора данных в формате UTC. source_at — это указанная дата из Telegram, если она доступна. Уведомления об удалении не содержат точного времени удаления, поэтому source_at остается нулевым. Порядок получения данных не обязательно соответствует порядку событий в источнике. В моментальных снимках истории используются более старые даты источника, но текущее время наблюдения.

## Семантика участников

message.new actor_id — это отправитель сообщения. В поле message.edited отсутствует предполагаемый редактор; поле payload.sender_id фиксирует отправителя наблюдаемого сообщения. Удаление actor_id остаётся нулевым. Сообщения службы членства сохраняют отправителя и тип действия, не преобразуя каждое удаление в добровольный выход из группы. Необработанные обновления участников сохраняют actor_id в том виде, в котором он был предоставлен. Снимки реакций не придумывают участника, внесшего изменения.

Уведомления об удалении для личных чатов и обычных групп содержат только идентификаторы сообщений. Эти чаты используют единую последовательность идентификаторов для всей учётной записи, поэтому каждый идентификатор идентифицирует одно конкретное сообщение данной учётной записи. Если сообщение с данным идентификатором ранее было сохранено в данном журнале, его удаление фиксируется в данном чате как message.deleted с именем метода payload.chat_resolution. Идентификаторы, которые никогда не сохранялись, хранятся как deletion.unscoped без chat_id; никаких предположений не делается. Каналы и супергруппы нумеруют сообщения по чатам и никогда не сопоставляются таким образом. Если удалённое сообщение было отправлено наблюдаемой учётной записью, payload.deleted_message_was_outgoing принимает значение true; информация об удаляющем пользователе по-прежнему не предоставляется.

An unscoped notice does not establish that a message was never saved: a matching chat may be outside the current observation scope, or a unique match may be unavailable. Recheck absence remains a separate observation from a deletion notification in report counts, filters and labels. A later recovery clears the current missing state while preserving the earlier unsuccessful check in the signed history; neither observation establishes a deletion notice.

Multiple IDs resolved to the same chat from one notification are grouped as `deletion.batch`, regardless of their count. The notification does not establish that the entire history was cleared, who performed the deletion, or whether it applied to all participants. Saved outgoing messages do not change these limits. Older journals may contain `history.cleared` events inferred from batches of ten or more IDs, with explanatory text attributing the deletion to the other participant. Those inferences are not supported by the update. Preserve those original signed records, but treat them as grouped deletion notifications; the current interface labels them accordingly.

## Объём охвата: непрерывность, пробелы и незафиксированные идентификаторы

Каждый подписанный ZIP-файл содержит файл `coverage.json`, HTML-отчёт открывается с той же сводкой, а файл `verify.py` пересчитывает её на основе файла `events.jsonl`, а не доверяет исходному файлу:

- **Непрерывное наблюдение с момента X до момента Y.** Период начинается с кода `observation.started` и заканчивается при паузе, остановке, потере соединения с Telegram, выходе из системы, запуске процесса без упорядоченной остановки или при отсутствии записей в течение более трёх минут во время наблюдения (сигналы о работоспособности записываются каждую минуту, поэтому отсутствие записей означает, что процесс остановился, завис или компьютер перешел в спящий режим). При изменении интервала сигналов о работоспособности в **разделе «Параметры»** каждый сигнал фиксирует это изменение, и допустимое время отсутствия записей становится равным трём интервалам, но никогда не менее трёх минут.
- **В списке пробелов** указывается временной интервал между периодами с указанием причины. Пробел, остающийся незаполненным на момент последней записи, обозначается как `not_resumed_by_last_record`.
- **Идентификаторы сообщений не фиксируются.** Для каналов и супергрупп, в которых сообщения нумеруются по чату, пропущенные идентификаторы между зафиксированными указываются в виде диапазонов. Они отмечаются как «не*зафиксированы*» — удаленные, никогда не доставленные или выходящие за пределы сохраненной истории — но никогда как «удаленные». Личные чаты и обычные группы используют общую для всей учетной записи нумерацию, поэтому пробелы внутри одного такого чата ничего не значат и там не указываются.
- Уведомления о пропусках на уровне чата (например, запрос Telegram о восстановлении разницы в одном канале) учитываются как заметки; они не прерывают общее охват.

### Отсутствующие номера сообщений (`gap_summary`)

**Предварительный просмотр.** `coverage.json` → `gap_summary` Измеряет номера, присвоенные Telegram, которые этот коллектор никогда не видел. Telegram нумерует сообщения один раз на канал или супергруппу и один раз на аккаунт во всех приватных чатах, ботах и обычных группах. Номер, находящийся между двумя наблюдаемыми сообщениями, либо наблюдается, либо отсутствует; непрерывный диапазон является утверждением о том, что каждое сообщение, пронумерованное в нём, было наблюдаемо. Пробел не указывает ни на какого участника, ни на причину.

| Область применения | Значение |
| --- | --- |
| `status` | `on`, или `off` если отключено в **разделе «Параметры» → «Анализ пробелов»** |
| `parameters` | Параметры, которые привели к получению результата, чтобы его можно было повторить |
| `chats[]` | По одной записи на канал или супергруппу, каждая из которых пронумерована отдельно |
| `account` | Последовательность личных чатов, ботов и обычных групп для всего аккаунта |
| `status` (для каждой последовательности) | `applicable`, или `not_applicable` с `reason` |
| `observed_from`, `observed_to`, `span` | Первый и последний наблюдаемый номер, а также размер диапазона |
| `observed`, `observed_without_content` | Наблюдаемые номера; те, которые известны только по записям об удалении или повторной проверке |
| `missing`, `density`, `gap_ranges`, `largest_gap` | Число, которое никогда не наблюдалось, его доля в диапазоне, количество прогонов, самый длинный прогон |
| `clusters[]` | Перечисленные пробелы: `low`, `high`, `missing`, а также соседние наблюдаемые числа `after` / `before` с указанием времени наблюдения |
| `service_estimate` | Только при включенной функции: количество отсутствующих номеров, которые были бы служебными сообщениями с учетом их доли в общем количестве наблюдений. Никогда не вычитается из `missing` |

Достоверность определяется на основе журнала, она никогда не принимается как данность:

- **Каналы и супергруппы** учитываются по каждому чату, в том числе при экспорте выбранных чатов. В расчёт включаются записи, выбранные по отправителю `not_applicable`.
- **Последовательность по всему аккаунту** измеряется только от первого до последнего сообщения, поступившего в период, когда был включен сбор данных по всему аккаунту, и включает приватные чаты, ботов, обычные группы и собственные сообщения аккаунта, при этом ни один из таких чатов не исключается (`scope.changed`). Числа, обозначенные `deletion.unscoped` считаются наблюдаемыми без учета содержания. Экспорт или передача выбранных чатов не позволяют измерить эту последовательность. Если сбор данных по всему аккаунту был выключен, а затем включен, в примечании указывается, что номера, использованные в промежуточный период, отображаются как пробелы.
- Сервисные сообщения представляют собой записи журнала с собственными номерами, поэтому они сами заполняют пробелы; необязательная оценка служит лишь для контекста.

`verify.py` пересчитывает `gap_summary` по `events.jsonl` с настройками из подписанного `coverage.json`，для старых архивов используются значения по умолчанию．В сводке выводится результат по аккаунту．Команда `get_capture_status` в MCP и командной строке возвращает расчёт для разрешённых чатов；общая нумерация аккаунта доступна только при доступе ко всему рабочему пространству．

Repeated observations of one service message count once, and the account service estimate uses only numbers inside the measured range. An applied scope must explicitly preserve the account's own messages before account-wide measurement is enabled; older records without that information cannot establish this condition. Stopped observation does not extend the measured range, and resuming it is noted. The live archive query has a time budget, including its database scan, and marks an unfinished measurement as partial.

Telegram documents the [separate message ID sequences](https://core.telegram.org/api/updates#message-id-sequences). These numbers describe observations; they do not identify a deletion actor or establish why a number is absent.

Когда Telegram перестает принимать учётную запись, запись `coverage.gap`, завершающая наблюдение, содержит `cause` (`account_banned`, `account_frozen`, `account_deleted`, `session_duplicated`, `session_revoked`, `session_expired`, `session_ended` или `not_authorized`) и ошибку Telegram; `verify.py` указывает причину, по которой период заканчивается.

Coverage combines recorded observation periods, interruptions and message outcomes. Assess it together with the selected chats, period and attachment policy; continuous operation alone does not establish complete delivery of Telegram updates.

## Продюсер

Подписанный манифест ZIP-архивов с доказательствами, экспортов чатов, журналов свидетелей и файлов с профилями лиц содержит `producer` : название программного обеспечения, версию, проект (PhishDestroy), домашнюю страницу и репозиторий исходного кода. В отчёте в формате HTML отображается та же строка, а `verify.py` выводит её в качестве части проверенных данных. Архивы, созданные до появления этого поля, проверяются так же, как и ранее, и в отчёте указываются как не содержащие сведения о создателе.

Каждая запись `observation.started` также указывает клиент Telegram, который осуществлял наблюдение: его `api_id` (ни в коем случае не хеш), независимо от того, является ли это встроенной публичной парой или собственным приложением оператора, описание клиента, отправленное в запросе на соединение Telegram, а также тип маршрута соединения с режимом IP (без адреса прокси или секрета). В отчете и записи `custody.json` перечислены все уникальные клиенты и маршруты с указанием времени их регистрации, а также случаи, когда ни один из перечисленных прокси не ответил, и запись Telegram зафиксировала адрес сервера. Об этом свидетельствуют журналы, записанные до этого.

## Профили пользователей

Файл профиля (`tgwitness-dossier-v1`, JSON) формируется по запросу на основе записей, уже имеющихся в журнале для одного чата; никакие данные из Telegram не извлекаются, а содержимое профиля никогда не записывается в журнал (включение и выключение профилей фиксируется как `dossier.changed`). Для каждого пользователя, у которого сохранено сообщение, указываются имя и история имений, флаги Telegram (бот, мошенничество, фейк, премиум, подтверждённый, ограниченный доступ, удалённый) на момент сохранения, идентификаторы фотографий, SHA-256 и перцептивный хеш (pHash, совместимый с `imagehash.phash`) аватара из локального кэша аватаров с похожими аватарами, активность (первое и последнее сообщение, количество сообщений, отредактированные и удалённые публикации, сообщения по часам UTC), кто кому отвечает, другие чаты в этом журнале, в которых данный пользователь писал, а также упомянутые кошельки (BTC, EVM, TRON, TON, LTC, DOGE, XMR, SOL; адреса в формате Base58Check проходят проверку контрольной суммы), номера телефонов, имена пользователей и ссылки, включая ссылки, скрытые за текстом.

Каждый факт сопровождается указанием записей журнала (`seq`), из которых он взят, а `record_hashes` содержит хэш каждой упомянутой записи. Заявление подписано ключом рабочей области:

```
python verify.py tgwitness-dossier-CHAT.json --fingerprint TRUSTED_SHA256 --evidence tgwitness-evidence.zip
```

Проверяет подпись, верифицирует сам экспорт доказательств (подпись, цепочку хешей и файлы) а также наличие каждой упомянутой записи в неизменённом виде в данном экспорте того же рабочего пространства. Хеши аватаров помечаются как полученные из локального кэша (а не из записей журнала). Упоминания представляют собой совпадения по шаблону — это подсказки для проверки, а не подтверждённые факты. Профили включаются для каждого чата, могут экспортироваться в виде ZIP-архива с шифрованием AES-256 и паролем, а также удаляются при отключении или при удалении чата из источников.

## Независимый свидетель

Журнал «Witness» (`tgwitness-witness-v1`) и сообщения в его канале сверяются с экспортом доказательств с помощью `verify.py --witness … --channel …`; см. раздел [«Независимый свидетель](https://phishdestroy.github.io/TgWitness/ru/docs/reference/witness/)».

## Манифест и контрольные точки

Файл manifest.json содержит информацию о формате, времени экспорта, открытом ключе, отпечатке, длине журнала, хеше начала, области действия, создателе, ограничениях, а также SHA-256 каждого элемента содержимого, кроме самих `manifest.json` и `manifest.sig`. Файл manifest.sig представляет собой подпись Ed25519 в кодировке base64, наложенную на канонический JSON-манифест. Проверяющее устройство отклоняет неожиданные или отсутствующие элементы, дубликаты имен, повреждённые файлы, нарушенную последовательность или цепочку, недействительные подписи, а также несоответствие предоставленной контрольной точке. Оно никогда не извлекает пути к архивам. Общий объём некомпрессированных данных ограничен 4 ГиБ; архивы `--max-gib N`, созданные с увеличенным пределом **параметров,** могут иметь больший размер.

Run verification from your installed TgWitness version or a reviewed checkout. The copy included in an archive supports portable use; check that copy against your trusted installation before executing it.

A checkpoint signs a statement containing the public key, journal length, head hash, and creation time. The verifier can check that a later archive contains the same prefix. Retain the checkpoint outside the collector, so later verification compares the archive with a reference held separately from it.

## Объем проверки

Verification checks the archive and the collection mode used to produce it. Choose the mode whose trust boundary matches the case, then retain its verification inputs.

| Режим сбора | Что проверяется | Материалы и условия проверки |
| --- | --- | --- |
| Локальное рабочее пространство | Record signatures, hash chain, manifest and attachment bytes | Independently retained collector fingerprint; the host administrator controls the local signing key |
| Локальное рабочее пространство с независимым свидетелем | Проверка архива и совпадения его начального участка с ранее сохранённой записью свидетеля | Separately trusted witness key and records; the checkpoint binds the prefix already observed |
| [Сбор через GitHub Actions](https://github.com/phishdestroy/TgWitness/blob/main/docs/SEALED-ACTIONS.md) | GitHub attestation of the archive digest, approved workflow and collector commits, hosted runner, fresh session/key origin and internal archive integrity | Trusted verifier policy, caller repository and GitHub attestation bundle; collection runs under the pinned workflow |
| [Облачное развёртывание](https://phishdestroy.github.io/TgWitness/ru/docs/reference/high-assurance/) | Provider lifecycle and access records, firewall and Cloudflare state, plus the collector's signed run record | Read-only queries to the provider and Cloudflare; availability of individual checks depends on the provider |
| [Конфиденциальная ВМ Intel TDX](https://phishdestroy.github.io/TgWitness/ru/docs/reference/high-assurance/#confidential-vm-on-phala-cloud-intel-tdx) | Quote signature and platform status, binding to the collector statement, compose and OS measurements | Intel trust chain and expected deployment measurements; retain the results of every required TDX check |

In sealed acquisition, the approved collector receives data through an authenticated Telegram connection inside the verified environment. Attestation binds the archive to that execution, so verification covers acquisition as well as later file integrity. This relies on the approved code and the platform trust chain listed above. GitHub capture verification requires a session created inside the run and rejects imported-session captures.

The run receipt records the collector version, file hashes and startup settings. GitHub provenance and TDX measurements provide the environment checks; the [validation record](https://phishdestroy.github.io/TgWitness/ru/docs/reference/verification/) identifies tested configurations.

TgWitness signs the observations it collects; Telegram and message authors do not issue these signatures. In a local workspace, material created before the first independent checkpoint still depends on the collector and its key holder. Coverage records describe the selected scope and collection outcomes, while verified external timestamps anchor the committed archive or journal boundary in time.

## Вложения

Файлы идентифицируются по хешу SHA-256 в каталоге media/. Событие media.saved связывает хеш и длину в байтах с конкретным событием сообщения. Исходные имена файлов являются метаданными, а не локальными путями. Байты мультимедиа загружаются асинхронно, поэтому немедленное удаление может помешать их фиксации. В качестве результатов отображаются: отключенный сбор данных, файлы чрезмерного или неизвестного размера, сбои при загрузке и прерванные загрузки. Сбой процесса может привести к появлению неимеющих ссылок неполных файлов; они не включаются в экспортируемые данные.

Экспортер в формате ZIP сверяет сохраненные медиафайлы с их именами. Экспорт в форматы JSONL, CSV и HTML проверяет сигнатуры событий, но не передаёт байты медиафайлов. Производные отчёты предназначены для удобства; файл events.jsonl является авторитетным представлением событий.

При полном экспорте чата вложения сохраняются в соответствии с настройками вложений рабочего пространства в папке media/ с именами в формате SHA-256. Каждая запись сообщения в файле chat.json указывает название файла (`file`, `file_sha256`) или причину его отсутствия (`file_status`), а также то, что видел читатель вокруг текста: ссылки за текстом, источник пересылки, кнопки ботов, подпись, просмотры и таймер автоматического удаления. Файл `verify.py` проверяет, что каждый указанный файл находится в подписанном манифесте под этим хешем.

## Надежный сбор и обработка подтверждений (0.2)

Обработка медиафайла и фиксация события сообщения осуществляются в рамках одной транзакции. Задание сохраняет исходный дескриптор сообщения Telegram; подписанное наблюдение связывает его SHA-256, учётную запись и политику размера. При восстановлении эта привязка проверяется перед загрузкой. Система никогда не извлекает текущее сообщение и незаметно заменяет его более новым вложением. Прерванные задания повторяются, в то время как постоянный сбой остаётся явным результатом.

Each workspace has its own journal and signing identity. A process.started event includes a run ID, local clocks, dependency versions, source-file hashes, initial account/scope, and capture settings. Heartbeats include the run ID, monotonic time, and queue state. The run receipt can also be downloaded as a separately signed statement. For verification of the execution environment, pair it with the GitHub attestation or TDX checks described in [Verification scope](https://phishdestroy.github.io/TgWitness/ru/docs/reference/evidence/#verification-scope).

Automatic checkpoints are retained locally on startup, every five minutes while observing (**Parameters → Signed checkpoint every**), and on orderly stop. Startup verification and export compare the journal against the latest retained local checkpoint. This can detect a database rollback when the checkpoint survives. Independent retention keeps that reference available outside the workspace; a verified external timestamp additionally anchors it in time.

После перезапуска возобновляется сохраненная позиция обновления Telegram (`catch_up_from` в `observation.started`), и запрашиваются пропущенные обновления. Периодическая повторная проверка фиксирует `message.recovered` для пропущенных сообщений и `message.missing_on_recheck`, когда Telegram больше не возвращает сохраненное сообщение; последнее не является уведомлением об удалении и не указывает ни лицо, удалившее сообщение, ни время.

### Внесайтовое копирование и восстановление (S3)

Внесайтовая копия (функция «Экспорт», по умолчанию отключена) загружает фрагменты журнала, сохраненные файлы, контрольные точки с их временными метками, а также готовые экспорты чатов в хранилище, совместимое с S3, зашифрованные с помощью AES-256-GCM перед загрузкой с использованием ключа, хранящегося в хранилище рабочей области; применяется функция удержания Object Lock, если это поддерживается хранилищем. Без загруженного ключа копия не подлежит чтению. Восстановление и проверка осуществляются с помощью `python -m tgwitness.replica restore --key-file KEY.json --out DIR`.

Для восстановления требуется пустой обычный каталог. Загруженные и расшифрованные объекты остаются в частном временном хранилище до тех пор, пока не будет проверен весь журнал и каждая сохраненная контрольная точка. Небезопасные пути к объектам, несогласованные диапазоны сегментов и журналы, длина которых меньше контрольной точки, отклоняются; в случае неудачной проверки восстановленные файлы не публикуются. Проверки срока хранения сравнивают возвращённый режим Object Lock и дату с крайним сроком, отправленным при загрузке (допуск на округление составляет одну секунду). Истекший, недействительный или сокращённый крайний срок не считается проверенным. Статус указывает на выбранный объект, срок хранения которого был считан обратно для данного цикла загрузки.

Отсутствие или повреждение локальных медиафайлов фиксируется как ошибка текущего прохода, при этом курсор медиафайлов остаётся перед этим местом, чтобы файл был повторно обработан в следующем проходе; файлы, контрольные точки и экспортированные данные, следующие за ним, по-прежнему копируются. При восстановлении все ссылки на сохраненные медиафайлы сверяются с расшифрованными хешами и зафиксированными размерами. Идентичные перекрывающиеся сегменты журнала от прерванных загрузок дедуплицируются; конфликтующие перекрытия отбрасываются. Контрольные точки, созданные во время загрузки, откладываются до тех пор, пока охватываемые ими записи журнала не будут скопированы, поэтому завершённый проход не публикует контрольную точку раньше, чем соответствующая запись в журнале.

### Потоковый экспорт моментальных снимков

При потоковом экспорте используется стабильный снимковый файл чтения SQLite. Его начало может оказаться более старым, чем текущий активный журнал к моменту завершения загрузки. Контрольная точка, созданная после этого снимка, может правильно показывать, что архив короче; сравнивайте с контрольной точкой, расположенной на уровне экспортируемого префикса или перед ним, а не с произвольной более поздней контрольной точкой.

## Подготовка RFC 3161 и проверка ответов (0.2)

В режиме «Доказательства» (по умолчанию отключен) отправляется только хеш SHA-256 каждой подписанной контрольной точки в указанные авторитетные источники по стандарту RFC 3161 и календари OpenTimestamps через маршрут рабочей области, но ни в коем случае не через MTProxy. Ответы хранятся в формате `checkpoints/anchors/`, экспортируются и проверяются с помощью `verify.py` (`--tsa-ca` проверяет подпись TSA; подтверждение доказательств OpenTimestamps осуществляется с помощью `ots upgrade` и `ots verify`).

Панель подготавливает архив запросов, содержащий канонические байты файла checkpoint.json, отпечаток сообщения с хэшем SHA-256 и случайный нонс в файле timestamp.tsq, а также контрольные суммы и инструкции. Сетевые запросы не осуществляются. Подготовленный архив не является доверенной временной меткой.

`python -m tgwitness.anchor verify` дважды вызывает OpenSSL: один раз для проверки байтов контрольной точки и один раз для проверки исходного запроса. Требуется явно указать файл доверенного центра сертификации; включённые сертификаты автоматически не считаются доверенными. Проверка запроса является опциональной в командной строке, поэтому сохраните и укажите параметр `--request` для проверки нонса. Результат указывает, была ли проведена проверка. Подпись контрольной точки сборщика и журнал по-прежнему необходимо проверять отдельно с помощью доверенного отпечатка сборщика.

Проверка включает в себя проверку подписи ответа, байтов контрольной точки и, при наличии, исходного запроса в рамках указанного доверия к центру сертификации. Проверка отзыва сертификатов и проверка достоверности долгосрочного архивирования после истечения срока действия сертификата выходят за рамки данного средства проверки. См. [процедуру](https://phishdestroy.github.io/TgWitness/ru/docs/reference/timestamp/) и [результаты проверки](https://phishdestroy.github.io/TgWitness/ru/docs/reference/verification/).

## Дополнительные записи в режиме сбора доказательств: устройства drand и Telegram

Ещё две записи могут выполняться с теми же проходами, что и временные метки. Обе по умолчанию отключены и вступают в силу только при включённом режиме доказательств: «Дополнительно» → «Доказательства и резервные копии» → **«Дополнительные свидетели» · опционально**, или `"drand": true` и `"devices": true` в `POST /api/evidence`. Сбой одного из них не останавливает работу другого или временных меток; панель отображает последний результат каждого из них под формой.

**drand** (`beacon.drand` ). При каждом проходе в журнал записывается новейший раунд drand quicknet — общедоступная случайная величина от League of Entropy (один раунд каждые 3 секунды): `chain` , `round` , `randomness` , `signature` , `round_time` и `relay` , ответивший на запрос. Проверенный непредсказуемый раунд служит нижней временной отметкой для последующих материалов, связанных хэш-ссылками. Проверенная временная метка на более поздней контрольной точке служит верхней временной отметкой. Эти проверки ограничивают связанный материал; охват сбора оценивается отдельно. Сборщик сначала обращается к `drand.cloudflare.com` , затем к ретрансляторам Protocol Labs через маршрут рабочей области, по одному запросу за каждый проход.

`verify.py` проверяет, что каждый случайный номер является SHA-256 своей подписи и что время раунда верно, а также сообщает о раундах, самом длинном отрезке без раунда и о том, насколько часы сборщика отставали от drand. Он не проверяет подпись BLS. `--check-drand` сравнивает раунды с ретранслятором Cloudflare и ретранслятором Protocol Labs — либо со всеми из них, либо со случайной выборкой из 100 записей в длинном журнале; раунд, который отличается, не проходит проверку.

Устройства **, Telegram,**, `account.devices`. При каждом проходе считываются сессии аккаунта с `account.getAuthorizations`, список Telegram отображается в «Настройки» → «Устройства», и записывается: полностью, если он изменился с момента предыдущего прохода, с хешами сеансов `added` и `removed`, в противном случае — только его количество и SHA-256. Сохраняются модель устройства, платформа, приложение и версия, дата создания и последней активности, страна и регион; IP-адреса не сохраняются, поскольку экспорт доказательств выходит из-под вашего контроля. Собственная сессия сборщика активна постоянно, поэтому только активность других сессий считается изменением. `verify.py` сообщает, как часто список записывался, а также о каждой новой и завершённой сессии. Он считывает список только во время работы наблюдения.

Чего они не показывают: drand подтверждает лишь порядок записей относительно общедоступного времени, а список устройств представляет собой заявление Telegram, прошедшее через сборщик и подписанное им, как и любая другая запись.

**Журнал Cloudflare Gateway** (`cloudflare.gateway_dns`). Для сервера, который осуществляет разрешение через Cloudflare Gateway ([Gateway DNS](https://phishdestroy.github.io/TgWitness/ru/docs/reference/high-assurance/#cloudflare-as-an-outside-witness)), каждый цикл копирует то, что Gateway зарегистрировал с момента предыдущего копирования: по одной записи за интервал не более трёх часов с указанием `from`, `until`, `location_id`, `address` сервера (если он задан) и `queries` в качестве `[at, name, type, rcode, decision, colo]`, в том числе в случае их отсутствия. Установите это в **«Журнал шлюза Cloudflare»**: учётная запись, местоположение, опциональный адрес и токен только для чтения (Account Analytics Read; Zero Trust PII Read для сохранения одного адреса общего местоположения). Панель проверяет их с помощью одного запроса перед сохранением; токен остается зашифрованным и никогда не попадает в журнал. В `verify.py` перечислены окна, наиболее часто искомые имена и время, не охваченное копией; запись, количество запросов которой не совпадает с количеством запросов, считается неудачной. Окно, содержащее более одной страницы запросов за одну секунду, сохраняет эту страницу и указывает, что остальная часть отсутствует. Копия представляет собой ответ Cloudflare, полученный через коллектор и подписанный им; в течение 24 часов любой, у кого есть токен только для чтения, может сравнить её с данными Cloudflare.
