## Live server journal inventory · 1 November 2026

At approximately 19:15 UTC, sequential read-only SQLite `query_only` queries counted events in ten workspace databases on a running server. Collection continued during the queries, so this is not an atomic snapshot across workspaces.

| Observed across the ten workspace databases | العدد |
| --- | --- |
| Workspaces with at least one `message.new` event | 8 |
| Journal records, including operational events | 1,610,818 |
| `message.new` events | 900,232 |
| `message.edited` events | 80,683 |
| `message.deleted` events | 400,536 |
| `message.recovered` events | 53,403 |
| `message.snapshot` events | 2,183 |
| `media.saved` events | 50,418 |
| `media.failed` events | 5,575 |
| `coverage.gap` events | 11 |
| Database bytes, excluding WAL files and media | 7,909,003,264 |

These are **event counts**, not unique messages, people or media files. The same message can appear in more than one workspace, and an edit or deletion can produce another journal event. `media.failed` counts historical failure events, not the current media queue. The queries did **not** newly verify signatures and the full hash chain of all 1,610,818 records, measure delivery or throughput, or establish that every Telegram event was captured. No message content, account or chat IDs, workspace labels, credentials or private files are published here.

At this review, the separately configured public monitor covered three sources: one capture response was OK and two reported `no_response`. That monitor is not a ten-workspace health summary. `no_response` means the observer could not obtain a response at that check; it does not establish message loss. The smaller 29 October test below has its own explicit signature and hash-chain verification.

## Recent offline and fault-injection checks · 1 November 2026

These checks use fictional data and local files; they add regression evidence for the current source, not another live Telegram delivery measurement:

| تحقق | What it exercised |
| --- | --- |
| [Source archive](https://github.com/phishdestroy/TgWitness/blob/main/tools/check_source_archive.py) | Two builds with identical source bytes but changed file times produced the same ZIP and checksum. Exact archived bytes and file hashes matched; private test files stayed out. A simulated write failure left the previous archive and checksum intact. |
| [Account export recovery](https://github.com/phishdestroy/TgWitness/blob/main/tools/check_account_export_recovery.py) | A simulated disk error on the second ZIP member left no published or partial ZIP. Resume kept every signed receipt byte-identical, produced an independently verifiable archive using the expected signing fingerprint, and retained the synthetic coverage gap as a partial result. Scale assertions guard against repeated task and receipt scans as histories grow. |
| [Minimized disclosure privacy](https://github.com/phishdestroy/TgWitness/blob/main/tools/check_disclosure_privacy.py) | Synthetic Unicode names and aliases, nested metadata, unknown senders and media fields were checked in all three identity modes and with text omission. A masking-limit failure did not silently weaken redaction; the original signed account export stayed unchanged. |
| [Linux media decoder and OCR](https://github.com/phishdestroy/TgWitness/blob/main/tools/check_media_worker.py) | A [Linux Docker CI check](https://github.com/phishdestroy/TgWitness/actions/runs/41341200341/job/124951395192) at commit `5a9e0814` passed generated Ogg/Opus, MP3, M4A, MP4 with video, WAV and FLAC inputs; forged-duration and secondary-file-reference controls; and 48 mutated parser fixtures (34 rejected, 14 decoded within bounds). Real Tesseract OCR ran with original bytes unchanged. The decoder and OCR ran in network-isolated containers without a Whisper model. |

The checks run in the [pull-request](https://github.com/phishdestroy/TgWitness/blob/main/.github/workflows/pr-check.yml) and [full Checks](https://github.com/phishdestroy/TgWitness/blob/main/.github/workflows/checks.yml) workflows. They test these failure boundaries, not every possible storage failure or whether a disclosure is automatically safe to publish. The media check does not measure speech recognition accuracy or Telegram delivery. Review each derivative before sharing.

## ملف تصدير محمي بكلمة مرور يُفتح باستخدام libarchive · 29 أكتوبر 2026

تم فتح أرشيف تم إنشاؤه بواسطة كود تشفير التصدير (WinZip AES-256، وهو التنسيق الذي يقرأه كل من 7-Zip وWinRAR ) باستخدام Windows `tar` (bsdtar 3.6.2، libarchive). باستخدام كلمة المرور الصحيحة، تطابق الملف المستخرج مع قيمة SHA-256 الأصلية؛ أما كلمة المرور الخاطئة فقد تم رفضها بعبارة «عبارة مرور غير صحيحة ». ولم يتم تشغيل برامج 7-Zip وWinRAR نفسها.

## اختبار Telegram المباشر · من 27 إلى 29 أكتوبر 2026

قام حساب Telegram حقيقي واحد، تم تسجيل الدخول إليه عبر مجموعة أزواج واجهة برمجة التطبيقات (API) المدمجة، بتسجيل مجموعة كبيرة واحدة من **27 أكتوبر الساعة 21:36 بالتوقيت العالمي المنسق (UTC) إلى 29 أكتوبر الساعة 05:15 بالتوقيت العالمي المنسق (UTC)**. تم تشغيل أداة التجميع 12 مرة خلال تلك الفترة.

| مسجلة | العدد |
| --- | --- |
| سجلات السجل، بما في ذلك نبضات القلب وسجلات الخدمة | 2,385 |
| رسائل جديدة | 1,291 |
| عمليات الحذف | 472 |
| تم حذفها بعد أن قام TgWitness بحفظ النص | 347 |
| التعديلات | 12 |
| الرسائل التي فاتت أثناء التوقف، تمت إضافتها عند إعادة الفحص | 12 |
| المرفقات المحفوظة | 17 |
| المرفقات لم يتم تنزيلها (التنزيل معطل، أو لا يوجد ملف للتنزيل) | 14 |
| يقوم Telegram FloodWait بالتوقف مؤقتًا لمدة 3 ثوانٍ في كل مرة أثناء إعادة الفحص | 8 |

- يتم التحقق من التوقيعات وسلسلة التجزئة لجميع السجلات البالغ عددها 2,385 سجلًا مقابل المفتاح العام للسجل.
- بعد إعادة التشغيل، يستأنف المجمع العمل من حالة التحديث المحفوظة (`pts`) ويقوم Telethon بملء الفجوات؛ ثم تضيف عملية إعادة الفحص الرسائل التي لا تزال مفقودة.
- في كل مرة يواجه فيها المجمع حالة «FloodWait»، ينتظر المجمع المدة المطلوبة ثم يواصل العمل.
- ظل الحساب مسجلاً للدخول، وأعيد الاتصال بنفس الجلسة في 29 أكتوبر.

لا يشمل هذا الاختبار: التعامل مع عدة حسابات في آن واحد، وأدوار المسؤولين، والبروكسيات، وانقطاعات الخدمة التي تزيد مدتها عن بضع ساعات، وإ[جراءات القبول المباشرة](https://github.com/phishdestroy/TgWitness/blob/main/docs/internal/LIVE_ACCEPTANCE.md) الكاملة. تحتوي الملفات العامة على هذه العناصر فقط: لا توجد معرّفات للحسابات أو الدردشات، ولا رسائل، ولا بيانات اعتماد.

تصف الإدخالات الأقدم أدناه عمليات التشغيل الخاصة بها؛ وقد استخدم معظمها عملاء اختبار اصطناعيين. فيما يلي أحدث النتائج الآلية.

## قوائم MTProxy العامة المدمجة · 29 أكتوبر 2026

هذا هو السجل التاريخي لاختبار الإصدار الأصلي الذي تم اختياره يدويًّا. للاطلاع على أوضاع التجميع التلقائي وعناوين IP الحالية، انظر [إعدادات الاتصال](https://phishdestroy.github.io/TgWitness/ar/docs/reference/connection/#ip-modes). الأرقام والميزات غير المدعومة الواردة أدناه تخص تلك النسخة التي تم اختبارها.

تمت إضافة لقطة عامة مجمعة وتحديث HTTPS صريح من SoliSpirit/mtproto و zakky8/mtproto-proxy-pro. على هذا المضيف، قام برنامج تنزيل التطبيق بجلب كلا الخلاصتين بنجاح في 29 أكتوبر 2026 الساعة 12:58 بالتوقيت العالمي المنسق (UTC): **118 نقطة نهاية فريدة متوافقة** بعد التصفية وإزالة التكرار والحد الأقصى المسموح به البالغ 64 إدخالًا لكل مصدر. وهذا يؤكد استرداد القائمة، وليس الاتصال أو تسليم الرسائل عبر نقاط النهاية تلك. لم يتم ربط أي حساب حقيقي بوكيل مدرج في القائمة خلال هذا العمل. [دليل المشغل والمستخدم](https://github.com/phishdestroy/TgWitness/blob/main/docs/ru/PROXIES.md).

تحتفظ استجابات المصدر الفاشلة/الفارغة/غير المتوافقة بالمدخلات والتواريخ السابقة. التحديثات لا تغير المسار المحدد. يتم التحقق من صحة العناوين العامة وتثبيت عناوين IP التي تم تحليلها عند الاختيار؛ بينما تظل مسارات المشغل/اليدوية منفصلة. أصبح اختبار الاتصال متاحًا الآن في اللوحة قبل تسجيل الدخول إلى الحساب. لا يزال TLS ee المزيف واختيار البروكسي التلقائي غير مدعومين. يتجاوز كتالوج المشغل الاشتراكات تمامًا.

- المجموعة الكاملة: **366 اختبارًا ناجحًا، 3 اختبارات تم تخطيها**، 287.94 ثانية. لا تزال تحذيرات التبعيات الحالية وحالات تخطي المنصات قائمة. اختبار الانحدار النهائي للقائمة العامة/الترجمة: **36 اختبارًا ناجحًا**، بما في ذلك رفض منافذ بروكسي التنزيل غير الصالحة؛ وهذا يتداخل مع المجموعة الكاملة.
- اجتياز اختبار التوافق مع المتصفحات باللغتين الإنجليزية والروسية، في الوضع الفاتح/الداكن بدقة 390/1440 بكسل: خيارات مدمجة، لا يوجد استدعاء خارجي عند فتح الإعدادات، تحديث صريح، احتفاظ بالمسارات و ذاكرة التخزين المؤقت أثناء الأعطال، فحص ما قبل تسجيل الدخول، عزل مساحة العمل في حالة الاستجابة المتأخرة، تفاصيل المصدر والتخطيط/التباين. لا توجد أخطاء في JavaScript أو طلبات خارجية للمتصفح.
- تمت الموافقة على الترجمة النهائية الثابتة لجميع اللغات الـ13؛ وتم ترجمة النص الجديد إلى الروسية مع توفير نصوص بديلة باللغة الإنجليزية في الأماكن الأخرى. وقد اجتاز الدليل المدمج المحدث فحوصات التخطيط والتباين في كلا السمتين.
- تم اجتياز فحوصات Ruff والنشر (259 ملفًا عامًا، 1,354 رابطًا محليًّا)؛ تم تحديث تحليل ملفات Compose و CI YAML. لم يتم تنفيذ Docker و CI عن بُعد هنا.
- اجتازت «العجلة المعاد بناؤها» اختبار التثبيت المنفصل، وتحميل قائمة الحزم، والتحقق من التصدير الموقّع . تطابقت جميع موارد الحزمة البالغ عددها 69 مع مساحة العمل؛ وتم التحقق من تجزئات المصدر.

## تدقيق إعداد روبوت Witness والوكيل · 29 أكتوبر 2026

يُعد إعداد الشاهد (الآن **«Extras» → «A bot in your channel**») شاهدًا يتم نشره بشكل مستقل: مفتاح جامع مثبت ، وتنزيل رمز مميز محدد النطاق، وقناة خاصة، وسياسة النشر، ومسار HTTP/SOCKS5، وواجهة برمجة تطبيقات Bot API مخصصة. يظل رمز البوت على مضيف الشاهد. ويقوم رمزه الجديد `--check-config` بالتحقق من صحة التكوين والملفات دون فتح اتصال شبكي أو إنشاء مفتاح. يتم تحديد مسارات ملفات JSON بجانب التكوين. تقوم جميع متغيرات الشاهد في Compose الآن بإعادة توجيه إعدادات وكيل HTTP وواجهة برمجة تطبيقات البوت.

تدعم إعدادات الحساب كتالوج MTProxy عامًا يديره المشغل، ومعاينة مخصصة لرابط بروكسي Telegram والحقول اليدوية الموجودة. تستبعد استجابات الكتالوج الأسرار؛ ويؤدي الاختيار إلى تخزين المسار في خزينة مساحة العمل. تؤدي الكتالوجات المفقودة أو غير الصحيحة إلى إتاحة المسارات اليدوية. لا يتم إنشاء أو تمكين عناوين بروكسي للمشروع أو خدمة الشاهد المستضافة بشكل افتراضي. يعرض مثال Caddy نقطة النهاية الرئيسية المحددة النطاق فقط عندما يتعين على شاهد خارجي الوصول إلى جامع تظل لوحته خاصة.

التحقق من الصحة:

تضمنت تمارين تغطية الانحدار الجديدة رفض StringSession، وتغييرات في الكود وحسابات المصادقة الثنائية (2FA)، وإلغاء البحث عن الهوية، وإلغاء تسجيل الدخول المعلق، والتحديثات من خلال المعالجات المسجلة على العملاء النشطين والمرفوضين والمستبدلين وعملاء الاختبار. ولا يساهم في الأحداث سوى المجمع النشط؛ بينما تظل بيانات الاعتماد المحفوظة والسجل الموقّع سليمة. تغطي الفحوصات الجديدة الأخرى البحث باستخدام Unicode بعد إعادة فتح قاعدة البيانات، وإدراج حدود سياسة المراقبة في التغطية، واستثناءات حزم المصادر العامة.

أطلق المشروع الفعلي `pythonw.exe` لوحة اصطناعية معزولة، وأرجع رمز حالة HTTP 200 واحتفظ بتشخيصات بدء التشغيل في `logs/server.log`. لم يحتوِ السجل على رمز اللوحة الذي تم إنشاؤه أو سجلات الوصول عبر HTTP. لم ينهِ الاختبار سوى عمليته الاصطناعية الخاصة. لم يتم تسجيل أي مهمة في «جدولة المهام»؛ ويظل تسجيل الدخول/تسجيل الخروج، ووضع السكون واستعادة الخدمة متطلبات منفصلة.

اجتاز اختبار التوافق مع Chromium **45 سيناريو**، دون حدوث أخطاء في JavaScript بالصفحة و دون ملاحظة أي طلبات خارجية. تغطي الفحوصات الجديدة تواريخ وأوقات الخط الزمني بدقة 601/768/850 بكسل ومسودات المرفقات عبر تحديث الحالة، والتعديلات الأحدث التي تتم أثناء الحفظ، ونتائج التحقق التي تم مسحها عند تبديل الحساب، واستجابات التحقق المتأخرة بعد التبديل إلى تطبيق آخر ثم العودة، وحدود التحقق الصريحة عند وصول أحداث جديدة. كما تم تصحيح تباعد أيقونة البحث/النص وإعادة تشغيل مجموعة المتصفحات.

استخدم تشغيل المتصفح بيئة التشغيل المثبتة في `.venv` و Playwright 1.62.0/Chromium المقدم من النظام، والذي أُضيف بعد بيئة المشروع في مسار الاستيراد. تم إيقاف تثبيت تابع تطويري اختياري أثناء بطء تنزيل Playwright؛ ولم يتم تأهيل أي إصدار جديد لأداة المتصفح. أكمل `python start.py --setup-only` العادي ترقية التطبيق. تشير المصدر والبيانات الوصفية المثبتة وتقرير علامة المشغل إلى الإصدار 0.5.1؛ اجتاز `pip check` الاختبار. اجتازت اختبارات الجاهزية على مسار جديد غير مستخدم، مع الاحتفاظ بالتحذير المتوقع بشأن مفتاح الخزنة المحلية.

تم تثبيت إصدار 0.5.1 بشكل منفصل وإجراء اختبار أولي عليه: تم تقديم جميع عناصر اللوحة/الدليل ، وتم رفض الوصول غير المصادق عليه إلى واجهة برمجة التطبيقات (API)، واجتازت ملفات ZIP للأدلة المكونة من 32 حدثًا، سواء المباشرة أو المتدفقة ، عملية التحقق المستقلة. تمت مقارنة ملفات التطبيق الموجودة في الحزمة المثبتة مع الملفات المصدرية. يستخدم أرشيف المصدر العام قائمة السماح الصريحة لأنواع الملفات ويرفض الملفات المصدرية المرتبطة؛ ويتم استبعاد المواد التي يتم إنشاؤها أثناء التشغيل الموجودة داخل دلائل المصدر من اختبارات الانحدار.

أثناء عملية إصلاح الكود، احتوى اختيار المصدر المفتوح ومجموعة المرشحين في Git على 86 ملفًا، دون تضمين أي دلائل بيانات وقت التشغيل. ولم يسفر الفحص عن أي تطابقات لأنماط المفاتيح الخاصة القابلة للتعرف عليها، ورموز GitHub، ورموز روبوتات Telegram، وأنماط StringSession. ويُعد هذا فحصًا محدودًا للأنماط، وليس تدقيقًا شاملاً للأسرار. تغطي اختبارات قواعد التجاهل اثني عشر عنصرًا شائعًا من الحسابات/البيانات/التصدير. تم تحليل ملفات YAML الخاصة بسير العمل/المشكلات/التأليف ونصوص مهام Windows بنجاح. تم حل روابط الوثائق المحلية.

تمت معالجة جميع النتائج السبع المستخلصة من المراجعة التي أجريت في 27 أكتوبر. لا يزال تنفيذ سير العمل على GitHub، وبيئة التشغيل على Linux/macOS/Docker، والتطبيق الحقيقي لـ Telegram، والتوافق مع البروكسيات الخارجية/TSA، وكفاءة التحمل تحت الأحمال المستمرة خارج نطاق هذا التشغيل المحلي. لم يتم إجراء أي نشر للمستودع، أو تسجيل للخدمة، أو جمع لحسابات حقيقية. تم تنفيذ ذلك.

### تحديث الوثائق باللغة الإنجليزية

يصف ملف README، ومرجع الحساب/الجلسة، وسير عمل التجميع، والدليل المرفق الآن المدخلات المدعومة، وسلوك مساحة العمل، وسياسات الأحداث، وتنسيقات التصدير باللغة الإنجليزية. تم تحديث اللقطات الثلاث العامة باستخدام بيانات اصطناعية. في تلك المرحلة، احتوى اختيار المصادر العامة على 88 ملفًا، بما في ذلك الدليلين الجديدين. جميع الروابط المحلية البالغ عددها 131 رابطًا عبر 23 مستندًا بتنسيق Markdown تعمل بشكل صحيح.

بعد تعديلات الواجهة والدليل، اجتاز اختبار Chromium مرة أخرى جميع السيناريوهات الـ45، دون ملاحظة أي أخطاء في جافا سكريبت للصفحة أو طلبات خارجية. لم يتم إعادة تشغيل مجموعة Python الكاملة من أجل تحديث هذه الوثائق والعرض التقديمي؛ وتنتمي نتيجة اجتياز الـ94 سيناريو المذكورة أعلاه إلى عملية إصلاح الكود السابقة.

تم تثبيت العجلة المعاد بناؤها على هدف جديد معزول. وقد عملت لوحة التحكم وأدوات التوجيه بنجاح، وتم رفض الوصول غير المصادق عليه إلى واجهة برمجة التطبيقات (API)، كما اجتازت عمليات التصدير المباشرة والمتدفقة التحقق المستقل لـ 32 حدثًا اصطناعيًا.

### تحديث بشأن التثبيت والنشر

اجتازت عمليات التثبيت المركزة والتعبئة وفحوصات الجاهزية **14 اختبارًا**، مع تخطي واحد لعدم توفر إنشاء رابط رمزي. تغطي فحوصات الغلاف الأصلي المسارات التي تحتوي على مسافات، وتوجيه الوسيطات، وأوضاع الإعداد/العرض التوضيحي، وانتشار الخروج غير الصفر. تختبر فحوصات Git Bash مساعد shell الخاص بـ Docker باستخدام برنامج خفي محاكى، بما في ذلك غياب Docker، وغياب Compose، وفشل انتظار حالة الصحة، ونجاح بدء التشغيل عبر منفذ بديل. لا تثبت هذه الفحوصات المحاكاة توافق وقت تشغيل Docker.

تم تثبيت نسخة كاملة من المصدر المفتوح في دليل Windows جديد يحتوي مساره على مسافات. أنشأ `scripts\Setup.cmd` بيئة جديدة وقام بتثبيت بيئة التشغيل المثبتة؛ وأبلغ `Start.cmd --check --json` عن جاهزيته دون إنشاء دليل البيانات المستهدف. نجح `pip check`. كما اجتازت العجلة المعاد بناؤها فحص الحزمة المثبتة، بما في ذلك عمليات التصدير المباشرة والمتدفقة لـ 32 حدثًا.

تم تحليل بناء جملة لغة Shell وخمسة ملفات YAML خاصة بسير العمل/Compose. تتوافق تكوينات Compose للمصدر والصور فيما يتعلق بإعدادات التخزين ووقت التشغيل. في تلك المرحلة، تم حل جميع الروابط المحلية البالغ عددها 139 رابطًا موزعة على 23 مستندًا بتنسيق Markdown. يحتوي اختيار المصادر العامة على 99 ملفًا.

تطبق تعريفات CI الآن إعدادات أصلية جديدة على أنظمة Windows/Linux/macOS، بالإضافة إلى التحقق من سلامة Compose والتحكم في الوصول والاستمرارية عبر إعادة إنشاء الحاويات، وتكوين Caddy. يعتمد سير عمل الإصدار على اجتياز هذه الفحوصات ويضيف اختبارًا أوليًا لمحاكاة ARM64. Docker غير متاح على هذا المضيف: التنفيذ الفعلي لـ Compose/Caddy، وإصدار الشهادات، وتنفيذ ARM64، وسير العمل عن بُعد/نشر الحزم لا تزال غير متاحة محليًّا. لم يتغير كود التطبيق/واجهة المستخدم في هذا التحديث؛ ولم يتم إعادة تشغيل نتائج Python والمتصفح الكاملة السابقة.

## الإصدار 0.5.0

اجتازت مجموعة اختبارات وقت التشغيل المثبتة بالكامل: **81 اختبارًا ناجحًا، وتخطي اختبار واحد**، في 22.00 ثانية، مع ظهور تحذير Starlette الحالي. يتم تخطي فحص أذونات POSIX في نظام Windows. تختبر المعالجات الجديدة إرسال الرسائل، والتعديلات، وعمليات الحذف المحددة النطاق/غير المحددة النطاق، والردود، وتحديثات المشاركين، ورسائل خدمة العضوية من خلال سياسات مختلفة. لا تنتج الفئات المعطلة أي ملاحظات حية مقابلة؛ وتظل تشخيصات التغطية واللقطات الصريحة متاحة. تتحقق الاختبارات من استمرار السياسة، وفصل مساحة العمل، وسجلات التدقيق الموقعة قبل/بعد، وسلوك السياسة غير المتغير، والتحقق الصارم، وإدراجها في إيصال العملية التالية.

تتحقق اختبارات الدخول التجريبية من أن قدراتها تختلف عن رمز لوحة التحكم المُهيأ، ولا يمكنها منح الصلاحية لمساحة عمل حية، ولا يمكنها تغيير إعدادات التجميع، ولا يتم إصدارها أو قبولها لطلبات عن بُعد أو مُعادة توجيه أو عبر الأصول أو ذات مضيف غير صالح. لا يؤدي فتح نسخة تجريبية مخزنة دون علامة تجريبية صريحة إلى تمكين الدخول التلقائي.

اجتاز اختبار قبول Chromium **39 سيناريو**، بما في ذلك الدخول إلى العرض التوضيحي المحلي دون إدخال رمز، وإعدادات المراقبة المسبقة، والانتقال من اختيار المصدر إلى السياسة، واستقلالية كل حساب على حدة، وفحص تخطيط سطح المكتب/320/390 بكسل وتباين النص. لم تكن هناك أخطاء في جافا سكريبت بالصفحة. تظل طلبات المضيف التي تم إدخالها بواسطة AdGuard في السجل. سجلت أداة HTTP للتنزيل إعادة تعيين الاتصال بعد أن قام العميل بإغلاق اتصاله؛ ولا تزال الاختبارات ناجحة. هذه النتيجة ليست من خدمة حية.

قام المشغل العادي بترقية البيئة المعزولة إلى الإصدار 0.5.0؛ وتتطابق الإصدارات المصدرية والمثبتة، وقد اجتازت عملية التحقق باستخدام pip. اجتازت مجموعة الاختبارات الكاملة اختبارات تشفير خزينة الأسرار الحالية، ورفض المفاتيح الخاطئة أو المفقودة، واختبارات التلاعب بالتوقيعات والملفات الوسائطية. لم يُعلن عن أي تشفير جديد لمحتوى الرسائل أو المرفقات من قِبل التطبيق.

يتم إعادة تشغيل العرض التوضيحي المحلي لإتاحة واجهة المستخدم المحدثة. يتم الاحتفاظ بالسجلات الاصطناعية الموجودة؛ ويؤدي إيقاف عملية العرض التوضيحي القديمة التي تعمل في الخلفية إلى إنشاء حدود للعمل دون اتصال بالإنترنت عند التشغيل التالي. لا يتم استخدام أي جلسة Telegram حقيقية لإجراء هذه الفحوصات.

أظهرت لوحة localhost:8787 قيد التشغيل الإصدار 0.5.0، والوصول التلقائي إلى العرض التوضيحي، وعناصر التحكم الخمسة في المراقبة، و33 حدثًا محفوظًا في السجل الاصطناعي. أما عجلة الإصدار 0.5.0 المثبتة بشكل منفصل فقد قدمت جميع موارد اللوحة/الدليل، ورفضت الوصول غير المصادق عليه إلى واجهة برمجة التطبيقات (API) ، وأنتجت ملف ZIP تم التحقق منه يحتوي على 32 حدثًا، سواء بشكل مباشر أو من خلال أداة المساعدة في التنزيل عبر البث. تظل إصدارات حزم وقت التشغيل مثبتة كما تم تسجيلها للإصدار 0.4.

## الإصدار 0.4.0

اجتازت مجموعة الاختبارات الكاملة المثبتة أثناء التشغيل: **78 اختبارًا ناجحًا، واختبار واحد تم تخطيه**، في 19.77 ثانية. يتطلب الاختبار الذي تم تخطيه أذونات POSIX؛ ولا يزال تحذير إهمال Starlette TestClient من المصدر الأصلي قائمًا. تغطي الاختبارات الجديدة التنزيل المتدفق/توجيه مساحة العمل، رؤوس التفويض، رفض الكتابة فوق الملفات، عمليات إعادة التوجيه، الاستجابات المقطوعة، حدود الحجم المعلن/الفعلي، القراءات المحدودة، التنظيف، أنظمة الملفات بدون روابط ثابتة، حالات فشل الاستعداد، وأنماط المشغل التي يجب ألا تقوم بتثبيت الحزم. تؤكد اختبارات التصدير وجود الملفات المؤقتة المحلية لمساحة العمل والتنظيف الانتقائي للملفات اليتيمة.

اجتاز اختبار التوافق مع Chromium جميع السيناريوهات الـ36 المدرجة دون أي أخطاء في جافا سكريبت بالصفحة. ويقوم بإجراء عمليات محاكاة لتسجيل الدخول عبر الهاتف/الرمز/التوثيق الثنائي (2FA)، والجلسات المحولة، ومساحتين عمل، و مسارات/حالات منفصلة، والملاحظات، والتوقيعات، ونقاط التفتيش، وطلبات الطابع الزمني، بالإضافة إلى:

- تصميمات لأجهزة سطح المكتب وبدقة 320/390 بكسل، دون تجاوز أفقي، مع عناصر تنقل واضحة، وحقل تسجيل الدخول الأول ضمن نافذة العرض الأولية التي تبلغ 844 بكسل.
- تباين النص مع الخلفية الصلبة وفقًا لعتبات النص WCAG AA. تم استبعاد عناصر التحكم المعطلة، والعتامة، وخلفيات الصور/التدرجات اللونية؛ فهذه ليست مراجعة كاملة لمعايير WCAG.
- استجابة تصدير محلية حقيقية تمت كتابتها من خلال محاكي لاختيار الملفات/الكتابة في نظام التشغيل (OS)، تليها عملية تحقق مستقلة من ملف ZIP؛ ولا يؤدي الإلغاء إلى إرسال أي طلب تصدير.
- يؤدي فشل الكتابة إلى إيقاف العملية؛ حيث يرفض الخيار الاحتياطي سعة 128 ميغابايت الاستجابة المُعلنة ذات الحجم الزائد دون تخصيص حمولة مطابقة.
- الدليل المحلي باللغة الإنجليزية على سطح المكتب وعلى كلا العرضين الضيقين.

لم يتم أتمتة مربع حوار الحفظ في نظام التشغيل وعمليات الكتابة الفعلية على المتصفح التي تبلغ عدة غيغابايت، كما لم تخضع للتحقق. تستخدم اختبارات التنزيل بلغة Python أجزاء محدودة وتركيبات loopback. ولا يزال القبول الكامل للنشر باستخدام Telegram الحقيقي أمرًا منفصلاً.

قام المثبت العادي بترقية `.venv` إلى الإصدار 0.4.0. تتطابق البيانات الوصفية المصدر والمثبتة؛ اجتاز `pip check` الاختبار. أبلغ `python start.py --check --json` عن جاهزيته على مسار اصطناعي جديد دون إنشاء دليل البيانات. ويظل تحذير تخزين المفتاح المحلي صحيحًا: السجلات/الوسائط غير مشفرة بواسطة التطبيق.

تم إنشاء حزمة الإصدار 0.4.0 وتثبيتها في دليل منفصل. تتطابق جميع ملفات التطبيق البالغ عددها 23 ملفًا مع المصدر بايتًا بايتًا. قدمت الحزمة المثبتة لوحة التحكم و الدليل/الموارد باللغة الإنجليزية، ورفضت الوصول غير المصادق عليه إلى واجهة برمجة التطبيقات (API)، وقامت بتصدير ملف ZIP مركب يحتوي على 32 حدثًا اجتاز عملية التحقق. كما جلب أمر التنزيل المتدفق الخاص بها ملف ZIP تم التحقق منه بشكل مستقل من التطبيق المثبت قيد التشغيل.

التوثيق العام والدليل المحلي باللغة الإنجليزية؛ روابط التوثيق المحلي تعمل. قام PowerShell بتحليل قالب مهام Windows، وقامت Python بتحليل ملف plist الخاص بنظام macOS. هذه عمليات تدقيق في بناء الجملة، وليست تنفيذًا للخدمة. لم يتم تسجيل أي مهمة/خدمة. يتضمن تكوين CI الآن فحوصات الجاهزية، لكن CI عن بُعد لم يتم تشغيله هنا.

أظهرت عملية تشغيل المتصفح 0.4 مرة أخرى حقن AdGuard في المضيف وخطأ OSError 10022 في عملية تنظيف مآخذ التوصيل asyncio في نظام Windows. تم اجتياز اختبارات المتصفح؛ ويتم الاحتفاظ بهذه الملاحظات البيئية بدلاً من التعامل معها على أنها سلوك ثابت للتطبيق. فشلت المحاولات الأولية في بيئة الحماية (sandbox) الخاصة بـ OpenSSL/المتصفح/pip؛ أما عمليات التشغيل المؤهلة الناجحة فقد استخدمت تنفيذًا معتمدًا خارج بيئة الحماية.

## الإصدار 0.3.0

اجتازت مجموعة برامج التشغيل المثبتة بالكامل: **61 اختبارًا**، مع تحذير واحد من Starlette TestClient في النسخة الأصلية بشأن إيقاف استخدامها. تشير بيانات التعريف الخاصة بوقت التشغيل إلى TgWitness 0.3.0 و python-socks 2.8.2؛ واجتازت عملية فحص pip. اجتازت عملية اختبار التوافق مع المتصفح دون أي أخطاء في جافا سكريبت بالصفحة.

تم إنشاء عجلة الإصدار 0.3.0 وتثبيتها في دليل حزم منفصل. وقد قدمت الخدمة للوحة التحكم والأصول، ورفضت طلب API غير مصدق، وقامت بتصدير سجل تركيبي مكون من 32 حدثًا اجتاز التحقق المستقل. تم حل روابط الوثائق المحلية. بعد تصحيح تطبيع المفتاح العاري في MTProxy، أُعيد تشغيل جميع اختبارات الاتصال/الأمان التسعة بنجاح.

تشمل التغطية الجديدة ما يلي:

- اسم المستخدم/كلمة المرور لـ SOCKS5 و HTTP CONNECT عبر خوادم اختبار loopback فعلية؛ يفشل الوكيل المُهيأ غير النشط بدلاً من اللجوء إلى الوجهة.
- التحقق من صحة الوكيل، واختيار وسيلة النقل MTProxy، ورفض أسرار TLS المزيفة، والاستمرارية، وعزل مساحة العمل، ورفض التغييرات أثناء المراقبة، واستبعاد الأسرار من حالة واجهة برمجة التطبيقات (API) والأحداث الموقعة.
- تحويل للقراءة فقط لمخططات Telethon SQLite الاصطناعية 7 و8؛ دون تغيير في تجزئة المصدر؛ ورفض التنسيقات الأخرى، وطرق عرض SQL، وملف WAL المعلق.
- المفتاح الرئيسي للخزينة الخارجية: مفاتيح مساحة عمل مشتقة مختلفة، وإعادة فتح ناجحة، ورفض المفاتيح الخاطئة أو المفقودة، وعدم وجود ترحيل ضمني للخزائن المحلية الموجودة.
- إعدادات الوكيل في المتصفح، ومسح بيانات الاعتماد، والإفصاح عن حماية التخزين، وصفحة الاتصال عبر الهاتف المحمول، وتفويض ملفات الجلسات المحولة، والمسارات المنفصلة، وجميع سيناريوهات التجميع/التصدير التي تمت تغطيتها سابقًا باستخدام عميل Telegram مزيف.

أثناء التطوير، انتظر اختبار التكرار (loopback) إلى أجل غير مسمى إغلاق النظير؛ بينما لاحظت تجربة أخرى إعادة تعيين اتصال Windows بعد المصافحة. يقوم الجهاز الآن بتحديد التبادل بأكمله ويعامل EOF/إعادة التعيين بعد اكتمال المصافحة على أنه إغلاق للاتصال. لا تزال تأكيدات المصافحة/المصادقة مطلوبة. وهذا لا ينطبق على مزودي البروكسي الحقيقيين ولا يشير إلى وجود عيب ثابت في نقل Telegram.

لا تزال ملاحظة طلب AdGuard الموضحة أدناه سارية. لم يتم استخدام أي حساب Telegram حقيقي، أو وكيل SOCKS/HTTP خارجي، أو خادم MTProxy نشط. MTProxy هو برنامج تجريبي وقد تم التحقق من خياراته المحددة/التحقق من صحة الأسرار، وليس التشغيل البيني الفعلي. تم اختبار أوامر جديدة لتحويل المفاتيح الخارجية والجلسات باستخدام أسرار اصطناعية فقط. لا تزال أنظمة Linux/macOS/Docker غير مؤهلة هنا.

لم يتم تكرار قياس معدل النقل 0.2 الوارد أدناه ويجب عدم تقديمه كمقياس أداء جديد متعدد الحسابات/البروكسي للإصدار 0.3.

## ملاحظات بيئية

أدت قيود بيئة الحماية (sandbox) في نظام Windows إلى حظر الدلائل المؤقتة الافتراضية لـ pytest/pip والعملية الفرعية لـ Playwright. استخدمت Pytest دليلًا مؤقتًا جديدًا داخل المشروع؛ وتطلبت عمليات التثبيت والمتصفح تنفيذًا معتمدًا خارج بيئة الحماية.

قام برنامج AdGuard المثبت على الجهاز بإدخال طلبات إلى local.adguard.org في المتصفح. ويحتفظ سجل المتصفح بهذه الطلبات. **ولا** يُعد هذا الاختبار دليلاً على عدم وجود أي طلبات صادرة في بيئة متصفح غير معدلة؛ حيث لا يحتوي مصدر التطبيق نفسه على أي طلبات خارجية تتعلق بالموارد أو شبكات توزيع المحتوى (CDN) أو التحليلات. ولم يتم تغيير إعدادات AdGuard.

كما سجل التشغيل النهائي للمتصفح خطأ OSError 10022 في عملية تنظيف مآخذ التوصيل asyncio في نظام Windows. اجتازت جميع اختبارات المتصفح ولم تحدث أية أخطاء في جافا سكريبت بالصفحة. لم يتم تحديد سبب هذا الخطأ، ولا يُثبت هذا التشغيل عدم وجود مشكلات في نقل البيانات من المضيف.

واجه أول اختبار HTTP للحزمة المثبتة باستخدام طلبات إغلاق الاتصال في urllib عمليات إعادة تعيين للاتصال، سواء داخل صندوق الحماية أو خارجه، ومع كلتا مجموعتي التبعيات. استخدم الاختبار النهائي اتصالات HTTP/1.1 الدائمة القياسية عبر http.client ونجح. كما اجتازت طلبات المتصفح الاختبار. لم يتم تحديد السبب الدقيق لعمليات إعادة الضبط؛ ولم يتم تصنيفها على أنها عيب ثابت في التطبيق.
