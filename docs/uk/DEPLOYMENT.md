# Розгортання та експлуатація

## Вибір інсталяції

Щоб отримати портативний пакет, розпакуйте файл `TgWitness-<version>-windows-amd64-portable.zip` з
GitHub Releases. Для інших способів завантажте та розпакуйте ZIP-файл з вихідним кодом або клонуйте
репозиторій, а потім виконайте наступну команду з каталогу проекту:

| Встановлення | Почати | Працює у фоновому режимі? |
| --- | --- | --- |
| Портативний пакет для Windows | `TgWitness.cmd` | Ні; залиште вікно відкритим. |
| Вбудовані в Windows | `Start.cmd` | Ні; для роботи у фоновому режимі скористайтеся додатковим завданням входу в систему. |
| Вбудована підтримка Linux/macOS | `sh start.sh` | Ні; для роботи у фоновому режимі використовуйте systemd/launchd. |
| Docker на будь-якому підтримуваному хості | `docker compose up -d --build --wait` | Так, поки працює демон Docker. |
| Допоміжна програма Docker для Windows | `scripts\Docker.cmd` | Так; допоміжний процес відстежує працездатність веб-сервера. |
| Допоміжна програма Docker для Linux/macOS | `sh scripts/docker-start.sh` | Так; допоміжний процес відстежує працездатність веб-сервера. |

Щодо хмарного сервера, доступ до якого має мати можливість перевірити третя сторона — створеного за допомогою
API провайдера, без SSH, доступ до якого можливий лише через Cloudflare Tunnel — див.
[розгортання з високим рівнем безпеки](../HIGH-ASSURANCE.md).

Вбудований запуск створює приватний образ `.venv` та встановлює закріплені залежності.
Docker компілює їх усередині образу, не потребуючи Python на хості. Для первинного
налаштування потрібен доступ до Інтернету. Якщо Python 3.11+ не знайдено, `Start.cmd` запитує до
встановлення Python 3.12 для поточного користувача Windows (winget, або інсталятор з python.org
після перевірки підпису Python Software Foundation); він ніколи не вимагає
прав адміністратора. Docker та служби ОС залишаються обов’язковими вимогами.

Нативні та портативні інсталяції використовують `data/live` у своїх папках. Docker використовує том із назвою `tgwitness-data`,
розташований за адресою `/data`. Це окремі інсталяції, доки ви свідомо не перенесете
весь каталог даних. Не варто очікувати, що новий контейнер Docker автоматично виявить нативні
облікові записи.

## Вимоги до інсталяції

Для нативної інсталяції потрібні Python 3.11 або новішої версії з `venv` та `ensurepip`, доступ до Інтернету
для встановлення першої залежності, а також каталог проєкту з правом запису для
`.venv`. Вбудована панель не потребує Node.js чи компіляції інтерфейсу. Запустіть програму-запускач зі
свого звичайного облікового запису в ОС; TgWitness не вимагає прав адміністратора чи root.

- **Windows:** `Start.cmd` перевіряє `py -3`, потім `python`, потім папки за замовчуванням для користувача та
  папку «Program Files», і вимагає версії 3.11 або пізнішої. Якщо жодна з них не працює,
  пропонується автоматична інсталяція для користувача, описана вище. `py -3 start.py` також працює.
  Портативний пакет взагалі не потребує Python.
- **Linux:** `start.sh` перевіряє `python3.13`, `python3.12`, `python3.11`, `python3` та
  `python` і виводить команду встановлення для apt, dnf, pacman, zypper, apk або Homebrew,
  якщо жодна з них не підходить. Для встановлення в Debian/Ubuntu може знадобитися пакет
  `python3-venv`, що відповідає обраному інтерпретатору. Стару версію Python, що встановлена за замовчуванням у дистрибутиві,
  необхідно замінити або доповнити Python 3.11+.
- **macOS:** встановіть актуальну версію Python 3.11+; не вважайте, що інтерпретатор, наданий ОС,
  відповідає вимогам. Використовуйте `python3 start.py` з каталогу проєкту.
- **Docker:** використовуйте Docker Engine/Desktop із Compose v2.20 або новішою версією. Docker Desktop
  повинен використовувати контейнери Linux у Windows. Контейнер встановлює свої
  власні залежності Python; на хості не потрібна окрема інсталяція Python.

## Локальний комп’ютер

У Windows використовуйте `Start.cmd`, а в Linux/macOS — `sh start.sh`. `scripts\Setup.cmd` або
`sh start.sh --setup-only` готують
середовище. Програма запуску встановлює необхідні залежності під час першого використання; під час наступних запусків
використовується вже готове середовище. Для налаштування та збору даних із Telegram потрібен доступ до Інтернету,
але перегляд наявних записів та створення експортних файлів можливі в автономному режимі.

Після налаштування запустіть `python start.py --check`, щоб перевірити локальні залежності, Ed25519,
сховище, конфігурацію ключів та адресу прослуховування без запуску колектора.
Використовуйте `--json` для структурованого виводу. Передайте потрібні `--data-dir`, `--host` та
`--port`. Ця перевірка не встановлює пакети, не створює журнал і не підключає Telegram;
це не є перевіркою цілісності чи охоплення. Процес запуску окремо перевіряє
існуючі журнали. `python start.py --help` також уникає встановлення.

Після запуску start.py виконайте допоміжні команди за допомогою `.venv\Scripts\python.exe` у
Windows або `.venv/bin/python` у Linux/macOS, або спочатку активуйте це середовище.
У наведених нижче прикладах `python -m ...` передбачається, що середовище вже активне.

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

Змінні середовища: TGWITNESS_DATA, TGWITNESS_HOST, TGWITNESS_PORT, TGWITNESS_TOKEN.
TGWITNESS_VAULT_KEY_FILE вибирає режим зовнішнього ключа для нової інсталяції; див. [Зовнішній головний ключ](../SECURITY-MODEL.md#external-master-key).
TGWITNESS_TOKEN, якщо вказано, має містити щонайменше 24 символи; використовуйте криптографічно
випадкове значення. Без нього програма генерує 256-бітний випадковий токен у файлі panel-token.txt.
Перезапис параметрів середовища не змінює цей файл. Перезапустіть систему, щоб оновити облікові дані.

Каталог даних може належати лише одному процесу. Міжплатформова блокування файлів ОС запобігає
випадковим паралельним операціям запису. Використовуйте один робочий процес Uvicorn. Панель може керувати будь-якою кількістю
робочих просторів, додаткові каталоги яких розміщуються в папці profiles/<id>/.
Для окремих екземплярів сервісу використовуйте окремі каталоги та порти. Файли WAL SQLite повинні зберігатися у локальному постійному
сховищі, а не в мережевій файловій системі. Не використовуйте один том для декількох реплік.

## Портативний пакет для Windows

Кожен реліз на GitHub містить `TgWitness-<version>-windows-amd64-portable.zip` та його
`.sha256`. Він містить офіційне вбудовуване середовище виконання Python 3.12 з python.org
(контрольна сума вказана в `tools/build_portable.py`), TgWitness та його зафіксовані залежності,
а також три програми запуску:

| Файл | Мета |
| --- | --- |
| `TgWitness.cmd` | Запустити панель; додаткові параметри передаються, наприклад, `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | Запустити демонстрацію синтезу в `data\demo` |
| `TgWitness-Check.cmd` | Виконайте перевірку готовності без запуску |

Закріплений російський словник морфології та профілі кольорів у форматі PDF включені до пакету для
використання в автономному режимі. Упаковка допускає лише відомі шляхи до цих файлів у каталогах залежностей
`data`; наявність несподіваних файлів у цих каталогах призводить до збою збірки.

Розпакуйте весь архів у папку з правами на запис, наприклад `Documents\TgWitness`; не запускайте
програму безпосередньо з архіву ZIP або з папки «Program Files». Середовище виконання використовує ізольований шлях до модулів,
тому інші інсталяції Python та `PYTHONPATH` не впливають на його роботу. Дані зберігаються у
папці `data` цього пакету. Щоб оновити програму, зупиніть TgWitness, розпакуйте нову версію в нову
папку та скопіюйте туди папку `data`.

Зберіть його самостійно на 64-бітній версії Windows із Python 3.12:

~~~sh
python tools/build_portable.py
~~~

## Контейнер

```sh
docker compose up -d --build --wait
```

Це створює іменований постійний том для /data.
Веб-порт прив'язано до 127.0.0.1:8787. Процес працює під UID 10001 із обмеженими
правами, кореневою файловою системою тільки для читання та каталогами /data і /tmp, доступними для запису.
`--wait` перевіряє працездатність веб-сервера перед поверненням; авторизація та
доставка повідомлень у Telegram відображаються на панелі. Надані допоміжні програми використовують 180-секундний тайм-аут готовності
після побудови. Початкове завантаження залежностей може тривати довше.

Обидва базові файли Compose використовують назву проєкту `tgwitness`, тому розпакування нового релізу
в інший каталог не призведе до автоматичного вибору нового тома даних. Залишайте активним лише одне
розгортання для цього проєкту. Для незалежних інсталяцій використовуйте унікальний
`docker compose -p NAME ...` та інший порт хоста, і зберігайте обидва під час оновлень.
Для старішого розгортання, що використовує іншу назву проєкту, продовжуйте використовувати його оригінальну
назву з `-p`; `docker compose ls` містить перелік існуючих проєктів.

Скопіюйте `deploy/env.example` у `.env` та змініть `TGWITNESS_PORT`, щоб використовувати інший порт
петлі зворотного зв’язку. Наприклад, `TGWITNESS_PORT=8788` відкриває доступ до панелі за адресою
`http://127.0.0.1:8788`; контейнер, як і раніше, слухає на порту 8787. `.env` ігнорується Git.

Отримати початковий токен:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

Корисні команди:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` перезапускає колектор після збою або перезапуску демона Docker.
На сервері під управлінням Linux увімкніть Docker під час завантаження за допомогою менеджера служб вашого дистрибутива,
зазвичай це `sudo systemctl enable --now docker`. У Windows/macOS увімкніть
параметр «Запускати під час входу» у Docker Desktop. Вихід із системи, перехід у режим сну або зупинка
демона Docker можуть перервати збір даних. Явно зупинений контейнер залишається
зупиненим, доки ви його знову не запустите.

У наведеному прикладі конфігурації обсяг тома /tmp обмежено 512 Мб. Процес експорту
замість цього використовує елемент `temporary-exports/` кожного робочого простору на постійному томі /data. Зарезервуйте там місце
для одночасних експортів, зростання журналу/WAL, мультимедіа та резервних копій.
Програма запуску використовує файл deploy/constraints.txt для фіксації відповідних версій залежностей середовища виконання.
Docker та сервери з високим рівнем безпеки встановлюються на основі файлів deploy/requirements.lock та
deploy/build.lock за допомогою команди pip --require-hashes: кожен файл пакета повинен відповідати SHA-256,
зафіксованому у коміті, тому файл, замінений на PyPI або дзеркалі, відхиляється. Пакеті, які
поставляються лише у вигляді вихідного коду (jieba, pyaes), компілюються з використанням setuptools, зафіксованих у файлі deploy/build.lock
(`--no-build-isolation`) запускачем, портативним компілятором для Windows та файлом Dockerfile,
тож pip не визначає окреме, незафіксоване середовище компіляції. Базовий образ Python
та пакети операційної системи все ще потребують незалежної кваліфікації для випуску.

Не використовуйте команду `docker compose down -v`, якщо ви не маєте наміру знищити журнал та ключі.
Звіт про стан контейнера відображає доступність веб-сервера, а не успішне отримання даних із Telegram.
Перевірте стан колектора панелі, сигнал активності, помилки та події охоплення.

### Профіль незалежного свідка

Опціональна служба `witness` запускає [незалежного свідка](../WITNESS.md) у власному
контейнері, з власним ключем та журналом у томі `witness-data`, а також лише токеном свідка, доступним лише для читання,
для колектора. Створіть токен у панелі в розділі **Додаткові інструменти → Додаткові функції → Незалежний свідок**, додайте його
разом із токеном бота та каналом до `.env`, а потім запустіть профіль:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

Ця служба звертається до колектора всередині мережі Compose за адресою `http://tgwitness:8787`
(`TGWITNESS_WITNESS_COLLECTOR`
замінює її, наприклад, `/profiles/<workspace ID>`
для
іншої робочої області). Для свідка на окремому сервері, який адмініструється кимось іншим, використовуйте
`deploy/compose/compose.witness.yaml`
, встановивши для `TGWITNESS_WITNESS_COLLECTOR`
HTTPS-адресу колектора;
цей файл містить лише свідка.

## Встановлення опублікованого образу

Скопіюйте `deploy/env.example` у `.env`. Встановіть для `TGWITNESS_IMAGE` опубліковану версію, використовуючи
шлях до репозиторію **малими літерами**, наприклад:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:1.0.1
TGWITNESS_PORT=8787
```

Запустіть цей файл окремо, замість `compose.yaml`:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

На хост-комп’ютері не потрібно виконувати збірку з вихідного коду, Python чи компілятор. Робочий процес випуску
розрахований на контейнери Linux AMD64 та ARM64, зокрема на віртуальну машину Linux у Docker Desktop.
Використовуйте тег версії або `ghcr.io/owner/repository@sha256:...` із підсумкової інформації про робочий процес.
Не налаштовано переміщення тегу `latest` або автоматичне оновлення додатків.
Образ та варіанти вихідного коду використовують один і той самий том даних, якщо назви їхніх проєктів збігаються.

## Автоматичний HTTPS на сервері

Використовуйте сервер із Docker, домен, який ви контролюєте, та постійне локальне сховище.
Направте записи A/AAAA домену на сервер; публікуйте AAAA лише в тому випадку, якщо до нього надходить IPv6.
Дозвольте вхідний трафік по TCP 80 та 443, а також вихідний трафік DNS/HTTPS для видачі сертифікатів.
Ці порти не повинні бути зайняті іншими службами.

Скопіюйте `deploy/env.example` у `.env` та вкажіть ім’я хосту без схеми та шляху:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

Запустіть збірку вихідного коду з використанням HTTPS-оверлею:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

Для опублікованого зображення замість цього використовуйте `deploy/compose/compose.image.yaml` як перший файл. Збережіть
обидва аргументи `-f` для подальших команд status, logs, update та stop.

Caddy отримує та оновлює сертифікат, перенаправляє HTTP на HTTPS і пересилає
запити до колектора у приватній мережі Compose. Стан сертифіката зберігається
у власному постійному томі. Порт хоста колектора залишається доступним лише для локальних з’єднань.
У наданій конфігурації Caddy не ввімкнено ведення журналу доступу.

Відкрийте `https://watch.your-domain.org` та введіть токен панелі. Готовність до створення
поширюється на контейнери; видача сертифікатів та доступність іззовні залежать від DNS
та брандмауера. Якщо HTTPS не готовий, перевірте DNS, правила брандмауера, а також:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

Надане зображення Caddy розміщене після тегу `2-alpine`. При завантаженні це зображення оновлюється;
якщо вам потрібні фіксовані версії інфраструктури, зафіксуйте перевірений дайджест у вашому розгортанні.

## Оновлення та резервні копії

Збережіть назву проєкту Compose та обсяг даних під час оновлень. Спочатку зупиніть
колектор і створіть повну резервну копію. Для розгортання на основі джерела за замовчуванням:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

Щоразу використовуйте нове місце для резервного копіювання, розташоване поза репозиторієм, і захищайте його як
матеріал, доступ до якого обмежений обліковим записом. Наведений приклад шляху є ілюстративним; використовуйте власне приватне
місце для резервного копіювання. Скопіюйте весь каталог, включаючи приховані файли, усі робочі простори, ключі,
журнали та мультимедійні файли. Якщо це налаштовано, окремо створіть резервну копію головного ключа зовнішнього сховища.
ЗIP-архів з доказами не є резервною копією програми, яку можна відновити. Для HTTPS також збережіть
томи Caddy, якщо вам потрібно зберегти стан його сертифіката/облікового запису.

Для розгортання з вихідного коду завантажте файли нової версії та виконайте наступну команду:

```sh
docker compose up -d --build --wait
```

Щоб розгорнути зображення, змініть `TGWITNESS_IMAGE` на потрібну версію, а потім виконайте:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

Використовуйте файл(и) Compose вашої інсталяції також для наведених вище команд зупинки та копіювання.
Збережіть `.env`, власні налаштування та ту саму назву проєкту. `down` зберігає іменовані
томи; **`down -v` видаляє їх**. Не копіюйте `.venv` між операційними системами
або версіями Python. Для оновлення нативного коду зупиніть TgWitness, створіть резервну копію всього його каталогу даних
, замініть вихідні файли та запустіть `python start.py --setup-only` перед запуском.

Після оновлення перевірте доступ до панелі, ідентифікацію облікового запису, стан спостереження та
обсяг покриття. Після перезапуску TgWitness відновлює збережену позицію оновлення Telegram і
запитує оновлення, пропущені під час оновлення. Для відкату може
знадобитися резервна копія, створена до оновлення, якщо в майбутній версії зміниться формат зберігання даних.

## Віддалений сервер

Забезпечте прив’язку служби до петлі зворотного зв’язку та використовуйте SSH-тунель, або завершуйте HTTPS на
зворотному проксі. Базовий файл Compose призначений лише для локального використання; додатковий оверлей
`deploy/compose/compose.https.yaml` забезпечує роботу Caddy для налаштованого домену.
Не вказуйте токен носія в URL-адресах та журналах проксі-сервера. Зворотний проксі-сервер повинен обмежувати
розмір запитів та частоту з’єднань. Не відкривайте доступ до простого HTTP в Інтернеті.

Приклади для systemd, завдання входу в систему Windows, агента користувача macOS та Caddy наведено
у папці [deploy/](../../deploy/README.md). Перед встановленням перевірте та адаптуйте їхні шляхи.
Це лише шаблони, а не локально виконувані налаштування платформи. Звичайний запускач не
реєструє жодних фонових служб чи завдань.

У Windows під час запуску безвіконного режиму `pythonw.exe` дані діагностики запуску та сервера зберігаються у
`logs/server.log` у каталозі даних (5 МіБ на файл, дві чергові резервні копії).
Під час запуску в консольному режимі зберігаються записи консолі. Реєстрація доступу по HTTP вимкнена в обох
режимах. Захищайте журнали разом із каталогом даних і перевіряйте їх перед тим, як надавати доступ.

## Перезапуск і прогалини

Останній запитуваний стан спостереження зберігається. Якщо спостереження було активним,
під час запуску система намагається відновити з’єднання та продовжити спостереження за вибраними джерелами. Ручна пауза скасовує
цю дію. Невдалий перезапуск реєструється та відображається на панелі.

TgWitness зберігає дані про стан оновлень Telegram для облікового запису та кожного каналу
(pts, qts, seq та date) у сховищі робочого простору та відновлює їх під час наступного запуску.
Потім клієнт запитує оновлення, пропущені під час зупинки процесу, а
періодична повторна перевірка відновлює пропущені повідомлення та фіксує збережені, які Telegram
більше не повертає. Діалоги перезавантажуються під час запуску. Кожен запуск фіксує попередню
головку журналу, межу офлайн-режиму та позицію оновлення, з якої відбулося відновлення.
Монітор перевіряє підключення кожні 10 секунд і додає сигнал активності щохвилини
(**Більше інструментів → Параметри → Запис активності кожні**).
Втрати з’єднання та періоди мовчання фіксуються як прогалини у покритті з зазначенням причини.
Знімки історії зберігаються як окремі спостереження поточної історії поруч із записами в режимі реального часу.

Черга медіафайлів зберігається в базі даних SQLite кожної робочої області. Повідомлення та відповідне завдання
фіксуються атомарно. Перервані завдання відновлюються для повторної спроби під час запуску.
Кожне завантаження має базовий тайм-аут у 120 секунд плюс час, необхідний для завантаження файлу розміром 256 КіБ/с, а також
обмеження у 1–2 000 МіБ на тип вкладення; тайм-аут, швидкість та кількість повторних спроб налаштовуються у розділі **Додаткові інструменти → Параметри**. Колектор
пропускає файли, розмір яких невідомий. Призупинення зберігає завдання в черзі. Повторна спроба використовує оригінальний
спостережуваний дескриптор файлу, а не останню версію повідомлення, яке було відредаговано згодом.
Тимчасові збої мають обмежену кількість повторних спроб; паузи FloodWait для медіа зберігаються після перезапуску.
Відновлення медіа є окремим від відновлення оновлень Telegram і не може відтворити зниклі файли.

## Резервне копіювання, відновлення та ємність

`tgwitness backup FOLDER`
копіює каталог даних, поки панель продовжує працювати:
спочатку контрольні точки, потім файли SQLite через API онлайн-резервного копіювання, а потім ключі, мультимедіа та
профілі, завдяки чому жодна скопійована контрольна точка не є новішою за скопійований журнал. `backup-manifest.json`
містить перелік SHA-256-хашів усіх файлів та заголовків журналів. Для відновлення зупиніть TgWitness і замініть
весь каталог даних цією папкою. Під час наступного запуску фіксується, що журнал було відновлено
зі старішої копії. Цей запис порівнює журнал із заголовком, що зберігається в
`TGWITNESS_STATE_DIR`
— папці поза каталогом даних: на томі `tgwitness-state`
у
Compose, `/var/lib/tgwitness-state`
у модулях systemd, а в інших випадках — у локальній папці стану користувача
. Без папки стану з правом запису відновлення не виявляється, і про це один раз повідомляється у журналі.

Якщо ця команда відсутня, зупиніть процес перед копіюванням **усього каталогу даних**, включаючи файли vault.key,
signing.enc, credentials.enc, файли бази даних SQLite та WAL, мультимедійні файли, токен, контрольні точки,
а також усі підкаталоги profiles/. Відновіть
повну копію, коли служба призначення зупинена. Відсутність ключів сховища або
невідповідність ключів підпису призведе до збою запуску; не створюйте ключі заново, щоб примусово отримати доступ.

Зберігайте резервні копії в таємниці, зашифрованими та з контролем доступу. ZIP-файли з доказами — це портативні
артефакти для перегляду, а не резервні копії додатків чи сеансів Telegram.
Автоматичного видалення після закінчення терміну зберігання не відбувається. Заплануйте місце на диску для всіх повідомлень, необроблених
метаданих, мультимедійних файлів, тимчасових експортів та резервних копій.

Перевірка запуску та експорт записів потоку замість завантаження всього журналу.
Експорт фіксує знімок стану на момент зчитування, тоді як нові записи в WAL можуть продовжуватися; тривалі процеси експорту
можуть зберігати сторінки WAL, тому ємність диска все ще має значення. Розмір ZIP-архівів обмежено 4 ГіБ
у нестисненому вигляді, щоб відповідати стандартним налаштуванням незалежного верифікатора; **Більше інструментів → Параметри → Найбільший підписаний ZIP**
збільшує обмеження, і такі архіви перевіряються за допомогою `verify.py --max-gib N`. Інші формати не мають обмеження на кількість подій.
Підтримувані браузери передають фрагменти відповіді у потоковому режимі до файлу, обраного користувачем. Інші браузери
буферизують не більше 128 MiB і перенаправляють передачі більшого розміру до авторизованого CLI:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

Використовуйте `--profile ID` з розділу **Експорт → Ідентифікатор робочої області** для іншої робочої області,
`--format zip|jsonl|csv|html`, `--url https://your-server` для віддаленого сервера або
`--max-mib`, щоб змінити обмеження на передачу даних у 5 ГіБ. Звичайний HTTP дозволено використовувати лише для
петлевого з’єднання. Токени передаються в заголовках, перенаправлення відхиляються, існуючі файли
не перезаписуються, а незавершені завантаження не публікуються як завершені файли.
Якщо TGWITNESS_TOKEN замінює згенерований токен, використовуйте окремо захищений файл,
що містить це активне значення: файл panel-token.txt не перезаписується під час заміни.
SHA-256 команди є лише контрольною сумою передачі; незалежно перевірте підписаний ZIP-файл.

На панелі відображаються медіафайли в черзі/з помилками, найстаріші медіафайли в очікуванні, вільний простір на диску, паузи запитів Telegram
та джерела, доступ до яких не підтверджено. Ці діагностичні дані не є
повноцінним монітором доставки «від кінця до кінця». Робочі простори використовують спільний процес; обліковий запис із великою кількістю запитів може
все одно впливати на інші. Залишаються окремі робочі процеси, зберігання/ротація, відновлення стійких оновлень
та повна кваліфікація розгортання. Доступ до панелі з обмеженим обсягом повноважень описано
у розділі [доступ та дозволи](../ACCESS.md); незалежні контрольні точки висвітлено у
[посібнику для свідків](../WITNESS.md).

Детальні інструкції: [підключення/безпека](../CONNECTION-SECURITY.md) та
[режими роботи](../OPERATIONS.md).
