证据与信任

导出数据、视频、网页存档和签名记录能证明什么，以及采集设备如何影响其可靠性。

导出文件、屏幕截图或录音均可作为有用证据。其可靠性取决于收集、保存和佐证的方式。有效的哈希值或签名用于验证保存的材料；但不能独立证明收集设备接收到了真实的源内容。此界限同样适用于TgWitness。

本指南将技术验证与法律评估区分开来。产品文档及下文所述的法律条款已于 2026 年 11 月 1 日进行审核；Hunchly 的对比分析描述的是其已发布的文档，而非针对新产品的审计。

信任在捕获过程中的作用#

此处的威胁模型假设攻击者或操作员可以在证据提交之前篡改收集环境。这是一项条件性分析，并非声称特定设备或产品已遭到入侵。

官方客户端和加密连接有助于保护正常使用。它们并不能使周围的操作系统、浏览器或显示设备本身变得值得信赖。如果内容在解密后但捕获前被替换，导出者仍能准确保存该内容，签名者也能正确对其签名。这两项操作均无需依赖有缺陷的哈希算法或伪造的签名。

在同一设备上制作的视频可以记录相同的替换后的显示内容。 另一台相机可以确认显示屏上显示的内容，但仅凭显示屏本身 无法验证 Telegram 提供的内容。同样，来自同一受控环境中的匹配 HTML、JSON、 屏幕截图和浏览器日志可能存在相同的 错误。它们的一致性是有用的背景信息；但这并不自动构成独立的 佐证。

Telegram 将其桌面版导出功能描述为离线 HTML/JSON 副本，并将 Takeout API 描述为检索选定账户数据的一种方式。这些描述并未提供最终导出存档的 Telegram 签名供接收方验证。我们的结论仅限于这些已记录的导出机制；这并非主张 Telegram 证据不具有法律价值。Telegram 桌面版导出，Takeout API。

同样的区分原则也适用于后台请求、缓存条目和网络 日志。它们可能揭示不一致之处，并有助于佐证数据收集。仅凭其 复杂性本身无法确定其生成者。一个独立运营的 存档或单独获取的服务记录提供了不同的来源供 比较，但须受其自身收集和保管限制的约束。

Hunchly 展示了相同的边界#

Hunchly 的文档描述了对 MHTML 截图、照片和附件进行 SHA-256 哈希计算，并附有独立的哈希验证。该文档还解释了为何一个被篡改的文件若附带新计算的哈希值，仍能通过该比对，并指出签名和来源佐证是额外的验证手段。Hunchly：内容、照片和附件的哈希计算。

其发布的《证据指南》（2018年10月17日修订版1.0）描述了针对MHTML捕获的 本地生成的GPG密钥和签名。该指南明确指出 访问本地私钥是重新对修改后的材料进行签名的一种方式。这是 已记录的信任限制，并非未披露的当前漏洞的证据。 该指南还指出，Chrome 会执行 MHTML 捕获操作。若将 Hunchly 描述为 仅依赖调查人员的信誉，则会忽略这些技术控制措施。 参见《Hunchly 证据指南》第 2–4 节。

使用特定产品收集的材料是否已被案件采纳，取决于相关裁决和具体情况。我们在此不就法院接受 Hunchly 或 TgWitness 的频率，或这两款产品是否获得法院的普遍认可作出任何声明。

TgWitness 增加了什么，以及其保护范围的界限#

TgWitness 将观察结果记录在经过签名且包含链接的日志中，并提供 接收方可核查的导出文件。保留的检查点、时间戳以及独立的 见证人，为审核人员提供了超出采集者当前文件范围的参考依据。 这些信息有助于揭示先前已提交记录中的变更。覆盖范围记录和 明确的采集结果有助于说明哪些内容已被捕获、哪些未被捕获。证据格式与移交、采集范围。

可能的替换时机至关重要：

  1. 签名后，若无法访问签名密钥：修改已签名的记录 或与清单绑定的文件，将无法通过可信验证器和密钥的验证。
  2. 使用收集器密钥时，在保留独立检查点后：替换日志可以具有有效的新签名，但如果前缀发生变更，则无法与该早期检查点进行比对。仅保存在同一受控设备上的检查点可随日志一同被替换。超出保留边界的记录需要单独覆盖。
  3. 在涵盖某项观察结果的检查点被独立保留之前：虚假输入可能被成功签名并锚定，包括在早期检查点之后 追加的新记录。生成的检查点或时间戳 仍然涵盖这些虚假记录；但这并不证明其真实性。

TgWitness 见证人接收收集器签署的检查点；它不会独立 读取底层的 Telegram 对话。其密钥和保留的记录必须 分别受到信任。当必须对提交的整个日志进行见证时，请使用需要最终导出边界的交接程序。 普通的完整性验证仍可报告未被见证的尾部内容。

经过验证的 RFC 3161 响应可证明在权威机构声明的时间点存在检查点。但这无法证明 Telegram 消息的发送时间或其内容的真实性。仅凭预先准备的请求或包含的响应文件是不够的。使用tgwitness.verify 验证导出文件时，检查其中包含的 TSA 签名需要通过--tsa-ca 明确信任的 CA。OpenTimestamps 收据需要独立的ots verify 验证，并在必要时进行证明升级。 时间戳流程 ，RFC 3161。

在GitHub Actions 捕获过程中，一个临时托管的运行器会收集 相关消息。认证将存档与经批准的工作流绑定。此模式 仍然依赖于 GitHub、经批准的软件及其依赖项、辅助程序/浏览器 以及隧道。它并非机密硬件、Telegram 签名，亦非证明 无人访问过主机的证据。本地签名的运行收据同样属于 自我报告的测量结果，而非硬件认证。

法律效力取决于其依据#

以下四个问题应保持独立：该项目是否如其所述，提交的字节是否与保留的记录相符，内容是否支持所声称的事实，以及适用规则是否允许其使用。加密校验仅涉及该基础的一部分。

在美国联邦诉讼程序中，《联邦证据规则》第901条规定了认证证据的方式， 包括知情证人的证词以及关于流程或系统的证据。 《联邦证据规则》第902(13)条和第902(14)条为某些电子记录和副本提供了认证途径，并附有程序性要求。其委员会说明将认证与传闻证据、相关性及归属等问题区分开来。仅凭软件签名本身并不构成该规则中所述的合格人员认证。《联邦证据规则》第901条，《联邦证据规则》第902条。

在适用加拿大《证据法》的情况下，第 31.1 条涉及 电子文件的认证。第 31.2 条将最佳证据规则与系统完整性 或适用的推定联系起来；第 31.3 条规定了推定 完整性的情形。这些是明确界定的证据条件，而非一种笼统的推定， 即任何持牌调查员或商业产品都是无懈可击的。 《加拿大证据法》第31.1条、第31.2条、第31.3条。

这些示例并不决定在其他司法管辖区或特定案件中的可采性。技术核查应一致地应用于支持或质疑指控的材料。本指南并不主张控方证据通常比辩方证据更容易被采纳。

准备一份可供他人评估的记录#

  • 描述账户、采集设备、操作员、软件版本、访问权限、选定范围及采集期间。记录中断情况和可能的安全漏洞，而非将成功的签名验证视为设备无感染的测试。
  • 保留原始包并记录传输过程、哈希值及时间来源。通过单独的可信通道保留密钥指纹和检查点。在报告中描述实际见证或时间戳覆盖范围之前，请先进行验证。
  • 寻求与该主张相符的独立佐证：其他参与者的记录、独立截图或依法获取的服务记录。说明其独立性及局限性；仅凭副本之间的一致性尚不足以作为依据。
  • 保留相关上下文。标明被省略的文件、不可用的历史记录和删节部分。必要时准备一份单独的简化披露版本，并描述其转换过程，但不得将其作为完整的原始版本呈现。
  • 向接收方提供验证说明及验证所需材料。确保观察结果、技术发现和分析师的结论能够明确区分。

对于特定的交接，需说明存档哈希值、可信密钥、验证结果以及外部覆盖的确切边界。分别描述来源真实性、账户归属、完整性及法律结论。这将为下一位审阅者提供具体的审查要点。
