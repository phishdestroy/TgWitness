# พยานอิสระ

Canonical page: https://phishdestroy.github.io/TgWitness/th/docs/reference/witness/

เรียกใช้ witness ด้วยกุญแจและบอทของตัวเอง เผยแพร่จุดตรวจสอบที่ลงนามแล้วไปยังช่อง และตรวจสอบการส่งออกข้อมูลกับจุดตรวจสอบดังกล่าว

[TgWitness](https://github.com/phishdestroy/TgWitness/blob/main/README.md) / [เอกสารประกอบ](https://github.com/phishdestroy/TgWitness/blob/main/docs/README.md) · [หลักฐานและการตรวจสอบ](https://phishdestroy.github.io/TgWitness/th/docs/reference/evidence/)

![หลักฐานและการตรวจสอบ](https://phishdestroy.github.io/TgWitness/assets/chapter-evidence.svg)

[ส่งออกและตรวจสอบ](https://phishdestroy.github.io/TgWitness/th/docs/reference/evidence/) · [ความมั่นใจสูง](https://phishdestroy.github.io/TgWitness/th/docs/reference/high-assurance/) · [คู่มือการใช้งานแผงควบคุม](https://phishdestroy.github.io/TgWitness/th/docs/reference/panel/#extras)

Witness เก็บจุดตรวจสอบที่ลงนามไว้แยกจาก collector มันตรวจสอบ ลายเซ็นของ collector และความต่อเนื่องของ journal ลงนามผลลัพธ์ด้วยกุญแจของตัวเอง และ เผยแพร่ไปยังช่อง Telegram ให้ทำงานบนเซิร์ฟเวอร์แยกต่างหากที่มีสิทธิ์เข้าถึงแบบอ่านอย่างเดียว ไปยังจุดปลายทาง witness ของ collector

แผนผังกระบวนการ · Collector → Witness (จุดตรวจสอบที่ลงนาม: จำนวนบันทึก + ค่าแฮชส่วนหัว); Witness → สมุดบันทึกพยาน, กุญแจส่วนตัว; Witness → ช่อง Telegram (โพสต์ที่ลงนามผ่านบอทของระบบเอง); ไฟล์ ZIP ของหลักฐาน → verify.py; สมุดบันทึกพยาน, กุญแจส่วนตัว → verify.py; ช่อง Telegram → verify.py (หน้าส่งออก Telegram Desktop หรือ t.me/s) · Collector · Witness · สมุดบันทึกพยาน,กุญแจส่วนตัว · ช่อง Telegram · ไฟล์ ZIP ของหลักฐาน · verify.py · จุดตรวจสอบที่ลงนาม: · จำนวนบันทึก + ค่าแฮชส่วนหัว · โพสต์ที่ลงนามผ่านบอทของระบบเ · อง · หน้าส่งออก Telegram Desktop · หรือ t.me/s

**แผนภาพในรูปแบบข้อความ**

1. Collector → Witness (จุดตรวจสอบที่ลงนาม: จำนวนบันทึก + ค่าแฮชส่วนหัว)
2. Witness → สมุดบันทึกพยาน, กุญแจส่วนตัว
3. Witness → ช่อง Telegram (โพสต์ที่ลงนามผ่านบอทของระบบเอง)
4. ไฟล์ ZIP ของหลักฐาน → verify.py
5. สมุดบันทึกพยาน, กุญแจส่วนตัว → verify.py
6. ช่อง Telegram → verify.py (หน้าส่งออก Telegram Desktop หรือ t.me/s)

## สิ่งที่ TgWitness สามารถทำได้ และสิ่งที่มันทำไม่ได้

| TgWitness มี | พยานไม่เคย |
| --- | --- |
| **โทเค็นพยาน**แบบอ่านอย่างเดียวสำหรับพื้นที่ทำงานหนึ่งแห่ง | เซสชัน Telegram หรือข้อมูลรับรอง API ของผู้เก็บข้อมูล |
| กุญแจ Ed25519 และบันทึกของตัวเอง | ห้องเก็บรักษาข้อมูลของระบบเก็บรวบรวม, กุญแจลงนาม หรือ โทเค็นแผงควบคุม |
| โทเค็นบอท Telegram ของตัวเอง | เนื้อหาข้อความ: ส่วนหัวประกอบด้วยจำนวนบันทึกและค่าแฮช |

โทเค็นถูกสร้างขึ้นใน **Extras → Independent witness**, แสดงขึ้นเพียงครั้งเดียวและเก็บไว้เพียงในรูปแบบ SHA-256 เท่านั้น มันเปิดจุดปลายทาง (endpoint) เพียงหนึ่งจุดเท่านั้น, `GET /api/witness/head`ซึ่งจะส่งคืน จุดตรวจสอบที่เพิ่งลงนาม พร้อมด้วยตัวนับคอลเลกชันที่ไม่มีเนื้อหาและสถานะการทำงาน มันไม่สามารถเปิดแผงควบคุม อ่านเนื้อหาข้อความ หรือเปลี่ยนแปลงการตั้งค่าได้ และ โทเค็นของแผงควบคุมไม่ได้รับการยอมรับที่นั่น สามารถเพิกถอนโทเค็นได้บนหน้าเดียวกัน ผู้รวบรวมจะบันทึก เมื่อกุญแจพยานใหม่เริ่มตรวจสอบ (`witness.seen`) และแสดงการตรวจสอบครั้งสุดท้ายต่อโทเค็นแต่ละตัว; พยานที่ยังไม่ตรวจสอบภายใน 2.5 ช่วง จะถูกทำเครื่องหมายว่าเกินกำหนด

พยานใหม่จะส่งคำท้าแบบสุ่มใน การโหวตแต่ละครั้ง; คำสั่งบันทึกจะสะท้อนคำท้าดังกล่าวภายใต้ลายเซ็นของผู้รวบรวม ตัวนับ ถูกผูกกับจุดตรวจสอบที่แม่นยำและถูกรวมไว้ในโพสต์ของพยานที่ลงนามแล้ว พยานรุ่นเก่า ยังคงได้รับการยอมรับจากพยานแบบสแตนด์อโลน การเพิ่มขนาดของบันทึกเพียงอย่างเดียวจะไม่ถูกนับเป็นข้อความใหม่

## สิ่งที่ระบบตรวจสอบและบันทึก

ทุกช่วงเวลา (ค่าเริ่มต้นคือ 10 นาที) TgWitness จะ:

1. ดึงส่วนหัวมาเอง (ผู้รวบรวมข้อมูลไม่สามารถส่งหรือข้ามส่วนหัวนี้ได้);
2. ตรวจสอบลายมือของผู้เก็บข้อมูล, กุญแจผู้เก็บข้อมูลที่ถูกตรึง (`--collector-fingerprint`, หรือกุญแจแรกที่พบ), จำนวนที่ไม่ลดลง และส่วนหัวที่ไม่เปลี่ยนแปลงที่จำนวนที่ไม่เปลี่ยนแปลง การพิสูจน์การรวมและการสอดคล้องของ Merkle ตรวจสอบว่าบันทึกที่เพิ่มขึ้นขยาย จุดตรวจสอบที่เก็บไว้ เมื่อการพิสูจน์ความต่อเนื่องถูกใช้แล้ว การลบมันจะถูกปฏิเสธ;
3. เพิ่มบันทึกที่ลงนามแล้วลงในบันทึกของตนเอง: `witness.anchor` ด้วยสถานะ `ok`, `key_changed`, `rollback` (จำนวนบันทึกน้อยกว่าเดิม), `fork` (ความยาวเท่ากัน แต่ส่วนหัวต่างกัน ) หรือ `invalid` (คำตอบไม่ผ่านการตรวจสอบ), หรือ `witness.no_response` เมื่อ ผู้รวบรวมข้อมูลไม่ตอบกลับ;
4. ส่งผลลัพธ์ไปยังช่อง (channel) พร้อมลายเซ็น รวมถึงข้อความ "no answer" ในขณะที่ TgWitness กำลังทำงานและสามารถเข้าถึง Bot API ได้ ID ของการโพสต์ถูกบันทึกไว้ (`witness.posted`), รวมถึงการโพสต์ที่ล้มเหลวด้วย (`witness.post_failed`).

โพสต์มีลักษณะดังนี้; บรรทัดสุดท้ายมีข้อความที่ลงนาม:

```
TgWitness witness #42 · journal head
Collector 3fa9c2d1e0b4a7f6: 18234 records
Head 9b1f…c07e
2026-10-28T19:40:00.123+00:00
TGW1.eyJhdCI6…<statement>.<signature>
```

## เรียกใช้พยาน

คุณจำเป็นต้องมีบอต Telegram (สร้างบอตด้วย @BotFather), ช่องที่บอตดังกล่าวเป็น ผู้ดูแลระบบ และที่อยู่ของผู้เก็บข้อมูลที่สามารถเข้าถึงได้จากผู้ให้คำพยาน — ผ่าน HTTPS นอก เครือข่ายส่วนตัว (ดูโปรไฟล์ HTTPS ใน[ส่วนการติดตั้ง](https://phishdestroy.github.io/TgWitness/th/docs/reference/deployment/))

เปิด **Extras → Independent witness → Configure** ในแผงควบคุม มีสามขั้นตอน ได้แก่ การเข้าถึงแบบอ่านอย่างเดียว ช่องของคุณ และช่วงเวลา จากนั้นจึงเริ่มทำงานของพยาน นโยบายการเผยแพร่ พร็อกซี HTTP/SOCKS5 (ไม่บังคับ) และที่อยู่ Bot API ที่กำหนดเอง อยู่ในส่วน**การตั้งค่าขั้นสูง** แบบฟอร์ม จะดาวน์โหลด `witness.json` พร้อมกุญแจผู้รวบรวม (collector key) ของพื้นที่ทำงานนี้ที่ถูกตรึงไว้ ดาวน์โหลดโทเค็น อ่านอย่างเดียวที่เพิ่งสร้างขึ้นโดยเลือก "**บันทึกไฟล์การเข้าถึง**เป็น" `witness-token.txt`; วางมันและ `bot-token.txt`ที่สร้างขึ้นบนโฮสต์ผู้สังเกตการณ์ไว้ข้างๆ JSON นั้น คอลเลกเตอร์จะไม่ได้รับโทเค็นบอท การดาวน์โหลดจะไม่เริ่มบริการหรือเผยแพร่ข้อความ ไม่มีผู้สังเกตการณ์โครงการที่โฮสต์ ถูกลงทะเบียนโดยอัตโนมัติ

```
python -m tgwitness.witness run --config witness.json --check-config
python -m tgwitness.witness run --config witness.json
python -m tgwitness.witness fingerprint --config witness.json
```

คำสั่งแรกตรวจสอบไฟล์การตั้งค่าและไฟล์ลับโดยไม่มีการส่งคำขอผ่านเครือข่ายหรือการสร้าง กุญแจ เส้นทางใน JSON เป็นเส้นทางสัมพัทธ์กับไฟล์นั้น ส่วนเส้นทาง CLI/สภาพแวดล้อมเป็นเส้นทางสัมพัทธ์กับ ไดเรกทอรีทำงาน เก็บลายนิ้วมือของพยานไว้ภายนอกโฮสต์ของมัน ตัวบ่งชี้ การสำรวจครั้งสุดท้ายของตัวเก็บข้อมูลยืนยันเพียงการร้องขอเท่านั้น; การเผยแพร่จะถูกรายงานโดย Proof หรือตรวจสอบ ในบันทึกพยานและช่องสื่อสาร

หากแผงควบคุมอยู่เบื้องหลังอุโมงค์ SSH ให้เปิดเผยเฉพาะจุดสิ้นสุดของ witness ที่กำหนดขอบเขตไว้บน ชื่อโฮสต์ HTTPS แยกต่างหาก โดยใช้[ตัวอย่าง Caddy นี้](https://github.com/phishdestroy/TgWitness/blob/main/deploy/Caddyfile.witness.example) พื้นที่ทำงานเริ่มต้นจะใช้ `https://witness.example.org` ส่วนพื้นที่ทำงานอื่น ๆ จะใช้ `https://witness.example.org/profiles/ID` โทเค็นยังคงจำเป็น; แผงควบคุมและ เส้นทาง API อื่น ๆ ของมันจะไม่ถูกส่งต่อโดยโฮสต์เสมือนนั้น

เลือก `all` สำหรับจุดตรวจสอบที่เผยแพร่เป็นประจำ ช่วงเวลา 5 นาที หมายถึงประมาณ 288 โพสต์ต่อพื้นที่ทำงานต่อวัน `changes`/`problems` ปล่อยให้จุดตรวจสอบบางส่วนไม่เผยแพร่โดยเจตนา MTProxy ใช้สำหรับไคลเอนต์ Telegram ของผู้รวบรวมข้อมูล การตรวจสอบ HTTP ของ Witness และ HTTPS Bot API ของ Telegram ใช้เส้นทางตรง/HTTP/SOCKS5 ของตนเอง ([Bot API](https://core.telegram.org/bots/api))

**ข้างๆ ตัวเก็บข้อมูล (collector) โดยใช้ Docker** (บนโฮสต์เดียวกัน — กระบวนการและกุญแจอิสระ แต่ ผู้ดำเนินการเดียวกัน): ใส่ค่าลงใน `.env` และเริ่มโปรไฟล์

```
TGWITNESS_WITNESS_TOKEN=tgww_...
TGWITNESS_WITNESS_BOT_TOKEN=123456:ABC...
TGWITNESS_WITNESS_CHANNEL=@your_witness_channel
# another workspace: TGWITNESS_WITNESS_COLLECTOR=http://tgwitness:8787/profiles/<workspace ID>

docker compose --profile witness up -d
docker compose logs witness     # prints the witness key fingerprint
```

หากใช้ภาพที่เผยแพร่แล้ว ให้ใช้`docker compose --project-directory . -f deploy/compose/compose.image.yaml --profile witness up -d`

**บนเซิร์ฟเวอร์ของผู้อื่น** (พยานอิสระที่แท้จริง): คัดลอกรีโพสิตอรีไปยังที่นั่น ตั้งค่า `TGWITNESS_WITNESS_COLLECTOR=https://your-collector.example.org` พร้อมทั้งค่าสามค่าข้างต้น ใน `.env` แล้ว

```
docker compose --project-directory . -f deploy/compose/compose.witness.yaml up -d
```

หรือโดยไม่ต้องใช้ Docker:

```
python -m tgwitness.witness run --collector https://your-collector.example.org \
    --token-file witness-token.txt --bot-token-file bot-token.txt --channel @your_witness_channel
```

### เผยแพร่ไปยัง Discord

ผู้เป็นพยานสามารถโพสต์ไปยังช่อง Discord แทน Telegram ได้ ใน Discord ให้เปิด **Edit Channel → Integrations → Webhooks** สร้าง webhook และคัดลอก URL ของมัน ใน แผงควบคุม ให้เลือก **Discord webhook · ช่องของคุณ** ในขั้นตอนที่ 2 บนเซิร์ฟเวอร์ของผู้เป็นพยาน ให้บันทึก URL ไว้เป็น `discord-webhook.txt` ข้างๆ `witness.json`; มันจะไม่ถึง collector เลย

```
python -m tgwitness.witness run --collector https://your-collector.example.org \
    --token-file witness-token.txt --discord-webhook-file discord-webhook.txt
```

ผู้เป็นพยาน (witness) มีผู้เผยแพร่เพียงหนึ่งราย: ช่อง Telegram หรือ webhook ของ Discord (ไม่ใช่ทั้งสองอย่างพร้อมกัน) โพสต์ จะนำข้อความที่ลงนามแล้วเดียวกันมา และไม่สามารถส่งการแจ้งเตือน (ping) ไปยังใครได้ โพสต์ที่ยาวกว่าขีดจำกัด 2,000 ตัวอักษรของ Discord จะถูกแทนที่ด้วยบรรทัดสั้น ๆ พร้อมแนบการตรวจสอบเต็มรูปแบบเป็น `witness-check.txt`. ID ของโพสต์แต่ละรายการจะถูกบันทึกเป็น `witness.posted`. `verify.py --channel`อ่านได้เฉพาะจากข้อมูลที่ส่งออกของช่อง Telegram เท่านั้น ดังนั้น สำหรับ Discord ให้เก็บรักษาสมุดบันทึกพยาน: มันเก็บ ทุกการตรวจสอบไว้

### ตัวเลือก

| ตัวเลือก | สภาพแวดล้อม | ค่าเริ่มต้น | ความหมาย |
| --- | --- | --- | --- |
| `--interval` | `TGWITNESS_WITNESS_INTERVAL` | 10 | ระยะเวลาระหว่างการตรวจสอบ: 1–1440 นาที |
| `--timeout` | `_TIMEOUT` | 30 | เวลาที่ต้องรอตัวเก็บข้อมูลและ API ของ Bot: 5–600 วินาที |
| `--post` | `_POST` | `all` | `all`: ทุกการตรวจสอบ; `changes`: ปัญหาใหม่หรือหัวข้อใหม่; `problems`: มีแต่ปัญหาและคำตอบที่ขาดหายไป |
| `--title` | `_TITLE` | `TgWitness witness` | คำแรกๆ ของทุกโพสต์ในช่อง |
| `--collector-fingerprint` | `_COLLECTOR_FINGERPRINT` | – | ให้ปักคีย์ผู้เก็บข้อมูลไว้แทนที่จะเชื่อถือคำตอบแรก |
| `--proxy` | `_PROXY` | direct | `socks5://host:port` หรือ `http://host:port` |
| `--bot-api` | `_BOT_API` | `https://api.telegram.org` | ที่อยู่ API ของบอท เช่น เซิร์ฟเวอร์ API ของบอทในท้องถิ่น |
| `--data-dir` | `_DATA` | `witness-data` | กุญแจ Witness และบันทึก |
| `--config` | `_CONFIG` | – | ไฟล์ JSON พร้อมตัวเลือกใดก็ตามข้างต้น |

ที่อยู่ของตัวเก็บข้อมูล โทเค็น และช่องมาจาก `--collector`, `--token` หรือ `--token-file`, `--bot-token` หรือ `--bot-token-file`, `--discord-webhook-file` และ `--channel`, หรือ `_COLLECTOR`, `_TOKEN`, `_TOKEN_FILE`, `_BOT_TOKEN`, `_BOT_TOKEN_FILE`, `_DISCORD_WEBHOOK_FILE` และ `_CHANNEL`, ซึ่งช่วยไม่ให้ข้อมูลลับปรากฏในรายการกระบวนการ

ไฟล์การตั้งค่าใช้ชื่อตัวเลือกที่มีขีดล่าง (underscore) พร้อมด้วย `texts` ซึ่งใช้แทนคำ ในโพสต์ของช่อง:

```
{"collector": "https://your-collector.example.org", "token_file": "witness-token.txt",
 "bot_token_file": "bot-token.txt", "channel": "@your_witness_channel",
 "interval": 5, "timeout": 30, "post": "changes", "title": "Partner witness",
 "texts": {"ok": "journal head", "no_response": "no answer from the collector", "records": "records"}}
```

กุญแจ `texts`: `ok`, `key_changed`, `rollback`, `fork`, `invalid`, `no_response`, `collector`, `records`, `head`. บรรทัดคำสั่งมีลำดับความสำคัญเหนือสภาพแวดล้อม และสภาพแวดล้อมมีลำดับความสำคัญเหนือไฟล์ ตัวเลือกหรือกุญแจข้อความที่ไม่รู้จักจะหยุดการทำงานของ witness พร้อมแสดงข้อความแจ้งเตือน แทนที่จะถูกละเลย คำที่ใช้ไม่เคยส่งผลต่อการตรวจสอบ: verify.py จะตรวจสอบโทเค็นที่ลงนามไว้ที่ท้ายทุก โพสต์ กับ `--post changes` หรือ `problems` การตรวจสอบที่ยังไม่ถูกโพสต์ยังคงอยู่ใน สมุดบันทึกพยาน และ `verify.py` จะแสดงรายการเหล่านั้นว่ายังไม่เคยถูกโพสต์; บันทึกเริ่มต้นจะระบุชื่อ นโยบาย การตรวจสอบทุกครั้งยังคงปรากฏในสมุดบันทึก ดังนั้นการโพสต์น้อยลงหมายถึงเวลา Telegram อิสระน้อยลง ไม่ใช่การตรวจสอบน้อยลง

แม้ไม่มีช่อง (channel) TgWitness ก็ยังคงเก็บบันทึกไว้ได้ เก็บลายนิ้วมือของกุญแจ TgWitness (`python -m tgwitness.witness fingerprint`) ไว้ที่อื่น

## หน้าหลักฐานสาธารณะสำหรับพื้นที่ทำงานหลายแห่ง

`python -m tgwitness.proof` witnesses สามารถจัดการพื้นที่ทำงานได้สูงสุด 32 พื้นที่พร้อมกัน และให้บริการหน้าแบบอ่านอย่างเดียว ที่มีผลการตรวจสอบล่าสุดที่ลงนามแล้วของแต่ละพื้นที่ทำงาน ทุกพื้นที่ทำงานจะได้รับกุญแจ witness และ journal ของตัวเองในโฟลเดอร์ data พร้อมด้วยกุญแจ collector ที่ถูกตรึงไว้; การโพสต์ไปยังช่อง Telegram เป็นตัวเลือกที่แต่ละพื้นที่ทำงานสามารถกำหนดได้เอง เริ่มจาก [proof.config.example](https://github.com/phishdestroy/TgWitness/blob/main/deploy/proof.config.example):

| Field | ความหมาย |
| --- | --- |
| `title` | ชื่อหน้า, 1–100 ตัวอักษร |
| `data_dir` | กุญแจและบันทึกของ Witness ที่เกี่ยวข้องกับไฟล์; ค่าเริ่มต้น `proof-data` |
| `interval`, `timeout` | จำนวนนาทีระหว่างการตรวจสอบ (1–1440, ค่าเริ่มต้น 5); จำนวนวินาทีที่ต้องรอ (5–600, ค่าเริ่มต้น 20) |
| `workspaces[].id`, `label` | ชื่อย่อตัวพิมพ์เล็กสั้นๆ และชื่อที่แสดง |
| `workspaces[].collector` | ที่อยู่ Collector; พื้นที่ทำงานอื่น ๆ จะลงท้ายด้วย `/profiles/<workspace ID>` |
| `workspaces[].collector_fingerprint` | จำเป็น, แตกต่างกันสำหรับแต่ละพื้นที่ทำงาน |
| `workspaces[].token_file` | ไฟล์ที่มีโทเค็นพยานแบบอ่านอย่างเดียวของพื้นที่ทำงานนั้น |
| `workspaces[].channel`, `bot_token_file` | ตัวเลือกเพิ่มเติม: โพสต์การตรวจสอบแต่ละครั้งไปยังช่อง |
| `workspaces[].proxy`, `bot_api` | ที่อยู่ API ของ Bot และเส้นทาง (Optional route) |

```
python -m tgwitness.proof --config proof.json --check-config
python -m tgwitness.proof --config proof.json --host 127.0.0.1 --port 8790
```

คำสั่งแรกจะตรวจสอบความถูกต้องของไฟล์และไฟล์โทเค็นโดยไม่เปิดการเชื่อมต่อ หน้านี้รับเฉพาะคำขอ GET และ HEAD:

- `/` แสดงทุกพื้นที่ทำงาน; พื้นที่ทำงานที่ยังไม่ได้รับการตรวจสอบเป็นเวลา 2.5 ช่วงจะได้รับการทำเครื่องหมายว่าล้าสมัย
- `/api/proof` ให้ผลลัพธ์เหมือนกับ JSON.
- `/api/proof/<id>` ดาวน์โหลดคำแถลงที่ลงนามล่าสุด (`tgwitness-public-proof-v1`): หมายเลขบันทึกพยานและแฮช, สถานะ, กุญแจผู้เก็บข้อมูลที่ตรึงไว้, จุดตรวจสอบ, ตัวนับการเก็บข้อมูล และว่าโพสต์ในช่องสำเร็จหรือไม่, ลงนามด้วยกุญแจพยานของพื้นที่ทำงานนั้น
- `/healthz` แสดงรหัสข้อผิดพลาด 503 เมื่อตัวติดตามของพื้นที่ทำงานหยุดทำงาน

ตั้งชื่อโฮสต์เฉพาะสำหรับหน้าดังกล่าว เช่น [Caddyfile.proof.example](https://github.com/phishdestroy/TgWitness/blob/main/deploy/Caddyfile.proof.example) เพื่อตรวจสอบ ให้ส่งออก หนังสือบันทึกพยานของพื้นที่ทำงานด้วย `python -m tgwitness.witness export --data-dir proof-data/<id> --out witness.zip` และใช้มัน ตามคำอธิบายด้านล่าง

## ตรวจสอบ

สำหรับผู้ใช้ TgWitness สามารถส่งออกบันทึกได้ดังนี้:

```
python -m tgwitness.witness export --out witness.zip
# Docker (add -f deploy/compose/compose.witness.yaml on a witness server):
docker compose exec witness python -m tgwitness.witness export --out /witness/witness.zip
docker compose cp witness:/witness/witness.zip .
```

จากนั้น สามารถทำได้ทุกที่ โดยใช้ไฟล์ ZIP ที่ลงนามจากเครื่องมือเก็บข้อมูล และช่องสนทนาที่ส่งออกจาก Telegram Desktop (*ส่งออกประวัติการสนทนา* → JSON จะได้ `result.json` ) หรือหน้าสาธารณะ `https://t.me/s/…` ของมัน:

```
python verify.py tgwitness-evidence.zip --fingerprint COLLECTOR_SHA256 \
    --witness witness.zip --witness-fingerprint WITNESS_SHA256 --channel result.json
```

`verify.py` ตรวจสอบบันทึกของ Witness (ห่วงโซ่และลายเซ็น) จากนั้น**ตรวจสอบว่าทุกหัวข้อความที่ Witness ได้เห็นเป็นส่วนหนึ่งของบันทึกที่ส่งออก**: บันทึกที่ตำแหน่งนั้นต้องมี แฮชที่ตรงกันพอดี หัวข้อความที่ไม่ตรงกันจะผ่านการตรวจสอบไม่สำเร็จ — บันทึกถูกเปลี่ยนแปลงหลังจาก Witness ได้เห็นมัน นอกจากนี้ยังรายงานหัวข้อความที่เห็นหลังการส่งออก ความผิดปกติที่พยาน บันทึกไว้ คำตอบที่ล้มเหลว ช่วงเวลามีจุดตรวจสอบที่ตรงกันอยู่ใน การส่งออกนี้ ("ได้รับการยืนยันจาก X ถึง Y") และช่องว่าง จุดตรวจสอบที่ตามมาไม่ขยายช่วงเวลานั้น ผลลัพธ์รวมถึงหมายเลขบันทึกที่ตรงกันล่าสุดและจำนวนบันทึกที่ตามมา ที่ไม่มีจุดตรวจสอบที่ตรงกัน เฉพาะคำตอบที่ลงนามด้วยกุญแจของไฟล์ส่งออกเองเท่านั้นที่นับ: ไฟล์ส่งออกที่ลงนาม ด้วยกุญแจที่ผู้เป็นพยานไม่เคยเห็นจะถูกรายงานว่าไม่ได้รับการเป็นพยาน และหากไม่มี`--fingerprint` ผู้ ลงนามจะยังคงไม่ถูกตรึง ด้วย`--channel` ทุกโพสต์ที่ลงนามต้องตรงกับบันทึกในสมุดบันทึกของผู้เป็นพยาน บันทึกต่อบันทึก: โพสต์ที่เปลี่ยนแปลงจะล้มเหลวในการตรวจสอบ ส่วนโพสต์ที่ขาดหายไปจะถูกรายการไว้ วันที่ใน ไฟล์ส่งออก JSON ของ Telegram ที่ให้มา เป็นข้อมูลเมตาที่แก้ไขได้ ซึ่งอยู่นอกโทเค็นผู้เป็นพยานที่ลงนาม การตรงกับโทเค็นไม่ยืนยันวันที่เผยแพร่; ผลลัพธ์จะรายงานอย่างชัดเจน ว่าการตรวจสอบเวลาเผยแพร่ไม่ได้ดำเนินการ

### จำเป็นต้องมีขอบเขตการส่งออกที่มีผู้เป็นพยาน

สำหรับการส่งต่อข้อมูลที่ต้องรวมถึงบันทึกสุดท้ายที่มีพยานรับรอง ให้เพิ่ม `--require-witness`:

```
python verify.py tgwitness-evidence.zip --fingerprint COLLECTOR_SHA256 \
    --witness witness.zip --witness-fingerprint WITNESS_SHA256 --require-witness
```

สิ่งนี้ต้องการลายนิ้วมือของพยานที่เก็บรักษาไว้อย่างอิสระและจุดตรวจสอบที่ตรงกัน ที่จุดสิ้นสุดที่แม่นยำของการส่งออกนี้ จุดตรวจสอบที่ครอบคลุมเพียงส่วนนำหน้าก่อนหน้านี้ ไม่เพียงพอ ให้หยุดการเก็บข้อมูลชั่วคราว ให้พยานสังเกตสถานะสุดท้าย และส่งออก ก่อนที่จะมีการเขียนบันทึกเพิ่มเติม; หากบันทึกมีการเปลี่ยนแปลง ให้เก็บจุดตรวจสอบอีกจุดและ ส่งออกสถานะนั้น จุดตรวจสอบที่สร้างขึ้นภายหลังเพียงอย่างเดียวไม่สามารถตรวจสอบค่าแฮชสุดท้ายของการส่งออกที่สั้นกว่าได้ เมื่อมีการระบุ `--channel` ด้วย การขาดโพสต์ที่อ้างว่ามีอยู่หรือชุดการจับคู่ที่ว่างเปล่าจะทำให้การตรวจสอบ ที่เข้มงวดนี้ล้มเหลว หากไม่มีตัวบ่งชี้นี้ การตรวจสอบความสมบูรณ์แบบปกติจะยังคงรายงาน บันทึกที่ไม่มีพยานยืนยัน โดยไม่ปฏิเสธอาร์ไคฟ์ที่สมบูรณ์ในส่วนอื่น

เก็บสมุดบันทึกพยานและกุญแจที่ตรึงไว้แยกกัน การตรวจสอบออนไลน์จะยืนยันความต่อเนื่อง ระหว่างจุดตรวจสอบ; การตรวจสอบออฟไลน์จะเปรียบเทียบทุกจุดตรวจสอบที่เก็บไว้กับ ไฟล์ที่ส่งออก พยานรุ่นเก่าที่ไม่มีหลักฐานความต่อเนื่องจะเก็บการเปรียบเทียบออฟไลน์ไว้และ ถูกรายงานโดยไม่ผ่านการตรวจสอบความต่อเนื่องออนไลน์ รายงานจะแสดงช่วงเวลาที่พยานหยุดทำงานและ การเผยแพร่ที่ล้มเหลวตามช่วงเวลา

### ตราประทับรายวันและปฏิทินเวลาประทับที่ไม่สามารถใช้งานได้

ผู้เป็นพยานจะปิดผนึกขอบเขตบันทึกของวัน UTC ก่อนหน้า และส่งค่าแฮชของ ผนึกที่ลงนามนั้นไปยัง OpenTimestamps การส่งข้อมูลปฏิทินถือเป็นหลักฐานที่รอการยืนยัน; เพียงคำมั่นสัญญา Bitcoin ที่ได้รับการตรวจสอบอย่างอิสระเท่านั้นที่จะได้รับการยืนยันในตัวตรวจสอบ

หากปฏิทินทั้งหมดล้มเหลว ตราประทับที่ลงนามแล้วและความพยายามที่ไม่สำเร็จจะยังคงอยู่ใน บันทึกประจำวัน การตรวจสอบบำรุงรักษาทุกชั่วโมงจะลองบันทึกเดิมอีกครั้ง รวมถึง หลังจากรีสตาร์ทหรือเปลี่ยนวันที่ มันจะสแกนตราประทับสูงสุด32 ตรา ส่งข้อมูลที่ขาดหายไปสูงสุด สองรายการ และใช้เวลาสูงสุด60 วินาทีในการลองใหม่ต่อรอบ คอร์เซอร์ แบบคงที่จะหมุนผ่านตราประทับที่เก่ากว่า ข้อมูลที่เก็บไว้จะปฏิบัติตาม เส้นทางการอัปเกรดหลักฐานที่มีอยู่

การลองใหม่จะไม่เขียนทับตราประทับใหม่ ไม่เปลี่ยนวันที่เดิม หรืออ้างว่า ปฏิทินได้รับมันมาก่อน การยืนยัน Bitcoin ที่เกิดขึ้นภายหลังยังคงเป็นการยืนยันจากภายนอก ที่เกิดขึ้นภายหลัง หลักฐานที่ขาดหายไปยังคงเป็น `none`; หลักฐานที่รอการยืนยันยังคงเป็น `pending` จนกว่า ผู้ตรวจสอบจะตรวจสอบมันอย่างอิสระ
