# Вопросы и проверки

[Независимая проверка](../TRUST.md) · [Что подтверждают данные](../FOR-THE-RECORD.md) · [Протокол проверки](../VERIFICATION.md)

В каждом из приведенных ниже ответов указано, что подтверждается записью, а также приведена команда или файл, с помощью которых
можно это проверить. Проверки не зависят от доверия к оператору, собравшему архив, или к
программе PhishDestroy.

Доверенные входные данные поступают не из проверяемого файла, а из другого источника: отпечаток
коллектора от отправителя, корневой сертификат органа, выдающего временные метки, от самого этого органа, фиксация
из вашей собственной проверки. Запускайте верификатор из установки или фиксации, которым вы доверяете;
копия внутри архива предназначена исключительно для удобства ([манифест и контрольные точки ](../EVIDENCE.md#manifest-and-checkpoints)).
Верификатор представляет собой один файл, [`tgwitness/verify.py`](../../tgwitness/verify.py), собранный из
[`tgwitness/verifier/`](../../tgwitness/verifier/README.md);
`python tools/build_standalone_verifier.py --check` обнаруживает расхождения между ними.
Проверки журнала и подписи находятся в `common`, `chain` и `journal` (в сумме 22 КБ);
примерно треть `verify.py` составляют сжатые данные перевода из `languages`.
Требуется Python 3.11+ и `cryptography`.

## Команды, используемые на этой странице

**Архив доказательств.** `--require evidence` завершает работу с кодом 2, если не выполнены все условия: целостность,
закрепленный ключ коллектора и время от стороннего источника, охватывающее последнюю запись.
Добавьте `--explain`, чтобы получить простое описание того, что проверяет каждая из этих проверок.

```sh
python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_SHA256 --tsa-ca TSA-ROOT.pem --check-bitcoin --require evidence
```

Чтобы прочитать сообщения свидетелей из Telegram, добавьте
`--witness witness.zip --witness-fingerprint WITNESS_SHA256 --channel https://t.me/s/WITNESS_CHANNEL`.
`--require-tier TIER` находится ниже с кодом 2 [уровень гарантии](../FOR-THE-RECORD.md#1-what-each-step-establishes).

**ZIP-архив исходного кода релиза** ([архив исходного кода релиза](../TRUST.md#release-source-archive)).
`COMMIT` — это полный SHA-хэш, который вы проверили:

```sh
gh attestation verify "TgWitness-${VERSION}.zip" --repo phishdestroy/TgWitness \
  --signer-workflow phishdestroy/TgWitness/.github/workflows/provenance.yml \
  --signer-digest "$COMMIT" --source-digest "$COMMIT" \
  --source-ref "refs/tags/v${VERSION}" --deny-self-hosted-runners
```

**Сбор через GitHub Actions** ([запечатанное доказательство](../TRUST.md#sealed-evidence)). `WORKFLOW_SHA`
— это `workflow_sha`, указанный в `tgwitness/sealed_policy.json` установки, которой вы доверяете:

```sh
gh attestation verify evidence.zip --bundle attestation.jsonl --repo OWNER/TgWitness \
  --signer-workflow phishdestroy/TgWitness/.github/workflows/sealed-collector.yml \
  --signer-digest WORKFLOW_SHA --deny-self-hosted-runners
python -m tgwitness.sealed_verify evidence.zip --bundle attestation.jsonl --repo OWNER/TgWitness
```

**Скрипт установщика перед запуском** ([проверить перед запуском](../INSTALLATION.md#verify-before-running)):

```sh
curl -fSLO https://get.destroy.tools/install.sh && curl -fSLO https://get.destroy.tools/install.sh.sig &&
curl -fSLO https://get.destroy.tools/release-signing.pub &&
test "$(openssl dgst -sha256 release-signing.pub | awk '{print $NF}')" = \
  '039d98a658ccda14253e45a00335b4a68d840976d8ec18b8d4355cc7c458447d' &&
openssl dgst -sha256 -verify release-signing.pub -signature install.sh.sig install.sh && bash install.sh
```

<a id="how-a-record-is-tied-to-telegram"></a>
## Как запись привязывается к Telegram

- Коллектор подписывает каждую запись в момент её поступления через
  аутентифицированное соединение с аккаунтом в Telegram. Журнал фиксирует это соединение и факт
  захвата ([откуда поступают сообщения](../EVIDENCE.md#where-the-messages-come-from)).
- Telegram доставляет сообщения каждому клиенту, включая официальные приложения, в рамках сеанса MTProto
 . Его ключ авторизации согласовывается с закреплённым серверным ключом Telegram, и
 каждое обновление расшифровывается и проходит проверку целостности (`msg_key`) с использованием этого ключа. Прокси или
 ретранслятор на пути не может читать, вставлять или изменять обновление.
- Соединение устанавливается с опубликованными сетевыми диапазонами Telegram. **Дополнительные инструменты → Карта системы**
  показывает для каждой подключённой учётной записи, находится ли её конечная точка в пуле Telegram
  (`TELEGRAM_NETWORKS` в [`tgwitness/topology.py`](../../tgwitness/topology.py)).
- Перехваченные кадры MTProto можно расшифровать с помощью собственного ключа сеанса и сопоставить с
  записями журнала по идентификатору сообщения и SHA-256 полезной нагрузки
  ([`tgwitness/forensics/`](../../tgwitness/forensics/)).
- Каждая запись содержит идентификаторы и даты сервера, присвоенные Telegram: чат, сообщение
  и отправитель. Другой аккаунт в том же чате получает те же идентификаторы, и
  `--compare` сверяет два экспорта друг с другом
  ([сравнение экспортов чата ](../EVIDENCE.md#comparing-chat-exports)).
- [Проверка свидетеля ](../ACCOUNTS.md#witness-probe) со второго аккаунта показывает, что
  сессия получала обновления в режиме реального времени; второй клиент, использующий тот же ключ, отображается как пропущенные
  ответы. Верификатор сообщает: «Запросы свидетелей: отправлено N, отвечено в режиме реального времени N».
- GitHub Actions фиксирует, а Intel TDX привязывает сессию, созданную в ходе выполнения, и
  ключ подписи к заверенному выполнению (`key_origin: created`;
  [область проверки](../EVIDENCE.md#verification-scope)).

**Что сообщает верификатор.** Достоверная подпись свидетельствует о том, что байты не изменились
с момента подписания; оператор передаёт получателю отпечаток ключа по
отдельному каналу. Без `--fingerprint`
последняя строка начинается с
`EVIDENCE: minimum not met · missing: confirmed signer key`
. С `--fingerprint`
:
`self_attested`
(подписи, цепочка хешей, манифест и хеши файлов). При использовании стороннего времени,
охватывающего последнюю запись:
`EVIDENCE: minimum met`
. При проверенном заверенном прогоне: профиль `attested`
(`evidence_conditions`
в [`tgwitness/verifier/witness.py`](../../tgwitness/verifier/witness.py)
).

<a id="how-records-are-fixed-against-later-change"></a>
## Как записи защищаются от последующих изменений

- Каждое наблюдение подписывается при поступлении и вставляется в хеш-цепочку
  ([что подписывается](../EVIDENCE.md#what-is-signed)). В режиме «доказательства» временные метки по умолчанию
  подписывают контрольные точки каждые 10 минут в трёх центрах сертификации времени (TSA), один из которых —
  сертифицированный правительством Бельгии центр eIDAS TSA (`DEFAULT_TSA` в `tgwitness/anchoring.py`), а также на
  OpenTimestamps.
- Изменение, вставка или удаление записи нарушает хеш-цепочку или подпись, и
  верификатор отклоняет архив. Метка фиксирует начало цепочки, которую она охватывает, в момент времени, зафиксированный третьей стороной,
  поэтому охваченная ею запись не может быть заменена позже без появления несоответствия. Записи после
  последней метки имеют имя: `EVIDENCE: minimum met up to record N of M · later records need a binding`.
- Триггеры SQLite в таблице журнала лишь предотвращают случайную перезапись или
  удаление записи приложением; обнаружение зависит от цепочки, подписей, отметки и свидетеля.
- При включенном drand каждый проход также записывает открытый раунд drand, который никто не знал до его
  наступления. Раунд устанавливает самое раннее время, а следующая метка — самое позднее, поэтому контрольную точку
  невозможно подготовить заранее; `--check-drand` сравнивает раунды с общедоступными ретрансляциями
  ([drand](../EVIDENCE.md#optional-records-in-evidence-mode-drand-and-telegram-devices)).
- Времена наблюдений, идущие в обратную сторону, фиксируются как регрессии хронологии
  (`tgwitness/verifier/journal.py`).
- Запись должна совпадать с тем, что Telegram доставил всем остальным участникам чата.
  Независимый экспорт того же чата показывает любые расхождения
  ([сравнение экспортов чата](../EVIDENCE.md#comparing-chat-exports)):
  `python -m tgwitness.verify first.zip --compare second.zip --fingerprint FIRST_SHA256 --compare-fingerprint SECOND_SHA256`.
- Свидетель со своим собственным ключом сохраняет префиксы более ранних журналов, а сообщения свидетеля,
  считываемые в режиме реального времени с t.me, содержат даты, установленные Telegram ([свидетель](../WITNESS.md)).
- GitHub Actions и Intel TDX избавляют оператора от необходимости заниматься сбором данных:
  сессия создаётся внутри заверенного запуска (импортированная сессия не попадает в профиль
  `attested`), а аттестация привязывает архив к утверждённому сборщику
  ([область проверки](../EVIDENCE.md#verification-scope)).

**Что указывается в отчете проверяющего.** Записи, охватываемые каждой отметкой, и интервал между
одной записью и следующей отметкой. В режиме проверки этот интервал соответствует графику проставления отметок.

<a id="checkpoints-and-witnesses"></a>
## Контрольные точки и свидетели

- Контрольная точка подписывается ключом сборщика. Она считается привязанной с момента, когда получатель
  получает её по другому каналу, до формирования архива
  ([манифест и контрольные точки](../EVIDENCE.md#manifest-and-checkpoints)).
- Свидетель работает как отдельный процесс со своим собственным ключом на хосте сборщика или на
  машине другого оператора ([свидетель](../WITNESS.md)). Верификатор проверяет, что
  ключ свидетеля отличается от ключа сборщика; «Кто владеет этим ключом, показывает
  запись о контроле ключей хранителя, хранящаяся вместе с его отпечатком» (`CONDITION_SCOPE` в
  [`tgwitness/verifier/witness.py`](../../tgwitness/verifier/witness.py)).
- Оба добавляют независимые копии начала журнала сверх минимального требования для подтверждения,
  которое заключается в времени, зафиксированном третьей стороной.
- Для `--channel` чтение страницы `https://t.me/s/…` или `https://telegram.me/s/…` в режиме реального времени
  предоставляет даты, установленные Telegram. Отредактированные сообщения игнорируются, а экспорт из Telegram Desktop
  или сохраненная страница считаются предоставленными метаданными.

**Результат.** Контрольная точка становится привязанной с момента её получения адресатом. Свидетель на
машине другого оператора не зависит от сборщика; сохраните запись о хранителе и
управлении ключом вместе с её отпечатком ([witness](../WITNESS.md)).

<a id="signed-on-receipt-compared-with-a-stamped-desktop-export"></a>
## Подписано при получении, сверялось с экспортным файлом Desktop, заверенным печатью

Квалифицированная временная метка в экспорте Telegram Desktop фиксирует файлы на момент
простановки метки. TgWitness фиксирует каждую запись на момент её поступления.

- Telegram Desktop сохраняет экспортные файлы в формате HTML или JSON без подписи. Их
  можно редактировать до того, как на них будет проставлена отметка времени, а затем квалифицированная отметка времени подтверждает,
  что отредактированные файлы существовали именно в этот момент. На
  странице [Export Clinic](https://phishdestroy.github.io/TgWitness/docs/export-clinic/)
  показан
  чат рядом с намеренно измененными файлами экспорта из Desktop.
- TgWitness подписывает каждое наблюдение по мере его поступления и связывает его с хеш-цепочкой
  ([что подписывается](../EVIDENCE.md#what-is-signed)
  ). Проставка временных меток по стандарту RFC 3161 и OpenTimestamps для
  подписанных контрольных точек включена по умолчанию в каждой цели настройки; **Доказательства по делу** также
  фиксируют раунды drand. Файлы `.tsr`
  и `.ots`
  , расположенные под `anchors/`
  , позволяют любому пользователю проверить их.
- TgWitness может использовать квалифицированную TSA. Ручная процедура по RFC 3161 отправляет контрольную точку
  в любой TSA и проверяет ответ с помощью
  `python -m tgwitness.anchor verify --checkpoint checkpoint.json --request timestamp.tsq --response timestamp.tsr --ca trusted-tsa-root.pem`
  ([процедура ](../TIMESTAMP.md#procedure)
  ). Сертификат аттестации Intel TDX
  запечатан квалифицированным TSA правительства Бельгии, корневой сертификат которого закреплён в
  `tgwitness/tsa_roots.py`
  ([сертификат аттестации ](../HIGH-ASSURANCE.md#attestation-certificate)
  ).

- В режиме «Evidence» каждая контрольная точка отправляется в квалифицированную службу временных отметок (TSA) правительства Бельгии
  совместно с freetsa.org и Sectigo (`DEFAULT_TSA` в `tgwitness/anchoring.py`).
  При установке `--tsa-ca` в качестве корневого сертификата данного поставщика `verify.py` сообщает о штампе как о
  квалифицированной временной отметке eIDAS и указывает организацию, осуществляющую временную отметку, из доверенного списка ЕС
  (`qualified_timestamp` в `tgwitness/verifier/timestamps.py`). В соответствии с Регламентом (ЕС)
  № 910/2014, статья 41(2), такая отметка дает основание предполагать, что указанное время
  является точным, а связанные с ней данные не повреждены, в каждом государстве-члене ЕС.

**Разница.** TgWitness подписывает каждую запись при получении и проставляет отметки на контрольных точках в
графике, поэтому байты с отметками — это именно те байты, которые были получены. Экспорт в формат Desktop защищен только
с момента проставления отметки; после этого он может быть отредактирован.

<a id="court-package-and-jurisdictions"></a>
## Судебный пакет и юрисдикции

- Сертификат судебного пакета «заполнен заранее в форме сертификата, предусмотренного Правилом
  902(13)/(14)» ([документы для суда](../INVESTIGATION-MODE.md#documents-for-court)).
  Его уведомление начинается словами «В соответствии с Федеральными правилами доказывания США» и заканчивается фразой «Перед подписанием адаптируйте этот
  шаблон к применимым правилам» (`NOTICE` в
  [`tgwitness/court.py`](../../tgwitness/court.py)).
- [Руководство по юрисдикциям](../JURISDICTION_GUIDANCE.md) в Report Studio охватывает 25
  юрисдикций: правовые основания, задачи по подготовке, правовые источники, меры безопасности при сборе данных
  и опциональное резюме на местном языке. Описательные отчеты содержат термины по юрисдикциям
  на 25 языках ([шаблоны и юрисдикции](../NARRATIVE.md#templates-and-jurisdictions)).
- Проверка архива везде одинакова: проверки подписей, RFC 3161, Bitcoin и
  аттестации носят технический характер. Квалифицированная временная метка eIDAS дает презумпцию
  соответствия статье 41(2) Регламента (ЕС) № 910/2014 в каждом государстве-члене ЕС.

**Результат.** Заявитель использует данный шаблон в том виде, в котором он применяется в федеральных судах США, и
адаптирует его к применимым нормам в других странах.

<a id="deleted-messages-and-data-protection"></a>
## Удаленные сообщения и защита данных

- TgWitness «записывает контент, поступающий на подключенную учетную запись Telegram»
  ([README](../../README.md)): сообщения, которые получает собственное приложение Telegram этой учетной записи,
  и ничего, кроме них. При поступлении уведомления об удалении функция наблюдения в режиме реального времени
  регистрирует уведомление и по замыслу сохраняет его текст.
- Программа не использует телеметрию и не имеет хостингового сервиса ([README](../../README.md)), поэтому
  она не хранит чьи-либо данные от своего имени. Как и в случае со скриншотом или экспортом из Telegram Desktop,
  обязанности по защите данных ложатся на того, кто собирает и использует запись. В руководстве по проекту
  перечислены законные интересы, на которые обычно ссылаются (GDPR, ст. 6(1)(f),
  преамбура 47 и 49; ст. 9(2)(f) в отношении правовых претензий), а также исключение из правила удаления «для
  установления или защиты правовых претензий (ст. 17(3)(e))»
  ([ответственность и защита данных](../PROJECT-GUIDE.md#responsibility-and-data-protection-gdpr)).
- Удаление одной записи нарушает хеш-цепочку, и верификатор сообщает об этом. Хранение
  планируется для каждой рабочей области, и удаление рабочей области приводит к удалению её записей. Внесайтовые копии, защищённые с помощью S3 Object Lock, не могут быть удалены до
  истечения срока их хранения (тот же раздел).
- Профили пользователей по умолчанию отключены и включаются для каждого чата. Экспорт данных позволяет
  отвечать на запросы о доступе в соответствии со ст. 15 (тот же раздел).

**Вывод.** GDPR регулирует деятельность физических лиц и организаций, занимающихся обработкой данных, а не программного обеспечения.
Удаленное сообщение остается в архиве в том виде, в каком оно сохранилось в любой копии, созданной до
удаления; в руководстве перечислены правовые основания, используемые для предъявления судебных исков.

<a id="a-public-mtproxy-relays-encrypted-traffic-only"></a>
## Общедоступный MTProxy передает только зашифрованный трафик

- Для новых рабочих пространств по умолчанию используются **Автоматический MTProxy · общедоступные списки** с настройкой **«Скрыть
  адрес»** ([MTProto, Telethon и прокси](../CONNECTION-SECURITY.md#mtproto-telethon-and-proxies)).
  Эти списки берутся из общедоступных источников, указанных в разделе
  [общедоступные прокси](../CONNECTION-SECURITY.md#public-proxies-supplied-by-your-installation).
- MTProxy передаёт только трафик Telegram. Этот трафик шифруется с помощью сеансового
  ключа, согласованного с закреплённым серверным ключом Telegram
  ([откуда поступают сообщения](../EVIDENCE.md#where-the-messages-come-from)), поэтому
  прокси ретранслирует его, не читая ни сообщений, ни ключей. Как сетевой ретранслятор, он по-прежнему
  получает адрес подключения, а также информацию о времени и объёме трафика.
- «Ни сессии Telegram, ни учетные данные API, ни токен панели, ни токен бота не отправляются
  поставщикам фидов» ([общедоступные прокси](../CONNECTION-SECURITY.md#public-proxies-supplied-by-your-installation)).
- Оператор выбирает остальные исходящие сервисы. Сервисы временных меток получают
  хеши контрольных точек, а не сообщения ([процедура](../TIMESTAMP.md#procedure)). ИИ по умолчанию
  отключен во всех рабочих пространствах и перед каждым запросом показывает данные, которые он отправит
  ([анализ](../ANALYSIS.md)). Уведомления не содержат текста сообщений, если не
  включена функция выдержек ([руководство по проекту](../PROJECT-GUIDE.md#responsibility-and-data-protection-gdpr)).
  **Дополнительные инструменты → Карта системы** отображает список подключений, которые пытается установить процесс
  ([карта системы](../SYSTEM-MAP.md)).
- Набор каталога оператора с `TGWITNESS_PROXY_CATALOG` «полностью отключает внешние
  подписки»; другой альтернативой является использование собственного маршрута SOCKS5 или HTTP
  ([безопасность соединения](../CONNECTION-SECURITY.md)).

**Результат.** Общедоступный прокси видит метаданные соединения: то, что сервер подключается к
Telegram, когда и в каком объеме — как и любой другой прокси или VPN. Он не может читать или изменять
сообщения, но может прервать соединение. Если метаданные имеют значение, используйте каталог операторов
или собственный маршрут.

<a id="built-in-api-pairs-identify-a-client-not-an-account"></a>
## Встроенные пары API идентифицируют клиента, а не учетную запись

В [руководстве по выделенным аккаунтам](https://phishdestroy.github.io/TgWitness/docs/dedicated-account/#api)
даны рекомендации по выбору и приведены ссылки на документацию Telegram по каждому пункту.

- **Пара служит для идентификации приложения.** Идентификатор API и хеш API позволяют Telegram идентифицировать приложение,
  но не предоставляют доступа к данным аккаунта. При входе в систему используется собственная
  авторизация аккаунта: код входа и пароль двухфакторной аутентификации (2FA) или сессия, в которой аккаунт уже авторизован.
- **Общая пара не предоставляет доступа.** При входе в систему создаётся ключ авторизации посредством
  обмена по алгоритму Диффи-Хеллмана; ключ никогда не отправляется, и другие программы с той же парой
  имеют свои собственные ключи. Трафик шифруется этим ключом, а не хешем API. В Telegram
  нет метода, который бы выводил список аккаунтов, сессий или сообщений по API-ID.
- **Встроенные пары являются общедоступными.** Пары официальных приложений Telegram (Desktop 2040,
  Android 6, Telegram X 21724, iOS 10840, macOS 2834, Web 2496) и остальные из пула
  опубликованы в открытом исходном коде клиентов Telegram и библиотек, таких как opentele,
  opentele2 и Grampo.
- [`tgwitness/api_pool.py`](../../tgwitness/api_pool.py) содержит 50 общедоступных пар. При новом
  входе в систему сначала пробуется пара Telegram Desktop (2040), затем до семи других, выбранных в случайном порядке
  (`login_order`); если Telegram отклоняет пару, пробуется следующая. Только пара Telegram
  Desktop (2040) отправляется с соответствующим описанием клиента Telegram Desktop
  ([методы аутентификации](../CONNECTION-SECURITY.md#authentication-methods)).
  Отсутствующие поля устройства берутся из встроенных каталогов opentele2
  ([API ID и хеш API](../ACCOUNTS.md#before-you-start-api-id-and-api-hash)).
- **Ваша собственная пара.** Введите её в поле **API ID + Hash**, и TgWitness будет использовать её вместо
  пары из пула. Встроенная пара регистрируется для суда таким же образом (следующий пункт). По
  опыту проекта использование новой личной пары с my.telegram.org приводит к выходу из системы
  большинства аккаунтов, поэтому используйте её только в тех случаях, когда дело требует использования вашего собственного приложения: создайте её с помощью
  специально выделенного аккаунта и введите её до начала сбора данных
  ([API ID и хеш API](../ACCOUNTS.md#before-you-start-api-id-and-api-hash)).
- Каждая запись `observation.started` указывает `api_id` (никогда не хеш), независимо от того, является ли
  пара встроенной или собственной у оператора, а также описание клиента и тип маршрута.
  Отчёты и `custody.json` перечисляют их ([producer](../EVIDENCE.md#producer)), поэтому
  получатель может увидеть, какой клиент осуществлял наблюдение.

**Результат.** Пара, с которой выполнен вход, не влияет на то, что получает аккаунт, а
имя записи определяет его. Telegram устанавливает ограничения со своей стороны независимо от того, какой профиль клиента
используется ([аккаунты](../ACCOUNTS.md#before-you-start-api-id-and-api-hash)), поэтому в руководстве
рекомендуется использовать отдельный аккаунт.

<a id="verifying-the-installer"></a>
## Проверка установщика

- Установка с помощью одной команды — это стандартный способ установки инструментов для разработчиков: Claude Code
  (`curl -fsSL https://claude.ai/install.sh | bash`
  ), rustup
  (`curl … https://sh.rustup.rs | sh`
  ), Homebrew и скрипт Docker `get.docker.com`
  используют
  один и тот же шаблон. TgWitness дополняет его приведёнными ниже проверками.
- Команды [verify-first](../INSTALLATION.md#verify-before-running)
  загружают
  скрипт, его отдельную подпись и открытый ключ, проверяют SHA-256 ключа, верифицируют
  подпись с помощью OpenSSL и только после этого запускают скрипт. Ожидаемый хеш ключа —
  SHA-256 от [`deploy/installer/release-signing.pub`](../../deploy/installer/release-signing.pub)
  :
  `git show origin/main:deploy/installer/release-signing.pub | sha256sum`
  .
- Установщик проверяет хеш SHA-256 и RSA-подпись пакета приложения и
  списка зависимостей перед установкой, и «как Bash, так и PowerShell останавливаются, если
  требуемая проверка завершается сбоем» (тот же раздел).
- [installer.yml](../../.github/workflows/installer.yml)
  выполняет сборку именно из `main`
  
  ревизии и проверяет результат на Linux и Windows. Он ожидает, пока `checks.yml`
  
  и `security-audit.yml`
  будут находиться в одном и том же коммите, публикует только в том случае, если `main`
  не сдвинулся,
  а затем проверяет общедоступные загрузки. В [manifest](https://get.destroy.tools/manifest.json)
  фиксируются версия, коммит, ID релиза и SHA-256 каждого артефакта.
- Альтернативами являются релизы GitHub с заверенным ZIP-архивом исходного кода ([release source archive](../TRUST.md#release-source-archive)
  ),
  установка из исходного кода и [Docker](../DEPLOYMENT.md)
  .

**Результат.** Чтобы проверить скрипт перед его запуском, используйте команды verify-first; в любом случае
программа установки проверяет подписи пакета и блокировки. Происхождение исходного кода подтверждается для
[ZIP-архива с исходным кодом релиза](../TRUST.md#release-source-archive).

<a id="tests-and-continuous-integration"></a>
## Тестирование и непрерывная интеграция

- Набор регрессионных тестов состоит из 126 тестовых модулей, содержащих около 950 тестовых функций. Он запускается в
  закрытой среде валидации с использованием синтетических учетных записей и фиктивного транспортного протокола Telegram.
  Тестовые файлы исключены из Git и из архивов исходного кода
  ([`.gitignore`](../../.gitignore), [`tools/build_source.py`](../../tools/build_source.py) [журнале валидации](../VERIFICATION.md).
- [Проверки](../../.github/workflows/checks.yml): lint, аудит закреплённых зависимостей, согласованность автономного
  верификатора, установка wheel и готовность пустой рабочей области. Полный запуск платформы
  охватывает Linux, Windows и macOS с Python 3.11–3.13.
- [Проверки PR](../../.github/workflows/pr-check.yml) повторяют проверку lint, аудит зависимостей и
  проверку готовности установленных пакетов, а также создают публичный сайт.
- [Приемка установщика](../../.github/workflows/installer-acceptance.yml) проверяет подписанные
  артефакты установщика и ревизию исходного кода, а затем устанавливает и проверяет файл wheel.
- [Проверки запечатанного образа](../../.github/workflows/sealed-checks.yml) создают запечатанный образ сборщика
  из закреплённой ревизии и импортирует его без подключения к сети.
- [Аудит безопасности](../../.github/workflows/security-audit.yml) запускает pip-audit на закреплённых файлах блокировки
, CodeQL для Python, JavaScript и рабочих процессов, а также Trivy на образах контейнеров.
- [Фузинг](../../.github/workflows/fuzz.yml) тестирует архив верификатора и разбор JSON.

**Результат.** Общедоступные рабочие процессы и журналы их выполнения показывают, какие проверки CI проводились для каждого
коммита. Сам набор регрессионных тестов не публикуется.
