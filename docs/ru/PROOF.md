# Стенд, на котором сбор можно проверить

Для первого живого стенда достаточно **одного сервера, двух или трёх отдельных
Telegram-аккаунтов и канала с контрольными хешами**. У каждого аккаунта своё рабочее
пространство, журнал и ключ. Отдельный процесс Proof опрашивает их и показывает общую
страницу состояния. Он получает только witness-токены, без сессий и переписки.

![Монитор Proof с тремя синтетическими аккаунтами](../assets/proof.png)

| Что проверяем | Чем подтверждаем |
| --- | --- |
| История не переписана после проверки | Опубликованный хеш и подписи; сверка с последующим экспортом |
| Коллектор записывает события сообщений | Подписанные счётчики новых сообщений, правок и удалений; независимый пересчёт по экспорту |
| Конкретное сообщение действительно дошло до каждого аккаунта | Контрольная последовательность «отправить → изменить → удалить» из другого Telegram-клиента |

Один растущий хеш не доказывает сбор: журнал растёт и от служебных heartbeat-записей.
На странице Proof они не засчитываются как новые сообщения. События восстановления
и загрузки старой истории также показаны отдельно.

## Запуск

1. В панели добавьте два отдельных аккаунта, выберите тестовую группу и включите сбор.
   Для каждого пространства создайте токен в **Дополнения → Бот в Telegram**, сохраните токен
   в отдельный файл и выпишите отпечаток ключа коллектора.
2. Скопируйте [пример конфигурации](../../deploy/proof.config.example) в
   `proof-config/proof.json`. Укажите реальные адреса, ID рабочих пространств,
   отпечатки ключей и пути к файлам токенов. Названия аккаунтов на странице публичные —
   удобно использовать нейтральные «Аккаунт A», «Аккаунт B».
3. Запустите проверку конфигурации и сервис:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.proof.yaml run --rm --no-deps proof \
  python -m tgwitness.proof --config /proof-config/proof.json --check-config
docker compose -f compose.yaml -f deploy/compose/compose.proof.yaml up -d --build
```

Страница доступна на `127.0.0.1:8790`. Для публичного доступа используйте отдельный
HTTPS-домен — [пример Caddy](../../deploy/Caddyfile.proof.example). Панель управления
аккаунтами публиковать вместе с ней не требуется. Каталог `proof-config` исключён из
Git и Docker-сборки; доступ к секретам должен иметь только оператор и пользователь
контейнера с UID 10001.

Без Docker замените в конфигурации `data_dir` на `../proof-data`, адреса — на реальные
адреса коллектора, затем запустите в окружении проекта:

```sh
python -m tgwitness.proof --config proof-config/proof.json --check-config
python -m tgwitness.proof --config proof-config/proof.json
```

Проверка конфигурации не подключается к Telegram или коллектору. Опрос по умолчанию
идёт раз в пять минут. Для каждого аккаунта видны подписанные счётчики, время
последнего события сообщения, очередь вложений, ошибки и хеш конца журнала. Пропавший
ответ, просроченная проверка или смена ключа не отображаются как исправный сбор.

## Трансляция хешей

Добавьте бота в свой канал с правом публикации. В каждую запись аккаунта в конфигурации
добавьте `channel` и `bot_token_file`:

```json
{"channel": "@your_proof_channel", "bot_token_file": "proof-bot-token.txt"}
```

Witness публикует хеш, счётчики, прирост между проверками и подписанный блок `TGW1`.
Ошибки ответа тоже попадают в журнал и канал. Первое измерение — начальная точка,
оно не изображает прирост. Отпечатки ключей witness сохраните отдельно от сервера.
Для каждого аккаунта ведётся собственный witness-журнал в `proof-data/<алиас>`.

Для своего HTTP/SOCKS5-прокси и сервера Bot API доступны поля `proxy` и `bot_api` в
записи аккаунта. Они относятся к свидетелю; MTProxy собирающего аккаунта настраивается
отдельно. [Настройка бота и каталога прокси через интерфейс](WITNESS.md).

## Контрольное сообщение — проверяем сам сбор

Сгенерируйте уникальную метку на машине независимого отправителя, вне коллектора;
команда ничего не отправляет:

```sh
python tools/verify_live_probe.py --new
```

Из другого Telegram-клиента отправьте в тестовую группу сообщение с этой меткой
и текстом `version 1`. Убедитесь, что оно появилось у обоих коллекторов. Измените
**то же сообщение**, оставив метку и заменив текст на `version 2`. После сохранения
правки удалите сообщение. Дождитесь уведомлений об удалении и следующего хеша в канале.

Экспортируйте журналы обоих аккаунтов и проверьте их:

```sh
python tools/verify_live_probe.py --nonce TGW-PROBE.REPLACE_WITH_GENERATED_NONCE \
  --workspace account-a account-a.zip FINGERPRINT_A \
  --workspace account-b account-b.zip FINGERPRINT_B --out probe-result.json
```

Проверяются подписи полных архивов, разные ключи аккаунтов и последовательность
нового сообщения, изменённой версии и удаления. Повторный экспорт одного аккаунта
за два разных не принимается. Загрузка сообщения только из истории не считается
проверкой живого приёма. Повторите сценарий после планового рестарта и ограниченного
разрыва сети; сохраните реальные успехи и пропуски. Сверяйте аккаунты с одинаковой
видимостью группы и одинаковыми настройками сбора.

## Проверка публичного JSON

На странице скачайте подписанный JSON, а из панели — соответствующий ZIP журнала:

```sh
python tgwitness/verify.py proof-account-a.json --fingerprint COLLECTOR_SHA256 \
  --witness-fingerprint WITNESS_SHA256 --evidence tgwitness-evidence.zip
```

Verifier проверит обе подписи, хеш нужного префикса журнала и заново посчитает события.
Без `--evidence` проверяются подписи, но не соответствие счётчиков реальным записям.
Проценты полноты и происхождение всех сообщений такая подпись не доказывает.

На одном сервере коллектор и witness зависят от одного оператора и одного хоста.
При падении всего сервера локальный witness тоже остановится. Для более сильного
пруфа вынесите witness на другой сервер/к другому оператору и добавьте внешний
контроль доступности. Полная схема и границы проверки — в [английской инструкции](../PROOF.md).

Автоматическая проверка новой страницы использует три синтетических пространства
на одном локальном сервере. Живой пилот на нескольких аккаунтах и Docker-развёртывание
нужно подтвердить отдельными результатами на выбранном сервере.
