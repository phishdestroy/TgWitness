# تیناری اور آپریشنز

## انسٹالیشن کا انتخاب کریں

پورٹیبل پیکیج کے لیے GitHub Releases سے `TgWitness-<version>-windows-amd64-portable.zip` نکالیں۔ دوسرے طریقوں کے لیے سورس ZIP ڈاؤن لوڈ کر کے نکالیں یا ریپوزیٹری کلون کریں، پھر پروجیکٹ ڈائریکٹری سے مندرجہ ذیل کمانڈ چلائیں:

| تنصیب | شروع کریں | کیا یہ پس منظر میں چلتا ہے؟ |
| --- | --- | --- |
| ونڈوز پورٹیبل پیکیج | `TgWitness.cmd` | نہیں؛ ونڈو کھلی رکھیں۔ |
| مقامی ونڈوز | `Start.cmd` | نہیں؛ پسِ منظر میں استعمال کے لیے اختیاری لاگ آن ٹاسک استعمال کریں۔ |
| مقامی لینکس/میک او ایس | `sh start.sh` | نہیں؛ پسِ منظر میں استعمال کے لیے systemd/launchd استعمال کریں۔ |
| کسی بھی سپورٹڈ ہوسٹ پر ڈوکر | `docker compose up -d --build --wait` | جی ہاں، جب Docker ڈیمن چل رہا ہو۔ |
| ونڈوز پر ڈاکر ہیلپر | `scripts\Docker.cmd` | جی ہاں؛ مددگار ویب سرور کی صحت کا انتظار کرتا ہے۔ |
| Linux/macOS پر ڈاکر ہیلپر | `sh scripts/docker-start.sh` | جی ہاں؛ مددگار ویب سرور کی صحت کا انتظار کرتا ہے۔ |

نیٹیو اسٹارٹ اپ ایک نجی `.venv` بناتا ہے اور منسلک انحصارات انسٹال کرتا ہے۔ Docker انہیں امیج کے اندر بناتا ہے، بغیر ہوسٹ Python کی ضرورت کے۔ پہلی بار سیٹ اپ کے لیے انٹرنیٹ کنکشن ضروری ہے۔ جب کوئی Python 3.11+ نہ ملے تو `Start.cmd` موجودہ Windows صارف کے لیے Python 3.12 انسٹال کرنے سے پہلے پوچھتا ہے (winget کے ذریعے، ورنہ اس کے Python Software Foundation کے دستخط کی تصدیق کے بعد python.org انسٹالر)؛ یہ کبھی بھی ایڈمنسٹریٹر کی اجازت نہیں مانگتا۔ Docker اور OS سروسز پہلے سے ضروری رہتی ہیں۔

نیٹیو اور پورٹیبل انسٹالیشنز اپنے فولڈر کے اندر ``data/live`` استعمال کرتی ہیں۔ Docker ``tgwitness-data`` نامی والیوم کو ``/data`` پر استعمال کرتا ہے۔ یہ الگ الگ انسٹالیشنز ہیں جب تک آپ جان بوجھ کر مکمل ڈیٹا ڈائریکٹری منتقل نہ کریں۔ نئے Docker کنٹینر سے توقع نہ کریں کہ وہ نیٹیو اکاؤنٹس خود بخود دریافت کر لے گا۔

## تنصیب کی ضروریات

مقامی تنصیب کے لیے Python 3.11 یا اس کے بعد کا ورژن، `venv` اور `ensurepip`، پہلی ڈیپنڈنسی کی تنصیب کے لیے انٹرنیٹ کنکشن، اور `.venv` کے لیے لکھنے کے قابل پروجیکٹ ڈائریکٹری درکار ہے۔ بنڈل شدہ پینل کے لیے Node.js یا فرنٹ اینڈ بلڈ کی ضرورت نہیں ہے۔ لانچر کو اپنے معمول کے OS اکاؤنٹ سے چلائیں؛ TgWitness کو ایڈمنسٹریٹر/روٹ حقوق کی ضرورت نہیں ہے۔

- **ونڈوز:** `Start.cmd` پہلے `py -3` چیک کرتا ہے، پھر `python`، پھر ڈیفالٹ پر-یوزر اور پروگرام فائلز انسٹال فولڈرز، اور ورژن 3.11 یا اس کے بعد درکار ہے۔ اگر ان میں سے کوئی کام نہ کرے تو یہ اوپر بیان کردہ خودکار پر-یوزر انسٹالیشن پیش کرتا ہے۔ `py -3 start.py` بھی کام کرتا ہے۔ پورٹیبل پیکج کو بالکل بھی پائتھن کی ضرورت نہیں۔
- **Linux:** `start.sh` پہلے `python3.13`، `python3.12`، `python3.11`، `python3` اور `python` کو آزمائیں، اور جب کوئی موزوں نہ ہو تو apt، dnf، pacman، zypper، apk یا Homebrew کے لیے انسٹال کمانڈ پرنٹ کریں۔ Debian/Ubuntu تنصیب کے لیے منتخب انٹرپریٹر سے مطابقت رکھنے والا `python3-venv` پیکیج درکار ہو سکتا ہے۔ ڈسٹری بیوشن کے پرانے ڈیفالٹ پائتھن کو پائتھن 3.11+ سے تبدیل یا اس کے ساتھ ضمیمہ کرنا ضروری ہے۔
- **macOS:** موجودہ Python 3.11+ کی تقسیم انسٹال کریں؛ یہ فرض نہ کریں کہ OS فراہم کردہ انٹرپریٹر اس شرط کو پورا کرتا ہے۔ پروجیکٹ ڈائریکٹری سے `python3 start.py` استعمال کریں۔
- **Docker:** Compose v2.20 یا اس سے نئے کے ساتھ Docker Engine/Desktop استعمال کریں۔ Docker Desktop کو Windows پر Linux کنٹینرز استعمال کرنا ضروری ہے۔ کنٹینر اپنی Python ڈیپنڈنسیز خود انسٹال کرتا ہے؛ ہوسٹ کو الگ Python انسٹالیشن کی ضرورت نہیں۔

ڈیٹا ڈائریکٹری کے لیے مستقل مقامی اسٹوریج استعمال کریں۔ پیغامات، میڈیا، WAL کی ترقی، ایکسپورٹس اور بیک اپ کی بنیاد پر گنجائش کا منصوبہ بنائیں؛ ہر ورک لوڈ کے لیے شواہد پر مبنی کوئی یونیورسل کم از کم ڈسک/RAM کی وضاحت موجود نہیں ہے۔ CPU آرکیٹیکچرز اور Python ورژنز جن کے پاس مطابقت پذیر dependency wheels نہیں ہیں، انہیں اضافی بلڈ ٹولز اور اپنی الگ توثیق کی ضرورت پڑ سکتی ہے۔ "پورٹیبل" کا مطلب یہ نہیں کہ یہ ہر آپریٹنگ سسٹم یا ہارڈویئر پر چلتا ہے۔

Windows 11/Python 3.12 مقامی طور پر تصدیق شدہ ہیں۔ Linux/macOS/کنٹینر کی تعریفیں اور CI فراہم کیے گئے ہیں لیکن اس ڈیولپمنٹ ہوسٹ پر چلائے نہیں گئے ہیں۔ درست دائرہ کار کے لیے [VERIFICATION.md](../VERIFICATION.md) دیکھیں۔

## مقامی کمپیوٹر

ونڈوز پر `Start.cmd` استعمال کریں یا لینکس/macOS پر `sh start.sh`۔ `scripts\Setup.cmd` یا `sh start.sh --setup-only` ماحول تیار کرتا ہے۔ لانچر پہلی بار استعمال پر انحصار شدہ فائلز انسٹال کرتا ہے؛ بعد میں لانچ کرنے پر ماحول دوبارہ استعمال ہوتا ہے۔ سیٹ اپ اور ٹیلیگرام سے ڈیٹا اکٹھا کرنے کے لیے انٹرنیٹ کنکشن ضروری ہے، لیکن موجودہ ریکارڈز براؤز کرنا اور ایکسپورٹس بنانا آف لائن بھی ممکن ہے۔

`python start.py --check` کو سیٹ اپ کے بعد چلائیں تاکہ مقامی انحصار، Ed25519، اسٹوریج، کلید کی تشکیلات اور سننے کا پتہ بغیر کلیکٹر شروع کیے جانچا جا سکے۔ ساختی آؤٹ پٹ کے لیے `--json` استعمال کریں۔ مطلوبہ `--data-dir`، `--host` اور `--port` پاس کریں۔ یہ چیک پیکیجز انسٹال نہیں کرتا، جرنل نہیں بناتا یا ٹیلیگرام سے کنکٹ نہیں کرتا؛ یہ سالمیت یا کوریج کی اہلیت نہیں ہے۔ Startup علیحدہ طور پر موجودہ جرنلز کی تصدیق کرتا ہے۔ `python start.py --help` بھی تنصیب سے گریز کرتا ہے۔

اختیارات:

start.py استعمال کرنے کے بعد، Windows پر `.venv\Scripts\python.exe` یا Linux/macOS پر `.venv/bin/python` کے ساتھ ضمنی کمانڈز چلائیں، یا پہلے اس ماحول کو فعال کریں۔ ذیل میں دیے گئے `python -m ...` کے مثالیں فرض کرتی ہیں کہ ماحول پہلے سے فعال ہے۔

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

ماحولیاتی متغیرات: TGWITNESS_DATA, TGWITNESS_HOST, TGWITNESS_PORT, TGWITNESS_TOKEN۔ TGWITNESS_VAULT_KEY_FILE نئی تنصیب کے لیے بیرونی کلید موڈ منتخب کرتا ہے؛ نیچے دیکھیں۔ TGWITNESS_TOKEN، اگر فراہم کیا جائے تو اس میں کم از کم 24 حروف ہونے چاہئیں؛ ایک کرپٹوگرافک طور پر بے ترتیب قدر استعمال کریں۔ اس کے بغیر، ایپ panel-token.txt میں 256-بٹ کا بے ترتیب ٹوکن پیدا کرتی ہے۔ ماحولیاتی اووررائیڈ اس فائل کو دوبارہ نہیں لکھتا۔ اسناد کو تبدیل کرنے کے لیے دوبارہ شروع کریں۔

بالکل ایک ہی عمل ڈیٹا ڈائریکٹری کا مالک ہو سکتا ہے۔ ایک کراس پلیٹ فارم OS فائل لاک غیر ارادی متوازی لکھنے والوں کو روکتا ہے۔ ایک Uvicorn ورکر استعمال کریں۔ پینل کسی بھی تعداد میں ورک اسپیسز کا انتظام کر سکتا ہے، اضافی ورک اسپیس ڈائریکٹریز profiles/<id>/ کے تحت۔ الگ الگ سروس انسٹنسز کے لیے الگ الگ ڈائریکٹریز اور پورٹس استعمال کریں۔ SQLite WAL فائلیں مقامی مستقل اسٹوریج میں ہونی چاہئیں، نیٹ ورک فائل سسٹم میں نہیں۔ ایک ہی والیوم کو ریپلیکیس کے درمیان شیئر نہ کریں۔

## ونڈوز پورٹیبل پیکیج

ہر GitHub ریلیز میں `TgWitness-<version>-windows-amd64-portable.zip` اور اس کا `.sha256` شامل ہوتا ہے۔ اس میں python.org سے حاصل کردہ سرکاری ایمبیڈ ایبل Python 3.12 رن ٹائم (چیک سم `tools/build_portable.py` میں پن کیا گیا)، TgWitness اور اس کی پن کی گئی ڈیپنڈنسیز، اور تین لانچرز شامل ہیں:

| فائل | مقصد |
| --- | --- |
| `TgWitness.cmd` | پینل شروع کریں؛ اضافی اختیارات منتقل کیے جاتے ہیں، مثلاً `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | `data\demo` میں مصنوعی ڈیمو شروع کریں |
| `TgWitness-Check.cmd` | شروع کیے بغیر تیاری کی جانچ چلائیں |

پورے آرکائیو کو لکھنے کے قابل فولڈر میں نکالیں، جیسے `Documents\TgWitness`؛ اسے ZIP کے اندر یا Program Files سے نہ چلائیں۔ رن ٹائم ایک الگ موڈیول راستہ استعمال کرتا ہے، اس لیے دوسری Python تنصیبات اور `PYTHONPATH` اس پر اثر نہیں ڈالتیں۔ ڈیٹا پیکج کے `data` فولڈر میں محفوظ رہتا ہے۔ اپ ڈیٹ کرنے کے لیے، TgWitness کو روک دیں، نئے ورژن کو ایک نئے فولڈر میں نکالیں اور `data` فولڈر کو منتقل کر دیں۔

Python 3.12 کے ساتھ 64-بٹ ونڈوز پر خود بنائیں:

~~~sh
python tools/build_portable.py
~~~

بلڈر رن ٹائم چیک سم کی تصدیق کرتا ہے، محدود انحصاروں کو پیکیج میں انسٹال کرتا ہے، ضم شدہ انٹرفریٹر کے ساتھ تیاری کی جانچ چلاتا ہے اور ZIP اور چیک سم کو `dist/` میں لکھتا ہے۔

## کنٹینر

```sh
docker compose up -d --build --wait
```

یہ /data کے لیے ایک نامزد مستقل والیوم بناتا ہے۔ ویب پورٹ کو 127.0.0.1:8787 پر میپ کیا گیا ہے۔ یہ عمل UID 10001 کے طور پر چلتا ہے، جس کی صلاحیتیں محدود کی گئی ہیں، ایک صرف پڑھنے کے قابل روٹ فائل سسٹم، اور لکھنے کے قابل /data اور /tmp کے ساتھ۔ `--wait` واپس کرنے سے پہلے ویب سرور کی صحت چیک کرتا ہے؛ یہ ٹیلیگرام کی اجازت یا ترسیل قائم نہیں کرتا۔ فراہم کردہ ہیلپرز بلڈنگ کے بعد 180 سیکنڈ کا ریڈی نیس ٹائم آؤٹ استعمال کرتے ہیں۔ ابتدائی انحصار کی ڈاؤن لوڈنگ اس سے زیادہ وقت لے سکتی ہے۔

دونوں بیس Compose فائلوں میں پروجیکٹ کا نام `tgwitness` استعمال ہوتا ہے، اس لیے کسی دوسری ڈائریکٹری میں نیا ریلیز نکالنے سے خاموشی سے نیا ڈیٹا والیوم منتخب نہیں ہوتا۔ اس پروجیکٹ کے لیے صرف ایک تعیناتی فعال رکھیں۔ آزاد تنصیبات کے لیے ایک منفرد `docker compose -p NAME ...` اور مختلف ہوسٹ پورٹ استعمال کریں، اور اپ ڈیٹس میں دونوں کو برقرار رکھیں۔ اگر آپ پرانی تعیناتی کے لیے مختلف پروجیکٹ نام استعمال کر رہے ہیں تو `-p` کے ساتھ اس کے اصل نام کا استعمال جاری رکھیں؛ `docker compose ls` موجودہ پروجیکٹس کی فہرست دکھاتا ہے۔

`deploy/env.example` کی کاپی `.env` میں کریں اور `TGWITNESS_PORT` کو تبدیل کریں تاکہ مختلف لوپ بیک پورٹ استعمال ہو۔ مثال کے طور پر، `TGWITNESS_PORT=8788` پینل کو `http://127.0.0.1:8788` پر ظاہر کرتا ہے؛ کنٹینر اب بھی پورٹ 8787 پر لسن کرتا ہے۔ `.env` Git کی طرف سے نظر انداز کیا گیا ہے۔

ابتدائی ٹوکن حاصل کریں:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

مفید کمانڈز:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` کریش یا Docker ڈیمون کے دوبارہ شروع ہونے کے بعد کلیکٹر کو دوبارہ شروع کرتا ہے۔ لینکس سرور پر، اپنے ڈسٹری بیوشن کے سروس مینیجر (عموماً `sudo systemctl enable --now docker`) کے ذریعے بوٹ پر ڈوکر کو فعال کریں۔ ونڈوز/macOS پر، ڈوکر ڈیسک ٹاپ کی 'start-at-sign-in' سیٹنگ کو فعال کریں۔ ڈیسک ٹاپ سے سائن آؤٹ، سلیپ موڈ، یا رُکا ہوا ڈوکر ڈیمون کلیکشن میں خلل ڈال سکتا ہے۔ ایک واضح طور پر رُکا ہوا کنٹینر تب تک رُکا رہتا ہے جب تک آپ اسے دوبارہ شروع نہ کریں۔

مثال کے کنفیگریشن میں /tmp والیوم کو 512 MiB تک محدود کیا گیا ہے۔ ایکسپورٹ کی تیاری ہر ورک اسپیس کے `temporary-exports/` کو مستقل /data پر استعمال کرتی ہے۔ وہاں متوازی برآمدات، جرنل/WAL کی ترقی، میڈیا اور بیک اپ کے لیے جگہ محفوظ کریں۔ لانچر اور Docker deploy/constraints.txt استعمال کرتے ہیں تاکہ اہل رن ٹائم انحصار ورژنز کو پن کیا جا سکے۔ یہ ہیش لاک شدہ سپلائی چین نہیں ہے: Python بیس امیج اور پیکیج آرٹیفیکٹس کو اب بھی آزادانہ ریلیز کی اہلیت درکار ہے۔

جب تک آپ جرنل اور کیز کو تباہ کرنے کا ارادہ نہ رکھتے ہوں، docker compose down -v استعمال نہ کریں۔ کنٹینر کی ہیلتھ رپورٹس ویب سرور کی دستیابی بتاتی ہیں، نہ کہ کامیاب ٹیلیگرام کیپچر۔ پینل کے کلیکٹر کی حالت، ہارٹ بیٹ، غلطیاں، اور کوریج ایونٹس کا معائنہ کریں۔

### آزاد شاہد کا پروفائل

اختیاری `witness` سروس ایک [آزاد گواہ](../WITNESS.md) کو اپنے کنٹینر میں چلاتی ہے، جس کی اپنی کلید اور جرنل `witness-data` والیوم میں ہوتے ہیں اور کلیکٹر کے لیے صرف ریڈ-اونلی گواہ ٹوکن فراہم کرتی ہے۔ ٹوکن کو پینل کے **Witness** صفحے پر بنائیں، اسے bot ٹوکن اور چینل کے ساتھ `.env` میں شامل کریں، پھر پروفائل شروع کریں:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

یہ سروس Compose نیٹ ورک کے اندر کلیکٹر تک پہنچتی ہے، جیسا کہ `http://tgwitness:8787`۔ (`TGWITNESS_WITNESS_COLLECTOR` اسے اووررائڈ کرتا ہے، مثال کے طور پر `/profiles/<workspace ID>` کسی دوسرے ورک اسپیس کے لیے)۔ کسی الگ سرور پر چلنے والے ویٹنس کے لیے، جہاں کوئی اور اسے چلا رہا ہو، وہاں `deploy/compose/compose.witness.yaml` استعمال کریں اور `TGWITNESS_WITNESS_COLLECTOR` کو کلیکٹر کے HTTPS ایڈریس پر سیٹ کریں؛ اس فائل میں صرف ویٹنس شامل ہوتی ہے۔

## شائع شدہ امیج انسٹال کریں

یہ ایک کامیاب [ریلیز ورک فلو](#خودکار-گٹ-ہب-ریلیزز) اور عوامی GHCR پیکیج کنفیگریشن کے بعد دستیاب ہوتا ہے۔ ریپوزیٹری کا مالک/نام اس سورس ٹری میں ہارڈ کوڈ نہیں کیا گیا ہے۔ اس ریلیز کے ورک فلو کے خلاصے میں دکھائی گئی تصویر استعمال کریں۔

`deploy/env.example` کی کاپی `.env` میں کریں۔ `TGWITNESS_IMAGE` کو شائع شدہ ورژن پر سیٹ کریں، **چھوٹے حروف کے** ریپوزیٹری پاتھ کا استعمال کرتے ہوئے، مثال کے طور پر:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.7.1
TGWITNESS_PORT=8787
```

`compose.yaml` کے بجائے اس فائل کو اکیلے چلائیں:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

ہوسٹ پر کسی سورس بلڈ، پائتھن یا کمپائلر کی ضرورت نہیں ہے۔ ریلیز ورک فلو لینکس AMD64 اور ARM64 کنٹینرز کو ہدف بناتا ہے، بشمول Docker Desktop کے لینکس VM۔ ورک فلو کے خلاصے سے ورژن ٹیگ یا `ghcr.io/owner/repository@sha256:...` استعمال کریں۔ `latest` ٹیگ کی حرکت یا بغیر نگرانی کے ایپلیکیشن اپ گریڈ ترتیب نہیں دیا گیا ہے۔ جب ان کے پروجیکٹ کے نام مماثل ہوں تو امیج اور سورس ورژنز ایک ہی ڈیٹا والیوم استعمال کرتے ہیں۔

## سرور پر خودکار HTTPS

ایک سرور استعمال کریں جس میں Docker نصب ہو، ایک ایسا ڈومین جس پر آپ کا کنٹرول ہو، اور مستقل مقامی اسٹوریج۔ ڈومین کے A/AAAA ریکارڈز کو سرور کی طرف پوائنٹ کریں؛ IPv6 کی دستیابی پر AAAA ریکارڈ شائع کریں۔ سرٹیفکیٹ جاری کرنے کے لیے اندر آنے والی TCP پورٹ 80 اور 443 اور باہر جانے والی DNS/HTTPS کی اجازت دیں۔ دیگر خدمات کو پہلے سے ان پورٹس پر قابض نہیں ہونا چاہیے۔

`deploy/env.example` کو `.env` میں کاپی کریں اور بغیر اسکیم یا راستے کے ہوسٹ نام مقرر کریں:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

HTTPS اوورلے کے ساتھ سورس بلڈ شروع کریں:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

شائع شدہ تصویر کے لیے، پہلی فائل کے طور پر `deploy/compose/compose.image.yaml` استعمال کریں۔ بعد میں اسٹیٹس، لاگز، اپ ڈیٹ اور اسٹاپ کمانڈز کے لیے دونوں `-f` آرگومنٹس کو برقرار رکھیں۔

Caddy سرٹیفیکیٹ حاصل اور تجدید کرتا ہے، HTTP کو HTTPS پر ری ڈائریکٹ کرتا ہے، اور نجی Compose نیٹ ورک پر موجود کلیکٹر کو درخواستیں فارورڈ کرتا ہے۔ سرٹیفیکیٹ کی حالت کے لیے ایک مستقل والیوم مختص ہے۔ کلیکٹر کا براہِ راست ہوسٹ پورٹ صرف لوپ بیک کے لیے محدود رہتا ہے۔ فراہم کردہ Caddy کنفیگریشن میں رسائی لاگنگ فعال نہیں ہے۔

`https://watch.your-domain.org` کھولیں اور پینل ٹوکن درج کریں۔ تیاری کی حالت سرٹیفیکیٹ جاری ہونے یا بیرونی رسائی کی تصدیق نہیں کرتی۔ اگر HTTPS تیار نہیں ہے تو DNS، فائر وال کے قواعد، اور:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

فراہم کردہ Caddy امیج اپنے ``2-alpine`` ٹیگ کے مطابق ہوتی ہے۔ پل کرنے سے وہ امیج ریفریش ہو جاتی ہے؛ اگر آپ کو فکسڈ انفراسٹرکچر ورژنز کی ضرورت ہو تو اپنی ڈیپلائمنٹ میں ایک ٹیسٹ شدہ ڈائجسٹ پن کریں۔

## اپ ڈیٹس اور بیک اپس

اپ ڈیٹس کے دوران Compose پروجیکٹ کا نام اور ڈیٹا والیوم برقرار رکھیں۔ سب سے پہلے کلیکٹر کو روکیں اور مکمل بیک اپ بنائیں۔ ڈیفالٹ سورس پر مبنی تعیناتی کے لیے:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

ہر بار ذخیرہ کرنے کی جگہ کے باہر ایک نیا بیک اپ مقام استعمال کریں اور اسے اکاؤنٹ تک رسائی کے قابل مواد کے طور پر محفوظ رکھیں۔ مثال کے راستے صرف وضاحتی ہیں؛ اپنی نجی بیک اپ جگہ استعمال کریں۔ پوری ڈائریکٹری کاپی کریں، بشمول پوشیدہ فائلیں، تمام ورک اسپیسز، کیز، جرنلز اور میڈیا۔ اگر ترتیب دیا گیا ہو تو بیرونی والٹ ماسٹر کلید کو الگ سے بیک اپ کریں۔ ثبوت ZIP قابل بحالی ایپلیکیشن بیک اپ نہیں ہے۔ HTTPS کے لیے، اگر آپ کو اس کا سرٹیفیکیٹ/اکاؤنٹ کی حالت برقرار رکھنی ہو تو Caddy والیومز کو بھی محفوظ کریں۔

ماخذ تعیناتی کے لیے، نئی ریلیز فائلیں حاصل کریں اور چلائیں:

```sh
docker compose up -d --build --wait
```

تصویری تعیناتی کے لیے، `TGWITNESS_IMAGE` کو مطلوبہ ورژن میں تبدیل کریں، پھر چلائیں:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

پچھلی stop/copy کمانڈز کے لیے اپنی انسٹالیشن کی Compose فائل(یں) بھی استعمال کریں۔ `.env`، کسٹم کنفیگریشن، اور ایک ہی پروجیکٹ کا نام برقرار رکھیں۔ `down` نامزد والیومز کو برقرار رکھتا ہے؛ **`down -v`** **انہیں حذف کرتا ہے۔** `.venv` کو آپریٹنگ سسٹمز یا Python ورژنز کے درمیان کاپی نہ کریں۔ نیٹیو اپ ڈیٹس کے لیے، TgWitness کو روک دیں، اس کے مکمل ڈیٹا ڈائریکٹری کا بیک اپ بنائیں، سورس فائلز کو تبدیل کریں، اور لانچ سے پہلے `python start.py --setup-only` چلائیں۔

اپ ڈیٹ کے بعد پینل تک رسائی، اکاؤنٹ کی شناخت، مشاہدے کی حالت اور کوریج چیک کریں۔ دوبارہ شروع کرنے سے رہ جانے والی ٹیلیگرام اپ ڈیٹس بحال نہیں ہوتیں۔ اگر مستقبل کا کوئی ورژن اسٹوریج فارمیٹس تبدیل کر دے تو رول بیک کے لیے پری اپ ڈیٹ بیک اپ درکار ہو سکتا ہے۔

## خودکار گٹ ہب ریلیزز

[ریلیز کا عمل](../../.github/workflows/release.yml) تب دستیاب ہوتا ہے جب اس پروجیکٹ کو GitHub ریپوزیٹری میں Actions فعال کرکے پش کیا جائے۔ یہ تب چلتا ہے جب GitHub ریلیز **شائع** ہوتی ہے، بشمول پری ریلیز۔ صرف ڈرافٹس اور ٹیگ پشز پیکجز شائع نہیں کرتے۔

1. پیکج کا ورژن اور تبدیلیوں کا لاگ سیٹ کریں، پھر ایک ریلیز شائع کریں جس پر `v` اور بالکل درست `pyproject.toml` ورژن ٹیگ کیا گیا ہو، جیسے `v0.7.1`۔
2. یہ ورک فلو ٹیگ کی توثیق کرتا ہے اور مشترکہ Windows/Linux/macOS Python، عمومی/اکاؤنٹ-امپورٹ/QR براؤزر، سورس پیکج، اور Docker چیکس چلاتا ہے۔ تازہ نیٹیو انسٹالیشن بھی تینوں آپریٹنگ سسٹمز پر Python 3.12 استعمال کرتے ہوئے کی جاتی ہے۔
3. ان چیکس کے پاس ہونے کے بعد، یہ QEMU کے تحت ARM64 امیج کا اسموک ٹیسٹ کرتا ہے، AMD64/ARM64 امیجز کو `ghcr.io/<lowercase-owner>/<lowercase-repository>:<version>` پر شائع کرتا ہے، اور ریلیز کے ساتھ سورس ZIP، چیک سم، اور Python ویل منسلک کرتا ہے۔ ایک الگ Windows جاب پورٹیبل ZIP اور اس کا چیک سم تیار کر کے منسلک کرتا ہے۔
4. پہلی اشاعت کے بعد، GHCR پیکیج سیٹنگز کھولیں اور اگر گمنام امیج پلز مقصود ہیں تو ویزبلٹی کو **پبلک** پر سیٹ کریں۔ صرف ایک پبلک سورس ریپوزیٹری پبلک کنٹینر پیکیج کی ضمانت نہیں دیتی۔ تنظیم کی پالیسیاں پیکیج کی اشاعت کی اجازت ہونی چاہئیں۔ ورک فلو میں `GITHUB_TOKEN` استعمال ہوتا ہے؛ ریپوزیٹری میں کوئی رجسٹری پاس ورڈ یا VPS کی تفصیلات شامل نہیں ہونی چاہئیں۔

اس مقامی تیاری سے دور دراز ورک فلو کی کامیابی ثابت نہیں ہوئی۔ ARM64 ایمولیشن صرف ایک ابتدائی جانچ ہے، نہ کہ اصل ہارڈویئر یا لائیو ٹیلیگرام کے لیے اہلیت۔ یہ ریلیز پیکجنگ کو خودکار کرتا ہے؛ سرور شروع کرنے کے لیے اب بھی Compose کمانڈ اور اس کے ڈومین/ہوسٹ کے پیشگی تقاضوں کی ضرورت ہوتی ہے۔ جب کوئی ریلیز شائع ہوتی ہے تو موجودہ سرورز خاموشی سے اپ گریڈ یا ری اسٹارٹ نہیں ہوتے۔

## دور دراز سرور

سروس کو لوپ بیک پر محدود رکھیں اور SSH ٹنل استعمال کریں، یا HTTPS کو ریورس پراکسی پر ختم کریں۔ بنیادی Compose فائل صرف مقامی استعمال کے لیے ہے؛ اختیاری `deploy/compose/compose.https.yaml` اوورلے ایک ترتیب شدہ ڈومین کے لیے Caddy فراہم کرتا ہے۔ بیئرر ٹوکن کو URLs اور پراکسی لاگز سے دور رکھیں۔ ریورس پراکسی کو درخواست کے حجم اور کنکشن کی شرح کو محدود کرنا چاہیے۔ سادہ HTTP کو انٹرنیٹ پر ظاہر نہ کریں۔

systemd، Windows لاگ آن ٹاسک، macOS یوزر ایجنٹ اور Caddy کے لیے مثالیں [deploy/](../../deploy/README.md) میں فراہم کی گئی ہیں۔ تنصیب سے پہلے ان کے راستوں کا جائزہ لیں اور انہیں ڈھالیں۔ یہ فراہم کردہ ٹیمپلیٹس ہیں، نہ کہ مقامی طور پر چلائی جانے والی پلیٹ فارم کی تصدیقات۔ عام لانچر کے ذریعے کوئی بیک گراؤنڈ سروس یا ٹاسک رجسٹر نہیں ہوتا۔

ونڈوز پر، ایک بغیر ونڈو کے `pythonw.exe` لانچ اسٹارٹ اپ/سرور تشخیصی معلومات کو `logs/server.log` کے ڈیٹا ڈائریکٹری میں محفوظ کرتا ہے (فی فائل 5 MiB، دو گھمائے گئے بیک اپ)۔ کنسول لانچز کنسول لاگنگ برقرار رکھتی ہیں۔ HTTP رسائی لاگنگ دونوں موڈز میں غیر فعال ہے۔ لاگز کو ڈیٹا ڈائریکٹری کے ساتھ محفوظ کریں اور شیئر کرنے سے پہلے ان کا جائزہ لیں۔

## دوبارہ آغاز اور وقفے

آخری درخواست کردہ مشاہداتی حالت محفوظ کی جاتی ہے۔ اگر مشاہدہ فعال تھا تو آغاز میں منتخب ذرائع سے دوبارہ کنکشن قائم کرنے اور کام دوبارہ شروع کرنے کی کوشش کی جاتی ہے۔ دستی طور پر وقفہ دینے سے یہ ارادہ ختم ہو جاتا ہے۔ ناکام دوبارہ آغاز ریکارڈ کیا جاتا ہے اور پینل میں دکھایا جاتا ہے۔

StringSession اجازت برقرار رکھتا ہے لیکن Telethon کی پائیدار اپ ڈیٹ/اینٹیٹی حالت برقرار نہیں رکھتا۔ ڈائیلاگز شروع ہونے پر دوبارہ لوڈ ہوتے ہیں۔ Telegram/Telethon چلتے ہوئے کچھ ٹرانسپورٹ رکاوٹوں سے بحال ہو سکتے ہیں، لیکن TgWitness عمل کے دوبارہ شروع ہونے پر پائیدار ری پلے کا دعویٰ نہیں کرتا۔ ہر آغاز پر پچھلا جرنل ہیڈ اور آف لائن حد ریکارڈ کی جاتی ہے۔ مانیٹر ہر 10 سیکنڈ میں کنیکٹیویٹی چیک کرتا ہے اور ہر منٹ میں ایک ہارٹ بیٹ شامل کرتا ہے (**پیرامیٹرز → لائیوس ریکارڈ ہر**)۔ مختصر وقفے رہ سکتے ہیں؛ ایک منسلک ٹرانسپورٹ مکمل اپ ڈیٹ کی ترسیل کی ضمانت نہیں دیتا۔ اسنیپ شاٹس واضح موجودہ-تاریخی مشاہدات ہیں، کبھی بھی خلا کی مرمت نہیں کرتے۔

میڈیا کی قطار ہر ورک اسپیس کے SQLite ڈیٹا بیس میں محفوظ ہوتی ہے۔ ایک پیغام اور اس کا کام ایٹمی طور پر محفوظ کیے جاتے ہیں۔ منقطع شدہ چلنے والے کام دوبارہ شروع کرنے پر دوبارہ کوشش کے لیے بحال کیے جاتے ہیں۔ ہر ڈاؤن لوڈ کے لیے 120 سیکنڈ کا بنیادی ٹائم آؤٹ ہوتا ہے، اس کے علاوہ اس کے سائز کے مطابق 256 KiB/s رفتار کے حساب سے وقت دیا جاتا ہے، اور ہر اٹیچمنٹ کی قسم کے لیے 1–2,000 MiB کی حد ہوتی ہے؛ ٹائم آؤٹ، رفتار اور دوبارہ کوششیں **پیرامیٹرز** میں ترتیب دی جاتی ہیں۔ کلیکٹر ان فائلوں کو چھوڑ دیتا ہے جن کا سائز معلوم نہ ہو۔ وقفہ کرنے سے قطار میں موجود کام برقرار رہتا ہے۔ دوبارہ کوشش اصل مشاہدہ شدہ فائل ڈسکرپٹر استعمال کرتی ہے، بعد میں ترمیم شدہ پیغام کے تازہ ترین ورژن کو کبھی نہیں۔ عارضی ناکامیوں کے لیے محدود دوبارہ کوششیں ہوتی ہیں؛ میڈیا FloodWait وقفے ری اسٹارٹ کے بعد بھی برقرار رہتے ہیں۔ میڈیا بحالی ٹیلیگرام اپ ڈیٹ بحالی سے الگ ہے اور غائب شدہ فائلوں کو دوبارہ پیدا نہیں کر سکتی۔

## بیک اپ، بحالی، اور گنجائش

**پورے ڈیٹا ڈائریکٹری** کی کاپی کرنے سے پہلے عمل کو روک دیں، جس میں vault.key، signing.enc، credentials.enc، SQLite ڈیٹا بیس/WAL فائلیں، میڈیا، ٹوکن، چیک پوائنٹس، اور تمام پروفائلز/سب ڈائریکٹریز شامل ہیں۔ جب منزل کی سروس بند ہو تو مکمل کاپی بحال کریں۔ گمشدہ والٹ کیز یا سائننگ کی کے عدم مطابقت سے آغاز ناکام ہو جاتا ہے؛ زبردستی رسائی کے لیے کیز دوبارہ پیدا نہ کریں۔

خفیہ بیک اپ کو انکرپٹڈ اور رسائی کے کنٹرول کے تحت رکھیں۔ ایویڈنس ZIPs قابلِ حمل جائزہ آئٹمز ہیں، نہ کہ ایپلیکیشن بیک اپ یا ٹیلیگرام سیشن بیک اپ۔ خودکار طور پر برقرار رکھنے یا حذف کرنے کا کوئی انتظام نہیں ہے۔ تمام پیغامات، خام میٹا ڈیٹا، میڈیا، عارضی ایکسپورٹس اور بیک اپ کے لیے ڈسک اسپیس کا منصوبہ بنائیں۔

پورے جرنل کو لوڈ کرنے کے بجائے اسٹارٹ اپ کی تصدیق اور ایکسپورٹ اسٹریم ریکارڈز۔ ایک ایکسپورٹ ریڈ سنپ شاٹ کو پن کرتا ہے جبکہ نئی WAL لکھائی جاری رہ سکتی ہے؛ طویل چلنے والی ایکسپورٹس WAL صفحات کو برقرار رکھ سکتی ہیں، لہٰذا ڈسک کی گنجائش اب بھی اہم ہے۔ ZIPs غیر کمپریسڈ حالت میں 4 GiB تک محدود ہیں تاکہ آزاد معائنہ کار کے ڈیفالٹ سے مطابقت ہو؛ **پیرامیٹرز → سب سے بڑا سائنڈ ZIP** حد بڑھاتا ہے، اور ایسے آرکائیوز کو `verify.py --max-gib N` کے ساتھ تصدیق کیا جاتا ہے۔ دیگر فارمیٹس میں ایونٹ کی تعداد کی کوئی حد نہیں ہوتی۔ سپورٹڈ براؤزرز صارف کے منتخب کردہ فائل میں جوابی ٹکڑوں کو اسٹریم کرتے ہیں۔ دیگر براؤزرز زیادہ سے زیادہ 128 MiB تک بفر کرتے ہیں اور بڑے ٹرانسفرز کو تصدیق شدہ CLI کی طرف بھیجتے ہیں:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

`--profile ID` کو **Exports → Workspace ID** سے دوسرے ورک اسپیس کے لیے استعمال کریں، `--format zip|jsonl|csv|html`، `--url https://your-server` کو ریموٹ سرور کے لیے، یا `--max-mib` کو 5 GiB ٹرانسفر حد تبدیل کرنے کے لیے۔ صرف لوپ بیک کے لیے سادہ HTTP کی اجازت ہے۔ ٹوکنز ہیڈرز میں بھیجے جاتے ہیں، ری ڈائریکٹس مسترد کیے جاتے ہیں، موجودہ فائلیں اووررائٹ نہیں ہوتیں، اور نامکمل ڈاؤن لوڈز مکمل فائلوں کے طور پر شائع نہیں کیے جاتے۔ اگر TGWITNESS_TOKEN تیار کردہ ٹوکن کو اووررائڈ کرتا ہے، تو اس فعال قدر کو ایک علیحدہ محفوظ فائل میں استعمال کریں: panel-token.txt اووررائڈ کے ذریعے دوبارہ لکھا نہیں جاتا۔ کمانڈ کا SHA-256 صرف ایک ٹرانسفر چیک سم ہے؛ دستخط شدہ ZIP کی خود سے تصدیق کریں۔

سرور ایکسپورٹ فائلیں ہر ورک اسپیس کے نجی `temporary-exports/` میں رہتی ہیں۔ کامیاب جوابات اپنی فائلیں صاف کر دیتے ہیں۔ منقطع ایکسپورٹس اگلی ورک اسپیس شروعات پر ہٹا دی جاتی ہیں جب اس کا خصوصی انسٹنس لاک برقرار ہوتا ہے۔ یہ ڈائریکٹری اسٹوریج تھریٹ/کیپیسٹی ماڈل کا حصہ ہے؛ ایک خفیہ شدہ ڈیٹا والیوم استعمال کریں۔ پروڈکشن سطح کے کثیر گیگا بائٹ ٹرانسفرز کے لیے آپ کے ہدف سسٹم پر اہلیت کی تصدیق ضروری ہے۔

پینل قطار میں شامل/ناکام میڈیا، سب سے پرانا زیر التواء میڈیا، خالی ڈسک، ٹیلیگرام درخواستوں کی معطلی، اور وہ ذرائع جن کی رسائی تصدیق شدہ نہیں، دکھاتا ہے۔ یہ تشخیصی ٹول مکمل اینڈ ٹو اینڈ ڈیلیوری مانیٹر نہیں ہے۔ ورک اسپیسز ایک ہی عمل شیئر کرتے ہیں؛ ایک شور کرنے والا اکاؤنٹ پھر بھی دوسروں کو متاثر کر سکتا ہے۔ الگ ورکر پراسیسز، ریٹینشن/روٹیشن، پائیدار اپ ڈیٹ ریکوری، ریموٹ چیک پوائنٹ اینکرنگ، کردار، اور مکمل تعیناتی کی اہلیت برقرار ہیں۔

## کنیکشن اور تحفظ کے اختیارات

کنیکشن روٹس ہر ورک اسپیس کے لیے مخصوص ہیں اور اجازت سے پہلے ترتیب دیے جانے چاہئیں۔ SOCKS5/HTTP CONNECT پن کیے گئے python-socks انحصار کا استعمال کرتے ہیں۔ MTProxy Telethon کے تجرباتی بے ترتیب مابین ٹرانسپورٹ کا استعمال کرتا ہے؛ Fake TLS ee سیکریٹس کی حمایت نہیں کی جاتی۔ کوئی خودکار براہ راست فال بیک ترتیب نہیں دیا گیا۔ یہ پورے سسٹم کا نیٹ ورک روٹ نہیں ہے۔

نئی تنصیبات کے لیے، TGWITNESS_VAULT_KEY_FILE ایک الگ محفوظ بے ترتیب ماسٹر کی فائل کی طرف اشارہ کرتا ہے۔ اسے کنٹینر میں /data کے باہر صرف پڑھنے کے لیے ماؤنٹ کریں۔ ہر ورک اسپیس کے ساتھ عوامی vault.external.json سالٹ میٹا ڈیٹا اور ماسٹر کی کو الگ الگ محفوظ رکھیں۔ موجودہ مقامی والٹس کے لیے منصوبہ بند منتقلی ضروری ہے؛ اس متغیر کو سیٹ کرنے سے وہ خاموشی سے تبدیل نہیں ہوتے۔ پیغامات/میڈیا کی ذخیرہ اندوزی اور برآمدات ایپلیکیشن میں انکرپٹڈ نہیں ہیں۔ جہاں ضروری ہو انکرپٹڈ والیومز اور مناسب نجی عارضی اسٹوریج استعمال کریں۔
