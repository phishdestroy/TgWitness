# Розгортання та експлуатація

## Вибір інсталяції

Для портативного пакета розпакуйте `TgWitness-<version>-windows-amd64-portable.zip` з GitHub Releases. Для інших способів завантажте й розпакуйте ZIP-архів із вихідним кодом або клонуйте репозиторій, а потім виконайте з каталогу проєкту відповідну команду:

| Інсталяція | Запуск | Працює у фоні? |
| --- | --- | --- |
| Портативний пакет для Windows | `TgWitness.cmd` | Ні; не закривайте вікно. |
| Нативна в Windows | `Start.cmd` | Ні; для роботи у фоні використовуйте необов’язкове завдання, що запускається під час входу в систему. |
| Нативна в Linux/macOS | `sh start.sh` | Ні; для роботи у фоні використовуйте systemd/launchd. |
| Docker на будь-якому підтримуваному хості | `docker compose up -d --build --wait` | Так, поки працює демон Docker. |
| Допоміжний скрипт Docker у Windows | `scripts\Docker.cmd` | Так; скрипт чекає, доки веб-сервер стане працездатним. |
| Допоміжний скрипт Docker у Linux/macOS | `sh scripts/docker-start.sh` | Так; скрипт чекає, доки веб-сервер стане працездатним. |

Якщо хмарний сервер має бути придатним для перевірки третьою стороною — створений через API провайдера, без SSH і доступний лише через Cloudflare Tunnel, — див. [розгортання з високим рівнем гарантій](../HIGH-ASSURANCE.md).

Нативний запуск створює приватне `.venv` і встановлює закріплені версії залежностей. Docker збирає їх усередині образу, тож Python на хості не потрібен. Для першого налаштування потрібен доступ до Інтернету. Якщо Python 3.11+ не знайдено, `Start.cmd` питає дозволу, перш ніж установити Python 3.12 для поточного користувача Windows (через winget, а інакше — інсталятором із python.org після перевірки його підпису Python Software Foundation); прав адміністратора він ніколи не запитує. Docker і служби ОС залишаються передумовами.

Нативні й портативні інсталяції використовують `data/live` у своїй папці. Docker використовує іменований том `tgwitness-data`, змонтований у `/data`. Це окремі інсталяції, доки ви свідомо не перенесете повний каталог даних. Не розраховуйте, що новий контейнер Docker автоматично знайде облікові записи нативної інсталяції.

## Вимоги до інсталяції

Для нативної інсталяції потрібні Python 3.11 або новіший з `venv` і `ensurepip`, доступ до Інтернету для першого встановлення залежностей і каталог проєкту з правом запису для `.venv`. Вбудована панель не потребує Node.js чи збирання фронтенду. Запускайте програму запуску від імені звичайного облікового запису ОС; TgWitness не потребує прав адміністратора чи root.

- **Windows:** `Start.cmd` перевіряє `py -3`, потім `python`, потім стандартні папки встановлення для окремого користувача та в Program Files і вимагає версії 3.11 або новішої. Якщо жоден варіант не підходить, він пропонує описане вище автоматичне встановлення для поточного користувача. `py -3 start.py` також працює. Портативному пакету Python не потрібен узагалі.
- **Linux:** `start.sh` пробує `python3.13`, `python3.12`, `python3.11`, `python3` і `python` і, якщо жоден не відповідає вимогам, виводить команду встановлення для apt, dnf, pacman, zypper, apk або Homebrew. В інсталяціях Debian/Ubuntu може знадобитися пакет `python3-venv`, що відповідає вибраному інтерпретатору. Старіший Python, який дистрибутив постачає за замовчуванням, потрібно замінити або доповнити Python 3.11+.
- **macOS:** установіть актуальний дистрибутив Python 3.11+; не розраховуйте, що інтерпретатор із комплекту ОС відповідає вимогам. Запускайте `python3 start.py` з каталогу проєкту.
- **Docker:** використовуйте Docker Engine/Desktop з Compose v2.20 або новішим. У Windows Docker Desktop має працювати з контейнерами Linux. Контейнер установлює власні залежності Python; окремий Python на хості не потрібен.

## Локальний комп’ютер

Використовуйте `Start.cmd` у Windows або `sh start.sh` у Linux/macOS. `scripts\Setup.cmd` або `sh start.sh --setup-only` готує середовище. Під час першого запуску програма запуску встановлює залежності; наступні запуски використовують те саме середовище. Доступ до Інтернету потрібен для налаштування та збору з Telegram, але перегляд наявних записів і створення експортів працюють офлайн.

Після налаштування запустіть `python start.py --check`, щоб перевірити локальні залежності, Ed25519, сховище, конфігурацію ключів і адресу прослуховування, не запускаючи колектор. Для структурованого виводу додайте `--json`. Передайте ті `--data-dir`, `--host` і `--port`, які плануєте використовувати. Перевірка не встановлює пакети, не створює журнал і не підключається до Telegram; це не кваліфікаційна перевірка цілісності чи охоплення. Наявні журнали перевіряються окремо під час запуску. `python start.py --help` також нічого не встановлює.

Після використання start.py запускайте допоміжні команди через `.venv\Scripts\python.exe` у Windows або `.venv/bin/python` у Linux/macOS чи спершу активуйте це середовище. Наведені нижче приклади `python -m ...` передбачають, що середовище активне.

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

Змінні середовища: TGWITNESS_DATA, TGWITNESS_HOST, TGWITNESS_PORT, TGWITNESS_TOKEN. TGWITNESS_VAULT_KEY_FILE вмикає режим зовнішнього ключа для нової інсталяції; див. [Зовнішній майстер-ключ](../SECURITY-MODEL.md#external-master-key). Якщо TGWITNESS_TOKEN задано, він має містити щонайменше 24 символи; використовуйте криптографічно випадкове значення. Без нього додаток генерує 256-бітний випадковий токен у panel-token.txt. Значення зі змінної середовища не перезаписує цей файл. Для ротації облікових даних потрібен перезапуск.

Каталог даних може належати лише одному процесу. Кросплатформне блокування файлу на рівні ОС запобігає випадковому одночасному запису. Використовуйте один робочий процес Uvicorn. Панель може керувати будь-якою кількістю робочих просторів; каталоги додаткових робочих просторів розташовано в profiles/<id>/. Для окремих екземплярів служби використовуйте окремі каталоги й порти. Файли SQLite WAL мають зберігатися в локальному постійному сховищі, а не в мережевій файловій системі. Не використовуйте один том для кількох реплік.

## Портативний пакет для Windows

Кожен реліз на GitHub містить `TgWitness-<version>-windows-amd64-portable.zip` і його `.sha256`. У пакеті є офіційне вбудовуване середовище виконання Python 3.12 з python.org (контрольну суму закріплено в `tools/build_portable.py`), TgWitness із закріпленими залежностями та три засоби запуску:

| Файл | Призначення |
| --- | --- |
| `TgWitness.cmd` | Запуск панелі; додаткові параметри передаються далі, наприклад `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | Запуск синтетичної демоверсії в `data\demo` |
| `TgWitness-Check.cmd` | Перевірка готовності без запуску |

Закріплений словник морфології російської мови та колірні профілі PDF входять до пакета для роботи офлайн. Пакування дозволяє лише їхні відомі шляхи до файлів у каталогах `data` залежностей; будь-які неочікувані файли в цих каталогах спричиняють збій збірки.

Розпакуйте весь архів у папку з правом запису, наприклад `Documents\TgWitness`; не запускайте його зсередини ZIP чи з Program Files. Середовище виконання використовує ізольований шлях модулів, тож інші інсталяції Python і `PYTHONPATH` на нього не впливають. Дані зберігаються в папці `data` пакета. Щоб оновити пакет, зупиніть TgWitness, розпакуйте нову версію в нову папку й скопіюйте туди папку `data`.

Щоб зібрати пакет самостійно, потрібні 64-бітна Windows і Python 3.12:

~~~sh
python tools/build_portable.py
~~~

## Контейнер

```sh
docker compose up -d --build --wait
```

Ця команда створює іменований постійний том для /data. Веб-порт прив’язано до 127.0.0.1:8787. Процес працює під UID 10001 із вилученими Linux capabilities, кореневою файловою системою лише для читання та доступними для запису /data і /tmp. `--wait` перевіряє працездатність веб-сервера, перш ніж повернути керування; авторизацію в Telegram і доставку видно в панелі. Надані допоміжні скрипти після збирання чекають на готовність не довше 180 секунд. Перше завантаження залежностей може тривати довше.

Обидва базові файли Compose використовують назву проєкту `tgwitness`, тож розпакування нового релізу в інший каталог не призведе до непомітного вибору нового тому даних. Тримайте активним лише одне розгортання цього проєкту. Для незалежних інсталяцій використовуйте унікальне `docker compose -p NAME ...` та інший порт хоста й зберігайте обидва значення під час оновлень. Для старішого розгортання з іншою назвою проєкту й далі використовуйте його початкову назву з `-p`; `docker compose ls` показує наявні проєкти.

Скопіюйте `deploy/env.example` у `.env` і змініть `TGWITNESS_PORT`, щоб використати інший порт на loopback-інтерфейсі. Наприклад, `TGWITNESS_PORT=8788` відкриває панель за адресою `http://127.0.0.1:8788`; контейнер і далі слухає порт 8787. `.env` ігнорується Git.

Отримайте початковий токен:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

Корисні команди:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` перезапускає колектор після збою або перезапуску демона Docker. На сервері Linux увімкніть автозапуск Docker під час завантаження системи через менеджер служб вашого дистрибутива, зазвичай `sudo systemctl enable --now docker`. У Windows/macOS увімкніть у Docker Desktop параметр запуску під час входу в систему. Вихід із сеансу на настільному комп’ютері, сплячий режим або зупинений демон Docker можуть перервати збір. Явно зупинений контейнер залишається зупиненим, доки ви знову його не запустите.

У прикладі конфігурації том /tmp обмежено 512 MiB. Для створення експортів натомість використовується каталог `temporary-exports/` кожного робочого простору на постійному томі /data. Зарезервуйте там місце для одночасних експортів, зростання журналу/WAL, медіафайлів і резервних копій. Програма запуску використовує deploy/constraints.txt, щоб закріпити кваліфіковані версії залежностей середовища виконання. Docker і сервери з високим рівнем гарантій встановлюють пакети з deploy/requirements.lock і deploy/build.lock з pip --require-hashes: кожен файл пакета має відповідати SHA-256, записаному в коміті, тож файл, підмінений на PyPI чи дзеркалі, буде відхилено. Базовий образ Python і пакети операційної системи все ще потребують незалежної кваліфікації релізу.

Не використовуйте docker compose down -v, якщо не маєте наміру знищити журнал і ключі. Стан справності контейнера відображає доступність веб-сервера, а не успішний збір із Telegram. Перевіряйте в панелі стан колектора, сигнал активності, помилки та події охоплення.

### Профіль незалежного свідка

Необов’язкова служба `witness` запускає [незалежного свідка](../WITNESS.md) в окремому контейнері з власним ключем і журналом у томі `witness-data`, а до колектора має доступ лише через токен свідка тільки для читання. Створіть токен у панелі в **Інші інструменти → Додатки → Незалежний свідок**, додайте його разом із токеном бота й каналом у `.env`, а потім запустіть профіль:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

Служба звертається до колектора всередині мережі Compose за адресою `http://tgwitness:8787` (`TGWITNESS_WITNESS_COLLECTOR` перевизначає її, наприклад `/profiles/<workspace ID>` для іншого робочого простору). Для свідка на окремому сервері, яким керує хтось інший, використовуйте там `deploy/compose/compose.witness.yaml`, задавши в `TGWITNESS_WITNESS_COLLECTOR` HTTPS-адресу колектора; цей файл містить лише свідка.

## Встановлення опублікованого образу

Скопіюйте `deploy/env.example` у `.env`. Укажіть у `TGWITNESS_IMAGE` опубліковану версію, використовуючи шлях до репозиторію **малими літерами**, наприклад:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.9.2
TGWITNESS_PORT=8787
```

Запускайте цей файл окремо, замість `compose.yaml`:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

На хості не потрібні ні збирання з вихідного коду, ні Python, ні компілятор. Робочий процес релізу розрахований на контейнери Linux AMD64 і ARM64, зокрема у віртуальній машині Linux Docker Desktop. Використовуйте тег версії або `ghcr.io/owner/repository@sha256:...` з підсумку робочого процесу. Рухомого тегу `latest` чи автоматичного оновлення додатка не налаштовано. Варіанти з образом і з вихідним кодом використовують той самий том даних, якщо назва проєкту збігається.

## Автоматичний HTTPS на сервері

Використовуйте сервер із Docker, домен, яким ви керуєте, і постійне локальне сховище. Спрямуйте записи A/AAAA домену на сервер; публікуйте AAAA лише тоді, коли сервер доступний через IPv6. Дозвольте вхідні з’єднання TCP 80 і 443 та вихідні DNS/HTTPS для видачі сертифіката. Ці порти не повинні бути вже зайняті іншими службами.

Скопіюйте `deploy/env.example` у `.env` і задайте ім’я хоста без схеми й шляху:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

Запустіть збирання з вихідного коду з HTTPS-оверлеєм:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

Для опублікованого образу натомість використовуйте першим файлом `deploy/compose/compose.image.yaml`. Зберігайте обидва аргументи `-f` для подальших команд перевірки стану, перегляду журналів, оновлення та зупинки.

Caddy отримує й поновлює сертифікат, перенаправляє HTTP на HTTPS і пересилає запити до колектора в приватній мережі Compose. Стан сертифіката зберігається в окремому постійному томі. Прямий порт колектора на хості й далі доступний лише через loopback. Надана конфігурація Caddy не вмикає журналювання доступу.

Відкрийте `https://watch.your-domain.org` і введіть токен панелі. Готовність у Compose стосується контейнерів; видача сертифіката й доступність ззовні залежать від DNS і брандмауера. Якщо HTTPS не готовий, перевірте DNS, правила брандмауера та:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

Наданий образ Caddy відстежує тег `2-alpine`. Команда pull оновлює цей образ; якщо вам потрібні фіксовані версії інфраструктури, закріпіть у своєму розгортанні перевірений digest.

## Оновлення та резервні копії

Під час оновлень зберігайте назву проєкту Compose і том даних. Спершу зупиніть колектор і зробіть повну резервну копію. Для стандартного розгортання з вихідного коду:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

Щоразу використовуйте нове місце для резервної копії поза репозиторієм і захищайте його як матеріал, що дає доступ до облікових записів. Шлях у прикладі наведено для ілюстрації; використовуйте власне приватне місце для резервних копій. Копіюйте весь каталог, зокрема приховані файли, усі робочі простори, ключі, журнали та медіафайли. Якщо налаштовано зовнішній головний ключ сховища, створіть його резервну копію окремо. ZIP-архів із доказами не є резервною копією додатка, з якої можна відновитися. Для HTTPS також збережіть томи Caddy, якщо потрібно зберегти його стан сертифіката й облікового запису.

Для розгортання з вихідного коду отримайте файли нового релізу та виконайте:

```sh
docker compose up -d --build --wait
```

Для розгортання з образу змініть `TGWITNESS_IMAGE` на потрібну версію, а потім виконайте:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

Для наведених вище команд зупинки й копіювання також використовуйте файл(и) Compose своєї інсталяції. Зберігайте `.env`, власну конфігурацію та ту саму назву проєкту. `down` зберігає іменовані томи; **`down -v` їх видаляє**. Не копіюйте `.venv` між операційними системами чи версіями Python. Для оновлення нативної інсталяції зупиніть TgWitness, створіть резервну копію всього його каталогу даних, замініть файли вихідного коду й перед запуском виконайте `python start.py --setup-only`.

Після оновлення перевірте доступ до панелі, ідентифікацію облікового запису, стан спостереження та охоплення. Після перезапуску TgWitness продовжує зі збереженої позиції оновлень Telegram і запитує оновлення Telegram, пропущені під час оновлення програми. Для відкату може знадобитися резервна копія, зроблена до оновлення, якщо майбутня версія змінить формати зберігання.

## Віддалений сервер

Тримайте службу прив’язаною до loopback і використовуйте SSH-тунель або завершуйте HTTPS на зворотному проксі. Базовий файл Compose призначений лише для локального доступу; необов’язковий оверлей `deploy/compose/compose.https.yaml` додає Caddy для налаштованого домену. Не допускайте потрапляння bearer-токена в URL-адреси та журнали проксі. Зворотний проксі має обмежувати розмір запитів і частоту з’єднань. Не відкривайте доступ до незашифрованого HTTP з Інтернету.

Приклади для systemd, завдання входу в Windows, агента користувача macOS і Caddy наведено в [deploy/](../../deploy/README.md). Перед встановленням перегляньте й адаптуйте шляхи в них. Це надані шаблони, а не виконані локально кваліфікаційні перевірки платформ. Звичайна програма запуску не реєструє жодної фонової служби чи завдання.

У Windows під час запуску без вікна через `pythonw.exe` діагностика запуску та сервера записується в `logs/server.log` у каталозі даних (5 MiB на файл, дві ротовані резервні копії). Під час запуску з консолі журналювання в консоль зберігається. Журналювання HTTP-доступу вимкнено в обох режимах. Захищайте журнали разом із каталогом даних і переглядайте їх, перш ніж кудись передавати.

## Перезапуск і прогалини

Останній запитаний стан спостереження зберігається. Якщо спостереження було активним, під час запуску додаток намагається знову підключитися та відновити вибрані джерела. Ручна пауза скасовує цей намір. Невдалий перезапуск фіксується й відображається в панелі.

TgWitness зберігає позицію оновлень Telegram для облікового запису та для кожного каналу (pts, qts, seq і date) у сховищі робочого простору й відновлює її під час наступного запуску. Потім клієнт запитує оновлення, пропущені, поки процес був зупинений, а періодична повторна перевірка відновлює пропущені повідомлення й фіксує збережені, які Telegram більше не повертає. Під час запуску діалоги завантажуються заново. Кожен запуск фіксує попередній заголовок журналу, межу офлайн-періоду та позицію оновлень, з якої відновлено роботу. Монітор перевіряє з’єднання кожні 10 секунд і щохвилини додає сигнал активності (**Інші інструменти → Параметри → Позначка активності кожні**). Розриви з’єднання й періоди тиші фіксуються як прогалини в охопленні із зазначенням причини. Знімки історії зберігаються як окремі спостереження поточної історії поруч із записами, отриманими в реальному часі.

Черга медіафайлів зберігається в базі даних SQLite кожного робочого простору. Повідомлення та його завдання фіксуються атомарно. Перервані завдання, що виконувалися, під час запуску повертаються для повторної спроби. Кожне завантаження має базовий тайм-аут 120 секунд плюс час на передачу файлу відповідного розміру зі швидкістю 256 KiB/s, а також обмеження 1–2000 MiB для кожного типу вкладень; тайм-аут, швидкість і кількість повторних спроб задаються в **Інші інструменти → Параметри**. Колектор пропускає файли невідомого розміру. Призупинення зберігає завдання в черзі. Повторна спроба використовує оригінальний спостережений дескриптор файлу, а не останню версію згодом відредагованого повідомлення. Тимчасові збої мають обмежену кількість повторних спроб; паузи FloodWait для медіа зберігаються після перезапуску. Відновлення медіа відокремлене від відновлення оновлень Telegram і не може відтворити зниклі файли.

## Резервне копіювання, відновлення та ємність

Перш ніж копіювати **весь каталог даних**, зупиніть процес. Копія має включати vault.key, signing.enc, credentials.enc, файли бази даних SQLite/WAL, медіафайли, токен, контрольні точки та всі підкаталоги profiles/. Відновлюйте повну копію, коли служба призначення зупинена. Відсутні ключі сховища або невідповідність ключа підпису призводять до збою запуску; не генеруйте ключі заново, щоб примусово отримати доступ.

Зберігайте резервні копії із секретами зашифрованими та з контрольованим доступом. ZIP-архіви з доказами — це портативні артефакти для перегляду, а не резервні копії додатка чи сесій Telegram. Автоматичного видалення за терміном зберігання немає. Плануйте дисковий простір для всіх повідомлень, необроблених метаданих, медіафайлів, тимчасових експортів і резервних копій.

Перевірка під час запуску та експорт обробляють записи потоково, а не завантажують увесь журнал. Експорт фіксує знімок для читання, а запис нових даних у WAL тим часом може тривати; тривалі експорти можуть утримувати сторінки WAL, тож ємність диска все одно важлива. ZIP-архіви обмежено 4 GiB у розпакованому вигляді відповідно до типового обмеження незалежного верифікатора; **Інші інструменти → Параметри → Найбільший підписаний ZIP-файл** підвищує це обмеження, а такі архіви перевіряються командою `verify.py --max-gib N`. Інші формати не мають обмеження на кількість подій. Підтримувані браузери передають частини відповіді потоково у файл, вибраний користувачем. Інші браузери буферизують не більше 128 MiB, а для більших передавань пропонують автентифікований CLI:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

Використовуйте `--profile ID` з **Експорт → Ідентифікатор робочого простору** для іншого робочого простору, `--format zip|jsonl|csv|html`, `--url https://your-server` для віддаленого сервера або `--max-mib`, щоб змінити обмеження передавання 5 GiB. Незашифрований HTTP дозволено лише для loopback. Токени передаються в заголовках, перенаправлення відхиляються, наявні файли не перезаписуються, а незавершені завантаження не публікуються як готові файли. Якщо TGWITNESS_TOKEN перевизначає згенерований токен, використовуйте окремо захищений файл із цим чинним значенням: panel-token.txt через перевизначення не перезаписується. SHA-256, який виводить команда, — лише контрольна сума передавання; підписаний ZIP перевіряйте незалежно.

Панель показує медіа в черзі та з помилками, найстаріші медіа в очікуванні, вільне місце на диску, паузи запитів до Telegram і джерела з непідтвердженим доступом. Ця діагностика не є повноцінним наскрізним моніторингом доставки. Робочі простори працюють в одному процесі; обліковий запис із великим навантаженням усе ще може впливати на інші. Ще не виконано: окремі робочі процеси, зберігання й ротація, надійне відновлення оновлень і повна кваліфікація розгортання. Доступ до панелі з обмеженою областю дії описано в розділі [доступ і дозволи](../ACCESS.md); незалежні контрольні точки — у [посібнику зі свідка](../WITNESS.md).

Детальні процедури: [підключення/безпека](../CONNECTION-SECURITY.md) і [режими роботи](../OPERATIONS.md).
