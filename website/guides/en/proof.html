Measure the events you actually expected

Use a known set of controlled actions as the denominator. The chart below illustrates six expected observations: send, edit and delete for each of two messages. It is a teaching example, not a live benchmark.

CAPTURE RATIO + RECEIPT DELAY
R = |observed ∩ expected| / |expected|
Δt = treceipt − taction

Match by the fresh marker, message ID and action type. Set a cutoff and record clock uncertainty before comparing delays. The denominator must be nonzero. Deletion delay is measured against your controlled action time; Telegram does not supply an exact deletion timestamp.

Assemble the pilot

  1. Create two or three workspaces with distinct Telegram accounts. Select a controlled test group in each and start observation.
  2. Create a read-only witness token for each workspace in Extras. Save each workspace’s signing-key fingerprint.
  3. Copy the example configuration to proof-config/proof.json. Fill in the addresses, token-file paths and distinct fingerprints. Choose neutral public labels.

For a native installation, set data_dir to ../proof-data and use your actual collector addresses. Check the configuration and launch:

python -m tgwitness.proof --config proof-config/proof.json --check-config
python -m tgwitness.proof --config proof-config/proof.json

Publish only the read-only monitor through HTTPS. Keep the collector’s control panel private. The public page shows states, counters and signed proofs; it does not provide conversation text or account sessions.

Prove delivery of specific events

  1. Generate a fresh marker with python tools/verify_live_probe.py --new. This command sends nothing.
  2. From another Telegram client, send the marker with “version 1” into your test group. Confirm both accounts recorded it.
  3. Edit the same message to “version 2”, confirm capture, then delete it and wait for deletion notices.
  4. Export each account’s journal and run the canary verifier with both archives and their trusted fingerprints.

Exercise restarts and interruptions

Repeat over several days and across a planned restart and bounded network interruption. Record expected events, captured events, delays and failures. Compare accounts only where visibility and collection settings match.

A single server is a useful pilot, but its local witness shares the same outage. Use a witness on another host for stronger continuity evidence.
