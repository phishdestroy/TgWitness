TgWitness / 文档

TgWitness 将账户可见的 Telegram 观察记录保存于经签名的日志中。 接收方可使用可信的 采集器密钥对保存的记录、附件和报告进行验证，随后将日志与独立保留的检查点进行比对。 本页介绍了格式、校验方法以及移交时需保留的材料。

Windows 用户可通过 VERIFY.cmd 开始操作：该程序会要求提供原始 ZIP 文件和独立获取的密钥指纹，显示附有说明的结果， 并保存一份独立的验证记录。有关设置和信任限制，请参阅验证启动程序和 便携式运行时。

什么是签名#

资料 保护 应保留的内容
日志中的每一项记录，包括操作事件 每个事件均包含 SHA-256 链和一个 Ed25519 签名 原始 events.jsonl（可信密钥指纹）及保留的检查点
证据 ZIP 文件内容 manifest.sig 对规范清单进行签名，该清单列出了内容文件的哈希值 完整的 ZIP 压缩包，包含其清单和签名
保留的附件 带签名的media.saved事件中包含SHA-256和字节计数；带签名的ZIP清单中包含文件哈希值 经过验证的 ZIP 文件中的原始字节

运行收据 包含采集器版本、源文件哈希值和启动设置的签名记录，该记录也包含在process.started中 所选验证模式对应的收据、相关日志及环境证据

独立版 CSV 不包含独立的加密签名；仅凭事件哈希值是不够的 请使用经过验证的 ZIP 文件中的原文件进行完整性校验
由浏览器生成的屏幕截图、打印件或 PDF 文件 衍生作品上不包含 TgWitness 的签名 保留原始的经过验证的软件包，并记录衍生版本的制作过程

采集器在生成每种导出格式之前，都会验证日志签名。 可读的 HTML 和 PDF 报告带有各自的印章；独立的 CSV 文件作为 已签名 ZIP 文件的一部分进行验证。保留 ZIP 文件以保留附件字节和清单， 并设置单独的检查点，用于将日志与较早的边界进行比对。

比较聊天记录导出文件#

使用独立保存的签名者 指纹，验证并比较两个已签名的聊天记录导出 ZIP 文件：

python -m tgwitness.verify first.zip --compare second.zip \
  --fingerprint FIRST_TRUSTED_KEY_SHA256 --compare-fingerprint SECOND_TRUSTED_KEY_SHA256

当两个存档均记录了相同的数字账号和聊天 ID 时，记录将通过消息 ID 进行配对。 未更改指完整的保存 JSON 记录完全一致： 包括全文、作者、日期、回复对象、嵌套元数据和未知字段。 JSON 对象键的顺序无关紧要；缺失字段、空值、值类型 以及数组顺序则会影响匹配结果。300 字符的预览仅用于显示。 已更改的条目 会将差异列为顶级字段changed_fields，包括预览中不可见的更改。 匹配过程中，重复的消息 ID 会被拒绝，而非相互覆盖。

差异可能表现为显示名称、浏览次数、收藏注释或其他 观察元数据的变更。仅凭差异本身无法确定 Telegram 内容是否被编辑， 也无法识别修改者身份，更无法证明哪个相互矛盾的存档是准确的。 未解析的记录仍保留在比较结果中；其保存表示形式的相等性 并不意味着其 Telegram 有效载荷已被解码。

对于不同或缺失的账户/聊天标识，该工具仅通过发件人、完整文本、文件哈希、媒体类型以及五秒 的时间容差来查找可能的 对应关系。它报告匹配（Matched），而非未更改（Unchanged）。这些候选结果并不能 证明消息的同一性或所有元数据的完全一致。未解析的记录仍被视为 未匹配。 成对记录中的差异仍列在changed中，包括在 内容模式下；这些差异并不能证明同一消息被编辑过。使用 --json时，matched统计成对记录的数量，而unchanged统计完整保存 记录完全相等的成对记录数量。在内容模式下，这两种统计结果均不能证明消息的同一性。现有的 changed_fields和整数形式的unchanged输出仍与 早期的比较结果兼容。归档格式和签名验证保持不变。

调查移交#

  1. 请在案件笔记中记录案件编号、操作员、Telegram 账户数字 ID、选定的 来源、采集政策及采集时间段。TgWitness 会保留观察记录，并在 “案件看板”中支持与来源关联的笔记和采集内容。请将移交和保管记录与案件 材料一并保存。 通过 实时验收程序核对预期的采集设置。
  2. 在依赖 其导出数据之前，请独立保留工作区的公钥指纹。在收集过程中，将签名检查点保存至收集器之外。 记录中断情况以及该账户可见性的限制。
  3. 导出带签名的 ZIP 文件并保留带签名的运行收据。请在 导出日志边界处或之前设置检查点。较晚的检查点会正确地拒绝 较早的导出，因为其长度不足。导出内容包含完整的工作区日志， 不受面板过滤器影响；请在分享前仔细审查相关材料。

  4. 请收件人使用可信的验证器副本以及 独立提供的指纹/检查点来验证 ZIP 文件。请在已激活 Python 环境的可信代码检出环境中： 

    python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --checkpoint retained-checkpoint.json

    当两个输入均已提供且被接受时，成功输出报告 key_pinned: true 和 checkpoint_checked: true 。保留验证结果。

    For a handover requiring the final exported record to be witnessed, use
`--witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness`.
This refuses an export with an unwitnessed tail. See the
[witness handover procedure](WITNESS.md#require-a-witnessed-export-boundary).
    1. 请在保管记录中记录归档文件的 SHA-256 值、导出边界、传输日期、发件人和 收件人。请保持原始包的完整性，并仅对副本进行操作。 请分享证据文件，而非应用程序的私有数据 目录——该目录还包含账户会话和签名密钥。 传输时，可将导出文件放入受密码保护的 AES-256 ZIP 压缩包中。该 密码仅用于保护机密性，且不会被存储；接收方解压 存档后，可验证其中未被篡改的签名导出文件。
    2. 如果需要独立的时间锚定，请遵循 RFC 3161 流程，并保留请求、检查点、可信 CA 信息以及经过验证的权威机构响应。仅准备请求 并不能获得时间戳。

验证成功即表明相对于可信采集器 密钥和保留边界，数据完整性得到保障。请参阅验证范围，了解 信任假设以及所执行检查的验证结果。

交接摘要#

一个已签名的 ZIP 文件包含整个工作区日志。当法院、律师或滥用举报部门仅需 部分聊天记录、特定时间段或特定人员时，可通过“导出 → 移交提取”功能，根据所选披露规则生成一份精简 副本（tgwitness-handover-v1）。 操作员需说明目的并选择聊天记录、可选时间段（UTC）、 提取涉及的对象，以及其他人员的处理方式（显示、替换为化名 P01、 P02…或被 省略），哪些消息正文保留，哪些附件和个人头像被包含，以及 文本中的电话号码和电子邮件地址是否被屏蔽。 该目的及这些规则将记录在 已签名的清单和报告中；日志将记录handover.exported条目，其中包含 生成该文件的访问者信息以及文件的SHA-256值，而非文件内容。

verify.py通过两种方式检查提取内容。显示为未更改的记录将进行全面验证：其 内容与哈希值、Ed25519签名以及与所包含前身记录的链接均需通过验证。 一个 简化记录会保留原始哈希值和签名，因此签名仍可验证，但 被隐藏的字段无法据此重新计算；记录中会注明被隐藏的内容，报告 也会标注出来。清单中会注明日志的长度和头部，并附有采集器对该 头部的签名，同时统计被省略的记录数量； coverage.json描述了所选的聊天记录。文件 名中的姓名不会被检测到。分享前请审查最终文件：自由文本、文件名和选定的 附件仍可能泄露个人身份。请保留完整的签名ZIP文件：解压后的文件属于信息披露，而非替代品。

通俗易懂的报告#

已签名的证据、移交文件和聊天记录 ZIP 包包含可读的 HTML 和 JSON 报告，此外， 当所需字体可用时，还会包含所选报告语言的 PDF 文件。每份 报告均使用工作区的 Ed25519 密钥进行封装，并可单独验证： python -m tgwitness.verify FILE --fingerprint KEY [--evidence ZIP]。

  • report.html / chat.html：封装语句（tgwitness-report-seal-v1）会关闭文件，并 对之前的每个字节的 SHA-256 进行签名。较长的日志和聊天记录会被拆分为 可配置大小的部分（报告设置，500 至 100,000 条记录；默认值为 5,000）： records/records-0001.html 或 messages/messages-0001.html，每个文件均带有其编号、范围 和总数，并与其 SHA-256 一起列在已签名的清单中。收集器心跳记录的连续序列 将显示为一行，除非“报告设置”中指定逐行显示。
  • report.json（tgwitness-report-json-v1，密钥 format、report、seal）：该密封对 report 的规范 JSON 中的 SHA-256 进行签名，因此案件系统和脚本可以读取相关事实， 并可在保持签名文件完整性的前提下，从中进行数据保护方面的筛选。
  • report.pdf / chat.pdf：一份用于打印和归档的正式文件，对相同的 字节进行两次签名，除签名值（/ByteRange）外，整个文件均包含在内。标准 PDF 签名 （adbe.pkcs7.detached、CMS 配合 SHA-256 和 ECDSA P-256）使用一份自签发的文档签名 证书，该证书存储在工作区保险库中；其主体序列号即为Ed25519密钥 指纹。Ed25519印章作为未签名的属性 2.25.240684792623320047764573196045913242332封装在CMS中，并通过 "content": "pdf-byte-range"标识证书的SHA-256，因此Ed25519密钥为该证书提供担保。 PDF 读取器会显示 文件在签名后是否发生过更改，并在证书被 信任之前将签名者标记为未知；请改用 Ed25519 指纹进行比对。中文、日文和韩文的 PDF 文件需要在服务器上 （或 TGWITNESS_FONT_DIR 中）安装相应字体；若未安装，ZIP 文件中仅包含 HTML 和 JSON 报告 。

在频道或超级群中，Telegram 按顺序为消息编号 1、2、3…… 聊天记录导出文件会列出 起始编号和结束编号、现有消息数量，以及所有缺失编号的连续区间（如 message-ids.json ）、清单和 chat.json 头部信息，并标记每个缺口在 聊天记录中的具体位置。 verify.py 从chat.json 开始重新计数。缺失的编号是指Telegram 未返回的消息（在导出前已被删除，或该账户无法查看）；在私聊和 基础群组中，编号在该账户的所有聊天中共享，且缺口不计入统计。

读取历史记录后，导出功能会按号码逐一重新向 Telegram 查询所有缺失的号码 （channels.getMessages，最多 10,000 个号码）。结果保存在 message-ids.json 文件和报告中。 若返回空响应，则记录该号码在重新检查时对该账户不可用； 但未说明具体原因。重新检查时返回的消息将被添加到导出结果中 并标记为 found_on_recheck。

每份报告均以开头。简而言之：先有一段概述，随后说明材料显示的内容以及未显示的内容 （账号背后是谁、消息传递的完整性、观察前的删除情况、无时间戳的 时间记录）。 当浏览器验证了印章的 签名（而非页面本身）后，页面自身的印章会变为琥珀色：浏览器不会为页面提供其自身的字节。 只有当 读者将文件拖放到页面底部的验证框中，且每个字节都匹配时，且仅当 显示的页面正是该文件时，印章才会变为绿色；否则将变为红色。

每份报告均精确标明程序名称：当收集器从代码检出运行时对应的 git 提交，或 安装程序设置的 TGWITNESS_COMMIT，以及其源文件的 SHA-256（source_tree_sha256、 路径的规范 JSON → SHA-256，适用于每个 .py、.js、.css、.html 和 .svg 文件在 包中），除非文件被修改，否则检出该提交即可重现上述内容。 Telegram 客户端的命名包含其库、API 层和数据中心。当观察开始以及聊天 导出开始和结束时，收集器会向 Telegram 查询其时间（updates.getState，整 秒），并记录 Telegram 的时间减去收集器时钟的时间，其中包含因 往返传输产生的不确定性；报告在“保管链”部分显示这些测量值。 聊天导出记录的 内容还包括读取历史记录的时间，而不仅仅是消息的日期。

离线报告查看器和存档指南#

在打开 chat.html 或 report.html 之前，请先解压完整的 ZIP 文件。该查看器提供搜索、 筛选、参与者、指标、记录详情以及无需服务器即可进行的 JSON/CSV 选择功能。请将 viewer/ 和 media/ 放在报告旁边。所选内容均为衍生文件：请使用 verify.py SELECTION.json --evidence ARCHIVE.zip 将其与签名存档进行比对。 验证器会检查报告 ID、签名密钥、归档边界以及每个选定项目；经过编辑、 缺失或重复的项目将导致验证失败。选择说明和创建时间仍属于未签名的元数据。

仅在完整、未经过滤且按升序排列的聊天记录流中显示消息编号缺口。隐藏 类别或未能加载数据块，绝不能将省略的行视为消息缺失的 证据。搜索高亮功能在HTML转义之前对纯文本进行操作，并保留字面标记。

该浏览器会检查清单签名、报告 ID 和密钥，以及所有列出的文件哈希值。它 会拒绝模棱两可或格式错误的 ZIP 结构、重复的文件名和不安全的路径，并将文件 大小限制在 256 MiB 以内，声明的总内容大小限制在 4 GiB 以内。对于更大的归档文件，请使用独立验证器。 此浏览器检查是对验证器对日志链和数据语义检查的补充。

README.txt包含一份入门指南、一份对齐的文件清单、验证说明以及 以报告语言编写的数据格式说明，随后是完整的英文指南。 SHA256SUMS涵盖了 其中列出的文件，但不包括该文件本身、manifest.json和manifest.sig；签名清单 还涵盖了SHA256SUMS。请保持原始ZIP文件不变，并将工作文件保存到 解压文件夹之外。PDF报告包含章节书签，后续页面上带有案件/报告标识。

导出时的聊天记录#

聊天导出记录了导出开始时 Telegram 对该聊天的描述：Telegram 自身的 标签（scam、fake、restricted 及其理由、verified）、用户名、描述、成员 和管理员数量、关联的讨论、内容保护、新成员是否能查看早期 消息，以及该账户从哪条消息开始能查看聊天记录（available_min_id）， 消息 1 的日期 （当该消息即为聊天创建时间时），以及聊天照片的 SHA-256（保存在 media/ 中）。 它记录了导出账户在聊天中的位置：角色、加入日期、邀请人，以及对于 管理员而言，其权限。Telegram 拒绝的请求将另行标注。

当导出账户为管理员时，导出操作会将聊天的管理员日志（Telegram 保存约 48 小时）读入 admin-log.json：其中包含删除和编辑操作的详细信息，包括操作内容及执行操作的账户。这是 唯一一份能明确指出删除者身份的删除记录。

指标#

报告列表及存档中包含 indicators.csv 、indicators.stix.json （STIX 2.1 ） 以及 indicators.misp.json （MISP 事件），滥用处理部门可据此对记录的消息采取行动： 链接和域名（包括隐藏在文本中、按钮内及链接预览中的内容）、加密货币 地址、Telegram 用户名和邀请链接、电话号码、电子邮件地址以及保存的图片。 比特币、莱特币、狗狗币和波场地址仅在 base58 校验和通过时才会被列出， SegWit 地址在 bech32 或 bech32m 校验和通过时会被列出，而 TON 地址在 CRC 校验通过时会被列出；EVM 和 Solana 地址则被标记为未经过校验。 图片包含 SHA-256 以及一个感知 哈希（dHash，64 位），其值在重新压缩或调整大小的副本中几乎保持不变。报告会写入 标记，以防止意外打开（hxxps[://]example[.]com ）；文件保留 原始值不变。 每个指示符均被标记为未知且不适用于自动检测（STIX 、 indicator_types: unknown 、MISP 、to_ids: false ，分发至本组织）：被 列出仅表示某条消息中包含该指示符，并不意味着其具有恶意。若链接的文本显示的 地址与其实际打开的地址不同，则该链接会在报告中被标记。

PDF报告末尾包含一份需由检查员亲笔签署的声明、一份供公证员或 法院专家使用的核对清单，以及一个二维码（首页亦有显示），其中包含报告ID、密钥指纹以及 权威数据的SHA-256，以便打印件可追溯至其存档。

事件规范化#

哈希输入必须包含以下字段：

seq, observed_at, source_at, kind, chat_id, message_id, actor_id, payload, previous_hash

使用与 Python 兼容的 JSON 格式进行序列化，采用 UTF-8 编码，对象键按顺序排列，不进行 ASCII 转义，不包含无关的空白字符，且不包含 NaN/无穷大：

json.dumps(value, ensure_ascii=False, sort_keys=True,
           separators=(",", ":"), allow_nan=False).encode("utf-8")

这些字节的 SHA-256 值即为事件哈希。签名采用 Ed25519 对 32 个原始哈希字节进行计算，随后进行 Base64 编码。第一个 previous_hash 由 64 个零组成。 序列号从 1 开始，并以 1 为增量递增。所有事件（包括操作性 事件）共用一条链。系统不抑制重复交付：重复 的观测结果是独立的收据，而非对独立 Telegram 操作的声明。

Telegram 的原始日期为 ISO 字符串；二进制字段将转换为包含 bytes_base64 的对象。消息正文、实体、媒体描述符、回复元数据、点赞、 以及服务操作（如有提供）均保留在原始消息元数据中。

observed_at 是采集器的 UTC 墙钟时间。source_at 是提供的 Telegram 日期 （如有）。删除通知不会提供确切的删除时间，因此 source_at 保持为空。传输接收顺序不一定与源事件 顺序一致。历史快照使用较早的源日期，但采用当前的观察时间。

行为主体语义#

message.new 中的 actor_id 即为消息发送者。message.edited 未推断出 编辑者；payload.sender_id 记录了被观察消息的发送者。 删除 actor_id 保持为 null。成员服务消息保留发送者和操作 类型，不会将每次移除都转换为自愿退出。原始参与者 更新保留所提供的 actor_id。反应快照不会虚构变更操作者。

私人聊天和普通群组的删除通知仅包含消息 ID。 这些聊天共享一个全账户通用的 ID 序列，因此一个 ID 代表该账户中的一条 消息。 当具有该 ID 的消息此前已保存在此日志中时， 删除操作将在该聊天中记录为 message.deleted，并使用 payload.chat_resolution 作为方法名称。从未被保存过的 ID 将作为 deletion.unscoped 保存，且不包含 chat_id；系统不会进行任何推测。 频道和超级群组按聊天对消息进行编号， 绝不会通过这种方式进行匹配。当被删除的消息是由被观察账户发送时， payload.deleted_message_was_outgoing 为 true；但仍未提供删除者信息。

无范围的提示并不意味着消息从未被保存：匹配的 聊天记录可能不在当前观察范围内，或者可能无法找到 唯一的匹配项。在报告计数、过滤器和标签中，未检测到与删除 通知仍属于不同的观察结果。后续的恢复操作会清除 当前的缺失状态，同时在 签名历史记录中保留先前的检查失败记录；这两种观察结果均不构成删除通知。

来自同一条通知且解析为同一聊天室的多个 ID 将被归类为 deletion.batch，无论其数量多少。该通知无法证明整个聊天记录是否已被 清除、由谁执行了删除操作，或该操作是否适用于所有参与者。 已保存的已发送消息不会改变这些限制。较早的日志中可能包含由十个或更多 ID 批次推断出的 history.cleared 事件，其说明 文本将删除行为归因于另一位参与者。这些推断未 得到本次更新的支持。请保留这些原始的签名记录，但将其 视为分组删除通知；当前界面已据此对其进行标注。

覆盖范围：连续性、缺失内容及未被观察到的 ID#

每个签名 ZIP 文件都包含 coverage.json，HTML 报告以相同的摘要开头，而 verify.py 会根据 events.jsonl 重新计算该摘要，而非直接信任该文件：

  • 从 X 到 Y 持续进行观察。一个时段以 observation.started 开始， 并以暂停、停止、Telegram 连接中断、注销、进程启动但未 有序停止，或在观察期间超过三分钟无任何记录而结束 （每分钟都会写入一次心跳记录，因此静默意味着进程停止、卡死或 计算机进入睡眠状态）。当在“参数”中更改心跳间隔时，每次心跳 都会记录该变更，且允许的静默时长变为三个间隔，但绝不少于三分钟。
  • “缺口”列出了各时段之间的时间间隔及原因。若最后 一条记录处仍存在缺口，则标记为 not_resumed_by_last_record。
  • 未观察到的消息 ID。对于按 聊天计数消息的频道和超级群组，观察到的消息 ID 之间的缺失 ID 将以范围形式列出。这些消息会被报告为 “未观察到”——即已被删除、从未送达或超出保存的历史记录范围——但绝不会被标记为 “已删除”。私人聊天和普通群组共享全账户范围的序列号，因此此类聊天内部的 缺口没有任何意义，也不会在此处列出。
  • 聊天层面的数据缺失通知（例如 Telegram 在某个 频道中要求恢复差异数据）被计为注释；它们不会中断全局覆盖。

缺失的消息编号（gap_summary)#

预览。 coverage.json → gap_summary 该工具统计 Telegram 分配的编号中，该 收集器从未检测到的数量。Telegram 针对每个频道或超级群组对消息进行一次编号，并针对 每个账户在私聊、机器人和普通群组中各进行一次编号。两个已观测 消息之间的编号要么已被观测到，要么缺失；连续的编号范围则表明 该范围内的所有编号消息均已被观测到。编号缺口既不指向特定行为主体，也不说明原因。

字段 含义
status on，或 off 在“参数”→“差距分析”中关闭时
parameters 生成该结果的参数，以便能够重现该结果
chats[] 每个频道或超级群对应一条记录，每条记录均单独编号
account 整个账户中私聊、机器人和普通群组的序列
status （按序列） applicable，或 not_applicable 使用 reason
observed_from, observed_to, span 首次和最后一次观察到的号码以及范围的大小
observed, observed_without_content 观测数值；仅通过删除或重新检查记录得知的数值
missing, density, gap_ranges, largest_gap 从未观测到的数字、其在范围中所占的比例、运行次数、最长运行时间
clusters[] 列出的缺失内容： low, high, missing，以及相邻的观测数值 after / before 及其观测时间
service_estimate 仅在启用时显示：根据观察到的占比，缺失的数字中有多少属于服务消息。该数值绝不会从 missing

有效性源自日志，绝不预设：

  • 频道和超级群的统计以聊天为单位进行，在所选聊天的导出文件中也是如此。 由发送方选定的记录将用于统计 not_applicable.
  • 全账户序列仅从全账户收集功能开启期间收到的第一条消息到最后一条消息进行统计， 并包含私聊、机器人、普通 群组以及该账户自身的消息，没有任何此类聊天被排除在外（scope.changed）。 标有 deletion.unscoped “count”命名的数字均视为已观察到的消息，不包含内容。导出或 移交选定聊天记录无法测量该数值。如果全账户收集功能曾被 关闭后又开启，则会提示说明：期间使用的数字将显示为缺口。
  • 服务消息是带有独立编号的日志记录，因此它们会自动填补间隙； 可选的估计时间仅作为上下文参考。

verify.py 重新计算 gap_summary 基于 events.jsonl 基于签名 coverage.json 成员中的参数（针对旧版存档使用默认值），并 在覆盖范围摘要中打印该账户范围内的行。该存档的 get_capture_status（MCP 和命令行）针对某次访问可能读取的聊天记录返回相同的测量结果； 而账户级序列仅适用于覆盖整个工作区的访问。

对同一条服务消息的重复观察仅计为一次，且账户服务估算 仅使用测量范围内的数值。在启用全账户测量之前，所应用的范围必须明确保留 该账户自身的消息；未包含该信息的旧记录 无法满足此条件。停止观察不会 延长测量范围，且恢复观察会被记录。实时存档查询有时间 限制（包括其数据库扫描），并将未完成的测量标记为部分完成。

Telegram 记录了独立的消息 ID 序列。 这些数字描述的是观察结果；它们既不能识别删除行为者，也不能确定 某个数字缺失的原因。

当Telegram停止接受该账户时，结束监视的coverage.gap记录 包含cause（account_banned、account_frozen、account_deleted、session_duplicated、 session_revoked、session_expired、session_ended或not_authorized）以及Telegram 错误；verify.py指明了该周期结束的原因。

覆盖范围包括记录的观察时段、中断情况及消息结果。 请结合所选的聊天、时间段和附件策略进行评估；仅凭连续 运行并不能证明 Telegram 更新已完整送达。

制作人#

证据 ZIP 包、聊天记录导出、Witness 日志以及 人员档案文件的声明中包含的签名清单包含 producer ：软件、版本、项目（PhishDestroy）、 主页和源代码仓库。HTML 报告中显示了相同的行，verify.py 将其作为已验证内容的一部分输出。 在此字段存在之前生成的归档文件仍按 原有方式进行验证，并在报告中显示为未指明生成者。

每条 observation.started 记录还会指明进行监视的 Telegram 客户端：其 api_id （绝非哈希值），无论该客户端是内置的公钥对还是运营商自有的应用程序， Telegram 连接请求中发送的客户端描述，以及连接 路由的类型及其 IP 模式（无代理地址或密钥）。 该报告和custody.json列出了每个 不同的客户端和路由及其记录时间，以及未列出的代理未响应的时间 和Telegram检测到服务器地址的时间。此前记录的日志中已有说明。

人物简介#

应请求，系统会基于日志中已有的 某次聊天的记录生成个人资料文件（tgwitness-dossier-v1，JSON）；该文件不会从 Telegram 获取任何数据，且个人资料内容绝不会 写入日志（个人资料的启用和停用将记录为 dossier.changed）。 对于每位拥有已保存消息的用户，该文件会列出其姓名和用户名历史记录、Telegram标记 （机器人、诈骗、虚假、高级、已验证、受限、已删除）——以保存时显示的状态为准，以及个人资料 照片ID、来自本地头像缓存中与该头像相似的头像的SHA-256和感知哈希（pHash，与imagehash.phash兼容） 、活动记录（首条和末条消息、 数量、已编辑和已删除的分享、按UTC小时划分的消息）、谁回复了谁、该用户曾在此日志中参与的其他聊天 中该用户曾发帖的聊天记录，以及被提及的钱包（BTC、EVM、TRON、TON、LTC、 DOGE、XMR、SOL；Base58Check地址已通过校验和验证）、电话号码、用户名和 链接，包括隐藏在文本背后的链接。

每个事实都会列出其来源的日志记录（seq），而 record_hashes 则包含 每个被引用的记录的哈希值。该声明使用工作区密钥进行签名：

python verify.py tgwitness-dossier-CHAT.json --fingerprint TRUSTED_SHA256 --evidence tgwitness-evidence.zip

该工具会检查签名，验证证据导出文件本身（包括签名、哈希链和文件）， 并确保每个被引用的记录在同一工作区的导出文件中完整无缺且未被修改。头像哈希值会被标注为来自本地缓存 （而非日志记录）。提及内容属于模式匹配——仅为待核查的线索，而非已验证的事实。 配置文件按聊天进行启用，可导出为带密码的 AES-256 压缩包，且 在关闭配置文件或聊天从来源中移除时被删除。

独立见证者#

将证人日志（tgwitness-witness-v1）及其频道帖子与 通过 verify.py --witness … --channel … 导出的证据进行比对；参见独立证人。

清单与检查点#

manifest.json 包含格式、导出时间、公钥、指纹、日志 长度、头部哈希、范围、生成者、限制条件，以及除 manifest.json 和 manifest.sig 本身之外 每个内容成员的 SHA-256 值。 manifest.sig 是规范化 manifest JSON 的 Base64 编码 Ed25519 签名。 验证器会拒绝处理意外/缺失的成员、名称重复、文件损坏、 序列/链断裂、签名无效以及与提供的检查点不匹配的情况。 它绝不会提取归档路径。它将声明的总未压缩大小限制为 4 GiB； 若提高 Parameters 限制，--max-gib N 允许创建更大的归档文件。

请从您已安装的 TgWitness 版本或经过审核的代码检出中运行验证。 存档文件中包含的副本支持便携式使用；在执行该副本之前，请将其与您的 可信安装版本进行比对。

检查点会对一条包含公钥、日志长度、头部 哈希值和创建时间的声明进行签名。验证者可以检查后续存档是否包含 相同的前缀。应将检查点保留在收集器之外，以便后续验证时将 存档与单独保存的参考值进行比对。

验证范围#

验证过程会检查存档文件及其生成所使用的采集模式。请选择 其信任边界与当前情况相匹配的模式，并保留该模式的验证输入。

带独立见证节点的本地工作区 归档校验以及与见证人保留的早期日志前缀的一致性 独立受信任的见证密钥和记录；检查点将已观察到的前缀进行绑定

在密封采集过程中，经批准的采集器通过经过身份验证的 Telegram 连接在已验证的环境内接收数据。证明将归档文件与 该执行过程绑定，因此验证既涵盖采集过程，也涵盖后续的文件完整性。 这依赖于经批准的代码以及上文列出的平台信任链。 GitHub 捕获验证要求在运行过程中创建会话，并拒绝 导入会话的捕获。

运行收据记录了收集器的版本、文件哈希值和启动设置。GitHub 来源信息和 TDX 测量结果用于环境验证； 验证记录标识了已测试的配置。

TgWitness会对收集到的观察结果进行签名；Telegram及消息作者不会生成 这些签名。在本地工作区中，首次独立 检查点之前创建的内容仍依赖于收集器及其密钥持有者。覆盖范围记录描述了 选定的范围和收集结果，而经过验证的外部时间戳则将 已提交的存档或日志边界锚定在特定时间点。

附件#

文件在 media/ 目录下通过 SHA-256 哈希值进行标识。media.saved 事件将哈希值和 字节长度与特定的消息事件相关联。原始文件名属于元数据，绝非本地 路径。 媒体数据以异步方式下载，因此立即删除可能导致 无法捕获。已禁用的采集、超大/未知大小的文件、下载失败 以及下载中断等结果均会显示。进程崩溃可能会留下 未被引用的部分文件；这些文件不会包含在导出数据中。

ZIP 导出工具会根据文件名对存储的媒体文件进行验证。JSONL、CSV 和 HTML 导出格式会验证事件签名，但不包含媒体文件数据。衍生报告 仅供参考；events.jsonl 才是权威的事件表示形式。

完整聊天导出会将工作区附件设置中的附件保存至 media/ 目录下，文件名格式为 SHA-256。 chat.json 中的每条消息记录都会标注其文件名称（file、 file_sha256）或缺失原因（file_status），并附带读者所看到的 文本周边内容：文本后面的链接、转发来源、机器人按钮、签名、查看次数以及 自动删除计时器。verify.py 会检查每个命名文件是否位于该哈希值对应的 签名清单中。

持久的收集与处理收据 (0.2)#

媒体任务及其消息事件提交在同一事务中完成。 该任务存储 原始 TL 消息描述符；签名的观测记录将其 SHA-256 值、账户 及大小策略进行绑定。恢复操作会在下载前验证该绑定。它绝不会获取 当前消息，也不会悄无声息地替换为更新版本的附件。中断的任务 会重试，而永久性失败则仍被视为明确的结果。

每个工作区都有自己的日志和签名身份。process.started 事件包含 运行 ID、本地时钟、依赖项版本、源文件哈希值、初始账户/作用域， 以及捕获设置。心跳消息包含运行 ID、单调时间和队列状态。 运行收据也可作为单独签名的声明下载。若要验证 执行环境，请将其与验证范围中所述的 GitHub 证明或 TDX 检查 结合使用。

系统会在启动时、观察过程中每五分钟（ 参数 → 每隔生成签名检查点）以及有序停止时，在本地保留自动检查点。启动验证和导出操作会将日志 与最新保留的本地检查点进行比对。当检查点完好无损时，此机制可检测到数据库回滚 情况。独立的保留机制确保该参考信息在 工作区之外仍可获取；经过验证的外部时间戳则进一步将其锚定在特定时间点。

重启后，将恢复已保存的 Telegram 更新位置（catch_up_from 位于 observation.started），并请求获取遗漏的更新。定期重新检查会记录 message.recovered 以获取遗漏的消息，并在 Telegram 不再 返回已保存消息时记录 message.missing_on_recheck；后者并非删除通知，且未指明删除者或时间。

异地备份与恢复（S3）#

异地副本（“导出”，默认关闭）会将日志片段、保留文件、检查点 及其时间戳，以及已完成的聊天记录导出上传至兼容 S3 的存储空间，上传前使用 AES-256-GCM 加密，所用密钥存储于工作区保险库中；若存储桶支持，则应用 对象锁定保留机制。若未下载密钥，则无法读取备份内容。请使用 python -m tgwitness.replica restore --key-file KEY.json --out DIR 进行恢复和验证。

恢复操作需要一个空的普通目录。下载的文件和解密后的对象将保存在私有 临时存储中，直至整个日志及所有保留的检查点均通过验证。不安全的对象 路径、不一致的段范围以及长度短于检查点的日志将被拒绝；验证失败 时，系统不会发布任何恢复文件。 保留性检查会将返回的“对象锁定” 模式和日期与上传时发送的截止时间进行比对（允许一秒的四舍五入误差）。过期、 无效或被缩短的截止时间均不视为已验证。状态报告将显示该上传批次中 被读取保留状态的抽样对象。

缺失或损坏的本地媒体文件将作为当前迭代的错误报告，并保持媒体光标停留在 该文件之前，以便在下一次迭代中重新尝试处理该文件；其后的文件、检查点和导出内容仍将 被复制。恢复过程会 将所有已保存媒体的引用与解密后的哈希值及记录的大小进行比对。 来自中断上传的 相同重叠日志段将被去重；冲突的重叠部分将被拒绝。 上传过程中创建的检查点将推迟处理，直至其所涵盖的日志记录被 复制完毕，因此一个完成的处理阶段不会在日志之前发布检查点。

流式导出快照#

流式导出使用稳定的 SQLite 读取快照。当下载完成时，该快照的起始点可能早于 当前的实时日志。在此快照之后创建的检查点 可能会正确报告存档长度较短；请与位于导出前缀处或之前的检查点进行比较， 而非任意的后续检查点。

RFC 3161 准备与响应验证 (0.2)#

证据模式（默认关闭）仅通过工作区路径（绝不通过 MTProxy）将每个签名检查点的 SHA-256 哈希值发送至列出的 RFC 3161 权威机构和 OpenTimestamps 日历。 响应结果保存在 checkpoints/anchors/ 中，经 verify.py 导出并验证（--tsa-ca 负责 验证 TSA 签名；使用 ots upgrade 和 ots verify 确认 OpenTimestamps 证明）。

该面板会准备一个请求存档，其中包含规范的 checkpoint.json 字节数据、 SHA-256 消息指纹以及 timestamp.tsq 文件中的随机非ce值、校验和及操作说明。 此过程不会发起任何网络请求。该准备过程不构成可信时间戳。

python -m tgwitness.anchor verify 会调用 OpenSSL 的 ts 函数两次：一次针对检查点 字节，一次针对原始请求。必须显式指定受信任的 CA 文件； 内置证书不会被自动信任。在命令行界面（CLI）中，请求验证为可选操作， 因此请保留并提供 --request 参数以验证非ce。结果将表明 是否已进行验证。收集器的检查点签名和日志仍需 使用可信收集器指纹分别进行验证。

验证过程会检查响应签名、检查点字节，以及（若提供） 在指定 CA 信任下原始请求的有效性。证书吊销检查以及证书过期后的 长期归档验证不属于当前验证器的范围。 请参阅相关流程和验证结果。

证据模式下的可选记录：drand 和 Telegram 设备#

还有两项记录功能可与时间戳在同一轮处理中运行。这两项功能默认均处于关闭状态， 且仅在证据模式开启时生效：[扩展] → [证据与备份] → [更多见证人] · 可选， 或 "drand": true 以及 "devices": true 在 POST /api/evidence中。其中一项失败不会阻止 另一项或时间戳的运行；面板会在表单下方显示每项的最新结果。

drand （beacon.drand ）。每次处理都会将最新一轮的 drand quicknet（即熵联盟的公共 随机数，每 3 秒一轮）写入日志：chain 、 round 、randomness 、signature 、round_time 以及响应的 relay 。一个经过验证的 不可预测的轮次为后续哈希链接的材料提供了较低的时间参考。 后续检查点上的经过验证的时间戳则提供时间上限。这些检查 界定了关联的数据范围；数据收集的覆盖范围则单独评估。收集器首先向 drand.cloudflare.com 发起请求，然后通过工作区路径向 Protocol Labs 的中继节点发起请求，每轮一次请求。

verify.py 会验证每个随机数是否为其签名的SHA-256 ，并检查轮次 时间是否正确，同时报告轮次数量、最长未生成轮次的间隔以及收集器时钟相对于 drand的延迟。 它不检查 BLS 签名。--check-drand 将轮次与 Cloudflare 中继、Protocol Labs 中继以及长日志中的全部轮次或随机 抽取的 100 个样本进行比对；若有任何轮次不一致，则验证失败。

、Telegram、（account.devices）设备。每次扫描都会读取该账户与 account.getAuthorizations的会话，即“设置”→“设备”中显示的Telegram列表，并完整记录： 若自上次处理以来发生变更，则完整记录，包含added和removed会话 哈希值；否则仅记录其数量及SHA-256。设备型号、平台、应用及版本、 创建时间和最后活动时间、国家和地区等信息将被保留；IP地址则不予保留，因为 证据导出后便不再由您掌控。 收集器自身的会话始终处于活动状态，因此 只有其他会话的活动才被视为变更。verify.py 报告列表 被记录的频率，以及每个新会话和已结束会话。它仅在观察运行期间读取该列表。

他们未展示的内容：drand 仅能证明记录相对于公共时间的顺序， 而设备列表是 Telegram 通过收集器提交的声明，由收集器签名， 与其他所有记录一样。

Cloudflare Gateway 日志 （cloudflare.gateway_dns）。 对于通过 Cloudflare Gateway（ Gateway DNS ）进行解析的服务器，每次 复制都会包含自上次复制以来 Gateway 记录的内容：每个时间窗口（最长三 小时）对应一条记录，包含 from、until、location_id、服务器的 address（若已设置），以及 queries（作为 [at, name, type, rcode, decision, colo]，即使没有记录时也包含）。 请在 下进行设置。Cloudflare Gateway日志：账户、位置、可选地址以及一个只读令牌（账户 Analytics 读取；零信任 PII 读取，用于保留共享位置的一个地址）。控制面板会在保存前通过 一次请求验证这些信息；令牌始终保持加密状态，且绝不会进入日志。 verify.py 列出了时间窗口、被查询次数最多的名称以及任何未被副本覆盖的时间段；如果某条记录 的计数与其查询不匹配，则该记录将失败。 若某个时间窗口在单秒内包含超过一页的 查询，则保留该页内容，并标注其余部分缺失。该副本是 Cloudflare 通过收集器返回的响应，并由收集器签名；在 24 小时内，任何持有 只读令牌的用户均可将其与 Cloudflare 进行比对。
