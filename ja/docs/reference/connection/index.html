TgWitness / ドキュメント · 導入と復旧

このドキュメントでは、TgWitness 0.8.0 の動作とその制限事項について説明します。認証、 ソースへのアクセス、ネットワーク接続、およびキャプチャの完全性は、それぞれ独立した状態です。 サインインの手順、ファイル形式、および複数アカウントについては、「 アカウントとセッション形式」からご確認ください。イベントポリシーや再起動時の 動作については、「収集の仕組み」をご覧ください。

接続設定の手順#

Connectionにおいて、管理者は「このアカウント」、「アカウント グループ」、または「すべてのアカウント」を選択し、ルートを選択できます。「選択内容の確認」には、 対象となるアカウントの一覧が表示されます。「準備と確認」は、保存済みのルートを変更することなく、 提案されたルートをテストします。「確認済みの接続を適用」は再度確認を行い、必要に応じて監視を一時停止し、 ルートを保存して、すでに実行中の監視を再開します。 以前にアイドル状態だったアカウントでは、収集は決して開始されません。履歴のダウンロードは 一時停止されたままとなり、別途再開することができます。切り替えを行う前に、アクティブなエクスポートを一時停止してください。

グループの変更では、デフォルトで各アカウントのルートが維持されます。プレビューに意図した変更が 表示されている場合にのみ、そのオプションをクリアしてください。 アプリケーションは各 アカウントの結果を報告します。これは、データベース全体にわたる「すべてか無か」のトランザクションではありません。 切り替えに失敗した場合、そのアカウントは以前の設定に戻ります。再開に失敗した場合は 明示的に表示されます。プレビューは10分後に期限切れとなり、接続 設定やグループメンバーシップの変更には、新たな確認が必要です。

ルート TgWitnessが管理するもの
直接 ホストからの接続。外部ホストのVPNは検出も強制もされません。
VPN アカウントごとに1つのフルトンネルWireGuardプロファイルがあり、ローカルのユーザースペースSOCKS5プロセスによって実行されます。ホストインターフェースやドライバはインストールされません。
私のプロキシ SOCKS5、HTTP CONNECT、またはMTProxyの認証情報。SOCKS5/HTTPフィールドにはURLを入力できます。複数のアカウントを選択すると、入力したプロキシが共有されます。
公開版 MTProto 既存のプールでは、Telegramルートが割り当てられています。詳細設定で別途適切なプロキシが設定されるまで、外部へのリクエストは無効になっています。
WARP 選択したアカウントごとに個別のローカルトンネルを設定し、WARP登録情報とWireGuardプロファイルをそのアカウントのVaultに保存します。

現在のルートチェックでは、アカウントのセッションではなく、 新規の未認証Telegramトランスポートを使用します。HTTP対応のルートについては、そのルート経由でCloudflareのHTTPS トレースも要求し、報告された出口IP、国、WARPの状態、 およびチェック時刻を表示します。 測定される遅延は、Telegram接続の確立時間であり、 ICMP pingの結果ではありません。トレースで「WARPアクティブ」と報告されない限り、WARPの準備は失敗します。 これらのチェックは接続性を確認するものであり、キャプチャされたメッセージの 真正性や完全性を確認するものではありません。ローカルプロセスが実行されているだけでは、出口チェックの成功とはみなされません。

ポータブル版WARPおよびWireGuard#

これは、非公式のWARP統合であり、 wgcf 2.3.1および wireproxy 1.1.3を使用しています。 管理者は、最初のダウンロードまたはWARP 登録の前に、設定を明示的に承認します。 これらのセットアップ接続は GitHub および Cloudflare に直接行われ、 マシンの IP アドレスが公開されます。通常のアカウントのトラフィックは、 アプリケーションが起動するまで既存の経路を維持します。Cloudflare が出口アドレスと国を選択します。別々のトンネルでも 同じ出口アドレスを共有できます。この機能では、国の選択、定期的な IP ローテーション、およびホスト全体の VPN キルスイッチは提供されません。

サポートされているヘルパーのダウンロード：LinuxおよびmacOSのx86-64/ARM64、ならびにWindowsのx86-64。 アーティファクトは、レビュー済みのソースに同梱されているSHA-256ハッシュと照合され、 キャッシュされた実行ファイルは起動前に再度チェックされます。 いかなるヘルパーも PATHに追加されたり、システムサービスとしてインストールされたり、パブリックリスナーが割り当てられたりすることはありません。すべてのファイルは ワークスペースのportable-routes/ディレクトリおよび暗号化されたボールトエントリ内に格納されます。 ループバックSOCKS5リスナーには、個別に生成された認証情報が必要です。

プライベートプロファイルおよびWARPアカウントの認証情報は、既存の ワークスペースボールトで暗号化されます。実行中、ヘルパーは所有者専用の平文設定ファイルを必要としますが、 通常停止時にはこのファイルは削除されます。ホストがクラッシュした場合、このファイルが 所有者専用のデータフォルダに残されることがあります。これによりディスクが暗号化されるわけではなく、 管理者からの保護もされません。 パネルの親パイプが 消失した場合、スーパーバイザーはトンネルを閉じます。失敗したトンネルは、直接的なフォールバックを有効にすることはありません。パネルを再起動すると 選択されたトンネルが復元され、起動に失敗した場合は、所定の遅延を置いて再試行されます。 Stop tunnel は監視も一時停止し、停止状態を維持します。 Start tunnel はトンネルを開始します。準備ができたら、別途監視を再開してください。

アップロードするWireGuardプロファイルには、1つのインターフェースと1つのピア、完全なIPv4 およびIPv6ルートを含める必要があります。また、フック、インクルード、環境変数の置換、余分な リスナーは含めないでください。パブリックエンドポイントアドレスは、起動前に解決および固定されます。 OpenVPN/IPsecおよびプライベートエンドポイントには、外部VPNまたはSOCKS5ゲートウェイを使用してください。

認証方法#

API ID および API ハッシュはアプリケーションを識別するものであり、アカウントへのログインに代わるものではありません。 TgWitness ではこれらはオプションです。優先順位は、フォームに入力されたペア、次に インポートされたアカウント JSON からのペア、次にワークスペースに保存されたペア、そして 50 組の 公開ペアのプールを順に試行し、Telegramが1つを拒否した場合は自動的にローテーションされます。 Telegram Desktopのペア（2040）のみ、対応するTelegram Desktopクライアントの説明とともに送信されます。 my.telegram. orgのAPI開発ツールから取得したご自身のペアは、すべてのアカウントで使用可能です。各アカウントには、引き続き独自の認証が適用されます。

Telegramはコードの配信方式を採用しており、SMSによる配信は保証されません。APIハッシュでは、 失効したセッションを復元したり、忘れた2FAパスワードを再発行したりすることはできません。TgWitnessは、 ログインコードやTelegramの2FAパスワードをディスクに保存することはありません。

非公開の情報源の場合、アカウントはすでにアクセス権を持っている必要があります。グループのユーザー名は 不要です。プロキシやセッションのインポートを行っても、メンバーシップや管理者 権限は付与されません。現在のメンバーシップがあっても、参加前の履歴へのアクセスが保証されるわけではありません。

Telethonのセッションファイルをインポートする#

Telethon SQLite、Pyrogram SQLite、および Telegram Desktop TData は、それぞれ異なる形式を使用しています。 パネルは、サポートされている構造を検出して変換しますが、ファイル名の変更は 変換には該当しません。「ファイル」から 1 つのセッションとその対応する JSON を選択し、「アカウントに接続」を押してください。最大 4 つの一致するファイルと 合計 8 MiB まで受け付けられます。 TData/JSONの詳細については、フォーマットの制限をご参照ください。 パスコードの復元機能はありません。電話/2FAまたはQRコードによるログインでは、別途認証が行われます。

オプションの「Telethon専用」コマンドラインパスは引き続き利用可能です：

  1. 元のセッションを使用しているクライアントを停止し、一貫性のあるコピーを作成してください。 コンバーターは、WAL/ジャーナルが未完了のファイルを拒否します。チェックを回避するためにそれらのファイルを削除するのではなく、元の クライアントを適切に終了させてください。
  2. TgWitness環境から、以下のコマンドを実行してください：
python -m tgwitness.sessions account.session --out account.tgwitness-session
  1. 「アカウントの追加」→「ファイル」で、結果ファイルをアップロードするか、 その文字列を貼り付けて、次に進んでください。
  2. 表示されている数値のアカウントIDを確認し、情報源を選択して、監視を開始してください。

変換されたファイルは、暗号化されていないアカウントアクセス秘密鍵です。 これを保護された ストレージに保管し、決してコミットしたり、第三者の変換サービスに送信したりしないでください。TgWitnessは 認証済みセッションを暗号化された保管庫に保存します。セッションをコピーしても 別の認証が作成されることはありません。クローン化された認証キーを使用してクライアントを同時に実行したり、 独立した更新配信が行われると想定したりしないでください。

変換処理では、元のメッセージやエンティティキャッシュ、あるいは 永続的な更新カーソルではなく、権限のみが転送されます。また、プロセスの再起動を跨いだ更新の復元は行われません。

MTProto、Telethon、およびプロキシ#

MTProtoはTelegramのプロトコルです。Telethonは、TgWitnessが使用するPythonクライアントライブラリです。 MTProxyはTelegramのトランスポートプロキシであり、SOCKS5およびHTTP CONNECTが一般的な トンネルを提供します。いずれもアカウント認証に代わるものではありません。

ログインする前に、各ワークスペースのルートをアカウント → 設定 → 接続設定 → 接続経路を変更するに保存してください。 新しいワークスペースは、デフォルトで自動MTProxy · 公開リストとアドレスを非表示にするが設定されます。 Directを明示的に使用していた既存のワークスペースは、それを許可するモードを維持します。

IPモード#

ルートによって接続方法が決定されます。パネルの「アカウント」 セクションにある「IPモード」および「IP保護」の設定により、サーバーのアドレスが公開されるタイミングが決まります。これらの設定は、 VPNをインストールしたり、マシンからのすべてのトラフィックをルーティングしたりするものではありません。

モード Telegram 外部からのリクエスト
アドレスを非表示にする (hide) プロキシをご利用ください。どのプロキシも機能しない場合は、しばらくお待ちください。直接的な代替手段はありません。 SOCKS5/HTTP が必要です。適切なプロキシがないリクエストは拒否されます。
最終手段としてのダイレクトメッセージ（fallback) 自動MTProxyは、設定された遅延時間が経過した後、Directを使用し、その後、正常に動作しているプロキシに戻る場合があります。 設定済みの外部プロキシ、またはアカウントのSOCKS5/HTTPルートの利用を推奨します。それ以外の場合は、「Direct」も許可されます。
トンネルまたはVPNを経由したサーバー（tunnel) ダイレクトルートおよび即時自動プールフォールバックが許可されています。 該当するプロキシが設定されていない場合は、ダイレクト接続が許可されます。

トンネルまたはVPNモードでは、そのネットワークを別途管理していることを前提としています。正常に動作する トンネルがない場合、宛先からはサーバー自身のアドレスが見えてしまいます。オプションの名前ではなく、 実際のネットワーク環境に応じてモードを選択してください。

インストール時に提供されるパブリックプロキシ#

組み込みのリストには、 SoliSpirit/mtproto、 zakky8/mtproto-proxy-pro、 kort0881/telegram-proxy-collector、 および 3yed-61/MTP-Collector の4つのソースが組み合わされています。 同梱のスナップショットには、エンドポイント情報、情報源の帰属、およびダウンロード日が含まれています。 プロバイダーがリストに掲載されていることは、そのプロキシが正常に動作することや、Telegramのすべての更新情報を配信することを保証するものではありません。

MTProxyはTelegramの通信接続を自動的にチェックし、正常に動作しているプロキシを維持するとともに、 接続に失敗した場合は別のプロキシに切り替えます。ワークスペースは、十分に 動作しているエントリが利用可能な場合、異なるプロキシを優先します。一意の出口アドレスは保証されません。 接続に失敗したプロキシは、 再試行する前に待機します。機能するプロキシが一つもない場合、IPモードによって、 収集を待機させるか、直接接続を使用できるかが決定されます。プロキシを変更しても、アカウントは 変更されず、そのジャーナルも消去されません。経路の選択や変更は、署名付きジャーナルに記録されます。

自動ルートが有効な場合、リストは1時間ごとに更新され、転送チェックは デフォルトで10分ごとに実行されます。これらの間隔は設定可能です。公開リストを更新すると リフレッシュが要求されますが、リストを閲覧するだけでは、保存済みの手動ルートは変更されません。

TelegramのトラフィックとHTTPSリクエストは、異なる経路を使用します。リストのダウンロードには、 別のHTTPS接続と、提供された外部リクエスト経路が使用されます。 TGWITNESS_PROXY_FEED_PROXYは、HTTP/SOCKS5プロキシを使用してその経路を明示的に上書きします。 両方のコレクター「Compose」バリアントは、これを転送します。バックグラウンドプールはメインワークスペースに従います。 Telegramのセッション、API認証情報、パネルトークン、ボットトークンは、フィードプロバイダーには送信されません。 プロバイダー名、スナップショットの日付、およびダウンロード経路は、「リストの出典」の下に表示されます。

MTProxyはTelegramのトラフィックのみを伝送します。タイムスタンプ、 通知、オフサイトコピー、ソースチェックなどのワークスペースのHTTP操作は、 設定されている場合は別のSOCKS5/HTTPプロキシを使用し、設定されていない場合はアカウントのSOCKS5/HTTPルートを使用します。どちらの設定もない場合、「Hide the address」は リクエストを拒否します。その他のモードでは「Direct」が許可されます。外部リクエストは無効にできます。明示的に 設定されたフィードダウンロードプロキシは、引き続き個別のオペレーターによるオーバーライドの対象となります。 独立したウィットネスサービスは、独自のルートを維持します。

オペレーター管理のプライベートサービスの場合、既存のサーバー環境設定「 TGWITNESS_ALLOW_PRIVATE_DESTINATIONS=1」により、プライベート宛先が許可され、 プロキシ側でのホスト名解決が維持されます。この設定はパネルからは有効化できません。「パブリック専用」 モードでは、パブリックリゾルバーにクエリを送信する前に.onion宛先を拒否します。Torオニオン サービスを利用するには、明示的なプライベート宛先設定と適切なプロキシが必要です。 この DNS の動作は、Telegram のトランスポートではなく、外部 HTTP 操作に適用されます。 Cloudflare は、JSON DNS エンドポイントについて文書化しています。

異なるプロキシを使用しても、異なる出口アドレスが保証されるわけではありません。これらの設定は、 Telegramの制限を無効にしたり、匿名性を保証したりするものではありません。

公開リストを独自のオペレーターカタログに置き換えるには、以下のオーバーライドを設定してください。 これにより、proxies配列が空の場合を含め、外部サブスクリプションが完全に無効化されます。

空のカタログをproxy-config/proxies.json にコピーし、デプロイ済みのパブリックエンドポイントを追加してください：

{"format": "tgwitness-proxy-catalog-v1", "proxies": [
  {"id": "project-eu", "label": "Project EU",
   "link": "tg://proxy?server=REPLACE_HOST&port=443&secret=REPLACE_SECRET"}
]}

例示された値は置き換える必要があります。最大32件の異なるエントリが受け入れられます。 認証済みリストは、共有秘密鍵なしでラベル／ホスト／ポートを返します。いずれかを選択すると、 その認証情報がワークスペースの保管庫に保存されます。明示的なトランスポートテストが行われるまでは、 可用性は未検証のままです。カタログの形式が不正な場合は、手動での設定が可能となります。

ネイティブ起動：TGWITNESS_PROXY_CATALOGをローカルのJSONパスに設定してください。Docker：

docker compose -f compose.yaml -f deploy/compose/compose.proxies.yaml up -d --build

オーバーレイはproxy-configを読み取り専用でマウントします。ファイルはコンテナのUID 10001から読み取り可能である必要があります。 当該ディレクトリは、Git、Dockerのビルドコンテキスト、およびソースアーカイブから除外されています。この カタログは収集アカウントを設定するものです。Witnessボットは、MTProxyではなく、独自の HTTP/SOCKS5ルートを使用します。

直接フォールバックは、上記のIPモードによって制御されます。ルートを変更する前に、 監視を一時停止してください。保存を行うと、古いクライアントは切断され、未完了のログインはキャンセルされます。 新しいクライアントは、保存されたルートを使用します。アカウントのジャーナルとセッションの紐付けは維持されます。 設定を変更すると、以前のルートが上書きされます。編集する際は、プロキシの認証情報を再入力してください。

認証情報はnetwork.encで暗号化されています。APIはユーザー名、 パスワード、またはシークレットを返しません。署名付きレコードには、ルートタイプと認証情報の 有無が含まれていますが、エンドポイントやシークレットは除外されています。オペレーターはパネル上で エンドポイントを確認できます。シークレットフィールドは、保存、ロック、またはワークスペースの切り替え後に消去されます。

「Telegram接続のテスト」は、ログイン前でも利用可能で、ルートを経由して一時的な 非認証のTelegram接続を開閉します。IPチェック サイトには接続しません。テストに成功しても、グループへのアクセス、完全な 配信、または匿名性が保証されるわけではなく、単にトランスポート接続が確立されたことを示すものです。

このプロキシは、Telegram DCからのメディア ダウンロードを含め、Telegramクライアントの接続に適用されます。ブラウザ、pip、SSH、および手動で起動されたTSAツールには、それぞれ別の経路が設定されています。 プロキシのホスト名はローカルで解決される場合があります。rdnsは宛先のホスト名に影響を及ぼしますが、 Telegramは多くの場合、数値のDC IPアドレスを提供します。

SOCKS5およびプレーンなHTTP CONNECT自体は、プロキシの認証情報や クライアントからプロキシへのトンネルを暗号化しません。TelegramのトラフィックはMTProtoによって別途保護されます。 信頼できないネットワーク上では、 プロキシへの適切なセキュアチャネルをご利用ください。プライベートグループは クラウドチャットであり、MTProto によってエンドツーエンド暗号化された「シークレットチャット」にはなりません。

「アカウント」の「ストレージ保護」には、これらの状態が表示されます。パネルトークンは アクセスシークレットであり、暗号化パスワードではありません。これにより管理者権限が付与され、 発行されたトークンはアカウントやチャットごとに範囲を限定することができます。ワークスペースは ホストプロセスを共有しており、独立したテナントではありません。

BitLocker、LUKS、FileVault、または管理対象の暗号化ボリュームは、 それぞれの脅威モデルに基づいてストレージを保護することができます。 ロック解除され、稼働中のマシンの管理者は、 依然としてデータを読み取ることができます。ストレージの計画には、SQLiteのWAL/SHM、メディア、一時的なエクスポートデータ、スワップ領域、バックアップ、 およびブラウザのダウンロードデータを含めてください。Dockerボリュームは、単に ボリュームであるという理由だけで暗号化されるわけではありません。TgWitnessは、SQLCipherやオブジェクト暗号化を実装していません。

外部マスターキー#

新規インストールを行う場合は、マスターキーをデータディレクトリの外に配置してください。 これにより、既存のローカルキー保管庫が自動的に移行されるわけではありません。サービスIDのみがアクセス可能なキー ディレクトリを用意し、以下のコマンドを実行してください：

python -m tgwitness.security create-master-key /private/keys/tgwitness-master.key
export TGWITNESS_VAULT_KEY_FILE=/private/keys/tgwitness-master.key
python -m tgwitness --data-dir /private/observations/new-case

PowerShell（インストール済みのプロジェクト環境を使用）：

python -m tgwitness.security create-master-key E:\PrivateKeys\tgwitness-master.key
$env:TGWITNESS_VAULT_KEY_FILE = 'E:\PrivateKeys\tgwitness-master.key'
python -m tgwitness --data-dir E:\PrivateData\new-case

Dockerでは、ファイルを/dataの外側（例えば /run/secrets/tgwitness-master.key）に読み取り専用でマウントし、環境変数をそのパスに設定してください。 サービスUIDは、そのファイルを読み取れる権限を持っている必要があります。キーバイトではなく、パスを 環境変数または設定ファイルを介して渡してください。

各ワークスペースには、ランダムなパブリックソルトと、 HKDF-SHA256を通じて導出された独自のFernetキーが割り当てられます。vault.external.jsonには、マスターキーではなく、導出メタデータが保存されます。 キーが欠落している、または間違っている場合、自動的に置き換えられることなく起動に失敗します。復旧のために、 ソルトのメタデータとマスターキーの両方を保管しておいてください。

すべてのワークスペースは同一のマスターキーから派生しており、その秘密鍵が漏洩すると、 インストール全体に影響が及びます。実行中のプロセスは秘密情報を復号化できます。これはHSMや パスワードKDFではありません。ランダムな鍵の代わりに、任意のユーザー設定のパスワードは使用できません。

意図的な移行が 実施され、検証されるまでは、既存のインストール環境については既存の鍵を維持してください。vault.keyを削除したり、マスターキーを置き換えたりすると、 セッションや署名鍵へのアクセスが失われる可能性があります。暗号化されたバックアップと鍵は別々に保管し、 隔離されたインスタンスで復旧テストを行ってください。
