# Розгортання та експлуатація

## Виберіть варіант встановлення

Для портативного пакета розпакуйте файл `TgWitness-<version>-windows-amd64-portable.zip` з GitHub Releases. Для інших методів завантажте та розпакуйте ZIP-архів з вихідним кодом або клонуйте репозиторій, а потім виконайте наступну команду з каталогу проєкту:

| Встановлення | Початок | Працює у фоновому режимі? |
| --- | --- | --- |
| Портативний пакет для Windows | `TgWitness.cmd` | Ні; залиште вікно відкритим. |
| Вбудована версія для Windows | `Start.cmd` | Ні; для роботи у фоновому режимі використовуйте додаткове завдання входу в систему. |
| Вбудована підтримка Linux/macOS | `sh start.sh` | Ні; для роботи у фоновому режимі використовуйте systemd/launchd. |
| Docker на будь-якому підтримуваному хості | `docker compose up -d --build --wait` | Так, поки працює демон Docker. |
| Допоміжна програма Docker для Windows | `Docker.cmd` | Так; допоміжна програма очікує на підтвердження працездатності веб-сервера. |
| Допоміжний інструмент Docker для Linux/macOS | `sh docker-start.sh` | Так; допоміжна програма очікує на підтвердження працездатності веб-сервера. |

Нативний запуск створює приватний `.venv` та встановлює закріплені залежності. Docker збирає їх усередині образу, не потребуючи Python на хості. Для первинного налаштування потрібен доступ до Інтернету. Якщо Python 3.11+ не знайдено, `Start.cmd` запитує дозвіл перед встановленням Python 3.12 для поточного користувача Windows (за допомогою winget, або інсталятора з python.org після перевірки підпису Python Software Foundation); він ніколи не вимагає прав адміністратора. Docker та служби ОС залишаються обов’язковими вимогами.

Нативні та портативні інсталяції використовують `data/live` у своїй папці. Docker використовує томі з іменем `tgwitness-data`, розташованому за адресою `/data`. Це окремі інсталяції, доки ви свідомо не перенесете весь каталог даних. Не очікуйте, що новий контейнер Docker автоматично виявить нативні облікові записи.

## Вимоги до встановлення

Для нативної інсталяції потрібні Python 3.11 або новішої версії з `venv` та `ensurepip`, доступ до Інтернету для інсталяції першої залежності, а також каталог проєкту з правами на запис для `.venv`. Вбудована панель не потребує Node.js чи фронтенд-збірки. Запустіть програму-запускач зі свого звичайного облікового запису в ОС; TgWitness не вимагає прав адміністратора/root.

- **Windows:** `Start.cmd` перевіряє `py -3`, потім `python`, а потім стандартні папки встановлення для кожного користувача та «Program Files»; для роботи потрібна версія 3.11 або пізніша. Якщо жодна з цих опцій не працює, пропонується автоматичне встановлення для кожного користувача, описане вище. `py -3 start.py` також працює. Портативний пакет взагалі не потребує Python.
- **Linux:** `start.sh` перевіряє `python3.13`, `python3.12`, `python3.11`, `python3` та `python` і виводить команду встановлення для apt, dnf, pacman, zypper, apk або Homebrew, якщо жодна з них не підходить. Для встановлення на Debian/Ubuntu може знадобитися пакет `python3-venv`, що відповідає обраному інтерпретатору. Стару версію Python, встановлену за замовчуванням у дистрибутиві, необхідно замінити або доповнити Python 3.11+.
- **macOS:** встановіть актуальну версію Python 3.11+; не вважайте, що інтерпретатор, що входить до складу ОС, відповідає вимогам. Використовуйте файл `python3 start.py` з каталогу проєкту.
- **Docker:** використовуйте Docker Engine/Desktop із Compose версії 2.20 або новішої. Docker Desktop повинен використовувати контейнери Linux у Windows. Контейнер встановлює власні залежності Python; на хості не потрібно окремо встановлювати Python.

Використовуйте постійне локальне сховище для каталогу даних. Плануйте ємність з урахуванням обсягу повідомлень, мультимедіа, зростання WAL, експорту та резервних копій; не існує обґрунтованих даними універсальних мінімальних вимог до дискового простору та оперативної пам’яті для кожного навантаження. Архітектури процесорів та версії Python без сумісних коліс залежностей можуть вимагати додаткових інструментів збірки та їхньої окремої атестації. Термін «портативний» не означає універсальної підтримки будь-яких ОС чи апаратного забезпечення.

Локально перевірено на Windows 11/Python 3.12. Налаштування для Linux/macOS/контейнерів та CI надаються, але не виконувалися на цьому хості для розробки. Точний обсяг перевірено див. у [файлі VERIFICATION.md](../VERIFICATION.md).

## Локальний комп'ютер

Використовуйте `Start.cmd` у Windows або `sh start.sh` у Linux/macOS. `Setup.cmd` або `sh start.sh --setup-only` готують робоче середовище. Програма-запускач встановлює необхідні залежності під час першого запуску; під час наступних запусків використовується вже готове середовище. Для налаштування та збору даних із Telegram потрібен доступ до Інтернету, але перегляд існуючих записів та створення експортних файлів працює в автономному режимі.

Після налаштування запустіть `python start.py --check`, щоб перевірити локальні залежності, Ed25519, сховище, конфігурацію ключів та адресу прослуховування без запуску колектора. Використовуйте `--json` для структурованого виводу. Передайте потрібні `--data-dir`, `--host` та `--port`. Ця перевірка не встановлює пакети, не створює журнал і не підключає Telegram; це не є перевіркою цілісності чи охоплення. Команда «Startup» окремо перевіряє наявні журнали. Команда `python start.py --help` також не виконує інсталяцію.

Параметри:

Після запуску start.py виконайте допоміжні команди за допомогою `.venv\Scripts\python.exe` у Windows або `.venv/bin/python` у Linux/macOS, або спочатку активуйте це середовище. У наведених нижче прикладах `python -m ...` передбачається, що середовище вже активне.

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

Змінні середовища: TGWITNESS_DATA, TGWITNESS_HOST, TGWITNESS_PORT, TGWITNESS_TOKEN. TGWITNESS_VAULT_KEY_FILE вибирає режим зовнішнього ключа для нової інсталяції; див. нижче. TGWITNESS_TOKEN, якщо вказано, має містити щонайменше 24 символи; використовуйте криптографічно випадкове значення. Без нього додаток генерує 256-бітний випадковий токен у файлі panel-token.txt. Перезапис змінних середовища не перезаписує цей файл. Перезапустіть додаток, щоб змінити облікові дані.

Каталог даних може належати лише одному процесу. Міжплатформова блокування файлів ОС запобігає випадковому одночасному запису. Використовуйте один робочий процес Uvicorn. Панель може керувати будь-якою кількістю робочих просторів, додаткові каталоги яких розміщуються у папці profiles/<id>/. Для окремих екземплярів сервісу використовуйте окремі каталоги та порти. Файли WAL бази даних SQLite мають зберігатися у локальному постійному сховищі, а не у мережевій файловій системі. Не використовуйте один том для декількох реплік.

## Портативний пакет для Windows

Кожен реліз на GitHub містить `TgWitness-<version>-windows-amd64-portable.zip` та його `.sha256`. Він містить офіційне вбудовуване середовище виконання Python 3.12 з python.org (контрольна сума вказана в `tools/build_portable.py`), TgWitness та його зафіксовані залежності, а також три програми запуску:

| Файл | Мета |
| --- | --- |
| `TgWitness.cmd` | Запустіть панель; додаткові параметри передаються, наприклад, `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | Запустіть синтетичну демонстрацію в `data\demo` |
| `TgWitness-Check.cmd` | Виконайте перевірку готовності без запуску |

Розпакуйте весь архів у папку з правами на запис, наприклад `Documents\TgWitness`; не запускайте програму зсередини ZIP-архіву або з папки «Program Files». Середовище виконання використовує ізольований шлях до модулів, тому інші інсталяції Python та `PYTHONPATH` не впливають на його роботу. Дані зберігаються у папці `data`, що входить до складу пакету. Для оновлення зупиніть TgWitness, розпакуйте нову версію в нову папку та скопіюйте туди папку `data`.

Скомпілюйте самостійно на 64-бітній Windows із Python 3.12:

~~~sh
python tools/build_portable.py
~~~

Програма-збірник перевіряє контрольну суму під час виконання, встановлює обмежені залежності в пакет, виконує перевірку готовності за допомогою вбудованого інтерпретатора та записує ZIP-файл і контрольну суму в `dist/`.

## Контейнер

```sh
docker compose up -d --build --wait
```

Це створює іменований постійний том для /data. Веб-порт прив’язано до 127.0.0.1:8787. Процес працює під UID 10001 зі скороченими правами, кореневою файловою системою, доступною лише для читання, та каталогами /data та /tmp, доступними для запису. `--wait` перевіряє працездатність веб-сервера перед поверненням; він не встановлює авторизацію Telegram та не забезпечує доставку повідомлень. Надані допоміжні програми використовують 180-секундний тайм-аут готовності після збірки. Початкове завантаження залежностей може зайняти більше часу.

Обидва базові файли Compose використовують назву проєкту `tgwitness`, тому розпакування нового релізу в інший каталог не призведе до автоматичного вибору нового тома даних. Для цього проєкту слід підтримувати активним лише одне розгортання. Для незалежних інсталяцій використовуйте унікальний `docker compose -p NAME ...` та інший порт хосту, і зберігайте обидва під час оновлень. Для старішого розгортання, що використовує іншу назву проєкту, продовжуйте використовувати його оригінальну назву з `-p`; `docker compose ls` містить перелік існуючих проєктів.

Скопіюйте `.env.example` до `.env` та змініть `TGWITNESS_PORT`, щоб використовувати інший порт зворотного зв’язку. Наприклад, `TGWITNESS_PORT=8788` відкриває доступ до панелі за адресою `http://127.0.0.1:8788`; контейнер і надалі слухає на порту 8787. `.env` ігнорується Git.

Отримати початковий токен:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

Корисні команди:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` перезапускає колектор після збою або перезапуску демона Docker. На сервері під управлінням Linux увімкніть Docker під час завантаження за допомогою менеджера служб вашого дистрибутива, зазвичай це `sudo systemctl enable --now docker`. У Windows/macOS увімкніть налаштування Docker Desktop «запускати при вході в систему». Вихід із системи, перехід у режим сну або зупинка демона Docker можуть перервати збір даних. Явно зупинений контейнер залишається зупиненим, доки ви його знову не запустите.

У прикладі конфігурації обсяг тома /tmp обмежено до 512 Мб. Замість цього при експорті використовується елемент `temporary-exports/` кожного робочого простору у постійному томі /data. Зарезервуйте там місце для одночасних експортів, зростання журналу/WAL, мультимедіа та резервних копій. Програма запуску та Docker використовують файл constraints.txt для фіксації відповідних версій залежностей середовища виконання. Це не ланцюг постачання з хеш-блокуванням: базовий образ Python та артефакти пакетів все ще потребують незалежної кваліфікації випуску.

Не використовуйте команду `docker compose down -v`, якщо ви не маєте наміру знищити журнал та ключі. Звіт про стан контейнера відображає доступність веб-сервера, а не успішність збору даних з Telegram. Перевіряйте стан колектора панелі, сигнал активності, помилки та події покриття.

### Профіль незалежного спостерігача

Опціональний сервіс `witness` запускає [незалежний свідок](../WITNESS.md) у власному контейнері з власним ключем та журналом у томі `witness-data`, а для колектора надає лише токен свідка, доступний лише для читання. Створіть токен на сторінці **«Witness»** панелі, додайте його разом із токеном бота та каналом до `.env`, а потім запустіть профіль:

```sh
docker compose --profile witness up -d          # compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

Сервіс підключається до колектора в мережі Compose за адресою `http://tgwitness:8787` (`TGWITNESS_WITNESS_COLLECTOR` замінює її, наприклад, `/profiles/<workspace ID>` для іншої робочої області). Для свідка на окремому сервері, який адмініструє хтось інший, використовуйте там `compose.witness.yaml`, встановивши для `TGWITNESS_WITNESS_COLLECTOR` HTTPS-адресу колектора; цей файл містить лише свідка.

## Встановіть опублікований образ

Це стає доступним після успішного проходження [робочого процесу випуску](#автоматизовані-релізи-на-github) та публічної конфігурації пакета GHCR. Ім’я власника репозиторію не вбудовано в це дерево вихідного коду. Використовуйте зображення, показане в підсумку робочого процесу цього випуску.

Скопіюйте `.env.example` у `.env`. Вкажіть `TGWITNESS_IMAGE` як опубліковану версію, використовуючи шлях до репозиторію **з малими літерами**, наприклад:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.6.1
TGWITNESS_PORT=8787
```

Запустіть цей файл окремо, замість `compose.yaml`:

```sh
docker compose -f compose.image.yaml pull
docker compose -f compose.image.yaml up -d --wait
docker compose -f compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

На хості не потрібні збірка з вихідного коду, Python чи компілятор. Робочий процес випуску орієнтований на контейнери Linux AMD64 та ARM64, включаючи віртуальну машину Linux у Docker Desktop. Використовуйте тег версії або `ghcr.io/owner/repository@sha256:...` із підсумку робочого процесу. Не налаштовано переміщення тегу `latest` або автоматичне оновлення додатка. Образ та варіанти з вихідним кодом використовують один і той самий том даних, якщо назви їхніх проєктів збігаються.

## Автоматичне ввімкнення HTTPS на сервері

Використовуйте сервер із Docker, домен, який ви контролюєте, та постійне локальне сховище. Направте записи A/AAAA домену на сервер; публікуйте AAAA лише в тому випадку, якщо до нього надходить IPv6. Дозвольте вхідний трафік TCP 80 та 443, а також вихідний трафік DNS/HTTPS для видачі сертифікатів. Ці порти не повинні бути зайняті іншими службами.

Скопіюйте `.env.example` у `.env` та вкажіть ім’я хосту без схеми та шляху:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

Запустіть збірку вихідного коду з накладенням HTTPS:

```sh
docker compose -f compose.yaml -f compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

Для опублікованого зображення замість цього використовуйте `compose.image.yaml` як перший файл. Збережіть обидва аргументи `-f` для подальших команд status, logs, update та stop.

Caddy отримує та оновлює сертифікат, перенаправляє HTTP на HTTPS та пересилає запити до колектора у приватній мережі Compose. Стан сертифіката зберігається у власному постійному томі. Порт прямого хосту колектора залишається лише для петлевого з’єднання. Надана конфігурація Caddy не вмикає реєстрацію доступу.

Відкрийте `https://watch.your-domain.org` та введіть токен панелі. Готовність до створення повідомлень не підтверджує видачу сертифіката або доступність іззовні. Якщо HTTPS не готовий, перевірте DNS, правила брандмауера та:

```sh
docker compose -f compose.yaml -f compose.https.yaml logs --tail 100 caddy
```

Наданий образ Caddy відповідає тегу `2-alpine`. Виконання команди pull оновлює цей образ; якщо вам потрібні фіксовані версії інфраструктури, закріпіть перевірений дайджест у вашому розгортанні.

## Оновлення та резервні копії

Збережіть назву проєкту Compose та обсяг даних під час оновлень. Спочатку зупиніть колектор і створіть повну резервну копію. Для розгортання за замовчуванням на основі вихідного коду:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

Кожного разу використовуйте нове місце для резервного копіювання, поза межами репозиторію, та захищайте його як матеріал, що вимагає доступу до облікового запису. Наведений приклад шляху є ілюстративним; використовуйте своє приватне місце для резервного копіювання. Скопіюйте весь каталог, включаючи приховані файли, усі робочі простори, ключі, журнали та мультимедійні файли. Окремо створіть резервну копію головного ключа зовнішнього сховища, якщо він налаштований. ZIP-архів з доказами не є резервною копією програми, яку можна відновити. Для HTTPS також збережіть томи Caddy, якщо вам потрібно зберегти стан його сертифіката/облікового запису.

Для розгортання з вихідного коду завантажте файли нової версії та виконайте:

```sh
docker compose up -d --build --wait
```

Для розгортання образу змініть `TGWITNESS_IMAGE` на бажану версію, а потім виконайте:

```sh
docker compose -f compose.image.yaml pull
docker compose -f compose.image.yaml up -d --wait
```

Використовуйте файли Compose вашої інсталяції також для наведених вище команд stop/copy. Збережіть `.env`, власні налаштування та ту саму назву проєкту. `down` зберігає іменовані томи; **`down -v` видаляє їх**. Не копіюйте `.venv` між операційними системами або версіями Python. Для оновлення з вихідного коду зупиніть TgWitness, створіть резервну копію всього каталогу даних, замініть вихідні файли та запустіть `python start.py --setup-only` перед запуском.

Після оновлення перевірте доступ до панелі, ідентифікацію облікового запису, стан спостереження та охоплення. Перезапуск не відновлює пропущені оновлення Telegram. Для відкату може знадобитися резервна копія, створена до оновлення, якщо в майбутніх версіях зміниться формат зберігання даних.

## Автоматизовані релізи на GitHub

[Процес випуску](../../.github/workflows/release.yml) готовий до використання після того, як цей проєкт буде відправлено до репозиторію GitHub із увімкненою функцією Actions. Він запускається під час **публікації** релізу на GitHub, включаючи попередні версії. Самі по собі чернетки та відправлення тегів не призводять до публікації пакетів.

1. Встановіть версію пакета та журнал змін, а потім опублікуйте реліз із тегом `v` та точним зазначенням версії `pyproject.toml`, наприклад `v0.6.1`.
2. Цей робочий процес перевіряє тег та виконує загальні перевірки, пов’язані з Python для Windows/Linux/macOS, браузером для імпорту загальних даних та QR-кодів, пакетом вихідного коду та Docker. Також виконується нова нативна інсталяція на всіх трьох операційних системах із використанням Python 3.12.
3. Після успішного проходження цих перевірок виконується тестування образу ARM64 у QEMU, публікуються образи AMD64/ARM64 на `ghcr.io/<lowercase-owner>/<lowercase-repository>:<version>`, а до релізу додаються вихідний ZIP-файл, контрольна сума та Python-коліщатко. Окреме завдання для Windows збирає та додає портативний ZIP-файл та його контрольну суму.
4. Після першої публікації відкрийте налаштування пакета GHCR і встановіть видимість на **«Public»**, якщо передбачається анонімне завантаження зображень. Сам по собі публічний репозиторій вихідного коду не гарантує публічного контейнерного пакета. Політика організації повинна дозволяти публікацію пакетів. У робочому процесі використовується тег `GITHUB_TOKEN`; у репозиторії не повинні міститися паролі до реєстру або облікові дані VPS.

Ця локальна підготовка не гарантує успішної роботи в віддаленому режимі. Емуляція ARM64 є лише попередньою перевіркою, а не кваліфікацією для роботи на нативному обладнанні чи в реальному середовищі Telegram. Це автоматизує пакування релізів; для запуску сервера все ще потрібна команда Compose та відповідні вимоги до домену/хосту. Існуючі сервери не оновлюються та не перезапускаються автоматично після публікації релізу.

## Віддалений сервер

Забезпечте, щоб сервіс був прив’язаний до петлі зворотного зв’язку та використовував SSH-тунель, або завершуйте HTTPS на зворотньому проксі. Базовий файл Compose доступний лише локально; опціональний оверлей `compose.https.yaml` надає Caddy для налаштованого домену. Не вказуйте токен bearer в URL-адресах та журналах проксі. Зворотній проксі повинен обмежувати розмір запитів та частоту з’єднань. Не відкривайте доступ до простого HTTP в Інтернеті.

Приклади для systemd, завдання входу в систему Windows, агента користувача macOS та Caddy наведено в папці [deploy/](../../deploy/README.md). Перед інсталяцією перегляньте та адаптуйте їхні шляхи. Це лише шаблони, а не локально виконані налаштування платформи. Звичайний запускач не реєструє жодних фонових служб чи завдань.

У Windows запуск без вікна `pythonw.exe` зберігає діагностичні дані запуску/сервера у `logs/server.log` у каталозі даних (5 МБ на файл, дві чергові резервні копії). Запуск у консолі зберігає журнали консолі. Реєстрація доступу по HTTP вимкнена в обох режимах. Захищайте журнали разом із каталогом даних та перевіряйте їх перед тим, як ділитися ними.

## Перезапуск та прогалини

Останній запитуваний стан спостереження зберігається. Якщо спостереження було активним, під час запуску система намагається відновити з’єднання та продовжити роботу з вибраними джерелами. Ручна пауза скасовує цю спробу. Невдалий перезапуск реєструється та відображається на панелі.

StringSession зберігає авторизацію, але не зберігає стійкий стан оновлень/сутностей Telethon. Діалоги перезавантажуються під час запуску. Telegram/Telethon може відновлювати деякі переривання передачі даних під час роботи, але TgWitness не гарантує стійкого відтворення даних після перезапуску процесу. При кожному запуску записується попередня головка журналу та межа офлайн-режиму. Монітор перевіряє підключення кожні 10 секунд і додає сигнал активності щохвилини (**Параметри → Запис активності кожні**). Короткі переривання можуть бути пропущені; підключений транспорт не гарантує повної доставки оновлень. Знімки — це явні спостереження поточної історії, а не відновлення пропусків.

Черга медіафайлів зберігається в базі даних SQLite кожного робочого простору. Повідомлення та відповідне завдання фіксуються атомарно. Перервані завдання відновлюються для повторної спроби під час запуску. Кожне завантаження має базовий тайм-аут у 120 секунд плюс час, необхідний для завантаження файлу розміром 256 КБ/с, а також обмеження у 1–2 000 МБ на тип вкладення; тайм-аут, швидкість та кількість спроб налаштуються у розділі **«Параметри**». Колектор пропускає файли, розмір яких невідомий. Призупинення зберігає завдання у черзі. Повторні спроби використовують оригінальний спостережуваний дескриптор файлу, а не останню версію повідомлення, яке було відредаговано згодом. Тимчасові збої мають обмежену кількість повторних спроб; паузи FloodWait для медіа зберігаються після перезапуску. Відновлення медіа є окремим від відновлення оновлень Telegram і не може відтворити зниклі файли.

## Резервне копіювання, відновлення та ємність

Зупиніть процес перед копіюванням **усього каталогу даних**, включаючи файли vault.key, signing.enc, credentials.enc, базу даних SQLite/файли WAL, мультимедіа, токен, контрольні точки та всі профілі/підкаталоги. Відновіть повну копію, поки служба призначення зупинена. Відсутність ключів сховища або невідповідність ключів підпису призведе до збою запуску; не генеруйте ключі заново, щоб примусово отримати доступ.

Зберігайте резервні копії в зашифрованому вигляді та з контролем доступу. ZIP-файли з доказами — це портативні артефакти для перегляду, а не резервні копії додатків чи сеансів Telegram. Автоматичного видалення після закінчення терміну зберігання не відбувається. Заплануйте місце на диску для всіх повідомлень, необроблених метаданих, мультимедіа, тимчасових експортів та резервних копій.

Перевірка при запуску та експорт записів потоку замість завантаження всього журналу. Експорт фіксує знімок прочитаних даних, тоді як запис нових даних у WAL може продовжуватися; тривалі експорті можуть зберігати сторінки WAL, тому ємність диска все ще має значення. Розмір ZIP-архівів обмежено 4 ГіБ у нестисненому вигляді, щоб відповідати налаштуванням за замовчуванням незалежного верифікатора; **Параметри → «Найбільший підписаний ZIP»** збільшує обмеження, і такі архіви перевіряються за допомогою `verify.py --max-gib N`. Інші формати не мають обмеження на кількість подій. Підтримувані браузери передають фрагменти відповіді у потоковому режимі до файлу, обраного користувачем. Інші браузери буферизують не більше 128 MiB і перенаправляють передачі більшого розміру до авторизованого CLI:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

Використовуйте `--profile ID` з **розділу** **«Експорт» → «Ідентифікатор робочого простору»** для іншого робочого простору, `--format zip|jsonl|csv|html`, `--url https://your-server` для віддаленого сервера або `--max-mib`, щоб змінити обмеження на передачу даних у 5 ГіБ. Простий HTTP дозволено лише для петлевого з’єднання. Токени передаються в заголовках, перенаправлення відхиляються, існуючі файли не перезаписуються, а незавершені завантаження не публікуються як завершені файли. Якщо TGWITNESS_TOKEN замінює згенерований токен, використовуйте окремо захищений файл, що містить це активне значення: файл panel-token.txt не перезаписується під час заміни. SHA-256 команди є лише контрольною сумою передачі; незалежно перевірте підписаний ZIP-архів.

Файли експорту сервера зберігаються у приватному каталозі `temporary-exports/` кожного робочого простору. У разі успішного завершення операції файли видаляються. Перервані експорти видаляються під час наступного запуску робочого простору, коли утримується ексклюзивна блокування його екземпляра. Цей каталог є частиною моделі загроз/ємності сховища; використовуйте зашифрований том даних. Передача даних обсягом у кілька гігабайтів у виробничих умовах все ще вимагає перевірки на вашій цільовій системі.

Панель відображає медіафайли в черзі/з помилками, найстаріші медіафайли в очікуванні, вільне місце на диску, паузи запитів Telegram та джерела, доступ до яких не підтверджено. Ці діагностичні дані не є повноцінним монітором доставки «від кінця до кінця». Робочі простори використовують спільний процес; обліковий запис із великим трафіком все ще може впливати на інші. Залишаються окремі робочі процеси, зберігання/ротація, відновлення стійких оновлень, фіксація віддалених контрольних точок, ролі та повна кваліфікація розгортання.

## Параметри підключення та захисту

Маршрути підключення визначаються для кожного робочого простору окремо і повинні бути налаштовані до авторизації. SOCKS5/HTTP CONNECT використовують закріплену залежність python-socks. MTProxy використовує експериментальний рандомізований проміжний транспорт Telethon; підроблені секрети TLS ee не підтримуються. Автоматичний прямий перехід на резервний маршрут не налаштований. Це не є загальносистемним мережевим маршрутом.

Для нових інсталяцій змінна TGWITNESS_VAULT_KEY_FILE вказує на окремо захищений файл з випадковим головним ключем. Змонтуйте його у режимі «тільки для читання» поза каталогом /data у контейнері. Зберігайте відкриті метадані salt у файлі vault.external.json окремо для кожної робочої області та головного ключа. Існуючі локальні сховища потребують планової міграції; встановлення цієї змінної не призведе до їх автоматичного перетворення. Зберігання повідомлень та медіафайлів, а також їх експорт не шифруються на рівні додатка. За необхідності використовуйте зашифровані томи та достатній обсяг приватного тимчасового сховища.

Детальні інструкції: [підключення/безпека](../CONNECTION-SECURITY.md) та [режими роботи](../OPERATIONS.md).
