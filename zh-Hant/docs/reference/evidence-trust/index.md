# 證據與信任

Canonical page: https://phishdestroy.github.io/TgWitness/zh-Hant/docs/reference/evidence-trust/

匯出資料、影片、網頁存檔及簽署紀錄能證明什麼，以及收集裝置如何影響其可靠性。

匯出檔案、螢幕截圖或錄影皆可作為有用證據。其可靠性取決於其蒐集、保存及佐證的方式**。有效的雜湊值或簽名用於驗證儲存的資料；但無法獨立證明蒐集裝置所接收的來源內容屬實。**此界線同樣適用於 TgWitness。

本指南將技術驗證與法律評估區分開來。產品文件及下方的法律條文已於 2026 年 11 月 1 日進行審閱；Hunchly 的比較內容描述的是其已發布的文件，而非新的產品審計報告。

## 信任在擷取過程中的作用

流程圖 · Telegram 帳戶與服務 → 客戶端、瀏覽器與作業系統; 客戶端、瀏覽器與作業系統 → 匯出、影片或頁面擷取; 匯出、影片或頁面擷取 → 雜湊值與收集器簽名; 雜湊值與收集器簽名 → 由獨立第三方保留的雜湊值 · Telegram 帳戶與服務 · 客戶端、瀏覽器與作業系統 · 匯出、影片或頁面擷取 · 雜湊值與收集器簽名 · 由獨立第三方保留的雜湊值

**圖表轉為文字**

1. Telegram 帳戶與服務 → 客戶端、瀏覽器與作業系統
2. 客戶端、瀏覽器與作業系統 → 匯出、影片或頁面擷取
3. 匯出、影片或頁面擷取 → 雜湊值與收集器簽名
4. 雜湊值與收集器簽名 → 由獨立第三方保留的雜湊值

此處的威脅模型假設攻擊者或操作者可在證據提交前篡改收集環境。這是一項條件性分析，並非聲稱特定裝置或產品已遭入侵。

官方客戶端與加密連線有助於保護正常使用。但這 並不意味著周邊的作業系統、瀏覽器或顯示裝置本身 即具可信度。若內容在解密後但擷取前遭到替換， 匯出者仍能準確儲存該內容，簽署者亦能正確簽署。這兩項 操作均無需仰賴已遭破解的雜湊演算法或偽造的簽名。

在同一裝置上拍攝的影片可記錄相同的替換後畫面。 另一台相機可確認螢幕上顯示的內容，但僅憑螢幕畫面 並不能驗證 Telegram 所提供的內容。同樣地，來自同一受控環境的匹配 HTML、JSON、 螢幕截圖及瀏覽器日誌可能存在相同的 錯誤。它們的一致性雖可作為有用的背景資訊，但並不自動構成 獨立的佐證。

## 各類證據所提供的貢獻

| 資料 | 有用的貢獻 | 剩餘問題 |
| --- | --- | --- |
| Telegram Desktop 匯出 | 可讀或可機讀的對話及選取的媒體 | 誰控制了客戶端和匯出檔案，其中包含哪些內容或排除哪些內容？ |
| 螢幕截圖或螢幕錄影 | 可見的上下文、操作順序與呈現方式 | 此呈现是否忠实反映原始内容，以及录制过程之外发生了什么事？ |
| 本地網頁存檔，包括 MHTML | 頁面內容及相關資源，供日後審查 | 瀏覽器向歸檔器提供了什麼資料，而該瀏覽器由誰控制？ |
| 由收集者簽署的存檔 | 對簽名位元的變更可透過可信賴金鑰及保留的參考進行檢測 | 在簽署前，誰控制了簽署金鑰及輸入資料？ |
| 獨立保留的檢查點或經驗證的時間戳記 | 保留的雜湊值或檢查點，用於與後續提交內容進行比對 | 涵蓋哪些位元組與邊界，且獨立第三方實際上證明了什麼？ |

Telegram 將其桌面版匯出功能描述為離線 HTML/JSON 副本，並將其 Takeout API 描述為檢索選定帳戶資料的方式。這些描述並未提供 最終匯出檔案的 Telegram 簽名，供收件者進行驗證。 我們的結論僅限於這些已記錄的匯出機制；這並非 聲稱 Telegram 證據不具法律價值。[Telegram 桌面版匯出功能](https://telegram.org/blog/export-and-more)、[Takeout API](https://core.telegram.org/api/takeout)。

此區分原則同樣適用於背景請求、快取項目及網路 日誌。這些資料可能揭露不一致之處，並有助於佐證資料蒐集的真實性。其 複雜性本身並不能證明由誰產生。一個獨立運作的 檔案庫或另行取得的服務紀錄，提供了不同的來源供 比對，但須受其自身蒐集與保管限制的約束。

## Hunchly 说明了相同的界限

Hunchly 的文件說明了對 MHTML 擷取內容、照片及附件進行 SHA-256 雜湊運算，並附有獨立的雜湊驗證。文件亦解釋了為何經竄改的檔案若附帶新計算出的雜湊值，仍能通過該比對，並指出簽名與來源佐證是額外的檢查機制。[Hunchly：內容、照片及附件的雜湊運算](https://support.maltego.com/support/solutions/articles/15000061289-content-photo-and-attachment-hashing)。

其已發布的*《證據指南》*（2018年10月17日第1.0版）描述了針對 MHTML 擷取所 生成的本地 GPG 金鑰與簽名。該指南明確指出 存取本地私鑰是重新簽署經修改資料的一種方式。這是一項 有據可查的信任限制，並非未公開當前漏洞的證據。 該指南亦指出，Chrome 會執行 MHTML 擷取。若將 Hunchly 描述為 僅依賴調查人員的聲譽，將忽略這些技術控制措施。 參見《[Hunchly 證據指南》第 2–4 節](https://hunch.ly/resources/Hunchly%20Evidence%20Guide.pdf)。

特定產品所蒐集的資料是否已被案件採納，須視相關裁決及具體情況而定。我們在此不就法院接受 Hunchly 或 TgWitness 的頻率，或這兩款產品是否獲得法院普遍認可，作出任何聲明。

## TgWitness 增添了什麼，以及其保護範圍的界限

TgWitness 將觀察結果記錄於經簽署且具連結的日誌中，並提供收件者可核對的匯出檔案。保留的檢查點、時間戳記以及獨立的見證者，為審查者提供了超出收集者當前檔案範圍的參考依據。這些有助於揭露先前已提交記錄中的變更。覆蓋範圍記錄與明確的收集結果有助於說明哪些內容已被擷取、哪些未被擷取。[證據格式與移交](https://phishdestroy.github.io/TgWitness/zh-Hant/docs/reference/evidence/)、[收集範圍](https://phishdestroy.github.io/TgWitness/zh-Hant/docs/reference/collection/)。

可能的替換時機至關重要：

1. **簽署後，若無法存取簽署金鑰：**修改已簽署的記錄 或與清單綁定的檔案，將無法通過可信驗證器與金鑰的驗證。
2. **使用收集器金鑰時，在保留獨立檢查點之後：**替換日誌可具有有效的新簽名，但若前綴遭變更，則無法 與該較早的檢查點進行比對。僅保留於同一 受控裝置上的檢查點，可連同日誌一併替換。超出 保留範圍的記錄需另行涵蓋。
3. **在涵蓋某項觀察結果的檢查點被獨立保留之前：**虛假輸入可能已被成功簽署並錨定，包括在較早檢查點之後 追加的新記錄。由此產生的檢查點或時間戳 仍涵蓋這些虛假記錄；但並不能證明其真實性。

TgWitness 見證者接收收集器簽署的檢查點；它不會獨立讀取底層的 Telegram 對話。其金鑰與保留的記錄必須分別受到信任。當必須對提交的完整日誌進行見證時，請使用[需要指定最終匯出邊界的交接程序](https://phishdestroy.github.io/TgWitness/zh-Hant/docs/reference/witness/#require-a-witnessed-export-boundary)。一般的完整性驗證仍可報告未經見證的尾部內容。

經驗證的 RFC 3161 回應可佐證檢查點於 當局聲明之時間點確實存在。但此並不能證明 Telegram 訊息的發送時間 或其內容是否屬實。僅憑預先準備的請求或內嵌的回應檔案 並不足夠。透過`tgwitness.verify` 驗證匯出檔案時，檢查 內含的 TSA 簽名需透過`--tsa-ca` 取得明確受信任的 CA。 OpenTimestamps 收據需經獨立的`ots verify` 驗證，並在必要時 進行證明升級。 [时间戳程序](https://phishdestroy.github.io/TgWitness/zh-Hant/docs/reference/timestamp/)，[RFC 3161](https://www.rfc-editor.org/rfc/rfc3161.html)。

在[GitHub Actions 擷取模式中](https://github.com/phishdestroy/TgWitness/blob/main/docs/SEALED-ACTIONS.md)，由臨時託管的執行器收集 訊息。驗證機制將存檔與經核准的工作流程綁定。此模式 仍依賴 GitHub、經核准的軟體與依賴項、輔助程式／瀏覽器 以及隧道。這並非機密硬體、Telegram 簽名，亦非證明 無人存取主機的證據。本機簽署的執行收據同樣屬於 自我報告的測量結果，而非硬體驗證。

## 法律效力取決於其依據

以下四个问题应保持独立：该项目是否如其所述，提交的字节是否与保留的记录相符，内容是否支持所声称的事实，以及适用规则是否允许其使用。加密验证仅能解决该基础的一部分。

在美國聯邦訴訟程序中，《規則 901》規定了認證證據的方式， 包括具備專業知識的證人證詞，以及關於某個流程或系統的證據。 《聯邦證據規則》第 902(13) 條及第 902(14) 條針對特定電子 紀錄及副本提供了認證途徑，並附有程序要求。其委員會備註將 認證與傳聞證據、相關性及歸屬等問題區分開來。單純的軟體 簽名並不等同於該處所述由合格人員所作的認證。[《聯邦證據規則》第 901](https://www.law.cornell.edu/rules/fre/rule_901) 條，[《聯邦證據規則》第 902 條](https://www.law.cornell.edu/rules/fre/rule_902)。

在加拿大《證據法》適用的情況下，第 31.1 條規範了電子文件的認證。第 31.2 條將最佳證據規則與系統完整性或適用的推定相連結；第 31.3 條則明定推定完整性的情境。這些是經明確定義的證據條件，並非一概推定任何持牌調查員或商業產品皆無誤。 [《加拿大證據法》，第 31.1 條](https://laws-lois.justice.gc.ca/eng/acts/C-5/section-31.1.html)、 第[31.2 條](https://laws-lois.justice.gc.ca/eng/acts/C-5/section-31.2.html)、 第[31.3](https://laws-lois.justice.gc.ca/eng/acts/C-5/section-31.3.html) 條。

這些範例並不決定在其他司法管轄區或特定案件中的可採納性。技術性檢查應一致地適用於支持或質疑指控的相關材料。本指南並未聲稱檢方證據通常比辯方證據更容易被採納。

## 準備一份可供他人評估的紀錄

- 請描述帳戶、蒐集裝置、操作者、軟體版本、存取權限、選定範圍及蒐集期間。應記錄中斷情況及可能的安全漏洞，而非將成功的簽名檢查視為裝置無瑕疵的測試。
- 保留原始封包，並記錄傳輸過程、雜湊值及時間來源。透過獨立的可信通道保留金鑰指紋與檢查點。在報告中描述相關內容前，請先驗證實際見證者或時間戳記的覆蓋範圍。
- 應尋求與該主張相符的獨立佐證：其他參與者的 紀錄、獨立擷取的資料，或依法取得的服務紀錄。說明 其獨立性與限制；僅憑副本間的一致性尚不足以作為依據。
- 保留相关上下文。标示已省略的档案、不可用的历史纪录及删节处。必要时准备一份[独立的简化版披露文件](https://github.com/phishdestroy/TgWitness/blob/main/docs/ACCOUNT-EXPORT.md#prepare-a-disclosure-for-a-lawyer-or-another-recipient)，并说明其转换过程，切勿将其呈现为完整的原始文件。
- 向收件者提供驗證說明，以及進行該等檢查所需的資料。請確保觀察結果、技術發現與分析師的結論能夠明確區分。

針對特定交接，請說明檔案雜湊值、可信密鑰、驗證結果以及外部涵蓋的精確範圍。請分別描述來源真實性、帳戶歸屬、完整性及法律結論。此舉可為下一位審查者提供具體的論點供其檢視。
