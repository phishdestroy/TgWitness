# استقرار و بهره‌برداری

## انتخاب روش نصب

برای بستهٔ قابل‌حمل، `TgWitness-<version>-windows-amd64-portable.zip` را از GitHub Releases
استخراج کنید. برای روش‌های دیگر، ZIP کد منبع را دانلود و استخراج کنید یا مخزن را clone کنید، سپس
دستور زیر را در دایرکتوری پروژه اجرا کنید:

| نصب | اجرا | در پس‌زمینه اجرا می‌شود؟ |
| --- | --- | --- |
| بستهٔ قابل‌حمل Windows | `TgWitness.cmd` | خیر؛ پنجره را باز نگه دارید. |
| نصب بومی Windows | `Start.cmd` | خیر؛ برای اجرا در پس‌زمینه از وظیفهٔ اختیاری هنگام ورود به سیستم استفاده کنید. |
| نصب بومی Linux/macOS | `sh start.sh` | خیر؛ برای اجرا در پس‌زمینه از systemd/launchd استفاده کنید. |
| روی هر میزبان پشتیبانی‌شده با Docker | `docker compose up -d --build --wait` | بله، تا زمانی که سرویس Docker (daemon) در حال اجراست. |
| ابزار کمکی Docker در Windows | `scripts\Docker.cmd` | بله؛ ابزار کمکی منتظر می‌ماند تا وب‌سرور سالم شود. |
| ابزار کمکی Docker در Linux/macOS | `sh scripts/docker-start.sh` | بله؛ ابزار کمکی منتظر می‌ماند تا وب‌سرور سالم شود. |

برای سرور ابری‌ای که شخص ثالث باید بتواند آن را بررسی کند — سروری که از طریق API ارائه‌دهنده و
بدون SSH ساخته می‌شود و فقط از طریق Cloudflare Tunnel به آن دسترسی هست —
[استقرار با اطمینان بالا](../HIGH-ASSURANCE.md) را ببینید.

اجرای بومی یک `.venv` خصوصی می‌سازد و وابستگی‌ها را با نسخه‌های تثبیت‌شده نصب می‌کند. Docker
آن‌ها را درون ایمیج می‌سازد و به Python روی میزبان نیازی ندارد. راه‌اندازی نخست به اینترنت نیاز
دارد. اگر Python 3.11 یا جدیدتر پیدا نشود، `Start.cmd` پیش از نصب Python 3.12 برای کاربر فعلی
Windows اجازه می‌گیرد (با winget، وگرنه با نصب‌کنندهٔ python.org پس از بررسی امضای Python Software
Foundation)؛ هرگز دسترسی مدیر سیستم درخواست نمی‌کند. Docker و سرویس‌های سیستم‌عامل همچنان
پیش‌نیازند.

نصب‌های بومی و قابل‌حمل از `data/live` درون پوشهٔ خود استفاده می‌کنند. Docker از ولوم نام‌دار
`tgwitness-data` در مسیر `/data` استفاده می‌کند. تا زمانی که کل دایرکتوری داده را آگاهانه منتقل
نکنید، این‌ها نصب‌های جداگانه‌ای هستند. انتظار نداشته باشید یک کانتینر جدید Docker حساب‌های نصب
بومی را خودکار پیدا کند.

## پیش‌نیازهای نصب

نصب بومی به Python 3.11 یا جدیدتر همراه با `venv` و `ensurepip`، دسترسی به اینترنت برای نخستین
نصب وابستگی‌ها و یک دایرکتوری پروژهٔ قابل‌نوشتن برای `.venv` نیاز دارد. پنل همراه به Node.js یا
بیلد فرانت‌اند نیازی ندارد. راه‌انداز را با حساب کاربری معمولی سیستم‌عامل اجرا کنید؛ TgWitness به
دسترسی مدیر سیستم/root نیاز ندارد.

- **در Windows:** `Start.cmd` به ترتیب `py -3`، `python` و سپس پوشه‌های پیش‌فرض نصبِ مخصوص کاربر و
  Program Files را بررسی می‌کند و نسخهٔ 3.11 یا جدیدتر لازم دارد. اگر هیچ‌کدام کار نکند، نصب
  خودکارِ مخصوص کاربر را که در بالا توضیح داده شد پیشنهاد می‌کند. `py -3 start.py` هم کار می‌کند.
  بستهٔ قابل‌حمل اصلاً به Python نیاز ندارد.
- **در Linux:** `start.sh` به ترتیب `python3.13`، `python3.12`، `python3.11`، `python3` و `python`
  را امتحان می‌کند و اگر هیچ‌کدام شرایط لازم را نداشته باشد، دستور نصب را برای apt، dnf، pacman،
  zypper، apk یا Homebrew چاپ می‌کند. در Debian/Ubuntu ممکن است بستهٔ `python3-venv` متناسب با
  مفسر انتخاب‌شده لازم باشد. Python پیش‌فرض قدیمی‌تر توزیع باید با Python 3.11 یا جدیدتر
  جایگزین شود یا نسخهٔ جدیدتر در کنار آن نصب شود.
- **در macOS:** یک توزیع جدید Python 3.11 یا جدیدتر نصب کنید؛ فرض نکنید مفسری که همراه سیستم‌عامل
  است این نیاز را برآورده می‌کند. در دایرکتوری پروژه از `python3 start.py` استفاده کنید.
- **با Docker:** از Docker Engine/Desktop با Compose v2.20 یا جدیدتر استفاده کنید. Docker Desktop
  در Windows باید از کانتینرهای Linux استفاده کند. کانتینر وابستگی‌های Python خودش را نصب
  می‌کند؛ میزبان به نصب جداگانهٔ Python نیازی ندارد.

## رایانهٔ محلی

در Windows از `Start.cmd` و در Linux/macOS از `sh start.sh` استفاده کنید. `scripts\Setup.cmd` یا
`sh start.sh --setup-only` محیط را آماده می‌کند. راه‌انداز در نخستین استفاده وابستگی‌ها را نصب
می‌کند و اجراهای بعدی از همان محیط استفاده می‌کنند. برای راه‌اندازی و جمع‌آوری از Telegram به
اینترنت نیاز است، اما مرور سوابق موجود و ساختن خروجی به‌صورت آفلاین کار می‌کند.

پس از راه‌اندازی، `python start.py --check` را اجرا کنید تا وابستگی‌های محلی، Ed25519،
ذخیره‌سازی، پیکربندی کلید و نشانی شنود را بدون اجرای جمع‌آورنده بررسی کنید. برای خروجی ساختاریافته
از `--json` استفاده کنید. مقادیر `--data-dir`، `--host` و `--port` موردنظر را بدهید. این بررسی
بسته نصب نمی‌کند، ژورنال نمی‌سازد و به Telegram وصل نمی‌شود؛ ارزیابی صلاحیت یکپارچگی یا پوشش هم
نیست. ژورنال‌های موجود هنگام راه‌اندازی جداگانه راستی‌آزمایی می‌شوند. `python start.py --help` هم
چیزی نصب نمی‌کند.

پس از استفاده از start.py، دستورهای کمکی را در Windows با `.venv\Scripts\python.exe` و در
Linux/macOS با `.venv/bin/python` اجرا کنید، یا ابتدا آن محیط را فعال کنید. مثال‌های
`python -m ...` در ادامه فرض می‌کنند محیط فعال است.

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

متغیرهای محیطی: TGWITNESS_DATA، TGWITNESS_HOST، TGWITNESS_PORT، TGWITNESS_TOKEN. متغیر
TGWITNESS_VAULT_KEY_FILE حالت کلید خارجی را برای نصب جدید انتخاب می‌کند؛ [کلید اصلی خارجی](../SECURITY-MODEL.md#external-master-key) را ببینید.
TGWITNESS_TOKEN در صورت تعیین باید دست‌کم 24 نویسه داشته باشد؛ از مقداری استفاده کنید که
به‌صورت رمزنگارانه تصادفی باشد. بدون آن، برنامه یک توکن تصادفی 256 بیتی در panel-token.txt تولید
می‌کند. مقداردهی از طریق متغیر محیطی آن فایل را بازنویسی نمی‌کند. برای چرخش اعتبارنامه‌ها، برنامه
را دوباره راه‌اندازی کنید.

هر دایرکتوری داده فقط می‌تواند متعلق به یک فرایند باشد. یک قفل فایل سیستم‌عامل که روی همهٔ
سکوها کار می‌کند از نوشتن هم‌زمانِ ناخواسته جلوگیری می‌کند. برای Uvicorn یک worker به کار
ببرید. پنل می‌تواند هر تعداد فضای کاری را مدیریت کند و دایرکتوری‌های فضاهای کاری اضافی زیر
profiles/<id>/ قرار می‌گیرند. برای نمونه‌های جداگانهٔ سرویس، از دایرکتوری‌ها و پورت‌های جداگانه
استفاده کنید. فایل‌های WAL در SQLite باید روی ذخیره‌سازی محلی پایدار باشند، نه روی فایل‌سیستم
شبکه‌ای. یک ولوم را بین چند replica مشترک نکنید.

## بستهٔ قابل‌حمل Windows

هر GitHub Release فایل `TgWitness-<version>-windows-amd64-portable.zip` و فایل `.sha256` آن را
دارد. این بسته شامل محیط اجرای رسمی و قابل‌جاسازی Python 3.12 از python.org (با چک‌سامی که در
`tools/build_portable.py` تثبیت شده)، TgWitness و وابستگی‌های نسخه‌تثبیت‌شدهٔ آن، و سه راه‌انداز
است:

| فایل | کاربرد |
| --- | --- |
| `TgWitness.cmd` | پنل را اجرا می‌کند؛ گزینه‌های اضافی عیناً منتقل می‌شوند، مثلاً `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | دموی مصنوعی را در `data\demo` اجرا می‌کند |
| `TgWitness-Check.cmd` | بررسی آمادگی را بدون اجرای برنامه انجام می‌دهد |

فرهنگ ریخت‌شناسی زبان روسی با نسخهٔ تثبیت‌شده و پروفایل‌های رنگ PDF برای استفادهٔ آفلاین در بسته
گنجانده شده‌اند. بسته‌بندی در دایرکتوری‌های `data` وابستگی‌ها فقط مسیرهای شناخته‌شدهٔ همین
فایل‌ها را مجاز می‌داند؛ هر فایل غیرمنتظره در این دایرکتوری‌ها باعث شکست بیلد می‌شود.

کل آرشیو را در پوشه‌ای قابل‌نوشتن مانند `Documents\TgWitness` استخراج کنید؛ آن را از داخل ZIP یا
از Program Files اجرا نکنید. محیط اجرا از مسیر ماژول ایزوله استفاده می‌کند، بنابراین نصب‌های دیگر
Python و `PYTHONPATH` روی آن اثری ندارند. داده‌ها در پوشهٔ `data` بسته می‌مانند. برای به‌روزرسانی،
TgWitness را متوقف کنید، نسخهٔ جدید را در پوشه‌ای جدید استخراج کنید و پوشهٔ `data` را به آنجا کپی
کنید.

برای ساختن بسته به‌دست خودتان روی Windows 64 بیتی با Python 3.12:

~~~sh
python tools/build_portable.py
~~~

## کانتینر

```sh
docker compose up -d --build --wait
```

این دستور یک ولوم نام‌دار و پایدار برای /data می‌سازد. پورت وب به 127.0.0.1:8787 نگاشت می‌شود.
فرایند با UID 10001، با capabilityهای حذف‌شده، فایل‌سیستم ریشهٔ فقط‌خواندنی و /data و /tmp
قابل‌نوشتن اجرا می‌شود. `--wait` پیش از بازگشت، سلامت وب‌سرور را بررسی می‌کند؛ وضعیت مجوز Telegram
و تحویل در پنل نمایش داده می‌شود. ابزارهای کمکی ارائه‌شده پس از بیلد، مهلت آمادگی 180 ثانیه‌ای
دارند. دانلود اولیهٔ وابستگی‌ها ممکن است بیشتر از این طول بکشد.

هر دو فایل پایهٔ Compose از نام پروژهٔ `tgwitness` استفاده می‌کنند، بنابراین استخراج نسخهٔ جدید
در دایرکتوری دیگر بی‌سروصدا ولوم دادهٔ جدیدی انتخاب نمی‌کند. برای این پروژه فقط یک استقرار را فعال
نگه دارید. برای نصب‌های مستقل، از `docker compose -p NAME ...` با نامی یکتا و پورت میزبان متفاوت
استفاده کنید و هر دو را در به‌روزرسانی‌ها حفظ کنید. برای استقرار قدیمی‌تری که نام پروژهٔ دیگری
دارد، همچنان نام اصلی آن را با `-p` به کار ببرید؛ `docker compose ls` پروژه‌های موجود را فهرست
می‌کند.

برای استفاده از پورت loopback دیگر، `deploy/env.example` را به `.env` کپی کنید و `TGWITNESS_PORT`
را تغییر دهید. برای مثال، `TGWITNESS_PORT=8788` پنل را در `http://127.0.0.1:8788` در دسترس قرار
می‌دهد؛ کانتینر همچنان روی 8787 گوش می‌دهد. Git فایل `.env` را نادیده می‌گیرد.

توکن اولیه را بازیابی کنید:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

دستورهای مفید:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

تنظیم `restart: unless-stopped` پس از کرش یا راه‌اندازی مجدد سرویس Docker (daemon)، جمع‌آورنده را
دوباره راه‌اندازی می‌کند. روی سرور Linux، اجرای Docker هنگام بوت را با مدیر سرویس توزیع خود فعال
کنید؛ معمولاً با `sudo systemctl enable --now docker`. در Windows/macOS، گزینهٔ اجرای Docker Desktop
هنگام ورود به سیستم را فعال کنید. خروج از حساب دسکتاپ، حالت خواب یا متوقف بودن سرویس Docker
می‌تواند جمع‌آوری را قطع کند. کانتینری که صراحتاً متوقف شده، تا وقتی دوباره آن را اجرا نکنید
متوقف می‌ماند.

در پیکربندی نمونه، ولوم /tmp به 512 MiB محدود است. خروجی‌ها در عوض در `temporary-exports/` هر
فضای کاری روی /data پایدار ساخته می‌شوند. در آنجا برای خروجی‌های هم‌زمان، رشد ژورنال/WAL، رسانه‌ها و
پشتیبان‌ها فضا کنار بگذارید. راه‌انداز از deploy/constraints.txt برای تثبیت نسخه‌های تأییدشدهٔ
وابستگی‌های زمان اجرا استفاده می‌کند. Docker و سرورهای با اطمینان بالا از deploy/requirements.lock و
deploy/build.lock با pip --require-hashes نصب می‌کنند: هر فایل بسته باید با یک SHA-256 ثبت‌شده در
commit مطابقت داشته باشد، بنابراین فایلی که در PyPI یا یک mirror جایگزین شده باشد رد می‌شود. ایمیج
پایهٔ Python و بسته‌های سیستم‌عامل همچنان به ارزیابی صلاحیت مستقل برای هر نسخه نیاز دارند.

از docker compose down -v استفاده نکنید، مگر اینکه قصد نابود کردن ژورنال و کلیدها را داشته باشید.
وضعیت سلامت کانتینر در دسترس بودن وب‌سرور را گزارش می‌کند، نه ثبت موفق از Telegram را. وضعیت
جمع‌آورنده، تپش قلب، خطاها و رویدادهای پوشش را در پنل بررسی کنید.

### پروفایل شاهد مستقل

سرویس اختیاری `witness` یک [شاهد مستقل](../WITNESS.md) را در کانتینر خودش اجرا می‌کند؛ کلید و
ژورنال خودش را در ولوم `witness-data` دارد و برای دسترسی به جمع‌آورنده فقط یک توکن شاهد فقط‌خواندنی
در اختیار دارد. توکن را در پنل از مسیر **ابزارهای بیشتر → افزونه‌ها → شاهد مستقل** بسازید، آن را
همراه با توکن بات و کانال به `.env` اضافه کنید، سپس پروفایل را اجرا کنید:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

این سرویس درون شبکهٔ Compose از طریق `http://tgwitness:8787` به جمع‌آورنده دسترسی دارد
(`TGWITNESS_WITNESS_COLLECTOR` این مقدار را جایگزین می‌کند؛ برای مثال `/profiles/<workspace ID>`
برای فضای کاری دیگر). برای شاهدی روی سرور جداگانه که شخص دیگری اداره‌اش می‌کند، در آنجا از
`deploy/compose/compose.witness.yaml` استفاده کنید و `TGWITNESS_WITNESS_COLLECTOR` را روی نشانی
HTTPS جمع‌آورنده تنظیم کنید؛ آن فایل فقط شاهد را در بر دارد.

## نصب ایمیج منتشرشده

فایل `deploy/env.example` را به `.env` کپی کنید. `TGWITNESS_IMAGE` را با مسیر مخزن به
**حروف کوچک** روی نسخهٔ منتشرشده تنظیم کنید، برای مثال:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.9.3
TGWITNESS_PORT=8787
```

این فایل را به‌تنهایی و به‌جای `compose.yaml` اجرا کنید:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

روی میزبان به بیلد از کد منبع، Python یا کامپایلر نیازی نیست. گردش‌کار انتشار کانتینرهای Linux با
معماری AMD64 و ARM64، از جمله ماشین مجازی Linux در Docker Desktop، را هدف می‌گیرد. از یک تگ نسخه
یا `ghcr.io/owner/repository@sha256:...` از خلاصهٔ گردش‌کار استفاده کنید. هیچ تگ متحرک `latest` یا
ارتقای خودکار و بدون نظارت برنامه پیکربندی نشده است. اگر نام پروژه یکسان باشد، نسخه‌های مبتنی بر
ایمیج و کد منبع از یک ولوم داده استفاده می‌کنند.

## فعال‌سازی خودکار HTTPS روی سرور

از سروری با Docker، دامنه‌ای که در اختیار شماست و ذخیره‌سازی محلی پایدار استفاده کنید. رکوردهای
A/AAAA دامنه را به سرور اشاره دهید؛ رکورد AAAA را فقط در صورتی منتشر کنید که سرور از طریق IPv6 در
دسترس باشد. ترافیک ورودی TCP روی 80 و 443 و ترافیک خروجی DNS/HTTPS را برای صدور گواهی مجاز کنید.
این پورت‌ها نباید از قبل در اختیار سرویس‌های دیگر باشند.

فایل `deploy/env.example` را به `.env` کپی کنید و نام میزبان را بدون scheme یا مسیر تنظیم کنید:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

بیلد از کد منبع را با لایهٔ HTTPS اجرا کنید:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

برای ایمیج منتشرشده، به‌جای آن `deploy/compose/compose.image.yaml` را فایل اول قرار دهید. هر دو
آرگومان `-f` را در دستورهای بعدی وضعیت، لاگ‌ها، به‌روزرسانی و توقف نگه دارید.

وب‌سرور Caddy گواهی را دریافت و تمدید می‌کند، HTTP را به HTTPS هدایت می‌کند و درخواست‌ها را در
شبکهٔ خصوصی Compose به جمع‌آورنده می‌فرستد. وضعیت گواهی ولوم پایدار خودش را دارد. پورت مستقیم
جمع‌آورنده روی میزبان همچنان فقط روی loopback در دسترس است. پیکربندی Caddy ارائه‌شده ثبت لاگ
دسترسی را فعال نمی‌کند.

نشانی `https://watch.your-domain.org` را باز کنید و توکن پنل را وارد کنید. آمادگی Compose
کانتینرها را پوشش می‌دهد؛ صدور گواهی و دسترس‌پذیری از بیرون به DNS و فایروال بستگی دارد. اگر HTTPS
آماده نیست، DNS، قواعد فایروال و خروجی دستور زیر را بررسی کنید:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

ایمیج Caddy ارائه‌شده تگ `2-alpine` خود را دنبال می‌کند. pull کردن، این ایمیج را تازه می‌کند؛ اگر
به نسخه‌های ثابت زیرساخت نیاز دارید، یک digest آزموده را در استقرار خود تثبیت کنید.

## به‌روزرسانی‌ها و پشتیبان‌گیری

نام پروژهٔ Compose و ولوم داده را در طول به‌روزرسانی‌ها حفظ کنید. ابتدا جمع‌آورنده را متوقف کنید و
یک پشتیبان کامل بگیرید. برای استقرار پیش‌فرض مبتنی بر کد منبع:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

هر بار از مقصد پشتیبان تازه‌ای بیرون از مخزن استفاده کنید و از آن مانند هر چیزی که دسترسی به
حساب را ممکن می‌کند محافظت کنید. مسیر نمونه فقط برای توضیح است؛ از محل پشتیبان خصوصی خودتان
استفاده کنید. کل دایرکتوری را، از جمله فایل‌های پنهان، همهٔ فضاهای کاری، کلیدها، ژورنال‌ها و
رسانه‌ها، کپی کنید. اگر کلید اصلی خارجی گاوصندوق پیکربندی شده، از آن جداگانه پشتیبان بگیرید.
ZIP مدرک، پشتیبان قابل‌بازیابی برنامه نیست. برای HTTPS، اگر لازم است وضعیت گواهی/حساب Caddy حفظ
شود، ولوم‌های Caddy را هم نگه دارید.

در استقرار از کد منبع، فایل‌های نسخهٔ جدید را تهیه کنید و اجرا کنید:

```sh
docker compose up -d --build --wait
```

در استقرار مبتنی بر ایمیج، `TGWITNESS_IMAGE` را به نسخهٔ موردنظر تغییر دهید، سپس اجرا کنید:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

برای دستورهای توقف/کپی بالا هم از فایل (یا فایل‌های) Compose نصب خود استفاده کنید. `.env`،
پیکربندی سفارشی و همان نام پروژه را حفظ کنید. `down` ولوم‌های نام‌دار را نگه می‌دارد؛
**`down -v` آن‌ها را حذف می‌کند**. `.venv` را بین سیستم‌عامل‌ها یا نسخه‌های مختلف Python کپی
نکنید. برای به‌روزرسانی نصب بومی، TgWitness را متوقف کنید، از کل دایرکتوری داده‌اش پشتیبان بگیرید،
فایل‌های کد منبع را جایگزین کنید و پیش از اجرا `python start.py --setup-only` را اجرا کنید.

پس از به‌روزرسانی، دسترسی به پنل، هویت حساب، وضعیت مشاهده و پوشش را بررسی کنید. پس از راه‌اندازی
مجدد، TgWitness از موقعیت ذخیره‌شدهٔ به‌روزرسانی‌های Telegram ادامه می‌دهد و به‌روزرسانی‌هایی را که
در طول به‌روزرسانی از دست رفته‌اند درخواست می‌کند. اگر نسخه‌ای در آینده قالب‌های ذخیره‌سازی را
تغییر دهد، بازگشت به نسخهٔ قبلی ممکن است به پشتیبانِ پیش از به‌روزرسانی نیاز داشته باشد.

## سرور راه دور

سرویس را به loopback محدود نگه دارید و از تونل SSH استفاده کنید، یا HTTPS را در یک پروکسی معکوس
خاتمه دهید. فایل پایهٔ Compose فقط برای استفادهٔ محلی است؛ لایهٔ اختیاری
`deploy/compose/compose.https.yaml` برای دامنهٔ پیکربندی‌شده Caddy را فراهم می‌کند. توکن bearer را
از URLها و لاگ‌های پروکسی دور نگه دارید. پروکسی معکوس باید اندازهٔ درخواست‌ها و نرخ اتصال را محدود
کند. HTTP بدون رمزگذاری را در معرض اینترنت قرار ندهید.

نمونه‌هایی برای systemd، وظیفهٔ ورود به سیستم در Windows، user agent در macOS و Caddy در
[deploy/](../../deploy/README.md) ارائه شده‌اند. پیش از نصب، مسیرهای آن‌ها را بررسی و متناسب‌سازی
کنید. این‌ها قالب‌های ارائه‌شده‌اند، نه ارزیابی صلاحیت سکو که به‌صورت محلی اجرا شده باشد.
راه‌انداز معمولی هیچ سرویس یا وظیفهٔ پس‌زمینه‌ای ثبت نمی‌کند.

در Windows، اجرای بدون پنجره با `pythonw.exe` اطلاعات عیب‌یابی راه‌اندازی/سرور را در
`logs/server.log` زیر دایرکتوری داده ذخیره می‌کند (5 MiB برای هر فایل، دو پشتیبان چرخشی). اجرا از
کنسول ثبت لاگ در کنسول را حفظ می‌کند. ثبت لاگ دسترسی HTTP در هر دو حالت غیرفعال است. از لاگ‌ها
همراه با دایرکتوری داده محافظت کنید و پیش از اشتراک‌گذاری آن‌ها را بازبینی کنید.

## راه‌اندازی مجدد و شکاف‌ها

آخرین وضعیت درخواست‌شدهٔ مشاهده ذخیره می‌شود. اگر مشاهده فعال بوده باشد، هنگام راه‌اندازی تلاش
می‌شود اتصال دوباره برقرار شود و منابع انتخاب‌شده از سر گرفته شوند. توقف دستی این قصد را پاک
می‌کند. راه‌اندازی مجدد ناموفق ثبت و در پنل نمایش داده می‌شود.

برنامهٔ TgWitness موقعیت به‌روزرسانی Telegram را برای حساب و برای هر کانال (pts، qts، seq و date)
در گاوصندوق فضای کاری ذخیره می‌کند و در اجرای بعدی بازیابی می‌کند. سپس کلاینت به‌روزرسانی‌هایی را
که هنگام توقف فرایند از دست رفته‌اند درخواست می‌کند، و بازبینی دوره‌ای پیام‌های ازدست‌رفته را
بازیابی و پیام‌های ذخیره‌شده‌ای را که Telegram دیگر برنمی‌گرداند ثبت می‌کند. فهرست گفتگوها
(dialogs) هنگام اجرا دوباره بارگذاری می‌شود. هر راه‌اندازی، سرِ ژورنال قبلی، مرز دورهٔ آفلاین و
موقعیت به‌روزرسانی‌ای را که از آن ادامه داده ثبت می‌کند. پایشگر هر 10 ثانیه اتصال را بررسی می‌کند
و هر دقیقه یک تپش قلب اضافه می‌کند (**ابزارهای بیشتر → پارامترها → ثبت نشانه فعالیت هر**). قطع
اتصال‌ها و دوره‌های سکوت به‌عنوان شکاف‌های پوشش همراه با دلیلشان ثبت می‌شوند. تصویرهای لحظه‌ای
تاریخچه به‌صورت مشاهدات جداگانهٔ «تاریخچهٔ فعلی» در کنار رکوردهای زنده ذخیره می‌شوند.

صف رسانه در پایگاه دادهٔ SQLite هر فضای کاری ذخیره می‌شود. پیام و کار مربوط به آن به‌صورت اتمیک
commit می‌شوند. کارهای در حال اجرایی که قطع شده‌اند هنگام راه‌اندازی برای تلاش دوباره بازیابی
می‌شوند. هر دانلود مهلت پایهٔ 120 ثانیه دارد، به‌علاوهٔ زمانی متناسب با اندازه‌اش با سرعت
256 KiB/s، و برای هر نوع پیوست سقفی بین 1 تا 2,000 MiB؛ مهلت، سرعت و تلاش‌های دوباره در
**ابزارهای بیشتر → پارامترها** قرار دارند. جمع‌آورنده فایل‌هایی را که اندازه‌شان معلوم نیست رد
می‌کند. توقف موقت، کارهای صف‌شده را حفظ می‌کند. تلاش دوباره از توصیفگر فایلی استفاده می‌کند که در
اصل مشاهده شده است، نه از آخرین نسخهٔ پیامی که بعداً ویرایش شده باشد. خطاهای موقت تعداد محدودی
تلاش دوباره دارند؛ توقف‌های FloodWait رسانه پس از راه‌اندازی مجدد هم برقرار می‌مانند. بازیابی
رسانه از بازیابی به‌روزرسانی‌های Telegram جداست و نمی‌تواند فایل‌های ناپدیدشده را دوباره بسازد.

## پشتیبان‌گیری، بازیابی و ظرفیت

پیش از کپی کردن **کل دایرکتوری داده**، شامل vault.key، signing.enc، credentials.enc، فایل‌های پایگاه
دادهٔ SQLite/WAL، رسانه‌ها، توکن، نقاط کنترل و همهٔ زیردایرکتوری‌های profiles/، فرایند را متوقف
کنید. نسخهٔ کامل را زمانی بازیابی کنید که سرویس مقصد متوقف است. نبودِ کلیدهای گاوصندوق یا ناهمخوانی
کلید امضا باعث شکست راه‌اندازی می‌شود؛ برای دسترسی اجباری، کلیدها را دوباره تولید نکنید.

پشتیبان‌هایی را که رازها را در بر دارند رمزگذاری‌شده و با کنترل دسترسی نگه دارید. ZIPهای مدرک
فایل‌هایی قابل‌حمل برای بازبینی‌اند، نه پشتیبان برنامه یا پشتیبان جلسهٔ Telegram. حذف خودکار بر
اساس دورهٔ نگهداری وجود ندارد. برای همهٔ پیام‌ها، فرادادهٔ خام، رسانه‌ها، خروجی‌های موقت و
پشتیبان‌ها فضای دیسک برنامه‌ریزی کنید.

راستی‌آزمایی هنگام راه‌اندازی و خروجی‌گیری، رکوردها را به‌صورت جریانی پردازش می‌کنند و کل ژورنال
را بارگذاری نمی‌کنند. هر خروجی یک تصویر لحظه‌ای خواندنی را ثابت نگه می‌دارد، در حالی که نوشتن‌های جدید
WAL می‌توانند ادامه یابند؛ خروجی‌های طولانی ممکن است صفحه‌های WAL را نگه دارند، پس ظرفیت دیسک همچنان
مهم است. ZIPها برای هماهنگی با پیش‌فرض ابزار راستی‌آزمایی مستقل به 4 GiB بدون فشرده‌سازی محدودند؛
**ابزارهای بیشتر → پارامترها → بزرگ‌ترین فایل ZIP امضا شده** این سقف را بالا می‌برد و چنین
آرشیوهایی با `verify.py --max-gib N` راستی‌آزمایی می‌شوند. قالب‌های دیگر سقفی برای تعداد رویدادها
ندارند. مرورگرهای پشتیبانی‌شده تکه‌های پاسخ را به‌صورت جریانی در فایلی که کاربر انتخاب کرده
می‌نویسند. مرورگرهای دیگر حداکثر 128 MiB را بافر می‌کنند و انتقال‌های بزرگ‌تر را به CLI
احرازهویت‌شده ارجاع می‌دهند:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

برای فضای کاری دیگر از `--profile ID` با مقدار **خروجی‌ها → شناسهٔ فضای کاری** استفاده کنید؛ همچنین
از `--format zip|jsonl|csv|html`، برای سرور راه دور از `--url https://your-server` و برای تغییر سقف
انتقال 5 GiB از `--max-mib`. HTTP بدون رمزگذاری فقط برای loopback مجاز است. توکن‌ها در هدرها
منتقل می‌شوند، تغییرمسیرها رد می‌شوند، فایل‌های موجود بازنویسی نمی‌شوند و دانلودهای ناتمام به‌عنوان
فایل کامل منتشر نمی‌شوند. اگر TGWITNESS_TOKEN جایگزین توکن تولیدشده شده باشد، از فایلی جداگانه و
محافظت‌شده که همان مقدار فعال را دارد استفاده کنید: این جایگزینی panel-token.txt را بازنویسی
نمی‌کند. SHA-256ای که دستور نشان می‌دهد فقط چک‌سام انتقال است؛ ZIP امضاشده را مستقلاً
راستی‌آزمایی کنید.

پنل رسانه‌های در صف/ناموفق، قدیمی‌ترین رسانهٔ در انتظار، فضای آزاد دیسک، توقف‌های درخواست Telegram
و منابعی را که دسترسی به آن‌ها تأیید نشده نمایش می‌دهد. این اطلاعات عیب‌یابی، پایشگر کاملِ تحویل
سرتاسری نیستند. فضاهای کاری یک فرایند را به اشتراک می‌گذارند؛ حسابی که بار زیادی ایجاد می‌کند
همچنان می‌تواند بر بقیه اثر بگذارد. فرایندهای worker جداگانه، نگهداری/چرخش، بازیابی پایدار
به‌روزرسانی‌ها و ارزیابی صلاحیت کامل استقرار هنوز باقی مانده‌اند. دسترسی محدودشده به پنل در
[دسترسی و مجوزها](../ACCESS.md) مستند شده است؛ نقاط کنترل مستقل در [راهنمای شاهد](../WITNESS.md)
پوشش داده شده‌اند.

روندهای تفصیلی: [اتصال/امنیت](../CONNECTION-SECURITY.md) و [حالت‌های عملیاتی](../OPERATIONS.md).
