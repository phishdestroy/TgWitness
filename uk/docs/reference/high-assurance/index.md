# Розгортання з високим рівнем безпеки

Canonical page: https://phishdestroy.github.io/TgWitness/uk/docs/reference/high-assurance/

Захищений сервер, що працює цілодобово без вихідних, на Hetzner або Phala Cloud, шлюз DNS та перевірки, які може повторити третя сторона.

Підписаний журнал підтверджує, що записи не були змінені **після** підписання. У серйозних випадках наступне питання полягає в тому, чи міг хтось змінити дані **до** їх підписання: хто запускав колектор, на якій машині та чи хтось входив у систему. Цей опціональний режим розгортає колектор таким чином, щоб третя сторона могла це перевірити, використовуючи записи, що зберігаються хмарним провайдером та Cloudflare, а не покладаючись на слова оператора.

Звичайне використання локальних середовищ та Docker залишається без змін. Ніщо тут не працює, доки ви не розгорнете систему за допомогою `python -m tgwitness.cloud`, а колектор зчитує дані зі свого хоста лише тоді, коли розгортання встановлює `TGWITNESS_ASSURANCE`.

Блок-схема · Оператор → Сервер, брандмауер без правил вхідного трафіку (API-інтерфейс провайдера); Оператор → Тунель і DNS (API Cloudflare); Сервер, брандмауер без правил вхідного трафіку → Тунель і DNS (тільки вихідні повідомлення); Сервер, брандмауер без правил вхідного трафіку → Ключ підпису, створений на сервері; Verifier, токени тільки для читання → Журнал провайдера та брандмауер; Verifier, токени тільки для читання → Адреса тунельного коннектора та вхідний трафік; Verifier, токени тільки для читання → Підписана заява /api/assurance; Verifier, токени тільки для читання → ЗIP-архів доказів · Оператор · Verifier, токени тількидля читання · Сервер, брандмауер безправил вхідного трафіку · Журнал провайдера табрандмауер · Адреса тунельногоконнектора та вхіднийтрафік · Підписана заява/api/assurance · ЗIP-архів доказів · Тунель і DNS · Ключ підпису, створений насервері · API-інтерфейс провайдера · API Cloudflare · тільки вихідні повідомлення

## Що може перевіряти верифікатор

| Заява | Як це перевіряється | Веде |
| --- | --- | --- |
| Сервер було створено за допомогою API провайдера у відомий час | Об’єкт «Сервер» та його створення у власному журналі провайдера | Провайдер |
| Ніхто не використовував шляхи доступу провайдера | Журнал запитів консолі, відновлення, скидання пароля, перебудови, ISO, образів, резервних копій | Провайдер |
| Ніщо не могло підключитися до нього | Брандмауер провайдера не має правил вхідного трафіку; SSH приховано з моменту першого запуску | Провайдер (брандмауер), хост (SSH) |
| До панелі можна отримати доступ лише через тунель | Вхідний тунель перенаправляє трафік виключно на панель; коннектор працює з адреси сервера | Cloudflare |
| Саме це програмне забезпечення працює | Підписаний хеш дерева вихідного коду колектора дорівнює копії розгорнутого коміту | Collector, перевірено за допомогою Git |
| Ключ підпису було створено на цьому сервері | Ключ підписує повідомлення, в якому вказано ідентифікатор сервера провайдера та хеш отриманого ним файлу cloud-init | Collector, перевірений провайдером |
| Журнал належить цьому ключу та серверу | Кожен процес, що запускається в доказі ZIP, містить показники хосту для цього сервера | Докази ZIP |

Показники хосту (SSH-приймачі та процеси, поточні сесії, входи в `wtmp`, завантаження) повідомляються самим колектором і підписуються під час кожного запуску процесу та у `host.state` записів щоразу, коли вони змінюються. Користувач із правами root на сервері міг би їх сфальсифікувати; вони підтримують записи провайдера та Cloudflare, а не замінюють їх.

## Провайдери

| `--provider` | Повноваження | Доступ Verifier лише для читання | Журнал провайдера для верифікатора | Зберігається для |
| --- | --- | --- | --- | --- |
| `hetzner` | `HCLOUD_TOKEN` | Токен для читання того самого проєкту | Дії сервера та брандмауера | Поки ці ресурси існують |
| `digitalocean` | `DIGITALOCEAN_TOKEN` | Особистий токен доступу тільки для читання | Дії Droplet | Поки Droplet існує |
| `linode` | `LINODE_TOKEN` | `linodes`, `firewall`, `events` області, доступні лише для читання | Події облікового запису, версії правил брандмауера | 90 днів |
| `vultr` | `VULTR_API_KEY` | Користувач із доступом на читання та `activity_logs` дозволом | Журнал активності облікового запису (метод, шлях, виконавець) | 30 днів, а з підпискою на журнал аудиту — ще довше |
| `aws` | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | `ec2:DescribeInstances`, `ec2:DescribeSecurityGroups`, `cloudtrail:LookupEvents` | Історія подій CloudTrail | 90 днів |
| `phala` | `PHALA_CLOUD_API_KEY` | Ключ API цього ж робочого простору | Зміни в додатку: зміни в коді та середовищі, перезапуски, оновлення ОС | Поки додаток існує |
| `generic` | немає | немає | none: **самозасвідчений** | – |

Для кожної справи використовуйте окремий проєкт, команду, обліковий запис або підобліковий запис: тоді доступ верифікатора «тільки для читання» показуватиме лише це розгортання. Повноваження зчитуються з `--provider-token-file` або з наведеної вище змінної, ніколи — з командного рядка. Для AWS у файлі вказується `ACCESS_KEY_ID SECRET_ACCESS_KEY [SESSION_TOKEN]`; регіон — це `--location`.

У кожному звіті вказується, що саме не відображається у записах кожного провайдера. Коротко: Hetzner реєструє запити до консолі; консоль відновлення DigitalOcean, Lish/Glish від Linode та веб- консоль Vultr не реєструються як такі, тому доступ root блокується під час першого завантаження, а для входу в консоль потрібно скинути пароль або змінити параметри завантаження, що реєструється. Vultr повертає адресу консолі будь-якому ключу, який може зчитувати інстанцію; ані запис, ані звіт її не зберігають.

## Конфіденційна віртуальна машина на Phala Cloud (Intel TDX)

При цьому `--provider phala` колектор працює у конфіденційній віртуальній машині Intel TDX на [Phala Cloud](https://phala.com/), якою керує dstack. Хост та персонал Phala не можуть читати її пам’ять, а процесор підписує підтвердження того, що саме запустила машина. Верифікатор не покладається лише на слова Phala: `tgwitness.tdx` самостійно перевіряє кожне підтвердження, аж до закріпленого кореневого сертифікату Intel SGX Root CA, порівнюючи його зі списками відкликаних сертифікатів Intel та підписаними даними платформи Intel, і відхиляє машини, які можна налагоджувати або мігрувати.

| Створення звіту | Що він показує |
| --- | --- |
| `tdx_binding` | Атестація охоплює підписану заяву збирача та випадкове значення цього запиту |
| `tdx_quote` | Intel гарантує достовірність сертифікації; вона вважається успішною лише тоді, коли Intel оцінює платформу як актуальну |
| `tdx_compose_hash` | RTMR3, відтворений із журналу подій dstack, вимірює кількість повідомлень, складених у додатку, про які повідомляє колектор |
| `tdx_compose` | Цей код байт за байтом збігається з тим, що генерує розгорнутий комміт: вихідні файли прив’язані за хешем, обидва зображення — за дайджестом, іншого коду немає |
| `tdx_identity` | Атестація надходить від розгорнутого додатка та екземпляра, з використанням ключів із KMS Phala та зашифрованого диска |
| `tdx_os` | При `--tdx-measurements`, MRTD та RTMR0-2 дорівнюють значенням, обчисленим на основі образу ОС dstack (`dstack-mr measure --json`) |

Кожен запуск колектора, зафіксований у журналі, має таке підтвердження, тому `verify --evidence` перевіряє кожен запуск. Список версій додатка від Phala слугує журналом постачальника: якщо код змінився після розгортання, звіт не проходить.

У панелі виберіть **«Конфіденційна віртуальна машина · Phala Cloud»** у розділі **«Додаткові функції»** → **«Сервер 24/7»** та вставте ключ API Phala Cloud; швидкий тунель працює так само, як на Hetzner. З командного рядка:

```
python -m tgwitness.cloud deploy --provider phala --name case-1 --server-type tdx.small \
    --ref v0.8.0 --repository https://github.com/phishdestroy/TgWitness --quick-tunnel \
    --provider-token-file phala-key.txt
python -m tgwitness.cloud verify --record deployments/case-1/deployment.json \
    --provider-token-file phala-key.txt --cloud-init deployments/case-1/docker-compose.yaml \
    --source CHECKOUT_OF_COMMIT --tdx-measurements dstack-mr.json
```

`--tdx-collateral` зчитує сертифікати та списки відкликаних сертифікатів Intel із файлу, а не завантажує їх із сайту Intel. Шлюз DNS тут недоступний: у Phala немає брандмауера провайдера для вихідного трафіку.

Атестація не може виключити наявність вразливості в модулі TDX або мікрокоді Intel, а також фізичного доступу до шини пам’яті. Той, хто контролює додаток в обліковому записі Phala, може розгорнути інший компоуз; він з’являється як нова версія з новим хешем компоузу. Хост контролює джерело часу машини та мережу.

## Перш ніж почати

1. Зона Cloudflare, її ідентифікатор облікового запису та токен API з правами **«Cloudflare Tunnel Edit**», **«Zone Read»** і **«DNS Edit»**, наданий за допомогою `--cloudflare-token-file` або `CLOUDFLARE_API_TOKEN`. Для верифікатора: **«Cloudflare Tunnel Read**», **«DNS Read»** та, для журналу аудиту, **«Account Settings Read**». Без домену [швидкий тунель](https://phishdestroy.github.io/TgWitness/uk/docs/reference/high-assurance/#quick-tunnel-without-a-domain) не потребує нічого з цього.
2. Повноваження провайдера з правом запису до виділеного проєкту; `lock` використовує те саме:

   - Hetzner: токен API з правами на читання та запис;
   - DigitalOcean: особистий токен доступу з правом запису;
   - Linode: особистий токен доступу з `linodes`, `firewall` та `events` областями доступу для читання/запису;
   - Vultr: ключ API виділеного облікового запису або субоблікового запису;
   - AWS: дозволено використовувати облікові дані IAM `ec2:DescribeVpcs`, `ec2:DescribeImages`, `ec2:CreateSecurityGroup`, `ec2:AuthorizeSecurityGroupIngress`, `ec2:RunInstances`, `ec2:CreateTags`, `ec2:DescribeInstances`, `ec2:DescribeSecurityGroupRules` та `ec2:RevokeSecurityGroupIngress`.
3. Коміт, який потрібно виконати. Тег релізу одноразово розпізнається як відповідний коміт за допомогою `git ls-remote`; сервер завжди отримує лише 40-символьний коміт.

## З панелі

На вашому комп’ютері через меню **«Додаткові» → «Сервер 24/7»** запускається те саме `deploy` для Hetzner у три кроки: виберіть Європу або США, вставте токен Hetzner (читання та запис), а потім перегляньте тип сервера, щомісячну вартість, адресу та версію, які панель знайшла за цим токеном. Нічого не створюється, доки ви не підтвердите. Панель показує кожен крок у вигляді `deploy` з’являється у звіті, а потім — адресу, токен панелі та відбиток ключа підпису. Без домену сервер отримує [швидкий тунель](https://phishdestroy.github.io/TgWitness/uk/docs/reference/high-assurance/#quick-tunnel-without-a-domain) ; **у розділі «Ваші сервери» → «Знайти поточну адресу»** його можна перевірити знову після перезапуску. Щоб отримати фіксовану адресу під власним доменом, відкрийте **«Додатково» · «Ваш власний домен»** і додайте токен Cloudflare (підготовлене посилання вибирає «Зона читання», «Редагування DNS» та «Редагування тунелю Cloudflare»).

Токени передаються з кожною запитом із вкладки браузера до TgWitness на тому самому комп’ютері і ніде не записуються; запис розгортання, відредагований файл cloud-init, токен панелі та, для швидкого тунелю, ключ адреси зберігаються в `deployments/NAME` всередині каталогу даних. Панель надає доступ до цього лише головному адміністратору через пряме з’єднання з петлею зворотного зв’язку (`127.0.0.1`, без проксі-серверів чи заголовків тунелю); панель, до якої звертаються через мережу, замість цього показує команди . Версія за замовчуванням відповідає тегу релізу панелі, що працює, який визначається через API GitHub. Місцезнаходження, тип сервера та ціна надходять з API Hetzner: `cpx22` якщо така пропонуються, інакше — найдешевший тип x86 з щонайменше 2 ГБ пам’яті.

## Швидкий тунель без домену

`--quick-tunnel` замінює `--zone`, `--cloudflare-account` та `--panel-host`; не використовується жоден обліковий запис або токен Cloudflare:

```
python -m tgwitness.cloud deploy --provider hetzner --name case-2026-11 --server-type cpx22 \
    --ref 0123456789abcdef0123456789abcdef01234567 --quick-tunnel --provider-token-file hetzner.token
```

На сервері cloudflared відкриває [швидкий тунель](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) до панелі: випадкова `https://….trycloudflare.com` адреса, яка змінюється щоразу, коли cloudflared або сервер перезапускається. Невеликий сервіс на сервері публікує кожну адресу у випадковій темі ntfy.sh , підписану (HMAC-SHA256) ключем, який зберігається лише у каталозі розгортання (`address-key.txt`), і повторює це кожні три години, оскільки ntfy.sh зберігає публікації протягом 12. `deploy` та **«Знайти поточну адресу»** приймають лише підписані публікації, тому підроблена публікація не може перенаправити вас та ваш токен панелі на чужу адресу. Тема міститься у записі та опублікованому cloud-init: кожен, хто має доступ до них, може прочитати поточну адресу, яка все одно вимагає введення токена панелі. Сервер у жодному разі не відкриває вхідний порт.

Скільки це коштує: жоден обліковий запис Cloudflare не веде обліку швидкого тунелю, тому `verify` звіт про тунель, коннектор та перевірку DNS буде недоступним, і результат, у кращому випадку, `incomplete`; записи провайдера, брандмауер, підписана заява, вимірювання хосту та порівняння інсталяторів перевіряються як зазвичай. Для порівняння байтів з еталонним інсталятором потрібен розгорнутий комміт, який уже знає `--quick-tunnel`; витяг версії 0.7.0 створює інсталятор домену та повідомляє про різницю. Cloudflare не надає швидким тунелям гарантії безперебійної роботи, дозволяє 200 запитів у процесі обробки та не підтримує Server-Sent Events, тому оновлення панелі в режимі реального часу (версії після 0.7.0) можуть не надходити через тунель, і сторінку доведеться перезавантажити; ця частина ще не перевірялася. У випадку, коли система має працювати безперебійно, використовуйте власний домен.

## Розгортання

Спочатку перегляньте все, що буде надіслано. `plan` не надсилає запитів до провайдера чи Cloudflare:

```
python -m tgwitness.cloud plan --provider hetzner --name case-2026-11 --server-type cpx22 \
    --ref 0123456789abcdef0123456789abcdef01234567 --zone example.org \
    --cloudflare-account CLOUDFLARE_ACCOUNT_ID --panel-host case.example.org
```

Потім виконайте розгортання з тими самими параметрами та обліковими даними:

```
python -m tgwitness.cloud deploy --provider hetzner --name case-2026-11 --server-type cpx22 \
    --ref 0123456789abcdef0123456789abcdef01234567 --zone example.org \
    --cloudflare-account CLOUDFLARE_ACCOUNT_ID --panel-host case.example.org \
    --witness-host case-witness.example.org \
    --provider-token-file hetzner.token --cloudflare-token-file cloudflare.token
```

Типи серверів для початку: `cpx22` (Hetzner), `s-1vcpu-2gb` (DigitalOcean), `g6-standard-1` (Linode), `vc2-1c-2gb` (Vultr), `t3.small` (AWS). `--location` та `--image` за замовчуванням для кожного провайдера — Ubuntu 24.04 у європейському регіоні.

`--repository` приймає коміт з іншого репозиторію Git за протоколом https без вказівки облікових даних в URL (за замовчуванням `https://github.com/phishdestroy/TgWitness.git`). `deploy` також приймає `--out` для іншого каталогу розгортання (за замовчуванням `deployments/NAME`; каталог, у якому вже знаходиться розгортання, відхиляється) та `--wait`, час у хвилинах, протягом якого слід чекати на підписану заяву колектора: від 1 до 240, за замовчуванням 20, або 60 для `generic`.

Команда:

1. створює тунель Cloudflare, вхідний трафік якого перенаправляє ім’я хосту панелі на саму панель, а також, якщо вказано, ім’я хосту свідка на `/api/witness/head` і `/api/assurance` тільки;
2. створює проксі-записи CNAME для цих імен хостів, відхиляючи імена, які вже існують;
3. створює брандмауер-провайдер без правил вхідного трафіку та сервер за ним без SSH-ключа, без резервних копій, без консольного агента та з cloud-init, який маскує SSH, блокує root, встановлює `cloudflared`, завантажує саме цей комміт, перевіряє його та запускає TgWitness як захищену службу systemd;
4. очікує на підписану заяву колектора та перевіряє, чи вказано в ній цей сервер та хеш цього файлу cloud-init.

`deployments/case-2026-11/` Потім містить:

| Файл | Зміст | Поділитися? |
| --- | --- | --- |
| `deployment.json` | Ідентифікатори, хеші, здійснені виклики API (метод, шлях, статус) та перше підписане твердження | Так, за допомогою верифікатора |
| `cloud-init.redacted.yaml` | Точний код cloud-init, у якому два секретні параметри замінено на `REDACTED` | Так |
| `panel-token.txt` | Токен панелі | Ні |

Кореневий пароль провайдера, токен тунелю та токен панелі ніколи не записуються `deployment.json`. Опублікуйте відбиток колектора, наведений у кінці, через канал, яким ви не керуєте самостійно, наприклад, через канал свідків або у повідомленні одержувачу.

Увійдіть у Telegram за адресою `https://case.example.org` за допомогою токена панелі, як зазначено в [посібнику з налаштування облікового запису](https://phishdestroy.github.io/TgWitness/uk/docs/reference/accounts/). Дії панелі записуються у підписаному журналі; це не сесії SSH. [Свідок](https://phishdestroy.github.io/TgWitness/uk/docs/reference/witness/) може запитувати `https://case-witness.example.org`.

SSH відсутній: якщо запуск не вдається, колектор ніколи не відповідає. Видаліть сервер і розгорніть його знову або скористайтеся розгортанням для налагодження, щоб знайти причину.

### Секрети в даних користувача

Cloud-init містить два секретні ключі: токен панелі та токен тунелю Cloudflare. Ключ підпису серед них немає; він створюється на сервері. Hetzner, DigitalOcean та Linode не повертають дані користувачів через свої API. Vultr повертає їх будь-якому ключу, який може читати інстанцію, а EC2 — через `DescribeInstanceAttribute`. Для AWS надайте верифікатору лише три дії з таблиці, ніколи `ec2:Describe*`. Для Vultr припускайте, що ключ верифікатора може зчитувати обидва токенів. Токен тунелю дозволяє запустити другий коннектор: `verify` повідомляє про будь-який коннектор, що не знаходиться на сервері, і заяви колектора не можна підробити таким чином, оскільки кожна з них підписується новим викликом. З `--quick-tunnel` другим секретом є ключ адреси: хто б його не прочитав, може опублікувати фальшиву адресу, яку панель прийме.

У публічній заяві збирача не вказуються адреса сервера та джерела логінів; обидві ці інформації залишаються у підписаному журналі.

## Налагодження розгортання та блокування

`--debug-ssh-key KEY --debug-ssh-from 198.51.100.4` зберігає SSH для одного ключа з однієї адреси або невеликої мережі, максимум /24 для IPv4 або /48 для IPv6. `KEY` вже зареєстрований у провайдера: ім’я або ID SSH-ключа в проєкті Hetzner, ID або відбиток SSH-ключа в команді DigitalOcean, ім’я користувача Linode, SSH-ключі якого додано до профілю root, ID SSH-ключа в обліковому записі Vultr або ім’я пари ключів EC2 у регіоні. Ці параметри не застосовуються до `generic`. Таке розгортання реєструється як `debug` і **ніколи не** позначається як «високого рівня безпеки». Коли ви закінчите, виконайте `sudo tgwitness-lock` як останню команду останнього сеансу SSH, а потім:

```
python -m tgwitness.cloud lock --record deployments/case-2026-11/deployment.json --provider-token-file hetzner.token
```

Брандмауер втрачає всі правила вхідного трафіку. Звіти показують, коли SSH було дозволено, а коли його було закрито; це вікно залишається видимим.

## Видалити розгортання

`destroy` Видаляє сервер та його брандмауер, знайдені за міткою розгортання, щоб розгортання, яке завершилося невдачею на півдорозі, також було видалено, а потім — записи DNS, що вказують на його тунель, та сам тунель. Журнал сервера та ключ підпису видаляються разом із ним: спочатку експортуйте докази. Запис залишається, позначений `removed`, із API-викликами видалення.

```
python -m tgwitness.cloud destroy --record deployments/case-2026-11/deployment.json --confirm case-2026-11 \
    --provider-token-file hetzner.token --cloudflare-token-file cloudflare.token
```

Видалення через API реалізовано для Hetzner. Для інших провайдерів `destroy` перед видаленням будь-чого зупиняється та вказує мітку для видалення в консолі провайдера. Ручно встановлений сервер (`generic`) втрачає лише свій тунель та записи DNS. Швидке розгортання тунелю не потребує токену Cloudflare: його тунель закінчується на сервері, а публікації з ntfy.sh втрачають чинність протягом 12 годин.

## Будь-який сервер (самосертифікований)

`--provider generic` призначений для сервера, придбаного або встановленого вручну. `deploy` створює тунель та DNS, записує `install.sh` (приватний) та `install.redacted.sh` (для публікації), а потім очікує. Скопіюйте `install.sh` на щойно встановлений сервер Ubuntu 24.04 і запустіть його там:

```
sudo bash install.sh
```

Він фіксує стан хоста в тому вигляді, яким він був (логіни, акаунти, `authorized_keys`, сокети прослуховування, сервіси, заплановані завдання, пакети), встановлює коміт, увімкне брандмауер хосту, видалить себе, замаскує SSH та завершить сесію. Звіт щодо такого сервера є, у кращому разі, **САМОПІДТВЕРДЖЕНИМ**: той, хто запустив інсталятор, мав права root до цього, і жодних записів про провайдера немає у розпорядженні верифікатора. Це все ж краще, ніж нез’ясований сервер: інвентар, хеш інсталятора та кожен наступний вхід підписані.

## Перевірити

Верифікатору потрібні `deployment.json`опублікований інсталятор, облікові дані лише для читання та, в ідеалі, копію коміту й доказ ZIP:

```
git clone -c core.autocrlf=false https://github.com/phishdestroy/TgWitness.git checkout
git -C checkout checkout 0123456789abcdef0123456789abcdef01234567
python -m tgwitness.cloud verify --record deployment.json \
    --provider-token-file read-only.token --cloudflare-token-file cloudflare-read.token \
    --fingerprint COLLECTOR_FINGERPRINT --cloud-init cloud-init.redacted.yaml \
    --source checkout --evidence tgwitness-evidence.zip --report report.md
```

Усі дані про провайдера та параметри Cloudflare запитуються верифікатором у цей момент; запис надає лише ідентифікатори, щодо яких слід зробити запит. Код виходу дорівнює 0 для **PASS**, 1 для **FAIL** та 2 для **REVIEW**, **INCOMPLETE** або **SELF-ATTESTED**. `--fingerprint` повинен надходити з незалежного каналу; без нього ключ порівнюється лише із записом оператора. `python verify.py` все одно перевіряє самі докази ZIP, як описано в розділі [«Докази](https://phishdestroy.github.io/TgWitness/uk/docs/reference/evidence/)».

Дії провайдера класифікуються: створення та запуск протягом 30 хвилин після створення проходять перевірку; консоль, відновлення, скидання пароля, перебудова, ISO, образи, знімки, резервні копії, Systems Manager, EC2 Instance Connect та відкриття брандмауера — не проходять перевірку; дії з живленням та все непередбачуване позначаються для перевірки. Невідома дія ніколи не проходить непоміченою.

## Звіт про передачу доказів

`--report report.md` створює звіт у форматі Markdown і `report.json` поруч із ним:

1. результат, відбиток ключа колектора, розгортання, провайдер, коміт, сервер, брандмауер, тунель;
2. кожен запит із зазначенням його статусу та джерела (API провайдера, API Cloudflare, звіт колектора, журнал доказів);
3. журнал провайдера з оцінкою кожної дії та, якщо провайдер це фіксує, виконавцем дії;
4. кінцеві точки Cloudflare, що містять з’єднання тунелю, конфігурацію та журнал аудиту;
5. підписана заява колекціонера;
6. що встановлює звіт, а що — ні;
7. команди для відтворення цього, а також SHA-256 кожного файлу, який було надано.

Передайте звіт, `report.json`, `deployment.json`, опублікований інсталятор та докази ZIP. Складіть звіт якомога раніше: журнали провайдерів зберігаються протягом обмеженого періоду.

## Cloudflare як зовнішній свідок

Усе це є необов’язковим. Без облікового запису Cloudflare сервер все одно працює, і два з цих варіантів працюють сьогодні:

| Що | Що він показує | У TgWitness |
| --- | --- | --- |
| Швидкий тунель або тунель вашого домену | До панелі можна отримати доступ лише через тунель | Майстер налаштування сервера, див. вище |
| ретранслятор drand `drand.cloudflare.com` | записи після раунду drand є новішими за нього: щоденник велося по ходу подій | режим доказів, **більше свідків**, без облікового запису ([формат](https://phishdestroy.github.io/TgWitness/uk/docs/reference/evidence/#optional-records-in-evidence-mode-drand-and-telegram-devices)) |
| Повідомлення про стан тунелю | коли тунель не працював, електронною поштою або через веб-хук від Cloudflare | Налаштуйте їх у панелі управління Cloudflare |
| DNS-шлюз (`--gateway-dns`або **Cloudflare Gateway DNS** у майстрі) | кожен домен, який сервер перевіряв, відповідь на який надавала Cloudflare через TLS; брандмауер Hetzner не дозволяє DNS-запитам досягати нічого іншого; чи може політика шлюзу переписати відповіді | Hetzner, безкоштовний тарифний план Zero Trust, без домену; `verify` перевіряє брандмауер, місцезнаходження, ведення журналів, політики, запити сервера та журнал аудиту; режим «evidence» копіює журнал у щоденник |
| Шлюз із клієнтом Cloudflare One на сервері — вихідний брандмауер, що пропускає лише трафік через Cloudflare | кожен з’єднання, встановлене сервером, а не лише DNS | ще не створено |
| Доступ перед панеллю | хто та коли увійшов до панелі | не реалізовано: потрібно мати власний домен |
| Реєстрація SSH-команд | кожна команда в сеансі налагодження | ще не створено |

Logpush, який зберігає власну копію Cloudflare в R2, є функцією для корпоративних клієнтів: у рамках безкоштовного тарифного плану Cloudflare відповідає `logpush is not enabled for this account`. Журнал шлюзу зберігається там 24 години, тому режим доказів копіює його в підписаний журнал (**журнал Cloudflare Gateway із DNS-запитами цього сервера** — токен лише для читання з доступом «Account Analytics Read»).

Без плану «Zero Trust» обліковий запис має одне DNS-розташування. Коли Cloudflare відхиляє інше, сервер використовує існуюче, а його запити розрізняються за адресою; цей фільтр також потребує доступу до персональних даних за принципом «Zero Trust», і `destroy` залишає спільне розташування. Один запит до журналу охоплює не більше трьох годин, тому копіювання та `verify` читання даних за день у тригодинних вікнах.

DNS-шлюз охоплює системний резолвер. DNS через HTTPS на порту 443 до іншого резолвера, а також з’єднання з адресами, які ніде не шукаються (наприклад, у дата-центрах Telegram), не фіксуються у його журналі.

Cloudflare не має доступу до шифрованих даних Telegram, інших пристроїв, пов’язаних з обліковим записом Telegram (список пристроїв у режимі «evidence mode» фіксує їх з боку Telegram) або гіпервізора провайдера.

1 листопада 2026 року Gateway DNS працював із реальним хмарним сервісом Hetzner та безкоштовним обліковим записом Cloudflare: Hetzner прийняв правила вихідного трафіку, на сервері було встановлено версію v0.7.0, і кожен запит проходив через Gateway за протоколом TLS, швидкий тунель працював через цей брандмауер, і `verify` прочитав 19 імен сервера з Cloudflare (дзеркала Ubuntu та Hetzner, GitHub, PyPI, NTP, тунель, ntfy.sh). Панель скопіювала 36 запитів у восьми вікнах до журналу та `verify.py` узагальнила їх без пропусків; `destroy` вилучила сервер і брандмауер та покинула спільне приміщення.

## Що це не встановлює

- Провайдер та його персонал контролюють гіпервізор, диски та мережу.
- Показники хосту самозвітуються збирачем даних.
- Раніше вміст правил брандмауера зберігається не в усіх журналах провайдерів; лише Linode зберігає версії правил.
- Це не містить нової інформації щодо автентичності повідомлень; див. розділ [«Докази](https://phishdestroy.github.io/TgWitness/uk/docs/reference/evidence/)».

## Перевірено тут

Логіка розгортання, блокування та верифікації перевіряється за допомогою автоматизованих тестів на основі імітованих API-інтерфейсів Hetzner, DigitalOcean, Linode, Vultr, EC2/CloudTrail та Cloudflare, створених на основі їхніх опублікованих довідників API, а також підписання запитів AWS — на основі опублікованих AWS прикладів. `tools/check_cloud_wizard.py` запускає майстер налаштування сервера панелі таким самим чином — із доменом та за допомогою швидкого тунелю. `tools/check_tdx.py` перевіряє справжні атестації Intel TDX з dcap-qvl та dstack аж до кореневого сертифіката Intel (джерела в [tools/tdx/README.md](https://github.com/phishdestroy/TgWitness/blob/main/tools/tdx/README.md)); `tools/check_phala.py`запускає команди розгортання, перевірки, журналу, знищення та майстра панелі на імітованому хмарному середовищі Phala Cloud, сертифікати якого походять із підробленої системи PKI, схожої на систему Intel. Шлях Phala ще не було випробувано на самому хмарному середовищі Phala Cloud.

1 листопада 2026 року швидкий тунельний маршрут працював через справжню **хмару Hetzner** (Нюрнберг, `cpx22`, TgWitness v0.7.0), справжнього ntfy.sh та GitHub, як з панелі управління, так і з коду:

- перевірка ціни, потім створення за допомогою кнопок на панелі: сервер запускається через 13 секунд, підписана заява з відповідними хешами екземпляра та інсталятора — приблизно через дві хвилини;
- власна панель сервера, що відкривається за адресою trycloudflare.com і приймає токен панелі; без токена вона видає код 401;
- після перезавантаження через API Hetzner сервер опублікував нову підписану адресу; **знайшов поточну адресу**, стара адреса перестала відповідати, ключ підпису залишився незмінним; непідписаний допис у темі ntfy.sh було проігноровано;
- `verify` щодо API Hetzner: сервер, брандмауер без правил вхідного трафіку, заява, прив’язка, вимірювання хосту, завантаження та хеш вихідного коду з гілки v0.7.0 пройшли перевірку; перевірки Cloudflare були недоступні, як описано вище; інсталятор відрізнявся від того, що використовується для збірки v0.7.0, і повністю збігався байт за байтом із тим, що використовується для збірки коду цієї версії;
- Видалення з панелі призвело до видалення саме того сервера та брандмауера, які були позначені під час розгортання; інші сервери та брандмауери в тому самому проєкті залишилися недоторканими.

Ще не тестувалося на реальних акаунтах: розгортання під вашим власним доменом (тунель Cloudflare та DNS), інші провайдери, розгортання для налагодження та `lock`, обліковий запис Telegram на такому сервері, а також оперативні оновлення пізніших версій через швидкий тунель. Перевірте перше розгортання на кожному провайдері за допомогою `plan`, розгортання для налагодження та `verify` перш ніж покладатися на нього під час роботи над справою.
