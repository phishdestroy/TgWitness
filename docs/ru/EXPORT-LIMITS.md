# Режим экспорта и ограничения в Telegram

Проверено 6 ноября 2026 года по UTC. Здесь сравниваются пути реализации, а не заявленная
пропускная способность. Telegram устанавливает свои квоты в зависимости от запроса и состояния учетной записи; в документации Telethon по
ошибкам ](https://docs.telethon.dev/en/stable/concepts/errors.html#avoiding-limits)
не указана универсальная частота запросов.

<a id="different-workloads-need-separate-measurements"></a>
## Для разных рабочих нагрузок требуются отдельные измерения

Определение тысяч ранее неизвестных имен пользователей отличается от чтения
тысяч страниц из одного известного чата. Необходимо отдельно измерять `contacts.resolveUsername`,
`messages.getHistory`, запросы участников и инициализацию Takeout.
Хэши доступа принадлежат учетной записи, которая их получила. Сохраненный участник может сократить
количество повторных определений, но другая учетная запись должна получить собственную информацию о доступе.
Имена пользователей могут переназначаться, поэтому записи идентифицируют учётные записи по числовому идентификатору.

Реализация Telethon [`get_entity`](https://github.com/LonamiWebs/Telethon/blob/v1/telethon/client/users.py)
явно предупреждает о повторном определении имени пользователя (примерно 50 имен пользователей за
короткий период, согласно данным наблюдений). Это не является официально объявленной почасовой квотой. Вызов
`get_entity(username)`
вызывает новый поиск; `get_input_entity`
может использовать существующий
локальный кэш учетной записи. При первом проходе по неизвестным именам пользователей по-прежнему требуется их определение.

Takeout использует [API экспорта](https://core.telegram.org/api/takeout) Telegram с
явно указанными флагами области действия и оболоченными запросами. Это может повлечь за собой задержку в связи с необходимостью утверждения.
Это не является исключением из всех ограничений и не предоставляет доступ к скрытым участникам.
Telegram принимает решение о праве на использование Takeout отдельно от защиты от пересылки. JSON —
это формат вывода; само по себе написание JSON не ускоряет получение данных через API.

наборы тестов из исходного кода или реальные измерения в Telegram. Варианты на Go и TypeScript
были проверены, но не запущены.

на рабочем столе также анализирует FloodWait и планирует обработку затронутого запроса по истечении указанного
количества секунд (плюс небольшой запас времени). Официальный экспорт не означает отсутствие ожидания.

<a id="tgwitness-behavior-and-measured-limits"></a>
## Поведение TgWitness и измеренные пределы

[Экспорт учетной записи](../ACCOUNT-EXPORT.md) поддерживает Takeout и надежные квитанции страниц.
[Экспорт распределенного чата](../DISTRIBUTED-EXPORT.md#history-acquisition) теперь имеет
опциональный путь истории Takeout для публичных каналов и супергрупп. Новые планы для
любого из этих механизмов передачи позволяют расширить блоки из 2 000 идентификаторов до 100 000 числовых идентификаторов в разреженных
историях без исключения каких-либо идентификаторов. Существующие подписанные планы сохраняют исходные
размеры блоков. Механизмы передачи и генерации сопровождают подписанные квитанции.
Этот путь прошел автономные тесты протокола и восстановления, а также проверки в браузере; устойчивая
пропускная способность Takeout не измерялась. Наблюдения в обычном режиме зафиксированы
в [квалификации с 50 источниками](../EXPORT-BENCHMARK-2026-11-06.md). Новые распределённые планы сохраняют подписанные
контрольные точки, содержащие до 100 декодированных сообщений внутри блока, с восстановлением, ограниченным наблюдателем,
и автономной верификацией. Эти локальные пакеты отличаются от квитанций на странице API
экспорта учётной записи; более старые распределённые планы сохраняют восстановление только по блокам.

Общий клиент выполняет RPC-вызовы одной учетной записи по одному в каждом из четырёх потоков
(оперативные обновления, запросы оператора, фоновые проверки, история и экспорт). Медленный
ответ не блокирует другие потоки; по-прежнему действуют общие ограничения по скорости и сроки выполнения методов.
Наряду с ними для каждой учетной записи выполняется до трёх страниц истории (`messages.getHistory`) и до
трёх операций чтения файлов (`upload.getFile`, `upload.getCdnFile`). Клиент сохраняет полный срок выполнения, запрошенный сервером,
для ограниченного метода до следующего его вызова, в том числе после повторного подключения. Теперь он записывает метод,
обёртки, продолжительность ожидания, фактический срок выполнения и количество вызовов клиента для каждого метода в
`telegram.backoff`. В деталях соединения отображаются метод и крайний срок в режиме паузы.
Аргументы и текст исключений опускаются. Счётчики запускаются с экземпляром клиента;
они не являются попытками на уровне канала передачи данных и не раскрывают повторные попытки внутри Telethon.
Существующий тип события и формат экспорта с указанием знака остаются без изменений.

`AccountPacer` охватывает историю, диалоги, журналы администрирования, повторную проверку идентификаторов сообщений и
страницы участников, включая запросы, обработанные с помощью Takeout. Изначально интервал составляет одну секунду,
после двадцати успешных массовых вызовов он сокращается до минимального значения в полсекунды,
а после FloodWait увеличивается, при этом максимальное значение ограничено десятью секундами. Это локальные
значения политики, а не квоты Telegram. Обученная задержка сохраняется для каждого аккаунта;
таймер следующей отправки принадлежит экземпляру клиента. Полные серверные ограничения по времени остаются
авторитетными, включая FLOOD_PREMIUM_WAIT.

Предыдущий анализ исходного кода касался ветви, предшествующей интеграции: её последовательная очередь
сама по себе не обеспечивала регулирование темпа. Текущий механизм массового регулирования темпа по-прежнему не охватывает обнаружение неизвестных
имен пользователей и не выделяет отдельных бюджетов для обычной истории и
истории Takeout. Существующий механизм защиты профиля не допускает добавления одной и той же учетной записи Telegram
в другое рабочее пространство; этот механизм защиты также был задействован и не должен дублироваться.
Он не координирует независимые установки на отдельных серверах.

Пилотный тест с 50 источниками выявил 31-секундный всплеск FloodWait `channels.getMessages`
при повторной проверке отсутствующих идентификаторов. Ранее эти вызовы использовали общий интервал ожидания сервера
учётной записи, но обходили локальный интервал массовых запросов. Теперь повторные проверки идентификаторов и страницы участников
также используют этот интервал, что устраняет данный нерегулярный всплеск. В ходе завершённой
квалификации было зафиксировано 690 событий отката в пилотных тестах и прерванных прогонах с
запрошенным временем ожидания от 3 до 31 секунды. Ожидания вызывались как историей, так и
повторной проверкой идентификаторов; в квалификации указаны версии источников и охват счетчиков.

Следующее изменение частоты стимуляции должно:

1. Вести по каждой учетной записи свой планировщик с отдельными бюджетами для обнаружения, обычной
   истории, истории Takeout и участников. Разрешать обертки Takeout до
   классификации. Сохранить существующий полный период ожидания для учетной записи при FloodWait.
2. Сохраняйте состояние планирования при переходе между чатами и при повторном создании клиента. При работе на нескольких серверах
   назначайте аккаунт одному активному рабочему процессу или координируйте его аренду и срок действия;
   дополнительная авторизация того же аккаунта не является независимой ресурсной единицей.
3. Уменьшайте интенсивность затронутой рабочей нагрузки после ожидания, обеспечивая ограниченное и постепенное
   восстановление. Откладывайте длительные или повторяющиеся ожидания с помощью устойчивого прогресса. Не повторяйте попытку
   неизменённой рабочей нагрузки сразу же с прежней скоростью после истечения срока.
4. Повторно используйте локальных для аккаунта пиров и проверенные контрольные точки страниц. Разграничивайте определение
   известного идентификатора и определение текущего владельца имени пользователя. Избегайте повторных
   полных поисков по профилю, когда достаточно кэшированного входного узла.
5. Раскрывайте время, затрачиваемое на получение, регулирование скорости, ожидание Telegram и фиксацию данных.
   Калибруйте скорости с помощью ограниченных активных пакетов; не объявляйте неизмеренные квоты.

Эти расширения планировщика массовых операций носят рекомендательный характер и не реализованы в системе. Благодаря использованию
стойких контрольных точек повторное получение фиксированных страниц после прерывания уже не требуется. Перекрытие
сетевых операций чтения и ограниченной локальной обработки может повысить пропускную способность без
увеличения параллелизма запросов; данное перекрытие также пока не реализовано.

Пилотный проект с ограниченной историей [одного/двух аккаунтов](../DISTRIBUTED-EXPORT.md#performance-measurements)
не позволяет оценить устойчивость обнаружения. Отдельный реальный мониторинг 4 408 публичных
ссылок с трехсекундными паузами между операциями верхнего уровня был приостановлен после получения 388
результатов: 380 доступных источников и 8 недоступных. Их зарегистрированное
количество сообщений о доступности составило 34 409 815; их последние идентификаторы составили 169 711 686.
Ни одна из этих сумм не подтверждает удаления или полноту необработанного списка.
Оба рабочих процесса получили FloodWait (зарегистрированные задержки составили 9 803 и 70 390 секунд).
В старом журнале не указан метод, приведший к сбою: приписывать эти задержки разрешению
имен пользователей или истории было бы спекуляцией. Оба клиента отключились; сохраненные
результаты остаются возобновляемыми.

Теперь модуль управления локальным инвентарем прекращает планирование при первом обнаружении FloodWait
(у другой учетной записи, возможно, уже находится запрос в процессе обработки), сохраняет полный крайний срок
и отклоняет новый пилот, если у любой из аккаунтов все еще сохраняется ожидание. Он ограничивает
пилотную версию до 20 новых источников на одну учетную запись и разделяет операции по разрешению источников интервалом не
меньше десяти секунд, при этом между операциями верхнего уровня должно быть не менее трёх секунд.
Это консервативные настройки локального пилота, а не квоты Telegram или
значения по умолчанию для производственной среды. Модуль находится вне репозитория; эти настройки не были проверены в ходе
нового рабочего запуска. Существующие подписанные квитанции повторно используются без повторного извлечения их источников.

Перед масштабированием измеряйте обнаружение, историю и привлечение участников независимо
на ограниченных партиях после истечения всех периодов ожидания. Составляйте отчеты о зафиксированных сообщениях, прошедшем времени
с учетом ожиданий, запросах по методам, недоступных источниках и частичном членстве.
Для разреженных числовых диапазонов идентификаторов сравнивайте историю на основе курсоров с фрагментацией с фиксированными идентификаторами:
пустые фрагменты могут добавлять запросы, не генерируя сообщений. Проводите это сравнение
отдельно от анализа удалений. Масштабирование до 10, 50 или 100 аккаунтов измеряется
отдельно от текущего пилотного проекта.

<a id="counts-and-id-boundaries"></a>
## Счетчики и границы идентификаторов

Не смешивайте подсчёты, предоставленные сервером, количество обнаруженных уникальных сообщений и диапазоны числовых идентификаторов.
Ответ Telegram с историей канала ](https://core.telegram.org/constructor/messages.channelMessages)
может содержать отметки результатов `inexact`. Подсчёт для выбранного диапазона дат основан на
количестве прочитанных в этом диапазоне сообщений, а не на смещении пагинации. В проанализированном коде tg-chat-dump `id_bounds` сужает диапазон дат,
но сохраняет общее количество из первоначального ответа с историей. История Telethon
`get_messages(limit=0)` получает общее количество с помощью необработанного запроса с `limit=1`.

Показатели совпадений отражают историю, видимую на момент наблюдения.
Если идентификаторы с 6 по 10 исчезнут до первого наблюдения, видимая история
идентификаторов с 1 по 5 может иметь количество на сервере, количество полученных данных и диапазон идентификаторов, равные пяти.
Различные итоговые значения аккаунтов также требуют определения времени измерения, фильтров, точности отклика
и условий доступа, прежде чем можно будет установить разницу в видимости.

Зафиксируйте привязку учетной записи, чат, время наблюдения, канал передачи данных и точную область
выбора с указанием любого сравнения подсчётов. Подсчитывайте наблюдаемые служебные сообщения отдельно;
вычитание расчётного соотношения служебных сообщений не может дать точного числа
удалений. Описывайте необъяснимые отсутствующие идентификаторы как отсутствие в пределах измеряемой области.
Подпись сборщика защищает записанные данные наблюдения от последующих изменений;
сохраняйте контекст запроса и интервал сбора данных наряду с подсчётом.
