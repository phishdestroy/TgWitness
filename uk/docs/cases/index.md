# Telegram · Проведіть розслідування у всіх чатах

Canonical page: https://phishdestroy.github.io/TgWitness/uk/docs/cases/

Ціла справа по каналах, групах, особистих чатах і ботах: зібрати, пов'язати, відновити хронологію, передати.

Один вигаданий інцидент від початку до кінця. Збір, пошук і профілі людей знаходять записи, [Case Board](https://phishdestroy.github.io/TgWitness/uk/docs/case-board/) їх упорядковує, [Report studio](https://phishdestroy.github.io/TgWitness/uk/docs/reports/) оформлює.

РЕАЛЬНИЙ ВИПАДОК / ЗМІНА АДРЕСАТА ПЛАТЕЖУ

### Один інцидент. Чотири розмови. Слід, який потрібно відтворити.

Пост у каналі веде на бота. У групі обговорюють нове платіжне посилання, бот його показує. Пост редагують, в особистому чаті посилання повторюють, повідомлення в групі зникає.

Хто опублікував кожну версію?Де з’явилося це посилання?Який файл було збережено?Що змінилося і коли?

Завантаження історії, ШІ, MCP, OCR і вебхуки: [Робота з архівом](https://phishdestroy.github.io/TgWitness/uk/docs/archive/).

## 1. Забезпечити охоплення всього облікового запису

Охоплення всього акаунта — лише на окремому акаунті. Основному — вибрані чати або папка.

1. [Підключіть акаунт](https://phishdestroy.github.io/TgWitness/uk/docs/accounts/) в окремому просторі. Запишіть номер справи, ID акаунта, простір і відбиток ключа.
2. **Джерела → Охоплення спостереження → Режим розслідування**: **Весь акаунт**, усі чотири типи джерел, **Власні дії**. Для кожного нового чату зберігаються профіль і останні **200 видимих повідомлень**. **Зберегти охоплення** й підтвердьте.
3. **Завантажити чати** й порівняйте зі списком чатів акаунта. Ліміт — 1000 діалогів (до 20 000 у **Параметри → Чати зі списку акаунта**); чати понад ліміт з'являться, коли стануть активними.
4. **Налаштування запису** → **Уся видима активність**, перевірте ліміти вкладень і місце на диску. Запустіть і перевірте на повідомленні, правці й видаленні.

«Весь акаунт» — це всі чати, які цей акаунт може відкрити, за винятком виключень. Секретних чатів немає. Нові чати додаються в міру появи, стара історія сама не завантажується.

## 2. Збирання історії та збереження файлів

Створіть колекцію в Case Board і позначте важливе. Ведіть реєстр джерел: ID чату, назва, акаунт, роль, початок живого збору, результат історії, результат медіа, прогалини.

| Потрібно | Дії на панелі | Що він пропонує |
| --- | --- | --- |
| Історія у всіх увімкнених чатах | Джерела → Завантажити повну історію | Доступні попередні повідомлення потрапляють до журналу робочого простору з можливістю призупинення/відновлення та підписаним звітом про хід роботи. [Посібник з історії](https://phishdestroy.github.io/TgWitness/uk/docs/reference/history/). |
| Існуючий контекст чату в журналі | Джерела → Налаштування запису → Знімок історії | Нещодавні повідомлення як підписані записи. Типово 500, до 10 000 у **Параметри → Найбільший знімок історії**. |
| Повна історія одного чату, яка наразі доступна для перегляду | Експорт повного чату → Експорт повного чату або Чати → Експорт чату | Окремий підписаний архів із `chat.json` і `chat.html`, по одному на чат. |
| Контекст появи нового чату | Сфера спостереження → Коли з’являється новий чат або бот | Його профіль і до 1000 останніх повідомлень (200 у режимі розслідування). На наявні чати не поширюється. |
| Обсяг вкладення в байтах | Завантаження видимих вкладень + обмеження за типами | Шукайте `media.saved` із SHA-256 і розміром. «У черзі», «пропущено» чи «помилка» — значить, не збережено. |

Експорт чату не потрапляє в журнал і профілі людей. Щоб шукати по старій історії всередині TgWitness, використовуйте **Завантажити всю історію** або знімки.

Тут: канал, група, чат із ботом і особистий чат, плюс файл рахунку та його хеш. Видалене до початку збору вже не повернути.

## 3. Відстежуйте розвиток розмови та свої власні дії

Хай працює. Позначте гарячі чати зірочкою як пріоритетні, налаштуйте перевірки в **Налаштування запису → Повторна перевірка** й стежте за `recheck.completed`, FloodWait і результатами медіа.

**Чати → Профіль → Зберегти профіль зараз** зберігає опис чату, команди бота й інші метадані.

**Підписка на бота або прийняття запрошення в рамках справи**

1. **Чати → Відкрити посилання Telegram**, спершу збережіть прев'ю. Посилання й прев'ю стають підписаними записами.
2. Якщо потрібно, **Приєднатися / відкрити й спостерігати** вступає в чат або запускає бота з його стартовим параметром.
3. Щоб задокументувати дію, відповідайте або натисніть **Натиснути кнопку** в панелі. Отримаєте `interaction.requested` і `interaction.result` з відповіддю бота.

Це справжні дії. Натискання кнопок в іншому застосунку не видно, лише відповідь бота. Без вебзастосунків, платежів і телефону/геолокації.

## 4. Відстежуйте користувачів, посилання та файли у чатах

1. **Журнал**, **Усі джерела**, шукайте фразу, домен чи юзернейм. Відкривайте результати й надсилайте їх **На дошку**.
2. **Чати → Люди → Увімкнути профілі**, оберіть людину: історія імен, відповіді, активність, **Також у…**, посилання, гаманці, телефони. Відкривайте процитовані записи.
3. Простежте той самий числовий ID користувача в інших чатах. Збіг імені, гаманця чи аватара — зачіпка, а не доказ.
4. Порівняйте хеші файлів. Однаковий SHA-256 = однакові байти. Хто їх надіслав — окреме питання.

Чотири чати містять різні спостереження. Слідкуйте за вихідними записами для кожного з’єднання; допис у каналі не має вказаного відправника.

Числові ідентифікатори та посилання на записи вигадані для цього покрокового керівництва. Ця пояснювальна схема показує, як пов’язати результати пошуку, профілі та перевірені записи; «Case Board» зберігає відповідні картки та посилання на джерела.

| Зв’язок | Додаткові спостереження | Висновок: залишити |
| --- | --- | --- |
| Той самий акаунт у Telegram | Ідентифікатор користувача 71001 у групі № 146 та приватному чаті № 205 | Той самий ID відправника в обох чатах. Хто це в реальному житті — інше питання. |
| Повторне призначення | `pay.example.invalid/new` у #146, метадані кнопки #173, відредаговані дописи #188 та #205 | Те саме посилання в чотирьох місцях. Хто ним керує — потрібні інші джерела. |
| Кількість байтів у файлі | Ідентичні повні значення SHA-256 у завершених квитанціях про надсилання медіафайлів № 151 та № 209 | Обидва файли збігаються побайтно. |

Профілі охоплюють лише тих, хто щось написав у *цьому просторі*, це не список учасників. Кількість цитат на факт: **Параметри → Записів на факт**.

## 5. Відтворити послідовність та позначити пропуски

Версії в **Чатах**, потім **Журнал** з **Усі джерела** + **Правки**, **Видалення**, **Охоплення**. У хронологію ставте обидва часи: дату Telegram і момент спостереження.

1. 09:00 · #101**Збережений допис у каналі**

   Початкове призначення збережено.
2. 09:12 · #146 / #151**Група надає інше посилання**

   Користувач 71001 публікує його; завантаження вкладення завершено.
3. 09:16 · #173**Бот показує те саме місце призначення**

   Збережені метадані клавіатури містять посилання.
4. 09:20 · #188**Зміни в оголошеннях каналу**

   Зберігаються як оригінальні, так і відредаговані спостереження.
5. 09:24 · #205 / #209**У приватному повідомленні це повторюється**

   Збережене вкладення має той самий повний SHA-256, що й № 151.
6. 09:28 · #231**Надходить повідомлення про видалення групи**

   Попереднє зауваження залишається в силі: не вказується ані особа, яка здійснила видалення, ані точний час видалення.

Наведені приклади часу спостереження та посилання. Між цими записами містяться й інші записи журналу.

Порядок у журналі — це порядок надходження, а не обов'язково порядок подій. Тримайте окремо живі записи, знімки, відновлені повідомлення, видалення й «не знайдено під час перевірки» та позначайте кожну прогалину як невідому.

## 6. Розширити сферу застосування на інші облікові записи, що збирають дані

Один простір на акаунт, ті самі кроки. Запишіть роль і відбиток кожного. Номери повідомлень свої в кожного акаунта, тож завжди вказуйте простір і чат.

[Група акаунтів](https://phishdestroy.github.io/TgWitness/uk/docs/groups/) показує статус, ділиться налаштуваннями й експортує всіх разом — у кожного свій журнал і ключ. Спільну хронологію по акаунтах збирайте у своїх нотатках.

Довга справа? Додайте [незалежного свідка](https://phishdestroy.github.io/TgWitness/uk/docs/witness/) й перевірте, що насправді ловить кожен акаунт.

## 7. Надайте пакет матеріалів справи, який можна перевірити

Підписаний ZIP з кожного простору (завжди весь журнал, фільтри не важливі), плюс профілі людей, експорти чатів і файли.

```
CASE-001/                         # assembled by the analyst
  case-notes.md                   # question, findings, alternative explanations
  sources.csv                     # every chat, role, acquisition result and gap
  timeline.csv                    # account + chat + message + seq + both times
  workspace-A/
    evidence.zip                  # complete signed observation journal
    retained-checkpoint.json
    profiles-operations.json      # separately signed people profiles
    history-channel.zip           # signed current-history export
    history-group.zip
    verification.txt
  workspace-B/                    # separate journal and trusted fingerprint
  witness/                        # retained checks, journal and signed posts
  SHA256SUMS                      # hashes of the delivered files
```

Відбитки передавайте окремо. Перевіряйте все за його власним простором:

```
python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --checkpoint retained-checkpoint.json
python -m tgwitness.verify profiles-operations.json --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --evidence evidence.zip
python -m tgwitness.verify history-channel.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256
```

Зберігайте вивід верифікатора, оригінали, охоплення й запис про передачу разом із висновками. Оформіть усе в Report studio. Якщо отримувачу треба менше, зробіть [скорочену передачу](https://phishdestroy.github.io/TgWitness/uk/docs/handover/).
