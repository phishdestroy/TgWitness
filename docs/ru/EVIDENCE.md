# Формат доказательств v1

TgWitness сохраняет видимые для аккаунта наблюдения в Telegram в подписанном журнале. Получатели могут проверить сохранённые записи, вложения и отчёты с помощью доверенного ключа сборщика, проверить внешнее время от третьей стороны для последней записи и сравнить журнал с контрольной точкой, которую они сохранили ранее. На этой странице описаны форматы, проверки и материалы, которые необходимо сохранить для передачи.

Получатели могут начать с запуска **файла VERIFY.cmd** в Windows: программа запросит исходный ZIP-файл и независимо полученный отпечаток ключа, отобразит результат с пояснениями и сохранит отдельный протокол проверки. См. информацию о [программах запуска проверки и переносимой среде выполнения](VERIFICATION_LAUNCHER.md) для ознакомления с настройками и ограничениями доверия.

<a id="what-is-signed"></a>
## Что подписывается

| Материалы | Защита | Что следует сохранять |
| --- | --- | --- |
| Каждое наблюдение журнала, включая операционные события | Цепочка SHA-256 и подпись Ed25519 для каждого события | Исходный файл ``events.jsonl``, отпечаток доверенного ключа и сохраненная контрольная точка |
| Содержимое ZIP-архива с доказательствами | Файл `manifest.sig`, подписывающий канонический манифест, в котором перечислены хеши файлов содержимого | Полный ZIP-архив, включая его манифест и подпись |
| Сохраненные вложения | SHA-256 и количество байтов в подписанном событии `media.saved`; хеш файла в подписанном манифесте ZIP-архива | Исходные байты внутри проверенного ZIP-архива |
| Контрольная точка | Подпись Ed25519, наложенная на длину журнала, хеш вершины журнала, открытый ключ и время создания | Независимая копия, сохраненная до спорного изменения |
| Квитанция о запуске | Подписанная запись о версии сборщика, хешах исходных файлов и начальных настройках, также включённая в `process.started` | Квитанция, соответствующий журнал и доказательства состояния среды для выбранного режима проверки |
| Доступные для чтения отчёты: файл `report.html` и его части, файлы `report.json`, `report.pdf`, `chat.pdf` | Печать Ed25519 для каждого файла, подтверждающая его содержимое; файл PDF также содержит стандартную подпись PDF (см. [Доступные для чтения отчёты](#readable-reports)) | Файл в том виде, в котором он был получен, и отпечаток доверенного ключа; ZIP-архив, описываемый этим файлом |
| Автономный файл CSV | Отсутствие автономной криптографической подписи; одних только хешей событий недостаточно | Для проверки целостности используйте точную копию, содержащуюся в проверенном ZIP-архиве |
| Скриншоты, распечатки или PDF-файлы, сгенерированные браузером | Отсутствует подпись TgWitness на производном файле | Сохраните исходный проверенный пакет и задокументируйте процесс создания производного файла |

Сборщик проверяет подписи журнала перед генерацией каждого экспортного формата. Четкие отчёты в форматах HTML и PDF содержат собственные печати; автономный файл CSV проверяется как часть подписанного ZIP-архива. Сохраните ZIP-архив, чтобы сохранить байты вложений и манифест, а также отдельную контрольную точку для сверки журнала с более ранней границей.

<a id="formats-and-verification-paths"></a>
## Форматы и пути проверки

Режим сбора данных и формат вывода отвечают на разные вопросы. Режим обеспечивает доказательства сбора и окружающей среды; каждый формат сохраняет или представляет часть этой записи с помощью приведённых ниже проверок.

| Вывод | Проверка и использование |
| --- | --- |
| ZIP-архив с доказательствами | Канонические события, подписанный манифест, охват, записи о хранении, вложения и доступные внешние квитанции; проверьте архив и выбранный в нём режим сбора данных. |
| Контейнер ASiC-E | Архив доказательств в формате ZIP представляет собой контейнер ETSI ASiC-E (EN 319 162-1) с записью о типе MIME (`mimetype`) и файлом `META-INF/ASiCManifest.xml`, подписанный с помощью CAdES собственным сертификатом рабочей области на уровне B-B или B-T при включенной функции временной маркировки. Такие валидаторы, как EU DSS, проверяют формат и целостность и, поскольку сертификат выдан самостоятельно, сообщают об отсутствии опорного пункта доверия. EU DSS 6.3 с настройками по умолчанию отклоняет контейнер, содержащий более 1000 файлов («Обнаружено слишком много файлов»). Скрипт `verify.py` проверяет манифест Ed25519 и каждый указанный в нём файл, а также значения SHA-256 в файле `META-INF/ASiCManifest.xml` и в добавленном файле `ASiCManifestNNN.xml` или `ASiCEvidenceRecordManifest.xml`; при этом он выдает ошибку, если обнаруживает запись в `META-INF/`, не охваченную ни одним из них. Он не проверяет подписи CAdES и сообщает об этом. |
| Отчёты в форматах HTML и JSON | Отдельные запечатанные просмотры со ссылками на источники, также перечисленные в манифесте ZIP-архива. Их зарегистрированные подсчёты обобщают типы событий журнала. |
| Отчёты в формате PDF | Печать Ed25519 плюс базовая подпись PAdES в формате PDF над диапазоном байтов: B-B или B-T с временной меткой подписи, если функция временной метки включена. Верификатор TgWitness использует доверенный ключ Ed25519; отображение доверия к сертификату в программе просмотра является отдельной проверкой. |
| CSV | Представление в виде электронной таблицы, включённое в манифест ZIP-архива. Экранирование формул обеспечивает безопасность использования таблицы; исходный подписанный текст сохраняется в журнале. |
| JSONL | Подписанные записи событий, включая ссылки на вложения. ZIP-архив с доказательствами дополнительно содержит сохраненные байты вложений. |
| Экспорт чата и представления, совместимые с Desktop | Сбор истории и доступных записей журнала администратора с требуемым отображением и подписанным архивом. Сохраненные версии данных оперативного мониторинга представляют собой отдельный канал сбора данных. |
| Медиафайлы и записи, содержащие только хеш-значения | Сохраненные байты сверяются с их SHA-256 и ссылкой на сообщение. Сбор «только хешей» сохраняет доступные метаданные хешей для последующего сравнения с байтами файла. |
| STIX/MISP и профили пользователей | Извлеченные наблюдения с привязкой к источнику, идентификаторы аккаунтов и аналитические совпадения. Сигнатуры профилей и хеши записей можно сверять с исходными доказательствами; происхождение кэша аватаров маркируется отдельно. |
| Выдержка из передаваемых данных | Подписанные правила раскрытия информации, неизменённые записи и помеченные минимизированные записи с сохранением исходных хешей/подписей. Используйте сохраненный оригинал для сравнения, требующего удержания определённых полей. |
| Свидетельские и временные квитанции | Предыдущие границы журналов, непрерывность и отдельные подтвержденные временные отметки. Они сопровождают проверки получения и архивирования. |
| Доставка с защитой паролем | Обеспечивает защиту вложенного пакета во время передачи. Формат `.tgwpw` использует шифрование с аутентификацией по алгоритму AES-GCM, включая аутентифицированную заключительную запись; вложенный журнал сохраняет свои подписи и квитанции о получении. |

Распечатка или снимок экрана представляют собой отображение подписанного материала. Идентификатор отчёта, отпечаток ключа и QR-ссылка помогают найти исходный файл для проверки. Декларации о хранении фиксируют информацию о назначенном эксперте и передаче; результаты верификатора и квитанции о получении сохраняются в качестве отдельных доказательств.

<a id="external-signatures"></a>
### Внешние подписи

Подпись также может быть получена от ключа, которым TgWitness никогда не располагает, например, от квалифицированной электронной подписи следователя или печати организации. При **экспорте внешняя подпись** на подготовленном экспорте без пароля передаёт байты для подписания: новый файл `META-INF/ASiCManifestNNN.xml`, содержащий список всех файлов с их SHA-256 для контейнера ASiC-E, или файл `manifest.json` экспорта для ZIP-архива. Подписывающий возвращает файл CMS (CAdES) с расширением .`.p7s` — отдельно или со встроенным содержимым.

TgWitness проверяет, что подпись охватывает именно эти байты, и верифицирует её с помощью сертификата подписавшего лица (RSA PKCS#1 v1.5, RSASSA-PSS, ECDSA, Ed25519, Ed448). Цепочка проверяется только по корневым сертификатам, предоставленным оператором; отзыв сертификатов, списки доверенных сертификатов и статус квалифицированности не проверяются. На панели отображается одно состояние для каждой подписи: ожидание подписи, вложение и не проверенное, проверена, алгоритм не поддерживается, подпись недействительна, подписанные байты не совпадают или сертификат не входит в цепочку, ведущую к предоставленному корневому сертификату. Изменение экспорта после передачи байтов приводит к установке для всех его подписей состояния «подписанные байты не совпадают».

**Загрузка с подписями** добавляет подписи и их манифесты в папку `META-INF` внутри контейнера ASiC-E. В случае ZIP-архива в внешний ZIP-архив помещаются неизменённый ZIP-файл, файлы `.p7s` и файл `SIGNATURES.txt`. Недопустимые подписи и подписи, наложенные на другие байты, исключаются. Подпись, алгоритм которой не может быть проверен TgWitness, включается в файл; её состояние отображается на панели, а также в файле `SIGNATURES.txt` для ZIP-архива.

<a id="signed-chat-images"></a>
### Подписанные изображения чата

**При загрузке подписанного ZIP-файла** в окне предварительного просмотра изображения сохраняются страницы в формате PNG, файл `pages.sig.json` и файл `README.txt`. Каждая страница заканчивается номерами записей журнала, отображаемыми на ней, чатом, временем рендеринга, отпечатком ключа рабочей области и командой, проверяющей его. Панель отправляет только SHA-256 каждой страницы и номера записей; сервер подтверждает, что записи принадлежат данному чату, подписывает заявление (`tgwitness-image-attestation-v1`) с помощью ключа рабочей области и фиксирует подписание в журнале как `export.image_attested`.

```
python verify.py page-01.png page-02.png pages.sig.json
python verify.py page-*.png pages.sig.json --fingerprint TRUSTED_SHA256 --evidence evidence.zip
```

Верификатор проверяет подпись, сопоставляет каждый файл PNG с подписанной страницей и сообщает отпечаток ключа. Параметр `--fingerprint` сравнивает подписавшего с отпечатком, полученным от отправителя независимым образом. Параметр `--evidence` считывает подписанный ZIP-архив доказательств из той же рабочей области и требует, чтобы каждая запись изображений присутствовала с тем же хешем. Изменение пикселя, изменение заявления или использование другого ключа приводит к сбою проверки. Изображения отображают сохраненные записи в собственном формате TgWitness; они не показывают то, что Telegram отображал кому-либо.

<a id="comparing-chat-exports"></a>
## Сравнение экспортов чатов

Проверьте и сравните два подписанных ZIP-архива экспорта чата с независимо сохраненными отпечатками подписи:

```sh
python -m tgwitness.verify first.zip --compare second.zip \
  --fingerprint FIRST_TRUSTED_KEY_SHA256 --compare-fingerprint SECOND_TRUSTED_KEY_SHA256
```

Параметры `--require` и `--require-tier` не допускаются к использованию вместе с `--compare`; проверьте требуемый профиль каждого архива с помощью его собственной проверки.

Если в обоих архивах зафиксированы одинаковые числовые идентификаторы аккаунта и чата, записи сопоставляются по идентификатору сообщения. **Неизменённый** означает равенство полной сохраненной записи в формате JSON: включаются полный текст, автор, даты, адресат ответа, вложенные метаданные и неизвестные поля. Порядок ключей в объекте JSON не имеет значения; значение имеют отсутствующие поля, нулевые значения, типы значений и порядок массивов. Предварительный просмотр длиной 300 символов предназначен исключительно для отображения. В записях с изменениями указываются отличающиеся поля верхнего уровня (`changed_fields`), включая изменения, невидимые в этом предварительном просмотре. Дубликаты идентификаторов сообщений отклоняются, а не перезаписывают друг друга при сопоставлении.

Разница может заключаться в изменении отображаемого имени, количества просмотров, аннотации коллекции или других метаданных наблюдения. Редактирования в Telegram отображаются как отдельные события редактирования, а проверка каждого архива показывает, является ли данный архив целостным. Непроанализированные записи остаются в сравнении и сравниваются на основе их сохраненного представления.

В случае несовпадения или отсутствия идентификаторов аккаунта/чата инструмент находит возможные соответствия с помощью отправителя, полного текста, хеша файла, типа медиафайла и пятисекундного временного допуска, после чего отмечает их как **Совпавшие (Matched)**, а не как **Неизменённые (Unchanged)**. Непроанализированные записи остаются без сопоставления. Различия в сопоставленных записях перечисляются в категории `changed`, в том числе в режиме просмотра содержимого. При использовании параметра `--json` команда `matched` подсчитывает потенциальные пары, а команда `unchanged` — пары, полные сохраненные записи которых совпадают. Существующие параметры `changed_fields` и целочисленный вывод `unchanged` остаются совместимыми с предыдущими результатами сравнения. Проверка формата архива и подписи остаются без изменений.

<a id="investigation-handoff"></a>
## Передача материалов расследования

1. Зафиксируйте в заметках по делу ссылку на дело, оператора, числовой идентификатор аккаунта в Telegram, выбранные источники, политику сбора данных и период сбора. TgWitness сохраняет наблюдения и поддерживает привязанные к источникам заметки и сбор данных в [Case Board](CASE-BOARD.md). Храните записи о передаче и хранении вместе с материалами дела. Проверьте настроенные параметры сбора данных с помощью [процедуры приёма в режиме реального времени](../internal/LIVE_ACCEPTANCE.md).
2. Перед тем как полагаться на экспортированные данные, самостоятельно сохраните отпечаток открытого ключа рабочей области. Оставьте режим «Доказательства» включённым (по умолчанию), чтобы контрольные точки получали квитанции в соответствии с RFC 3161 и OpenTimestamps. Во время сбора данных сохраняйте подписанные контрольные точки вне сборщика. Зафиксируйте прерывания и ограничения видимости аккаунта.
3. Экспортируйте **подписанный ZIP**-файл и сохраните подписанную квитанцию о запуске. Используйте контрольную точку, расположенную на границе экспортируемого журнала или перед ней. Более поздняя контрольная точка может правильно отклонить более ранний экспорт как слишком короткий. Экспорт включает полный журнал рабочей области, независимо от фильтров панели; проверьте материалы перед их передачей.
4. Попросите получателя проверить ZIP-архив с помощью доверенной копии верификатора, независимо предоставленного отпечатка и корневого сертификата органа, выдающего временные метки, полученного отдельно. Из доверенной среды с активной средой Python:

   ```sh
   python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --tsa-ca TSA-ROOT.pem --checkpoint retained-checkpoint.json --require evidence
   ```

Отпечаток и проверенная временная метка последней записи соответствуют минимальным требованиям к доказательству; в противном случае команда `--require evidence` завершит работу с кодом 2. Контрольная точка является вспомогательной проверкой, поскольку она подписана ключом сборщика. Успешный вывод сообщает `key_pinned: true` и `checkpoint_checked: true`, если оба входных параметра предоставлены и приняты. Сохраните результат проверки.

Для передачи, требующей подтверждения окончательной экспортируемой записи, используйте параметры ``--witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness``. Это не допустит экспорта с неподтверждённой конечной частью. Добавьте параметр ``--channel https://t.me/s/WITNESS_CHANNEL``, чтобы использовать даты, установленные Telegram в сообщениях свидетелей, в качестве внешнего времени. Ознакомьтесь с [процедурой передачи с участием свидетелей](../WITNESS.md#require-a-witnessed-export-boundary).
5. Зафиксируйте в вашем журнале хранения SHA-256 архива, границу экспорта, дату передачи, отправителя и получателя. Сохраняйте исходный пакет в неизменном виде и работайте с копиями. Делитесь файлами доказательств, а не каталогом личных данных приложения, который также содержит сеансы аккаунтов и секретные ключи подписи. Для передачи выберите ZIP-архив с защитой паролем по стандарту AES-256 или более надёжный контейнер `.tgwpw`. ZIP использует недорогую схему вычисления пароля WinZip; используйте длинную случайную парольную фразу. `.tgwpw` использует scrypt и AES-256-GCM и открывается с помощью команды `unseal-password` автономного верификатора. Пароль не сохраняется и служит исключительно для обеспечения конфиденциальности; получатель расшифровывает архив и использует верификатор для проверки содержащегося в нём подписанного экспорта, который остаётся неизменённым.
6. Для присвоения временной метки контрольной точке вне режима «Доказательства» следуйте [процедуре](TIMESTAMP.md), описанной в [RFC 3161](TIMESTAMP.md), и сохраните запрос, контрольную точку, информацию о доверенном центре сертификации (CA) и проверенный ответ уполномоченного органа. Сама по себе подготовка запроса не обеспечивает получение временной метки.

Для файла `.tgwpw` используйте независимо полученный верификатор и выберите новый выходной файл с исходным расширением: ``python verify.py unseal-password export.tgwpw --out evidence.zip``. Команда запросит ввод пароля; опция ``--password-stdin`` считывает одну строку для автоматизации. Она никогда не перезаписывает существующий файл и публикует открытый текст только после аутентификации всех записей. Затем выполните обычную проверку подписи на расшифрованном файле. Контейнер использует алгоритм scrypt (`N=131072`, `r=8`, `p=1`, соль длиной 16 байт; требуется около 128 MiB оперативной памяти) и AES-256-GCM с записями размером 1 MiB и аутентифицированной заключительной записью. Зашифрованная запись метаданных хранит внутреннее имя файла, поэтому загруженные контейнеры можно переименовывать.

Успешная проверка подтверждает целостность относительно доверенного ключа сборщика и сохраненного граничного значения. См. [раздел Область проверки](#verification-scope) для ознакомления с допущениями о доверии и [результатами валидации](VERIFICATION.md) выполненных проверок.

<a id="handover-extract"></a>
## Выдержка для передачи

Подписанный ZIP-архив содержит весь журнал рабочих областей. Если суду, адвокату или службе по борьбе со злоупотреблениями требуются лишь отдельные чаты, определенный период или конкретные участники, то **в разделе Экспорт → Выдержка для передачи** формируется сокращённая копия (`tgwitness-handover-v1`) в соответствии с выбранными правилами раскрытия информации. Оператор указывает цель и выбирает чаты, опциональный период (UTC), участников, к которым относится выдержка, а также определяет, что произойдет с остальными участниками (будут ли они отображаться, заменяться псевдонимами P01, P02… или исключены), какие тексты сообщений сохраняются, какие вложения и фотографии профилей включаются, а также маскируются ли номера телефонов и адреса электронной почты в текстах. Цель и эти правила указываются в подписанном манифесте и в отчёте; в журнале регистрируется запись `handover.exported` с указанием учетной записи, подготовившей выдержку, и значением SHA-256 файла, а не его содержанием.

Скрипт `verify.py` проверяет выдержку двумя способами. Запись, указанная как неизменённая, проверяется в полном объёме: её содержание сверяется с хешем, подписью Ed25519 и ссылкой на включённую предыдущую версию. В сокращённой записи сохраняются исходный хеш и подпись, поэтому подпись по-прежнему проходит проверку, но скрытые поля невозможно пересчитать на её основе; в записи указывается, что именно было скрыто, и это отмечается в отчёте. Записи об обслуживании на уровне аккаунта (запуски и остановки, пробелы в покрытии, уведомления о подключении, сети и хранении, изменения области действия и настроек) сохраняют только поля, указанные для их типа: списки чатов в них сокращаются до выбранных чатов, а их итоги пересчитываются; при пропуске в ходе проверки в реальном времени чата, не входящего в выборку, этот чат, номера его сообщений и аккаунт свидетеля теряются; в выбранном для проверки чате аккаунт свидетеля заменяется его псевдонимом, если только не отображаются все участники или он не является одним из выбранных лиц. Манифест указывает длину журнала и его вершину с подписью сборщика над этой вершиной, а также подсчитывает количество исключённых записей; файл ``coverage.json`` описывает выбранные чаты. Новые выдержки также содержат файл ``proofs.jsonl``: для каждой включённой записи и для вершины журнала приводится путь Меркла от исходного хеша записи до корня журнала, указанного в подписанном манифесте. Скрипт `verify.py` проверяет каждый путь, благодаря чему подтверждается, что каждая запись принадлежит одному и тому же журналу данной длины и с указанной вершиной журнала, даже без полного журнала; проверка выдержки из 100 сообщений занимает примерно одну секунду независимо от размера журнала. Параметр `--range=CHAT:FROM-TO` дополнительно подтверждает, что сообщения от FROM до TO в чате присутствуют в выдержке, и сообщает, сколько записей было проверено для них. Если для некоторых номеров диапазона в выдержке отсутствуют записи, указывается также их количество: они были исключены в соответствии с правилами формирования выдержки, удалены или никогда не использовались, и сама по себе выдержка не позволяет определить, что именно произошло. Имена, содержащиеся в именах файлов, не обнаруживаются. Перед передачей файлов тщательно проверьте итоговые файлы: свободный текст, имена файлов и выбранные вложения по-прежнему могут позволить идентифицировать людей. Сохраните полный подписанный ZIP-архив: выдержка является раскрытием информации, а не её заменой.

<a id="readable-reports"></a>
## Удобные для чтения отчёты

Подписанные ZIP-архивы с доказательствами, передачей данных и чатами содержат читаемые отчёты в форматах HTML и JSON, а также в формате PDF при наличии необходимых шрифтов на выбранном языке отчёта. Каждый отчёт запечатан ключом Ed25519 рабочей области и может быть проверен отдельно: ``python -m tgwitness.verify FILE --fingerprint KEY [--evidence ZIP]``.

- `report.html` / `chat.html`: заявление о запечатывании (`tgwitness-report-seal-v1`) закрывает файл и подписывает SHA-256 каждого байта, предшествующего ему. Объёмные журналы и чаты разбиваются на части настраиваемого размера (в настройках отчёта — от 500 до 100 000 записей; по умолчанию — 5 000): `records/records-0001.html` или `messages/messages-0001.html`, каждая из которых запечатана с указанием номера, диапазона и общего количества записей, а также перечислена с указанием SHA-256 в подписанном манифесте. Серии сигналов о работоспособности сборщиков отображаются одной строкой, если только в «Настройках отчёта» не указано их поочерёдное отображение.
- `report.json` (`tgwitness-report-json-v1`, ключи `format`, `report`, `seal`): печать подписывает SHA-256 канонического JSON-файла отчёта (`report`), благодаря чему данные могут быть прочитаны системами рассмотрения дел и скриптами, а также на их основе может быть произведён отбор для защиты данных, при этом подписанный файл остаётся целостным.
- `report.pdf` / `chat.pdf`: официальный документ для печати и архивирования, подписанный дважды на одни и те же байты — весь файл, за исключением значения подписи (`/ByteRange`). Стандартная подпись в формате PDF соответствует базовому стандарту PAdES (ETSI EN 319 142-1, `/SubFilter /ETSI.CAdES.detached`: CMS с использованием SHA-256 и ECDSA P-256, signing-certificate-v2, без указания времени подписания CMS; заявленное время — `/M`) на уровне B-B или B-T с отметкой времени подписи по RFC 3161 в CMS, если функция простановки отметки времени включена и центр простановки отметки времени отвечает по маршруту на запросы за пределами Telegram. Используется самостоятельно выданный сертификат для подписи документов, хранящийся в хранилище рабочей области; его серийный номер субъекта представляет собой отпечаток ключа Ed25519. Печать Ed25519 передаётся внутри CMS в виде неподписанного атрибута `2.25.240684792623320047764573196045913242332` и указывает SHA-256 сертификата с `"content": "pdf-byte-range"`, таким образом ключ Ed25519 подтверждает подлинность сертификата. Значение подписи находится за пределами `/ByteRange`, поэтому `verify.py` принимает CMS только в том виде, в котором его записывает TgWitness: один сертификат, один подписант, указывающий его, отделённое содержимое, отсутствие повторяющихся атрибутов, отсутствие неподписанных атрибутов, кроме печати и временной метки подписи (отпечаток и подпись TSA которой он проверяет), а также только нулевое заполнение после CMS. Сертификат не является квалифицированным: программа просмотра PDF отображает подпись как действительную, а подписавшего — как неизвестного или недоверенного, пока сертификат не будет признан доверенным; вместо этого сравните отпечаток Ed25519. Для PDF-файлов на китайском, японском и корейском языках требуется шрифт на сервере (или в каталоге `TGWITNESS_FONT_DIR`); в отсутствие такого шрифта архив ZIP содержит только отчёты в форматах HTML и JSON.
- `report.en.html`, `report.en.pdf` / `chat.en.html`, `chat.en.pdf`: английский оригинал того же отчёта, если язык отчёта не является английским; он запечатан и подписан таким же образом и указан под именем `report.original` в подписанном манифесте. Отчёт на выбранном языке открывается с рекомендацией приложить к нему английский оригинал с заверенным или присяжным переводом; см. раздел [Перевод отчётов для суда](../TRANSLATION.md).

В канале или супергруппе Telegram нумерует сообщения 1, 2, 3… по порядку. Экспорт чата перечисляет первый и последний номер, количество присутствующих сообщений и все последовательности отсутствующих номеров в файлах ``message-ids.json``, манифесте и заголовке ``chat.json``, а также отмечает каждый пробел в том месте, где он встречается в стенограмме. Скрипт `verify.py` пересчитывает их из файла `chat.json`. Отсутствующий номер — это сообщение, которое Telegram не вернул (удалённое до экспорта или невидимое для аккаунта); в личных чатах и базовых группах номера являются общими для всех чатов данного аккаунта, и пробелы не учитываются.

После считывания истории экспорт заново запрашивает у Telegram каждый отсутствующий номер по номеру (с помощью `channels.getMessages`, до 10 000 номеров, включая 1 000 под первым сообщением, равномерно распределённых по всем пробелам, если их больше). Результат находится в файле `message-ids.json` и отчёте. Пустой ответ фиксирует, что номер недоступен для данного аккаунта на момент повторной проверки; причина не указывается. Сообщение, возвращённое при повторной проверке, добавляется в экспорт и помечается как `found_on_recheck`.

Если в наблюдаемой рабочей области были обнаружены сообщения чата, удалённые, отсутствующие при повторной проверке или отредактированные, в экспорт чата добавляется файл `journal-changes.jsonl`: эти записи журнала, каждая сохраненная версия и уведомление, каждая из которых сопровождается хешем и подписью Ed25519, полученными в журнале. Скрипт `verify.py` пересчитывает хеш каждой записи, сверяет её подпись с ключом экспорта и сравнивает количество записей с подписанным манифестом; экспорт доказательств содержит полную цепочку хешей. В отчёте эти сообщения перечислены в разделах **Удаления и Предыдущие версии**.

Каждый отчёт начинается с **раздела Кратко**: один абзац, затем — что показывают материалы и что включает в себя запись. Печать на самой странице становится янтарного цвета, когда браузер проверил подпись печати, а не самой страницы: браузер не присваивает странице собственные байты. Она становится зелёной только в том случае, если читатель перетаскивает файл в поле проверки внизу страницы и все байты совпадают, а также только если отображаемая страница соответствует данному файлу; в противном случае она становится красной.

В каждом отчёте точно указывается название программы: коммит Git, при котором сборщик запускается из репозитория или установщик устанавливает переменную `TGWITNESS_COMMIT`, а также SHA-256 исходных файлов (`source_tree_sha256` — канонический JSON-массив, содержащий путь к SHA-256 каждого файла с расширением `.py`, `.js`, `.css`, `.html` и `.svg` в пакете), который воспроизводится при извлечении из этого коммита, если файлы не были изменены. Клиент Telegram указывается с указанием его библиотеки, уровня API и центра обработки данных. При начале наблюдения, а также при начале и окончании экспорта чата сборщик запрашивает у Telegram время (функция `updates.getState`, в целых секундах) и фиксирует время Telegram за вычетом времени по часам сборщика с погрешностью, обусловленной временем прохождения сигнала туда и обратно; эти измерения отображаются в отчётах в разделе «Цепочка контроля». При экспорте чата также фиксируется время считывания истории, помимо дат сообщений.

<a id="offline-report-viewer-and-archive-guide"></a>
### Программа просмотра отчётов в автономном режиме и руководство по архивированию

Перед открытием файлов `chat.html` или `report.html` необходимо полностью распаковать ZIP-архив. Программа просмотра предоставляет функции поиска, фильтров, просмотра участников, индикаторов, сведений о записях и выбора данных в форматах JSON/CSV без подключения к серверу. Сохраните папки `viewer/` и `media/` рядом с отчётом. Выделенные фрагменты являются производными: используйте команду ``verify.py SELECTION.json --evidence ARCHIVE.zip`` для их сравнения с подписанным архивом. Верификатор проверяет идентификатор отчёта, ключ подписи, границы архива и каждый выбранный элемент; отредактированные, отсутствующие и дублирующиеся элементы не проходят проверку. Примечания к выделенным фрагментам и время создания остаются неподписанными метаданными.

Пробелы в номерах сообщений отображаются только для полной, нефильтрованной ленты чата в порядке возрастания. Скрытие категории или сбой при загрузке фрагмента данных не должны превращать пропущенную строку в доказательство отсутствия сообщения. Выделение результатов поиска осуществляется в виде простого текста до HTML-эскейпинга, что позволяет сохранить буквальную разметку.

Браузер проверяет подписи манифеста, идентификатор отчёта и ключ, а также все указанные хеши файлов. Он отклоняет неоднозначные или некорректно сформированные структуры ZIP, дубликаты имён и небезопасные пути, а также ограничивает размер файлов 256 MiB и объявлённый общий объём содержимого 4 GiB. Для архивов большего размера используйте автономный верификатор. Данная проверка в браузере дополняет проверки верификатора, касающиеся цепочек журналов и семантики данных.

Файл `README.txt` содержит вводную инструкцию, выровненный перечень файлов, инструкции по проверке и примечания по формату данных на языке отчёта, а также полное руководство на английском языке. Файл `SHA256SUMS` охватывает перечисленные в нём файлы, за исключением самого себя, файлов `manifest.json` и `manifest.sig`; подписанный манифест также охватывает файл `SHA256SUMS`. Сохраняйте исходный ZIP-архив без изменений и сохраняйте рабочие файлы за пределами папки с извлечённым содержимым. Отчёты в формате PDF содержат закладки по разделам, а на последующих страницах — идентификаторы дела и отчёта.

<a id="the-chat-at-export-time"></a>
### Содержание чата на момент экспорта

Экспорт чата фиксирует информацию, предоставленную Telegram о данном чате на момент начала экспорта: собственные метки Telegram (`scam`, `fake`, `restricted` с указанием причин, `verified`), имена пользователей, описание, количество участников и администраторов, связанное обсуждение, защита контента, информация о том, видят ли новые участники предыдущие сообщения и с какого сообщения данный аккаунт имеет доступ к истории (`available_min_id`), дату первого сообщения, если это дата создания чата, а также SHA-256-хэш фотографии чата (сохраненной в папке `media/`). Также фиксируется статус аккаунта, осуществляющего экспорт, в чате: роль, дата присоединения, имя пригласившего, а для администратора — его права. В случае отказа Telegram указывается название соответствующего запроса.

Если аккаунт, осуществляющий экспорт, является администратором, при экспорте в файл `admin-log.json` записывается журнал действий администратора чата (Telegram хранит его в течение примерно 48 часов): удаления и правки с указанием предоставленного содержания, действующего аккаунта и даты исходного действия. Эти записи дополняют сохраненные версии записей в «LiveJournal» и записи о получении уведомлений об удалении.

<a id="indicators"></a>
### Индикаторы

В списке отчётов и в архиве в файлах `indicators.csv`, `indicators.stix.json` (STIX 2.1) и `indicators.misp.json` (событие MISP) содержатся данные, на основании которых служба по борьбе со злоупотреблениями может принимать меры в отношении зафиксированных сообщений: ссылки и домены (в том числе скрытые в тексте, в кнопках и в предварительном просмотре ссылок), адреса криптовалютных кошельков, имена пользователей Telegram и ссылки для приглашения, номера телефонов, адреса электронной почты и сохраненные изображения. Адреса Bitcoin, Litecoin, Dogecoin и TRON указываются только при наличии контрольной суммы base58; адреса SegWit — при наличии контрольной суммы bech32 или bech32m; адреса TON — при наличии контрольной суммы CRC; адреса XRP Ledger — при наличии контрольной суммы; адреса EVM и Solana помечаются как непроверенные. Также указываются хеши транзакций: 32-байтовый хеш, всегда начинающийся с `0x`, и простая 64-символьная шестнадцатеричная строка — только в том случае, если этот же текст обозначает транзакцию (например, `tx`, `hash`, `transaction`, название блокчейн-браузера). Простой хеш не указывает на цепочку, поскольку Bitcoin, TRON, TON и другие используют одинаковый формат; об этом указано в записи, и цепочку необходимо определить с помощью эксплорера. Ссылки на платежи (`bitcoin:`, `ethereum:`, `solana:`, `tron:`, `litecoin:`, `dogecoin:`, `ton:`) приводятся с указанием цепочки, адреса, суммы, контракта токена и метки, если эта информация содержится в ссылке; кроме того, адрес длиной 20 символов или более, указанный в ссылке, также указывается как адрес кошелька, взятый из ссылки на платеж. Изображения сопровождаются хешем SHA-256 и перцептивным хешем (dHash, 64 бита), которые остаются практически неизменными даже при повторном сжатии или изменении размера копий. В отчётах индикаторы записываются таким образом, чтобы их нельзя было случайно открыть (`hxxps[://]example[.]com`); значения файлов сохраняются в исходном виде. Каждый индикатор помечается как «неизвестный» и не предназначен для автоматического обнаружения (STIX `indicator_types: unknown`, MISP `to_ids: false`, распространение в пределах собственной организации): его наличие в списке означает, что он содержался в сообщении, а не то, что он является вредоносным. Ссылка, текст которой указывает адрес, отличный от того, на который она ведёт, отмечается в отчёте.

Отчёты в формате PDF завершаются заявлением эксперта, которое необходимо подписать от руки, контрольным списком для нотариуса или судебного эксперта, а также QR-кодом (также расположенным на первой странице) с идентификатором отчёта, отпечатком ключа и хэшем SHA-256 достоверных данных, благодаря чему распечатка позволяет отследить отчёт до его архива.

<a id="event-canonicalization"></a>
## Канонизация событий

Входные данные для хеша состоят именно из следующих полей:

~~~text
seq, observed_at, source_at, kind, chat_id, message_id, actor_id, payload, previous_hash
~~~

Сериализация осуществляется с использованием JSON, совместимого с Python, с кодировкой UTF-8, отсортированными ключами объектов, без ASCII-эскейпинга, без незначительных пробелов и без значений NaN/бесконечности:

~~~python
json.dumps(value, ensure_ascii=False, sort_keys=True,
           separators=(",", ":"), allow_nan=False).encode("utf-8")
~~~

SHA-256 этих байтов становится хешем события. Подпись формируется с помощью алгоритма Ed25519 над 32 исходными байтами хеша, а затем кодируется в Base64. Первый предыдущий хеш (previous_hash) состоит из 64 нулей. Порядковые номера начинаются с 1 и увеличиваются на 1. Все события, включая операционные, находятся в одной цепочке. Подавление дубликатов доставки отсутствует: повторные наблюдения представляют собой отдельные квитанции, а не утверждение о различных действиях Telegram.

Исходные даты Telegram представляют собой строки в формате ISO; двоичные поля преобразуются в объекты, содержащие bytes_base64. Текст сообщения, сущности, дескрипторы медиафайлов, метаданные ответов, реакции и действия сервиса сохраняются в исходных метаданных сообщения, если они были предоставлены. Активное сообщение также сохраняет обновление Telegram, которое его доставило, в поле ``transport_update``; если это обновление содержит то же сообщение, что и ``raw``, его поле ``message`` принимает значение `{"same_as": "raw"}` вместо второй копии.

`observed_at` — это время записи записи в UTC, зафиксированное сборщиком; `source_at` — это дата, предоставленная данным событием Telegram. Записи, созданные при обработке актуального обновления, содержат `payload.received_at` (время в UTC, когда обновление достигло сборщика) и `payload.processing_delay_ms`. При редактировании в режиме реального времени сохраняется указанная дата редактирования, в моментальных снимках истории сохраняется дата сообщения с текущим временем наблюдения, а в обычном уведомлении об удалении фиксируется время получения с нулевой датой источника. Записи в журнале администратора отдельно сохраняют указанную дату действия. Порядок получения и порядок событий источника представляют собой отдельные временные шкалы, при этом для сравнения доступны данные наблюдений по часам и внешние квитанции.

<a id="actor-semantics"></a>
## Семантика участников

Присвоение авторства осуществляется в соответствии с источником события. Поля ``message.new.actor_id`` и ``message.edited.payload.sender_id`` сохраняют идентификатор отправителя сообщения. Обычные уведомления ``message.deleted`` содержат идентификаторы сообщений и имеют поле `actor` с нулевым значением; доступные записи журнала администратора содержат указанные в них действие, участника и дату. Сообщения службы членства сохраняют отправителя и тип действия, необработанные обновления участников сохраняют указанный ``actor_id``, а моментальные снимки реакций сохраняют указанные в них счёты и видимые идентификаторы. Изучайте эти записи вместе с сохраненными версиями и [квитанциями о взаимодействии с панелью](COLLECTION.md#own-actions).

Уведомления об удалении для личных чатов и обычных групп содержат только идентификаторы сообщений. Эти чаты используют одну общую для всех аккаунтов последовательность идентификаторов, поэтому каждый идентификатор идентифицирует одно-единственное сообщение данного аккаунта. Если сообщение с данным идентификатором было ранее сохранено в этом журнале, удаление фиксируется в данном чате как message.deleted с параметром payload.chat_resolution, указывающим метод. Идентификаторы, которые никогда не сохранялись, хранятся как `deletion.unscoped`: это фактическое уведомление об удалении, чат которого не был соотнесён. Это отличается от `message.missing_on_recheck`, которое фиксирует недоступный результат запроса, а также от пробела в сохраненных идентификаторах сообщений. Каналы и супергруппы подсчитывают количество сообщений по каждому чату и никогда не сопоставляются таким образом. Если удалённое сообщение было отправлено наблюдаемым аккаунтом, значение payload.deleted_message_was_outgoing равно true; при этом отправитель по-прежнему не указан.

Уведомление без области действия сохраняет собственную метку, поскольку соответствующий чат может находиться за пределами текущего наблюдения или не иметь однозначного соответствия. Отсутствие при повторной проверке остаётся отдельным событием, отличающимся от уведомления об удалении в подсчётах отчётов, фильтрах и метках. Последующее восстановление сбрасывает текущее состояние отсутствия, сохраняя при этом предыдущую неудачную проверку в подписанной истории; уведомления об удалении остаются отдельным типом событий.

Несколько идентификаторов, относящихся к одному и тому же чату из одного уведомления, группируются как `deletion.batch`, независимо от их количества, с идентификаторами сообщений в том виде, в каком их отправил Telegram, и с указанием количества сообщений, отправленных данным аккаунтом. В уведомлении Telegram перечислены сообщения; в журнале администратора чата указан действующий администратор, если аккаунт имеет доступ к просмотру этого журнала. Связь (`message.deletion_attributed`) устанавливается в зависимости от того, что поступило первым: запрос, в котором запись в журнале администратора была обнаружена до уведомления об удалении, сопоставляется при регистрации самого уведомления.

<a id="coverage-continuity-gaps-and-unobserved-ids"></a>
## Охват: непрерывность, пробелы и ненаблюдаемые идентификаторы

Каждый подписанный ZIP-архив содержит файл `coverage.json`; HTML-отчёт открывается с той же сводкой, а скрипт `verify.py` пересчитывает её на основе файла `events.jsonl`, а не полагается на данные этого файла:

- **Непрерывное наблюдение с момента X до момента Y.** Период начинается с события `observation.started` и заканчивается при паузе, остановке, потере соединения с Telegram, выходе из системы, запуске процесса без упорядоченной остановки или при отсутствии записей в течение более трёх минут во время наблюдения (сигналы пульса записываются каждую минуту, поэтому отсутствие сигналов означает, что процесс остановился, завис или компьютер перешёл в спящий режим). При изменении интервала сигналов пульса в разделе **Дополнительные инструменты → Параметры** каждый сигнал пульса фиксирует это изменение, и допустимое время отсутствия записей становится равным трём интервалам, но никогда не может быть меньше трёх минут.
- В списке **Пробелы** указано время между периодами с указанием причины. Пробел, остававшийся открытым на момент последней записи, помечается как `not_resumed_by_last_record`.
- **Идентификаторы сообщений, не подвергшиеся наблюдению.** Для каналов и супергрупп, в которых подсчёт сообщений ведётся по каждому чату, пропущенные ID между зафиксированными указываются в виде диапазонов. Они фиксируются как *не зафиксированные* — удалённые, никогда не доставленные или выходящие за пределы сохраненной истории — но никогда не указываются как «удалённые». Личные чаты и обычные группы используют общую для всего аккаунта нумерацию, поэтому пробелы внутри одного такого чата не имеют значения и там не отображаются.
- Уведомления о пробелах на уровне чата (например, запрос Telegram на восстановление разницы в одном канале) учитываются как примечания; они не прерывают глобальный охват.
- **Записи сеансов.** Отдельно перечисляются периоды, в течение которых счетчик обновлений Telegram увеличивался, хотя ни одно обновление не достигло данного сеанса (`updates_diverted`), данный сеанс был исключён из списка сеансов Telegram, хотя его соединение продолжало функционировать (`session_revoked_externally`), либо ответ от свидетеля поступил только из истории (`probe_ack_missed_live`). Верификатор также сообщает об источнике сеансного ключа Telegram, о других сеансах, вошедших в систему на момент начала наблюдения, о сеансах, добавленных в ходе наблюдения, об уведомлениях Telegram о безопасности (777000), о других сеансах, завершённых из рабочей области, о периодах, когда активна была только одна сеанс, о количестве запросов к свидетелю и об обновлениях телефонных звонков. См. [аккаунты](ACCOUNTS.md#witness-probe). При включенном режиме [строгого выбора чатов](COLLECTION.md#strict-chosen-chats) (`scope.strict` в `observation.started`) список сеансов (за исключением случаев, когда это единственный сеанс или когда включена функция **Устройства Telegram**), уведомления о безопасности и обновления о телефонных звонках не собираются, поэтому их отсутствие ничего не означает, а удаление сопоставляется с проверкой сеанса только в том случае, если такая проверка выполнялась в течение 10 минут до него.

<a id="update-sequence-pts"></a>
### Последовательность обновлений (`pts`)

Telegram нумерует обновления, связанные с сообщениями, с помощью `pts`: одна последовательность для аккаунта (личные чаты и базовые группы вместе) и по одной для каждого канала или супергруппы. Сборщик регистрирует каждый полученный им непрерывный отрезок без пробелов в виде записи `coverage.sequence`: первые и последние `pts`, количество обновлений каждого типа, а также информацию о том, были ли они отправлены в режиме реального времени или получены с помощью `getDifference` или `getChannelDifference`. Пробел представляет собой запись `coverage.gap`, а `coverage.gap_closed` указывает `pts`, начиная с которых последовательность вновь становится непрерывной.

Непрерывный отрезок свидетельствует о том, что каждое обновление Telegram, пронумерованное в данной последовательности между первым и последним точками (`pts`), достигло клиента Telegram данного сборщика. Это не говорит ни о содержании сообщений Telegram, которые никогда не отправлялись на этот аккаунт, ни о времени до первой зафиксированной точки (`pts`), ни об отрезках, которые сборщик не зафиксировал. Переход к следующей точке (`pts`), который не покрывается ни одной зафиксированной последовательностью или разницей, отображается как разрыв.

Запрос `GET /api/continuity` для интервала (`since`, `until`, `chat_id`) возвращает информацию о том, является ли каждая последовательность непрерывной, а также перечисляет разрывы с указанием их причин. Скрипт `verify.py` выводит те же данные на основе записей архива в разделе **Непрерывность последовательности**.

<a id="missing-message-numbers-gap_summary"></a>
### Отсутствующие номера сообщений (`gap_summary`)

Руководство для читателя по данному разделу, а также по периодам наблюдения и пробелам см. в разделе [Охват и отсутствующие данные](COVERAGE.md).

**Предварительный просмотр.** `coverage.json` → `gap_summary` измеряет номера, присвоенные Telegram, но никогда не зафиксированные данным сборщиком. Telegram нумерует сообщения один раз на канал или супергруппу и один раз на аккаунт во всех личных чатах, ботах и обычных группах. Номер, расположенный между двумя наблюдаемыми сообщениями, либо наблюдается, либо отсутствует; непрерывный диапазон является утверждением о том, что каждое сообщение, пронумерованное в нём, было зафиксировано. Пробел не указывает ни на конкретного участника, ни на причину.

| Поле | Значение |
| --- | --- |
| `status` | `on` или `off`, если функция отключена в разделе **Дополнительные инструменты → Параметры → Анализ пробелов** |
| `parameters` | Параметры, на основе которых был получен результат, что позволяет повторить его |
| `chats[]` | По одной записи на канал или супергруппу, каждая из которых имеет собственный номер |
| `account` | Последовательность личных чатов, ботов и обычных групп по всему аккаунту |
| `status` (для каждой последовательности) | `applicable` или `not_applicable` с указанием `reason` |
| `observed_from`, `observed_to`, `span` | Первый и последний номер, который был зафиксирован при наблюдении, а также размер диапазона |
| `observed`, `observed_without_content` | Наблюдаемые номера; те, которые известны только из записей об удалении или повторной проверке |
| `missing`, `density`, `gap_ranges`, `largest_gap` | Никогда не наблюдавшиеся номера, их доля в диапазоне, количество последовательностей, самая длинная последовательность |
| `clusters[]` | Указанные пробелы: `low`, `high`, `missing` и соседние наблюдаемые числа `after` / `before` с указанием времени их наблюдения |
| `service_estimate` | Только при включенной функции: сколько отсутствующих чисел соответствовало бы служебным сообщениям при их доле во время наблюдения. Никогда не вычитается из числа `missing` |

Действительность определяется на основе журнала, никогда не предполагается:

- **Каналы и супергруппы** измеряются по каждому чату, в том числе при экспорте выбранных чатов. Записи, выбранные отправителем, делают измерение `not_applicable`.
- **Последовательность по всем аккаунтам** измеряется только от первого до последнего сообщения, поступившего в период, когда сбор данных по всем аккаунтам был включён, и учитывает личные чаты, ботов, обычные группы и собственные сообщения аккаунта, при этом ни один из таких чатов не исключается (`scope.changed`). Числа, обозначенные как `deletion.unscoped`, считаются подвергающимися наблюдению без учета содержания. Экспорт или передача выбранных чатов не позволяют измерить этот показатель. Если сбор данных по всем аккаунтам был отключён, а затем снова включён, появляется примечание о том, что использованные в промежуточный период числа отображаются в виде пробелов.
- Сервисные сообщения представляют собой записи журнала со своими собственными номерами, поэтому они самостоятельно заполняют свои пробелы; дополнительная оценка носит исключительно контекстный характер.

Скрипт `verify.py` пересчитывает `gap_summary` на основе файла `events.jsonl` с использованием параметров, указанных в подписанном элементе `coverage.json` (по умолчанию для старых архивов), и выводит строку, охватывающую всю учётную запись, в своём сводном отчёте о покрытии. Функция `get_capture_status`, доступная в архиве (MCP и командная строка), возвращает те же данные для чатов, к которым может получить доступ пользователь; последовательность, охватывающая всю учётную запись, доступна только при доступе, охватывающем всё рабочее пространство. При запросе всех чатов сразу выводится список, содержащий не более 50 каналов и супергрупп без их `clusters[]`, а остальные чаты указываются как `chats_truncated`; для просмотра одного чата в полном объёме необходимо запросить его по `chat_id`. Файл `coverage.json` в архиве с подписью не сокращается.

Повторные наблюдения одного служебного сообщения учитываются один раз, а при оценке обслуживания аккаунта используются только числа, находящиеся в пределах измеряемого диапазона. Применяемый диапазон должен явно сохранять собственные сообщения аккаунта до включения измерения на уровне всего аккаунта; измерение начинается с записей, содержащих эту информацию. Измеряемый диапазон охватывает текущее наблюдение, и его возобновление фиксируется. Запрос к архиву в режиме реального времени имеет временной лимит, включая сканирование базы данных, и помечает незавершённое измерение как частичное.

Telegram документирует [отдельные последовательности идентификаторов сообщений](https://core.telegram.org/api/updates#message-id-sequences). Эти номера описывают наблюдения; уведомления об удалении, повторные проверки и журнал администратора фиксируют причины отсутствия того или иного номера там, где Telegram его указывает.

Когда Telegram прекращает обслуживание аккаунта, запись `coverage.gap`, завершающая наблюдение, содержит `cause` (`account_banned`, `account_frozen`, `account_deleted`, `session_duplicated`, `session_revoked`, `session_expired`, `session_ended` или `not_authorized`) и ошибку Telegram; скрипт `verify.py` указывает причину, по которой заканчивается данный период.

Показатель «Coverage» объединяет зафиксированные периоды наблюдения, перерывы и результаты обработки сообщений. Оценивайте его с учётом выбранных чатов, периода и политики в отношении вложений; результаты повторной проверки и зафиксированные пробелы показывают, насколько полно отслеживались обновления аккаунта.

<a id="producer"></a>
## Разработчик

Подписанный манифест ZIP-архивов с доказательствами, экспортов чатов, журналов свидетелей и файлов с описанием профилей пользователей содержит информацию о `producer`: программное обеспечение, версию, проект (PhishDestroy), домашнюю страницу и репозиторий исходного кода. В отчёте в формате HTML и в верификаторе отображается эта подписанная запись о производителе. Хеши исходных файлов идентифицируют зафиксированное дерево исходного кода для сравнения с доверенной версией. Происхождение выполнения проверяется отдельно с помощью [подтверждения получения данных из GitHub](SEALED-ACTIONS.md) или [измерений Intel TDX](PHALA.md), если они включены. Архивы, созданные до появления поля «производитель», по-прежнему поддерживаются и идентифицируются как устаревшие записи.

Каждая запись `observation.started` также указывает клиент Telegram, который осуществлял наблюдение: его `api_id` (ни в коем случае не хеш), является ли это встроенной публичной парой или собственным приложением оператора, описание клиента, отправленное в запросе на подключение Telegram, а также тип маршрута подключения с указанием режима IP (без прокси-адреса или секретного ключа). В отчёте и файле ``custody.json`` перечислены все уникальные клиенты и маршруты с указанием времени их регистрации, а также моменты, когда ни один из перечисленных прокси не ответил и Telegram получил адрес сервера. Журналы, записанные до этого, содержат соответствующие сведения.

<a id="people-profiles"></a>
## Профили пользователей

Файл профиля (`tgwitness-dossier-v1`, JSON) формируется по запросу на основе записей, уже имеющихся в журнале для одного чата; никакие данные не извлекаются из Telegram, а содержимое профиля никогда не записывается в журнал (включение и выключение профилей фиксируется как `dossier.changed`). Для каждого пользователя, у которого сохранены сообщения, в файле указаны имя и история имена пользователя, флаги Telegram (бот, мошенничество, фейк, премиум, подтверждённый, ограниченный доступ, удалённый) на момент сохранения, идентификаторы фотографии профиля, SHA-256 и перцептивный хеш (pHash, совместимый с `imagehash.phash`) аватара из локального кэша аватаров с похожими аватарами, активность (первое и последнее сообщение, количество сообщений, отредактированные и удалённые публикации, сообщения по часам UTC), кто кому отвечает, другие чаты в данном журнале, в которых данное лицо писало, а также упомянутые кошельки (BTC, EVM, TRON, TON, LTC, DOGE, XMR, SOL; адреса в формате Base58Check проходят проверку контрольной суммы), номера телефонов, имена пользователей и ссылки, включая ссылки, скрытые за текстом.

Каждый факт содержит список записей журнала (`seq`), из которых он происходит, а `record_hashes` хранит хеш каждой упомянутой записи. Заявление подписано ключом рабочей области:

```sh
python verify.py tgwitness-dossier-CHAT.json --fingerprint TRUSTED_SHA256 --evidence tgwitness-evidence.zip
```

проверяет подпись, удостоверяет сам экспорт доказательств (подпись, цепочку хешей и файлы), а также наличие каждой упомянутой записи в неизменённом виде в этом экспорте той же рабочей области. Хэши аватаров помечены как полученные из локального кэша (а не из записей журнала). Упоминания представляют собой совпадения по шаблону и служат поводом для проверки. Профили включаются для каждого чата отдельно, могут экспортироваться в виде ZIP-архива с шифрованием AES-256 и паролем, а также удаляются при отключении или при удалении чата из источников.

<a id="independent-witness"></a>
## Независимый свидетель

Журнал свидетеля (`tgwitness-witness-v1`) и его сообщения в канале проверяются на соответствие экспорту доказательств с помощью команды `verify.py --witness … --channel …`; см. раздел [Независимый свидетель](WITNESS.md). При наличии публичного адреса `https://t.me/s/…` или `https://telegram.me/s/…` верификатор считывает дату каждого сообщения из Telegram, и самая ранняя такая дата сообщения в начале экспорта служит внешним временем для последней записи. Даты из любого другого источника являются предоставленными метаданными.

<a id="manifest-and-checkpoints"></a>
## Манифест и контрольные точки

Файл `manifest.json` содержит формат, время экспорта, открытый ключ, отпечаток, длину журнала, хеш вершины журнала, область действия, создателя, ограничения, а также SHA-256 каждого элемента содержимого, кроме самих файлов ``manifest.json`` и ``manifest.sig``. Файл `manifest.sig` представляет собой подпись Ed25519 в кодировке base64, наложенную на канонический JSON-манифест. Верификатор отклоняет неожиданные или отсутствующие элементы, дубликаты имен, повреждённые файлы, нарушенную последовательность или цепочку, недействительные подписи, а также несоответствие предоставленной контрольной точке. Он никогда не извлекает пути к файлам в архиве. Общий объявленный размер в несжатом виде ограничен 4 ГиБ; параметр ``--max-gib N`` позволяет создавать архивы большего размера при повышении предельного значения в разделе **Дополнительные инструменты → Параметры**.

Крупный архив проверяется сразу несколькими процессами: элементы хешируются параллельно, и после первых 5 000 записей хеш содержимого и подпись каждой записи проверяются рабочими процессами, в то время как главный процесс последовательно отслеживает цепочку, охват и привязки. Параметр `--jobs N` устанавливает количество процессов; значение по умолчанию `auto` использует по одному процессу на каждый процессор (не более 16), а параметр `--jobs 1` выполняет всю обработку в одном процессе. Результат в обоих случаях одинаков, а изменение отклоняется с одинаковым сообщением. Хеши в позициях, указанных сохраненными контрольными точками и анкерами временных меток, сохраняются в течение этого единственного прохода, поэтому каждый анкер сравнивается без повторного чтения журнала. На компьютере с 32 потоками обработка архива объёмом 10,8 ГБ, содержащего 400 000 записей, заняла 58,9 с в одном процессе, 15,2 с при использовании 4 процессов и 8,4 с при использовании 16; один проход по записям в порядке их расположения затем устанавливает предельное время.

Запустите проверку из установленной версии TgWitness или из проверенной копии. Копия, включённая в архив, поддерживает переносимое использование; перед запуском сверьте эту копию с вашей проверенной установкой.

Контрольная точка подписывает заявление, содержащее открытый ключ, длину журнала, хеш вершины и время создания. Он также содержит самый последний раунд drand, полученный рабочими областями (`drand_anchor`): перед каждой периодической контрольной точкой сборщик запрашивает ретранслятор drand через внешний маршрут рабочих областей, поэтому применимы такие механизмы, как Hide IP, прокси-серверы и отключенный внешний маршрут, в результате чего сама контрольная точка никогда не устанавливает внешнее соединение. Верификатор может проверить, содержит ли более поздний архив тот же префикс. С помощью параметров `--checkpoint` и `--check-drand` он подтверждает этот раунд с помощью ретрансляторов drand и сообщает, что контрольная точка была подписана не ранее времени данного раунда; раунд не изменяет уровень гарантии. Храните контрольную точку вне сборщика, чтобы при последующей верификации архив сравнивался с эталонной копией, хранящейся отдельно от него. Ключ сборщика подписывает её, поэтому она связывает записи с ней только в том случае, если получатель получил её до получения архива через другой канал; сама по себе она не соответствует минимальным требованиям к доказательству.

<a id="reading-a-verification-result"></a>
## Чтение результата проверки

Верификатор отдельно сообщает о целостности архива, привязке подписавшего и проверках уровня достоверности. Действительная подпись свидетельствует о том, что байты не изменились с момента подписания. Оператор передаёт отпечаток ключа получателю по отдельному каналу. Без параметра `--fingerprint` неповреждённый архив проходит проверки подписи и формата с параметром `signer_pinned: false`, а заключительная строка начинается со слова `EVIDENCE: minimum not met · missing: confirmed signer key`.

Для автоматизированной политики локального архива, требующей привязанного подписавшего и соблюдения минимальных требований к доказательствам:

```sh
python -m tgwitness.verify evidence.zip --strict --json --fingerprint TRUSTED_KEY_SHA256 --tsa-ca TSA-ROOT.pem --require evidence
```

Используйте отпечаток, сохраненный через доверенный канал получателя. Доверенный свидетель также может закрепить сборщик с помощью согласованного журнала, заверенного свидетелем; укажите параметры `--witness`, `--witness-fingerprint` и `--require-witness`. Параметр `--strict` приводит к завершению работы со статусом 2 в случае незакреплённого подписанта; невыполнение требований `--require-tier` или `--require evidence` также приводит к завершению работы со статусом 2. Параметр `--require evidence` требует наличия параметра `--fingerprint` и внешнего времени от третьей стороны, охватывающего последнюю запись. Ознакомьтесь с параметрами `signer_pinned`, `requirements_met` и результатами проверки достоверности, а не только с кодом завершения. Вместо этого в режиме [запечатанного получения](../TRUST.md#sealed-evidence) для аутентификации дайджеста получения используется собственный верификатор подтверждения и утверждённая политика.

<a id="verification-scope"></a>
## Объём проверки

Проверка охватывает архив и режим сбора, использованный для его создания. Выберите режим, граница доверия которого соответствует данному случаю, а затем сохраните его входные данные для проверки.

| Режим сбора | Что проверяет верификатор | Входные данные для проверки и граница доверия |
| --- | --- | --- |
| Локальная рабочая область | Подписи записей, цепочка хешей, манифест и байты вложений | Отпечаток сборщика, сохраняемый получателем, и внешнее время от третьей стороны: проверенные квитанции по стандарту RFC 3161 или OpenTimestamps, либо записи свидетелей, прочитанные с t.me. Сохраненные контрольные точки и записи свидетелей служат в качестве вспомогательных проверок |
| Локальная рабочая область с независимым свидетелем | Проверки архива плюс согласованность с более ранним префиксом журнала, хранящимся у свидетеля | Отпечаток и записи свидетеля; запись о контроле ключей хранителя показывает, кто владеет ключом свидетеля. При использовании параметра `--channel https://t.me/s/…` даты, установленные Telegram для сообщений, служат внешним временным отметкам |
| [Запись с помощью GitHub Actions](SEALED-ACTIONS.md) | Аттестация GitHub: дайджест архива, утвержденные коммиты рабочего процесса и сборщика, размещённый запускающий модуль, новый источник сеанса/ключа и целостность внутреннего архива | Политика доверенного верификатора, репозиторий вызывающей стороны и пакет подтверждений GitHub; сбор данных выполняется в рамках закреплённого рабочего процесса |
| [Развертывание в облаке](HIGH-ASSURANCE.md) | Записи о жизненном цикле и доступе провайдера, состояние брандмауэра и Cloudflare, а также подписанная запись о запуске сборщика | Запросы только для чтения к провайдеру и Cloudflare; доступность отдельных проверок зависит от провайдера |
| [Конфиденциальная виртуальная машина Intel TDX](PHALA.md#confidential-vm-on-phala-cloud-intel-tdx) | Подпись цитаты и статус платформы, привязка к заявлению сборщика, составные показатели и измерения ОС | Цепочка доверия Intel и ожидаемые показатели развертывания; сохранение результатов каждой обязательной проверки TDX |

При «запечатанном» сборе данных утверждённый сборщик получает данные через аутентифицированное соединение Telegram внутри проверенной среды. Аттестация привязывает архив к данному запуску, поэтому проверка охватывает как сам процесс сбора, так и последующую целостность файлов. Это основано на утверждённом коде и цепочке доверия платформы, перечисленных выше. Проверка записей с GitHub требует сеанса, созданного в рамках данного запуска, и отклоняет записи, импортированные из других сеансов.

В квитанции запуска фиксируются версия сборщика, хеши файлов и настройки запуска. Проверка происхождения GitHub и показатели TDX обеспечивают проверку среды; [запись валидации](VERIFICATION.md) идентифицирует протестированные конфигурации.

<a id="where-the-messages-come-from"></a>
### Откуда поступают сообщения

Telegram доставляет сообщения каждому клиенту, включая официальные приложения, в рамках сеанса MTProto. Ключ авторизации сеанса согласовывается с закреплённым серверным ключом Telegram, и каждое обновление поступает в зашифрованном виде с проверкой целостности с использованием этого ключа. Сборщик получает сообщения через аутентифицированный сеанс аккаунта и регистрирует каждое наблюдение в журнале по мере его поступления, указывая идентификаторы чата, сообщения и отправителя, а также дату, установленную Telegram для каждого сообщения. В развертываниях GitHub Actions и Intel TDX аттестация также связывает данную сессию и ключ подписи с утверждённым запуском сборщика.

В журнале фиксируется источник ключа авторизации. При входе в систему с помощью телефона или QR-кода, а также при независимом входе из файла сеанса в поле ``account.authorized`` записывается значение ``key_origin: "created"``; при сборе данных на основе импортированного файла ``.session``, объекта `TData` или ключа JSON записывается значение ``imported``. Импортированный ключ также существует независимо от источника его происхождения. Развертывания с аттестацией отклоняют импортированные ключи.

Происхождение записи из Telegram подтверждается на основе аутентифицированного подключения аккаунта, записей о подключении и сборе данных в журнале, захваченных кадров MTProto, сопоставленных с записями журнала ([`tgwitness/forensics/`](../../tgwitness/forensics)), даты отправки каждого сообщения в Telegram, а также — в случае заверенного сбора данных — проверенной среды выполнения. Подписи архива сохраняют данную запись для последующей проверки. Сохраненные контрольные точки фиксируют пределы более ранних журналов, записи об охвате показывают результаты сбора, а проверенные внешние временные метки позволяют определить момент фиксации байтов во времени.

Для локальной рабочей области получатель предоставляет данные от доверенного сборщика или свидетеля. В случае запечатанного сбора данных доверенная политика и аттестация связывают дайджест архива с утвержденным выполнением сборщика. Это различные пути проверки; сообщите о завершении проверок для выбранного пути.

<a id="attachments"></a>
## Вложения

Файлы идентифицируются с помощью SHA-256 в каталоге медиафайлов. Событие media.saved связывает хеш и длину в байтах с конкретным событием сообщения. Исходные имена файлов являются метаданными, а не локальными путями. Байты медиафайлов загружаются асинхронно, поэтому немедлённое удаление может помешать их фиксации. В качестве результатов отображаются: отключённый сбор данных, файлы превышающие допустимый размер или с неизвестным размером, сбои при загрузке и прерванные загрузки. Сбой процесса может привести к появлению неимеющих ссылок неполных файлов; они не включаются в экспортируемые данные.

Экспортер в формат ZIP использует верификатор для проверки сохраненных медиафайлов по их именам. Экспорты в форматах JSONL, CSV и HTML проверяют сигнатуры событий, но не содержат байтов медиафайлов. Производные отчёты служат для удобства; файл events.jsonl является авторитетным представлением событий.

При полном экспорте чата вложения сохраняются в соответствии с настройками вложений рабочей области в папке медиафайлов с именами, сформированными на основе SHA-256. Каждая запись сообщения в файле chat.json содержит название файла (`file`, `file_sha256`) или причину его отсутствия (`file_status`), а также информацию о том, что пользователь видел вокруг текста: ссылки, расположенные за текстом, источник пересылки, кнопки ботов, подпись, количество просмотров и таймер автоматического удаления. Скрипт `verify.py` проверяет, что каждый указанный файл присутствует в подписанном манифесте под соответствующим хешем.

<a id="durable-collection-and-process-receipts-02"></a>
## Надежное хранение и обработка квитанций (0.2)

Обработка медиафайлов и фиксация события сообщения выполняются в рамках одной транзакции. Задание сохраняет исходный дескриптор сообщения TL; подписанное наблюдение связывает его SHA-256, аккаунт и политику размера. При восстановлении эта привязка проверяется перед загрузкой. Система никогда не извлекает текущее сообщение и незаметно заменяет его более новым вложением. Прерванные задания повторяются, тогда как постоянный сбой остаётся явным результатом.

Каждая рабочая область имеет собственный журнал и идентификатор подписи. Событие process.started содержит идентификатор запуска, данные локальных часов, версии зависимостей, хеши исходных файлов, исходные аккаунты/область действия, а также настройки захвата. Сигналы пульсации включают идентификатор запуска, монотонное время и состояние очереди. Квитанцию о запуске также можно загрузить в виде отдельно подписанного отчета. Для проверки среды выполнения используйте её в сочетании с аттестацией GitHub или проверками TDX, описанными в [разделе Область проверки](#verification-scope).

Автоматические контрольные точки сохраняются локально при запуске, каждые пять минут в ходе наблюдения (**Дополнительные инструменты → Параметры → Подписанная контрольная точка каждые**) и при упорядоченной остановке. Проверка при запуске и экспорт сравнивают журнал с последней сохраненной локальной контрольной точкой. Это позволяет обнаружить откат базы данных, если контрольная точка сохранилась. Независимое хранение обеспечивает доступность этой ссылки за пределами рабочей области; проверенная внешняя временная метка дополнительно фиксирует её во времени.

После перезапуска возобновляется сохраненная позиция обновлений Telegram (`catch_up_from` в `observation.started`), и запрашиваются пропущенные обновления. Сохраненная позиция охватывает только те обновления, обработка которых завершилась, поэтому обновления, которые всё ещё находились в ожидании на момент разрыва соединения или остановки процесса, запрашиваются повторно. Периодическая повторная проверка фиксирует значение ``message.recovered`` для пропущенных сообщений и ``message.missing_on_recheck``, когда Telegram больше не возвращает сохраненное сообщение; последнее значение не является уведомлением об удалении и не указывает ни удаляющего пользователя, ни время.

<a id="off-site-copy-and-restore-s3"></a>
### Внешняя копия и восстановление (S3)

Внешняя копия (**Настройки → Уведомления и внешняя копия → Внешняя копия** или **Дополнительные инструменты → Дополнительные функции → Доказательства и резервные копии**; по умолчанию отключена) загружает сегменты журнала, сохраненные файлы, контрольные точки с их временными метками и готовые экспорты чатов в хранилище, совместимое с S3; данные шифруются с помощью алгоритма AES-256-GCM перед загрузкой с использованием ключа, хранящегося в хранилище рабочей области; функция Object Lock применяется, если корзина поддерживает эту функцию. Без загруженного ключа копию невозможно прочитать. Восстановление и проверка выполняются с помощью команды ``python -m tgwitness.replica restore --key-file KEY.json --out DIR``.

Для восстановления требуется пустой обычный каталог. Загруженные и расшифрованные объекты остаются в частном временном хранилище до тех пор, пока не будет проверен весь журнал и каждая сохраненная контрольная точка. Небезопасные пути к объектам, несогласованные диапазоны сегментов и журналы, короче контрольной точки, отклоняются; в случае неудачной проверки восстановленные файлы не публикуются. Проверки срока хранения сравнивают возвращаемый режим блокировки объекта и дату с крайним сроком, отправленным при загрузке (допуск на округление составляет одну секунду). Истекший, недействительный или сокращённый крайний срок не считается подтверждённым. Статус указывает на выборочный объект, срок хранения которого был считан обратно для данного прохода загрузки.

Отсутствие или повреждение медиафайлов фиксируется как ошибка данного цикла и курсор медиафайлов останавливается перед ним, благодаря чему попытка восстановления медиафайлов повторяется в следующем цикле; медиафайлы, контрольные точки и экспортированные данные, расположенные после этого места, по-прежнему копируются. Проверка восстановления сравнивает все ссылки на сохраненные медиафайлы с расшифрованными хешами и записанными размерами. Идентичные перекрывающиеся сегменты журнала из прерванных загрузок дедуплицируются; конфликтующие перекрытия отбрасываются. Контрольные точки, созданные во время загрузки, откладываются до тех пор, пока не будут скопированы охватываемые ими записи журнала, поэтому завершённый проход не публикует контрольную точку раньше, чем соответствующая ей запись в журнале.

<a id="streaming-export-snapshots"></a>
### Снимки потокового экспорта

Потоковый экспорт использует стабильный снимк чтения SQLite. Его начало может оказаться более старым, чем текущий активный журнал, к моменту завершения загрузки. Контрольная точка, созданная после этого снимка, может правильно указать, что архив стал короче; сравнивайте с контрольной точкой, расположенной на уровне экспортируемого префикса или перед ним, а не с произвольной более поздней контрольной точкой.

<a id="rfc-3161-preparation-and-response-verification-02"></a>
## Подготовка в соответствии с RFC 3161 и проверка ответов (0.2)

Режим «Доказательства» отправляет только SHA-256 каждой подписанной контрольной точки перечисленным авторитетам RFC 3161 и календарям OpenTimestamps по маршруту рабочей области и никогда через MTProxy. Отметки времени включены по умолчанию в каждой цели настройки; **доказательства для конкретного случая** также фиксируют drand. Ответы хранятся в папке `checkpoints/anchors/`, экспортируются в виде файлов `.tsr` и `.ots` в папке `anchors/` и проверяются с помощью скрипта `verify.py` (опция `--tsa-ca` проверяет подпись TSA; подтверждение доказательств OpenTimestamps осуществляется с помощью команд `ots upgrade` и `ots verify`).

Авторитет RFC 3161, давший сбой два раза подряд, выжидает перед следующей попыткой: один интервал, затем два, четыре и так далее до шести часов или столько, сколько указано в его параметре ``Retry-After``, но не более одного дня. При прохождении проверки, в ходе которой обнаруживаются только ожидающие авторитеты, запись не создаётся; в противном случае файл `anchor.completed` перечисляет их в разделе `deferred` с указанием `retry_at`. До тех пор, пока они не ответят вновь, панель отображает временные метки как **Degraded**.

Панель подготавливает архив запросов, содержащий канонические байты файла checkpoint.json, отпечаток сообщения SHA-256 и случайный нонс в файле timestamp.tsq, а также контрольные суммы и инструкции. Сетевые запросы не отправляются; токеном, возвращаемым центром сертификации в ответ на данный запрос, является временная метка.

Команда ``python -m tgwitness.anchor verify`` проверяет ответ на соответствие байтам контрольных точек и исходному запросу без использования OpenSSL. Требуется явно указать файл доверенного центра сертификации; включённые сертификаты не считаются доверенными автоматически. Проверка запроса в командной строке является опциональной, поэтому для проверки нонса необходимо сохранить и указать параметр `--request`. Результат указывает, была ли проверка выполнена. Подпись контрольной точки сборщика и журнал по-прежнему необходимо проверять отдельно с помощью доверенного отпечатка сборщика.

В ходе проверки проверяются подпись ответа, байты контрольной точки и, при наличии, исходный запрос в соответствии с указанным доверием к ЦС. Для временных меток, полученных в режиме «Доказательства», команда ``verify.py`` также проверяет сохраненные доказательства OCSP или CRL ([отзыв сертификата подписи](TIMESTAMP.md#signing-certificate-revocation)). Ознакомьтесь с [процедурой](TIMESTAMP.md) и [результатами проверки](VERIFICATION.md).

<a id="optional-records-in-evidence-mode-drand-and-telegram-devices"></a>
## Дополнительные записи в режиме «Доказательства»: устройства drand и Telegram

Ещё две записи могут обрабатываться в тех же проходах, что и временные метки. Обе вступают в силу только при включённом режиме «Доказательства». Включение **режима сбора доказательств для конкретного дела** активирует drand; в противном случае обе функции запускаются по умолчанию. Переключайте их в разделе «Дополнительные инструменты» → «Дополнительные функции» → «Доказательства и резервные копии» → **Дополнительные свидетели · опционально** или с помощью параметров `"drand": true` и `"devices": true` в запросе `POST /api/evidence`. Сбой в работе одной из них не останавливает работу другой или генерацию временных меток; панель отображает последние результаты каждой из них под формой.

**drand** (`beacon.drand`). Каждый проход записывает в журнал новейший раунд drand quicknet — публичную генерацию случайных чисел от League of Entropy (один раунд каждые 3 секунды): `chain`, `round`, `randomness`, `signature`, `round_time` и `relay`, ответивший на запрос. Проверенный непредсказуемый раунд служит нижней временной отметкой для последующих данных, связанных хешами. Проверенная временная метка на более поздней контрольной точке служит верхней временной отметкой. Эти проверки ограничивают временной диапазон связанных данных. Сборщик сначала обращается к `drand.cloudflare.com`, а затем к ретрансляторам Protocol Labs через маршрут рабочей области, по одному запросу на каждый проход.

Скрипт `verify.py` проверяет, что каждый элемент случайности является SHA-256 его подписи и что время раунда верно, а также сообщает о раундах, самом длинном отрезке без раунда и о том, насколько часы сборщика отставали от drand. `--check-drand` сравнивает раунды с ретранслятором Cloudflare и ретранслятором Protocol Labs — либо со всеми из них, либо со случайной выборкой из 100 записей в длинном журнале; раунд, который отличается, не проходит проверку.

**Устройства Telegram** (`account.devices`). При каждом проходе с помощью `account.getAuthorizations` считываются сеансы аккаунта — список, отображаемый Telegram в разделе «Настройки» → «Устройства», — и фиксируются: в полном виде, если с момента предыдущего прохода произошли изменения, с указанием хешей `added` и `removed`; в противном случае — только их количество и SHA-256. Сохраняются модель устройства, платформа, приложение и его версия, дата создания и последней активности, страна и регион; IP-адреса не сохраняются, поскольку экспорт доказательств выходит за пределы вашего контроля. Собственная сессия сборщика активна постоянно, поэтому в качестве изменения учитывается только активность других сеансов. Скрипт ``verify.py`` сообщает о частоте записи списка, а также о каждой новой и завершённой сеансе. Он считывает список только во время работы процесса наблюдения.

Что они показывают: drand упорядочивает записи в соответствии с общедоступным временем, а список устройств представляет собой отчёт Telegram, проходящий через сборщика и подписанный им, как и любая другая запись.

**Журнал Cloudflare Gateway** (`cloudflare.gateway_dns`). Для сервера, который осуществляет разрешение через Cloudflare Gateway ([Gateway DNS](HIGH-ASSURANCE.md#cloudflare-as-an-outside-witness)), при каждом проходе копируется то, что Gateway зарегистрировал с момента предыдущего копирования: одна запись на каждый интервал продолжительностью не более трёх часов с указанием `from`, `until`, `location_id`, `address` сервера (если он задан) и `queries` в формате `[at, name, type, rcode, decision, colo]`, в том числе в случае их отсутствия. Укажите следующие данные в разделе **Журнал Cloudflare Gateway**: аккаунт, местоположение, адрес (по желанию) и токен только для чтения (Account Analytics Read; Zero Trust PII Read для сохранения одного адреса из общего местоположения). Панель проверяет эти данные с помощью одного запроса перед сохранением; токен остаётся зашифрованным и никогда не попадает в журнал. Скрипт ``verify.py`` выводит список интервалов, наиболее часто запрашиваемые имена, а также периоды, не охваченные ни одной копией; запись, количество запросов в которой не совпадает с количеством запросов, считается неудачной. Интервал, содержащий более одной страницы запросов за одну секунду, сохраняет эту страницу и указывает, что остальная часть отсутствует. Копия представляет собой ответ Cloudflare, полученный через сборщика и подписанный им; в течение 24 часов любой пользователь, обладающий токеном только для чтения, может сравнить её с данными Cloudflare.
