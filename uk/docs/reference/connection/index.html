Довідка / Налаштування

Підключення, проксі-сервери та захист даних

Аутентифікація, автоматичні пули проксі-серверів, режими IP, політика резервного переходу, зовнішні запити та зберігання секретних даних.

Цей документ описує поведінку TgWitness 0.8.0 та її обмеження. Аутентифікація, доступ до джерел, мережеве з’єднання та повнота збору даних — це окремі стани. Щоб дізнатися про етапи входу, формати файлів та роботу з кількома обліковими записами, почніть з розділу «Облікові записи та формати сеансів». Щодо політик подій та поведінки при перезапуску див. розділ «Як працює збір даних».

Покрокове налаштування з’єднання#

У «Підключення» адміністратор може вибрати «Цей обліковий запис» , «Група облікових записів» або «Усі облікові записи» , а потім вибрати маршрут. «Переглянути вибір» відображає список облікових записів, яких це стосується. «Підготувати та перевірити» перевіряє запропонований маршрут, не змінюючи збережений. «Застосувати перевірене підключення» перевіряє ще раз, призупиняє спостереження, якщо це необхідно, зберігає маршрут і відновлює спостереження, яке вже виконувалося. Збір даних ніколи не розпочинається на обліковому записі, який раніше перебував у неактивному стані. Завантаження історії залишається призупиненим і може бути відновлено окремо. Перед перемиканням слід призупинити активні експорті.

Зміни в групі за замовчуванням зберігають облікові записи з їхнім власним маршрутом. Скасуйте цю опцію лише тоді, коли у попередньому перегляді відображаються саме ті зміни, які ви плануєте. Додаток повідомляє про результат для кожного облікового запису окремо; це не транзакція типу «все або нічого» між базами даних. У разі невдалого перемикання для цього облікового запису відновлюються попередні налаштування. Неможливість відновлення відображається явно. Термін дії попереднього перегляду закінчується через десять хвилин, а зміни в налаштуваннях з’єднання або членстві в групі вимагають нової перевірки.

Маршрут Що управляє TgWitness
Прямий Підключення з хосту; VPN зовнішнього хосту не виявлено та не застосовується.
VPN Один профіль WireGuard із повним тунелем на кожен обліковий запис, що виконується локальним процесом SOCKS5 у просторі користувача. Жодних мережевих інтерфейсів чи драйверів не встановлено.
Мій проксі-сервер Повноваження SOCKS5, HTTP CONNECT або MTProxy. У поля SOCKS5/HTTP можна ввести URL-адресу. При виборі декількох облікових записів цей введений проксі-сервер використовується для всіх них.
Публічний MTProto Існуючий пул призначає маршрути Telegram. Зовнішні запити відключені, доки в розширених налаштуваннях не буде налаштовано окремий відповідний проксі-сервер.
WARP Окремий локальний тунель для кожного вибраного облікового запису, з реєстрацією WARP та профілем WireGuard, що зберігається у сховищі цього облікового запису.

Перевірка поточного маршруту використовує новий неавтентифікований транспорт Telegram, а не сесію облікового запису. Для маршрутів, що підтримують HTTP, також запитується HTTPS-трасування Cloudflare через цей маршрут і відображаються повідомлені вихідна IP-адреса, країна, стан WARP та час перевірки. Виміряна затримка — це час встановлення з’єднання Telegram, а не ICMP-пінг. Підготовка WARP завершується невдало, якщо трасування не повідомляє про активний стан WARP. Ці перевірки встановлюють наявність з’єднання, а не автентичність чи повноту зафіксованих повідомлень. Сам по собі запущений локальний процес не є успішною перевіркою виходу.

Портативні WARP та WireGuard#

Це неофіційна інтеграція WARP з використанням wgcf 2.3.1 та wireproxy 1.1.3 . Адміністратор явно погоджується на налаштування перед першим завантаженням або реєстрацією в WARP. Ці з’єднання для налаштування встановлюються безпосередньо з GitHub та Cloudflare і розкривають IP-адресу пристрою. Трафік звичайного облікового запису зберігає існуючий маршрут до запуску програми. Cloudflare обирає вихідну адресу та країну; окремі тунелі можуть використовувати одну вихідну адресу. Ця функція не підтримує вибір країни, періодичну ротацію IP-адрес та загальний для хосту VPN-kill-switch.

Підтримувані версії допоміжних програм для завантаження: Linux та macOS x86-64/ARM64, а також Windows x86-64. Артефакти перевіряються на відповідність хешам SHA-256, що містяться у перевіреному вихідному коді, а кешовані виконувані файли перевіряються ще раз перед запуском. Жодна допоміжна програма не додається до PATH, не встановлюється як системна служба та не має загальнодоступного прослуховувача. Усі файли знаходяться у каталозі portable-routes/ робочої області та у зашифрованих записах сховища. Для прослуховувача з петлевим підключенням SOCKS5 потрібні незалежно згенеровані облікові дані.

Приватні профілі та облікові дані облікового запису WARP шифруються за допомогою існуючого сховища робочого простору. Під час роботи допоміжній програмі потрібен конфігураційний файл у вигляді відкритого тексту, доступний лише власнику; він видаляється при звичайному завершенні роботи. Збій хоста може залишити цей файл у папці даних, доступній лише власнику. Це не шифрує диск і не захищає від його адміністратора. Супервізор закриває тунель, якщо батьківський канал панелі зникає. Тунель, що зазнав збою, ніколи не вмикає прямий резервний варіант. Перезапуск панелі відновлює вибраний тунель; невдалі запуски повторюються з обмеженою затримкою. Зупинити тунель також призупиняє спостереження та зберігає стан зупинки. Запустити тунель запускає тунель; відновити спостереження окремо, коли будете готові.

Завантажені профілі WireGuard повинні містити один інтерфейс та один пір, повні маршрути IPv4 та IPv6, а також не містити хуків, включень, підстановок змінних середовища чи додаткових слухачів. Адреси публічних кінцевих точок визначаються та фіксуються перед запуском. Використовуйте зовнішній VPN або шлюз SOCKS5 для OpenVPN/IPsec та приватних кінцевих точок.

Методи автентифікації#

Ідентифікатор API та хеш API ідентифікують додаток; вони не замінюють дані для входу в обліковий запис. У TgWitness їх використання є необов’язковим. Пріоритет: спочатку пара, введена у форму, потім — з імпортованого JSON-файлу облікового запису, потім — пара, збережена в робочій області, а потім — вбудований пул із 50 публічних пар, які перевіряються у випадковому порядку з автоматичною ротацією, коли Telegram відхиляє одну з них. Лише пара Telegram Desktop (2040) надсилається разом із відповідним описом клієнта Telegram Desktop. Вашу власну пару з Інструментів розробки API на my.telegram.org можна використовувати з усіма вашими обліковими записами; кожен обліковий запис все одно має власну авторизацію.

Telegram обирає доставку коду; доставка SMS не гарантується. Хеш API не може відновити скасовану сесію або замінити забутий пароль 2FA. TgWitness не зберігає коди входу або пароль 2FA Telegram на диску.

Для приватного джерела обліковий запис повинен уже мати доступ. Ім’я користувача групи не потрібне. Проксі або імпорт сеансу не надають ані членства, ані прав адміністратора. Поточне членство не гарантує доступу до історії до приєднання.

Імпортувати файл сеансу Telethon#

Telethon SQLite, Pyrogram SQLite та Telegram Desktop TData використовують різні формати. Панель виявляє та конвертує підтримувані структури; перейменування файлу не є конвертацією. Виберіть одну сесію та відповідний файл JSON у розділі «Файли», а потім натисніть «Підключити обліковий запис». Приймається до чотирьох відповідних файлів загальним обсягом до 8 МіБ. Детальніше див. обмеження форматів для TData/JSON. Функція відновлення пароля відсутня. Вхід за допомогою телефону/2FA або QR-коду створює окрему авторизацію.

Додатковий шлях командного рядка, доступний лише для Telethon, залишається у використанні:

  1. Зупиніть роботу клієнта, який використовує оригінальну сесію, і створіть її точну копію. Конвертер відхиляє файли з незавершеним WAL/журналом. Належним чином закрийте оригінальний клієнт, замість того щоб видаляти ці файли, щоб обійти перевірку.
  2. У середовищі TgWitness виконайте:
python -m tgwitness.sessions account.session --out account.tgwitness-session
  1. У розділі «Додати обліковий запис» → «Файли» завантажте результат або вставте його рядок і продовжуйте.
  2. Перевірте відображений числовий ідентифікатор облікового запису, виберіть джерела та розпочніть спостереження.

Перетворений файл є незашифрованим секретом доступу до облікового запису. Зберігайте його в захищеному сховищі та ніколи не заносьте його у репозиторій і не надсилайте стороннім сервісам конвертації. TgWitness зберігає авторизовану сесію у своєму зашифрованому сховищі. Копіювання сесії не створює окремої авторизації: не запускайте одночасно клієнти з клонованими ключами авторизації та не розраховуйте на незалежну доставку оновлень.

Конвертація передає авторизацію, а не оригінальні повідомлення, кеш об’єкта чи постійний курсор оновлення. Вона не забезпечує відновлення оновлень після перезапуску процесу.

MTProto, Telethon та проксі-сервери#

MTProto — це протокол Telegram. Telethon — це клієнтська бібліотека на Python, яку використовує TgWitness. MTProxy — це транспортний проксі-сервер Telegram; SOCKS5 та HTTP CONNECT забезпечують загальні тунелі. Жоден із них не замінює аутентифікацію облікового запису.

Збережіть маршрут для кожного робочого простору в меню «Акаунт» → «Налаштування» → «Налаштування з’єднання» → «Змінити маршрут з’єднання» перед входом у систему. Для нових робочих просторів за замовчуванням встановлено режим «Автоматичний» MTProxy · публічні списки з опцією «Приховати адресу». Існуючі робочі простори, які явно використовували режим «Прямий», зберігають режим, що це дозволяє.

Режими IP#

Маршрут визначає тип з’єднання. Режим IP, а саме налаштування захисту IP у розділі «Акаунт» панелі управління, визначає, коли адреса сервера може бути розкрита. Ці налаштування не встановлюють VPN і не перенаправляють весь трафік пристрою.

Режим Telegram Зовнішні запити
Приховати адресу (hide) Використовуйте проксі-сервер; якщо жоден не працює, зачекайте. Прямого альтернативного варіанту немає. Вимагає SOCKS5/HTTP; відхиляє запити без відповідного проксі-сервера.
Direct — як крайній захід (fallback) Автоматичний MTProxy може використовувати Direct після налаштованої затримки, а потім повернутися до робочого проксі-сервера. Бажано використовувати налаштований зовнішній проксі-сервер або маршрут SOCKS5/HTTP облікового запису; в іншому випадку допускається використання Direct.
Сервер, розташований за тунелем або VPN (tunnel) Дозволено використання прямих маршрутів та негайного автоматичного переходу на резервний пул. Прямий доступ дозволено, якщо не налаштовано відповідний проксі-сервер.

Режим тунелю або VPN передбачає, що ви керуєте цією мережею окремо. Без діючого тунелю адресати можуть бачити власну адресу сервера. Обирайте режим відповідно до вашої фактичної мережі, а не за назвою опції.

Публічні проксі-сервери, що надаються вашою інсталяцією#

Вбудований список об’єднує чотири джерела: SoliSpirit/mtproto, zakky8/mtproto-proxy-pro, kort0881/telegram-proxy-collector та 3yed-61/MTP-Collector. У комплекті знімка містяться дані про кінцеві точки, атрибуцію джерел та дати завантаження. Наявність провайдера у списку не є доказом того, що проксі працює або передає кожне оновлення Telegram.

MTProxy автоматично перевіряє зв’язок із транспортною мережею Telegram, підтримує робочий проксі-сервер і перемикається на інший у разі його збою. Робочі простори віддають перевагу різним проксі-серверам, коли є достатня кількість робочих записів; унікальна вихідна адреса не гарантується. Проксі, що вийшли з ладу, відпочивають перед черговою спробою. Якщо жоден не працює, режим IP визначає, чи збір даних повинен чекати, чи можна використовувати пряме з’єднання. Зміна проксі не змінює обліковий запис і не стирає його журнал. Вибір маршрутів та зміни фіксуються у підписаному журналі.

Поки автоматичні маршрути активні, списки оновлюються щогодини, а перевірки трафіку виконуються за замовчуванням кожні десять хвилин. Ці інтервали можна налаштувати. Оновлення публічних списків вимагає оновлення; сам перегляд списку не змінює збережений ручний маршрут.

Трафік Telegram та HTTPS-запити використовують різні маршрути. Завантаження списків використовують окреме HTTPS-з’єднання та наданий маршрут зовнішніх запитів. «TGWITNESS_PROXY_FEED_PROXY» явно замінює цей маршрут проксі-сервером HTTP/SOCKS5; обидва варіанти колектора Compose перенаправляють його. Фоновий пул слідує за основною робочою областю. Жодних сесій Telegram, облікових даних API, токенів панелі чи токенів ботів не надсилається постачальникам даних. Назви постачальників, дати знімків та маршрут завантаження вказані в розділі «Звідки походить список».

MTProxy передає лише трафік Telegram. HTTP-операції робочого простору, такі як мітки часу, сповіщення, позасайтові копії та перевірки джерел, використовують окремий SOCKS5/HTTP-проксі, якщо він налаштований, а потім — маршрут SOCKS5/HTTP облікового запису. Без жодного з них функція «Приховати адресу» відхиляє запит; інші режими дозволяють прямий доступ. Зовнішні запити можна вимкнути. Явно налаштований проксі для завантаження стрічки залишається окремим переопределением оператора. Незалежна служба свідків зберігає власний маршрут.

Для приватних сервісів, що управляються оператором, існуюче налаштування серверного середовища TGWITNESS_ALLOW_PRIVATE_DESTINATIONS=1 дозволяє приватні адреси призначення та зберігає визначення імені хосту на стороні проксі. Його неможливо ввімкнути з панелі. Режим «лише публічні» відхиляє адреси призначення у форматі .onion перед запитом до публічного резолвера; сервіси Tor onion вимагають явного налаштування приватних адрес призначення та відповідного проксі. Ця поведінка DNS застосовується до зовнішніх HTTP-операцій, а не до транспортного протоколу Telegram. Cloudflare надає документацію щодо кінцевої точки DNS у форматі JSON.

Параметри автоматичного пулу У розділі **Параметри → Автоматичний MTProxy** налаштуйте поріг відмов, час очікування, заплановану ротацію, спільне використання проксі та допустиму затримку переходу на резервний сервер. | Параметр | За замовчуванням | | --- | --- | | Відключення перед заміною | 3 протягом 10 хвилин | | Кількість проксі, що перевіряються за одну спробу з’єднання | 3 | | Перша / максимальна пауза після збою | 10 хвилин / 6 годин | | Запланована ротація | Вимкнено; увімкнути при збої | | Акаунти на один проксі | 0: краще використовувати окремі записи, об’єднувати за потреби. Встановіть 1, щоб чекати на ексклюзивний запис. | | Затримка до дозволеного переходу на Direct | 10 хвилин; прихована адреса все ще відхиляє Direct | | Оновлення каналу / перевірки транспорту | 60 / 10 хвилин; значення основної робочої області застосовуються до спільного пулу | Різні проксі-сервери не гарантують різних вихідних адрес. Ці налаштування не перекривають обмеження Telegram і не забезпечують анонімності.

Щоб замінити публічний список на власний каталог операторів, налаштуйте наведені нижче параметри заміщення. Це повністю вимикає зовнішні підписки, навіть якщо масив proxies порожній.

Скопіюйте порожній каталог у папку proxy-config/proxies.json та додайте свої розгорнуті публічні кінцеві точки:

{"format": "tgwitness-proxy-catalog-v1", "proxies": [
  {"id": "project-eu", "label": "Project EU",
   "link": "tg://proxy?server=REPLACE_HOST&port=443&secret=REPLACE_SECRET"}
]}

Приклади значень необхідно замінити. Допускається до 32 різних записів. Автентифікований список повертає мітки/хости/порти без спільних секретів; вибір одного з них зберігає його облікові дані у сховищі робочого простору. Доступність залишається неперевіреною до проведення явного тесту транспорту. У разі неправильно сформованого каталогу залишається можливість ручної конфігурації.

Запуск у нативній середовищі: вкажіть TGWITNESS_PROXY_CATALOG як місцевий шлях до файлу JSON. Docker:

docker compose -f compose.yaml -f deploy/compose/compose.proxies.yaml up -d --build

Накладка монтує каталог proxy-config у режимі «тільки для читання»; файли повинні бути доступні для читання контейнером з UID 10001. Цей каталог виключено з Git, контексту збірки Docker та архівів вихідного коду. Цей каталог налаштовує облікові записи для збору даних; бот-свідок використовує власний маршрут HTTP/SOCKS5, а не MTProxy.

Прямий резервний варіант регулюється режимом IP, описаним вище. Призупиніть спостереження перед зміною маршруту. Збереження розриває з’єднання зі старими клієнтами та скасовує незавершений вхід; новий клієнт використовує збережений маршрут. Прив’язка журналу/сесії до облікового запису зберігається. Налаштування замінюють попередній маршрут: під час редагування введіть облікові дані проксі-сервера заново.

Реквізити облікових даних шифруються за алгоритмом network.enc. API не повертає ім’я користувача, пароль або секретний ключ. Підписані записи містять тип маршруту та інформацію про наявність реквізитів облікових даних, виключаючи кінцеву точку та секретні ключі. Оператор може бачити кінцеву точку на панелі. Поля з секретними даними очищаються після збереження, блокування або перемикання робочих просторів.

Функція «Перевірити з’єднання з Telegram», доступна також до входу в систему, відкриває та закриває тимчасове неавторизоване з’єднання з Telegram через маршрут. Вона не звертається до веб-сайту для перевірки IP-адреси. Успішне виконання функції підтверджує наявність транспортного з’єднання, але не означає доступ до груп, повну доставку повідомлень або анонімність.

Проксі застосовується до з’єднань клієнта Telegram, включаючи завантаження медіафайлів із серверів Telegram DC. Браузер, pip, SSH та інструменти TSA, що запускаються вручну, мають окремі маршрути. Ім’я хосту проксі може вирішуватися локально. rdns впливає на імена хостів призначення; Telegram часто надає числові IP-адреси DC.

SOCKS5 та звичайний HTTP CONNECT самі по собі не шифрують облікові дані проксі-сервера або тунель «клієнт-проксі». MTProto окремо захищає трафік Telegram. У ненадійній мережі використовуйте відповідний захищений канал для підключення до проксі. Приватні групи є хмарними чатами; MTProto не перетворює їх на секретні чати з наскрізним шифруванням.

Захист сховища в обліковому записі відображає ці стани. Токен панелі є секретом доступу, а не паролем шифрування. Він надає адміністраторський доступ; видані токени можуть бути обмежені обліковими записами та чатами. Робочі простори використовують спільний хост-процес і не є ізольованими орендарями.

BitLocker, LUKS, FileVault або керований зашифрований том можуть захистити сховище в рамках відповідних моделей загроз. Адміністратор розблокованої машини, що працює, все одно може читати дані. У плануванні сховища слід враховувати файли SQLite WAL/SHM, мультимедіа, тимчасові експортовані дані, обмінну пам’ять, резервні копії та завантажені з браузера файли. Том Docker не шифрується лише тому, що це том. TgWitness не реалізує SQLCipher або шифрування об’єктів.

Зовнішній головний ключ#

Для нової інсталяції розмістіть головний ключ поза каталогом даних. Це не призведе до автоматичного перенесення існуючого сховища локальних ключів. Підготуйте каталог ключів, доступ до якого має лише ідентифікатор служби, а потім виконайте:

python -m tgwitness.security create-master-key /private/keys/tgwitness-master.key
export TGWITNESS_VAULT_KEY_FILE=/private/keys/tgwitness-master.key
python -m tgwitness --data-dir /private/observations/new-case

PowerShell із використанням встановленого середовища проекту:

python -m tgwitness.security create-master-key E:\PrivateKeys\tgwitness-master.key
$env:TGWITNESS_VAULT_KEY_FILE = 'E:\PrivateKeys\tgwitness-master.key'
python -m tgwitness --data-dir E:\PrivateData\new-case

У Docker підключіть файл у режимі «тільки для читання» поза межами /data, наприклад, у /run/secrets/tgwitness-master.key, і встановіть змінну середовища на цей шлях. UID служби повинен мати права на читання цього файлу. Передавайте шлях, а не байти ключа, через файли середовища/конфігурації.

Кожен робочий простір отримує випадковий публічний солт та власний ключ Fernet, отриманий за допомогою HKDF-SHA256. vault.external.json зберігає метадані виведення, а не головний ключ. Відсутність або неправильність ключа призводить до збою запуску без його автоматичної заміни. Зберігайте як метадані солта, так і головний ключ для відновлення.

Усі робочі середовища походять від одного головного ключа; його компрометація впливає на всю інсталяцію. Процес, що виконується, може розшифровувати секретні дані. Це не HSM і не KDF на основі пароля. Довільні паролі, створені людиною, не приймаються замість випадкового ключа.

Зберігайте існуючий ключ для існуючих інсталяцій доти, доки не буде здійснено та перевірено цілеспрямовану міграцію. Видалення vault.key або заміна головного ключа може призвести до втрати доступу до сесій/ключів підпису. Зберігайте зашифровані резервні копії та ключі окремо та перевіряйте можливість відновлення в ізольованому екземплярі.
