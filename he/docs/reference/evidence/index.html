TgWitness / תיעוד

TgWitness משמרת תצפיות מ-Telegram הנראות בחשבון ביומן חתום. הנמענים יכולים לאמת את הרשומות, הקבצים המצורפים והדוחות שנשמרו מול מפתח אספן מהימן, ולאחר מכן להשוות את היומן עם נקודת ביקורת שנשמרה באופן עצמאי. דף זה מתאר את הפורמטים, הבדיקות והחומר שיש לשמור לצורך המסירה.

Recipients can start with VERIFY.cmd on Windows: it asks for the original ZIP and independently obtained key fingerprint, displays an explained result, and saves a separate verification transcript. See verification launchers and the portable runtime for setup and trust limits.

Comparing chat exports#

Verify and compare two signed chat-export ZIPs with independently retained signer fingerprints:

python -m tgwitness.verify first.zip --compare second.zip \
  --fingerprint FIRST_TRUSTED_KEY_SHA256 --compare-fingerprint SECOND_TRUSTED_KEY_SHA256

When both archives record the same numeric account and chat IDs, records are paired by message ID. Unchanged means equality of the complete saved JSON record: full text, author, dates, reply target, nested metadata and unknown fields are all included. JSON object key order does not matter; absent fields, nulls, value types and array order do. The 300-character preview is only for display. Changed entries name the differing top-level changed_fields, including changes invisible in that preview. Duplicate message IDs are rejected instead of overwriting one another during matching.

A difference can be a changed display name, view count, collection annotation or other observation metadata. It does not by itself establish a Telegram edit, identify who made a change, or prove which contradictory archive is accurate. Unparsed records remain in the comparison; equality of their saved representation does not mean their Telegram payload was decoded.

For different or missing account/chat identities, the tool only finds possible correspondences using sender, complete text, file hash, media type and a five-second time tolerance. It reports Matched, not Unchanged. These candidates do not establish message identity or equality of all metadata. Unparsed records remain unmatched. Differences in paired records remain listed in changed, including in content mode; these differences do not prove edits of the same message. With --json, matched counts pairs and unchanged counts pairs whose complete saved records are equal. Neither count proves message identity in content mode. The existing changed_fields and integer unchanged output remain compatible with earlier comparison results. Archive format and signature verification are unchanged.

העברת חקירה#

  1. רשמו את מספר התיק, המפעיל, מזהה החשבון המספרי של Telegram, המקורות שנבחרו, מדיניות האיסוף ותקופת האיסוף בהערות התיק שלכם. TgWitness משמרת תצפיות ותומכת בהערות ובאוספים המקושרים למקורות ב -Case Board. שמרו את רישומי ההעברה והשמירה יחד עם חומרי התיק שלכם. בדקו את הגדרת האיסוף המתוכננת באמצעות נוהל הקבלה בזמן אמת.
  2. יש לשמור את טביעת האצבע של המפתח הציבורי של סביבת העבודה באופן עצמאי לפני ההסתמכות על הייצואים שלה. יש לשמור נקודות ביקורת חתומות מחוץ לאספן במהלך האיסוף. יש לתעד הפרעות ומגבלות הנראות של החשבון.
  3. ייצא קובץ ZIP חתום ושמור את אישור ההפעלה החתום. השתמש בנקודת ביקורת ב- או לפני גבול היומן המיוצא. נקודת ביקורת מאוחרת יותר עלולה לדחות כראוי ייצוא מוקדם יותר בטענה שהוא קצר מדי. הייצואים כוללים את יומן סביבת העבודה המלא, ללא תלות במסנני הפאנלים; בדוק את החומר לפני שתשתף אותו.

  4. יש לבקש מהנמען לאמת את קובץ ה-ZIP באמצעות עותק מהימן של תוכנת האימות ו טביעת האצבע/נקודת הבדיקה שסופקו בנפרד. מתוך סביבת פיתוח מהימנה שבה סביבת ה-Python פעילה:

    python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --checkpoint retained-checkpoint.json

    דוחות פלט מוצלחים מציגים את key_pinned: true ו-checkpoint_checked: true כאשר שני הקלטים מסופקים ומתקבלים. יש לשמור את תוצאת האימות.

    For a handover requiring the final exported record to be witnessed, use
`--witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness`.
This refuses an export with an unwitnessed tail. See the
[witness handover procedure](WITNESS.md#require-a-witnessed-export-boundary).
    1. תעדו את ה-SHA-256 של הארכיון, גבולות הייצוא, תאריך ההעברה, השולח וה נמען ברישום השמירה שלכם. שמרו על החבילה המקורית שלמה ועבדו מהעתקים. שתפו קבצי ראיות במקום את ספריית הנתונים הפרטיים של היישום, המכילה גם הפעלות חשבון וסודות חתימה. לצורך העברה, ניתן לארוז את הייצוא בקובץ ZIP המוגן בסיסמה ב-AES-256. הסיסמה מגנה רק על הסודיות ואינה נשמרת; הנמען מחלץ את הארכיון ומאמת את הייצוא החתום שבתוכו, אשר נותר ללא שינוי.
    2. אם נדרשת קיבוע זמן עצמאי, יש לפעול לפי הנוהל המפורט ב-RFC 3161 ולשמור את הבקשה, נקודת הבדיקה, מידע על רשות האישור (CA) המהימנה ותגובת הרשות המאומתת. הכנת בקשה בלבד אינה מספיקה לקבלת חותמת זמן.

אימות מוצלח קובע את תקינות הנתונים ביחס למפתח האספן המהימן ולגבולות שנשמרו. ראו את היקף האימות לקבלת הנחות האמון ותוצאות האימות עבור הבדיקות שבוצעו.

קטע מתוך מסמך המסירה#

קובץ ZIP חתום מכיל את כל יומן סביבת העבודה. כאשר בית משפט, עורך דין או מחלקת תלונות זקוקים רק לחלק מהצ'אטים, לתקופה מסוימת או לאנשים ספציפיים, האפשרות "ייצוא → תמצית למסירה" מכינה עותק מצומצם (tgwitness-handover-v1) בהתאם לכללי הגילוי שנבחרו. המפעיל מציין את המטרה ובוחר את הצ'אטים, תקופה אופציונלית (UTC), האנשים שעליהם מתייחס התמצית, מה קורה לכל השאר (מוצגים, מוחלפים בשמות בדויים P01, P02… או שיושמטו ), אילו טקסטים של הודעות יישארו, אילו קבצים מצורפים ותמונות פרופיל ייכללו, והאם מספרי טלפון וכתובות דוא"ל בטקסטים יוסתרו. המטרה וכללים אלה מופיעים ב מניפסט החתום ובדוח; היומן מתעד את handover.exported עם הגישה ש הכינה אותו וה-SHA-256 של הקובץ, ולא את התוכן.

verify.py בודק תמצית בשתי דרכים. רשומה המוצגת כבלתי-משתנה מאומתת במלואה: תוכנה מול ה-hash שלה, חתימת ה-Ed25519 שלה והקישור שלה לקודמת הכלולה. רשומה מצומצמת שומרת על ה-hash והחתימה המקוריים, כך שהחתימה עדיין מאומתת, אך לא ניתן לחשב מחדש את השדות שהוסתרו; הרשומה מציינת מה הוסתר והדוח מסמן זאת. המניפסט מציין את אורך היומן ואת הכותרת עם חתימת האספן על אותה כותרת, וסופר את הרשומות שהושמטו; הקובץ coverage.json מתאר את הצ'אטים שנבחרו. שמות המופיעים בתוך שמות קובצים אינם מזוהים. יש לעיין בקבצים הסופיים לפני השיתוף: טקסט חופשי, שמות קבצים וקבצים מצורפים שנבחרו עדיין עלולים לזהות אנשים. יש לשמור את קובץ ה-ZIP החתום במלואו: החילוץ מהווה חשיפה, ולא תחליף.

דוחות קריאים#

ראיות חתומות, מסמכי מסירה וקבצי ZIP של צ'אטים מכילים דוחות קריאים בפורמטים HTML ו-JSON, וכן קובצי PDF כאשר הגופנים הנדרשים זמינים, בשפת הדוח שנבחרה. כל דוח חתום במפתח Ed25519 של סביבת העבודה וניתן לאמתו בנפרד: python -m tgwitness.verify FILE --fingerprint KEY [--evidence ZIP].

  • report.html / chat.html: הצהרת החתימה (tgwitness-report-seal-v1) סוגרת את הקובץ ו חותמת על ה-SHA-256 של כל בייט שלפניה. יומנים וצ'אטים ארוכים מחולקים לחלקים בגודל הניתן להגדרה (הגדרות דוח, 500 עד 100,000 רשומות; 5,000 כברירת מחדל): records/records-0001.html או messages/messages-0001.html, כל אחד חתום במספרו, בטווח ובסך הכל, ומפורט עם ה-SHA-256 שלו במניפסט החתום. רצפים של פעימות לב של האספן מוצגים כשורה אחת, אלא אם כן הגדרות הדוח מפרטות אותם אחד אחד.
  • report.json (tgwitness-report-json-v1, מפתחות format, report, seal): החותם חותם על ה- SHA-256 של ה-JSON הקנוני של ה-report, כך שניתן לקרוא את הנתונים במערכות ובסקריפטים של בתי משפט וניתן לבצע בחירה לצורך הגנה על נתונים מתוך הנתונים הללו, בעוד שהקובץ החתום נשאר שלם.
  • report.pdf / chat.pdf: מסמך רשמי להדפסה ותיוק, חתום פעמיים על אותם בייטים, על הקובץ כולו למעט ערך החתימה (/ByteRange). חתימת PDF הסטנדרטית (adbe.pkcs7.detached, CMS עם SHA-256 ו-ECDSA P-256) משתמשת בתעודת חתימת מסמכים שהונפקה באופן עצמאי המונפק עצמית, המאוחסן בכספת סביבת העבודה; המספר הסידורי של הנושא שלו הוא טביעת האצבע של המפתח Ed25519 . החותם Ed25519 מועבר בתוך ה-CMS כתכונה לא חתומה 2.25.240684792623320047764573196045913242332 ומזהה את ה-SHA-256 של האישור באמצעות "content": "pdf-byte-range", כך שהמפתח Ed25519 מעיד על תוקפו של האישור. קורא PDF מראה האם הקובץ השתנה לאחר החתימה ומגדיר את החותם כ"לא ידוע" עד שהאישור ייחשב אמין; יש להשוות במקום זאת את טביעת האצבע Ed25519. קבצי PDF בסינית, ביפנית ובקוריאנית זקוקים לגופן בשרת (או ב-TGWITNESS_FONT_DIR); ללא גופן כזה, קובץ ה-ZIP מכיל את הדוחות HTML ו-JSON בלבד.

בערוץ או בקבוצת-על, Telegram ממיספר את ההודעות 1, 2, 3… לפי הסדר. ייצוא צ'אט מפרט את המספר הראשון והאחרון, כמה הודעות קיימות וכל רצף של מספרים חסרים ב- message-ids.json , במניפסט ובכותרת chat.json , ומסמן כל פער במקום שבו הוא מופיע בתמליל. verify.py מונה אותם מחדש החל מ-chat.json . מספר חסר הוא הודעה ש-Telegram לא החזירה (נמחקה לפני הייצוא, או שאינה נראית לחשבון); בצ'אטים פרטיים וב קבוצות בסיסיות המספרים משותפים לכל הצ'אטים של החשבון, והפערים אינם נספרים.

After reading the history, the export asks Telegram for every absent number again, by number (channels.getMessages, up to 10,000 numbers). The result is in message-ids.json and the report. An empty answer records that the number is unavailable to this account at recheck time; it leaves the cause unspecified. A message returned on recheck is added to the export and marked found_on_recheck.

כל דוח נפתח ב-. בקצרה : פסקה אחת, ולאחר מכן מה החומר מראה ומה הוא אינו מראה (מי עומד מאחורי חשבון, שלמות המסירה, מחיקות לפני הניטור, זמן שעון ללא חותמת זמן). חותמת האבטחה של הדף עצמו הופכת לכתומה כאשר הדפדפן אימת את חתימת החותמת, ולא את הדף: דפדפן אינו מעניק לדף את הבייטים שלו. הוא הופך לירוק רק כאשר הקורא גורר את הקובץ אל תיבת הבדיקה בתחתית הדף וכל בייט תואם, ורק אם הדף המוצג הוא אותו קובץ; אחרת הוא הופך לאדום.

כל דוח מציין את שם התוכנית במדויק: ה-git commit שבו האספן פועל מתוך צ'ק-אאוט או שהמתקין מגדיר את TGWITNESS_COMMIT, ואת ה-SHA-256 של קבצי המקור שלו (source_tree_sha256, ה-JSON הקנוני של הנתיב → SHA-256 של כל קובץ .py, .js, .css, .html ו-.svg בחבילה), אשר צ'ק-אאוט של אותו commit משחזר, אלא אם כן הקבצים שונו. ה-Telegram נקרא על שם הספרייה, שכבת ה-API ומרכז הנתונים שלו. כאשר מתחיל הניטור וכאשר ייצוא צ'אט מתחיל ומסתיים, האספן שואל את Telegram לגבי הזמן שלו (updates.getState, שניות שלמות) ורושם את הזמן של Telegram פחות השעון של האספן, עם אי-הוודאות הנובעת מהמסלול הלוך ושוב; הדוחות מציגים מדידות אלה תחת "שרשרת האחריות". ייצוא צ'אט מתעד גם מתי הוא קרא את ההיסטוריה, בנוסף לתאריכי ההודעות.

מציג דוחות במצב לא מקוון ומדריך לארכיון#

חלץ את קובץ ה-ZIP המלא לפני פתיחת chat.html או report.html. הצופה מספק חיפוש, מסננים, משתתפים, אינדיקטורים, פרטי רשומות ובחירות JSON/CSV ללא צורך בשרת. שמור את viewer/ ו-media/ לצד הדוח. הבחירות הן נגזרות: השתמש ב-verify.py SELECTION.json --evidence ARCHIVE.zip כדי להשוות אותן לארכיון החתום. המאמת בודק את מזהה הדוח, מפתח החתימה, גבולות הארכיון וכל פריט שנבחר; פריטים שעברו עריכה, חסרים או כפולים ייפסלו. הערות הבחירה וזמן היצירה נותרים כמטא-נתונים לא חתומים.

פערים במספרי ההודעות מוצגים רק עבור פיד צ'אט שלם, לא מסונן ועולה בסדר עולה. הסתרת קטגוריה או כישלון בטעינת גוש נתונים אינם רשאים להפוך שורה שהושמטה לראיה להיעדרות הודעה. הדגשות החיפוש פועלות על טקסט רגיל לפני בריחה מ-HTML, תוך שמירה על סימון מילולי.

הדפדפן בודק חתימות מניפסט, מזהה הדוח והמפתח, וכן את כל חתימות ההאש של הקבצים המפורטים. הוא דוחה מבני ZIP מעורפלים או פגומים, שמות כפולים ונתיבים לא בטוחים, ומגביל את גודל הקבצים ל-256 MiB ואת סך התוכן המוצהר ל-4 GiB. השתמשו במאמת העצמאי עבור ארכיונים גדולים יותר. בדיקה זו של הדפדפן משלימה את בדיקות המאמת לגבי שרשראות היומנים וסמנטיקת הנתונים.

README.txt מכיל מדריך התחלה, רשימת קבצים מותאמת, הוראות אימות והערות על פורמט הנתונים בשפת הדוח, ולאחר מכן מדריך מלא באנגלית. SHA256SUMS מכסה את הקבצים המפורטים בתוכו, למעט הקובץ עצמו, manifest.json ו-manifest.sig; המניפסט החתום מכסה גם את SHA256SUMS. יש לשמור על קובץ ה-ZIP המקורי ללא שינויים ולשמור קבצי עבודה מחוץ ל תיקייה שחולצה. דוחות PDF כוללים סימניות לסעיפים וזיהוי תיק/דוח בעמודים הבאים.

הצ'אט בזמן הייצוא#

ייצוא צ'אט מתעד את מה ש-Telegram אמר על הצ'אט בתחילת הייצוא: התוויות של Telegram עצמו (scam, fake, restricted עם הנימוקים, verified), שמות משתמש, תיאור, מספר המשתתפים והמנהלים, הדיון המקושר, הגנת תוכן, האם משתתפים חדשים רואים הודעות קודמות ומאיזו הודעה בחשבון זה ניתן לראות את ההיסטוריה (available_min_id), התאריך של הודעה 1 כאשר מדובר בהקמת הצ'אט, ו-SHA-256 של תמונת הצ'אט (שנשמרה ב-media/). היא מתעדת את מקומו של החשבון המייצא בצ'אט: תפקיד, תאריך הצטרפות, מי הזמין אותו, ובמקרה של מנהל, את זכויותיו. בקשה ש-Telegram דחה מופיעה תחת שם אחר.

כאשר החשבון המייצא הוא מנהל, הייצוא קורא את יומן המנהל של הצ'אט (Telegram נשמר כ- 48 שעות) אל admin-log.json: מחיקות ועריכות, כולל התוכן והחשבון שביצע את הפעולה. זהו הרישום היחיד של מחיקה המציין מי ביצע אותה.

אינדיקטורים#

רשימת הדוחות והארכיון מכילים את indicators.csv , indicators.stix.json (STIX 2.1 ) ו-indicators.misp.json (אירוע MISP ), אשר על פיהם יכול צוות הטיפול בתלונות לפעול בהודעות המוקלטות: קישורים ודומיינים (גם כאלה המוסתרים מאחורי טקסט, בכפתורים ובתצוגה מקדימה של קישורים), כתובות מטבעות קריפטוגרפיים, שמות משתמש וקישורי הזמנה ב-Telegram , מספרי טלפון, כתובות דוא"ל ותמונות שמורות. כתובות ביטקוין, לייטקוין, דוג'קוין ו-TRON מופיעות ברשימה רק כאשר בדיקת ה-base58 שלהן תקינה, כתובות segwit כאשר בדיקת ה-bech32 או ה-bech32m שלהן תקינה, וכתובות TON כאשר בדיקת ה-CRC שלהן תקינה; כתובות EVM ו-Solana מסומנות כלא נבדקות. התמונות נושאות את SHA-256 ואת ה-hash התפיסתי (dHash, 64 סיביות) שנשאר כמעט ללא שינוי גם בעותקים שעברו דחיסה מחדש או שינוי גודל. הדוחות כותבים אינדיקטורים כך שלא ייפתחו בטעות (hxxps[://]example[.]com ); הקבצים שומרים על הערכים כפי שהיו. כל אינדיקטור מסומן כ"לא ידוע" וכ"לא לזיהוי אוטומטי" (STIX , indicator_types: unknown , MISP , to_ids: false , הפצה לארגון עצמו): עצם הופעתו ברשימה מעידה שהודעה כללה אותו, ולא שהוא זדוני. קישור שהטקסט שלו מציג כתובת שונה מזו שנפתחת מסומן בדוח.

הדוחות מסוג PDF מסתיימים בהצהרה של הבוחן שיש לחתום עליה בכתב יד, ברשימת בדיקה עבור נוטריון או מומחה מטעם בית המשפט, ובקוד QR (המופיע גם בעמוד הראשון) הכולל את מזהה הדוח, טביעת האצבע של המפתח ו ה-SHA-256 של הנתונים המוסמכים, כך שהדפסה תוביל חזרה לארכיון.

קנוניזציה של אירועים#

קלט ה-hash מורכב בדיוק מהשדות הבאים:

seq, observed_at, source_at, kind, chat_id, message_id, actor_id, payload, previous_hash

יש לבצע סידוריזציה באמצעות JSON תואם Python ב-UTF-8, עם מפתחות אובייקטים ממוינים, ללא החלפת תווים ב-ASCII, ללא רווחים חסרי משמעות וללא NaN/אינסוף:

json.dumps(value, ensure_ascii=False, sort_keys=True,
           separators=(",", ":"), allow_nan=False).encode("utf-8")

ה-SHA-256 של אותם בייטים הופך להאש של האירוע. החתימה היא Ed25519 על 32 בייטי ההאש הגולמיים, ולאחר מכן מקודדת ב-base64. ה-previous_hash הראשון הוא 64 אפסים. מספרי הרצף מתחילים ב-1 ועולים ב-1. כל האירועים, כולל אירועים תפעוליים, משתפים שרשרת אחת. אין דיכוי של מסירות כפולות: תצפיות חוזרות הן קבלות נפרדות, ולא טענה לפעולות נפרדות ב-Telegram.

תאריכי טלגרם גולמיים הם מחרוזות ISO; שדות בינאריים הופכים לאובייקטים המכילים bytes_base64. טקסט ההודעה, ישויות, תיאורי מדיה, מטא-נתונים של תשובות, תגובות, ופעולות שירות נשמרים במטא-נתוני ההודעה הגולמיים כאשר הם מסופקים.

observed_at הוא שעון הקיר של האספן ב-UTC. source_at הוא תאריך טלגרם שסופק, כאשר הוא זמין. התראות על מחיקה אינן מספקות שעת מחיקה מדויקת, ולכן source_at נשאר ריק. סדר קבלת הנתונים אינו בהכרח סדר האירועים במקור. תמונות מצב של ההיסטוריה משתמשות בתאריכי מקור ישנים יותר, אך בזמני תצפית עדכניים.

סמנטיקה של שחקנים#

message.new actor_id הוא שולח ההודעה. ל-message.edited אין עורך משוער; payload.sender_id מתעד את שולח ההודעה שנצפתה. מחיקה actor_id נשאר null. הודעות שירות החברות שומרות על השולח וסוג הפעולה, מבלי להמיר כל הסרה לעזיבה מרצון. עדכוני משתתפים גולמיים שומרים על actor_id כפי שסופק. תמונות מצב של תגובות אינן ממציאות גורם שינוי.

התראות מחיקה עבור צ'אטים פרטיים וקבוצות רגילות מכילות רק מזהי הודעות. לצ'אטים אלה יש רצף מזהים משותף לכל החשבון, ולכן מזהה מסוים מזהה הודעה אחת של חשבון זה. כאשר הודעה עם מזהה זה נשמרה קודם לכן ביומן זה, המחיקה נרשמת בצ'אט כ-message.deleted עם payload.chat_resolution כשם השיטה. מזהים שמעולם לא נשמרו נשמרים כ-deletion.unscoped ללא chat_id; לא נעשות השערות כלשהן. ערוצים וקבוצות-על מונים הודעות לפי צ'אט, ולכן לעולם אינם מותאמים בדרך זו. כאשר ההודעה שנמחקה נשלחה על ידי החשבון הנצפה, payload.deleted_message_was_outgoing הוא true; זהות המוחק עדיין לא מסופקת.

An unscoped notice does not establish that a message was never saved: a matching chat may be outside the current observation scope, or a unique match may be unavailable. Recheck absence remains a separate observation from a deletion notification in report counts, filters and labels. A later recovery clears the current missing state while preserving the earlier unsuccessful check in the signed history; neither observation establishes a deletion notice.

Multiple IDs resolved to the same chat from one notification are grouped as deletion.batch, regardless of their count. The notification does not establish that the entire history was cleared, who performed the deletion, or whether it applied to all participants. Saved outgoing messages do not change these limits. Older journals may contain history.cleared events inferred from batches of ten or more IDs, with explanatory text attributing the deletion to the other participant. Those inferences are not supported by the update. Preserve those original signed records, but treat them as grouped deletion notifications; the current interface labels them accordingly.

היקף: רציפות, פערים ומזהים שלא נצפו#

כל קובץ ZIP חתום נושא את coverage.json, דוח ה-HTML נפתח עם אותו סיכום, ו- verify.py מחשב אותו מחדש מ-events.jsonl במקום להסתמך על הקובץ:

  • נצפה ברציפות מ-X עד Y. תקופה מתחילה ב-observation.started ו מסתיימת בהפסקה, עצירה, אובדן חיבור ל-Telegram, יציאה מהמערכת, התחלת תהליך ללא עצירה מסודרת, או יותר משלוש דקות ללא כל תיעוד במהלך התצפית (דופקים נרשמים מדי דקה, ולכן שתיקה פירושה שהתהליך נעצר, קפא או שה מחשב נכנס למצב שינה). כאשר מרווח הדופק משתנה בפרמטרים, כל דופק מתעד זאת, והשתיקה המותרת הופכת לשלושה מרווחים, לעולם לא פחות משלוש דקות.
  • רשימת הפערים מציינת את הזמן שחלף בין תקופות, יחד עם הסיבה לכך. פער שעדיין פתוח ברישום האחרון מסומן כ-not_resumed_by_last_record.
  • מזהי הודעות שלא נצפו. עבור ערוצים וקבוצות-על, המונים הודעות לפי צ'אט, המזהים החסרים בין המזהים שנצפו מפורטים כטווחים. הם מדווחים כ "לא נצפו" — נמחקו, מעולם לא נמסרו או נמצאים מחוץ להיסטוריה השמורה — לעולם לא כ "נמחקו". צ'אטים פרטיים וקבוצות רגילות חולקים רצף המשותף לכל החשבון, ולכן פערים בתוך צ'אט כזה אינם משמעותיים ואינם מפורטים שם.
  • הודעות על פערים ברמת הצ'אט (לדוגמה, בקשת טלגרם לשחזור ההבדלים בערוץ אחד ) נספרות כהערות; הן אינן מפריעות לכיסוי הכולל.

מספרי הודעות חסרים (gap_summary)#

תצוגה מקדימה. coverage.json → gap_summary מדידה של המספרים ש-Telegram הקצה ואשר אספן זה מעולם לא ראה. Telegram ממספר הודעות פעם אחת לכל ערוץ או סופר-קבוצה, ופעם אחת לכל חשבון בכל הצ'אטים הפרטיים, הבוטים והקבוצות הרגילות. מספר שבין שתי הודעות שנצפו הוא או שנצפה או חסר; טווח רציף מהווה קביעה חיובית כי כל הודעה שמספרה נכלל בו נצפתה. פער אינו מציין שחקן כלשהו או סיבה כלשהי.

תחום משמעות
status on, או off כאשר האפשרות כבויה ב-Parameters → Gap analysis
parameters הפרמטרים שהובילו לתוצאה, כדי שניתן יהיה לשחזר אותה
chats[] רשומה אחת לכל ערוץ או סופר-קבוצה, כאשר כל אחת ממוספרת בנפרד
account רצף הצ'אטים הפרטיים, הבוטים והקבוצות הרגילות בכל החשבון
status (לכל רצף) applicable, או not_applicable עם reason
observed_from, observed_to, span המספר הראשון והאחרון שנצפו וגודל הטווח
observed, observed_without_content מספרים שנצפו; אלה הידועים רק מתוך רישום מחיקה או רישום בדיקה חוזרת
missing, density, gap_ranges, largest_gap מספרים שלא נצפו מעולם, חלקם בטווח, מספר הריצות, הריצה הארוכה ביותר
clusters[] פערים המפורטים: low, high, missing, והמספרים הסמוכים שנצפו after / before עם זמני התצפית שלהם
service_estimate רק כאשר האפשרות מופעלת: כמה מהמספרים החסרים היו הודעות שירות לפי שיעור הופעתן שנצפה. לעולם לא מופחת מ- missing

התוקף נגזר מהיומן, ואין להניח אותו מראש:

  • ערוצים וקבוצות-על נמדדים לפי צ'אט, וכן בייצוא של צ'אטים נבחרים. הרישומים שנבחרו על ידי השולח מהווים את הבסיס למדידה not_applicable.
  • הרצף ברמת החשבון נמדד רק מההודעה הראשונה ועד האחרונה שהתקבלה בזמן שאיסוף הנתונים של החשבון כולו היה פעיל, וכלל צ'אטים פרטיים, בוטים, קבוצות רגילות והודעות של החשבון עצמו, ללא החרגת אף צ'אט מסוג זה (scope.changed). מספרים המכונים deletion.unscoped נחשבים כנצפים ללא תוכן. ייצוא או העברה של צ'אטים נבחרים אינם יכולים למדוד זאת. אם איסוף הנתונים של החשבון כולו הופעל ונכבה, תופיע הערה המציינת כי המספרים ששימשו בינתיים מופיעים כפערים.
  • הודעות השירות הן רשומות ביומן עם מספרין משלהן, ולכן הן ממלאות את הפערים בעצמן; האומדן האופציונלי נועד רק להקשר.

verify.py מחשב מחדש gap_summary מ events.jsonl עם הפרמטרים שב- coverage.json (הגדרות ברירת מחדל לארכיונים ישנים יותר) ו מדפיס את השורה ברמת החשבון בסיכום הכיסוי שלו. ה- get_capture_status(MCP ושורת הפקודה) מחזיר את אותה המדידה עבור הצ'אטים שהגישה עשויה לקרוא; הרצף ברמת החשבון כולו רק לגישה המכסה את כל סביבת העבודה.

Repeated observations of one service message count once, and the account service estimate uses only numbers inside the measured range. An applied scope must explicitly preserve the account's own messages before account-wide measurement is enabled; older records without that information cannot establish this condition. Stopped observation does not extend the measured range, and resuming it is noted. The live archive query has a time budget, including its database scan, and marks an unfinished measurement as partial.

Telegram documents the separate message ID sequences. These numbers describe observations; they do not identify a deletion actor or establish why a number is absent.

כאשר Telegram מפסיק לקבל את החשבון, הרשומה coverage.gap שמסיימת את המעקב נושאת את cause (account_banned, account_frozen, account_deleted, session_duplicated, session_revoked, session_expired, session_ended או not_authorized) ואת השגיאה Telegram; verify.py מציין את הסיבה לסיום התקופה.

Coverage combines recorded observation periods, interruptions and message outcomes. Assess it together with the selected chats, period and attachment policy; continuous operation alone does not establish complete delivery of Telegram updates.

מפיק#

הרשימה החתומה של קבצי ZIP המכילים ראיות, ייצוא צ'אטים, יומני עדים והצהרות בקבצי פרופיל המשתמשים מכילה את producer : תוכנה, גרסה, פרויקט (PhishDestroy), דף הבית ומאגר הקוד המקור. הדוח ב-HTML מציג את אותה השורה, ו-verify.py מדפיס אותה כחלק ממה שאומת. ארכיונים שנוצרו לפני שקיים שדה זה מאומתים כ בעבר ומדווחים ככאלה שאינם מציינים את שם היוצר.

כל רשומת observation.started מציינת גם את שם הלקוח Telegram שביצע את הניטור: ה-api_id שלו (לעולם לא את ההאש), בין אם מדובר בזוג ציבורי מובנה או ביישום של המפעיל עצמו, תיאור הלקוח שנשלח בבקשת החיבור של Telegram, וסוג מסלול החיבור עם מצב ה-IP (ללא כתובת פרוקסי או סוד). הדוח ו-custody.json מפרטים כל לקוח ומסלול נפרד עם מועד הרישום שלהם, וכן את הפעמים שבהן אף פרוקסי מהרשימה לא ענה ו-Telegram זיהה את כתובת השרת. יומנים שנרשמו לפני כן מציינים זאת.

פרופילים אישיים#

קובץ פרופיל (tgwitness-dossier-v1, JSON) נבנה על פי בקשה מתוך רשומות שכבר נמצאות ביומן עבור צ'אט אחד; לא נשאב דבר מ-Telegram ותוכן הפרופיל לעולם לא נכתב ביומן (הפעלה וכיבוי של פרופילים נרשמים כ-dossier.changed). עבור כל אדם שיש לו הודעה שמורה, הוא מפרט את ההיסטוריה של השם ושם המשתמש, דגלי טלגרם (בוט, הונאה, מזויף, פרימיום, מאומת, מוגבל, נמחק) כפי שנראו בזמן השמירה, תעודות זיהוי תמונה, SHA-256 והאש תפיסתי (pHash, תואם ל-imagehash.phash) של האווטאר ממאגר האווטארים המקומי עם אווטארים דומים, פעילות (ההודעה הראשונה והאחרונה, מספרים, שיתופים שעברו עריכה ונמחקו, הודעות לפי שעה UTC), מי עונה למי, צ'אטים אחרים ביומן זה שבו האדם כתב, וארנקים שהוזכרו (BTC, EVM, TRON, TON, LTC, DOGE, XMR, SOL; כתובות Base58Check מאומתות באמצעות בדיקת סיכום), מספרי טלפון, שמות משתמש ו קישורים, כולל קישורים המוסתרים מאחורי טקסט.

כל עובדה מציינת את רשומות היומן (seq) שממנה היא נלקחה, ו-record_hashes מכיל את ה-hash של כל רשומה שמצוטטת. ההצהרה חתומה במפתח סביבת העבודה:

python verify.py tgwitness-dossier-CHAT.json --fingerprint TRUSTED_SHA256 --evidence tgwitness-evidence.zip

בודק את החתימה, מאמת את ייצוא הראיות עצמו (חתימה, שרשרת האש וקבצים) ומבטיח שכל רשומה המוזכרת קיימת ללא שינוי בייצוא זה של אותו מרחב עבודה. האשים של האווטרים מסומנים כמקורם במטמון המקומי (לא מרשומות היומן). אזכורים הם התאמות לדפוס — רמזים לבדיקה, לא עובדות מאומתות. הפרופילים מופעלים לפי צ'אט, ניתנים לייצוא כקובץ ZIP מוצפן ב-AES-256 עם סיסמה, ו נמחקים כאשר הם כבויים או כאשר הצ'אט מוסר מהמקורות.

יומן העד (tgwitness-witness-v1) והפרסומים בערוץ שלו נבדקים מול ייצוא ראיות באמצעות verify.py --witness … --channel …; ראו "עד עצמאי".

מניפסט ונקודות בקרה#

הקובץ manifest.json כולל את הפורמט, זמן הייצוא, המפתח הציבורי, טביעת האצבע, אורך היומן, ה-hash הראשי, ההיקף, היוצר, המגבלות ו-SHA-256 של כל רכיב תוכן מלבד manifest.json ו-manifest.sig עצמם. manifest.sig הוא חתימת base64 Ed25519 על קובץ ה-JSON הקנוני של המניפסט. המאמת דוחה רכיבים בלתי צפויים או חסרים, שמות כפולים, קבצים פגומים, רצף או שרשרת שבורים, חתימות לא חוקיות ואי-התאמה לנקודת ביקורת שסופקה. הוא לעולם אינו מחלץ נתיבי ארכיון. הוא מגביל את הגודל הכולל המוצהר ללא דחיסה ל-4 GiB; קובץ --max-gib N מאפשר ארכיונים גדולים יותר שנוצרו עם הגבלת פרמטרים מוגברת.

Run verification from your installed TgWitness version or a reviewed checkout. The copy included in an archive supports portable use; check that copy against your trusted installation before executing it.

A checkpoint signs a statement containing the public key, journal length, head hash, and creation time. The verifier can check that a later archive contains the same prefix. Retain the checkpoint outside the collector, so later verification compares the archive with a reference held separately from it.

היקף האימות#

Verification checks the archive and the collection mode used to produce it. Choose the mode whose trust boundary matches the case, then retain its verification inputs.

מצב איסוף מה בודק המאמת קלט אימות וגבולות אמון
סביבת עבודה מקומית Record signatures, hash chain, manifest and attachment bytes Independently retained collector fingerprint; the host administrator controls the local signing key
סביבת עבודה מקומית עם עד עצמאי בדיקות הארכיון וכן התאמה לקידומת היומן הקודמת שנשמרה על ידי העד Separately trusted witness key and records; the checkpoint binds the prefix already observed
תיעוד פעולות GitHub GitHub attestation of the archive digest, approved workflow and collector commits, hosted runner, fresh session/key origin and internal archive integrity Trusted verifier policy, caller repository and GitHub attestation bundle; collection runs under the pinned workflow
פריסה בענן Provider lifecycle and access records, firewall and Cloudflare state, plus the collector's signed run record Read-only queries to the provider and Cloudflare; availability of individual checks depends on the provider
מכונת וירטואלית סודית של Intel TDX Quote signature and platform status, binding to the collector statement, compose and OS measurements Intel trust chain and expected deployment measurements; retain the results of every required TDX check

In sealed acquisition, the approved collector receives data through an authenticated Telegram connection inside the verified environment. Attestation binds the archive to that execution, so verification covers acquisition as well as later file integrity. This relies on the approved code and the platform trust chain listed above. GitHub capture verification requires a session created inside the run and rejects imported-session captures.

The run receipt records the collector version, file hashes and startup settings. GitHub provenance and TDX measurements provide the environment checks; the validation record identifies tested configurations.

TgWitness signs the observations it collects; Telegram and message authors do not issue these signatures. In a local workspace, material created before the first independent checkpoint still depends on the collector and its key holder. Coverage records describe the selected scope and collection outcomes, while verified external timestamps anchor the committed archive or journal boundary in time.

קובצים מצורפים#

הקובצים ממוינים לפי SHA-256 בתיקיית media/. אירוע media.saved מקשר בין חתימת hash ואורך ב-byte לאירוע הודעה ספציפי. שמות הקבצים הגולמיים הם מטא-נתונים, לעולם לא נתיבים מקומיים. בייטים של מדיה מורידים באופן אסינכרוני, ולכן מחיקה מיידית עלולה למנוע את לכידתם. איסוף מושבת, קבצים גדולים מדי או בגודל לא ידוע, כשלים בהורדה, והורדות שנקטעו מוצגים בתוצאות. קריסת תהליך עלולה להשאיר קבצים חלקיים ללא הפניה; הם אינם נכללים בייצוא.

יצואן ה-ZIP מאמת את קבצי המדיה המאוחסנים מול שמותיהם. ייצוא בפורמטים JSONL, CSV ו-HTML מאמת את חתימות האירועים אך אינו כולל את נתוני המדיה עצמם. דוחות נגזרים נועדו לנוחות המשתמש; הקובץ events.jsonl הוא התיעוד המוסמך של האירועים.

ייצוא צ'אט מלא שומר קבצים מצורפים בהתאם להגדרות הקבצים המצורפים של סביבת העבודה בתיקייה media/, תחת שמות מסוג SHA-256. כל רשומת הודעה ב-chat.json מציינת את שם הקובץ שלה (file, file_sha256) או את הסיבה להיעדרותו (file_status), יחד עם מה שהקורא ראה סביב הטקסט: קישורים מאחורי הטקסט, מקור ההעברה, כפתורי בוט, חתימה, צפיות ו טיימר המחיקה האוטומטית. verify.py בודק שכל קובץ ששמו צוין נמצא במניפסט החתום תחת אותו חשיש.

איסוף קבוע וקבלות תהליך (0.2)#

משימת מדיה והתחייבות לאירוע ההודעה שלה מתבצעות בעסקה אחת. המשימה מאחסנת את תיאור ההודעה המקורי מ-TL; התצפית החתומה קושרת את ה-SHA-256, החשבון, ומדיניות הגודל שלה. תהליך השחזור מאמת את הקישור לפני ההורדה. הוא לעולם אינו מביא את ההודעה הנוכחית ומחליף בשקט קובץ מצורף חדש יותר. משימות שנקטעו מופעלות מחדש, בעוד שכישלון קבוע נשאר תוצאה מפורשת.

Each workspace has its own journal and signing identity. A process.started event includes a run ID, local clocks, dependency versions, source-file hashes, initial account/scope, and capture settings. Heartbeats include the run ID, monotonic time, and queue state. The run receipt can also be downloaded as a separately signed statement. For verification of the execution environment, pair it with the GitHub attestation or TDX checks described in Verification scope.

Automatic checkpoints are retained locally on startup, every five minutes while observing (Parameters → Signed checkpoint every), and on orderly stop. Startup verification and export compare the journal against the latest retained local checkpoint. This can detect a database rollback when the checkpoint survives. Independent retention keeps that reference available outside the workspace; a verified external timestamp additionally anchors it in time.

לאחר הפעלה מחדש, מיקום העדכון השמור של Telegram מתחדש (catch_up_from ב- observation.started) ומבוצעת בקשה לעדכונים שהוחמצו. בדיקה חוזרת תקופתית מתעדת את message.recovered עבור הודעות שהוחמצו ואת message.missing_on_recheck כאשר Telegram כבר לא מחזיר הודעה שמורה; האחרון אינו הודעת מחיקה ואינו מציין את שם המחיק או את הזמן.

העתקה ושחזור מחוץ לאתר (S3)#

העותק מחוץ לאתר (ייצוא, כבוי כברירת מחדל) מעלה קטעי יומן, קבצים שנשמרו, נקודות ביקורת עם חותמות הזמן שלהן וייצוא צ'אטים מוגמרים לאחסון תואם S3, מוצפנים באמצעות AES-256-GCM לפני ההעלאה תחת מפתח המאוחסן בכספת סביבת העבודה; שמירת Object Lock חלה כאשר הדלי תומך בכך. ללא המפתח שהורד, לא ניתן לקרוא את העותק. שחזור ואימות באמצעות python -m tgwitness.replica restore --key-file KEY.json --out DIR.

השחזור דורש ספרייה רגילה וריקה. קבצים שהורדו ואובייקטים מפוענחים נשמרים באחסון זמני פרטי עד לאימות היומן כולו וכל נקודת ביקורת שנשמרה. נתיבי אובייקטים לא בטוחים, טווחי קטעים לא עקביים ויומנים הקצרים מנקודת ביקורת נדחים; אימות כושל אינו מפרסם קבצים משוחזרים. בדיקות השמירה משוות את מצב נעילת האובייקט והתאריך שהוחזרו עם המועד האחרון שנשלח בעת ההעלאה (סובלנות עיגול של שנייה אחת). מועד אחרון שפג תוקפו, לא תקף או מקוצר אינו נחשב כמאומת. הסטטוס מדווח על האובייקט שנדגם ששמירתו נקראה בחזרה עבור מחזור ההעלאה הזה.

מדיה מקומית חסרה או פגומה מדווחת כשגיאה של המעבר, והסמן נשאר על המדיה שלפניה, כך שהקובץ ינסה שוב במעבר הבא; הקבצים, נקודות הבדיקה והייצוא שאחריה עדיין מועתקים. בדיקות השחזור משוות את כל ההפניות למדיה שנשמרה מול חשישים מפוענחים וגדלים שנרשמו. קטעי יומן חופפים זהים מהעלאות שנקטעו עוברים דה-דופליקציה; חפיפות סותרות נדחות. נקודות ביקורת שנוצרו במהלך העלאה נדחות עד שרישומי היומן שהן מכסות הועתקו, כך שמעבר שהושלם אינו מפרסם נקודת ביקורת לפני היומן שלה.

תמונות מצב של ייצוא הזרמה#

ייצוא הזרם משתמש בתמונת מצב קריאה יציבה של SQLite. החלק הראשון שלה עשוי להיות ישן יותר מהיומן החי הנוכחי עם השלמת ההורדה. נקודת ביקורת שנוצרה לאחר אותה תמונת מצב עשויה לדווח נכונה שהארכיון קצר יותר; יש להשוות לנקודת ביקורת בנקודת ההתחלה של הייצוא או לפניה, ולא לנקודת ביקורת מאוחרת שרירותית.

הכנה לאימות תגובות לפי RFC 3161 (0.2)#

מצב הראיות (כבוי כברירת מחדל) שולח רק את ה-SHA-256 של כל נקודת ביקורת חתומה לרשויות RFC 3161 וללוחות השנה של OpenTimestamps המפורטים, דרך נתיב סביבת העבודה ולעולם לא דרך MTProxy. התשובות נשמרות ב-checkpoints/anchors/, מיוצאות ונבדקות על ידי verify.py (--tsa-ca בודק את חתימת ה-TSA; מאמת את הוכחות OpenTimestamps באמצעות ots upgrade ו-ots verify).

הפאנל מכין ארכיון בקשות המכיל את הבתים הקנוניים של הקובץ checkpoint.json, טביעת הודעה ב-SHA-256 ו-nonce אקראי בקובץ timestamp.tsq, סכומי ביקורת והוראות. לא מתבצעת כל בקשת רשת. ההכנה אינה מהווה חותמת זמן מהימנה.

python -m tgwitness.anchor verify קורא ל-OpenSSL פעמיים: פעם אחת ביחס לבייטים של נקודת הבדיקה ופעם אחת ביחס לבקשה המקורית. נדרש במפורש קובץ CA מהימן; תעודות כלולות אינן נחשבות לאמינות באופן אוטומטי. בדיקת הבקשה היא אופציונלית ב-CLI, לכן יש לשמור ולהזין את האופציה --request כדי לבדוק את ה-nonce. התוצאה מציינת אם הבדיקה בוצעה. חתימת נקודת הבדיקה של האספן ויומן הראיות עדיין חייבים להיות מאומתים בנפרד באמצעות טביעת האצבע המהימנה של האספן.

תהליך האימות בודק את חתימת התגובה, את בתים של נקודת הבדיקה, וכאשר הם מסופקים, את הבקשה המקורית תחת אמון ה-CA שצוין. בדיקות ביטול ואימות ארכיוני לטווח ארוך לאחר פקיעת תוקף האישור אינן נכללות במסגרת המאמת הנוכחי. ראו את הנוהל ותוצאות האימות.

רשומות אופציונליות במצב ראיות: מכשירי drand ו-Telegram#

ניתן להפעיל שני תיעודים נוספים באותם מחזורים כמו חותמות הזמן. שניהם כבויים כברירת מחדל ו נכנסים לתוקף רק כאשר מצב הראיות מופעל: תוספות → ראיות וגיבויים → עדים נוספים · אופציונלי, או "drand": true ו "devices": true ב POST /api/evidence. תקלה באחד מהם אינה עוצרת את השני או את חותמות הזמן; הלוח מציג את התוצאה האחרונה של כל אחד מהם מתחת לטופס.

drand (beacon.drand ). בכל מעבר נכתבת הסבב החדש ביותר של drand quicknet, האקראיות הציבורית של League of Entropy (סבב כל 3 שניות), ביומן: chain , round , randomness , signature , round_time וה-relay שהשיב. סבב מאומת ובלתי צפוי מספק נקודת ייחוס זמן תחתונה לחומר המקושר באמצעות hash הבא. חותמת זמן מאומתת בנקודת ביקורת מאוחרת יותר מספקת נקודת ייחוס זמן עליונה. בדיקות אלה מגדירות את גבולות החומר המקושר; כיסוי האיסוף מוערך בנפרד. האספן פונה תחילה ל-drand.cloudflare.com , ולאחר מכן לממסרים של Protocol Labs, דרך נתיב סביבת העבודה, בקשה אחת לכל מעבר.

verify.py בודק שכל אקראיות היא ה-SHA-256 של החתימה שלה ושזמן הסיבוב נכון, ומדווח על הסיבובים, על הרצף הארוך ביותר ללא סיבוב ועל הפער בין drand לשעון האספן. הוא אינו בודק את חתימת ה-BLS. ה---check-drand משווה את הסיבובים עם ממסר של Cloudflare וממסר של Protocol Labs, את כולם או מדגם אקראי של 100 מתוך יומן ארוך; סיבוב שונה נכשל באימות.

, Telegram, , account.devices. בכל מחזור קריאה, המערכת קוראת את הפעילויות של החשבון עם account.getAuthorizations, הרשימה Telegram המוצגת תחת 'הגדרות' → 'מכשירים', ומתעדת אותה: במלואו כאשר חל שינוי מאז המעבר הקודם, עם חשישי ההפעלה added ו-removed, ואחרת רק את מספרן ואת SHA-256. דגם המכשיר, הפלטפורמה, האפליקציה והגרסה, תאריך היצירה והפעילות האחרונה, המדינה והאזור נשמרים; כתובות IP אינן נשמרות, מכיוון שייצוא הראיות יוצא משליטתך. הפעלה של האספן עצמו פעילה כל הזמן, ולכן רק פעילות של הפעלות אחרות נחשבת כשינוי. verify.py מדווחת על תדירות הרישום של הרשימה ועל כל הפעלה חדשה ומסתיימת. היא קוראת את הרשימה רק בזמן שהמעקב פועל.

מה שהם לא מראים: drand מוכיח לא יותר מאשר את סדר הרשומות ביחס לזמן הציבורי, ורשימת המכשירים היא הצהרתו של Telegram באמצעות האספן, החתומה על ידי האספן כמו כל רשומה אחרת.

יומן Cloudflare Gateway (cloudflare.gateway_dns). עבור שרת שמתבצע דרך Cloudflare Gateway ( Gateway DNS ), כל העתקה מעתיקה את מה ש-Gateway תיעד מאז ההעתקה הקודמת: רשומה אחת לכל חלון של שלוש שעות לכל היותר עם from, until, location_id, address של השרת כאשר הוא מוגדר, ו- queries כ-[at, name, type, rcode, decision, colo], גם כאשר לא היה כזה. הגדר זאת תחת יומן Cloudflare Gateway : חשבון, מיקום, כתובת אופציונלית ואסימון לקריאה בלבד (קריאת Analytics לקריאה; Zero Trust PII לקריאה כדי לשמור כתובת אחת של מיקום משותף). הלוח בודק אותם בבקשה אחת לפני השמירה; האסימון נשאר מוצפן ולעולם אינו נכנס ליומן. verify.py מפרט את החלונות, השמות שנחפשו ביותר וכל זמן שאין עותק שמכסה; רשומה שמספרה אינו תואם את השאילתות שלה נכשלת. חלון המכיל יותר מעמוד אחד של שאילתות בשנייה אחת שומר את העמוד הזה ומציין שהשאר חסר. העותק הוא התשובה של Cloudflare דרך האספן, חתומה על ידי האספן; תוך 24 שעות כל מי שיש לו אסימון לקריאה בלבד יכול להשוות אותה עם Cloudflare.
