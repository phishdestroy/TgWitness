證據格式

簽名 ZIP 檔案的內容、記錄類型、處理回執、使用者檔案、異地備份及離線驗證。

TgWitness 會將 Telegram 帳戶可見的觀察記錄保存於經簽署的日誌中。 收件者可透過可信賴的 收集器金鑰，驗證已保存的記錄、附件及報告，並將日誌與獨立保留的檢查點進行比對。 本頁說明格式、驗證程序以及移交時應保留的資料。

Recipients can start with VERIFY.cmd on Windows: it asks for the original ZIP and independently obtained key fingerprint, displays an explained result, and saves a separate verification transcript. See verification launchers and the portable runtime for setup and trust limits.

何謂「簽名」#

資料 保護 應保留的內容
每則日誌記錄，包括操作事件 每個事件皆包含 SHA-256 鏈及 Ed25519 簽名 原始 events.jsonl（可信金鑰指紋）及保留的檢查點
證據 ZIP 檔案內容 manifest.sig 對規範性清單進行簽名，該清單列出了內容檔案的雜湊值 完整的 ZIP 檔案，包含其清單檔與簽名檔
保留的附件 簽名過的 media.saved 事件中包含 SHA-256 值與位元組計數；簽名過的 ZIP 清單中包含檔案雜湊值 經驗證 ZIP 檔案內的原始位元組
檢查點 針對日誌長度、開頭雜湊值、公鑰及建立時間進行 Ed25519 簽名 在爭議性變更發生前保留的獨立副本
執行收據 Signed record of the collector version, source-file hashes and start settings, also included in process.started The receipt, associated journal and the environment evidence for the selected verification mode
易讀的報告：report.html 及其各部分，report.json、report.pdf、chat.pdf 每個檔案均附有針對其內容的 Ed25519 封印；PDF 亦附帶標準的 PDF 簽名（參見 可讀性報告 ） 收到的檔案及其可信金鑰指紋；該檔案所對應的 ZIP 檔案
獨立版 CSV 不包含獨立的加密簽名；僅憑事件雜湊值並不足夠 請使用經驗證 ZIP 檔案中的原始內容進行完整性檢查
由瀏覽器產生的螢幕截圖、列印文件或 PDF 檔案 衍生作品上不得出現 TgWitness 簽名 請保留原始的已驗證套件，並記錄衍生版本的製作過程

收集器會在生成每種匯出格式之前，先驗證日誌簽名。 易於閱讀的 HTML 和 PDF 報告各自附有專屬印章；獨立的 CSV 檔案則作為 已簽署 ZIP 檔案的一部分進行驗證。請保留 ZIP 檔案以維持附件位元組與清單， 並另設檢查點，用以將日誌與較早的邊界進行比對。

Comparing chat exports#

Verify and compare two signed chat-export ZIPs with independently retained signer fingerprints:

python -m tgwitness.verify first.zip --compare second.zip \
  --fingerprint FIRST_TRUSTED_KEY_SHA256 --compare-fingerprint SECOND_TRUSTED_KEY_SHA256

When both archives record the same numeric account and chat IDs, records are paired by message ID. Unchanged means equality of the complete saved JSON record: full text, author, dates, reply target, nested metadata and unknown fields are all included. JSON object key order does not matter; absent fields, nulls, value types and array order do. The 300-character preview is only for display. Changed entries name the differing top-level changed_fields, including changes invisible in that preview. Duplicate message IDs are rejected instead of overwriting one another during matching.

A difference can be a changed display name, view count, collection annotation or other observation metadata. It does not by itself establish a Telegram edit, identify who made a change, or prove which contradictory archive is accurate. Unparsed records remain in the comparison; equality of their saved representation does not mean their Telegram payload was decoded.

For different or missing account/chat identities, the tool only finds possible correspondences using sender, complete text, file hash, media type and a five-second time tolerance. It reports Matched, not Unchanged. These candidates do not establish message identity or equality of all metadata. Unparsed records remain unmatched. Differences in paired records remain listed in changed, including in content mode; these differences do not prove edits of the same message. With --json, matched counts pairs and unchanged counts pairs whose complete saved records are equal. Neither count proves message identity in content mode. The existing changed_fields and integer unchanged output remain compatible with earlier comparison results. Archive format and signature verification are unchanged.

調查交接#

  1. 請在案件筆記中記錄案件編號、操作人員、Telegram 帳戶的數字 ID、已選取的 來源、蒐集政策及蒐集期間。TgWitness 會保存觀察記錄，並支援在 「案件看板」中建立與來源連結的筆記及蒐集資料。請將轉移與保管記錄與您的案件 資料一併保存。 透過 即時驗收程序，核對預期的蒐集設定是否正確。
  2. 在依賴 其匯出內容之前，請先獨立保留工作區的公鑰指紋。在收集過程中，請將簽名檢查點儲存於收集器之外。 記錄中斷情況以及該帳戶可見性的限制。
  3. 匯出經簽名的 ZIP 檔案並保留經簽名的執行收據。請在 匯出日誌邊界處或之前設定檢查點。若檢查點設定在較後位置，系統將能正確地拒絕 較早的匯出檔案，因其長度不足。匯出內容包含完整的工作區日誌， 無論面板篩選條件為何；請在分享前審閱相關資料。

  4. 請收件者使用可信的驗證器副本，並搭配 獨立提供的指紋／檢查點，來驗證 ZIP 檔案。請從一個可信的檢查點開始，並確保 其 Python 環境已啟動：

    python -m tgwitness.verify evidence.zip --fingerprint TRUSTED_PUBLIC_KEY_SHA256 --checkpoint retained-checkpoint.json

    當兩個輸入皆已提供且被接受時，成功產出的報告將顯示 key_pinned: true 和 checkpoint_checked: true 。請保留驗證結果。

    For a handover requiring the final exported record to be witnessed, use
`--witness witness.zip --witness-fingerprint TRUSTED_WITNESS_SHA256 --require-witness`.
This refuses an export with an unwitnessed tail. See the
[witness handover procedure](WITNESS.md#require-a-witnessed-export-boundary).
    1. 請在您的保管紀錄中記錄檔案的 SHA-256 值、匯出邊界、傳輸日期、發送者及 收件者。請保持原始封包完整，並僅 使用副本進行操作。請分享證據檔案，而非應用程式的私有資料 目錄，該目錄亦包含帳戶會話及簽名密鑰。 傳輸時，可將匯出檔案放入受密碼保護的 AES-256 ZIP 壓縮檔中。該 密碼僅用於保護機密性，且不會被儲存；收件者解壓縮 檔案後，即可驗證其中未經變更的簽名匯出檔案。
    2. 若需獨立的時間錨定，請遵循 RFC 3161 程序，並保留請求、檢查點、可信 CA 資訊以及經驗證的授權機構回應。僅準備請求 並無法取得時間戳記。

驗證成功即表示相對於可信收集器 金鑰及保留邊界，資料完整性已獲確立。請參閱驗證範圍，了解 信任假設以及所執行檢查的驗證結果。

交接摘要#

一個已簽名的 ZIP 檔案包含整個工作區日誌。當法院、律師或濫用通報部門僅需 部分聊天記錄、特定時間段或特定人員時，可透過「匯出 → 移交摘錄」功能，依據選定的揭露規則生成精簡版 副本（tgwitness-handover-v1）。 操作員需說明目的，並選擇對話內容、可選的時間範圍（UTC）、 摘錄所涉及的人物，以及其他人員的處理方式（顯示、替換為化名 P01、 P02… 或 省略），哪些訊息內容保留，哪些附件及個人資料照片納入，以及 訊息中的電話號碼和電子郵件地址是否需被遮蔽。 該目的及相關規則將載於 經簽署的清單及報告中；日誌會記錄「handover.exported」，並標註 生成該日誌的存取者以及檔案的 SHA-256 值，而非內容本身。

verify.py 透過兩種方式檢查提取檔。若記錄顯示未經變更，則會進行完整驗證：其 內容將與其雜湊值、Ed25519 數位簽名以及與所包含前一版本的連結進行比對。 一則 經簡化的記錄會保留原始雜湊值與簽名，因此簽名仍可通過驗證，但 被隱藏的欄位無法據此重新計算；該記錄會列出被隱藏的內容，而報告 也會標示出來。清單會列出日誌長度與開頭，並附上收集者對該 開頭的簽名，同時統計被省略的記錄數量； coverage.json描述所選的聊天紀錄。檔案 名稱中的姓名不會被偵測到。分享前請審閱最終檔案：自由文字、檔案名稱及選定的 附件仍可能揭露個人身分。請保留完整的簽名 ZIP 檔案：解壓縮後的檔案屬於資訊揭露，並非替代品。

易讀的報告#

已簽署的證據、移交檔案及聊天 ZIP 檔均包含可讀取的 HTML 和 JSON 報告，此外 若所需字型可用，還會提供以選定報告語言產生的 PDF 檔案。每份 報告均以工作區的 Ed25519 金鑰加密封存，並可單獨驗證： python -m tgwitness.verify FILE --fingerprint KEY [--evidence ZIP]。

  • report.html / chat.html：封存陳述式（tgwitness-report-seal-v1）會關閉檔案，並 對其前面的每個位元組的 SHA-256 進行簽名。長篇日誌和聊天記錄會分割為 可配置大小的部分（報告設定，500 至 100,000 筆記錄；預設為 5,000 筆）： records/records-0001.html 或 messages/messages-0001.html，每個皆以其編號、範圍 及總數進行封存，並連同其 SHA-256 一併列於已簽署的清單中。收集器心跳訊號的連續記錄 將顯示為一行，除非「報告設定」中指定逐一列出。
  • report.json（tgwitness-report-json-v1、金鑰 format、report、seal）：該憑證對 report 的規範 JSON 中的 SHA-256 進行簽署，因此案件系統與腳本可讀取相關事實 並能據此進行資料保護的篩選，同時保持簽署檔案的完整性。
  • report.pdf / chat.pdf：一份供列印及歸檔之正式文件，針對相同 位元組進行兩次簽署，範圍涵蓋除簽名值（/ByteRange）以外的整個檔案。標準的 PDF 簽名 （adbe.pkcs7.detached、CMS 搭配 SHA-256 及 ECDSA P-256）使用一份自行簽發的文件簽署 憑證，該憑證儲存於工作區金庫中；其主體序號即為 Ed25519 金鑰 指紋。Ed25519 印章以未簽署屬性 2.25.240684792623320047764573196045913242332 的形式 封存於 CMS 之中，並以 "content": "pdf-byte-range" 標示憑證的 SHA-256， 因此 Ed25519 金鑰即為該憑證提供擔保。 PDF 讀取器會顯示 檔案在簽署後是否曾被修改，並在憑證被 視為可信之前，將簽署者標示為「未知」；請改為比對 Ed25519 指紋。中文、日文及韓文的 PDF 檔案需要在伺服器上 （或於 TGWITNESS_FONT_DIR 中）具備對應字型；若無此字型，ZIP 檔案僅會包含 HTML 和 JSON 報告 。

在頻道或超級群組中，Telegram 會依序為訊息編號 1、2、3…。聊天記錄匯出檔會列出 起始與結束編號、現有訊息數量，以及所有缺失編號的區段（如 message-ids.json ）、清單檔與 chat.json 標頭，並標記每個缺口在 對話紀錄中的位置。 verify.py 會從 chat.json 開始重新編號。缺失的編號是指 Telegram 未傳回的訊息（在匯出前已被刪除，或該帳號無法看見）；在私人聊天室和 基本群組中，編號由該帳號的所有聊天室共用，且不會計入缺口。

After reading the history, the export asks Telegram for every absent number again, by number (channels.getMessages, up to 10,000 numbers). The result is in message-ids.json and the report. An empty answer records that the number is unavailable to this account at recheck time; it leaves the cause unspecified. A message returned on recheck is added to the export and marked found_on_recheck.

每份報告均以 開頭。簡而言之 ：先有一段文字，接著說明資料顯示的內容以及未顯示的內容 （帳戶背後的人物、傳輸的完整性、監測前的刪除行為、未附時間戳記的 時間）。 當瀏覽器驗證完印章的 簽名（而非頁面本身）後，該頁面的印章標記會轉為琥珀色：瀏覽器不會為頁面提供其自身的位元組。 只有當 讀者將檔案拖曳至頁面底部的驗證區，且每個位元組均完全吻合，同時 顯示的頁面正是該檔案時，印章才會轉為綠色；否則將轉為紅色。

每份報告均精確標明程式名稱：當收集器從檢出版本執行時對應的 git 提交，或 安裝程式設定的 TGWITNESS_COMMIT，以及其原始檔案的 SHA-256（source_tree_sha256、 路徑的規範 JSON → SHA-256，適用於每個 .py、.js、.css、.html 和 .svg 檔案在 套件中），只要檔案未被修改，檢出該提交即可重現上述內容。 Telegram 客戶端的命名包含其函式庫、API 層及資料中心。當監測開始，以及當聊天 匯出開始與結束時，收集器會向 Telegram 查詢其時間（updates.getState，以 整秒為單位），並記錄 Telegram 的時間減去收集器的時鐘時間，其中包含因 往返傳輸產生的不確定性；報告會在「保管鏈」欄位中顯示這些測量值。 除了訊息的日期外，聊天記錄匯出還會記錄 讀取歷史紀錄的時間點。

離線報告檢視器與歸檔指南#

在開啟 chat.html 或 report.html 之前，請先解壓縮完整的 ZIP 檔案。此檢視器提供搜尋、 篩選、參與者、指標、記錄詳細資訊，以及無需伺服器即可進行的 JSON/CSV 選取功能。請將 viewer/ 和 media/ 置於報告旁。選取項目屬衍生內容：請使用 verify.py SELECTION.json --evidence ARCHIVE.zip 將其與簽名存檔進行比對。 驗證器會檢查報告 ID、簽署金鑰、存檔邊界以及每個選取項目；經編輯、 遺漏或重複的項目將被判定為失敗。選取註記與建立時間仍屬未簽署的元資料。

訊息編號的間隙僅會出現在完整、未經篩選且按升序排列的聊天記錄中。隱藏某個 類別或無法載入某個資料區塊，絕不能將省略的行視為缺少 訊息的證據。搜尋標示功能會針對HTML轉義前的純文字進行操作，並保留字面標記。

瀏覽器會檢查清單簽名、報告 ID 與金鑰，以及所有列出的檔案雜湊值。它 會拒絕模稜兩可或格式錯誤的 ZIP 結構、重複名稱及不安全的路徑，並將檔案 大小限制在 256 MiB 內，且宣告的總內容大小不得超過 4 GiB。若需處理更大的壓縮檔，請使用獨立驗證器。 此瀏覽器檢查功能可補充驗證器對日誌鏈及資料語義的檢查。

README.txt 包含一份入門指南、對齊後的檔案清單、驗證說明及資料 格式說明（均以報告語言撰寫），其後附有完整的英文指南。 SHA256SUMS 涵蓋 其中列出的檔案，但不包括該檔案本身、manifest.json 及 manifest.sig；經簽名的清單 亦涵蓋 SHA256SUMS。請保持原始 ZIP 檔案不變，並將工作檔案儲存於 解壓縮資料夾之外。PDF 報告包含章節書籤，且後續頁面載有案件／報告識別資訊。

匯出時的聊天內容#

聊天室匯出檔案會記錄在匯出開始時，Telegram 針對該聊天室所做的說明：Telegram 自身的 標籤（scam、fake、restricted 及其理由、verified）、使用者名稱、描述、成員 及管理員人數、關聯的討論串、內容保護設定、新成員是否能查看較早的 訊息，以及該帳號從哪則訊息開始能查看歷史紀錄（available_min_id）， 若該聊天室為新建立，則為第一則訊息的 日期，以及聊天室照片的 SHA-256（儲存於 media/）。 它會記錄匯出帳號在聊天室中的地位：角色、加入日期、邀請者，以及若為 管理員，其權限。若 Telegram 拒絕某項請求，則會列出該請求的名稱。

當匯出帳戶為管理員時，匯出過程會將該聊天室的管理員日誌（Telegram 約保留 48 小時）讀取至 admin-log.json：其中包含刪除與編輯的紀錄，以及相關內容與執行該操作的帳戶。這 是唯一一份能明確指出刪除者身分之刪除紀錄。

指標#

報告清單及存檔中以 indicators.csv 、indicators.stix.json （STIX 2.1 ） 以及 indicators.misp.json （MISP 事件）標示，濫用處理部門可據此針對記錄訊息中的以下內容採取行動： 連結與網域（包括隱藏於文字後、按鈕內及連結預覽中的內容）、加密貨幣 地址、Telegram 使用者名稱與邀請連結、電話號碼、電子郵件地址及儲存的圖片。 比特幣、萊特幣、狗狗幣和波場（TRON）地址僅在 Base58 校驗和通過時才會列出， SegWit 地址則需其 Bech32 或 Bech32m 校驗和通過，而 TON 地址則需其 CRC 校驗和通過；EVM 和 Solana 地址則標記為「未經檢查」。 圖片包含 SHA-256 以及一個感知 雜湊（dHash，64 位元），即使經過重新壓縮或調整大小的副本，該雜湊值仍幾乎保持不變。報告會寫入 標記，以防止意外開啟（hxxps[://]example[.]com ）；檔案則保留 原始的數值。 每個指標均標記為「未知」且不適用於自動偵測（STIX 、 indicator_types: unknown 、MISP 、to_ids: false ，分發至自身組織）：被 列出僅表示訊息中包含該指標，並不代表其具有惡意。若連結的顯示文字與實際開啟的 地址不符，該連結將在報告中被標記。

PDF 報告末尾包含一份需由審查員親筆簽署的聲明、供公證人或 法院專家使用的核對清單，以及一個 QR 碼（亦位於首頁），其中包含報告 ID、金鑰指紋及 權威資料的 SHA-256，以便列印本能追溯至其存檔。

事件規範化#

雜湊輸入必須精確包含以下這些欄位：

seq, observed_at, source_at, kind, chat_id, message_id, actor_id, payload, previous_hash

請使用與 Python 相容的 JSON 格式進行序列化，採用 UTF-8 編碼、物件鍵值排序，不進行 ASCII 轉義，不包含無意義的空白字元，且不包含 NaN 或無窮大：

json.dumps(value, ensure_ascii=False, sort_keys=True,
           separators=(",", ":"), allow_nan=False).encode("utf-8")

這些位元的 SHA-256 值即為事件雜湊。簽名採用 Ed25519 演算法對 32 位元原始雜湊位元進行運算，隨後進行 Base64 編碼。第一個 previous_hash 為 64 個零。 序號從 1 開始，並以 1 為單位遞增。所有事件（包括運作 事件）共用同一條鏈。本系統不進行重複傳送抑制：重複 的觀察結果僅代表不同的收據，而非聲稱存在不同的 Telegram 操作。

Telegram 的原始日期為 ISO 字串；二進位欄位則轉為包含 bytes_base64 的物件。訊息內容、實體、媒體描述符、回覆元資料、反應， 以及服務動作，若已提供，皆會保留於原始訊息元資料中。

observed_at 為收集器的 UTC 牆鐘時間。source_at 為提供的 Telegram 日期 （如有）。刪除通知不會提供確切的刪除時間，因此 source_at 將保持為 null。傳輸接收順序未必等同於來源事件 的順序。歷史快照會使用較早的來源日期，但採用當前的觀察時間。

行為者語義#

message.new 中的 actor_id 代表訊息發送者。message.edited 並未推斷出 編輯者；payload.sender_id 則記錄所觀察訊息的發送者。 刪除 actor_id 仍為 null。成員服務訊息會保留發送者與動作 類型，不會將每次移除都視為自願退出。原始參與者 更新會保留所提供的 actor_id。反應快照不會虛構變更行為者。

私人聊天室和一般群組的刪除通知僅包含訊息 ID。 這些聊天室共用一套適用於整個帳戶的 ID 序列，因此一個 ID 代表該 帳戶中的一則訊息。 當具有該 ID 的訊息先前已儲存於此日誌中時， 刪除操作將在該聊天室中以 message.deleted 形式記錄，並使用 payload.chat_resolution 作為方法名稱。從未被儲存過的 ID 則以 deletion.unscoped 形式保存，且不包含 chat_id；系統絕不會進行任何推測。 頻道和超級群組會針對每個聊天室分別編號訊息，且 絕不會以此方式進行配對。當被刪除的訊息是由被監測帳戶發送時， payload.deleted_message_was_outgoing 為 true；但仍未提供刪除者資訊。

An unscoped notice does not establish that a message was never saved: a matching chat may be outside the current observation scope, or a unique match may be unavailable. Recheck absence remains a separate observation from a deletion notification in report counts, filters and labels. A later recovery clears the current missing state while preserving the earlier unsuccessful check in the signed history; neither observation establishes a deletion notice.

Multiple IDs resolved to the same chat from one notification are grouped as deletion.batch, regardless of their count. The notification does not establish that the entire history was cleared, who performed the deletion, or whether it applied to all participants. Saved outgoing messages do not change these limits. Older journals may contain history.cleared events inferred from batches of ten or more IDs, with explanatory text attributing the deletion to the other participant. Those inferences are not supported by the update. Preserve those original signed records, but treat them as grouped deletion notifications; the current interface labels them accordingly.

涵蓋範圍：連續性、缺口及未被偵測的 ID#

每個簽名 ZIP 檔案均包含 coverage.json，HTML 報告開頭會顯示相同的摘要，而 verify.py 會根據 events.jsonl 重新計算該摘要，而非直接信任該檔案：

  • 從 X 到 Y 持續進行監測。一個週期始於 observation.started，並 終止於暫停、停止、Telegram 連線中斷、登出、未經 正常關機的程序啟動，或監測期間超過三分鐘無任何記錄 （每分鐘會寫入一次心跳訊號，因此靜默表示程序已停止、凍結或 電腦進入休眠狀態）。當在「參數」中變更心跳間隔時，每次心跳 都會記錄此變更，且允許的靜默時間將調整為三個間隔，絕不低於三分鐘。
  • 「缺口」欄位列出各期間之間的時間間隔及其原因。若最後 一筆記錄處仍有未填補的缺口，則標記為 not_resumed_by_last_record。
  • 未偵測到的訊息 ID。對於會針對每個 對話進行訊息編號的頻道和超級群組，偵測到的 ID 之間缺失的 ID 會以範圍形式列出。這些 ID 會被報告為 「未偵測到」—— 可能是已被刪除、從未送達，或超出已儲存的歷史紀錄範圍 —— 絕不會直接標示為 「已刪除」。私人對話和一般群組共用全帳戶範圍的序列號，因此單一 對話內的缺口並無特殊意義，亦不會在該處列出。
  • 聊天層級的資料缺口通知（例如 Telegram 在某個 頻道中要求恢復差異）將被計為備註；此類通知不會中斷整體涵蓋範圍。

缺失的訊息編號（gap_summary)#

預覽。 coverage.json → gap_summary 用於統計 Telegram 所分配但此 收集器從未偵測到的訊息編號。Telegram 會針對每個頻道或超級群組編號一次，並針對每個 帳號在私人聊天、機器人及一般群組中各編號一次。兩個已偵測 訊息之間的編號，要麼已被偵測到，要麼缺失；若為連續範圍，則表示 該範圍內所有編號的訊息均已被偵測到。若出現編號缺口，則不指明任何行為者或原因。

領域 含義
status on，或 off 當在「參數」→「差距分析」中關閉時
parameters 產生該結果的參數，以便能夠重現該結果
chats[] 每個頻道或超級群組各佔一筆記錄，每筆記錄均獨立編號
account 整個帳戶範圍內的私人聊天、機器人及一般群組的序列
status （依序列而定） applicable，或 not_applicable 使用 reason
observed_from, observed_to, span 首次與最後一次觀察到的號碼，以及該範圍的大小
observed, observed_without_content 觀察到的數字；僅能透過刪除或重新檢查記錄得知的數字
missing, density, gap_ranges, largest_gap 從未觀察到的數字、其在範圍中所佔的比例、運行次數、最長運行時間
clusters[] 列出的缺漏： low, high, missing，以及相鄰的觀察號碼 after / before 及其觀察時間
service_estimate 僅在啟用時顯示：根據其觀察到的佔比，有多少個缺失的號碼屬於服務訊息。從未從中扣除 missing

有效性源自日誌，絕不預設：

  • 頻道與超級群組的統計是按每則聊天進行計算，在選定聊天的匯出檔案中亦同。 由發送者選定的記錄將作為統計依據 not_applicable.
  • 全帳戶序列僅從 在「全帳戶收集」功能啟用期間收到的第一則至最後一則訊息開始計算，並包含私人聊天、機器人、一般 群組以及該帳戶自身的訊息，且不排除任何此類聊天（scope.changed）。 以 deletion.unscoped 計數的數字均視為已觀察到的訊息，但不包含內容。若僅對選定的聊天室進行匯出或 移交，則無法測量此數值。若「全帳戶收集」功能曾被 關閉後又重新開啟，系統會註明在此期間使用的數字將顯示為空缺。
  • 服務訊息是具有獨立編號的日誌記錄，因此會自行填補空缺； 可選的預估時間僅供上下文參考。

verify.py 重新計算 gap_summary 根據 events.jsonl 使用簽名 coverage.json 成員中的參數（針對較舊的存檔採用預設值），並 在覆蓋範圍摘要中列印該帳戶範圍內的行。該存檔的 get_capture_status（MCP 與命令列）針對某次存取可能讀取的聊天室，會返回相同的測量結果； 而帳戶層級的序列僅適用於涵蓋整個工作區的存取。

Repeated observations of one service message count once, and the account service estimate uses only numbers inside the measured range. An applied scope must explicitly preserve the account's own messages before account-wide measurement is enabled; older records without that information cannot establish this condition. Stopped observation does not extend the measured range, and resuming it is noted. The live archive query has a time budget, including its database scan, and marks an unfinished measurement as partial.

Telegram documents the separate message ID sequences. These numbers describe observations; they do not identify a deletion actor or establish why a number is absent.

當 Telegram 停止接受該帳戶時，結束監測的 coverage.gap 記錄 會攜帶 cause（account_banned、account_frozen、account_deleted、session_duplicated、 session_revoked、session_expired、session_ended 或 not_authorized）以及 Telegram 錯誤；verify.py 則標示該週期結束的原因。

Coverage combines recorded observation periods, interruptions and message outcomes. Assess it together with the selected chats, period and attachment policy; continuous operation alone does not establish complete delivery of Telegram updates.

製作人#

證據 ZIP 檔案、聊天記錄匯出檔、Witness 日誌以及 人員檔案的聲明中所包含的簽名清單中，皆載有 producer ：軟體名稱、版本、專案（PhishDestroy）、 官方網站及原始碼儲存庫。HTML 報告中亦顯示相同內容，而 verify.py 會將其列為已驗證項目之一。 在此欄位建立之前所製作的檔案，其驗證結果與 先前相同，且報告中會標示為未指明產生者。

每個 observation.started 記錄亦會標明進行監測的 Telegram 客戶端：其 api_id （絕非雜湊值），無論該客戶端是內建的公開鍵對還是營運商自有的應用程式， Telegram 連線請求中傳送的客戶端描述，以及連線 路徑的類型與 IP 模式（不含代理伺服器地址或密鑰）。 該報告與custody.json列出了每個 不同的客戶端及路由，並標註其記錄時間，以及未列出的代理未回應的時間點， 以及Telegram偵測到伺服器位址的時間。此前記錄的日誌皆有載明。

人物簡介#

系統會應要求，根據日誌中已有的 單一聊天記錄，建立一個個人檔案檔案（tgwitness-dossier-v1，JSON）；不會從 Telegram 擷取任何資料，且個人檔案內容絕不會 寫入日誌（啟用或停用個人檔案的動作會以 dossier.changed 形式記錄）。 針對每位擁有已儲存訊息的使用者，系統會列出其姓名與使用者名稱歷史紀錄、Telegram 標記 （機器人、詐騙、假帳號、付費帳號、已驗證、受限、已刪除）——以儲存當下的狀態為準——以及個人資料 照片 ID、來自本地頭像快取中與該頭像相似的頭像之 SHA-256 及感知雜湊（pHash，相容於 imagehash.phash）， 活動紀錄（第一則與最後一則訊息、 數量、已編輯及已刪除的分享、按 UTC 小時劃分的訊息）、誰回覆了誰、該人物曾發文的 中該人曾發文的對話，以及被提及的錢包（BTC、EVM、TRON、TON、LTC、 DOGE、XMR、SOL；Base58Check 地址已通過校驗和驗證）、電話號碼、使用者名稱及 連結，包括隱藏於文字後面的連結。

每個事實都會列出其來源的日誌記錄（seq），而 record_hashes 則包含 每個被引用的記錄的雜湊值。該陳述已使用工作區金鑰進行簽署：

python verify.py tgwitness-dossier-CHAT.json --fingerprint TRUSTED_SHA256 --evidence tgwitness-evidence.zip

會檢查簽名、驗證證據匯出檔本身（包含簽名、雜湊鏈及檔案）， 並確認每個被引用的記錄在同一工作區的該匯出檔中均完整無缺且未經修改。頭像雜湊值會標示為來自本地快取 （而非日誌記錄）。提及內容屬模式匹配——僅為待查證的線索，而非經核實的事實。 各聊天室皆可個別啟用個人檔案功能，可匯出為帶有密碼的 AES-256 加密 ZIP 檔案，且 當個人檔案功能關閉，或該聊天室從來源中移除時，相關資料即會被刪除。

獨立見證人#

會將「證人日誌」（tgwitness-witness-v1）及其頻道貼文，與 透過 verify.py --witness … --channel … 匯出的證據進行比對；請參閱「獨立證人」。

清單與檢查點#

manifest.json 包含格式、匯出時間、公鑰、指紋、日誌 長度、首部雜湊、範圍、產生者、限制，以及除 manifest.json 和 manifest.sig 本身以外 每個內容成員的 SHA-256 雜湊值。 manifest.sig 是對規範化 manifest JSON 進行 Base64 編碼的 Ed25519 簽名。 驗證器會拒絕處理意外出現或缺失的成員、名稱重複、檔案損毀、 序列/鏈路中斷、簽名無效，以及與提供的檢查點不匹配的情況。 它絕不會提取存檔路徑。它將聲明總未壓縮大小限制為 4 GiB； 若提高 Parameters 限制，--max-gib N 允許建立更大的存檔。

Run verification from your installed TgWitness version or a reviewed checkout. The copy included in an archive supports portable use; check that copy against your trusted installation before executing it.

A checkpoint signs a statement containing the public key, journal length, head hash, and creation time. The verifier can check that a later archive contains the same prefix. Retain the checkpoint outside the collector, so later verification compares the archive with a reference held separately from it.

驗證範圍#

Verification checks the archive and the collection mode used to produce it. Choose the mode whose trust boundary matches the case, then retain its verification inputs.

收集模式 驗證者檢查的內容 驗證輸入與信任邊界
本地工作區 Record signatures, hash chain, manifest and attachment bytes Independently retained collector fingerprint; the host administrator controls the local signing key
具備獨立見證者的本機工作區 檔案校驗，以及與見證者所保留的早期日誌前綴是否一致 Separately trusted witness key and records; the checkpoint binds the prefix already observed
GitHub Actions 擷取 GitHub attestation of the archive digest, approved workflow and collector commits, hosted runner, fresh session/key origin and internal archive integrity Trusted verifier policy, caller repository and GitHub attestation bundle; collection runs under the pinned workflow
雲端部署 Provider lifecycle and access records, firewall and Cloudflare state, plus the collector's signed run record Read-only queries to the provider and Cloudflare; availability of individual checks depends on the provider
Intel TDX 機密虛擬機器 Quote signature and platform status, binding to the collector statement, compose and OS measurements Intel trust chain and expected deployment measurements; retain the results of every required TDX check

In sealed acquisition, the approved collector receives data through an authenticated Telegram connection inside the verified environment. Attestation binds the archive to that execution, so verification covers acquisition as well as later file integrity. This relies on the approved code and the platform trust chain listed above. GitHub capture verification requires a session created inside the run and rejects imported-session captures.

The run receipt records the collector version, file hashes and startup settings. GitHub provenance and TDX measurements provide the environment checks; the validation record identifies tested configurations.

TgWitness signs the observations it collects; Telegram and message authors do not issue these signatures. In a local workspace, material created before the first independent checkpoint still depends on the collector and its key holder. Coverage records describe the selected scope and collection outcomes, while verified external timestamps anchor the committed archive or journal boundary in time.

附件#

檔案在 media/ 目錄下以 SHA-256 雜湊值作為位址。media.saved 事件會將雜湊值與 位元組長度連結至特定的訊息事件。原始檔案名稱屬於元資料，絕非 本機路徑。 媒體資料的位元組會以非同步方式下載，因此若訊息被立即刪除，可能會導致 無法擷取。系統會顯示以下結果：收集功能已停用、檔案過大／大小未知、下載失敗， 以及下載中斷。若程序發生當機，可能會留下 未被引用的部分檔案；這些檔案不會包含在匯出檔案中。

ZIP 匯出工具會根據檔案名稱驗證儲存的媒體檔案。JSONL、CSV 和 HTML 匯出格式會驗證事件簽名，但不包含媒體位元組。衍生報告 僅供方便使用；events.jsonl 才是具有權威性的事件表示形式。

完整聊天記錄匯出會將工作區附件設定中的附件儲存至 media/ 目錄，並以 SHA-256 作為檔案名稱。 chat.json 中的每則訊息記錄會標示其檔案名稱（file、 file_sha256）或缺失原因（file_status），並一併記錄讀者所見的 文字周邊內容：文字後方的連結、轉發來源、機器人按鈕、簽名、瀏覽次數以及 自動刪除計時器。verify.py 會檢查每個被標示的檔案是否存在於該雜湊值對應的 簽名清單中。

持久的蒐集與處理收據 (0.2)#

媒體任務及其訊息事件提交將整合於單一交易中。 該任務儲存 原始 TL 訊息描述符；經簽名的觀察記錄會綁定其 SHA-256 值、帳號 及大小政策。還原功能會在下載前驗證該綁定關係。系統絕不會擷取 當前訊息，也不會默默替換為較新的附件。中斷的任務 會重新嘗試執行，而永久失敗則仍為明確的結果。

Each workspace has its own journal and signing identity. A process.started event includes a run ID, local clocks, dependency versions, source-file hashes, initial account/scope, and capture settings. Heartbeats include the run ID, monotonic time, and queue state. The run receipt can also be downloaded as a separately signed statement. For verification of the execution environment, pair it with the GitHub attestation or TDX checks described in Verification scope.

Automatic checkpoints are retained locally on startup, every five minutes while observing (Parameters → Signed checkpoint every), and on orderly stop. Startup verification and export compare the journal against the latest retained local checkpoint. This can detect a database rollback when the checkpoint survives. Independent retention keeps that reference available outside the workspace; a verified external timestamp additionally anchors it in time.

重新啟動後，系統將恢復已儲存的 Telegram 更新位置（catch_up_from 位於 observation.started），並請求補取遺漏的更新。定期重新檢查會記錄 message.recovered 以追蹤遺漏的訊息，並在 Telegram 不再 返回已儲存訊息時記錄 message.missing_on_recheck；後者並非刪除通知，亦未指明刪除者或時間。

站外備份與還原 (S3)#

離線副本（「匯出」，預設為關閉）會將日誌片段、保留檔案、檢查點 及其時間戳記，以及完成的聊天記錄匯出上傳至 S3 相容儲存空間，並在 AES-256-GCM 加密，並使用儲存於工作區金庫中的金鑰；若儲存桶支援，則會套用 Object Lock 保留機制。若未下載金鑰，則無法讀取該副本。請使用 python -m tgwitness.replica restore --key-file KEY.json --out DIR 進行還原與驗證。

還原功能需要一個空的普通資料夾。下載的檔案及解密後的物件會暫存於私有 臨時儲存空間中，直至整個日誌及每個保留的檢查點均通過驗證為止。不安全的物件 路徑、不一致的區段範圍，以及長度短於檢查點的日誌均會被拒絕；驗證失敗時 將不會發布任何還原檔案。 保留檢查會將回傳的「物件鎖定」 模式與日期，與上傳時傳送的截止時間進行比對（容許一秒的四捨五入誤差）。已過期、 無效或縮短的截止時間均不視為已驗證。狀態會回報該次上傳過程中 讀取到保留狀態的抽樣物件。

若本地媒體檔案遺失或損毀，系統會將其標記為當次處理的錯誤，並將媒體游標停留在 該處之前，以便在下一次處理時重新嘗試讀取該檔案；其後面的檔案、檢查點及匯出內容仍會 照常複製。還原過程會 將所有已保存媒體的參照與解密後的雜湊值及記錄的大小進行比對。 來自中斷上傳的 相同重疊日誌區段將被去重；衝突的重疊區段則會被拒絕。 上傳過程中建立的檢查點會被延遲，直到其所涵蓋的日誌記錄已被 複製為止，因此完成的處理階段不會在日誌之前發布檢查點。

串流匯出快照#

串流匯出採用穩定的 SQLite 讀取快照。當下載完成時，其起始點可能比 當前的即時日誌更早。在此快照之後建立的檢查點 可能會正確地顯示該存檔較短；請與位於匯出前綴處或之前的檢查點 進行比較，而非任意的較晚檢查點。

RFC 3161 準備與回應驗證 (0.2)#

「證據模式」（預設為關閉）僅會透過工作區路徑（絕不經由 MTProxy），將每個簽名檢查點的 SHA-256 雜湊值傳送至列出的 RFC 3161 權威機構及 OpenTimestamps 日曆。 回覆內容將以 checkpoints/anchors/ 格式保存、匯出，並由 verify.py 進行驗證（--tsa-ca 負責 驗證 TSA 簽名；使用 ots upgrade 和 ots verify 確認 OpenTimestamps 證明）。

該面板會準備一個請求存檔，其中包含標準的 checkpoint.json 位元組、 SHA-256 訊息指紋以及 timestamp.tsq 中的隨機非ce值、校驗和與操作說明。 此過程不會發出任何網路請求。此準備程序並非可信時間戳記。

python -m tgwitness.anchor verify 會對 OpenSSL 進行兩次 ts 驗證：一次針對檢查點 位元組，一次針對原始請求。必須明確指定可信賴的 CA 檔案； 內建憑證不會自動被視為可信。在命令列介面（CLI）中， 請求檢查為可選功能，因此請保留並提供 --request 參數以檢查非ce值。結果會顯示 是否已進行檢查。收集器的檢查點簽名與日誌仍須 透過可信的收集器指紋分別進行驗證。

驗證程序會檢查回應簽名、檢查點位元組，以及（若已提供） 在指定 CA 信任框架下的原始請求。憑證撤銷檢查以及憑證過期後的 長期歸檔驗證，不在本驗證器的處理範圍內。 請參閱相關程序與驗證結果。

證據模式下的可選記錄：drand 及 Telegram 裝置#

另有兩項記錄功能可與時間戳記在同一輪處理中執行。這兩項功能預設皆為關閉狀態， 且僅在「證據模式」開啟時才會生效：[進階] → [證據與備份] → [更多見證者] · 可選， 或 "drand": true 以及 "devices": true 在 POST /api/evidence中。其中一項功能發生錯誤並不會阻礙 另一項功能或時間戳記的運作；面板會在表單下方顯示各項功能的最新結果。

drand （beacon.drand ）。每次處理都會將最新一輪的 drand quicknet（即「熵聯盟」的公開 隨機數，每 3 秒一輪）寫入日誌：chain 、 round 、randomness 、signature 、round_time 以及回應的 relay 。一個經過驗證的 不可預測的輪次，為後續透過雜湊連結的材料提供較早的時間參考點。 後續檢查點上的經驗證時間戳記則提供時間上限參考。這些檢查 界定了鏈結資料的範圍；資料收集的覆蓋範圍則另行評估。收集器會先查詢 drand.cloudflare.com ，接著透過工作區路徑查詢 Protocol Labs 的中繼站，每輪執行一次請求。

verify.py 會檢查每個隨機數是否為其簽名的 SHA-256 ，並確認 輪次時間是否正確，同時回報輪次數、最長未產生隨機數的區間，以及 收集器時鐘相對於 drand 的滯後程度。 它不會檢查 BLS 簽名。--check-drand 會將輪次與 Cloudflare 中繼站、Protocol Labs 中繼站，或是長日誌中所有中繼站， 或隨機抽取的 100 個樣本進行比對；若有任何一輪次不符，驗證即告失敗。

、Telegram 裝置、（account.devices）。每次掃描都會讀取該帳戶與 account.getAuthorizations 的會話，以及「設定」→「裝置」中顯示的 Telegram 清單，並完整記錄： 若自上次處理後有所變更，則完整記錄該清單，並包含added與removed的 會話雜湊值；否則僅記錄其數量及SHA-256。裝置型號、平台、應用程式及版本、 建立時間與最後活動時間、國家及地區均予以保留；IP 位址則不予保留，因為 證據匯出後便不再由您掌控。 收集器自身的會話始終處於活躍狀態，因此 僅有其他會話的活動才被視為變更。verify.py 會回報清單 被記錄的頻率，以及每個新建立與結束的會話。它僅在觀察程序執行期間讀取該清單。

他們未展示的內容：drand 僅能證明記錄相對於公開時間的順序， 而裝置清單是 Telegram 透過收集器發出的聲明，並由收集器簽署， 如同其他所有記錄一樣。

Cloudflare Gateway 日誌 (cloudflare.gateway_dns)。 對於透過 Cloudflare Gateway（ Gateway DNS ）進行解析的伺服器，每次 複製都會擷取自上次複製以來 Gateway 所記錄的內容：每個時間窗（最長三 小時）對應一筆記錄，包含 from、until、location_id、伺服器的 address（若已設定），以及 queries（當其值為 [at, name, type, rcode, decision, colo] 時，即使該欄位為空亦然）。 請在 下設定 Cloudflare Gateway 日誌 ：帳戶、位置、可選地址以及一個唯讀代幣（帳戶 分析讀取權限；零信任 PII 讀取權限，用於保留共享位置中的一個地址）。控制面板會在儲存前透過單一請求驗證 這些資訊；憑證始終保持加密狀態，且絕不會進入日誌。 verify.py 列出時間窗、查詢最頻繁的名稱，以及任何未被副本涵蓋的時間點；若某筆記錄 的計數與其查詢不符，則會失敗。 若某個時間窗在單一秒內包含超過一頁的 查詢，則保留該頁並標示其餘部分遺失。該副本是 Cloudflare 透過收集器傳回的回應，並由收集器簽署；在 24 小時內，任何持有 唯讀憑證者皆可將其與 Cloudflare 進行比對。
