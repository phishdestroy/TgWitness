# Project review — 29 October 2026

Initial review of the working tree on Windows 11 / Python 3.12.10. Application code was
not changed during the initial review. All Telegram accounts, chat content and remote storage
used by the probes were synthetic. No live Telegram actions were performed.

The findings and original test results below describe the state before the follow-up fixes.
They exposed failures in chat routing, action retries, rechecks and backup verification that
the original happy-path tests missed.

## Follow-up fixes

All eight finding groups have been addressed in the working tree:

## Findings

### 1. P1 — Sending during a chat switch can send the old draft to the new chat

Location: `tgwitness/static/app.js:1649` and `tgwitness/static/app.js:2004`.

`openChat()` changes `state.chat` immediately, then awaits the new message list. Until
that response arrives, the old chat heading, draft and enabled Send button remain on
screen. The submit handler reads the already changed `state.chat`.

Browser reproduction: hold the new chat's `/messages` response, then submit the existing
draft. The visible heading was **A synthetic bot**, intended recipient `888`, but the
successful API receipt identified group `-1000000000123` as the recipient.

Fix direction: bind the composer to an explicit account/chat identity, and invalidate or
disable it synchronously before switching destinations. Sending must use that bound
identity and refuse a mismatch while a switch is pending. Preserve drafts per destination
only if that is a deliberate product decision.

### 2. P1 — Callback actions can repeat despite the request-ID protection

Locations: `tgwitness/static/app.js:1994`, `tgwitness/interactions.py:226`,
`tgwitness/collector.py:411`.

Two independently reproduced paths:

- The POST succeeds, but the subsequent status refresh fails. The panel removes the
  request ID before refreshing and displays the refresh error instead of the successful
  action receipt. Retrying the visible button gets a new ID and performs a second callback.
  Browser reproduction recorded one callback after the first click, a hidden success
  receipt and an error toast, then two callbacks after the retry.
- The shared Telethon client enables RPC retries, with a default of two. Its installed
  `_call()` implementation retries `GetBotCallbackAnswerRequest` after `RpcCallFailError`.
  This method has no `random_id` for application-level deduplication. A probe using the
  actual installed Telethon call implementation and a fake sender observed two transport
  attempts for one invocation. The first attempt's side effect can be ambiguous.

Fix direction: show and retain the action receipt independently of refresh operations;
do not turn a display-refresh failure into an apparent action failure. Use a deliberately
controlled retry policy for non-idempotent Telegram actions, retaining an unknown outcome
when necessary. A browser request ID alone does not control retries inside Telethon.

### 3. P1 — Backup restore writes outside the requested output directory

Location: `tgwitness/replica.py:328`.

Object names supplied by the storage provider become filesystem paths without a containment
check. Download and cleartext temporary files are opened before object authentication.

Reproduction: storage listed `audit/../outside.bin.tgwr` and returned arbitrary invalid
ciphertext. Restore correctly rejected decryption, but had already created
`outside.bin.download` outside the requested restore directory, containing the remote
bytes. This probe stayed within a newly created audit directory.

Fix direction: validate the prefix, allowed object categories and every relative path;
reject traversal, absolute paths, drive paths and symlink escapes before creating directories
or files. Stage downloads in a private directory with safe generated filenames.

### 4. P1 — Restore accepts a journal shorter than its retained checkpoint

Location: `tgwitness/replica.py:363`.

Restore skips a checkpoint whose `event_count` exceeds the downloaded journal length,
then reports the total number of checkpoint files as `checkpoints_verified`.

Reproduction: a correctly signed checkpoint covered two events, while storage supplied
only the first valid event. Restore returned success with `events=1` and
`checkpoints_verified=1`. The checkpoint that would prove truncation was not checked.

Fix direction: verify the retained checkpoints and reject a journal shorter than a trusted
checkpoint. Count only checks actually performed. If incomplete restore is ever supported,
make it an explicit result with missing ranges, never a successful complete verification.

### 5. P1 — Rechecks miss attachment replacements and removed bot keyboards

Location: `tgwitness/collector.py:1280`.

The recheck comparison only considers message text and buttons. It also requires the
current message to have an edit date or reply markup before comparing it at all.

Reproductions:

- Document ID changed from `500` to `501`, with unchanged caption and a later edit date.
  Recheck recorded zero edits, leaving only the original attachment observation.
- A saved bot keyboard was removed, and the current message had no edit date or reply
  markup. Recheck recorded zero edits and retained the old buttons as current.

Fix direction: compare the current observable content against the saved version even
when markup has disappeared. Include attachment identity and other relevant content
fields in the comparison, while keeping incidental transport changes out of versioning.

### 6. P2 — Recheck ignores the setting that excludes outgoing messages

Location: `tgwitness/collector.py:1258`.

Live message handlers call `own_skipped()`, but history recovery inside `recheck_chat()`
does not. With `scope.own_actions=false`, a synthetic missed outgoing message was still
saved as `message.recovered`.

Fix direction: apply the configured outgoing-message policy consistently to rechecks
and other automatic intake paths. Explicit panel actions can remain separately journaled
as documented, but background recovery must not silently override the scope setting.

### 7. P2 — Expired Object Lock retention is reported as verified

Location: `tgwitness/replica.py:208`.

The check tests for a nonempty retention date and matching mode but does not compare the
date with the requested retention period.

Reproduction: request COMPLIANCE retention for 365 days; storage returns
`retain_until=2000-01-01T00:00:00Z`. The result still contains `verified=true`.

Fix direction: parse and validate the returned deadline against the actual requested
deadline, with a documented clock tolerance. Missing, invalid, expired or shortened
retention must not count as verified.

### 8. P2 — The current checks pipeline is failing

Locations: `tests/test_i18n.py:28`, `tools/check_browser.py:148`,
`.github/workflows/checks.yml`.

The full Python run fails its dictionary-coverage test. The general browser acceptance
also stops at missing static-page dictionary entries, including the dedicated-account
guide. These are pre-existing translation coverage gaps, separate from the new English
mini-client controls. Later checks in that browser run do not execute after the assertion.

Fix direction: reconcile the actual supported-language policy with the completeness checks.
Do not report the whole checks pipeline as passing while these failures remain.
