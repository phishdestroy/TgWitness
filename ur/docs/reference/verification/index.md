## Live server journal inventory · 1 November 2026

At approximately 19:15 UTC, sequential read-only SQLite `query_only` queries counted events in ten workspace databases on a running server. Collection continued during the queries, so this is not an atomic snapshot across workspaces.

| Observed across the ten workspace databases | گنتی |
| --- | --- |
| Workspaces with at least one `message.new` event | 8 |
| Journal records, including operational events | 1,610,818 |
| `message.new` events | 900,232 |
| `message.edited` events | 80,683 |
| `message.deleted` events | 400,536 |
| `message.recovered` events | 53,403 |
| `message.snapshot` events | 2,183 |
| `media.saved` events | 50,418 |
| `media.failed` events | 5,575 |
| `coverage.gap` events | 11 |
| Database bytes, excluding WAL files and media | 7,909,003,264 |

These are **event counts**, not unique messages, people or media files. The same message can appear in more than one workspace, and an edit or deletion can produce another journal event. `media.failed` counts historical failure events, not the current media queue. The queries did **not** newly verify signatures and the full hash chain of all 1,610,818 records, measure delivery or throughput, or establish that every Telegram event was captured. No message content, account or chat IDs, workspace labels, credentials or private files are published here.

At this review, the separately configured public monitor covered three sources: one capture response was OK and two reported `no_response`. That monitor is not a ten-workspace health summary. `no_response` means the observer could not obtain a response at that check; it does not establish message loss. The smaller 29 October test below has its own explicit signature and hash-chain verification.

## Recent offline and fault-injection checks · 1 November 2026

These checks use fictional data and local files; they add regression evidence for the current source, not another live Telegram delivery measurement:

| چیک | What it exercised |
| --- | --- |
| [Source archive](https://github.com/phishdestroy/TgWitness/blob/main/tools/check_source_archive.py) | Two builds with identical source bytes but changed file times produced the same ZIP and checksum. Exact archived bytes and file hashes matched; private test files stayed out. A simulated write failure left the previous archive and checksum intact. |
| [Account export recovery](https://github.com/phishdestroy/TgWitness/blob/main/tools/check_account_export_recovery.py) | A simulated disk error on the second ZIP member left no published or partial ZIP. Resume kept every signed receipt byte-identical, produced an independently verifiable archive using the expected signing fingerprint, and retained the synthetic coverage gap as a partial result. Scale assertions guard against repeated task and receipt scans as histories grow. |
| [Minimized disclosure privacy](https://github.com/phishdestroy/TgWitness/blob/main/tools/check_disclosure_privacy.py) | Synthetic Unicode names and aliases, nested metadata, unknown senders and media fields were checked in all three identity modes and with text omission. A masking-limit failure did not silently weaken redaction; the original signed account export stayed unchanged. |
| [Linux media decoder and OCR](https://github.com/phishdestroy/TgWitness/blob/main/tools/check_media_worker.py) | A [Linux Docker CI check](https://github.com/phishdestroy/TgWitness/actions/runs/41341200341/job/124951395192) at commit `5a9e0814` passed generated Ogg/Opus, MP3, M4A, MP4 with video, WAV and FLAC inputs; forged-duration and secondary-file-reference controls; and 48 mutated parser fixtures (34 rejected, 14 decoded within bounds). Real Tesseract OCR ran with original bytes unchanged. The decoder and OCR ran in network-isolated containers without a Whisper model. |

The checks run in the [pull-request](https://github.com/phishdestroy/TgWitness/blob/main/.github/workflows/pr-check.yml) and [full Checks](https://github.com/phishdestroy/TgWitness/blob/main/.github/workflows/checks.yml) workflows. They test these failure boundaries, not every possible storage failure or whether a disclosure is automatically safe to publish. The media check does not measure speech recognition accuracy or Telegram delivery. Review each derivative before sharing.

## پاس ورڈ سے محفوظ شدہ ایکسپورٹ libarchive کے ساتھ کھولا گیا · 29 اکتوبر 2026

ایک آرکائیو جو ایکسپورٹ انکرپشن کوڈ (WinZip AES-256، وہ فارمیٹ جو 7-Zip اور WinRAR پڑھتے ہیں) کے ذریعے لکھا گیا تھا، Windows `tar` (bsdtar 3.6.2, libarchive) کے ساتھ کھولا گیا۔ صحیح پاس ورڈ کے ساتھ نکالی گئی فائل کا اصل SHA-256 سے میل تھا؛ غلط پاس ورڈ کے ساتھ "Incorrect passphrase" کی پیغام کے ساتھ مسترد کر دیا گیا۔ 7-Zip اور WinRAR خود چلائے نہیں گئے۔

## بلٹ ان عوامی MTProxy فہرستیں · 29 اکتوبر 2026

یہ اصل دستی انتخابی بلڈ کا تاریخی ٹیسٹ ریکارڈ ہے۔ موجودہ خودکار پول اور آئی پی موڈز کے لیے [کنکشن سیٹنگز](https://phishdestroy.github.io/TgWitness/ur/docs/reference/connection/#ip-modes) دیکھیں۔ نیچے دیے گئے اعداد و شمار اور غیر معاونت یافتہ خصوصیات اسی آزمائے گئے ریویژن سے متعلق ہیں۔

ایک بنڈل شدہ عوامی سنپ شاٹ اور SoliSpirit/mtproto اور zakky8/mtproto-proxy-pro سے واضح HTTPS ریفریش شامل کیا گیا۔ اس ہوسٹ پر، ایپلیکیشن ڈاؤن لوڈر نے 29 اکتوبر 2026 کو 12:58 UTC پر دونوں فیڈز کامیابی کے ساتھ حاصل کیے: فلٹرنگ، ڈی ڈپلیکیشن اور فی ماخذ 64 انٹری کی حد کے بعد **118 منفرد مطابقت پذیر اینڈ پوائنٹس**۔ یہ صرف فہرست بازیافت کی تصدیق کرتا ہے، نہ کہ ان اینڈ پوائنٹس کے ذریعے کنیکٹیویٹی یا پیغام رسانی کی۔ اس کام کے دوران کوئی حقیقی اکاؤنٹ درج شدہ پروکسی سے منسلک نہیں کیا گیا تھا۔ [آپریٹر اور صارف گائیڈ](https://github.com/phishdestroy/TgWitness/blob/main/docs/ru/PROXIES.md)۔

ناکام/خالی/غیر مطابقت پذیر ماخذ کے جوابات پچھلی اندراجات اور تاریخیں برقرار رکھتے ہیں۔ اپ ڈیٹس منتخب کردہ راستے کو تبدیل نہیں کرتے ہیں۔ عوامی پتے کی تصدیق کی جاتی ہے اور منتخب کرنے پر IPs کو پن کیا جاتا ہے؛ آپریٹر/مینوئل راستے الگ رہتے ہیں۔ کنکشن پروب اب اکاؤنٹ لاگ ان سے پہلے پینل میں دستیاب ہے۔ جعلی TLS ee اور خودکار پروکسی انتخاب کی حمایت نہیں کی جاتی۔ آپریٹر کا کیٹلاگ سبسکرپشنز کو مکمل طور پر اووررائڈ کرتا ہے۔

- مکمل سوئٹ: **366 پاس، 3 چھوڑے گئے**، 287.94 سیکنڈ۔ موجودہ انحصار کی انتباہات اور پلیٹ فارم چھوڑنے کے اقدامات برقرار ہیں۔ آخری پبلک-لسٹ/مقامی کاری ریگریشن: **36 پاس**، بشمول غیر درست ڈاؤن لوڈ-پراکسی پورٹس کی مستردگی؛ یہ مکمل سوئٹ کے ساتھ اوورلیپ کرتا ہے۔
- براؤزر کی منظوری انگریزی/روسی، ہلکے/گہرے رنگ میں 390/1440 پکسلز پر: مربوط اختیارات، کھولتے وقت کوئی بیرونی درخواست نہیں، واضح ریفریش، ناکامیوں کے دوران راستے اور کیش برقرار رکھنا، لاگ ان سے پہلے جانچ، تاخیر شدہ جوابی ورک اسپیس کا علیحدہ کرنا، ماخذ کی تفصیلات اور لے آؤٹ/کنٹراسٹ۔ کوئی جاوا اسکرپٹ کی غلطیاں یا بیرونی براؤزر کی درخواستیں نہیں۔
- تمام 13 لوکیشنز کے لیے حتمی جامد ترجمے کی کوریج منظور کر لی گئی؛ نئی کاپی کو روسی میں ترجمہ کیا گیا ہے اور دیگر جگہوں پر واضح انگریزی متبادل فراہم کیے گئے ہیں۔ اپ ڈیٹ شدہ بلٹ ان گائیڈ نے دونوں تھیمز میں لے آؤٹ/کنٹراسٹ چیکس پاس کر لیے۔

براہِ راست Auth Key فلو کو مصنوعی شناختی دستاویزات کے ساتھ حقیقی امپورٹ اور اجازت کے اینڈ پوائنٹس کے ذریعے آزمایا گیا۔ چیکز میں نامکمل کیز، DC کی کمی، غلط User IDs، اکاؤنٹ کی شناخت میں عدم مطابقت، محفوظ شدہ API شناختی دستاویزات، درخواست کی ظاہر ہونے والی پیش رفت، خفیہ کلیئرنگ، اور ترمیمات یا طریقہ کار کی تبدیلیوں کے بعد تاخیر سے آنے والے جوابات شامل ہیں۔ تمام چار سائن ان طریقوں کو 320، 390، اور 1440 پکسلز پر چیک کیا گیا۔ فائل پِکر فارمیٹ گائیڈنس سے پہلے آتا ہے، اور کنیکٹ بٹن ابتدائی 844-پکسل ویوپورٹ میں فٹ بیٹھتا ہے جب API سیٹنگز بند ہوں۔ اس UI ایکسیپٹنس رن میں اصلی آتھ کی (Auth Key) کی کوئی توثیق نہیں کی گئی۔

پینل ریفریش کو دونوں براؤزر سوٹس کے ساتھ دوبارہ چیک کیا گیا: کسی بھی صفحے کی جاوا اسکرپٹ کی غلطیاں یا بیرونی درخواستیں نہیں دیکھیں گئیں۔ اکاؤنٹ سوٹ اب ایک API ID/ہیش جوڑا چسپاں کرنے، فیلڈز کو تبدیل کیے بغیر خراب یا متعدد جوڑوں کو مسترد کرنے، صرف میٹا ڈیٹا کی رہنمائی کرنے، اور سائن ان طریقہ کار میں تبدیلی یا دستی کریڈینشل ترمیم کے بعد پرانے امپورٹ جوابات کو نظر انداز کرنے کا احاطہ کرتا ہے۔ سیٹ اپ گائیڈ، واضح آغاز/وقف، خالی تلاش کی بازیابی، اور آخری کنکشن/مقامی گائیڈ لے آؤٹ اور 320، 390، اور 1440 پکسلز پر ٹھوس متن کے کنٹراسٹ کے لیے چھ اضافی مخصوص چیک پاس ہوئے۔ براہِ راست لاگ ان کی اپ ڈیٹ ایک واحد فون/کوڈ-درخواست آپریشن شامل کرتی ہے اور فون، QR، اور سیشن لاگ ان کے لیے موجودہ ورک اسپیس کے محفوظ شدہ API جوڑے کو دوبارہ استعمال کرتی ہے۔ اوپر دیے گئے مکمل پائتھن سوئٹ میں نئی مستقل مزاجی، جزوی اسناد کی تردید، اور ورک اسپیس علیحدگی کے ٹیسٹ شامل ہیں۔ براؤزر کی جانچ میں براہِ راست فون انٹری، محفوظ شدہ اسناد کے دوبارہ استعمال، صرف میٹا ڈیٹا پر مبنی روٹنگ، ایک بٹن سے فائل کی اجازت، اور ڈپلیکیٹ اکاؤنٹ کی مستردگی شامل ہیں۔ سادہ پینل-ٹوکن اور فون فارموں کو بھی 320، 390، اور 1440 پکسلز پر ابتدائی اسکرولنگ کے بغیر چیک کیا گیا۔ ایک مطابقت چیک نے تصدیق کی کہ براہِ راست فون فارم پہلے کے کنفیگر/کوڈ اینڈ پوائنٹس استعمال کر سکتا ہے جبکہ ایک پرانی پراسیس ابھی بھی چل رہی ہو۔

ایک صارف کی فراہم کردہ اکاؤنٹ کو عوامی ٹیسٹ فکسچر کے علاوہ، علیحدہ طور پر چیک کیا گیا۔ اس کے Telethon، Pyrogram، اور TData ان پٹس ایک ہی اجازت نامے پر حل ہوئے؛ ہمراہ JSON نے API کی تصدیق نامے فراہم کیے۔ تمام چار فائلیں 0.6.0 پینل کے ذریعے لوڈ کی گئیں اور ٹیلیگرام نے متوقع عددی اکاؤنٹ آئی ڈی کی تصدیق کی۔ ماخذ فائلیں بغیر تبدیلی کے رہیں۔ کوئی ذرائع منتخب نہیں کیے گئے اور مشاہدہ بند رہا۔ یہ ایک امپورٹ/لاگ ان کی مثال کو ثابت کرتا ہے، نہ کہ لائیو کلیکشن، بازیابی، یا صلاحیت کو۔

ٹیلیگرام نے ایک حقیقی QR ٹوکن بھی جاری کیا، جسے اسکین کیے بغیر منسوخ کر دیا گیا۔ مکمل QR تصدیق اور 2FA کے عمل کو مصنوعی کلائنٹس کے ساتھ آزمایا گیا؛ حقیقی ٹیلیگرام ایپ کے خلاف موبائل تصدیق ایک علیحدہ منظوری کا مرحلہ ہے۔ عوامی فائلوں میں کوئی حقیقی اکاؤنٹ شناختی نمبر، راز، یا اسکرین شاٹس شامل نہیں ہیں۔

لانچر اپ گریڈ مکمل ہو گیا؛ ماخذ، انسٹال شدہ میٹا ڈیٹا، اور تیاری کا نشان رپورٹ 0.6.0، کے ساتھ qrcode 8.2 اور ایک کامیاب `pip check`۔ انسٹال شدہ پہیہ پینل اور رہنما کے لیے کام آیا، غیر مستند API درخواستوں کو مسترد کیا، اور آزادانہ طور پر براہِ راست اور اسٹریم شدہ 32-ایونٹ مصنوعی برآمدات کی تصدیق کی۔ اپ ڈیٹ شدہ آف لائن گائیڈ کو 320، 390، اور 1440 پکسلز پر چیک کیا گیا۔ عوامی اسکرین شاٹس مصنوعی ہی ہیں۔

ماخذ ریلیز میں 107 اجازت یافتہ فائلیں شامل ہیں۔ مقامی دستاویزاتی روابط حل ہو جاتے ہیں۔ Docker/Caddy کے ذریعے چلانا، ریموٹ CI/پیکیج کی اشاعت، ARM64 رن ٹائم، مسلسل جمع کاری، اور مکمل لائیو ٹیلیگرام قبولیت میٹرکس یہاں بغیر کسی پابندی کے برقرار ہیں۔

## ورژن 0.5.1

ونڈوز 11 / پائتھن 3.12.10 پر، مکمل پروجیکٹ ماحول کا سیٹ پاس ہو گیا: **94 پاس ہوئے، 2 چھوڑے گئے**، 31.21 سیکنڈ میں، موجودہ اسٹارلیٹ وارننگ کے ساتھ۔ جن کو چھوڑا گیا ہے، ان کے لیے POSIX اجازتوں اور سم لنک (symlink) بنانے کی ضرورت ہے جو اس ہوسٹ پر دستیاب نہیں ہیں۔ ڈاؤن لوڈ HTTP فکسچر نے ایک درخواست-تھریڈ تشخیصی رپورٹ پرنٹ کی؛ تمام دعوے (assertions) پاس ہو گئے۔ یہ رن ہوسٹ ٹرانسپورٹ کے مسائل کے نہ ہونے کا ثبوت فراہم نہیں کرتا۔

نئی ریگریشن کوریج مشقوں نے مسترد شدہ StringSession، کوڈ اور 2FA اکاؤنٹ کی تبدیلیاں، منسوخ شدہ شناختی تلاش، زیر التواء لاگ ان منسوخی، اور فعال، مسترد شدہ، منسوخ شدہ اور پروب کلائنٹس پر رجسٹرڈ ہینڈلرز کے ذریعے اپ ڈیٹس کو مسترد کر دیا۔ صرف فعال کلیکٹر ہی واقعات کا حصہ ڈالتا ہے؛ محفوظ شدہ اسناد اور دستخط شدہ تاریخ برقرار رہتی ہے۔ دیگر نئے چیکس میں ڈیٹا بیس کو دوبارہ کھولنے کے بعد یونیکوڈ تلاش، کوریج میں مانیٹرنگ پالیسی کی حدوں کا شامل ہونا، اور پبلک سورس پیکیجنگ استثنیات شامل ہیں۔

اصل پروجیکٹ `pythonw.exe` نے ایک الگ تھلگ مصنوعی پینل شروع کیا، HTTP 200 واپس کیا اور `logs/server.log` میں اسٹارٹ اپ تشخیص کو برقرار رکھا۔ لاگ میں پیدا شدہ پینل ٹوکن یا HTTP رسائی کے ریکارڈز شامل نہیں تھے۔ ٹیسٹ نے صرف اپنی ہی مصنوعی پراسیس کو ختم کیا۔ کوئی ٹاسک شیڈولر ٹاسک رجسٹرڈ نہیں تھا؛ لاگ آن/سائن آؤٹ، سلیپ اور سروس ریکوری الگ الگ اہلیت کے طور پر رہتے ہیں۔

## ورژن 0.3.0

مکمل پن کیے گئے رن ٹائم سوئٹ نے **61 ٹیسٹ** پاس کیے، ایک اپ اسٹریم Starlette TestClient ڈیپریکی ایشن وارننگ کے ساتھ۔ رن ٹائم میٹا ڈیٹا کے مطابق TgWitness 0.3.0 اور python-socks 2.8.2 ہیں؛ pip چیک پاس ہوا۔ براؤزر ایکسیپٹنس رن بغیر کسی صفحے کی جاوا اسکرپٹ ایررز کے پاس ہوا۔

ورژن 0.3.0 کا وہیل تیار کیا گیا اور ایک علیحدہ پیکیج ڈائریکٹری میں انسٹال کیا گیا۔ اس نے پینل اور اثاثوں کو فراہم کیا، ایک غیر مستند API درخواست کو مسترد کیا، اور ایک 32-واقعات پر مشتمل مصنوعی جریدہ برآمد کیا جو آزادانہ تصدیق میں کامیاب رہا۔ مقامی دستاویزات کے لنکس حل ہو گئے۔ MTProxy بیئر-کی نارملائزیشن اصلاح کے بعد، تمام نو کنکشن/سیکیورٹی ٹیسٹ کامیابی کے ساتھ دوبارہ چلائے گئے۔

نئی کوریج میں شامل ہیں:

- SOCKS5 صارف نام/پاس ورڈ اور HTTP CONNECT حقیقی لوپ بیک ٹیسٹ سرورز کے ذریعے؛ ایک غیر فعال کنفیگر کی گئی پروکسی منزل پر واپس جانے کے بجائے ناکام ہو جاتی ہے۔
- پراکسی کی توثیق، MTProxy ٹرانسپورٹ کے انتخاب، جعلی TLS ee سیکرٹس کی مستردگی، دیرپا ذخیرہ، ورک اسپیس کا علیحدگی، مشاہدے کے دوران تبدیلیوں کی مستردگی، اور API کی حالت اور دستخط شدہ واقعات سے خفیہ معلومات کا استثناء۔
- مصنوعی Telethon SQLite سکیمہ 7 اور 8 کی صرف-پڑھنے والی تبدیلی؛ ماخذ ہیش میں کوئی تبدیلی نہیں؛ دیگر فارمیٹس، SQL ویوز، اور ایک زیر التواء WAL فائل کی مستردی۔
- بیرونی والٹ ماسٹر کلید: مختلف مشتق ورک اسپیس کلیدیں، کامیاب دوبارہ کھولنا، غلط/غائب کلید کی مستردگی، اور موجودہ مقامی والٹس کی کوئی ضمنی منتقلی نہیں۔
- براؤزر پراکسی سیٹنگز، کریڈنشل کلیئرنگ، اسٹوریج پروٹیکشن انکشاف، موبائل کنکشن صفحہ، تبدیل شدہ سیشن فائل کی اجازت، الگ راستے، اور ایک جعلی ٹیلیگرام کلائنٹ کے ساتھ پہلے بیان کیے گئے تمام کلیکشن/ایکسپورٹ منظرنامے۔

ترقی کے دوران ایک لوپ بیک ٹیسٹ ہم منصب کے بند ہونے کا انتظار کرتا رہا؛ ایک اور چلائے گئے ٹیسٹ نے ہینڈ شیک کے بعد ونڈوز کنکشن کے ری سیٹ ہونے کا مشاہدہ کیا۔ اب یہ فکسچر پورے تبادلے کو محدود کرتا ہے اور مکمل ہینڈ شیک کے بعد EOF/ری سیٹ کو کنکشن کی بندش کے طور پر سمجھتا ہے۔ ہینڈ شیک/تصدیق کے دعوے ضروری ہیں۔ یہ حقیقی پروکسی فراہم کنندگان کو مستثنیٰ نہیں کرتا اور نہ ہی ٹیلیگرام کے ٹرانسپورٹ میں کسی مستقل خرابی کا اشارہ دیتا ہے۔

نیچے بیان کردہ AdGuard ہوسٹ کی درخواست کا مشاہدہ اب بھی لاگو ہے۔ کوئی حقیقی ٹیلیگرام اکاؤنٹ، SOCKS/HTTP پروکسی کے علاوہ، یا لائیو MTProxy سرور استعمال نہیں کیا گیا۔ MTProxy تجرباتی ہے اور اس کے منتخب کردہ اختیارات/خفیہ تصدیق کی گئی ہے، نہ کہ لائیو ہم آہنگی۔ نئی بیرونی-چابی اور سیشن کنورژن کمانڈز صرف مصنوعی رازوں کے ساتھ آزمائی گئیں۔ لینکس/macOS/Docker یہاں غیر مستند رہتے ہیں۔

نیچے دی گئی 0.2 تھروپٹ کی پیمائش کو دوبارہ نہیں کیا گیا اور اسے 0.3 کے لیے نئے ملٹی اکاؤنٹ/پراکسی بینچ مارک کے طور پر پیش نہیں کیا جانا چاہیے۔

## ماحولیاتی مشاہدات

ونڈوز سینڈباکس کی پابندیوں نے ڈیفالٹ pytest/pip عارضی ڈائریکٹریز اور Playwright سب پروسیس کو بلاک کر دیا۔ Pytest نے پروجیکٹ کے اندر ایک نئی عارضی ڈائریکٹری استعمال کی؛ انسٹالیشن اور براؤزر کے عمل کے لیے سینڈباکس کے باہر منظوری یافتہ عملدرآمد درکار تھا۔

مشین کے AdGuard نے براؤزر میں local.adguard.org کے لیے درخواستیں داخل کیں۔ براؤزر کی رسید ان درخواستوں کو برقرار رکھتی ہے۔ یہ چلائی گئی ٹیسٹ غیر تبدیل شدہ براؤزر ماحول میں صفر آؤٹ باؤنڈ درخواستوں کا ثبوت **نہیں** ہے؛ ایپ کے ماخذ میں خود کوئی بیرونی اثاثہ/CDN/تجزیاتی درخواستیں شامل نہیں ہیں۔ AdGuard کی ترتیبات تبدیل نہیں کی گئیں۔

آخری براؤزر رن نے ایک ونڈوز asyncio ساکٹ-کلین اپ OSError 10022 کو بھی لاگ کیا۔ تمام براؤزر اسرٹیشنز پاس ہو گئے اور کسی بھی صفحے پر جاوا اسکرپٹ کی غلطیاں پیش نہیں آئیں۔ اس کی وجہ معلوم نہیں ہو سکی اور یہ رن ہوسٹ ٹرانسپورٹ کے مسائل کی عدم موجودگی کا ثبوت نہیں دیتا۔

پہلی انسٹال شدہ پیکیج HTTP پروب نے urllib کے connection-close درخواستوں کا استعمال کرتے ہوئے، سینڈباکس کے اندر اور باہر دونوں میں، اور دونوں ڈپینڈنسی سیٹس کے ساتھ کنکشن ری سیٹس کا سامنا کیا۔ آخری پروب نے http.client کے ذریعے معیاری HTTP/1.1 مستقل کنکشنز استعمال کیے اور کامیاب رہی۔ براؤزر کی درخواستیں بھی کامیاب رہیں۔ ری سیٹس کی درست وجہ معلوم نہیں ہو سکی؛ انہیں ایک درست شدہ ایپلیکیشن کی خرابی قرار نہیں دیا گیا۔

## باقی اہلیت

محفوظ شدہ لائیو جرنل اصل جمع، ترامیم، حذف کے نوٹس، منسلکات، دوبارہ جانچ اور ریٹ-لیمٹ ہینڈلنگ کو مستند بناتا ہے۔ یہ مکمل ترسیل یا کردار کی نمائش، ردعمل کرنے والوں، طویل FloodWait، اکاؤنٹ کی پابندیوں اور نیٹ ورک/عمل کی رکاوٹ سے بحالی کے کنٹرول شدہ میٹرکس کو ثابت نہیں کرتا۔ QR ٹوکن کا اجرا مکمل شدہ موبائل QR تصدیق سے الگ رہتا ہے۔

ڈوکر بلڈ/رن، لینکس/میک او ایس انسٹالیشن، مسلسل زیادہ لوڈ، آزاد سیکیورٹی جائزہ، ایک حقیقی آزاد TSA ردعمل، سرٹیفیکیٹ کی منسوخی/آرکائیول کی توثیق اور عدالتی سرٹیفیکیشن ریکارڈ شدہ اہلیت سے باہر ہیں۔ محفوظ شدہ MTProto اسٹیٹ اور کیچ اپ نافذ کر دیے گئے ہیں؛ ایٹمی پائیدار ری پلے ابھی تک قائم نہیں ہوا ہے۔ ایڈمن لاگ کلیکشن، اضافی ری ایکٹر لسٹس اور ترجیحی شارٹ پولنگ الگ خصوصیات کے طور پر موجود ہیں۔ کنٹرول شدہ کوالیفیکیشن میٹرکس کے لیے [لائیو قبولیت](https://github.com/phishdestroy/TgWitness/blob/main/docs/internal/LIVE_ACCEPTANCE.md) دیکھیں۔
