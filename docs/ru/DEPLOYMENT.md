# Развертывание и эксплуатация

## Выберите вариант установки

Для получения портативного пакета извлеките файл `TgWitness-<version>-windows-amd64-portable.zip` из релизов GitHub. Для других способов загрузите и распакуйте ZIP-архив с исходным кодом или клонируйте репозиторий, а затем выполните следующую команду из каталога проекта:

| Установка | Начало | Работает в фоновом режиме? |
| --- | --- | --- |
| Портативный пакет для Windows | `TgWitness.cmd` | Нет; оставьте окно открытым. |
| Встроенная версия для Windows | `Start.cmd` | Нет; для работы в фоновом режиме используйте дополнительную задачу входа в систему. |
| Версии для Linux и macOS | `sh start.sh` | Нет; для работы в фоновом режиме используйте systemd/launchd. |
| Docker на любом поддерживаемом хосте | `docker compose up -d --build --wait` | Да, при условии, что демон Docker работает. |
| Вспомогательная утилита Docker для Windows | `scripts\Docker.cmd` | Да; вспомогательная программа отслеживает работоспособность веб-сервера. |
| Вспомогательная утилита Docker для Linux/macOS | `sh scripts/docker-start.sh` | Да; вспомогательная программа отслеживает работоспособность веб-сервера. |

При запуске нативное приложение создаёт частный образ `.venv` и устанавливает закреплённые зависимости. Docker собирает их внутри образа, не требуя наличия Python на хосте. Для первоначальной настройки необходим доступ к Интернету. Если Python версии 3.11 или выше не обнаружен, `Start.cmd` запрашивает разрешение перед установкой Python 3.12 для текущего пользователя Windows (с помощью winget или, в противном случае, установщика с сайта python.org после проверки подписи Python Software Foundation); при этом никогда не запрашиваются права администратора. Docker и системные службы ОС остаются обязательными условиями.

Нативные и переносимые установки используют `data/live` внутри своей папки. Docker использует томат с именем `tgwitness-data`, расположенный по адресу `/data`. Эти установки являются отдельными, пока вы сознательно не перенесёте весь каталог данных. Не ожидайте, что новый контейнер Docker автоматически обнаружит нативные учётные записи.

## Требования к установке

Для установки нативной версии требуется Python 3.11 или более поздней версии с `venv` и `ensurepip`, доступ в Интернет для установки первой зависимости, а также каталог проекта с правами на запись для `.venv`. Для работы панели, входящей в комплект, не требуется Node.js или сборка фронтенда. Запустите программу-запускник из своей обычной учётной записи в ОС; TgWitness не требует прав администратора или root.

- **Windows:** `Start.cmd` проверяет `py -3`, затем `python`, далее — папки установки по умолчанию для каждого пользователя и папку «Program Files»; для работы требуется версия 3.11 или более поздняя. Если ни один из вариантов не сработает, предлагается автоматическая установка в папку пользователя, как описано выше. Также работает `py -3 start.py`. Портативный пакет не требует установки Python.
- **Linux:** `start.sh` проверяет `python3.13`, `python3.12`, `python3.11`, `python3` и `python` и выводит команду установки для apt, dnf, pacman, zypper, apk или Homebrew, если ни один из вариантов не подходит. Для установки в Debian/Ubuntu может потребоваться пакет `python3-venv`, соответствующий выбранному интерпретатору. Устаревшую версию Python, установленную по умолчанию в дистрибутиве, необходимо заменить или дополнить версией Python 3.11+.
- **macOS:** установите актуальную версию Python 3.11+; не следует полагать, что интерпретатор, поставляемый с операционной системой, соответствует требованиям. Используйте файл `python3 start.py` из каталога проекта.
- **Docker:** используйте Docker Engine/Desktop с Compose версии 2.20 или более поздней. В Windows Docker Desktop должен использовать контейнеры Linux. Контейнер устанавливает собственные зависимости Python; на хосте не требуется отдельная установка Python.

Используйте постоянное локальное хранилище для каталога данных. Планируйте объём памяти с учётом объёма сообщений, мультимедиа, роста WAL, экспортов и резервных копий; не существует основанных на фактических данных универсальных минимальных требований к объёму дискового пространства и оперативной памяти для всех типов нагрузок. Архитектуры процессоров и версии Python, не имеющие совместимых колес зависимостей, могут потребовать дополнительных инструментов сборки и собственной квалификации. Термин «портативный» не означает универсальной поддержки всех операционных систем или аппаратного обеспечения.

Работа на Windows 11 с Python 3.12 проверена локально. Описания для Linux, macOS и контейнеров, а также средства непрерывной интеграции (CI) предоставляются, однако на данном хосте разработки они не запускались. Точный объем работ см. в [файле VERIFICATION.md](../VERIFICATION.md).

## Локальный компьютер

Используйте `Start.cmd` в Windows или `sh start.sh` в Linux/macOS. `scripts\Setup.cmd` или `sh start.sh --setup-only` обеспечивают подготовку рабочей среды. При первом запуске программа-запускает устанавливает необходимые зависимости; при последующих запусках используется уже подготовленная среда. Для настройки и сбора данных из Telegram требуется доступ к Интернету, однако просмотр существующих записей и создание экспортов возможны в автономном режиме.

После настройки запустите команду `python start.py --check`, чтобы проверить локальные зависимости, Ed25519, хранилище, конфигурацию ключей и адрес прослушивания без запуска коллектора. Для получения структурированного вывода используйте команду `--json`. Передайте нужные параметры `--data-dir`, `--host` и `--port`. Эта проверка не предусматривает установку пакетов, создание журнала или подключение к Telegram; она не является проверкой целостности или охвата. При запуске отдельно проверяются существующие журналы. Команда `python start.py --help` также не запускает установку.

Параметры:

После запуска start.py выполните вспомогательные команды с помощью `.venv\Scripts\python.exe` в Windows или `.venv/bin/python` в Linux/macOS, либо сначала активируйте данную среду. Приведенные ниже примеры `python -m ...` предполагают, что среда уже активна.

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

Переменные среды: TGWITNESS_DATA, TGWITNESS_HOST, TGWITNESS_PORT, TGWITNESS_TOKEN. Переменная TGWITNESS_VAULT_KEY_FILE определяет режим использования внешнего ключа при новой установке; см. ниже. TGWITNESS_TOKEN, если указан, должен содержать не менее 24 символов; используйте криптографически случайное значение. В отсутствие этого параметра приложение генерирует 256-битный случайный токен в файле panel-token.txt. Переопределение переменной среды не приводит к перезаписи этого файла. Перезапустите приложение для смены учетных данных.

Каталог данных может принадлежать ровно одному процессу. Кроссплатформенная блокировка файлов на уровне ОС предотвращает случайные одновременные записи. Используйте один рабочий процесс Uvicorn. Панель управления может управлять любым количеством рабочих пространств, при этом дополнительные каталоги рабочих пространств должны находиться в папке profiles/<id>/. Для отдельных экземпляров сервиса используйте отдельные каталоги и порты. Файлы WAL базы данных SQLite должны храниться в локальном постоянном хранилище, а не в сетевой файловой системе. Не используйте один том для нескольких реплик.

## Портативный пакет для Windows

Каждый релиз на GitHub содержит `TgWitness-<version>-windows-amd64-portable.zip` и `.sha256`. Он включает в себя официальную встраиваемую среду выполнения Python 3.12 с сайта python.org (контрольная сумма указана в `tools/build_portable.py`), TgWitness и его закреплённые зависимости, а также три программы запуска:

| Файл | Цель |
| --- | --- |
| `TgWitness.cmd` | Запустите панель; дополнительные параметры передаются без изменений, например, `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | Запустите синтетическую демонстрацию в `data\demo` |
| `TgWitness-Check.cmd` | Запустите проверку готовности без запуска |

Распакуйте весь архив в папку с правами на запись, например `Documents\TgWitness`; не запускайте программу из ZIP-архива или из папки «Program Files». Среда выполнения использует изолированный путь к модулям, поэтому другие установки Python и папка `PYTHONPATH` не влияют на её работу. Данные хранятся в папке `data`, входящей в состав пакета. Для обновления остановите работу TgWitness, распакуйте новую версию в новую папку и скопируйте туда папку `data`.

Скомпилируйте его самостоятельно на 64-разрядной версии Windows с использованием Python 3.12:

~~~sh
python tools/build_portable.py
~~~

Сборщик проверяет контрольную сумму среды выполнения, устанавливает ограниченные зависимости в пакет, запускает проверку готовности с помощью встроенного интерпретатора и записывает ZIP-архив и контрольную сумму в `dist/`.

## Контейнер

```sh
docker compose up -d --build --wait
```

При этом создаётся именованный постоянный том для каталога /data. Веб-порт сопоставляется с адресом 127.0.0.1:8787. Процесс запускается с UID 10001 с ограниченными правами, корневой файловой системой, доступной только для чтения, а также каталогами /data и /tmp, доступными для записи. `--wait` проверяет работоспособность веб-сервера перед возвратом результата; он не осуществляет авторизацию в Telegram и не обеспечивает доставку сообщений. Предоставленные вспомогательные программы используют таймаут готовности в 180 секунд после сборки. Первоначальная загрузка зависимостей может занять больше времени.

Оба базовых файла Compose используют название проекта `tgwitness`, поэтому при извлечении нового выпуска в другой каталог новый том данных не выбирается автоматически. Оставляйте активным только одно развёртывание для данного проекта. Для независимых установок используйте уникальный идентификатор `docker compose -p NAME ...` и другой порт хоста, а при обновлениях сохраняйте оба. Для более старого развёртывания, использующего другое название проекта, продолжайте использовать его исходное название с `-p`; `docker compose ls` содержит список существующих проектов.

Скопируйте `deploy/env.example` в `.env` и измените `TGWITNESS_PORT`, чтобы использовать другой порт обратной связи. Например, `TGWITNESS_PORT=8788` открывает доступ к панели по адресу `http://127.0.0.1:8788`; контейнер по-прежнему прослушивает порт 8787. `.env` игнорируется в Git.

Получение начального токена:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

Полезные команды:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` перезапускает коллектор после сбоя или перезапуска демона Docker. На сервере под управлением Linux включите запуск Docker при загрузке системы с помощью диспетчера служб вашего дистрибутива, как правило, `sudo systemctl enable --now docker`. В Windows/macOS включите настройку «Запускать при входе в систему» в Docker Desktop. Выход из системы, переход в режим сна или остановка демона Docker могут прервать сбор данных. Явно остановленный контейнер останется в остановленном состоянии до тех пор, пока вы не запустите его заново.

В приведённой конфигурации размер тома /tmp ограничен 512 MiB. При экспорте данных вместо него используется элемент `temporary-exports/` каждого рабочего пространства в постоянном томе /data. Зарезервируйте там место для одновременных экспортов, роста журнала/WAL, мультимедиа и резервных копий. Программа запуска и Docker используют файл deploy/constraints.txt для фиксации утверждённых версий зависимостей среды выполнения. Это не цепочка поставок с фиксированным хешем: базовый образ Python и артефакты пакетов по-прежнему требуют независимой квалификации выпуска.

Не используйте команду `docker compose down -v`, если только вы не намерены уничтожить журнал и ключи. Отчеты о работоспособности контейнера отражают доступность веб-сервера, а не успешность сбора данных из Telegram. Проверяйте состояние коллектора на панели управления, наличие сигналов о работоспособности, ошибки и события, связанные с охватом.

### Профиль независимого наблюдателя

Дополнительный сервис `witness` запускает [независимый witness](../WITNESS.md) в собственном контейнере с собственным ключом и журналом в томе `witness-data`, а для коллектора предоставляется только токен witness, доступный только для чтения. Создайте токен на странице **«Witness»** панели управления, добавьте его вместе с токеном бота и каналом в `.env`, а затем запустите профиль:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

Сервис подключается к коллектору внутри сети Compose по адресу `http://tgwitness:8787` (`TGWITNESS_WITNESS_COLLECTOR` переопределяет его; например, `/profiles/<workspace ID>` для другого рабочего пространства). Для свидетеля на отдельном сервере, управляемом другим лицом, используйте там файл `deploy/compose/compose.witness.yaml`, указав в `TGWITNESS_WITNESS_COLLECTOR` HTTPS-адрес коллектора; этот файл содержит только свидетель.

## Установите опубликованный образ

Данная документация становится доступной после успешного завершения [рабочего процесса выпуска](#автоматические-релизы-на-github) и публичной настройки конфигурации пакета GHCR. Имя владельца репозитория не закреплено в исходном коде. Воспользуйтесь изображением, представленным в сводке рабочего процесса данного выпуска.

Скопируйте `deploy/env.example` в `.env`. Укажите для `TGWITNESS_IMAGE` опубликованную версию, используя путь к репозиторию **в** **нижнем регистре**, например:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.7.1
TGWITNESS_PORT=8787
```

Запустите этот файл самостоятельно вместо `compose.yaml`:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

На хост-компьютере не требуется сборка исходного кода, Python или компилятор. Рабочий процесс выпуска ориентирован на контейнеры Linux AMD64 и ARM64, включая виртуальную машину Linux в Docker Desktop. Используйте тег версии или тег `ghcr.io/owner/repository@sha256:...` из сводки рабочего процесса. Не настроено перемещение тега `latest`, а также автоматическое обновление приложения. Варианты образа и исходного кода используют один и тот же том данных, если их названия проектов совпадают.

## Автоматическая настройка HTTPS на сервере

Используйте сервер с Docker, домен, находящийся под вашим контролем, и постоянное локальное хранилище. Настройте записи A/AAAA домена на этот сервер; публикуйте запись AAAA только в том случае, если к серверу осуществляется доступ по IPv6. Разрешите входящий трафик по портам TCP 80 и 443, а также исходящий трафик DNS/HTTPS для выдачи сертификатов. Эти порты не должны быть заняты другими службами.

Скопируйте `deploy/env.example` в `.env` и укажите имя хоста без указания схемы или пути:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

Запустите сборку исходного кода с использованием HTTPS-оверлея:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

Для опубликованного изображения вместо этого используйте `deploy/compose/compose.image.yaml` в качестве первого файла. Сохраните оба аргумента `-f` для последующих команд status, logs, update и stop.

Caddy получает и обновляет сертификат, перенаправляет HTTP-запросы на HTTPS и пересылает их коллектору в частной сети Compose. Состояние сертификата хранится в отдельном постоянном томе. Порт хоста коллектора, к которому осуществляется прямое подключение, остается доступным только для локального цикла. В предоставленной конфигурации Caddy регистрация доступа не включена.

Откройте `https://watch.your-domain.org` и введите токен панели. Проверка готовности не подтверждает выдачу сертификата или доступность извне. Если HTTPS не готов, проверьте настройки DNS, правила брандмауэра, а также:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

Предоставленный образ Caddy следует за тегом `2-alpine`. При выполнении команды «pull» этот образ обновляется; если вам требуются фиксированные версии инфраструктуры, закрепите проверенный дайджест в вашем развертывании.

## Обновления и резервное копирование

Сохраните название проекта Compose и объём данных при обновлениях. Сначала остановите сборщик данных и создайте полную резервную копию. Для развёртывания по умолчанию на основе исходного кода:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

Каждый раз используйте новое место для резервного копирования, находящееся за пределами репозитория, и защищайте его как материал, требующий доступа к учётной записи. Приведённый пример пути носит иллюстративный характер; используйте своё личное место для резервного копирования. Скопируйте весь каталог, включая скрытые файлы, все рабочие пространства, ключи, журналы и мультимедийные файлы. Если настроен, отдельно создайте резервную копию главного ключа внешнего хранилища. ZIP-архив с доказательствами не является резервной копией приложения, из которой можно восстановить данные. При использовании HTTPS также сохраните тома Caddy, если вам необходимо сохранить состояние его сертификата или учётной записи.

Для развертывания исходного кода загрузите файлы новой версии и выполните следующую команду:

```sh
docker compose up -d --build --wait
```

Для развёртки с использованием образа замените `TGWITNESS_IMAGE` на нужную версию, а затем выполните:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

Используйте файлы Compose вашей установки также для приведённых выше команд stop и copy. Сохраните `.env`, пользовательскую конфигурацию и прежнее название проекта. `down` сохраняет именованные тома; **`down -v` удаляет их**. Не копируйте `.venv` между операционными системами или версиями Python. Для обновления исходного кода остановите TgWitness, создайте резервную копию всего каталога данных, замените исходные файлы и запустите `python start.py --setup-only` перед запуском.

После обновления проверьте доступ к панели, идентификационные данные учётной записи, состояние мониторинга и охват. Перезапуск не восстанавливает пропущенные обновления Telegram. Для отката может потребоваться резервная копия, созданная до обновления, если в будущей версии будут изменены форматы хранения данных.

## Автоматические релизы на GitHub

[Процесс выпуска версий](../../.github/workflows/release.yml) готов к использованию после того, как данный проект будет запущен в репозиторий GitHub с включенной функцией Actions. Он запускается при **публикации** релиза на GitHub, включая предварительные версии. Сами по себе черновики и добавление тегов не приводят к публикации пакетов.

1. Укажите версию пакета и журнал изменений, а затем опубликуйте релиз с тегом `v` и точным указанием версии `pyproject.toml`, например `v0.7.1`.
2. Данный рабочий процесс проверяет тег и запускает общие проверки для Windows/Linux/macOS: проверку Python, проверку браузера (общую, импорта учетной записи и QR-кода), проверку исходного пакета и проверку Docker. Также выполняется установка с нуля на всех трёх операционных системах с использованием Python 3.12.
3. После успешного прохождения этих проверок выполняется предварительное тестирование образа ARM64 в среде QEMU, образы AMD64/ARM64 публикуются на `ghcr.io/<lowercase-owner>/<lowercase-repository>:<version>`, а к релизу прилагаются исходный ZIP-файл, контрольная сумма и пакет Python wheel. Отдельная задача для Windows собирает и прилагает переносимый ZIP-файл и его контрольную сумму.
4. После первой публикации откройте настройки пакета GHCR и установите видимость на **«Public»**, если предполагается анонимная загрузка образов. Наличие общедоступного репозитория исходного кода само по себе не гарантирует общедоступность пакета контейнера. Политики организации должны разрешать публикацию пакетов. В рабочем процессе используется тег `GITHUB_TOKEN`; в репозитории не должны храниться пароли реестра или учетные данные VPS.

Успех удалённого рабочего процесса не гарантируется данной локальной подготовкой. Эмуляция ARM64 является лишь предварительной проверкой, а не квалификацией для работы на нативном оборудовании или в реальной среде Telegram. Данная процедура автоматизирует создание пакетов релизов; для запуска сервера по-прежнему требуется команда Compose и наличие необходимых домена/хоста. Существующие серверы не обновляются и не перезапускаются автоматически при публикации релиза.

## Удалённый сервер

Обеспечьте привязку сервиса к петлевому интерфейсу и используйте SSH-туннель либо завершайте HTTPS-соединение на обратном прокси-сервере. Базовый файл Compose предназначен исключительно для локального использования; дополнительный оверлей `deploy/compose/compose.https.yaml` предоставляет Caddy для настроенного домена. Не допускайте появления токена bearer в URL-адресах и журналах прокси-сервера. Обратный прокси-сервер должен ограничивать размер запросов и частоту подключений. Не открывайте доступ к простому HTTP из Интернета.

Примеры для systemd, задачи входа в систему Windows, пользовательского агента macOS и Caddy приведены в папке [deploy/](../../deploy/README.md). Перед установкой проверьте и при необходимости скорректируйте их пути. Это предоставленные шаблоны, а не локально выполняемые настройки для конкретной платформы. Обычный запускатель не регистрирует никаких фоновых служб или задач.

В системе Windows при запуске в фоновом режиме `pythonw.exe` диагностические данные о запуске и работе сервера сохраняются в папке `logs/server.log`, расположенной в каталоге данных (5 МБ на файл, две резервные копии с ротацией). При запуске в консольном режиме сохраняются консольные журналы. Регистрация доступа по HTTP отключена в обоих режимах. Защищайте журналы вместе с каталогом данных и проверяйте их перед передачей.

## Перезапуск и пробелы

Последнее запрошенное состояние наблюдения сохраняется. Если наблюдение было активным, при запуске происходит попытка повторного подключения и возобновления работы с выбранными источниками. Ручная пауза отменяет эту попытку. Неудачная попытка перезапуска регистрируется и отображается на панели.

StringSession сохраняет авторизацию, но не сохраняет устойчивое состояние обновлений и сущностей Telethon. Диалоги перезагружаются при запуске. Telegram/Telethon способен восстанавливать некоторые сбои в транспорте во время работы, однако TgWitness не гарантирует устойчивого воспроизведения данных после перезапуска процесса. При каждом запуске фиксируются предыдущая начальная точка журнала и граница автономного режима. Монитор проверяет подключение каждые 10 секунд и отправляет сигнал проверки работоспособности каждую минуту. Кратковременные перебои могут остаться незамеченными; наличие подключения не гарантирует полной доставки обновлений. Снимки представляют собой явные наблюдения текущей истории, но ни в коем случае не восстановление пропущенных данных.

Очередь медиафайлов хранится в базе данных SQLite каждого рабочего пространства. Сообщение и соответствующее задание фиксируются атомарно. Прерванные выполняющиеся задания восстанавливаются для повторной попытки при запуске. Каждая загрузка имеет таймаут в 120 секунд и настраиваемый лимит размера от 1 до 100 MiB. Коллектор пропускает файлы с неизвестным размером. При приостановке работы задачи в очереди сохраняются. При повторной попытке используется исходный дескриптор файла, а не последняя версия сообщения, отредактированная впоследствии. Для временных сбоев предусмотрено ограниченное количество попыток; приостановки FloodWait в очереди мультимедиа сохраняются после перезапуска. Восстановление мультимедиа осуществляется отдельно от восстановления обновлений Telegram и не позволяет воссоздать исчезнувшие файлы.

## Резервное копирование, восстановление и емкость

Прекратите процесс перед копированием **всего каталога данных**, включая файлы vault.key, signing.enc, credentials.enc, базу данных SQLite и файлы WAL, мультимедиа, токен, контрольные точки, а также все подкаталоги profiles/. Восстановите полную копию при остановленном целевом сервисе. Отсутствие ключей хранилища или несоответствие ключей подписи приводят к сбою запуска; не генерируйте ключи заново для принудительного доступа.

Храните секретные резервные копии в зашифрованном виде с контролем доступа. ZIP-файлы с доказательствами представляют собой переносимые артефакты для анализа, а не резервные копии приложения или сеансов Telegram. Автоматического удаления данных по истечении срока хранения не предусмотрено. Запланируйте дисковое пространство для всех сообщений, исходных метаданных, мультимедиа, временных экспортов и резервных копий.

Проверка при запуске и экспорт записей потока вместо загрузки всего журнала. Экспорт фиксирует моментальный снимок прочитанных данных, в то время как запись новых данных в WAL может продолжаться; при длительном экспорте страницы WAL могут сохраняться, поэтому объём дискового пространства по-прежнему имеет значение. Размер ZIP-архивов ограничен 4 ГиБ в несжатом виде, чтобы соответствовать требованиям независимого верификатора. В других форматах ограничения по количеству событий отсутствуют. Поддерживаемые браузеры передают фрагменты ответов в файл, выбранный пользователем. Другие браузеры буферизуют не более 128 MiB и направляют более объёмные передачи в авторизованный CLI:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

Используйте `--profile ID` из **раздела** **«Экспорт» → «Идентификатор рабочей области»** для другой рабочей области, `--format zip|jsonl|csv|html`, `--url https://your-server` для удалённого сервера или `--max-mib`, чтобы изменить ограничение на передачу данных в 5 ГиБ. Простой HTTP разрешён только для loopback. Токены передаются в заголовках, перенаправления не допускаются, существующие файлы не перезаписываются, а незавершённые загрузки не публикуются как завершённые файлы. Если TGWITNESS_TOKEN переопределяет сгенерированный токен, используйте отдельно защищённый файл, содержащий это активное значение: файл panel-token.txt не перезаписывается при переопределении. SHA-256 команды является лишь контрольной суммой передачи; независимо проверьте ZIP-архив с подписью.

Файлы экспорта сервера хранятся в частном каталоге `temporary-exports/` каждого рабочего пространства. При успешном завершении операции файлы удаляются. Прерванные экспорты удаляются при следующем запуске рабочего пространства с удержанием эксклюзивной блокировки экземпляра. Данный каталог является частью модели угроз и емкости хранилища; рекомендуется использовать зашифрованный том данных. Передача данных объёмом в несколько гигабайт в производственных условиях по-прежнему требует проверки на совместимость с вашей целевой системой.

На панели отображаются медиафайлы в очереди или с ошибками, самые старые медиафайлы в ожидании, свободное место на диске, паузы в запросах Telegram, а также источники, доступ к которым не подтверждён. Данные диагностические показатели не являются полноценным монитором доставки от начала до конца. Рабочие пространства используют общий процесс; поэтому активная учетная запись по-прежнему может влиять на работу других. Остаются нерешенными вопросы, касающиеся отдельных рабочих процессов, хранения и ротации данных, восстановления после сбоев при обновлении, привязки удалённых контрольных точек, ролей и полной квалификации развёртывания.

## Параметры подключения и защиты

Маршруты подключения задаются для каждого рабочего пространства и должны быть настроены до авторизации. SOCKS5/HTTP CONNECT используют закреплённую зависимость python-socks. MTProxy использует экспериментальный рандомизированный промежуточный транспорт Telethon; секретные ключи Fake TLS ee не поддерживаются. Автоматический прямой переход на резервный маршрут не настроен. Это не сетевой маршрут, действующий в масштабе всей системы.

При новой установке переменная TGWITNESS_VAULT_KEY_FILE должна указывать на отдельно защищённый файл с случайным мастер-ключом. Смонтируйте его в режиме «только для чтения» вне каталога /data в контейнере. Сохраняйте открытые метаданные salt из файла vault.external.json отдельно для каждой рабочей области и мастер-ключа. Существующие локальные хранилища требуют плановой миграции; установка этой переменной не приводит к их автоматическому преобразованию. Хранение сообщений и мультимедиа, а также их экспорт не шифруются на уровне приложения. При необходимости используйте зашифрованные тома и достаточное объёмное частное временное хранилище.

Подробные инструкции: [подключение/безопасность](../CONNECTION-SECURITY.md) и [режимы работы](../OPERATIONS.md).
