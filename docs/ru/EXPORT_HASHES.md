# Хеши файлов и предварительная проверка экспорта

Функция «Экспорт аккаунта» поддерживает действия с медиафайлами: `download`, `hashes_only` и `exclude` — как через стандартный API, так и через Takeout. Воспользуйтесь существующим диалоговым окном настроек экспорта или отправьте [утвержденную конфигурацию](../../examples/export-hashes.json) методом `POST /api/account-export/start`. Параметр `chat_ids: []` выбирает все видимые чаты выбранных типов; укажите ID, чтобы ограничить область действия.

`media_types` выбирает подходящие типы. `media_action` — это действие по умолчанию для них; `media_actions` переопределяет настройки для отдельных типов. Необязательный параметр `media_rules[kind].action` используется в случае отсутствия соответствующего переопределения в `media_actions`. Например, `{"photo":"download","video":"hashes_only"}` загружает выбранные фотографии и записывает хеши выбранных видео. Неотмеченные типы остаются исключёнными независимо от переопределений. Фотографии профиля по-прежнему включаются отдельно по желанию. Выбранные дополнительные данные аккаунта в формате JSON не относятся к медиафайлам сообщений и по-прежнему загружаются, если `include_other_data` имеет значение true.

Анимированные файлы MP4 подчиняются правилу анимации; видеостикеры — правилу стикеров, независимо от порядка атрибутов в Telegram. Функция «Экспорт аккаунта» вызывает круглое видеосообщение (`video_message`); конфигурация ограниченного сбора данных использует `video_note` для той же категории медиафайлов.

Параметр `max_media_file_mib` ограничивает объём загружаемых файлов. Параметр `oversized_media: "hashes_only"` вместо этого запрашивает хеши для более крупных файлов, соответствующих критериям. При сборе хешей их байты не загружаются. При запросе хешей серверный предел допустимого размера файлов в Takeout увеличивается, в то время как локальный модуль записи данных по-прежнему обеспечивает соблюдение выбранного ограничения на загрузку. Неподдерживаемые или недоступные хеши не приводят к автоматическому переходу к загрузке файла.

`max_total_gib` ограничивает количество уникальных байтов сохраненных медиафайлов, а не конечный ZIP-файл, отчёт или JSON-файл с хешами. Повторные ссылки повторно используют кэш вложений с установленным ограничением и не расходуют этот лимит повторно. `unique_media_bytes` отражает фактическое количество уникальных байтов сохраненных файлов; устаревший счётчик `bytes_saved` по-прежнему суммирует ссылки в сообщениях, благодаря чему старые архивы остаются поддающимися проверке. Для удаления из кэша может потребоваться дополнительный запрос; идентичное сохраненное содержимое по-прежнему занимает один файл.

`budget_exhausted: "hashes_only"` (по умолчанию) переключает оставшиеся допустимые загрузки на серверные хеши, когда бюджет на медиафайлы или резерв на упаковку могут быть превышены. Вместо этого `"stop_files"` фиксирует отсутствующие файлы. Сбои при получении хешей по-прежнему отображаются явно. Успешно загруженные файлы и полные манифесты хешей подписываются в частном кэше результатов до того, как страница сообщения будет запечатана, поэтому остановка в середине страницы не приводит к потере уже загруженных вложений.

При значении `messages_first: true` (по умолчанию) все выбранные страницы истории и метаданных аккаунта сохраняются и подписываются до начала запросов на файлы или хеши. Истекающие ссылки на файлы Telegram остаются в зашифрованной частной очереди. Верификатор «Возобновление» проверяет замороженные страницы и продолжает работу с них, не перечитывая отредактированные или удалённые сообщения. При обработке вложений за один раз запечатывается не более десяти дополненных сообщений, чтобы ограничить потребление памяти в случае большого объёма хеш-манифестов. Приостановленное локальное задание можно либо возобновить, либо **завершить с сохранением данных**; при завершении создаётся архив, а недоступная история и вложения явно фиксируются.

`export_format` принимает форматы `tgwitness`, `telegram_json`, `telegram_html` и `telegram_both`. Совместимые представления добавляют файлы `result.json` и/или `export_results.html` со страницами офлайн-чатов. Основные поля чата и сообщений соответствуют [схеме JSON Telegram Desktop](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/export/output/export_output_json.cpp); TgWitness формирует их на основе своего подписанного журнала. Даты указаны в формате UTC, сообщения упорядочены по ID, а пути к медиафайлам ссылаются на те же самые файлы, прошедшие дедупликацию. Файлы `tgwitness_media` и `hashes/index.jsonl` содержат результаты, состоящие исключительно из хешей. Подписанный JSONL остаётся авторитетным источником, включая исходные поля, не отображённые в совместимом представлении.

<a id="what-the-hashes-mean"></a>
## Что означают хеши

Метод Telegram [`upload.getFileHashes`](https://core.telegram.org/method/upload.getFileHashes) предоставляет хеши SHA-256 для диапазонов. Каждый [`fileHash`](https://core.telegram.org/constructor/fileHash) имеет смещение, длину и хеш. Эти данные отличаются от идентификатора файла, `access_hash` или контрольной суммы метаданных.

Экспорт фиксирует вариант документа или точный размер фотографии, ожидаемую длину, упорядоченные диапазоны, а также информацию о том, охватывают ли они весь файл. Конечный диапазон в Telegram может выходить за пределы EOF; при сравнении хешируются только существующие байты. Различные варианты фотографии могут законно содержать разные байты. В общедоступный манифест не включаются ни хэш доступа, ни ссылки на файлы с истекшим сроком действия.

Запросы на вычисление хешей обращаются к центру обработки данных медиафайлов. При повторных запросах используется ранее полученный результат. Перенос данных между центрами обработки данных и ссылки с истекшим сроком действия обрабатываются без смены настроенного канала передачи. Недоступность или частичное покрытие фиксируются и делают выбранное вложение неполным; его нельзя считать полноценным вложением, содержащим только хеш.

<a id="compare-a-downloaded-file"></a>
## Сравнение загруженного файла

Сначала проверьте архив с помощью отпечатка ключа подписи, проверенного независимым источником. Файл ``hashes/index.jsonl`` сопоставляет ссылки на чаты, сообщения и вложения с отдельными манифестами в формате JSON, расположенными в папке ``hashes/``. Эти же манифесты встроены в подписанные страницы сообщений; при проверке архива индекс и автономный манифест сверяются с этими страницами. HTML-транскрипт содержит ссылки на каждый полный манифест с хешами.

Выполните:

```text
python -m tgwitness.file_hashes path/to/hash-manifest.json path/to/local-file.jpg
```

Результат различает состояния `match` (совпадение), `different` (различие), `missing` (отсутствие), `different_size_or_representation` (различие в размере или представлении) и `incomplete_hash_coverage` (неполное покрытие хешей). Эта команда считывает локальный файл, а не данные из Telegram. Совпадение подтверждает, что проверенные локальные диапазоны байтов совпадают с записанными хешами файлов Telegram.

<a id="check-settings-before-starting"></a>
## Проверьте настройки перед запуском

Воспользуйтесь **пунктом Настройки проверки и размер** в открывшемся диалоговом окне или отправьте запрос `POST /api/account-export/preflight` с теми же параметрами. Параметр `?sample=false` позволяет проверить конфигурацию и локальный диск без чтения данных из Telegram.

Ограниченная выборка считывает не более 1 000 видимых диалогов и последние 25 сообщений из не более чем 12 соответствующих чатов в течение 20 секунд. При этом не запускается функция «Takeout», не осуществляется загрузка вложений, отправка сообщений, вступление в чаты или изменение настроек экспорта. К выборке применяются правила отбора и политика в отношении медиафайлов. В отчёте указываются известные объёмы выбранных данных для скачивания, ссылки на дубликаты, неизвестные размеры и расчётный размер хеш-манифеста. Дополнительные метаданные для аккаунта и аватары не включаются в эту оценку.

Значение `fit: "unknown"` указано намеренно, даже если выборка соответствует требованиям: выборка учитывает последние сообщения, а размер более старой истории измеряется во время экспорта, в частности при использовании фильтров по дате или отправителю. Оценки хешей в формате JSON основаны на диапазонах по 128 КиБ и 160 байтах на диапазон плюс накладные расходы на файл, исходя из наблюдаемых ответов; фактические диапазоны могут отличаться. Продолжительность не фиксирована, поскольку ограничения по скорости, утверждение, подключение и формирование отчётов могут варьироваться. Явно чрезмерный объём выборочных байтов вызывает специальные предупреждения о превышении бюджета или нехватке места на диске. Критически низкий уровень свободного места на диске и начало пустого блока выбора.

Утверждение экспорта осуществляется отдельно от входа с помощью QR-кода, телефона или двухфакторной аутентификации (2FA). Когда Telegram запрашивает утверждение, воспользуйтесь уже авторизованным устройством, чтобы разрешить экспорт, а затем, при желании, **проверьте статус утверждения** до истечения срока. Экспорт и авторизация возобновятся с того же места. Ожидание из-за ограничений скорости отображается отдельно.

<a id="restricted-github-capture-and-single-chat-export"></a>
## Ограниченный захват данных из GitHub и экспорт из отдельного чата

Существующая форма ограниченного сбора данных теперь предоставляет те же три действия с медиафайлами, переопределения по типу/ограничения на загрузку, поведение при превышении размера, выбор аватаров и обработку сообщений в первую очередь. По умолчанию в пользовательском интерфейсе отображаются только хеши, а аватары отключены. Язык по умолчанию остаётся английским. Новая страница приложения не добавляется.

Сервер с ограниченным доступом принимает [конфигурацию выбора](../../examples/sealed-hashes.json) по запросам `POST /api/preflight` или `POST /api/collect`. При предварительной проверке за 20 секунд считывается не более 25 последних сообщений из выбранного чата. Выдается отчет о фактическом свободном месте на диске, оставшемся времени сбора, известном объеме выборочных данных в байтах, предполагаемом JSON-файле с уникальными хешами и отдельных ограничениях на передачу данных. При этом не запрашиваются хеши, не загружаются файлы и не изменяется выбор. Настройки и чат фиксируются при запуске сбора данных. Выбранная политика фиксируется в подписанных записях `sealed.selection`, «наблюдение» и «history».

Для экспорта данных всей учётной записи или выбранного чата используйте те же конечные точки с [настройками выбора аккаунта](../../examples/sealed-account.json): `mode: "account"` и `account_options`. Данный режим поддерживает стандартный API и Takeout, даты, политики файлов, дополнительные разделы аккаунта и совместимые форматы вывода. По умолчанию форма охватывает только все доступные чаты и хеши. Режим «журнал событий» по-прежнему представляет собой отдельный вариант стандартного API для одного чата. Предварительная проверка аккаунта использует описанный выше ограниченный образец с несколькими чатами.

Утверждение экспорта через Takeout не зависит от успешной аутентификации по телефону, QR-коду и двухфакторной аутентификации (2FA). Проверьте запрос Telegram в существующем сеансе; клиентам, недавно вошедшим в систему, может потребоваться более старый сеанс или некоторое время ожидания. Пользовательский интерфейс отображает фактическую задержку Telegram, а **функция Проверить одобрение экспорта** возобновляет выполнение той же задачи. Если срок одобрения превышает время жизни исполнителя, завершите процесс с честным частичным результатом и запустите новый цикл после одобрения; снимки GitHub из нового сеанса не передают авторизации Telegram между циклами.

Подписанный файл ``account-export.zip`` включён во внешний архив доказательств и привязан к событию журнала ``sealed.account_export``. Проверка охватывает оба архива, их идентификаторы подписи и привязку. По истечении срока действия или достижении предела хранения у исполнителя уже подписанная история и завершённые вложения финализируются; непрочитанная история и незавершённые вложения регистрируются как отсутствующие до того, как новая авторизация будет отозвана.

При значении параметра ``messages_first: true`` оба модуля обработки вложений ожидают завершения чтения истории. Приостановленная история заставляет их находиться в режиме ожидания. Полное получение хешей приводит к созданию записей ``media.hashed`` и одного файла ``hashes/<digest>.json`` на каждый уникальный манифест. В отчёте в формате HTML они обозначаются как **Хэши файлов;** для **не загруженного содержимого** указывается исходное сообщение, охват в байтах и количество диапазонов, а также предоставляется ссылка на файл JSON. Неполное получение хешей приводит к созданию записей о неудачных вложениях. Верификатор архива проверяет полное покрытие диапазонов и связывает каждый файл с хешем с соответствующей заверенной записью в журнале. Новое разрешение отзывается по завершении; отсутствие подтверждения отзыва остается явным.

Отдельный экспортер для отдельных чатов также соблюдает общую политику захвата, включая хеши и отключенные аватары. Настройте его с помощью объекта `capture` из примера посредством запроса `POST /api/capture`, а затем воспользуйтесь существующим экспортом чата. Записи хешей привязываются к подписанному файлу `chat.json`; их отдельные манифесты проверяются с помощью `verify_chat_export`. Существующая стандартная форма записи пока не предоставляет доступ ко всем этим новым полям политики; при интерактивной настройке хешей используйте форму «Экспорт учетной записи» или форму с ограниченным доступом.

Экспорт одного чата, завершившийся сбоем или отмененный, сохраняет прочитанные сообщения и вложения, сохраненные на данный момент, в папке `partial-exports/<chat id>/` рабочей области под заявлением, подписанным ключом сборщика (`tgwitness-chat-partial-v1`: хеш данных, количество сообщений, диапазон идентификаторов, сеансы и причина остановки). В процессе чтения истории заявление обновляется каждые 5 000 сообщений и ещё раз по завершении чтения, до начала загрузки вложений, благодаря чему в случае сбоя процесса для повторного чтения остаётся, в крайнем случае, только неподписанная конечная часть. При следующем экспорте того же чата той же учётной записью происходит проверка заявления, считываются сообщения, более поздние, чем сохраненный диапазон, сохраненные сообщения переносятся, и процесс продолжается ниже самого младшего сохраненного номера; в поле ``acquisition.sessions`` и в ограничениях указываются все сеансы. Сохраненные данные, не прошедшие проверку или принадлежащие другому аккаунту, откладываются без изменений, и экспорт начинается с самого нового сообщения; при первом запуске спустя более семи дней отложенная копия удаляется. После неудачного или отмененного экспорта на панели отображается сохраненный диапазон с кнопками «Возобновить экспорт» и «Начать сначала»; Функция «Начать сначала» удаляет сохранённые данные и заново считывает чат, начиная с самого нового сообщения. Если Telegram прекращает авторизацию аккаунта во время экспорта, сборщик также создаёт подписанный архив сохранённого диапазона, помеченный как `partial` и указывающий запись `coverage.gap` о потере данных; экспорт аккаунта, завершённый с сохранёнными данными, указывает ту же запись в `account_loss`. Успешный экспорт удаляет сохранённые рабочие данные.

Во время считывания истории этот же экспорт создаёт архив в режиме реального времени рядом с сохраненными сообщениями (`tgwitness-live-chat-export-v1`). Его первый элемент, `live/export.json`, представляет собой подписанное начальное заявление, в котором указаны название экспорта, чат, аккаунт, а также хеши файлов `README.txt`, `verify.py` и набора для проверки. Сообщения следуют страницами, каждая из которых содержит не более 2 000 записей или 8 MiB, и закрываются не позднее чем через десять секунд после появления первого сообщения: Файл `live/pages/NNNNNN.jsonl` содержит записи в точном соответствии с прочитанными данными, начиная с самых новых; файл `live/pages/NNNNNN.html` отображает их для читателя, а файл `live/seals/NNNNNN.json` подписывает как хеши, так и подсчёты, диапазон номеров, а также SHA-256 предыдущей печати или начального заявления. После каждой страницы файлы `manifest.json` и `manifest.sig` перезаписываются в конце ZIP-архива с указанием состояния (`reading`, `complete` или `stopped` и причины), итоговых данных и начальной печати, а файл синхронизируется, так что после каждой печати архив представляет собой полный ZIP-файл. **Команда Download messages read so far** копирует файл до момента его последней печати. Процесс, остановленный во время записи, восстанавливается при следующем запуске на основе записи `.sealed`, хранящейся рядом с архивом; в случае повреждения файла программа `verify.py` считывает элементы один за другим, проверяет цепочку печатей до последней неповреждённой печати и выводит байты, следующие за ней. Записи в «живом» архиве пока не содержат полей вложений; файлы, повторные проверки и отчёты относятся к завершённому экспорту, в ходе которого «живой» архив удаляется вместе с другими рабочими данными.

Вложения, уже сохраненные для того же файла Telegram (идентификатор документа или фотографии, вариант размера и размер в байтах), используются повторно вместо повторной загрузки. Активная запись записывает в файл ``media.saved`` значения ``bytes_reused`` и ``downloaded_bytes: 0`` равные 0; при экспорте чата сообщение помечается как ``file_reused``. Повторно используемые байты перед применением подвергаются повторному хешированию.

## Ограничения и статус выпуска

| Путь | Область применения / транспорт | Политика хеша | Предварительная проверка | Сообщения перед вложениями |
|---|---|---|---|---|
| Экспорт аккаунта | Все / выбранные чаты; стандартный API или Takeout | Пользовательский интерфейс и API | Пользовательский интерфейс и API; пример ограниченного количества чатов | По умолчанию сначала отображается подписанная история; возобновляемая очередь зашифрованных вложений |
| Экспорт одного чата | Один чат; стандартный API | API для совместного создания снимков | Отсутствует специальная форма | Сначала история, затем отдельный этап загрузки файлов с возможностью одновременной загрузки до трёх файлов |
| Ограниченный экспорт аккаунта GitHub | Все / выбранные чаты; новое стандартное API или сеанс Takeout | Существующая форма и API | Ограниченный образец с несколькими чатами | Обязательно; частичное завершение по истечении срока или при достижении лимита хранения |
| Ограниченный журнал событий GitHub | Один чат; новый регулярный сеанс API | Существующая форма и API | Пример с выбранным чатом | Настраиваемый; включён по умолчанию в форме |

Срок действия запечатанного файла включает в себя вход в систему и утверждение. Система управления допускает не более 120 минут записи, при этом ограничение рабочего процесса составляет 220 минут, включая сборку, запечатывание, заверение, шифрование, загрузку и очистку. Контейнер имеет ограничение по оперативной памяти в 2 ГиБ. Одна попытка создания ZIP-файла с доказательствами имеет максимальный размер **в распакованном виде** 4 ГиБ. Для более объёмных результатов используйте приведённый ниже многочастный путь. Свободное место на диске измеряется во время выполнения; фиксированный объём дискового пространства для исполняющего модуля не предполагается. При создании аккаунта резервируется место для его архива, а на одноразовом исполняющем модуле — для его внешней зашифрованной копии. Это консервативный резерв.

Когда создание отформатированного ZIP-файла превышает этот предел или заканчивается место на диске, ограниченный сборщик удаляет неудавшийся временный ZIP-файл и один раз пытается выполнить компактную упаковку. При этом сохраняются полный подписанный журнал, отчет об охвате, все сохраненные файлы, манифесты с серверными хешами, контрольные точки и материалы для проверки. Из него исключаются дубликаты CSV, отформатированные отчёты в форматах JSON/HTML/PDF, индикаторы и файлы просмотра. Файл ``sealed.packaging`` фиксирует причину; подписанный манифест и файл ``PACKAGING.json`` идентифицируют сжатый результат, а файл ``index.html`` объясняет, как его читать и проверять. Компактный ZIP-файл использует ту же зашифрованную передачу данных и тот же верификатор архива. Ошибки доступа и несвязанные ошибки ввода-вывода не вызывают запуск этого резервного механизма.

Если размер сжатого результата превышает ограничение на размер одного ZIP-архива или его временная копия не помещается, сборщик передаёт сжатый ZIP-архив напрямую в виде зашифрованных частей, сохраняя журнал и все сохраненные файлы. Успешно сформированные ZIP-архивы размером более 128 MiB также используют части. Каждый зашифрованный файл содержит не более 128 MiB открытого текста. Файл ``evidence.parts.json`` содержит подписанный манифест с упорядоченными именами, размерами, хешами открытого текста, зашифрованными хешами и хешем всего архива; GitHub подтверждает подлинность этого манифеста. Файл ``delivery.tgwsealed`` содержит манифест и подтверждение подлинности, а файлы ``delivery-000001.tgwsealed`` и т. д. — части архива. Загружаются только зашифрованные файлы.

После открытия файла ``delivery.tgwsealed`` и извлечения архива ``delivery.zip`` сохраните зашифрованные части рядом с файлом ``evidence.parts.json`` и запустите надёжные установленные инструменты:

```text
python -m tgwitness.sealed_parts evidence.parts.json --key sealed-key.json --out evidence.zip
python -m tgwitness.sealed_verify evidence.parts.json --bundle attestation.jsonl --repo OWNER/FORK --max-gib 64
```

Программа сборки отклоняет отсутствующие, переставленные или измененные части и никогда не перезаписывает существующий выходной файл. Предельный размер для проверки указан явно; увеличивайте его только в случае ожидаемого архива большего размера. Браузер может расшифровывать отдельные пронумерованные части без загрузки всего архива. Если место на диске исчерпано даже после использования резерва и резервного варианта сжатия, выполнение явно завершается с ошибкой. Межпрогоновой перенос запечатанных полномочий или автоматическое продолжение на другом исполнителе отсутствуют.

Функция «Экспорт аккаунта» теперь разбивает HTML-чаты на страницы. Каждая страница содержит не более 250 записей сообщений и, как правило, не более 512 КиБ исходного JSON; одна запись большего размера сохраняется без изменений. Эти ограничения применяются к входным записям. Первая страница сохраняет формат `chats/ID.html`, последующие страницы используют формат `chats/ID-2.html` и т. д. Ссылки «Предыдущая»/«Следующая», непрерывная нумерация записей и точные ссылки на страницы работают в автономном режиме. Все страницы подписываются через манифест архива; авторитетный JSONL, квитанции и параметры получения остаются без изменений. Пагинация ускоряет открытие объёмных чатов, но не ограничивает общий размер отчётов и не применяет пагинацию к автономным копиям для обмена.

Совместимый рендерер протестирован на синтетическом тексте/символах в кодировке UTF-16, идентификаторах чатов, упорядочивании сообщений, политиках работы с медиафайлами, частичных результатах и проверке подписанного архива. TgWitness формирует файлы в формате Telegram Desktop из записей, выбранных для экспорта. Проверки исторического получения сопоставляли хеши диапазонов в режиме реального времени с ранее загруженными байтами медиафайлов Telegram из записанных представлений; одни только идентификаторы файлов никогда не устанавливают байтовую идентичность.

Обновление кода в форке само по себе **не** приводит к обновлению закреплённого сборщика. Для выпуска требуются неизменяемые фиксации исходного кода и рабочего процесса, а также соответствующая запись в политике доверия; не следует ослаблять проверку, чтобы принимать произвольный код из форка. Существующие архивы остаются поддающимися проверке; новые архивы включают обновлённый автономный верификатор.
