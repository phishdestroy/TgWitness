# डिप्लॉयमेंट और संचालन

## इंस्टॉलेशन चुनें

पोर्टेबल पैकेज के लिए GitHub Releases से `TgWitness-<version>-windows-amd64-portable.zip` निकालें।
अन्य तरीकों के लिए सोर्स ZIP डाउनलोड करके निकालें या रिपॉज़िटरी क्लोन करें, फिर प्रोजेक्ट
डायरेक्टरी से निम्नलिखित चलाएँ:

| इंस्टॉलेशन | शुरू करना | बैकग्राउंड में चलता है? |
| --- | --- | --- |
| Windows पोर्टेबल पैकेज | `TgWitness.cmd` | नहीं; विंडो खुली रखें। |
| नेटिव Windows | `Start.cmd` | नहीं; बैकग्राउंड में चलाने के लिए वैकल्पिक लॉगऑन टास्क इस्तेमाल करें। |
| नेटिव Linux/macOS | `sh start.sh` | नहीं; बैकग्राउंड में चलाने के लिए systemd/launchd इस्तेमाल करें। |
| किसी भी समर्थित होस्ट पर Docker | `docker compose up -d --build --wait` | हाँ, जब तक Docker डेमन चल रहा है। |
| Windows पर Docker हेल्पर | `scripts\Docker.cmd` | हाँ; हेल्पर वेब-सर्वर के स्वस्थ होने की प्रतीक्षा करता है। |
| Linux/macOS पर Docker हेल्पर | `sh scripts/docker-start.sh` | हाँ; हेल्पर वेब-सर्वर के स्वस्थ होने की प्रतीक्षा करता है। |

ऐसे क्लाउड सर्वर के लिए जिसे कोई तीसरा पक्ष जाँच सके — जो प्रदाता के API से बनाया गया हो, बिना
SSH के, और जिस तक केवल Cloudflare Tunnel से पहुँचा जाए —
[हाई-एश्योरेंस डिप्लॉयमेंट](../HIGH-ASSURANCE.md) देखें।

नेटिव स्टार्टअप एक निजी `.venv` बनाता है और पिन की गई डिपेंडेंसी इंस्टॉल करता है।
Docker उन्हें होस्ट Python के बिना इमेज के अंदर बिल्ड करता है। पहली बार सेटअप के लिए इंटरनेट
एक्सेस चाहिए। Python 3.11+ न मिलने पर `Start.cmd` मौजूदा Windows उपयोगकर्ता के लिए Python 3.12
इंस्टॉल करने से पहले पूछता है (winget से, अन्यथा Python Software Foundation के हस्ताक्षर की जाँच
के बाद python.org इंस्टॉलर से); यह कभी एडमिनिस्ट्रेटर अधिकार नहीं माँगता।
Docker और OS सेवाएँ पूर्वापेक्षाएँ बनी रहती हैं।

नेटिव और पोर्टेबल इंस्टॉलेशन अपने फ़ोल्डर के अंदर `data/live` इस्तेमाल करते हैं। Docker `/data` पर
`tgwitness-data` नाम का वॉल्यूम इस्तेमाल करता है। जब तक आप जानबूझकर पूरी डेटा डायरेक्टरी
माइग्रेट नहीं करते, ये अलग-अलग इंस्टॉलेशन रहते हैं। यह उम्मीद न करें कि नया Docker कंटेनर नेटिव
खाते अपने-आप ढूँढ लेगा।

## इंस्टॉलेशन की आवश्यकताएँ

नेटिव इंस्टॉलेशन के लिए `venv` और `ensurepip` सहित Python 3.11 या नया संस्करण, पहली बार डिपेंडेंसी
इंस्टॉल करने के लिए इंटरनेट एक्सेस, और `.venv` के लिए लिखने योग्य प्रोजेक्ट डायरेक्टरी चाहिए।
साथ आने वाले पैनल को Node.js या फ़्रंटएंड बिल्ड की ज़रूरत नहीं है। लॉन्चर अपने सामान्य OS खाते से
चलाएँ; TgWitness को एडमिनिस्ट्रेटर/root अधिकारों की ज़रूरत नहीं है।

- **Windows:** `Start.cmd` पहले `py -3`, फिर `python`, फिर डिफ़ॉल्ट प्रति-उपयोगकर्ता और
  Program Files इंस्टॉल फ़ोल्डर जाँचता है, और संस्करण 3.11 या नया माँगता है। अगर कुछ भी काम न करे,
  तो यह ऊपर बताए गए स्वचालित प्रति-उपयोगकर्ता इंस्टॉलेशन की पेशकश करता है। `py -3 start.py` भी
  काम करता है। पोर्टेबल पैकेज को Python की बिल्कुल ज़रूरत नहीं है।
- **Linux:** `start.sh` बारी-बारी से `python3.13`, `python3.12`, `python3.11`, `python3` और `python`
  आज़माता है, और अगर कोई भी उपयुक्त न हो तो apt, dnf, pacman, zypper, apk या Homebrew के लिए
  इंस्टॉल कमांड दिखाता है। Debian/Ubuntu इंस्टॉलेशन में चुने गए इंटरप्रेटर से मेल खाने वाला
  `python3-venv` पैकेज ज़रूरी हो सकता है। डिस्ट्रीब्यूशन के पुराने डिफ़ॉल्ट Python को बदलना होगा
  या उसके साथ Python 3.11+ जोड़ना होगा।
- **macOS:** Python 3.11+ का कोई मौजूदा डिस्ट्रीब्यूशन इंस्टॉल करें; यह न मानें कि OS के साथ आया
  इंटरप्रेटर इस आवश्यकता को पूरा करता है। प्रोजेक्ट डायरेक्टरी से `python3 start.py` इस्तेमाल करें।
- **Docker:** Compose v2.20 या नए के साथ Docker Engine/Desktop इस्तेमाल करें। Windows पर Docker
  Desktop को Linux कंटेनर इस्तेमाल करने चाहिए। कंटेनर अपनी Python डिपेंडेंसी खुद इंस्टॉल करता है;
  होस्ट पर अलग Python इंस्टॉलेशन की ज़रूरत नहीं है।

## स्थानीय कंप्यूटर

Windows पर `Start.cmd` या Linux/macOS पर `sh start.sh` इस्तेमाल करें। `scripts\Setup.cmd` या
`sh start.sh --setup-only` एनवायरनमेंट तैयार करता है। लॉन्चर पहली बार चलने पर डिपेंडेंसी इंस्टॉल
करता है; बाद के लॉन्च उसी एनवायरनमेंट का दोबारा उपयोग करते हैं। सेटअप और Telegram संग्रह के लिए
इंटरनेट एक्सेस चाहिए, लेकिन मौजूदा रिकॉर्ड देखना और निर्यात बनाना ऑफ़लाइन भी होता है।

सेटअप के बाद `python start.py --check` चलाएँ, ताकि संग्रहकर्ता शुरू किए बिना स्थानीय डिपेंडेंसी,
Ed25519, स्टोरेज, कुंजी कॉन्फ़िगरेशन और लिसनिंग पते की जाँच हो सके। संरचित आउटपुट के लिए
`--json` इस्तेमाल करें। इच्छित `--data-dir`, `--host` और `--port` दें। यह जाँच न पैकेज इंस्टॉल
करती है, न जर्नल बनाती है और न Telegram से कनेक्ट होती है; यह अखंडता या कवरेज का औपचारिक
सत्यापन नहीं है। स्टार्टअप मौजूदा जर्नलों का सत्यापन अलग से करता है। `python start.py --help`
भी कुछ इंस्टॉल नहीं करता।

start.py इस्तेमाल करने के बाद सहायक कमांड Windows पर `.venv\Scripts\python.exe` या Linux/macOS
पर `.venv/bin/python` से चलाएँ, या पहले वह एनवायरनमेंट सक्रिय करें। नीचे दिए गए `python -m ...`
उदाहरण मानते हैं कि एनवायरनमेंट सक्रिय है।

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

एनवायरनमेंट वेरिएबल: TGWITNESS_DATA, TGWITNESS_HOST, TGWITNESS_PORT, TGWITNESS_TOKEN।
TGWITNESS_VAULT_KEY_FILE नए इंस्टॉलेशन के लिए बाहरी-कुंजी मोड चुनता है; देखें [बाहरी मास्टर कुंजी](../SECURITY-MODEL.md#external-master-key)।
TGWITNESS_TOKEN दिया जाए तो उसमें कम से कम 24 वर्ण होने चाहिए; क्रिप्टोग्राफ़िक रूप से यादृच्छिक
मान इस्तेमाल करें। इसके बिना ऐप panel-token.txt में 256-बिट का यादृच्छिक टोकन बनाता है।
एनवायरनमेंट वेरिएबल से दिया गया मान उस फ़ाइल को दोबारा नहीं लिखता। क्रेडेंशियल बदलने के लिए
रीस्टार्ट करें।

एक डेटा डायरेक्टरी का स्वामी ठीक एक ही प्रोसेस हो सकता है। क्रॉस-प्लेटफ़ॉर्म OS फ़ाइल लॉक गलती से
एक साथ लिखने वाले प्रोसेस को रोकता है। एक ही Uvicorn वर्कर इस्तेमाल करें। पैनल कितने भी वर्कस्पेस
प्रबंधित कर सकता है; अतिरिक्त वर्कस्पेस की डायरेक्टरी profiles/<id>/ के अंतर्गत होती हैं।
अलग सेवा इंस्टेंस के लिए अलग डायरेक्टरी और पोर्ट इस्तेमाल करें। SQLite WAL फ़ाइलें स्थानीय
स्थायी स्टोरेज पर होनी चाहिए, नेटवर्क फ़ाइलसिस्टम पर नहीं। एक वॉल्यूम को कई रेप्लिका में साझा न करें।

## Windows पोर्टेबल पैकेज

हर GitHub Release में `TgWitness-<version>-windows-amd64-portable.zip` और उसकी `.sha256` फ़ाइल
होती है। इसमें python.org का आधिकारिक एम्बेडेबल Python 3.12 रनटाइम (चेकसम
`tools/build_portable.py` में पिन है), TgWitness और उसकी पिन की गई डिपेंडेंसी, और तीन लॉन्चर हैं:

| फ़ाइल | उद्देश्य |
| --- | --- |
| `TgWitness.cmd` | पैनल शुरू करता है; अतिरिक्त विकल्प आगे भेज दिए जाते हैं, जैसे `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | `data\demo` में सिंथेटिक डेमो शुरू करता है |
| `TgWitness-Check.cmd` | शुरू किए बिना तैयारी की जाँच चलाता है |

पिन किया गया रूसी मॉर्फ़ोलॉजी शब्दकोश और PDF कलर प्रोफ़ाइल ऑफ़लाइन उपयोग के लिए पैकेज में शामिल
हैं। पैकेजिंग डिपेंडेंसी की `data` डायरेक्टरी में केवल उनके ज्ञात फ़ाइल पथों की अनुमति देती है;
उन डायरेक्टरी में कोई अनपेक्षित फ़ाइल हो तो बिल्ड विफल हो जाता है।

पूरा आर्काइव किसी लिखने योग्य फ़ोल्डर में निकालें, जैसे `Documents\TgWitness`; इसे ZIP के अंदर
से या Program Files से न चलाएँ। रनटाइम एक अलग-थलग मॉड्यूल पथ इस्तेमाल करता है, इसलिए दूसरे
Python इंस्टॉलेशन और `PYTHONPATH` उस पर असर नहीं डालते। डेटा पैकेज के `data` फ़ोल्डर में रहता है।
अपडेट करने के लिए TgWitness बंद करें, नया संस्करण नए फ़ोल्डर में निकालें और `data` फ़ोल्डर
उसमें कॉपी करें।

64-बिट Windows पर Python 3.12 के साथ इसे खुद बिल्ड करें:

~~~sh
python tools/build_portable.py
~~~

## कंटेनर

```sh
docker compose up -d --build --wait
```

यह /data के लिए एक नामित स्थायी वॉल्यूम बनाता है।
वेब पोर्ट 127.0.0.1:8787 पर मैप होता है। प्रोसेस UID 10001 के रूप में चलता है — हटाई गई
capabilities, केवल-पढ़ने योग्य रूट फ़ाइलसिस्टम और लिखने योग्य /data तथा /tmp के साथ।
`--wait` लौटने से पहले वेब-सर्वर की सेहत जाँचता है; Telegram ऑथराइज़ेशन और डिलीवरी की स्थिति
पैनल में दिखती है। दिए गए हेल्पर बिल्ड के बाद तैयारी के लिए 180 सेकंड का टाइमआउट इस्तेमाल करते
हैं। शुरुआती डिपेंडेंसी डाउनलोड में इससे ज़्यादा समय लग सकता है।

दोनों बेस Compose फ़ाइलें प्रोजेक्ट नाम `tgwitness` इस्तेमाल करती हैं, इसलिए नई रिलीज़ किसी दूसरी
डायरेक्टरी में निकालने पर चुपचाप नया डेटा वॉल्यूम नहीं चुना जाता। इस प्रोजेक्ट के लिए केवल एक
डिप्लॉयमेंट सक्रिय रखें। स्वतंत्र इंस्टॉलेशन के लिए अलग `docker compose -p NAME ...` और अलग होस्ट
पोर्ट इस्तेमाल करें, और अपडेट के समय दोनों को बनाए रखें। अलग प्रोजेक्ट नाम वाले पुराने
डिप्लॉयमेंट के लिए `-p` के साथ उसका मूल नाम ही इस्तेमाल करते रहें; `docker compose ls` मौजूदा
प्रोजेक्ट की सूची दिखाता है।

`deploy/env.example` को `.env` में कॉपी करें और दूसरा लूपबैक पोर्ट इस्तेमाल करने के लिए
`TGWITNESS_PORT` बदलें। उदाहरण के लिए, `TGWITNESS_PORT=8788` पैनल को
`http://127.0.0.1:8788` पर उपलब्ध कराता है; कंटेनर फिर भी 8787 पर सुनता है। `.env` को Git अनदेखा करता है।

शुरुआती टोकन प्राप्त करें:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

उपयोगी कमांड:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` क्रैश या Docker डेमन के रीस्टार्ट के बाद संग्रहकर्ता को फिर से शुरू करता
है। Linux सर्वर पर अपने डिस्ट्रीब्यूशन के सर्विस मैनेजर से बूट पर Docker सक्षम करें, आमतौर पर
`sudo systemctl enable --now docker`। Windows/macOS पर Docker Desktop की साइन-इन पर अपने-आप शुरू
होने वाली सेटिंग सक्षम करें। डेस्कटॉप से साइन-आउट, स्लीप या रुका हुआ Docker डेमन संग्रह को
बाधित कर सकता है। स्पष्ट रूप से रोका गया कंटेनर तब तक रुका रहता है जब तक आप उसे फिर से शुरू नहीं करते।

उदाहरण कॉन्फ़िगरेशन में /tmp वॉल्यूम 512 MiB तक सीमित है। निर्यात तैयार करने के लिए इसके बजाय
स्थायी /data पर हर वर्कस्पेस की `temporary-exports/` इस्तेमाल होती है। वहाँ एक साथ चलने वाले
निर्यात, जर्नल/WAL की बढ़त, मीडिया और बैकअप के लिए जगह आरक्षित रखें।
लॉन्चर रनटाइम डिपेंडेंसी के जाँचे-परखे संस्करण पिन करने के लिए deploy/constraints.txt इस्तेमाल करता है।
Docker और हाई-एश्योरेंस सर्वर deploy/requirements.lock और deploy/build.lock से
pip --require-hashes के साथ इंस्टॉल करते हैं: हर पैकेज फ़ाइल का कमिट में दर्ज SHA-256 से मेल खाना
ज़रूरी है, इसलिए PyPI या किसी मिरर पर बदली गई फ़ाइल अस्वीकार हो जाती है। Python बेस इमेज और
ऑपरेटिंग सिस्टम पैकेजों के लिए अब भी रिलीज़ का स्वतंत्र सत्यापन ज़रूरी है।

जब तक आप जर्नल और कुंजियाँ नष्ट करना न चाहें, docker compose down -v इस्तेमाल न करें।
कंटेनर की सेहत वेब-सर्वर की उपलब्धता बताती है, Telegram से सफल कैप्चर नहीं।
पैनल में संग्रहकर्ता की स्थिति, हार्टबीट, त्रुटियाँ और कवरेज इवेंट देखें।

### स्वतंत्र गवाह प्रोफ़ाइल

वैकल्पिक `witness` सेवा एक [स्वतंत्र गवाह](../WITNESS.md) को उसके अपने कंटेनर में चलाती है;
उसकी अपनी कुंजी और जर्नल `witness-data` वॉल्यूम में रहते हैं, और संग्रहकर्ता तक पहुँच के लिए उसके
पास केवल-पढ़ने वाला गवाह टोकन होता है। टोकन पैनल में **अधिक उपकरण → अतिरिक्त सुविधाएँ → स्वतंत्र गवाह**
में बनाएँ, उसे बॉट टोकन और चैनल के साथ `.env` में जोड़ें, फिर प्रोफ़ाइल शुरू करें:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

सेवा Compose नेटवर्क के अंदर संग्रहकर्ता तक `http://tgwitness:8787` पर पहुँचती है
(`TGWITNESS_WITNESS_COLLECTOR` इसे बदल देता है, उदाहरण के लिए किसी दूसरे वर्कस्पेस के लिए
`/profiles/<workspace ID>`)। अगर गवाह किसी अलग सर्वर पर हो और उसे कोई और चलाता हो, तो वहाँ
`deploy/compose/compose.witness.yaml` इस्तेमाल करें और `TGWITNESS_WITNESS_COLLECTOR` को
संग्रहकर्ता के HTTPS पते पर सेट करें; उस फ़ाइल में केवल गवाह है।

## प्रकाशित इमेज इंस्टॉल करें

`deploy/env.example` को `.env` में कॉपी करें। `TGWITNESS_IMAGE` को प्रकाशित संस्करण पर सेट करें और
रिपॉज़िटरी पथ **छोटे अंग्रेज़ी अक्षरों** में लिखें, उदाहरण के लिए:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.9.2
TGWITNESS_PORT=8787
```

`compose.yaml` के बजाय यह फ़ाइल अकेले चलाएँ:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

होस्ट पर सोर्स बिल्ड, Python या कंपाइलर की ज़रूरत नहीं है। रिलीज़ वर्कफ़्लो Linux AMD64 और
ARM64 कंटेनरों को लक्षित करता है, जिसमें Docker Desktop का Linux VM भी शामिल है।
वर्कफ़्लो सारांश से संस्करण टैग या `ghcr.io/owner/repository@sha256:...` इस्तेमाल करें।
न कोई बदलता हुआ `latest` टैग कॉन्फ़िगर है, न बिना निगरानी के एप्लिकेशन अपग्रेड।
प्रोजेक्ट नाम एक जैसा हो तो इमेज और सोर्स वाले रूप एक ही डेटा वॉल्यूम इस्तेमाल करते हैं।

## सर्वर पर स्वचालित HTTPS

ऐसा सर्वर इस्तेमाल करें जिस पर Docker हो, आपके नियंत्रण वाला डोमेन, और स्थायी स्थानीय स्टोरेज।
डोमेन के A/AAAA रिकॉर्ड सर्वर की ओर इंगित करें; AAAA केवल तभी प्रकाशित करें जब IPv6 से सर्वर तक
पहुँचा जा सके। प्रमाणपत्र जारी होने के लिए इनबाउंड TCP 80 और 443 तथा आउटबाउंड DNS/HTTPS की
अनुमति दें। ये पोर्ट पहले से किसी दूसरी सेवा के पास नहीं होने चाहिए।

`deploy/env.example` को `.env` में कॉपी करें और बिना स्कीम या पथ के होस्टनेम सेट करें:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

HTTPS ओवरले के साथ सोर्स बिल्ड शुरू करें:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

प्रकाशित इमेज के लिए इसके बजाय पहली फ़ाइल के रूप में `deploy/compose/compose.image.yaml` इस्तेमाल
करें। बाद के स्टेटस, लॉग, अपडेट और स्टॉप कमांड के लिए भी दोनों `-f` आर्ग्युमेंट रखें।

Caddy प्रमाणपत्र प्राप्त और नवीनीकृत करता है, HTTP को HTTPS पर रीडायरेक्ट करता है, और अनुरोधों को
निजी Compose नेटवर्क पर संग्रहकर्ता तक भेजता है। प्रमाणपत्र की स्थिति का अपना स्थायी वॉल्यूम है।
संग्रहकर्ता का सीधा होस्ट पोर्ट केवल लूपबैक पर रहता है।
दिया गया Caddy कॉन्फ़िगरेशन एक्सेस लॉगिंग सक्षम नहीं करता।

`https://watch.your-domain.org` खोलें और पैनल टोकन दर्ज करें। Compose की तैयारी केवल कंटेनरों पर
लागू होती है; प्रमाणपत्र जारी होना और बाहर से पहुँच DNS और फ़ायरवॉल पर निर्भर करते हैं। अगर HTTPS
तैयार नहीं है, तो DNS, फ़ायरवॉल नियम और यह जाँचें:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

दी गई Caddy इमेज अपने `2-alpine` टैग का अनुसरण करती है। pull करने से वह इमेज ताज़ा हो जाती है;
अगर आपको इन्फ्रास्ट्रक्चर के स्थिर संस्करण चाहिए, तो अपने डिप्लॉयमेंट में जाँचा हुआ डाइजेस्ट पिन करें।

## अपडेट और बैकअप

अपडेट के दौरान Compose प्रोजेक्ट नाम और डेटा वॉल्यूम बनाए रखें। पहले संग्रहकर्ता रोकें और पूरा
बैकअप बनाएँ। डिफ़ॉल्ट सोर्स-आधारित डिप्लॉयमेंट के लिए:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

हर बार रिपॉज़िटरी के बाहर नया बैकअप गंतव्य इस्तेमाल करें और उसे खाते तक पहुँच देने वाली सामग्री
की तरह सुरक्षित रखें। उदाहरण का पथ केवल समझाने के लिए है; अपना निजी बैकअप स्थान इस्तेमाल करें।
पूरी डायरेक्टरी कॉपी करें, जिसमें छिपी फ़ाइलें, सभी वर्कस्पेस, कुंजियाँ, जर्नल और मीडिया शामिल हों।
अगर बाहरी वॉल्ट मास्टर कुंजी कॉन्फ़िगर है, तो उसका अलग से बैकअप लें।
सबूत ZIP ऐसा एप्लिकेशन बैकअप नहीं है जिससे रीस्टोर किया जा सके। HTTPS के लिए, अगर Caddy के
प्रमाणपत्र/खाते की स्थिति बनाए रखनी है, तो उसके वॉल्यूम भी सुरक्षित रखें।

सोर्स डिप्लॉयमेंट के लिए नई रिलीज़ फ़ाइलें प्राप्त करें और चलाएँ:

```sh
docker compose up -d --build --wait
```

इमेज डिप्लॉयमेंट के लिए `TGWITNESS_IMAGE` को इच्छित संस्करण पर बदलें, फिर चलाएँ:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

ऊपर के stop/copy कमांड के लिए भी अपने इंस्टॉलेशन की Compose फ़ाइल (या फ़ाइलें) इस्तेमाल करें।
`.env`, अपना कस्टम कॉन्फ़िगरेशन और वही प्रोजेक्ट नाम बनाए रखें। `down` नामित वॉल्यूम रखता है;
**`down -v` उन्हें हटा देता है**। `.venv` को अलग-अलग ऑपरेटिंग सिस्टम या Python संस्करणों के बीच
कॉपी न करें। नेटिव अपडेट के लिए TgWitness रोकें, उसकी पूरी डेटा डायरेक्टरी का बैकअप लें, सोर्स
फ़ाइलें बदलें और लॉन्च से पहले `python start.py --setup-only` चलाएँ।

अपडेट के बाद पैनल एक्सेस, खाते की पहचान, निरीक्षण की स्थिति और कवरेज जाँचें। रीस्टार्ट के बाद
TgWitness सहेजी गई Telegram अपडेट पोज़िशन से फिर शुरू करता है और अपडेट के दौरान छूटे अपडेट
माँगता है। अगर भविष्य का कोई संस्करण स्टोरेज फ़ॉर्मैट बदलता है, तो रोलबैक के लिए अपडेट से पहले का
बैकअप ज़रूरी हो सकता है।

## रिमोट सर्वर

सेवा को लूपबैक पर बाँधे रखें और SSH टनल इस्तेमाल करें, या HTTPS को रिवर्स प्रॉक्सी पर टर्मिनेट
करें। बेस Compose फ़ाइल केवल स्थानीय उपयोग के लिए है; वैकल्पिक `deploy/compose/compose.https.yaml`
ओवरले कॉन्फ़िगर किए गए डोमेन के लिए Caddy देता है। bearer टोकन को URL और प्रॉक्सी लॉग से बाहर
रखें। रिवर्स प्रॉक्सी को अनुरोध का आकार और कनेक्शन दर सीमित करनी चाहिए। सादा HTTP इंटरनेट पर
उजागर न करें।

systemd, Windows लॉगऑन टास्क, macOS यूज़र एजेंट और Caddy के उदाहरण
[deploy/](../../deploy/README.md) में दिए गए हैं। इंस्टॉल करने से पहले उनके पथ जाँचें और अपनी
ज़रूरत के अनुसार बदलें। ये उपलब्ध कराए गए टेम्पलेट हैं, स्थानीय रूप से चलाकर किया गया प्लेटफ़ॉर्म
सत्यापन नहीं। सामान्य लॉन्चर कोई बैकग्राउंड सेवा या टास्क पंजीकृत नहीं करता।

Windows पर बिना विंडो वाले `pythonw.exe` लॉन्च में स्टार्टअप/सर्वर डायग्नोस्टिक्स डेटा डायरेक्टरी
के अंतर्गत `logs/server.log` में सहेजे जाते हैं (प्रति फ़ाइल 5 MiB, दो रोटेट किए गए बैकअप)।
कंसोल से लॉन्च करने पर लॉग कंसोल में ही आते रहते हैं। HTTP एक्सेस लॉगिंग दोनों मोड में बंद है।
लॉग को डेटा डायरेक्टरी की तरह ही सुरक्षित रखें और साझा करने से पहले उनकी समीक्षा करें।

## रीस्टार्ट और अंतराल

अंतिम बार माँगी गई निरीक्षण स्थिति सहेजी जाती है। अगर निरीक्षण सक्रिय था, तो स्टार्टअप दोबारा
कनेक्ट होने और चुने गए स्रोतों को फिर शुरू करने की कोशिश करता है। मैन्युअल विराम यह इरादा हटा
देता है। विफल रीस्टार्ट दर्ज किया जाता है और पैनल में दिखाया जाता है।

TgWitness खाते और हर चैनल के लिए Telegram की अपडेट पोज़िशन (pts, qts, seq और date) वर्कस्पेस
वॉल्ट में सहेजता है और अगली शुरुआत पर उसे बहाल करता है। इसके बाद क्लाइंट वे अपडेट माँगता है जो
प्रोसेस बंद रहने के दौरान छूट गए, और आवधिक पुनर्जाँच छूटे संदेश वापस लाती है तथा उन सहेजे गए
संदेशों को दर्ज करती है जिन्हें Telegram अब नहीं लौटाता। शुरुआत पर डायलॉग दोबारा लोड होते हैं।
हर स्टार्टअप पिछला जर्नल हेड, ऑफ़लाइन सीमा और वह अपडेट पोज़िशन दर्ज करता है जहाँ से काम फिर
शुरू हुआ। मॉनिटर हर 10 सेकंड में कनेक्टिविटी जाँचता है और हर मिनट एक हार्टबीट जोड़ता है
(**अधिक उपकरण → पैरामीटर → सक्रियता रिकॉर्ड हर**)।
डिस्कनेक्शन और शांत अवधियाँ अपने कारण के साथ कवरेज अंतराल के रूप में दर्ज होती हैं।
इतिहास के स्नैपशॉट लाइव रिकॉर्ड के साथ अलग वर्तमान-इतिहास निरीक्षणों के रूप में सहेजे जाते हैं।

मीडिया कतार हर वर्कस्पेस के SQLite डेटाबेस में सहेजी जाती है। संदेश और उसका जॉब एक साथ एटॉमिक
रूप से कमिट होते हैं। चलते-चलते बीच में रुके जॉब स्टार्टअप पर दोबारा कोशिश के लिए बहाल किए जाते
हैं। हर डाउनलोड का मूल टाइमआउट 120 सेकंड है, जिसमें फ़ाइल के आकार के हिसाब से 256 KiB/s की गति
पर लगने वाला समय जुड़ता है, और हर अटैचमेंट प्रकार के लिए 1–2,000 MiB की सीमा है; टाइमआउट, गति
और दोबारा कोशिशें **अधिक उपकरण → पैरामीटर** में हैं। संग्रहकर्ता उन फ़ाइलों को छोड़ देता है जिनका
आकार अज्ञात है। विराम देने पर कतार का काम बना रहता है। दोबारा कोशिश मूल रूप से देखे गए फ़ाइल
डिस्क्रिप्टर का उपयोग करती है, बाद में संपादित संदेश के नवीनतम संस्करण का कभी नहीं। अस्थायी
विफलताओं के लिए दोबारा कोशिशें सीमित हैं; मीडिया के FloodWait विराम रीस्टार्ट के बाद भी बने रहते
हैं। मीडिया रिकवरी Telegram अपडेट रिकवरी से अलग है और गायब हो चुकी फ़ाइलें दोबारा नहीं बना सकती।

## बैकअप, रीस्टोर और क्षमता

**पूरी डेटा डायरेक्टरी** कॉपी करने से पहले प्रोसेस रोकें, जिसमें vault.key, signing.enc,
credentials.enc, SQLite डेटाबेस/WAL फ़ाइलें, मीडिया, टोकन, चेकपॉइंट और profiles/ की सभी
सबडायरेक्टरी शामिल हैं। पूरी प्रति तब रीस्टोर करें जब गंतव्य सेवा रुकी हुई हो। वॉल्ट कुंजियाँ न
होने या साइनिंग कुंजी मेल न खाने पर स्टार्टअप विफल होता है; ज़बरदस्ती पहुँच पाने के लिए कुंजियाँ
दोबारा न बनाएँ।

गोपनीय जानकारी वाले बैकअप एन्क्रिप्टेड और एक्सेस-नियंत्रित रखें। सबूत ZIP समीक्षा के लिए
पोर्टेबल सामग्री हैं, एप्लिकेशन बैकअप या Telegram सेशन बैकअप नहीं।
रिटेंशन अवधि पूरी होने पर अपने-आप हटाने की कोई व्यवस्था नहीं है। सभी संदेशों, कच्चे मेटाडेटा,
मीडिया, अस्थायी निर्यात और बैकअप के लिए डिस्क स्थान की योजना बनाएँ।

स्टार्टअप सत्यापन और निर्यात पूरा जर्नल लोड करने के बजाय रिकॉर्ड स्ट्रीम करते हैं।
निर्यात एक रीड स्नैपशॉट पिन करता है, जबकि WAL में नए लेखन जारी रह सकते हैं; लंबे समय तक चलने
वाले निर्यात WAL पेज रोके रख सकते हैं, इसलिए डिस्क क्षमता फिर भी मायने रखती है। स्वतंत्र
वेरिफ़ायर के डिफ़ॉल्ट से मेल खाने के लिए ZIP असंपीड़ित रूप में 4 GiB तक सीमित हैं;
**अधिक उपकरण → पैरामीटर → सबसे बड़ी हस्ताक्षरित ZIP** यह सीमा बढ़ाता है, और ऐसे आर्काइव
`verify.py --max-gib N` से सत्यापित किए जाते हैं। अन्य फ़ॉर्मैट में इवेंट की संख्या पर कोई सीमा नहीं है।
समर्थित ब्राउज़र जवाब के हिस्सों को उपयोगकर्ता द्वारा चुनी गई फ़ाइल में स्ट्रीम करते हैं। अन्य
ब्राउज़र अधिकतम 128 MiB बफ़र करते हैं और बड़े ट्रांसफ़र के लिए प्रमाणीकृत CLI की ओर भेजते हैं:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

किसी दूसरे वर्कस्पेस के लिए **निर्यात → वर्कस्पेस आईडी** से `--profile ID`,
`--format zip|jsonl|csv|html`, रिमोट सर्वर के लिए `--url https://your-server`, या 5 GiB की
ट्रांसफ़र सीमा बदलने के लिए `--max-mib` इस्तेमाल करें। सादा HTTP केवल लूपबैक के लिए अनुमत है।
टोकन हेडर में भेजे जाते हैं, रीडायरेक्ट अस्वीकार किए जाते हैं, मौजूदा फ़ाइलें ओवरराइट नहीं होतीं,
और अधूरे डाउनलोड पूरी फ़ाइलों के रूप में प्रकाशित नहीं किए जाते।
अगर TGWITNESS_TOKEN बनाए गए टोकन की जगह लेता है, तो उसी सक्रिय मान वाली, अलग से सुरक्षित फ़ाइल
इस्तेमाल करें: यह बदला हुआ मान panel-token.txt को दोबारा नहीं लिखता।
कमांड का SHA-256 केवल ट्रांसफ़र चेकसम है; हस्ताक्षरित ZIP का सत्यापन स्वतंत्र रूप से करें।

पैनल कतार में लगे/विफल मीडिया, सबसे पुराना लंबित मीडिया, खाली डिस्क स्थान, Telegram अनुरोधों के
विराम और वे स्रोत दिखाता है जिन तक पहुँच की पुष्टि नहीं हुई है। ये डायग्नोस्टिक्स डिलीवरी की पूरी
एंड-टू-एंड निगरानी नहीं हैं। वर्कस्पेस एक ही प्रोसेस साझा करते हैं; बहुत ज़्यादा सक्रिय खाता फिर भी
दूसरों को प्रभावित कर सकता है। अलग वर्कर प्रोसेस, रिटेंशन/रोटेशन, स्थायी अपडेट रिकवरी और
डिप्लॉयमेंट का पूरा सत्यापन अभी बाकी हैं। पैनल तक सीमित दायरे वाली पहुँच
[एक्सेस और अनुमतियाँ](../ACCESS.md) में बताई गई है; स्वतंत्र चेकपॉइंट
[गवाह गाइड](../WITNESS.md) में शामिल हैं।

[संचालन मोड](../OPERATIONS.md)।
