# Подключение, прокси и защита данных

В данном документе описано поведение TgWitness версии 1.0.1 и его ограничения. Аутентификация, доступ к источнику, сетевое соединение и полнота сбора данных представляют собой отдельные состояния. Информацию о шагах входа в систему, форматах файлов и работе с несколькими аккаунтами см. в разделах, посвящённых [аккаунтам и форматам сеансов](ACCOUNTS.md). Информацию о политиках событий и поведении при перезапуске см. в разделе, [посвящённом работе коллекций](COLLECTION.md).

<a id="guided-connection-setup"></a>
## Настройка подключения с помощью мастера

В разделе **Дополнительные инструменты → Учётная запись → Маршрут подключения** администратор может выбрать **Этот аккаунт**, **Группа аккаунтов** или **Все аккаунты**, а затем выбрать маршрут. В списке **Просмотр выбора** отображаются затронутые аккаунты. Функ**ция Подготовить и проверить** позволяет протестировать предлагаемый маршрут без изменения сохраненного. **Применение проверенного подключения** подтверждает предварительный просмотр, при необходимости приостанавливает наблюдение, сохраняет маршрут и возобновляет уже запущенное наблюдение. Сбор данных никогда не запускается в аккаунте, который ранее находился в неактивном состоянии. Загрузка истории остается приостановленной и может быть возобновлена отдельно. Перед переключением приостановите активные экспорты.

При изменении настроек группы аккаунты по умолчанию сохраняют свои собственные маршруты. Снимайте эту опцию только в том случае, если в предварительном просмотре отображаются именно те изменения, которые вы намереваетесь внести. Приложение сообщает результаты по каждому аккаунту; это не транзакция типа «всё или ничего» для всех баз данных. В случае неудачного переключения восстанавливаются предыдущие настройки данного аккаунта. Невозможность возобновления отображается явно. Срок действия предварительного просмотра истекает через десять минут, а изменения в настройках подключения или членстве в группе требуют новой проверки.

При применении успешный результат предварительной проверки используется повторно в течение 90 секунд, если его маршрут, режим и политика остаются неизменными. Управляемый туннель по-прежнему должен иметь тот же запущенный процесс. Более старые результаты, изменившиеся процессы туннелей и автоматические маршруты пула MTProxy проверяются заново. Подписанная запись приложения сохраняет исходное время проверки, а также фиксирует повторное использование и срок действия записи. Каждая предварительная проверка закрывает свой временный неавторизованный клиент; сборщик подключается, используя собственную авторизованную сессию.

| Маршрут | Что управляет TgWitness |
| --- | --- |
| Прямой | Соединения с хоста; VPN внешнего хоста не обнаруживается и не принудительно настраивается. |
| VPN | Один профиль WireGuard с полным туннелем на каждый аккаунт, реализуемый локальным процессом SOCKS5 в пользовательском пространстве. Никаких хост-интерфейсов или драйверов не устанавливается. |
| Мой прокси | Учетные данные SOCKS5, HTTP CONNECT или MTProxy. В поля SOCKS5/HTTP можно ввести URL-адрес. При выборе нескольких аккаунтов введенные данные прокси используются совместно. |
| Общедоступный MTProto | Существующий пул назначает маршруты Telegram. Внешние запросы отключены до тех пор, пока в расширенных настройках не будет настроен отдельный подходящий прокси-сервер. |
| WARP | Отдельный локальный туннель для каждого выбранного аккаунта с регистрацией в WARP и профилем WireGuard, хранящимся в хранилище данных этого аккаунта. |

Проверка текущего маршрута использует новый неавторизованный транспорт Telegram, а не сеанс аккаунта. Она открывает транспортное соединение через маршрут к центру обработки данных аккаунта и выполняет один неавторизованный цикл MTProto (`req_pq_multi`); при этом не создаётся ключ авторизации и не используется аккаунт. Указанная задержка представляет собой время установления соединения плюс время обратного цикла, и проверка фиксирует обе части отдельно. Для маршрутов, поддерживающих HTTP, также запрашивается HTTPS-трассировка Cloudflare через данный маршрут и отображаются указанные в ней IP-адрес выхода, страна, состояние WARP и время проверки. Подготовка WARP завершается сбоем, если в трассировке не указано, что WARP активен. Эти предварительные проверки отображают состояние доступности маршрута и наблюдаемый выходной узел. Просмотрите зафиксированные записи в результатах сбора и проверки архива. Сам по себе запущенный локальный процесс не является признаком успешной проверки выхода.

Панель отслеживает скользящее среднее значение последних пяти проверок. Маршрут считается **медленным**, если среднее значение превышает 5 секунд или три проверки подряд превышают это значение, и **недоступным —** после двух неудачных проверок подряд; изменения фиксируются в записях `network.slow_route` и `network.route_recovered`. В случае медленного маршрута WARP **функция Re-roll WARP** перезапускает туннель аккаунта через другие конечные точки Cloudflare WARP, сохраняет самый быстрый вариант и фиксирует изменения в поле `network.warp_rerolled` с указанием времени до и после; **функция New WARP identity** регистрирует новое устройство WARP и сохраняет его только в том случае, если оно работает быстрее. Адрес локального прокси, аккаунт Telegram и его сеанс остаются прежними; соединения Telegram восстанавливаются через перезапущенный туннель. Медленный маршрут WARP перенастраивается автоматически не чаще одного раза в 30 минут; если это не помогает, дальнейшие перенастройки ожидают вмешательства оператора.

<a id="portable-warp-and-wireguard"></a>
### Портативный WARP и WireGuard

Это **неофициальная интеграция WARP** с использованием [wgcf 2.3.1](https://github.com/ViRb3/wgcf/releases/tag/v2.3.1) и [wireproxy 1.1.3](https://github.com/windtf/wireproxy/releases/tag/v1.1.3). Администратор явно соглашается на настройку до первой загрузки или регистрации в WARP. Эти настройки подключения осуществляются напрямую к GitHub и Cloudflare и раскрывают IP-адрес устройства. Обычный трафик аккаунта сохраняет существующий маршрут до момента применения. Cloudflare выбирает адрес выхода и страну; отдельные туннели могут использовать один и тот же адрес выхода. Данная функция не поддерживает выбор страны, периодическую ротацию IP-адресов и глобальный для всего хоста «kill switch» VPN.

Поддерживаемые версии вспомогательных программ: Linux и macOS (x86-64/ARM64), а также Windows (x86-64). Артефакты проверяются по хешам SHA-256, включённым в проверенный исходный код, а исполняемые файлы из кэша проверяются повторно перед запуском. Хелпер не добавляется в PATH, не устанавливается в качестве системной службы и не получает публичного прослушивателя. Все файлы хранятся в каталоге `portable-routes/` рабочей области и в зашифрованных записях хранилища. Для прослушивателя SOCKS5 с обратной связью требуются независимо сгенерированные учетные данные.

Личные профили и учетные данные аккаунта WARP шифруются с помощью существующей рабочей области. Во время работы вспомогательной программе требуется конфигурационный файл в виде открытого текста, доступный только владельцу; при нормальном завершении работы он удаляется. В случае сбоя хоста этот файл может остаться в папке данных, доступной только владельцу. Это не обеспечивает шифрование диска и не защищает от действий его администратора. Супервизор закрывает туннель, если исчезает родительский канал панели. Неудавшийся туннель никогда не включает прямой резервный вариант. Перезапуск панели восстанавливает выбранный туннель; неудавшиеся запуски повторяются с ограниченной задержкой. **Остановка туннеля** также приостанавливает наблюдение и сохраняет состояние остановки. **Запуск туннеля** запускает туннель; возобновите наблюдение отдельно, когда будете готовы.

Загруженные профили WireGuard должны содержать один интерфейс и один узел-партнёр, полные маршруты IPv4 и IPv6, а также не должны содержать хуков, включений, подстановок переменных среды или дополнительных прослушивателей. Адреса публичных конечных точек разрешаются и фиксируются до запуска. Для OpenVPN/IPsec и частных конечных точек используйте внешний VPN-шлюз или SOCKS5-шлюз.

<a id="authentication-methods"></a>
## Методы аутентификации

**Идентификатор API и хеш API идентифицируют приложение; они не заменяют вход в аккаунт.** В TgWitness они являются необязательными. Приоритет: сначала пара, введённая в форму, затем пара из импортированного JSON-файла аккаунта, далее пара, сохраненная в рабочей области, и, наконец, встроенный пул из 50 публичных пар, которые пробуются в случайном порядке с автоматической ротацией в случае отказа Telegram. Только пара Telegram Desktop (2040) отправляется с соответствующим описанием клиента Telegram Desktop. Ваша собственная пара, полученная с помощью инструментов разработки API на сайте [my.telegram.org,](https://my.telegram.org) может использоваться со всеми вашими аккаунтами; при этом каждый аккаунт по-прежнему имеет собственную авторизацию.

| Метод | Требования | Поддержка TgWitness |
| --- | --- | --- |
| Телефон, код, двухфакторная аутентификация (2FA) — необязательно | Доступ к аккаунту; пара API — по желанию | Вход в панель управления |
| HEX-ключ аутентификации + DC-идентификатор | Полный ключ длиной 512 символов и DC 1–5 | Вкладка **«Ключ** прямой **аутентификации»**; опционально: проверка идентификатора пользователя перед сохранением авторизации |
| Строка сеанса Telethon | Допустимая строка сеанса | Вход в панель управления |
| Telethon SQLite`.session` | Закрытая, согласованная копия | Прямой импорт схем в панель 7/8; опциональный автономный интерфейс командной строки |
| Pyrogram SQLite`.session` | Закрытый производственный сеанс пользователя | Прямой импорт схем через панель управления 2/3 |
| Telegram Desktop TData ZIP | Одна современная учетная запись; локальный пароль, если защищена | Преобразование в памяти с проверкой контрольной суммы и дешифрования |
| JSON-файл аккаунта | Поддерживаемые поля API/сеанса/ключа | Метаданные самостоятельно заполняют учетные данные API; по-прежнему требуется вход с помощью сеанса/ключа или номера телефона/QR-кода |
| Вход с помощью QR-кода | Подтверждение из авторизованного приложения Telegram | Локальное генерация QR-кода, срок действия/повторная попытка, опциональная двухфакторная аутентификация |
| TDLib / Pyrogram StringSession | Другие форматы, специфичные для библиотек | Не поддерживается |
| Токен бота | Бот с собственной моделью доступа/обновления | Не используется данным сборщиком |

Telegram самостоятельно выбирает способ доставки кода, в том числе решает, отправлять ли SMS. Хеш API не может восстановить аннулированный сеанс или заменить забытый пароль двухфакторной аутентификации. TgWitness не сохраняет коды входа или пароль двухфакторной аутентификации Telegram на диск.

Для частного источника у аккаунта уже должен быть доступ. Имя пользователя группы не требуется. Использование прокси или импорт сеанса не дают ни членства, ни прав администратора. Настройки чата определяют, видят ли участники историю, накопленную до их присоединения.

<a id="import-a-telethon-session-file"></a>
## Импорт файла сеанса Telethon

Файлы Telethon SQLite, Pyrogram SQLite и TData для Telegram Desktop используют разные форматы. Панель автоматически определяет и преобразует поддерживаемые структуры; переименование файла не является преобразованием. Выберите один сеанс и сопутствующий ему файл JSON в разделе **Файлы**, нажмите **Проверить файлы**, а затем **Подключить аккаунт**. Допускается до четырёх совпадающих файлов общим объёмом до 8 MiB. Подробности о [ограничениях форматов](ACCOUNTS.md) см. в разделе «TData/JSON». Возможность восстановления пароля отсутствует. Вход с помощью телефона/двухфакторной аутентификации (2FA) или QR-кода создаёт отдельную авторизацию.

Дополнительный путь командной строки, доступный только в Telethon, по-прежнему остается в вашем распоряжении:

1. Остановите работу клиента, использующего исходный сеанс, и создайте согласованную копию. Конвертер отклоняет файлы с незавершённым журналом WAL. Чтобы обойти эту проверку, правильно закройте исходный клиент вместо удаления этих файлов.
2. Из среды TgWitness выполните:

```sh
python -m tgwitness.sessions account.session --out account.tgwitness-session
```

3. В разделе **Добавить аккаунт → Файлы** загрузите результат или вставьте его строку и продолжите.
4. Проверьте отображаемый числовой идентификатор аккаунта, выберите источники и начните наблюдение.

**Преобразованный файл представляет собой незашифрованный секрет доступа к аккаунту.** Храните его в защищённом хранилище и ни в коем случае не фиксируйте его в базе данных и не отправляйте сторонним службам преобразования. TgWitness сохраняет авторизованный сеанс в своём зашифрованном хранилище. Копирование сеанса не приводит к созданию отдельной авторизации: не запускайте параллельные клиенты с клонированными ключами авторизации и не предполагайте независимую доставку обновлений.

Конвертация передаёт авторизацию, а не исходные сообщения, кэш сущностей или постоянный курсор обновлений. Она не обеспечивает восстановление обновлений при перезапуске процессов.

<a id="mtproto-telethon-and-proxies"></a>
## MTProto, Telethon и прокси

MTProto — это протокол Telegram. Telethon — это библиотека клиента на языке Python, которую использует TgWitness. MTProxy — это транспортный прокси Telegram; SOCKS5 и HTTP CONNECT обеспечивают общие туннели. Ни один из них не заменяет аутентификацию аккаунтов.

Сохраните маршрут для каждой рабочей области в разделе **Дополнительные инструменты → Аккаунты → Настройки → Настройки подключения → Изменить маршрут подключения** перед входом в систему. Для новых рабочих областей по умолчанию установлен режим **Автоматический MTProxy · Общедоступные списки** с параметром **Скрыть адрес**. Существующие рабочие области, в которых явно использовался режим «Прямой», сохраняют режим, допускающий его использование.

Файлы читаются через отдельные соединения, отличные от тех, что используются для чтения сообщений, как это делается в официальных приложениях. В собственном центре обработки данных аккаунта повторно используется ключ авторизации аккаунта с новым сеансом MTProto; для другого центра обработки данных создаётся один ключ, который авторизуется во время подключения аккаунта и хранится исключительно в памяти. Каждое файловое соединение использует тот же маршрут, что и аккаунт. Их количество на один центр обработки данных ограничено параметром **Параметры → Производительность → Количество файловых соединений на один центр обработки данных Telegram**; значение «0» означает, что файлы считываются исключительно через основное соединение аккаунта. Одновременно может быть установлено не более пяти соединений Telegram для всех аккаунтов данной инсталляции.

<a id="ip-modes"></a>
## Режимы IP

Маршрут определяет тип соединения. Режим IP, а также **настройка Защита IP** в разделе «Аккаунт» панели управления определяют, в каких случаях адрес сервера может быть раскрыт. Эти настройки не устанавливают VPN и не перенаправляют весь трафик компьютера.

| Режим | Telegram | Внешние запросы |
| --- | --- | --- |
| Скрыть адрес (`hide`) | Использовать прокси; ждать, если ни один не работает. Прямой резервный вариант отсутствует. | Требуется SOCKS5/HTTP; отклоняются запросы без подходящего прокси-сервера. |
| Прямой доступ в качестве крайней меры (резервный вариант — `fallback`) | Автоматический MTProxy может использовать прямой доступ по истечении настроенной задержки, а затем вернуться к работающему прокси-серверу. | Отдавайте предпочтение настроенному внешнему прокси-серверу или маршруту SOCKS5/HTTP аккаунта; в противном случае допускается использование прямого подключения. |
| Сервер, расположенный за туннелем или VPN (`tunnel`) | Допускаются маршруты «Прямой» и немедленное переключение на резервный пул. | Режим «Прямой» разрешён, если не настроен ни один подходящий прокси-сервер. |

Режим «туннель» или «VPN» предполагает, что вы управляете данной сетью отдельно. Без работающего туннеля адресаты могут видеть собственный адрес сервера. Выбирайте режим в соответствии с вашей фактической сетью, а не по названию опции.

<a id="choose-a-route"></a>
### Выберите маршрут

| Маршрут | Настройки | Граница |
| --- | --- | --- |
| Автоматический MTProxy | Встроенные списки или каталог операторов | Обеспечивает работоспособность маршрута Telegram; прямой переход на резервный вариант зависит от режима IP |
| Прямой | Режим туннеля или VPN | Telethon использует сетевой маршрут хоста |
| SOCKS5 | Хост, порт, опционально — имя пользователя/пароль | python-socks, поддержка удалённого DNS-адреса |
| HTTP CONNECT | Хост, порт, опционально — имя пользователя/пароль | Обычный HTTP CONNECT; TLS для самого прокси не реализован |
| MTProxy | Хост, порт, секретный ключ | Экспериментальный транспорт Telethon; 32 шестнадцатеричных цифры или `dd` + 32 шестнадцатеричных цифры |

Поддельные секретные ключи TLS `ee` отклоняются. Нормализация в Telethon 1.45 может удалять префикс и домен, однако это не реализует функцию «Поддельный TLS». Вставьте ссылку `tg://proxy?server=…&port=…&secret=…` или `https://t.me/proxy?server=…&port=…&secret=…` и выберите **Заполнить поля из ссылки**. Это позволит проверить и заполнить поля без установления соединения или сохранения; проверьте и сохраните маршрут отдельно. Поля для ручного ввода остаются доступными. См. раздел [Прокси-ссылки Telegram](https://core.telegram.org/api/links#proxy-links).

<a id="public-proxies-supplied-by-your-installation"></a>
### Общедоступные прокси, предоставляемые вашей установкой

Встроенный список объединяет семь источников: [SoliSpirit/mtproto](https://github.com/SoliSpirit/mtproto), [zakky8/mtproto-proxy-pro](https://github.com/zakky8/mtproto-proxy-pro), [kort0881/telegram-proxy-сборщик](https://github.com/kort0881/telegram-proxy-collector), [3yed-61/MTP-сборщик](https://github.com/3yed-61/MTP-Collector), [Therealwh/MTPproxyLIST](https://github.com/Therealwh/MTPproxyLIST), [KhodeJav/telegram-proxy-сборщик](https://github.com/KhodeJav/telegram-proxy-collector) и [tgmtproxy/telegram-mtproto-проxy-list](https://github.com/tgmtproxy/telegram-mtproto-proxy-list). Включённый в пакет снэпшот содержит данные о конечных точках, информацию об авторах источников и даты загрузки. Эти записи служат исходными данными; приведённые ниже проверки подключения определяют, какие прокси-серверы будут использоваться.

**MTProxy автоматически** проверяет доступность транспортного протокола Telegram, поддерживает рабочий прокси-сервер и переключается на другой в случае сбоя. Рабочие области отдают предпочтение разным прокси-серверам при наличии достаточного количества рабочих записей; прокси-серверы могут использовать общий выходной адрес. Неработающие прокси-серверы переходят в режим ожидания перед повторной попыткой. Если ни один из них не работает, режим IP определяет, следует ли сбору данных перейти в режим ожидания или можно использовать прямое соединение. Смена прокси-серверов не приводит к смене аккаунта или удалению его журнала. Выбор и изменения маршрутов фиксируются в подписанном журнале.

Пока активны автоматические маршруты, списки обновляются ежечасно, а проверки транспортного соединения по умолчанию выполняются каждые десять минут. Эти интервалы можно настроить. **Обновление публичных списков** инициирует их перезагрузку; простой просмотр списка не изменяет сохраненный ручной маршрут.

**Трафик Telegram и HTTPS-запросы используют разные маршруты.** Загрузка списков осуществляется через отдельное HTTPS-соединение и предоставленный маршрут внешних запросов. Параметр `TGWITNESS_PROXY_FEED_PROXY` явно переопределяет этот маршрут, используя прокси HTTP/SOCKS5; оба варианта сборщиков Compose перенаправляют его. Фоновый пул следует за основной рабочей областью. Никакие сеансы Telegram, учетные данные API, токен панели или токен бота не отправляются поставщикам фидов. Названия поставщиков, даты создания снимков и маршрут загрузки отображаются в разделе **Откуда берётся список**.

MTProxy передаёт исключительно трафик Telegram. HTTP-операции рабочей области, такие как отметки времени, уведомления, внешние копии и проверки источников, используют отдельный SOCKS5/HTTP-прокси, если он настроен, а в противном случае — маршрут SOCKS5/HTTP учетного аккаунта. При отсутствии того или другого параметра режим «Скрыть адрес» отклоняет запрос; остальные режимы допускают использование прямого подключения. Внешние запросы можно отключить. Явно настроенный прокси для загрузки фидов по-прежнему является отдельным параметром, переопределяемым оператором. Независимая служба свидетелей сохраняет свой собственный маршрут.

Для частных сервисов, управляемых оператором, существующий параметр серверной среды `TGWITNESS_ALLOW_PRIVATE_DESTINATIONS=1` разрешает частные пункты назначения и сохраняет разрешение имен хостов на стороне прокси. Его невозможно включить через панель управления. Режим «Только публичные» отклоняет адреса в формате `.onion` перед отправкой запроса в публичный резолвер; для onion-сервисов Tor требуется явная настройка частных адресов назначения и подходящий прокси-сервер. Данное поведение DNS применимо к внешним HTTP-операциям, но не к транспортному протоколу Telegram. Cloudflare предоставляет документацию по [конечной точке DNS в формате JSON](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json/).

Чтобы заменить общедоступный список собственным каталогом операторов, настройте приведённое ниже переопределение. Оно полностью отключает внешние подписки, в том числе в случае, когда массив `proxies` пуст.

Скопируйте [пустой каталог](../../deploy/proxies.config.example) в папку ``proxy-config/proxies.json`` и добавьте свои развернутые публичные конечные точки:

```json
{"format": "tgwitness-proxy-catalog-v1", "proxies": [
  {"id": "project-eu", "label": "Project EU",
   "link": "tg://proxy?server=REPLACE_HOST&port=443&secret=REPLACE_SECRET"}
]}
```

Приведённые в примере значения необходимо заменить. Допускается до 32 уникальных записей. Авторизованный список возвращает метки/хосты/порты без общих секретных ключей; при выборе одной из записей её учетные данные сохраняются в хранилище рабочей области. Доступность остаётся непроверенной до момента явного тестирования транспорта. При наличии некорректно сформированного каталога сохраняется возможность ручной настройки.

Запуск в нативном режиме: установите переменную `TGWITNESS_PROXY_CATALOG`, указав путь к локальному файлу JSON. Docker:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.proxies.yaml up -d --build
```

Оверлей монтирует каталог ``proxy-config`` в режиме «только для чтения»; файлы должны быть доступны для чтения контейнеру с UID 10001. Данный каталог исключается из Git, контекста сборки Docker и архивов исходного кода. Этот каталог настраивает аккаунты для сбора данных; [бот-свидетель](WITNESS.md) использует собственный маршрут HTTP/SOCKS5, а не MTProxy.

Прямой переход на резервный маршрут регулируется описанным выше IP-режимом. Перед изменением маршрута приостановите наблюдение. Сохранение приведет к отключению старых клиентов и отмене незавершённого входа; новый клиент будет использовать сохраненный маршрут. Связь между журналом и сеансом аккаунта сохраняется. Настройки заменяют предыдущий маршрут: при редактировании введите учетные данные прокси заново.

Учетные данные шифруются в файле ``network.enc``. API не возвращает имя пользователя, пароль или секретный ключ. Подписанные записи содержат тип маршрута и информацию о наличии учетных данных, исключая конечную точку и секретные ключи. Оператор может увидеть конечную точку в панели управления. Поля с секретными данными очищаются после сохранения, блокировки или переключения рабочих областей.

**Функция Проверить соединение с Telegram**, доступная также до входа в систему, открывает и закрывает временное неавторизованное соединение с Telegram через данный маршрут. Она не обращается к сайту проверки IP-адресов. Успешное выполнение подтверждает работоспособность транспортного соединения, но не доступ к группам, полную доставку сообщений или анонимность.

Прокси применяется к соединениям клиента Telegram, включая загрузку медиафайлов из Telegram DC. Для браузера, pip, SSH и запускаемых вручную инструментов TSA предусмотрены отдельные маршруты. Имя хоста прокси может разрешаться локально. `rdns` влияет на имена хостов назначения; Telegram часто предоставляет числовые IP-адреса DC.

SOCKS5 и простой HTTP CONNECT сами по себе не шифруют учетные данные прокси или туннель «клиент-прокси». MTProto отдельно защищает трафик Telegram. В ненадежной сети используйте подходящий безопасный канал для подключения к прокси. Личные чаты — это облачные чаты, защищенные протоколом MTProto при передаче данных; секретные чаты с сквозным шифрованием представляют собой отдельный тип чатов, которые регистрируются [модулем Секретный чат](PSEUDO-SECRET.md).

<a id="encryption-and-signatures"></a>
## Шифрование и подписи

| Уровень | Реализовано | Ответственность оператора |
| --- | --- | --- |
| Трафик Telegram | Telethon MTProto | Надежность платформы, маршрутизация и доступность |
| Веб-панель | Токен носителя, значение по умолчанию для loopback, ограничения на количество запросов | HTTPS- или SSH-туннель для удалённого доступа |
| Секретные данные | Fernet для учетных данных API, сеансов, учетных данных прокси и закрытого ключа подписи | Защита ключа дешифрования и хоста, на котором выполняется программа |
| Ключ хранилища | Локальный ключ или внешний главный ключ для новой установки | Раздельное защищённое хранилище и резервное копирование ключей |
| Сообщения и вложения | Хранение данных приложения в виде открытого текста | Зашифрованный диск/том |
| ZIP/JSONL/CSV/HTML | Проверка целостности, отсутствие шифрования содержимого | Защита экспортированных копий и передач данных |
| Происхождение и время | Подписанный журнал, квитанция о обработке, инструменты RFC 3161 | Доверенный ключ, независимые контрольные точки/TSA и процедура хранения |

**Защита хранилища** в «Аккаунте» отображает эти состояния. Токен панели представляет собой секретный ключ доступа, а не пароль шифрования. Он предоставляет права администратора; [выданные токены](ACCESS.md) могут быть ограничены по аккаунтам и чатам. Рабочие области используют общий хост-процесс и не являются изолированными арендаторами.

BitLocker, LUKS, FileVault или управляемый зашифрованный том могут обеспечить защиту хранилища в соответствии с их соответствующими моделями угроз. Администратор разблокированной работающей машины по-прежнему может считывать данные. При планировании хранилища учитывайте файлы WAL/SHM SQLite, медиафайлы, временные экспорты, файлы подкачки, резервные копии и загрузки из браузера. Том Docker не шифруется только по той причине, что он является томом.

<a id="external-master-key"></a>
## Внешний мастер-ключ

При **новой** установке разместите мастер-ключ за пределами каталога данных. Это не приводит к автоматической миграции существующего хранилища локальных ключей. Подготовьте каталог ключей, доступный только для учетной записи службы, а затем выполните:

```sh
python -m tgwitness.security create-master-key /private/keys/tgwitness-master.key
export TGWITNESS_VAULT_KEY_FILE=/private/keys/tgwitness-master.key
python -m tgwitness --data-dir /private/observations/new-case
```

PowerShell, используя установленную среду проекта:

```powershell
python -m tgwitness.security create-master-key E:\PrivateKeys\tgwitness-master.key
$env:TGWITNESS_VAULT_KEY_FILE = 'E:\PrivateKeys\tgwitness-master.key'
python -m tgwitness --data-dir E:\PrivateData\new-case
```

В Docker смонтируйте файл в режиме «только для чтения» вне каталога `/data`, например, в `/run/secrets/tgwitness-master.key`, и установите переменную среды, указывающую на этот путь. Идентификатор пользователя службы (UID) должен иметь права на чтение этого файла. Передавайте путь, а не байты ключа, через файлы среды или конфигурации.

Каждая рабочая область получает случайный открытый соль и собственный ключ Fernet, полученный с помощью алгоритма HKDF-SHA256. Файл ``vault.external.json`` хранит метаданные о производстве ключа, а не сам мастер-ключ. Отсутствие или неверность ключа приводит к сбою запуска без его автоматической замены. Сохраните как метаданные о соли, так и мастер-ключ для восстановления.

Все рабочие области производятся от одного и того же мастер-ключа; его компрометация затрагивает всю установку. Запущенный процесс может расшифровывать секретные данные. Это не HSM и не KDF на основе пароля. Произвольные пароли, введенные пользователем, не допускаются вместо случайного ключа.

Сохраняйте существующий ключ для действующих установок до тех пор, пока не будет осуществлена и проверена целенаправленная миграция. Удаление файла ``vault.key`` или замена мастер-ключа может привести к потере доступа к сеансам и ключам подписи. Храните зашифрованные резервные копии и ключи отдельно и тестируйте восстановление в изолированном экземпляре.
