## Сейчас: исходный код предварительной версии 0.9

Рабочие пространства учетной записи, данные о доставке Telegram, записи взаимодействий, мультимедиа, подписанные
экспорты, токены панелей с ограниченной областью действия, политики прокси и отдельный свидетель, проверяющий актуальность
и непрерывность. Сюда входит только то, что фактически получают учетная запись и сборщик данных.

Перед каждым выпуском мы:

- провести проверку бэкэнда и браузера для релизного коммита и зафиксировать, что не прошло или не было протестировано;
- скомпилировать исходный код, файл wheel и портативную версию для Windows из того же коммита, проверить их содержимое и сначала опубликовать SHA-256;
- не включать в архив исходного кода сессии, учетные данные, журналы и результаты тестирования;
- отклонять поврежденные деревья OpenTimestamps и указывать подтверждения Bitcoin как `bitcoin-unverified`
  (использовать `ots verify` для реальной проверки); согласно RFC 3161 по-прежнему требуется `--tsa-ca` получателя;
- помечать места, где перевод ещё отсутствует, как «английский вариант по умолчанию».

Импорт сторонних архивов Desktop, дампов кэша устройств и восстановленных автономных
записей не входит в данную дорожную карту. TgWitness записывает собственные наблюдения. Создание
JSON-файлов, совместимых с Desktop, на основе данных, полученных при импорте учетной записи, по-прежнему поддерживается; см.
[экспорт учетной записи](../ACCOUNT-EXPORT.md).

Свидетель уже проходит контрольные точки и задает новые задачи. Оставшаяся
работа контроллера должна проверить весь путь с помощью реального коллектора:

- каждый ответ привязан к новому запросу, зарегистрированному ключу сборщика и ранее заверенной заголовке;
- набор наблюдателей фиксируется при регистрации запроса, отсутствующие наблюдатели остаются видимыми;
- исходящие квитанции и задания сохраняются транзакционно, сохраняются после перезапуска, повторяются с отсрочкой;
- квитанции можно экспортировать для автономной проверки; свидетелю передаются только метаданные, обязательства и подписи;
- бесплатная пилотная версия на хостинге недоступна до тех пор, пока не будет измерено использование ресурсов.

Завершено: перезапуск, потеря связи, повторяющиеся ответы, изменение ключа и экспорт
с неподтвержденным хвостом — все это можно проверить по сохраненным квитанциям.

<a id="next-independent-observation-and-offline-review"></a>
## Далее: независимое наблюдение и проверка в автономном режиме

- Проверить работу реализованных функций предварительного просмотра в браузере с опцией «opt-in», AyuGram и Trusted Live с помощью
  разрешенных тестовых аккаунтов. Каждая из них имеет собственные данные для входа, ключ и журнал. Сообщение,
  прокрученное за пределы экрана, не должно рассматриваться как удаленное.
- Офлайн-воспроизведение записанного материала в браузере с четкими отметками о пропущенных медиафайлах.
- Сохранение вложений, экспортированных в исходном формате, в Trusted Live и сокращение объема ручной работы,
  необходимой для привязки видимых сообщений к кадрам, без выдумывания идентификаторов на основе пикселей.
- Сопоставление идентификаторов и версий сообщений между наблюдателями и сохранение несоответствий. Чтение базы данных первого
  сборщика не считается повторным наблюдением.

Задача выполнена, если тестовый чат с отправкой сообщений, редактированием, удалением, изменением кнопок и перезапуском наблюдателя
выглядит корректно в офлайн-пакете.

- Более длительные рабочие циклы, тесты восстановления, установки на Linux/macOS и контейнеры на реальных целях.

Подписанные квитанции фиксируют изменения в истории, которые уже были подтверждены свидетелями. Следующий шаг
расширяет эту систему доверия на сам сборщик: сборку, подписавшую запись, и
свидетелей на отдельных хостах, управляемых разными администраторами.

<a id="proposed-trust-in-the-build"></a>
## Предложение: доверие к сборке

Получатель должен иметь возможность увидеть, какая сборка собрала запись, в каком журнале она
отображалась, какие свидетели её хранили и где имеются пробелы. Сегодня квитанция прогона измеряет
файлы программы, [проверка кода](../PANEL.md#code-check) сравнивает их с общедоступным коммитом,
а [свидетель](../WITNESS.md) публикует контрольные точки. Далее, по порядку:

1. Хранить манифест релиза, SBOM и подтверждения рабочих процессов, привязанные к протестированной версии и акту приемки.
2. На сервере-свидетеле должна быть создана устойчивая очередь исходящих данных, которая сохраняется после перезапуска и отображает повторные попытки.
   Задержка с доставкой никогда не считается своевременной.
3. Проведите квалификационную проверку существующих рабочих процессов подготовки чернового релиза и управляемого сохранения на GitHub для каждого кандидата в релиз.
4. Используйте GitHub в качестве дополнительного хранилища для ежечасных подписанных блоков контрольных точек, без принудительной отправки (force-push).
5. Несколько серверов-свидетелей, управляемых разными людьми, с видимой ротацией ключей.
6. Тестирование в режиме реального времени на перезапуск, потерю связи, использование старых резервных копий и изменение сборок.

Ещё не всё: подписание по пороговому значению (FROST), зеркало GitLab, привязка к Nostr, соподписанты.

<a id="release-automation"></a>
## Автоматизация выпуска

Конвейер выпуска предусматривает следующий процесс: **черновой вариант → проверенные ресурсы и подтверждения → публикация**,
закрепленные входные данные, манифест выпуска и проверку происхождения установщика. Эти
этапы должны выполняться именно для данного кандидата. Задания, находящиеся в очереди или пропущенные, никогда не считаются пройденными проверками.

Установщик с предварительным просмотром по одной команде работает по тому же принципу: каждый основной коммит
проходит проверку, точно соответствующий подписанный пакет устанавливается на одноразовые хосты под Ubuntu и Windows,
а публикация откладывается до завершения CI по приложению или безопасности. Непрошедшие проверку кандидаты оставляют
доступной предыдущую публичную версию для скачивания. Публичное HTTPS-принятие может быть запущено
отдельно по отношению к опубликованной фиксации; это не относится к Telegram-захвату
или существующему серверу пользователя.
