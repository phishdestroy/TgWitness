# तैनाती और संचालन

## स्थापना चुनें

पोर्टेबल पैकेज के लिए GitHub Releases से `TgWitness-<version>-windows-amd64-portable.zip` निकालें। अन्य तरीकों के लिए स्रोत ZIP डाउनलोड और निकालें या रिपॉजिटरी क्लोन करें, फिर प्रोजेक्ट डायरेक्टरी से निम्नलिखित चलाएँ:

| स्थापना | शुरू करें | क्या यह पृष्ठभूमि में चलता है? |
| --- | --- | --- |
| विंडोज पोर्टेबल पैकेज | `TgWitness.cmd` | नहीं; विंडो खुली रखें। |
| नेटिव विंडोज | `Start.cmd` | नहीं; पृष्ठभूमि उपयोग के लिए वैकल्पिक लॉगऑन कार्य का उपयोग करें। |
| नेटिव लिनक्स/मैकओएस | `sh start.sh` | नहीं; पृष्ठभूमि उपयोग के लिए systemd/launchd का उपयोग करें। |
| किसी भी समर्थित होस्ट पर डॉकर | `docker compose up -d --build --wait` | हाँ, जब Docker डेमन चल रहा हो। |
| Windows पर Docker हेल्पर | `scripts\Docker.cmd` | हाँ; हेल्पर वेब-सर्वर की स्वास्थ्य स्थिति का इंतजार करता है। |
| Linux/macOS पर डॉकर हेल्पर | `sh scripts/docker-start.sh` | हाँ; हेल्पर वेब-सर्वर की स्वास्थ्य स्थिति का इंतजार करता है। |

नेटिव स्टार्टअप एक निजी `.venv` बनाता है और पिन की गई निर्भरताओं को इंस्टॉल करता है। Docker इन्हें होस्ट Python की आवश्यकता के बिना इमेज के अंदर ही बिल्ड करता है। पहली बार सेटअप के लिए इंटरनेट एक्सेस आवश्यक है। जब कोई Python 3.11+ नहीं मिलता है, तो `Start.cmd` वर्तमान Windows उपयोगकर्ता के लिए Python 3.12 इंस्टॉल करने से पहले पूछता है (winget, अन्यथा इसकी Python Software Foundation हस्ताक्षर की जाँच करने के बाद python.org इंस्टॉलर); यह कभी भी व्यवस्थापक विशेषाधिकारों का अनुरोध नहीं करता है। Docker और OS सेवाएँ पूर्व-आवश्यकताएँ बनी रहती हैं।

नेटिव और पोर्टेबल इंस्टॉलेशन अपने फ़ोल्डर के अंदर `data/live` का उपयोग करते हैं। Docker `tgwitness-data` नामक वॉल्यूम को `/data` पर उपयोग करता है। ये अलग-अलग इंस्टॉलेशन हैं जब तक आप जानबूझकर पूरी डेटा डायरेक्टरी को माइग्रेट नहीं करते। नए Docker कंटेनर से नेटिव खातों का स्वचालित रूप से पता लगाने की उम्मीद न करें।

## स्थापना आवश्यकताएँ

नेटिव इंस्टॉलेशन के लिए Python 3.11 या बाद का संस्करण, `venv` और `ensurepip`, पहली निर्भरता इंस्टॉलेशन के लिए इंटरनेट एक्सेस, और `.venv` के लिए लिखने योग्य प्रोजेक्ट डायरेक्टरी की आवश्यकता है। बंडल किए गए पैनल के लिए Node.js या फ्रंटएंड बिल्ड की आवश्यकता नहीं है। अपने सामान्य OS खाते से लॉन्चर चलाएँ; TgWitness को एडमिनिस्ट्रेटर/रूट विशेषाधिकारों की आवश्यकता नहीं है।

- **Windows:** `Start.cmd` पहले `py -3` की जाँच करता है, फिर `python`, फिर डिफ़ॉल्ट प्रति-उपयोगकर्ता और Program Files इंस्टॉलेशन फ़ोल्डर्स, और इसे संस्करण 3.11 या बाद का संस्करण चाहिए। यदि इनमें से कोई भी काम नहीं करता है, तो यह ऊपर वर्णित स्वचालित प्रति-उपयोगकर्ता इंस्टॉलेशन प्रदान करता है। `py -3 start.py` भी काम करता है। पोर्टेबल पैकेज को बिल्कुल भी Python की आवश्यकता नहीं है।
- **Linux:** `start.sh` पहले `python3.13`, `python3.12`, `python3.11`, `python3` और `python` को आज़माता है, और जब कोई भी उपयुक्त नहीं मिलता है तो apt, dnf, pacman, zypper, apk या Homebrew के लिए इंस्टॉल कमांड प्रिंट करता है। Debian/Ubuntu इंस्टॉलेशन के लिए चयनित इंटरप्रेटर से मेल खाने वाले `python3-venv` पैकेज की आवश्यकता हो सकती है। किसी डिस्ट्रिब्यूशन के पुराने डिफ़ॉल्ट पाइथन को पाइथन 3.11+ से बदलने या पूरक करने की आवश्यकता हो सकती है।
- **macOS:** एक वर्तमान Python 3.11+ वितरण स्थापित करें; यह न मानें कि OS-प्रदत्त इंटरप्रेटर आवश्यकता को पूरा करता है। प्रोजेक्ट निर्देशिका से `python3 start.py` का उपयोग करें।
- **Docker:** Compose v2.20 या उससे नए संस्करण के साथ Docker Engine/Desktop का उपयोग करें। Windows पर Docker Desktop को Linux कंटेनरों का उपयोग करना चाहिए। कंटेनर अपनी Python निर्भरताएँ स्वयं इंस्टॉल करता है; होस्ट को अलग से Python इंस्टॉलेशन की आवश्यकता नहीं है।

डेटा निर्देशिका के लिए स्थायी स्थानीय भंडारण का उपयोग करें। संदेशों, मीडिया, WAL वृद्धि, निर्यात और बैकअप से क्षमता की योजना बनाएँ; प्रत्येक कार्यभार के लिए साक्ष्य-आधारित सार्वभौमिक न्यूनतम डिस्क/RAM विनिर्देश नहीं है। CPU आर्किटेक्चर और Python संस्करण जिन्हें संगत निर्भरता व्हील्स नहीं मिलते, उन्हें अतिरिक्त बिल्ड टूल्स और अपनी योग्यता की आवश्यकता हो सकती है। "पोर्टेबल" सार्वभौमिक OS या हार्डवेयर समर्थन का दावा नहीं है।

Windows 11/Python 3.12 स्थानीय रूप से सत्यापित है। Linux/macOS/कंटेनर परिभाषाएँ और CI प्रदान किए गए हैं, लेकिन इस विकास होस्ट पर निष्पादित नहीं किए गए हैं। सटीक दायरे के लिए [VERIFICATION.md](../VERIFICATION.md) देखें।

## स्थानीय कंप्यूटर

Windows पर `Start.cmd` का उपयोग करें या Linux/macOS पर `sh start.sh`। `scripts\Setup.cmd` या `sh start.sh --setup-only` वातावरण तैयार करता है। लॉन्चर पहली बार उपयोग पर निर्भरताएँ इंस्टॉल करता है; बाद में लॉन्च होने पर वातावरण का पुन: उपयोग होता है। सेटअप और टेलीग्राम संग्रह के लिए इंटरनेट एक्सेस आवश्यक है, लेकिन मौजूदा रिकॉर्ड ब्राउज़ करना और एक्सपोर्ट बनाना ऑफ़लाइन काम करता है।

सेटअप के बाद `python start.py --check` चलाएँ ताकि कलेक्टर शुरू किए बिना स्थानीय निर्भरताएँ, Ed25519, स्टोरेज, कुंजी कॉन्फ़िगरेशन और लिसनिंग एड्रेस की जाँच की जा सके। संरचित आउटपुट के लिए `--json` का उपयोग करें। इच्छित `--data-dir`, `--host` और `--port` पास करें। यह जाँच पैकेज इंस्टॉल नहीं करती, जर्नल नहीं बनाती या टेलीग्राम से कनेक्ट नहीं करती; यह अखंडता या कवरेज योग्यता नहीं है। स्टार्टअप अलग से मौजूदा जर्नलों का सत्यापन करता है। `python start.py --help` भी इंस्टॉलेशन से बचता है।

विकल्प:

start.py का उपयोग करने के बाद, Windows पर `.venv\Scripts\python.exe` और Linux/macOS पर `.venv/bin/python` के साथ सहायक कमांड चलाएँ, या पहले उस वातावरण को सक्रिय करें। नीचे दिए गए `python -m ...` उदाहरण मानते हैं कि वातावरण सक्रिय है।

~~~sh
python -m tgwitness --data-dir /path/to/private/data --host 127.0.0.1 --port 8787
~~~

पर्यावरण चर: TGWITNESS_DATA, TGWITNESS_HOST, TGWITNESS_PORT, TGWITNESS_TOKEN। TGWITNESS_VAULT_KEY_FILE नए इंस्टॉलेशन के लिए बाहरी-कुंजी मोड चुनता है; नीचे देखें। TGWITNESS_TOKEN, यदि प्रदान किया गया हो, तो उसमें कम से कम 24 वर्ण होने चाहिए; एक क्रिप्टोग्राफ़िक रूप से यादृच्छिक मान का उपयोग करें। इसके बिना, ऐप panel-token.txt में एक 256-बिट का यादृच्छिक टोकन उत्पन्न करता है। एनवायरनमेंट ओवरराइड उस फ़ाइल को फिर से नहीं लिखता है। क्रेडेंशियल्स को रोटेट करने के लिए ऐप को पुनः आरंभ करें।

सटीक रूप से एक ही प्रक्रिया डेटा निर्देशिका की मालिक हो सकती है। एक क्रॉस-प्लेटफ़ॉर्म OS फ़ाइल लॉक आकस्मिक समवर्ती लेखकों को रोकता है। एक Uvicorn वर्कर का उपयोग करें। पैनल किसी भी संख्या में वर्कस्पेस का प्रबंधन कर सकता है, जिसमें profiles/<id>/ के अंतर्गत अतिरिक्त वर्कस्पेस डायरेक्टरी होती हैं। अलग-अलग सेवा इंस्टेंस के लिए, अलग-अलग डायरेक्टरी और पोर्ट का उपयोग करें। SQLite WAL फ़ाइलें स्थानीय स्थायी स्टोरेज में होनी चाहिए, नेटवर्क फ़ाइलसिस्टम में नहीं। एक ही वॉल्यूम को रेप्लिका के बीच साझा न करें।

## विंडोज पोर्टेबल पैकेज

प्रत्येक GitHub रिलीज़ में `TgWitness-<version>-windows-amd64-portable.zip` और इसकी `.sha256` शामिल होती है। इसमें python.org से आधिकारिक एम्बेडेबल Python 3.12 रनटाइम (`tools/build_portable.py` में चेकसम पिन किया गया), TgWitness और इसकी पिन की गई निर्भरताएँ, और तीन लॉन्चर शामिल हैं:

| फ़ाइल | उद्देश्य |
| --- | --- |
| `TgWitness.cmd` | पैनल शुरू करें; अतिरिक्त विकल्प पारित किए जाते हैं, उदाहरण के लिए `TgWitness.cmd --port 8790` |
| `TgWitness-Demo.cmd` | `data\demo` में सिंथेटिक डेमो शुरू करें |
| `TgWitness-Check.cmd` | शुरू किए बिना तत्परता जाँच चलाएँ |

पूरे आर्काइव को `Documents\TgWitness` जैसे लिखने योग्य फ़ोल्डर में निकालें; इसे ZIP के अंदर या Program Files से न चलाएँ। रनटाइम एक अलग मॉड्यूल पथ का उपयोग करता है, इसलिए अन्य Python इंस्टॉलेशन और `PYTHONPATH` इसका प्रभाव नहीं डालते। डेटा पैकेज के `data` फ़ोल्डर में रहता है। अपडेट करने के लिए, TgWitness को रोकें, नए संस्करण को एक नए फ़ोल्डर में निकालें और `data` फ़ोल्डर को दूसरी ओर कॉपी करें।

इसे स्वयं 64-बिट विंडोज पर पाइथन 3.12 के साथ बनाएं:

~~~sh
python tools/build_portable.py
~~~

बिल्डर रनटाइम चेकसम की पुष्टि करता है, प्रतिबंधित निर्भरताओं को पैकेज में इंस्टॉल करता है, एम्बेडेड इंटरप्रेटर के साथ तैयारता जांच चलाता है और ZIP तथा चेकसम को `dist/` में लिखता है।

## कंटेनर

```sh
docker compose up -d --build --wait
```

यह /data के लिए एक नामित स्थायी वॉल्यूम बनाता है। वेब पोर्ट को 127.0.0.1:8787 पर मैप किया गया है। यह प्रक्रिया UID 10001 के साथ, क्षमताओं को सीमित करके, केवल-पठनीय रूट फ़ाइल सिस्टम और लिखने योग्य /data तथा /tmp के साथ चलती है। `--wait` लौटने से पहले वेब-सर्वर की स्वास्थ्य जांच करता है; यह टेलीग्राम प्राधिकरण या डिलीवरी स्थापित नहीं करता। प्रदान किए गए हेल्पर बिल्ड के बाद 180-सेकंड का रेडीनेस टाइमआउट उपयोग करते हैं। प्रारंभिक निर्भरता डाउनलोड में इससे अधिक समय लग सकता है।

दोनों बेस Compose फ़ाइलें प्रोजेक्ट नाम `tgwitness` का उपयोग करती हैं, इसलिए किसी अन्य डायरेक्टरी में नई रिलीज़ निकालने पर चुपचाप नया डेटा वॉल्यूम नहीं चुना जाता। उस प्रोजेक्ट के लिए केवल एक डिप्लॉयमेंट सक्रिय रखें। स्वतंत्र इंस्टॉलेशन के लिए, एक अद्वितीय `docker compose -p NAME ...` और एक अलग होस्ट पोर्ट का उपयोग करें, और अपडेट पर दोनों को बनाए रखें। एक अलग प्रोजेक्ट नाम का उपयोग करने वाले पुराने डिप्लॉयमेंट के लिए, `-p` के साथ इसके मूल नाम का उपयोग जारी रखें; `docker compose ls` मौजूदा प्रोजेक्ट्स की सूची देता है।

`deploy/env.example` की प्रतिलिपि `.env` में करें और `TGWITNESS_PORT` को किसी अन्य लूपबैक पोर्ट का उपयोग करने के लिए बदलें। उदाहरण के लिए, `TGWITNESS_PORT=8788` पैनल को `http://127.0.0.1:8788` पर एक्सपोज़ करता है; कंटेनर अभी भी 8787 पर सुनता है। `.env` Git द्वारा अनदेखा किया गया है।

प्रारंभिक टोकन प्राप्त करें:

~~~sh
docker compose exec tgwitness cat /data/panel-token.txt
~~~

उपयोगी कमांड:

```sh
docker compose ps
docker compose logs --tail 100 -f
docker compose stop
docker compose up -d --wait
```

`restart: unless-stopped` क्रैश या Docker डेमन रीस्टार्ट के बाद कलेक्टर को पुनः आरंभ करता है। Linux सर्वर पर, अपने डिस्ट्रीब्यूशन के सर्विस मैनेजर (आमतौर पर `sudo systemctl enable --now docker`) का उपयोग करके बूट पर Docker को सक्षम करें। Windows/macOS पर, Docker Desktop की 'start-at-sign-in' सेटिंग को सक्षम करें। डेस्कटॉप साइन-आउट, स्लीप, या एक रुका हुआ Docker डेमन संग्रह को बाधित कर सकता है। स्पष्ट रूप से रोका गया कंटेनर तब तक रुका रहता है जब तक आप इसे फिर से शुरू नहीं करते।

उदाहरण कॉन्फ़िगरेशन में /tmp वॉल्यूम को 512 MiB तक सीमित किया गया है। एक्सपोर्ट निर्माण इसके बजाय प्रत्येक वर्कस्पेस के `temporary-exports/` का उपयोग स्थायी /data पर करता है। वहाँ एक साथ होने वाले एक्सपोर्ट, जर्नल/WAL वृद्धि, मीडिया और बैकअप के लिए जगह आरक्षित करें। लॉन्चर और Docker योग्य रनटाइम निर्भरता संस्करणों को पिन करने के लिए deploy/constraints.txt का उपयोग करते हैं। यह एक हैश-लॉक की गई आपूर्ति श्रृंखला नहीं है: Python बेस इमेज और पैकेज आर्टिफैक्ट्स को अभी भी स्वतंत्र रिलीज़ योग्यता की आवश्यकता होती है।

जब तक आप जर्नल और कुंजियों को नष्ट करने का इरादा न रखें, तब तक docker compose down -v का उपयोग न करें। कंटेनर स्वास्थ्य रिपोर्ट वेब-सर्वर की उपलब्धता दिखाती है, सफल टेलीग्राम कैप्चर नहीं। पैनल के कलेक्टर की स्थिति, हार्टबीट, त्रुटियाँ और कवरेज इवेंट्स की जाँच करें।

### स्वतंत्र गवाह प्रोफ़ाइल

वैकल्पिक `witness` सेवा अपने स्वयं के कंटेनर में एक [स्वतंत्र विटनेस](../WITNESS.md) चलाती है, जिसमें `witness-data` वॉल्यूम में अपनी खुद की कुंजी और जर्नल होते हैं, और कलेक्टर के लिए केवल एक रीड-ओनली विटनेस टोकन होता है। पैनल के **विटनेस** पेज पर टोकन बनाएँ, इसे एक बॉट टोकन और चैनल के साथ `.env` में जोड़ें, फिर प्रोफ़ाइल शुरू करें:

```sh
docker compose --profile witness up -d          # deploy/compose/compose.image.yaml: same flag
docker compose logs witness                     # witness key fingerprint
```

यह सेवा Compose नेटवर्क के भीतर कलेक्टर तक `http://tgwitness:8787` पर पहुँचती है (`TGWITNESS_WITNESS_COLLECTOR` इसे ओवरराइड करता है, उदाहरण के लिए दूसरे वर्कस्पेस के लिए `/profiles/<workspace ID>`)। किसी अन्य व्यक्ति द्वारा चलाए जा रहे अलग सर्वर पर विटनेस के लिए, वहाँ `deploy/compose/compose.witness.yaml` का उपयोग करें और `TGWITNESS_WITNESS_COLLECTOR` को कलेक्टर के HTTPS पते पर सेट करें; उस फ़ाइल में केवल विटनेस होता है।

## एक प्रकाशित इमेज इंस्टॉल करें

यह एक सफल [रिलीज़ वर्कफ़्लो](#सवचलत-github-रलज) और सार्वजनिक GHCR पैकेज कॉन्फ़िगरेशन के बाद उपलब्ध होता है। रिपॉजिटरी का मालिक/नाम इस स्रोत वृक्ष में हार्डकोड नहीं किया गया है। उस रिलीज़ के वर्कफ़्लो सारांश में दिखाई गई इमेज का उपयोग करें।

`deploy/env.example` की प्रतिलिपि `.env` में करें। `TGWITNESS_IMAGE` को प्रकाशित संस्करण पर सेट करें, **छोटे अक्षरों वाले** रिपॉजिटरी पथ का उपयोग करके, उदाहरण के लिए:

```dotenv
TGWITNESS_IMAGE=ghcr.io/your-owner/your-repository:0.7.1
TGWITNESS_PORT=8787
```

`compose.yaml` के बजाय, इस फ़ाइल को अकेले चलाएँ:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
docker compose --project-directory . -f deploy/compose/compose.image.yaml exec tgwitness cat /data/panel-token.txt
```

होस्ट पर किसी स्रोत बिल्ड, पाइथन, या कंपाइलर की आवश्यकता नहीं है। रिलीज़ वर्कफ़्लो लिनक्स AMD64 और ARM64 कंटेनरों को लक्षित करता है, जिसमें डॉकर डेस्कटॉप का लिनक्स वीएम भी शामिल है। वर्कफ़्लो सारांश से एक संस्करण टैग या `ghcr.io/owner/repository@sha256:...` का उपयोग करें। `latest` टैग को स्थानांतरित करने या बिना निगरानी वाले एप्लिकेशन अपग्रेड को कॉन्फ़िगर नहीं किया गया है। इमेज और सोर्स वेरिएंट्स तब एक ही डेटा वॉल्यूम का उपयोग करते हैं जब उनके प्रोजेक्ट का नाम मेल खाता है।

## सर्वर पर स्वचालित HTTPS

Docker के साथ एक सर्वर, एक ऐसा डोमेन जिसका आप नियंत्रण करते हैं, और स्थायी स्थानीय भंडारण का उपयोग करें। डोमेन के A/AAAA रिकॉर्ड्स को सर्वर पर इंगित करें; केवल तभी AAAA प्रकाशित करें जब IPv6 उस तक पहुँच जाए। प्रमाणपत्र जारी करने के लिए इनबाउंड TCP 80 और 443 तथा आउटबाउंड DNS/HTTPS की अनुमति दें। अन्य सेवाओं के पास पहले से ही ये पोर्ट नहीं होने चाहिए।

`deploy/env.example` की प्रतिलिपि `.env` में करें और बिना स्कीम या पथ के होस्टनेम सेट करें:

```dotenv
TGWITNESS_DOMAIN=watch.your-domain.org
```

HTTPS ओवरले के साथ स्रोत बिल्ड शुरू करें:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml up -d --build --wait
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml exec tgwitness cat /data/panel-token.txt
```

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml -f deploy/compose/compose.https.yaml up -d --wait
```

प्रकाशित छवि के लिए, इसके बजाय पहली फ़ाइल के रूप में `deploy/compose/compose.image.yaml` का उपयोग करें। बाद में स्थिति, लॉग, अपडेट और स्टॉप कमांड के लिए दोनों `-f` आर्गुमेंट्स को बनाए रखें।

Caddy प्रमाणपत्र प्राप्त करता है और नवीनीकृत करता है, HTTP को HTTPS पर पुनर्निर्देशित करता है, और निजी Compose नेटवर्क पर कलेक्टर को अनुरोध अग्रेषित करता है। प्रमाणपत्र की स्थिति के लिए इसका अपना स्थायी वॉल्यूम होता है। कलेक्टर का प्रत्यक्ष होस्ट पोर्ट केवल लूपबैक के लिए ही रहता है। प्रदान की गई Caddy कॉन्फ़िगरेशन एक्सेस लॉगिंग सक्षम नहीं करती है।

`https://watch.your-domain.org` खोलें और पैनल टोकन दर्ज करें। तैयार होने की स्थिति प्रमाणपत्र जारी होने या बाहरी पहुँच की पुष्टि नहीं करती। यदि HTTPS तैयार नहीं है, तो DNS, फ़ायरवॉल नियमों की जाँच करें, और:

```sh
docker compose -f compose.yaml -f deploy/compose/compose.https.yaml logs --tail 100 caddy
```

प्रदान की गई Caddy इमेज अपने `2-alpine` टैग का अनुसरण करती है। पुल करने पर वह इमेज रिफ्रेश हो जाती है; यदि आपको स्थिर इन्फ्रास्ट्रक्चर संस्करणों की आवश्यकता है तो अपनी डिप्लॉयमेंट में एक परीक्षणित डाइजेस्ट पिन करें।

## अपडेट और बैकअप

अपडेट्स के दौरान Compose प्रोजेक्ट का नाम और डेटा वॉल्यूम संरक्षित रखें। सबसे पहले कलेक्टर को रोकें और एक पूर्ण बैकअप बनाएं। डिफ़ॉल्ट स्रोत-आधारित डिप्लॉयमेंट के लिए:

```sh
docker compose stop
docker compose cp tgwitness:/data ../tgwitness-backup-before-update
```

प्रत्येक बार एक नई बैकअप गंतव्य का उपयोग करें, रिपॉजिटरी के बाहर, और इसे खाता-पहुँच सामग्री के रूप में सुरक्षित रखें। उदाहरण पथ केवल दिखावटी है; अपना निजी बैकअप स्थान उपयोग करें। छिपी हुई फ़ाइलों, सभी वर्कस्पेस, कुंजियाँ, जर्नल और मीडिया सहित पूरी निर्देशिका की प्रतिलिपि बनाएँ। यदि कॉन्फ़िगर किया गया हो तो एक बाहरी वॉल्ट मास्टर कुंजी का अलग से बैकअप लें। एक सबूत ज़िप (evidence ZIP) पुनर्स्थापित करने योग्य एप्लिकेशन बैकअप नहीं है। HTTPS के लिए, यदि आपको इसके प्रमाणपत्र/खाते की स्थिति को बनाए रखने की आवश्यकता है तो कैडी वॉल्यूम को भी संरक्षित करें।

स्रोत परिनियोजन के लिए, नई रिलीज़ फ़ाइलें प्राप्त करें और चलाएँ:

```sh
docker compose up -d --build --wait
```

इमेज डिप्लॉयमेंट के लिए, `TGWITNESS_IMAGE` को इच्छित संस्करण में बदलें, फिर चलाएँ:

```sh
docker compose --project-directory . -f deploy/compose/compose.image.yaml pull
docker compose --project-directory . -f deploy/compose/compose.image.yaml up -d --wait
```

पिछली स्टॉप/कॉपी कमांड्स के लिए भी अपने इंस्टॉलेशन की Compose फ़ाइल(ओं) का उपयोग करें। `.env`, कस्टम कॉन्फ़िगरेशन, और उसी प्रोजेक्ट नाम को बनाए रखें। `down` नामित वॉल्यूम रखता है; **`down -v`** **उन्हें हटाता है**। `.venv` को ऑपरेटिंग सिस्टम या Python संस्करणों के बीच कॉपी न करें। नेटिव अपडेट के लिए, TgWitness को रोकें, इसकी पूरी डेटा निर्देशिका का बैकअप लें, स्रोत फ़ाइलों को बदलें, और लॉन्च से पहले `python start.py --setup-only` चलाएँ।

अपडेट के बाद पैनल एक्सेस, खाता पहचान, अवलोकन स्थिति और कवरेज की जाँच करें। पुनरारंभ करने से छूटी हुई टेलीग्राम अपडेट पुनर्निर्मित नहीं होतीं। यदि कोई भविष्य का संस्करण भंडारण प्रारूप बदलता है, तो रोलबैक के लिए पूर्व-अपडेट बैकअप की आवश्यकता हो सकती है।

## स्वचालित GitHub रिलीज़

यह [रिलीज़ वर्कफ़्लो](../../.github/workflows/release.yml) तब उपयोग के लिए तैयार हो जाता है जब इस प्रोजेक्ट को Actions सक्षम किए गए GitHub रिपॉजिटरी में पुश किया जाता है। यह तब चलता है जब GitHub रिलीज़ **प्रकाशित** होती है, जिसमें प्री-रिलीज़ भी शामिल है। केवल ड्राफ़्ट और टैग पुश करने से पैकेज प्रकाशित नहीं होते।

1. पैकेज का संस्करण और चेंजलाग सेट करें, फिर `v` और सटीक `pyproject.toml` संस्करण के साथ टैग की गई एक रिलीज प्रकाशित करें, जैसे `v0.7.1`।
2. यह वर्कफ़्लो टैग को मान्य करता है और साझा किए गए Windows/Linux/macOS Python, सामान्य/खाता-आयात/QR ब्राउज़र, स्रोत-पैकेज, और Docker जांचों को चलाता है। Python 3.12 का उपयोग करके तीनों ऑपरेटिंग सिस्टम पर ताज़ा नेटिव इंस्टॉलेशन भी किया जाता है।
3. इन जाँचों के पास होने के बाद, यह QEMU के तहत ARM64 इमेज का स्मोक-टेस्ट करता है, AMD64/ARM64 इमेज को `ghcr.io/<lowercase-owner>/<lowercase-repository>:<version>` पर प्रकाशित करता है, और सोर्स ZIP, चेकसम, और Python व्हील को रिलीज़ में संलग्न करता है। एक अलग Windows जॉब पोर्टेबल ZIP और इसकी चेकसम को बिल्ड करके संलग्न करता है।
4. पहली प्रकाशन के बाद, GHCR पैकेज सेटिंग्स खोलें और यदि अनाम इमेज पुल का इरादा है तो दृश्यता को **सार्वजनिक** पर सेट करें। केवल एक सार्वजनिक स्रोत रिपॉजिटरी सार्वजनिक कंटेनर पैकेज की गारंटी नहीं देती। संगठन नीतियों को पैकेज प्रकाशन की अनुमति देनी चाहिए। वर्कफ़्लो `GITHUB_TOKEN` का उपयोग करता है; रिपॉजिटरी में कोई रजिस्ट्री पासवर्ड या वीपीएस क्रेडेंशियल नहीं होना चाहिए।

इस स्थानीय तैयारी से दूरस्थ वर्कफ़्लो की सफलता स्थापित नहीं हुई है। ARM64 इम्यूलेशन एक स्मोक चेक है, यह नेटिव-हार्डवेयर या लाइव टेलीग्राम योग्यता नहीं है। यह रिलीज़ पैकेजिंग को स्वचालित करता है; सर्वर शुरू करने के लिए अभी भी Compose कमांड और इसके डोमेन/होस्ट पूर्वापेक्षाओं की आवश्यकता होती है। जब कोई रिलीज़ प्रकाशित होती है तो मौजूदा सर्वर चुपचाप अपग्रेड या रीस्टार्ट नहीं होते।

## रिमोट सर्वर

सेवा को लूपबैक तक सीमित रखें और SSH टनल का उपयोग करें, या HTTPS को रिवर्स प्रॉक्सी पर टर्मिनेट करें। बेस Compose फ़ाइल केवल स्थानीय है; वैकल्पिक `deploy/compose/compose.https.yaml` ओवरले कॉन्फ़िगर किए गए डोमेन के लिए Caddy प्रदान करता है। बेयरर टोकन को URLs और प्रॉक्सी लॉग्स से दूर रखें। रिवर्स प्रॉक्सी को अनुरोध आकार और कनेक्शन दरों को सीमित करना चाहिए। सादा HTTP को इंटरनेट पर न खोलें।

systemd, Windows लॉगऑन टास्क, macOS यूज़र एजेंट और Caddy के उदाहरण [deploy/](../../deploy/README.md) में दिए गए हैं। इंस्टॉलेशन से पहले उनके पथों की समीक्षा/अनुकूलन करें। ये प्रदान किए गए टेम्प्लेट हैं, स्थानीय रूप से निष्पादित प्लेटफ़ॉर्म क्वालिफिकेशन्स नहीं। सामान्य लॉन्चर द्वारा कोई बैकग्राउंड सर्विस या टास्क पंजीकृत नहीं किया जाता।

Windows पर, विंडो रहित `pythonw.exe` लॉन्च स्टार्टअप/सर्वर डायग्नोस्टिक्स को `logs/server.log` में डेटा निर्देशिका के अंतर्गत संग्रहीत करता है (प्रति फ़ाइल 5 MiB, दो रोटेटेड बैकअप)। कंसोल लॉन्च कंसोल लॉगिंग बनाए रखते हैं। HTTP एक्सेस लॉगिंग दोनों मोड में अक्षम है। लॉग्स को डेटा निर्देशिका के साथ सुरक्षित करें और साझा करने से पहले उनकी समीक्षा करें।

## पुनरारंभ और अंतराल

अंतिम अनुरोधित अवलोकन स्थिति संग्रहीत रहती है। यदि अवलोकन सक्रिय था, तो स्टार्टअप चयनित स्रोतों से फिर से कनेक्ट करने और उन्हें फिर से शुरू करने का प्रयास करता है। मैन्युअल पॉज़ उस इरादे को रद्द कर देता है। एक असफल पुनरारंभ दर्ज किया जाता है और पैनल में दिखाया जाता है।

StringSession प्राधिकरण बनाए रखता है लेकिन Telethon की टिकाऊ अपडेट/इकाई स्थिति नहीं। डायलॉग्स स्टार्ट पर फिर से लोड होते हैं। Telegram/Telethon चलने के दौरान कुछ ट्रांसपोर्ट रुकावटों से उबर सकते हैं, लेकिन TgWitness प्रक्रिया पुनरारंभ होने पर टिकाऊ रीप्ले का दावा नहीं करता। हर स्टार्टअप पिछले जर्नल हेड और ऑफ़लाइन सीमा को रिकॉर्ड करता है। मॉनिटर हर 10 सेकंड में कनेक्टिविटी की जाँच करता है और हर मिनट एक हार्टबीट जोड़ता है (**पैरामीटर → लाइवनेस रिकॉर्ड हर**)। संक्षिप्त रुकावटें छूट सकती हैं; एक कनेक्टेड ट्रांसपोर्ट पूरी अपडेट डिलीवरी की गारंटी नहीं देता। स्नैपशॉट स्पष्ट वर्तमान-इतिहास अवलोकन होते हैं, कभी भी गैप की मरम्मत नहीं।

मीडिया कतार प्रत्येक कार्यक्षेत्र के SQLite डेटाबेस में संग्रहीत होती है। एक संदेश और उसका कार्य परमाणु रूप से प्रतिबद्ध किए जाते हैं। रुके हुए चल रहे कार्यों को पुनः प्रयास के लिए आरंभ पर पुनः प्राप्त किया जाता है। प्रत्येक डाउनलोड में 120-सेकंड का बेस टाइमआउट और उसके आकार के लिए 256 KiB/s की गति का समय होता है, और प्रति अटैचमेंट प्रकार 1–2,000 MiB की सीमा होती है; टाइमआउट, गति और पुनः प्रयास **पैरामीटर के** अंतर्गत होते हैं। कलेक्टर उन फ़ाइलों को छोड़ देता है जिनका आकार अज्ञात है। रोकने पर कतार में मौजूद काम बरकरार रहता है। पुनः प्रयास मूल देखे गए फ़ाइल डिस्क्रिप्टर का उपयोग करता है, कभी भी बाद में संपादित संदेश के नवीनतम संस्करण का नहीं। अस्थायी विफलताओं के लिए सीमित पुनः प्रयास होते हैं; मीडिया फ्लडवेट पॉज़ पुनरारंभ से बच जाते हैं। मीडिया रिकवरी टेलीग्राम अपडेट रिकवरी से अलग है और गायब फ़ाइलों को पुनः बना नहीं सकती।

## बैकअप, पुनर्स्थापना, और क्षमता

**पूरे डेटा डायरेक्टरी** की प्रतिलिपि लेने से पहले प्रक्रिया को रोकें, जिसमें vault.key, signing.enc, credentials.enc, SQLite डेटाबेस/WAL फ़ाइलें, मीडिया, टोकन, चेकपॉइंट्स, और सभी प्रोफ़ाइल/उपनिर्देशिकाएँ शामिल हैं। जब गंतव्य सेवा बंद हो, तब पूरी प्रतिलिपि को पुनर्स्थापित करें। खोई हुई वॉल्ट कुंजियाँ या साइनिंग-की असंगति से स्टार्टअप विफल हो जाता है; जबरदस्ती पहुँच के लिए कुंजियाँ पुनः उत्पन्न न करें।

बैकअप को एन्क्रिप्टेड और एक्सेस-नियंत्रित रखें। सबूत ZIP फ़ाइलें पोर्टेबल समीक्षा कलाकृतियाँ हैं, न कि एप्लिकेशन बैकअप या टेलीग्राम-सत्र बैकअप। स्वचालित रूप से उन्हें बनाए नहीं रखा जाता और न ही हटाया जाता है। सभी संदेशों, कच्चे मेटाडेटा, मीडिया, अस्थायी एक्सपोर्ट्स और बैकअप के लिए डिस्क स्थान की योजना बनाएँ।

पूरे जर्नल को लोड करने के बजाय स्टार्टअप सत्यापन और एक्सपोर्ट स्ट्रीम रिकॉर्ड्स। एक एक्सपोर्ट एक रीड स्नैपशॉट को पिन करता है जबकि नए WAL राइट्स जारी रह सकते हैं; लंबे समय तक चलने वाले एक्सपोर्ट WAL पेजों को बनाए रख सकते हैं, इसलिए डिस्क क्षमता अभी भी मायने रखती है। ZIPs को 4 GiB तक बिना संपीड़ित के सीमित किया गया है ताकि यह स्वतंत्र सत्यापक की डिफ़ॉल्ट सेटिंग से मेल खाए; **पैरामीटर → सबसे बड़ी साइन की गई ZIP** सीमा बढ़ाती है, और ऐसे आर्काइव्स को `verify.py --max-gib N` के साथ सत्यापित किया जाता है। अन्य प्रारूपों में इवेंट-काउंट की कोई सीमा नहीं होती है। समर्थित ब्राउज़र उपयोगकर्ता द्वारा चुनी गई फ़ाइल में प्रतिक्रिया चंक्स को स्ट्रीम करते हैं। अन्य ब्राउज़र अधिकतम 128 MiB तक बफ़र करते हैं और बड़ी ट्रांसफ़र को प्रमाणीकृत CLI पर निर्देशित करते हैं:

~~~sh
python -m tgwitness.download --token-file data/live/panel-token.txt --out evidence.zip
~~~

किसी अन्य वर्कस्पेस के लिए **Exports → Workspace ID** से `--profile ID` का उपयोग करें, रिमोट सर्वर के लिए `--format zip|jsonl|csv|html`, `--url https://your-server`, या 5 GiB ट्रांसफर सीमा बदलने के लिए `--max-mib` का उपयोग करें। प्लेन HTTP केवल लूपबैक के लिए ही अनुमत है। टोकन हेडर में यात्रा करते हैं, रीडायरेक्ट अस्वीकार कर दिए जाते हैं, मौजूदा फ़ाइलों को ओवरराइट नहीं किया जाता है, और अधूरे डाउनलोड को पूरी हुई फ़ाइलों के रूप में प्रकाशित नहीं किया जाता है। यदि TGWITNESS_TOKEN उत्पन्न टोकन को ओवरराइड करता है, तो उस सक्रिय मान वाली एक अलग से सुरक्षित फ़ाइल का उपयोग करें: panel-token.txt को ओवरराइड द्वारा फिर से नहीं लिखा जाता है। कमांड का SHA-256 केवल एक ट्रांसफर चेक्सम है; हस्ताक्षरित ZIP को स्वतंत्र रूप से सत्यापित करें।

सर्वर एक्सपोर्ट फाइलें प्रत्येक वर्कस्पेस के निजी `temporary-exports/` में रहती हैं। सफल प्रतिक्रियाएँ अपनी फाइलों को साफ़ कर देती हैं। रुकी हुई एक्सपोर्ट फाइलें अगले वर्कस्पेस स्टार्टअप पर हटा दी जाती हैं, जब तक कि उसका एक्सक्लूसिव इंस्टेंस लॉक बना रहता है। यह डायरेक्टरी स्टोरेज थ्रेट/कैपेसिटी मॉडल का हिस्सा है; एक एन्क्रिप्टेड डेटा वॉल्यूम का उपयोग करें। प्रोडक्शन-स्केल मल्टी-गीगाबाइट ट्रांसफर के लिए अभी भी आपके टारगेट सिस्टम पर योग्यता की आवश्यकता होती है।

पैनल कतारबद्ध/असफल मीडिया, सबसे पुराना लंबित मीडिया, खाली डिस्क, टेलीग्राम अनुरोध विराम, और उन स्रोतों को प्रदर्शित करता है जिनकी पहुंच पुष्टि नहीं हुई है। ये निदान एक पूर्ण एंड-टू-एंड डिलीवरी मॉनिटर नहीं हैं। वर्कस्पेस एक ही प्रक्रिया साझा करते हैं; एक शोरगुल वाला खाता अभी भी दूसरों को प्रभावित कर सकता है। अलग वर्कर प्रोसेस, रिटेंशन/रोटेशन, टिकाऊ अपडेट रिकवरी, रिमोट चेकपॉइंट एंकरिंग, भूमिकाएँ, और पूर्ण डिप्लॉयमेंट योग्यता बनी रहती हैं।

## कनेक्शन और सुरक्षा विकल्प

कनेक्शन मार्ग प्रत्येक कार्यक्षेत्र के लिए होते हैं और प्राधिकरण से पहले कॉन्फ़िगर किए जाने चाहिए। SOCKS5/HTTP CONNECT पिन किए गए python-socks निर्भरता का उपयोग करते हैं। MTProxy Telethon के प्रयोगात्मक यादृच्छिक मध्यवर्ती परिवहन का उपयोग करता है; Fake TLS ee secrets समर्थित नहीं हैं। कोई स्वचालित प्रत्यक्ष फॉलबैक कॉन्फ़िगर नहीं किया गया है। यह कोई सिस्टम-व्यापी नेटवर्क मार्ग नहीं है।

नई इंस्टॉलेशन के लिए, TGWITNESS_VAULT_KEY_FILE एक अलग से सुरक्षित रैंडम मास्टर-की फ़ाइल की ओर इशारा करता है। इसे /data के बाहर एक कंटेनर में केवल-पढ़ने के लिए माउंट करें। प्रत्येक वर्कस्पेस के साथ सार्वजनिक vault.external.json सॉल्ट मेटाडेटा और मास्टर की को अलग-अलग सुरक्षित रखें। मौजूदा स्थानीय वॉल्ट के लिए एक नियोजित माइग्रेशन की आवश्यकता है; इस वेरिएबल को सेट करने से वे चुपचाप परिवर्तित नहीं हो जाते। संदेश/मीडिया भंडारण और निर्यात एप्लिकेशन-एन्क्रिप्टेड नहीं हैं। जहाँ आवश्यक हो, एन्क्रिप्टेड वॉल्यूम और पर्याप्त निजी अस्थायी भंडारण का उपयोग करें।
