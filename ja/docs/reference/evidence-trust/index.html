証拠と信頼

エクスポートデータ、動画、ウェブアーカイブ、および署名付き記録が何を立証し得るか、また収集デバイスがそれらの信頼性にどのような影響を与えるか。

エクスポート、スクリーンショット、または記録は有用な証拠となり得ます。その信頼性は、収集、保存、および裏付けの方法に依存します。有効なハッシュや署名は保存された資料を検証するものであり、収集デバイスが真実のソースコンテンツを受信したことを単独で立証するものではありません。この境界線はTgWitnessにも適用されます。

本ガイドでは、技術的な検証と法的評価を区別しています。製品ドキュメントおよび以下の法的規定は、2026年11月1日に確認されました。Hunchlyの比較は、公開されているドキュメントを説明するものであり、新たな製品監査ではありません。

信頼がキャプチャに介入する場面#

ここでの脅威モデルは、証拠が確定される前に、攻撃者またはオペレーターが収集 環境を改変できることを前提としています。これは条件付きの分析であり、 特定のデバイスや製品が侵害されたという主張ではありません。

公式クライアントと暗号化された接続は、通常の使用を保護するのに役立ちます。それらは、周囲のオペレーティングシステム、ブラウザ、またはディスプレイを、それ自体として信頼できるものにするものではありません。復号化後、キャプチャ前にコンテンツが置き換えられた場合でも、エクスポーターはそれを正確に保存でき、署名者は正しく署名することができます。いずれの操作も、破られたハッシュアルゴリズムや偽造された署名を必要としません。

同じデバイスで撮影された動画は、同じ置換された表示を記録することができます。 別のカメラを使用すれば、ディスプレイに何が表示されていたかを確認することはできますが、ディスプレイだけでは Telegramが提供した内容を認証することはできません。同様に、1つの制御された環境から得られたHTML、JSON、 スクリーンショット、およびブラウザログが一致している場合でも、それらは同じ 不具合を共有している可能性があります。それらの整合性は有用な文脈情報ですが、自動的に独立した 裏付けとなるわけではありません。

独立して保持されたチェックポイントまたは検証済みタイムスタンプ 後の提出物との比較用に保持されたハッシュまたはチェックポイント どのバイトおよび境界が対象となっており、独立した当事者は実際に何を証明しているのでしょうか？

Telegramは、デスクトップエクスポートをオフラインのHTML/JSONコピーとして、またTakeout APIを選択したアカウントデータを取得する手段として文書化しています。これらの説明には、 受信者が検証するための、最終的にエクスポートされたアーカイブに対するTelegramの署名は含まれていません。 我々の結論は、文書化されたこれらのエクスポートメカニズムに限定されるものであり、 Telegramの証拠に法的価値がないという主張ではありません。Telegramデスクトップエクスポート、Takeout API。

同様の区別は、バックグラウンドリクエスト、キャッシュエントリ、およびネットワークログにも適用されます。これらは不整合を明らかにし、収集内容の裏付けとなる場合があります。それらの複雑さだけでは、誰がそれらを作成したかを立証するものではありません。独立して運営されるアーカイブや別途入手したサービス記録は、比較対象となる別の情報源を提供しますが、それらは独自の収集および保管上の制限に従うものとします。

Hunchlyは同じ境界を例示しています#

Hunchlyのドキュメントでは、MHTMLキャプチャ、写真、および添付ファイルのSHA-256ハッシュ化と、独立したハッシュ検証について説明しています。また、改変されたファイルに新たに計算されたハッシュが添付されている場合でも、その比較を通過してしまう理由を解説し、追加のチェックとして署名とソースの照合を挙げています。Hunchly：コンテンツ、写真、および添付ファイルのハッシュ化。

公開されている『証拠ガイド』（2018年10月17日版、改訂1.0）には、MHTMLキャプチャ用にローカルで生成されるGPG鍵および署名について記載されています。同ガイドでは、ローカルの秘密鍵へのアクセスを、改変された資料に再度署名する方法として明示的に特定しています。これは文書化された信頼性の制限であり、未公開の現在の脆弱性の証拠ではありません。 また、同ガイドでは、ChromeがMHTMLキャプチャを実行すると述べられています。Hunchlyについて、調査員の評判のみに依存していると説明することは、これらの技術的な制御を省略することになります。Hunchly証拠ガイド、第2～4節。

特定の製品で収集された資料が事件において採用されたかどうかは、関連する判決および状況によって決まります。当社は、裁判所がHunchlyやTgWitnessをどの程度の頻度で採用しているか、あるいはいずれの製品も裁判所から一般的な承認を得ているかについて、ここでは一切言及しません。

TgWitnessが追加する機能と、その保護の範囲#

TgWitnessは、署名付きでリンクされたジャーナルに観察結果を記録し、受信者が確認できるエクスポートデータを提供します。保持されたチェックポイント、タイムスタンプ、および独立した証人により、レビュー担当者は収集者の現在のファイル以外の参照情報も得ることができます。これらは、以前にコミットされた記録への変更を明らかにするのに役立ちます。カバレッジ記録と明示的な収集結果は、何がキャプチャされ、何がキャプチャされなかったかを説明するのに役立ちます。証拠の形式と引き渡し、 収集範囲。

置換のタイミングは重要です：

  1. 署名後、署名鍵へのアクセスがない状態で、署名済みレコードまたはマニフェストに紐付けられたファイルを変更すると、信頼できる検証者および鍵による検証に失敗します。
  2. コレクターキーを使用する場合、独立したチェックポイントが保持された後は、置換ジャーナルに有効な新しい署名を含めることは可能ですが、プレフィックスが変更されると以前のチェックポイントとの比較に失敗します。同じ管理対象デバイス上でのみ保持されているチェックポイントは、ジャーナルとともに置き換えることができます。保持された境界を超える記録については、別途対応が必要です。
  3. 観察対象を網羅するチェックポイントが独立して保持される前に：虚偽の入力データは、以前のチェックポイントの後に追加された新しいレコードを含め、正常に署名され、アンカー設定される可能性があります。その結果として生成されたチェックポイントやタイムスタンプは、依然としてそれらの虚偽のレコードを網羅していますが、その真実性を立証するものではありません。

TgWitnessは、コレクターが署名したチェックポイントを受信するものであり、基となるTelegramの会話内容を独自に読み取るものではありません。その鍵および保持された記録は、別途信頼される必要があります。提出されたジャーナル全体を証人処理する必要がある場合は、最終的なエクスポート境界を必要とする引き継ぎ手順を使用してください。通常の整合性チェックでも、証人処理されていない末尾部分を報告することは可能です。

検証済みの RFC 3161 レスポンスは、当局が明示した時刻にチェックポイントが存在したことを裏付けることができます。ただし、Telegram メッセージがいつ送信されたか、あるいはその内容が真実であったか否かを立証するものではありません。事前に作成されたリクエストや、添付されたレスポンスファイルのみでは不十分です。tgwitness.verify を使用してエクスポートを検証する際、添付された TSA 署名を検証するには、--tsa-ca を通じて明示的に信頼された CA が必要です。OpenTimestamps のレシートには、独立したots verify が必要であり、必要に応じて証明のアップグレードを行う必要があります。 タイムスタンプ手順、RFC 3161。

GitHub Actionsのキャプチャでは、一時的にホストされたランナーがメッセージを収集します。アテステーションは、アーカイブを承認済みのワークフローに紐付けます。このモードでは依然として、GitHub、承認済みのソフトウェアと依存関係、ヘルパー／ブラウザおよびトンネルを信頼しています。これは、機密性の高いハードウェアでも、Telegramの署名でも、また誰もホストにアクセスしなかったという証明でもありません。ローカルで署名された実行レシートも、自己申告による測定値であり、ハードウェアによるアテステーションではありません。

法的効力は根拠によって異なります#

以下の4つの問いは明確に区別されるべきです。その項目が主張されている通りであるかどうか、 提出されたバイトが保持されている記録と一致しているかどうか、その内容が 主張されている事実を裏付けているかどうか、そして適用される規則がその使用を許可しているかどうか。暗号学的 検証は、その根拠の一部にしか対処しません。

米国連邦手続において、規則901は証拠を認証する方法を規定しており、これには事情に精通した証人の証言やプロセスまたはシステムに関する証拠が含まれます。 規則902(13)および902(14)は、特定電子記録およびその写しについて、手続き上の要件を伴う認証手段を規定しています。これらの規則に関する委員会注記では、認証を伝聞証拠、関連性、帰属といった問題と区別しています。ソフトウェア署名のみでは、そこに記述されている「適格者による認証」には該当しません。連邦証拠規則901、連邦証拠規則902。

カナダの「証拠法」が適用される場合、第31.1条は電子文書の認証について規定しています。第31.2条は、最良証拠の原則をシステムの完全性または適用可能な推定と結びつけています。第31.3条は、完全性の推定が適用される状況を規定しています。これらは定義された証拠上の条件であり、認可を受けた調査員や商用製品がすべて絶対的に正確であるという包括的な推定ではありません。 カナダ証拠法、第31.1条、第31.2条、第31.3条。

これらの例は、他の法域や特定の事件における証拠採用の可否を決定づけるものではありません。技術的な検証は、主張を裏付ける資料にも、それに異議を唱える資料にも一貫して適用されるべきです。本ガイドは、検察側の証拠が一般的に弁護側の証拠よりも採用されやすいと主張するものではありません。

他者が評価できる記録を作成してください#

  • アカウント、収集デバイス、オペレーター、ソフトウェアバージョン、アクセス権限、選択された範囲、および収集期間について記述してください。署名チェックの成功を「デバイスがクリーンである」というテスト結果として扱うのではなく、中断や侵害の可能性について記録してください。
  • 元のパッケージを維持し、転送、ハッシュ、および時刻のソースを記録してください。 鍵のフィンガープリントとチェックポイントは、別途信頼されたチャネルを通じて保持してください。 レポートに記載する前に、実際の証人またはタイムスタンプの適用範囲を検証してください。
  • 主張にふさわしい独立した裏付けを探してください：他の参加者の記録、独立したキャプチャ、または合法的に取得されたサービス記録などです。それらの独立性と制限について説明してください。コピー間の整合性だけでは不十分です。
  • 関連する文脈を維持してください。省略されたファイル、利用できない履歴、および黒塗り箇所を明示してください。必要に応じて、別途、最小限に縮小した開示文書を 作成し、それを完全な原本として提示することなく、その変換内容を説明してください。
  • 受信者に対して検証手順と、その検証に必要な資料を提供してください。 観察結果、技術的所見、および分析者の結論を明確に区別できるようにしてください。

特定の引き継ぎについては、アーカイブのハッシュ、信頼できる鍵、検証結果、および外部でカバーされている正確な境界を明記してください。ソースの真正性、アカウントの帰属、完全性、および法的結論について、それぞれ個別に記述してください。これにより、次のレビュー担当者は検証すべき具体的な主張を把握できます。
