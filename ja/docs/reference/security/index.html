TgWitness / ドキュメント · 導入と復旧

このページでは、ローカルまたはサーバー上のワークスペースにおけるアクセス、保存、およびネットワーク保護について説明します。 GitHubランナーまたはIntel TDX機密VMでの収集については、収集環境のチェックを追加する 検証モードを参照してください。 アカウントの接続、通知、タイムスタンプ、オフサイトコピー、およびウィットネスには、それぞれ独自のルーティング設定があります。

エリア 要約すると
アクセス 管理者キーに加え、アカウントやチャットへの範囲限定アクセス、7種類の権限、および取り消し可能なセッションを備えています。デフォルトではlocalhostで動作します。
保存中の機密情報 セッション、APIペア、署名鍵、およびプロキシ設定は、Fernetを用いて暗号化されています。
メッセージとメディア 暗号化されずに保存されます：ディスクの暗号化と厳格なアクセス権限の設定を行ってください
完全性 すべての記録に対して、SHA-256ハッシュチェーンとEd25519署名が適用されています。
ローカル・トラスト・バウンダリー ホスト管理者はワークスペースとその署名鍵を管理します。独立したチェックポイントは、以前のジャーナル境界を保持します。

脆弱性に関する報告については、セキュリティポリシーをご参照ください。

アクセスモデル#

メインパネルのトークンにより、完全な制御権が与えられます。他のユーザーには、対象を 限定したアクセス権を付与することができます。具体的には、選択したワークスペースやチャット、権限、有効期限、 IP制限、ログイン制限、および取り消し可能なセッションなどです。チャット限定のアクセス権を持つユーザーは、 たとえ権限にチェックが入っていても、ワークスペース全体の操作を行うことはできません。 ワークスペースはプロセスを共有しており、ホスト管理者からデータを隔離することはありません。

パネルはデフォルトでlocalhostをリッスンします。ブラウザでのサインインにより、アクセストークンが セッション認証情報と交換され、ブラウザはこれをベアラートークンとして送信します。これは、 認証クッキーではなく、sessionStorageに保存されます。ロックまたはサインアウトを行うと、 ブラウザのセッションがクリアされます。ブラウザを閉じたりセッションを終了したりしても、データの収集は停止しません。

発行されたトークンおよびセッション認証情報は、暗号化された保管庫内にハッシュとして保存されます。 失効処理を行うと、関連するセッションは終了します。権限の変更は、その後の リクエストに反映されます。ダウンロードされたファイルは取り消すことができません。管理者は 自身のブラウザセッションを制限することもできますが、メインパネルのトークンを直接使用するスクリプトは 完全なアクセス権を維持し、それらのブラウザセッションの制限をバイパスします。

認証失敗については、クライアントアドレスごとにレート制限が適用されます。IP制限には、 アプリケーションが認識するアドレスが使用されます。これを利用する前に、 リバースプロキシの動作を確認してください。Witnessの認証情報は、読み取り専用のチェックポイント／ヘルス認証情報として別途管理されています。

デモへのアクセス#

/api/demo-accessは、明示的に 開始された隔離された合成デモ用の、意図的に認証されていないブートストラップです。これは、プロセス存続期間に有効な個別の機能を発行しますが、 実際のパネルトークンやTGWITNESS_TOKENのオーバーライドを発行することは決してありません。 この機能の発行および使用には、 ループバックピアとホストが必要であり、ヘッダーの転送やクロスオリジンリクエストは行われません。追加の ワークスペースや認証済みセッションが存在する場合、このパスは無効になります。ライブワークスペースでは、 この機能は発行されません。このデモでは、アカウントの接続や収集設定の変更は行えません。

パネルの内容とエクスポート機能#

このパネルでは、外部フォント、分析ツール、CDNリソース、および埋め込みリモートメディアは一切使用していません。 Telegramから取得したテキストは、HTMLではなくテキストとして挿入されます。ダウンロードされた添付ファイルは バイナリ添付ファイルとして提供されます。JSONL形式でのエクスポートでは元の文字列が保持されますが、HTML形式では エスケープ処理が行われます。また、数式となる可能性のあるCSVのセルには、アポストロフィが接頭辞として付加されます。

エクスポートデータには認証および署名用の秘密鍵は含まれませんが、 収集されたソースメタデータ、識別子、および場合によっては個人情報や機密情報が意図的に含まれています。 Telegramのアクセスハッシュやファイル参照情報が、生のソースメタデータに含まれる場合があります。

保存中の機密情報#

Telegram APIの認証情報、セッション、および署名鍵はFernetで暗号化されています。 ローカルのメッセージおよびメディアについては、ホストのディスクまたはボリュームによって暗号化が行われます。 ワークスペースには通常のファイルが保存されます。エクスポートにはパスワードで保護されたAES-256 ZIPを使用でき、 オフサイトのコピーにはAES-256-GCMが使用されます。

Vaultキーは、デフォルトで保護されたデータディレクトリに設定されます。別途保存するには、以下の外部マスターキーファイル を使用してください。Unixでは、新しい秘密鍵ファイルにはモード0600を、新しいデータ ディレクトリには0700を設定します。Windowsでは、サービスアカウントおよび 承認された管理者のためにディレクトリのACLを設定してください。既存のディレクトリ権限は維持されます。

外部マスターキー#

新しいデータディレクトリの場合、TGWITNESS_VAULT_KEY_FILE を使用して外部のランダムな マスターキーを指定できます。HKDF-SHA256 と個別のランダムなソルトにより、ワークスペースごとに異なる Fernet キーが 導出されます。復旧のためには vault.external.json を保持しておく必要があります。マスターキーが欠落しているか 間違っている場合、処理は失敗します。既存のローカルボールトは、自動的に移行されることはありません。 パネルには、選択されたキー保存モードが表示されます。どちらのモードでも、ディスク暗号化によりローカルの メッセージおよびメディアファイルが保護されます。設定の詳細については、「 接続とデータ保護」を参照してください。

プロキシとネットワーク経路#

プロキシ設定はVault内で暗号化されます。パスワードおよびMTProxyのシークレットは、 APIによって返されることも、証拠記録に書き込まれることもありません。各ワークスペースは、 Telegramのルーティング方法とIPモードを個別に選択します。

「アドレスを非表示」を選択すると、Telegramへの直接アクセスが制限され、外部への HTTPリクエストにはプロキシが必要となります。「明示的に選択されたフォールバックモード」では、遅延後にTelegramへの 直接アクセスが可能になります。「トンネル/VPNモード」では、直接接続が許可されます。トンネル モードを選択しても、VPNのインストールや検証は行われません。これらの設定は、マシン全体の トラフィック、ブラウザ、パッケージマネージャー、またはローカルプロキシホストによるDNS解決を制御するものではありません。

MTProxyはTelegramのトラフィックのみを転送します。外部リクエストについては、別の SOCKS5/HTTPプロキシ、ワークスペースのSOCKS5/HTTPルート、または許可された直接ルートを使用できます。 また、これらを無効にすることも可能です。独立したWitnessには独自のトランスポート設定があります。 通常のSOCKS5/HTTP CONNECT認証は、これらのプロキシ プロトコル自体によって暗号化されません。偽のTLS MTProxyシークレットは、引き続きサポートされていません。

サインインとセッションのインポート#

変換された .tgwitness-session ファイルには、 Vault に読み込まれて保存されるまで、平文の認証シークレットが含まれています。オフライン CLI は、検証済みの Telethon スキーマを受け付けます。 パネルインポートでは、さらにPyrogram SQLite、最新のシングルアカウント用TData ZIP、 およびドキュメント化されたJSON入力も受け付けます。認証が必要で、4ファイル／8 MiBに制限されており、 アーカイブの解凍や元のファイルの保存を行わずに、メモリ内でアップロードを処理します。 正規化された認証情報は、リクエストを行った認証済みブラウザにのみ返されます。 これらは、Telegramによる認証が成功した後、暗号化された保管庫に保存されます。 元のファイルおよび変換後のファイルを保護し、複数のクライアントによる認証情報の複製を防止してください。

データ処理では、コンテナのチェックサム、ローカルでの復号ハッシュ、および構造の 長さを検証します。指定されたデスクトップ版のローカルパスコードは一時的に使用されるのみで、保存されることはありません。 この限定的なパーサーは、すべてのデスクトップ版との互換性を保証するものではありません。 QR画像はローカルで生成され、短命なTelegramログイントークンを含んでおり、 外部のレンダリングサービスへ送信されることはありません。ロック、ワークスペースの切り替え、新規ログイン、 および経路の変更により、保留中のQR試行はキャンセルされます。タブの再読み込みや閉じ操作を行うと、 有効期限が切れるまで試行が保留されたままになる場合があります。QRログインに成功した場合でも、アカウントの紐付けは引き続き適用されます。 通常のAPIボディは16 KiBに制限されたままですが、認証済みインポートルートでは 最大12 MiBのエンコード済みJSONを受け付け、デコード後のファイルサイズの上限については別途適用されます。

ログインコードおよびTelegramの2段階認証パスワードは保存されません。電話番号およびコードのハッシュ値は、 認証処理中にメモリ内に保持されます。Telegramのセッションによりアカウントへのアクセスが許可されますが、 データディレクトリ、セッション、トークン、Vaultキー、または秘密署名鍵をGitHubにアップロードすることは決してありません。

ログと転送#

デフォルトのAPI検証レスポンスは、認証情報を 反映しないよう置き換えられています。アプリケーションのアクセスログ記録は無効化されています。リバースプロキシを 設定する際は、Authorizationヘッダーやリクエスト本文をログに記録しないようにしてください。HTTPではトークンやログイン シークレットが平文で送信されます。localhostから通信を行う際は、常にHTTPSまたはSSHトンネルをご利用ください。

完全性の制限#

ローカル検証では、レコードの署名、ハッシュチェーン、添付ファイル、およびエクスポートマニフェストがチェックされます。 管理者はローカル署名鍵を保持しており、別の署名付きジャーナルを作成することができます。 独立して保持されるチェックポイントは、そのチェックポイントがカバーするプレフィックスの置換を検出します。 鍵のフィンガープリントとチェックポイントは、受信者または独立した証人に保管してください。

独立した検証が可能な収集方法としては、GitHub Actionsによるキャプチャ またはIntel TDXによるデプロイを選択してください。 これらの検証ツールは、アーカイブの完全性に加え、ワークフローの来歴やハードウェア測定値も検証します。 オプションのタイムスタンプと暗号化されたオフサイトコピーにより、タイムアンカーと復元可能なコピーが提供されます。 証拠フォーマットには、各モードにおける検証手順が記載されています。

問題があると思われる場合#

元のデータディレクトリはそのまま保持し、分析には別のコピーを使用してください。 セキュリティポリシーに従い、影響を受けるバージョン、操作、再現手順を報告してください。その際、アカウントデータや認証情報は非公開にしてください。
