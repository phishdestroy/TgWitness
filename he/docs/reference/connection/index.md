## הגדרת חיבור מודרכת

ב-**Connection**, המנהל יכול לבחור **חשבון זה**, **חשבון קבוצה** או **כל החשבונות**, ולאחר מכן לבחור מסלול. **סקירת הבחירה** מפרטת את החשבונות המושפעים. **הכנה ובדיקה** בודקת את המסלול המוצע מבלי לשנות את המסלול השמור. **החלת החיבור שנבדק** בודקת שוב, מעכבת את הניטור אם יש צורך, שומרת את המסלול ומחדשת את הניטור שכבר היה פעיל. המערכת לעולם לא מתחילה איסוף נתונים בחשבון שהיה במצב של חוסר פעילות בעבר. הורדות ההיסטוריה נותרות בהשהיה וניתן לחדשן בנפרד. יש להשהות ייצוא פעיל לפני המעבר.

שינויים בקבוצה שומרים על חשבונות במסלולם המקורי כברירת מחדל. יש לבטל אפשרות זו רק כאשר תצוגה מקדימה מציגה את השינויים הרצויים. האפליקציה מדווחת על התוצאה של כל חשבון בנפרד; אין מדובר בעסקה של "הכל או כלום" על פני כל מסדי הנתונים. מעבר שנכשל משחזר את ההגדרות הקודמות של אותו חשבון. כישלון בחידוש מוצג באופן מפורש. תצוגות מקדימות פוקעות לאחר עשר דקות, ושינויים בהגדרות החיבור או בחברות בקבוצה מחייבים בדיקה מחודשת.

| מסלול | מה מנהל ה-TgWitness |
| --- | --- |
| ישיר | חיבורים מהמארח; VPN של מארח חיצוני אינו מזוהה או נאכף. |
| VPN | פרופיל WireGuard אחד עם מנהרה מלאה לכל חשבון, המופעל על ידי תהליך SOCKS5 במרחב המשתמש המקומי. לא מותקן ממשק מארח או מנהל התקן. |
| הפרוקסי שלי | אישורי CONNECT מסוג SOCKS5, HTTP או MTProxy. ניתן להזין כתובת URL בשדות SOCKS5/HTTP. בחירת מספר חשבונות תשתמש בפרוקסי שהוזן. |
| MTProto ציבורי | המאגר הקיים מקצה מסלולי Telegram. בקשות חיצוניות מושבתות עד להגדרת פרוקסי מתאים נפרד בהגדרות המתקדמות. |
| WARP | מנהרה מקומית נפרדת לכל חשבון שנבחר, עם רישום WARP ופרופיל WireGuard המאוחסנים בכספת של אותו חשבון. |

בדיקת המסלול הנוכחי משתמשת בהעברה חדשה ולא מאומתת של Telegram, ולא בהפעלה של החשבון. עבור מסלולים התומכים ב-HTTP, היא מבקשת גם את עקבות ה-HTTPS של Cloudflare דרך אותו מסלול ומציגה את כתובת ה-IP היוצאת המדווחת, המדינה, מצב ה-WARP וזמן הבדיקה. השהיה הנמדדת היא זמן הקמת החיבור של Telegram, ולא פינג ICMP. הכנת ה-WARP נכשלת אלא אם כן המעקב מדווח ש-WARP פעיל. בדיקות אלו קובעות את קיומה של קישוריות, ולא את האותנטיות או השלמות של ההודעות שנלכדו. תהליך מקומי פועל כשלעצמו אינו מהווה בדיקת יציאה מוצלחת.

### WARP ו-WireGuard ניידים

זוהי אינטגרציה לא רשמית של **עם WARP** באמצעות [wgcf 2.3.1](https://github.com/ViRb3/wgcf/releases/tag/v2.3.1) ו- [wireproxy 1.1.3](https://github.com/windtf/wireproxy/releases/tag/v1.1.3). המנהל מאשר במפורש את ההתקנה לפני ההורדה הראשונה או הרישום ל-WARP. חיבורי ההתקנה הללו מובילים ישירות ל-GitHub ול-Cloudflare ו חושפים את כתובת ה-IP של המחשב. תעבורת חשבונות רגילה שומרת על המסלול הקיים שלה עד להפעלת היישום. Cloudflare בוחרת את כתובת היציאה ואת המדינה; מנהרות נפרדות יכולות לחלוק כתובת יציאה אחת. בחירת המדינה, סיבוב כתובות IP תקופתי ו-VPN kill switch ברמת המארח אינם כלולים בתכונה זו.

הורדות עוזרים נתמכות: לינוקס ו-macOS x86-64/ARM64, ו-Windows x86-64. הארטיפקטים נבדקים מול חשישים מסוג SHA-256 הכלולים במקור שנבדק, וקבצי ההפעלה במטמון נבדקים שוב לפני ההפעלה. אף כלי עזר אינו מתווסף ל- PATH, אינו מותקן כשירות מערכת, ואינו מקבל מאזין ציבורי. כל הקבצים נמצאים תחת ספריית `portable-routes/` של סביבת העבודה וברשומות הכספת המוצפנות. המאזין SOCKS5 בלולאה חוזרת דורש אישורים שנוצרו באופן עצמאי.

פרופילים פרטיים ופרטי הזדהות של חשבון WARP מוצפנים באמצעות כספת סביבת העבודה הקיימת. בזמן הפעולה, התוכנה העוזרת זקוקה לקובץ תצורה בטקסט רגיל המיועד לבעלים בלבד; קובץ זה מוסר בעת כיבוי רגיל. קריסת מארח עלולה להשאיר קובץ זה מאחור בתיקיית הנתונים המיועדת לבעלים בלבד. פעולה זו אינה מצפינה את הדיסק ואינה מגנה מפני מנהל המערכת. המפקח סוגר את המנהרה אם הצינור האב של הלוח נעלם. מנהרה שנכשלה לעולם אינה מאפשרת מעבר ישיר לגיבוי. הפעלה מחדש של הלוח משחזרת מנהרה נבחרת; ניסיונות התחלה שנכשלו יבוצעו מחדש עם עיכוב מוגבל. **עצירת המנהרה** גם מעכבת את הניטור ושומרת על מצב העצירה. **הפעלת המנהרה** מפעילה את המנהרה; יש לחדש את הניטור בנפרד כאשר מוכנים.

פרופילים של WireGuard שהועלו חייבים להכיל ממשק אחד ו-Peer אחד, נתיבי IPv4 ו-IPv6 מלאים, וללא hooks, includes, תחליפי סביבה או מאזינים נוספים. כתובות נקודות קצה ציבוריות נפתרות ומוצמדות לפני ההפעלה. השתמש ב-VPN חיצוני או בשער SOCKS5 עבור OpenVPN/IPsec ונקודות קצה פרטיות.

## שיטות אימות

**מזהה ה-API וה-hash של ה-API מזהים יישום; הם אינם מחליפים את פרטי הכניסה לחשבון.** הם אופציונליים ב-TgWitness. סדר העדיפות: זוג שהוזן בטופס, לאחר מכן זוג מתוך קובץ JSON של חשבון מיובא, לאחר מכן הזוג שנשמר בסביבת העבודה, ולבסוף מאגר מובנה של 50 , הנבדקים בסדר אקראי עם סיבוב אוטומטי כאשר טלגרם דוחה אחד מהם. רק הצמד של Telegram Desktop (2040) נשלח עם תיאור תואם של לקוח Telegram Desktop. ניתן להשתמש בצמד משלכם מכלי פיתוח ה-API ב-[my.telegram.org](https://my.telegram.org) עם כל החשבונות שלכם; לכל חשבון עדיין יש אישור משלו.

| שיטה | דרישות | תמיכת TgWitness |
| --- | --- | --- |
| טלפון, קוד, אימות דו-שלבי (2FA) אופציונלי | גישה לחשבון; זוג API אופציונלי | כניסה לפאנל |
| מפתח אימות HEX + מזהה DC | מפתח מלא בן 512 תווים ו-DC 1–5 | כרטיסיית "**מפתח אימות** ישיר"; מזהה המשתמש האופציונלי נבדק לפני שמירת האישור |
| Telethon StringSession | מחרוזת הפעלה תקפה | כניסה לפאנל |
| Telethon SQLite `.session` | טקסט סגור ועקבי | ייבוא ישיר של סכמות לפאנל 7/8; CLI אופציונלי במצב לא מקוון |
| Pyrogram SQLite `.session` | הפעלת משתמש בסביבת ייצור סגורה | ייבוא ישיר של סכמות לפאנל 2/3 |
| Telegram Desktop TData ZIP | חשבון אחד מודרני; קוד גישה מקומי אם החשבון מוגן | המרה בזיכרון עם בדיקות סיכום ביקורת/פענוח |
| קובץ JSON של החשבון | שדות API/session/key נתמכים | המטא-נתונים לבדם ממלאים את פרטי הזיהוי של ה-API; עדיין נדרשת כניסה באמצעות סשן/מפתח או טלפון/QR |
| כניסה באמצעות QR | אישור מאפליקציית Telegram מורשית | יצירת QR מקומית, תוקף/ניסיון חוזר, אימות דו-שלבי (2FA) אופציונלי |
| TDLib / Pyrogram StringSession | פורמטים נוספים ספציפיים לספריות | לא נתמך |
| אסימון בוט | בוט עם מודל גישה/עדכון משלו | לא בשימוש על ידי אוסף זה |

Telegram בוחרת באספקת קודים; משלוח SMS אינו מובטח. חתימת API אינה יכולה לתקן הפעלה שבוטלה או להחליף סיסמת 2FA שנשכחה. TgWitness אינה שומרת קודי כניסה או את סיסמת ה-2FA של Telegram בדיסק.

במקרה של מקור פרטי, על החשבון להיות בעל גישה כבר מראש. אין צורך בשם משתמש של קבוצה. שימוש בפרוקסי או ייבוא הפעלה אינם מעניקים זכויות חברות או זכויות מנהל. חברות נוכחית אינה מבטיחה גישה להיסטוריה מלפני ההצטרפות.

## ייבוא קובץ הפעלה של Telethon

Telethon SQLite, Pyrogram SQLite ו-Telegram Desktop TData משתמשים בפורמטים שונים. הלוח מזהה וממיר את המבנים הנתמכים; שינוי שם הקובץ אינו נחשב להמרה. בחר סשן אחד ואת קובץ ה-JSON הנלווה אליו תחת **"קובצים**", ולאחר מכן לחץ על **"חבר חשבון"**. ניתן לקבל עד ארבעה קבצים תואמים ו 8 MiB בסך הכל. ראו [מגבלות הפורמט](https://phishdestroy.github.io/TgWitness/he/docs/reference/accounts/) לפרטים על TData/JSON. אין אפשרות לשחזור סיסמה. כניסה באמצעות טלפון/2FA או QR יוצרת אישור נפרד.

נתיב שורת הפקודה האופציונלי, המיועד אך ורק ל-Telethon, נותר זמין:

1. הפסק את פעולת הלקוח המשתמש בהפעלה המקורית וצור עותק תואם. הממיר דוחה קבצים עם WAL/יומן לא גמור. סגור את הלקוח המקורי כראוי במקום למחוק את הקבצים הללו כדי לעקוף את הבדיקה.
2. מסביבת TgWitness, הפעל:

```
python -m tgwitness.sessions account.session --out account.tgwitness-session
```

1. תחת **"הוסף חשבון" → "קבצים**", טען את התוצאה או הדבק את המחרוזת שלה, והמשך.
2. בדקו את מזהה החשבון המספרי המוצג, בחרו מקורות והתחילו במעקב.

**הקובץ שהומר הוא סיסמת גישה לחשבון שאינה מוצפנת.** יש לשמור אותו במקום אחסון מוגן, ואסור בשום אופן להעלות אותו או לשלוח אותו לשירות המרה של צד שלישי. TgWitness שומר את ההפעלה המורשית בכספת המוצפנת שלו. העתקת הפעלה אינה יוצרת הרשאה נפרדת: אין להפעיל לקוחות במקביל עם מפתחות אימות משוכפלים ולהניח כי העדכונים מועברים באופן עצמאי.

ההמרה מעבירה הרשאות, ולא את ההודעות המקוריות, את מטמון הישות או סמן עדכון קבוע. היא אינה מתקנת שחזור עדכונים לאחר הפעלה מחדש של התהליך.

## MTProto, Telethon ושרתי פרוקסי

MTProto הוא הפרוטוקול של טלגרם. Telethon היא ספריית הלקוח ב-Python שבה משתמש TgWitness. MTProxy הוא פרוקסי העברה של טלגרם; SOCKS5 ו-HTTP CONNECT מספקים מנהרות כלליות. אף אחד מהם אינו מחליף את אימות החשבון.

שמור את המסלול עבור כל סביבת עבודה ב-**חשבון → הגדרות → הגדרות חיבור → שנה מסלול חיבור** לפני הכניסה. סביבות עבודה חדשות מוגדרות כברירת מחדל ל**-אוטומטי MTProxy · רשימות ציבוריות** עם האפשרות **"הסתר את הכתובת"**. סביבות עבודה קיימות שהשתמשו במפורש ב-Direct שומרות על מצב המאפשר זאת.

## מצבי IP

המסלול בוחר את החיבור. מצב ה-IP, **הגנת ה-IP** בסעיף "חשבון" בלוח הבקרה, קובע מתי כתובת השרת עשויה להיחשף. בקרות אלה אינן מתקינות VPN ואינן מנתבות את כל התעבורה של המחשב.

| מצב | Telegram | בקשות חיצוניות |
| --- | --- | --- |
| הסתר את הכתובת (`hide`) | השתמש בפרוקסי; המתן אם אף אחד לא עובד. אין פתרון חלופי ישיר. | נדרש SOCKS5/HTTP; בקשות ללא פרוקסי מתאים יידחו. |
| Direct כפתרון אחרון (`fallback`) | MTProxy האוטומטי עשוי להשתמש ב-Direct לאחר העיכוב שהוגדר, ולאחר מכן לחזור לפרוקסי פעיל. | יש להעדיף פרוקסי חיצוני שהוגדר מראש או את נתיב ה-SOCKS5/HTTP של החשבון; אחרת, מותר להשתמש ב-Direct. |
| שרת מאחורי מנהרה או VPN (`tunnel`) | מותר להשתמש בקישורים ישירים ובמעבר אוטומטי מיידי למאגר חלופי. | גישה ישירה מותרת כאשר לא הוגדר שרת proxy מתאים. |

מצב המנהרה או ה-VPN מניח שאתם מנהלים את הרשת הזו בנפרד. ללא מנהרה פעילה, היעדים יכולים לראות את כתובת השרת עצמו. בחרו את המצב בהתאם לרשת שלכם בפועל, ולא לפי שם האפשרות.

### בחר מסלול

| מסלול | הגדרות | גבולות |
| --- | --- | --- |
| MTProxy אוטומטי | רשימות מובנות או קטלוג אופרטורים | שומר על מסלול טלגרם פעיל; המעבר לגיבוי ישיר תלוי במצב ה-IP |
| ישיר | מצב מנהרה או VPN | Telethon משתמש במסלול הרשת של המארח |
| SOCKS5 | שרת, יציאה, שם משתמש/סיסמה (אופציונלי) | python-socks, תמיכה ב-DNS של יעד מרוחק |
| HTTP CONNECT | שרת, יציאה, שם משתמש/סיסמה (אופציונלי) | HTTP CONNECT רגיל; TLS לפרוקסי עצמו אינו מיושם |
| MTProxy | שרת, יציאה, סוד | שיטת העברה ניסיונית של Telethon; 32 ספרות הקסדצימליות או `dd` + 32 ספרות הקסדצימליות |

סודות TLS מזויפים מסוג `ee` נדחים. הנורמליזציה של Telethon 1.45 יכולה להסיר קידומת ודומיין, אך היא אינה מיישמת TLS מזויף. הדביקו `tg://proxy?server=…&port=…&secret=…` או `https://t.me/proxy?server=…&port=…&secret=…` ובחרו **באפשרות "מלא שדות מהקישור"**. פעולה זו מאמתת וממלאת את השדות ללא יצירת חיבור או שמירה; בדקו ושמרו את המסלול בנפרד. שדות ידניים נשארים זמינים. ראו [קישורי פרוקסי של טלגרם](https://core.telegram.org/api/links#proxy-links).

### פרוקסי ציבוריים המסופקים על ידי ההתקנה שלכם

הרשימה המובנית משלבת ארבעה מקורות: [SoliSpirit/mtproto](https://github.com/SoliSpirit/mtproto), [zakky8/mtproto-proxy-pro](https://github.com/zakky8/mtproto-proxy-pro), [kort0881/telegram-proxy-collector](https://github.com/kort0881/telegram-proxy-collector) [ו-3yed-61/MTP-Collector](https://github.com/3yed-61/MTP-Collector). תמונת המצב המצורפת מכילה נתוני נקודות קצה, ייחוס למקורות ותאריכי הורדה. הופעתו של ספק ברשימה אינה מהווה הוכחה לכך שהפרוקסי פועל או מספק כל עדכון של טלגרם.

**MTProxy האוטומטי** בודק את קישוריות התקשורת של טלגרם, שומר על פרוקסי פעיל ומעביר לפרוקסי אחר כאשר הוא נכשל. סביבות העבודה מעדיפות פרוקסי שונים כאשר יש מספיק רשומות פעילות זמינות; כתובת יציאה ייחודית אינה מובטחת. פרוקסי שנכשלו נחים לפני ניסיון נוסף. אם אף אחד לא עובד, מצב ה-IP קובע אם האיסוף חייב להמתין או שמותר להשתמש בחיבור ישיר. החלפת פרוקסי אינה משנה את החשבון או מוחקת את היומן שלו. בחירות ושינויים במסלול נרשמים ביומן החתום.

כאשר מסלולים אוטומטיים פעילים, הרשימות מתעדכנות מדי שעה ובדיקות העברה מתבצעות מדי עשר דקות כברירת מחדל. ניתן להגדיר מרווחי זמן אלה. **עדכון רשימות ציבוריות** מחייב רענון; הצגת הרשימה בלבד אינה משנה מסלול ידני שנשמר.

**תעבורת טלגרם ובקשות HTTPS משתמשות בנתיבים שונים.** הורדות רשימות משתמשות ב חיבור HTTPS נפרד ובנתיב הבקשות החיצוני המסופק. `TGWITNESS_PROXY_FEED_PROXY` מבטל במפורש נתיב זה באמצעות פרוקסי HTTP/SOCKS5; שני גרסאות ה-Compose של האספן מעבירות אותו. מאגר הרקע פועל בהתאם לסביבת העבודה הראשית. לא נשלחים לספקי העדכונים שום הפעלות טלגרם, פרטי הזדהות ל-API, אסימון לוח הבקרה או אסימון בוט. שמות הספקים, תאריכי הצילום ומסלול ההורדה מופיעים תחת **"מאיפה מגיעה הרשימה"**.

MTProxy מעביר תעבורת Telegram בלבד. פעולות HTTP של סביבת העבודה, כגון חותמות זמן, התראות, עותקים מחוץ לאתר ובדיקות מקור, משתמשות בפרוקסי SOCKS5/HTTP נפרד כאשר הוא מוגדר, ולאחר מכן במסלול SOCKS5/HTTP של החשבון. ללא אף אחד מהם, האפשרות "הסתר את הכתובת" דוחה את הבקשה; המצבים האחרים מאפשרים "ישיר". ניתן להשבית בקשות חיצוניות. פרוקסי להורדת פיד שהוגדר במפורש נשאר כקיצור דרך נפרד של המפעיל. שירות העדים העצמאי שומר על המסלול שלו.

עבור שירותים פרטיים המנוהלים על ידי מפעיל, הגדרת סביבת השרת הקיימת `TGWITNESS_ALLOW_PRIVATE_DESTINATIONS=1` מאפשרת יעדים פרטיים ושומרת על פתרון שמות מארחים בצד הפרוקסי. לא ניתן להפעיל אותה מהלוח. מצב "ציבורי בלבד" דוחה יעדים ב-`.onion` לפני פנייה למפתרון הציבורי; שירותי Tor onion מחייבים הגדרה מפורשת של יעד פרטי ופרוקסי מתאים. התנהגות ה-DNS הזו חלה על פעולות HTTP חיצוניות, ולא על תעבורת Telegram. Cloudflare מתעדת את [נקודת הקצה של ה-DNS ב-JSON](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json/).

****פרמטרים אוטומטיים של מאגר****

תחת **פרמטרים → MTProxy אוטומטי**, הגדר את סף הכשל, זמן ההמתנה, הרוטציה המתוכננת, שיתוף הפרוקסי ועיכוב הגיבוי המותר.

| בקרה | ברירת מחדל |
| --- | --- |
| ניתוק לפני החלפה | 3 בתוך 10 דקות |
| מספר ה-proxies שנבדקו בכל ניסיון חיבור | 3 |
| מנוחה ראשונה / מקסימלית לאחר כשל | 10 דקות / 6 שעות |
| רוטציה מתוכננת | מושבת; הפעל במקרה של כשל |
| חשבונות לכל פרוקסי | 0: העדיפו ערכים נפרדים, צרו ערכים משותפים במידת הצורך. הגדירו את 1 להמתנה לערך בלעדי. |
| השהיה לפני מעבר לגיבוי ישיר המותר | 10 דקות; הסתרת הכתובת עדיין מסרבת ל-Direct |
| בדיקות רענון/העברה של פיד | פרוטוקולים 60/10; ערכי סביבת העבודה הראשית חלים על המאגר המשותף |

שימוש בפרוקסי שונים אינו מבטיח כתובות יציאה שונות. הגדרות אלה אינן עוקפות את המגבלות של Telegram ואינן מוכיחות אנונימיות.

כדי להחליף את הרשימה הציבורית בקטלוג המפעילים שלך, הגדר את העקיפה שלהלן. פעולה זו מבטלת לחלוטין את המנויים החיצוניים, גם כאשר מערך ה-`proxies` שלו ריק.

העתיקו [את הקטלוג הריק](https://github.com/phishdestroy/TgWitness/blob/main/deploy/proxies.config.example) ל-`proxy-config/proxies.json` והוסיפו את נקודות הקצה הציבוריות שהטמעתם:

```
{"format": "tgwitness-proxy-catalog-v1", "proxies": [
  {"id": "project-eu", "label": "Project EU",
   "link": "tg://proxy?server=REPLACE_HOST&port=443&secret=REPLACE_SECRET"}
]}
```

יש להחליף את ערכי הדוגמה. מתקבלים עד 32 ערכים נפרדים. הרשימה המאומתת מחזירה תוויות/מארחים/יציאות ללא סודות משותפים; בחירת אחד מהם שומרת את פרטי הזיהוי שלו בכספת סביבת העבודה. הזמינות נותרת בלתי נבדקת עד לביצוע בדיקת העברה מפורשת. קטלוג פגום מאפשר ביצוע תצורה ידנית.

הפעלה מקומית: הגדר את `TGWITNESS_PROXY_CATALOG` לנתיב ה-JSON המקומי. Docker:

```
docker compose -f compose.yaml -f deploy/compose/compose.proxies.yaml up -d --build
```

השכבה (overlay) מעגנת את `proxy-config` כקריאה בלבד; הקבצים חייבים להיות קריאים על ידי ה-UID 10001 של הקונטיינר. ספרייה זו אינה נכללת ב-Git, בהקשר הבנייה של Docker ובארכיוני המקור. קטלוג זה מגדיר את חשבונות האיסוף; [בוט ה-witness](https://phishdestroy.github.io/TgWitness/he/docs/reference/witness/) משתמש במסלול HTTP/SOCKS5 משלו, ולא ב-MTProxy.

המעבר הישיר נשלט על ידי מצב ה-IP שלעיל. יש להשהות את המעקב לפני שינוי מסלול. שמירה מנתקת לקוחות ישנים ומבטלת התחברות שלא הושלמה; לקוח חדש משתמש במסלול השמור. הקישור בין היומן/הפעלה של החשבון נשאר. ההגדרות מחליפות את המסלול הקודם: יש להזין מחדש את פרטי הכניסה לפרוקסי בעת עריכתו.

פרטי ההזדהות מוצפנים ב-`network.enc`. ה-API אינו מחזיר את שם המשתמש, הסיסמה או המפתח הסודי. הרשומות החתומות מכילות את סוג המסלול ואת המידע האם פרטי ההזדהות קיימים, ללא ציון נקודת הקצה והמפתחות הסודיים. המפעיל יכול לראות את נקודת הקצה בלוח הבקרה. שדות המפתחות הסודיים מתנקים לאחר שמירה, נעילה או מעבר בין סביבות עבודה.

**בדיקת חיבור ל-Telegram**, הזמינה גם לפני הכניסה, פותחת וסוגרת חיבור זמני וללא אישור ל-Telegram דרך המסלול. היא אינה יוצרת קשר עם אתר לבדיקת IP. הצלחה בבדיקה מאשרת קישוריות העברה, אך לא גישה לקבוצה, מסירה מלאה או אנונימיות.

הפרוקסי חל על חיבורי לקוח Telegram, כולל הורדות מדיה מ-Telegram DC. לדפדפן, ל-pip, ל-SSH ולכלי TSA המופעלים ידנית יש נתיבים נפרדים. שם המארח של הפרוקסי עשוי להיות מתורגם באופן מקומי. `rdns` משפיע על שמות המארחים היעדיים; Telegram מספקת לעתים קרובות כתובות IP מספריות של DC.

SOCKS5 ו-HTTP CONNECT רגיל אינם מצפינים כשלעצמם את פרטי הזיהוי של ה-proxy או את מנהרת ה-client-to-proxy. MTProto מגן בנפרד על תעבורת טלגרם. יש להשתמש בערוץ מאובטח מתאים אל ה-proxy ברשת שאינה מהימנה. קבוצות פרטיות הן צ'אטים בענן; MTProto אינו הופך אותן לצ'אטים סודיים המוצפנים מקצה לקצה.

## הצפנה וחתימות

| שכבה | יושם | אחריות המפעיל |
| --- | --- | --- |
| תעבורת טלגרם | Telethon MTProto | אמון בפלטפורמה, מסלול וזמינות |
| לוח בקרה מקוון | אסימון נושא, ברירת מחדל של לולאה חוזרת, מגבלות בקשות | HTTPS או מנהרת SSH לגישה מרחוק |
| סודות | Fernet לאחסון פרטי הזדהות ל-API, פרטי הפעלה, פרטי הזדהות לפרוקסי ומפתח חתימה פרטי | יש להגן על מפתח הפענוח ועל השרת המארח |
| מפתח הכספת | מפתח מקומי, או מפתח ראשי חיצוני להתקנה חדשה | אחסון נפרד ומוגן וגיבוי מפתחות |
| הודעות וקבצים מצורפים | אחסון יישומים בטקסט רגיל | דיסק/נפח מוצפן |
| ZIP/JSONL/CSV/HTML | בדיקות תקינות, ללא הצפנת תוכן | הגנה על עותקים מועתקים והעברות |
| מקור ומועד | יומן חתום, אישור תהליך, כלים לפי RFC 3161 | מפתח מהימן, נקודות ביקורת עצמאיות/TSA והליך שמירה |

**ההגנה על האחסון** בחשבון מציגה מצבים אלה. אסימון הפאנל הוא סוד גישה, ולא סיסמת הצפנה. הוא מעניק גישה למנהל; ניתן להגביל את טווח [האסימונים שהונפקו](https://phishdestroy.github.io/TgWitness/he/docs/reference/access/) לחשבונות ולצ'אטים. סביבות העבודה חולקות את תהליך המארח ואינן דיירים מבודדים.

BitLocker, LUKS, FileVault או אמצעי אחסון מוצפן מנוהל יכולים להגן על האחסון בהתאם למודלי האיום הרלוונטיים. מנהל מערכת של מחשב פועל שאינו נעול עדיין יכול לקרוא את הנתונים. יש לכלול את SQLite WAL/SHM, מדיה, ייצוא זמני, swap, גיבויים והורדות דפדפן בתכנון האחסון. אמצעי אחסון של Docker אינו מוצפן רק בגלל היותו אמצעי אחסון. TgWitness אינו מיישם SQLCipher או הצפנת אובייקטים.

## מפתח ראשי חיצוני

להתקנה **חדשה**, יש למקם את המפתח הראשי מחוץ לספריית הנתונים. פעולה זו אינה מעבירה באופן אוטומטי כספת מפתחות מקומית קיימת. הכינו ספריית מפתחות הנגישה רק לזהות השירות, ולאחר מכן הפעל:

```
python -m tgwitness.security create-master-key /private/keys/tgwitness-master.key
export TGWITNESS_VAULT_KEY_FILE=/private/keys/tgwitness-master.key
python -m tgwitness --data-dir /private/observations/new-case
```

PowerShell, תוך שימוש בסביבת הפרויקט המותקנת:

```
python -m tgwitness.security create-master-key E:\PrivateKeys\tgwitness-master.key
$env:TGWITNESS_VAULT_KEY_FILE = 'E:\PrivateKeys\tgwitness-master.key'
python -m tgwitness --data-dir E:\PrivateData\new-case
```

ב-Docker, יש לעגן את הקובץ לקריאה בלבד מחוץ ל-`/data`, למשל ב- `/run/secrets/tgwitness-master.key`, ולהגדיר את משתנה הסביבה לנתיב זה. על ה-UID של השירות להיות בעל הרשאת קריאה לקובץ. יש להעביר את הנתיב, ולא את בתים המפתח, דרך קובצי סביבה/תצורה.

כל סביבת עבודה מקבלת "סולט" (salt) ציבורי אקראי ומפתח Fernet משלה, הנגזר באמצעות HKDF-SHA256. ה-`vault.external.json` מאחסן את מטא-הנתונים של הגזירה, ולא את המפתח הראשי. מפתח חסר או שגוי יגרום לכישלון ההפעלה, מבלי להחליפו בשקט. יש לשמור הן את מטא-הנתונים של ה"סולט" והן את המפתח הראשי לצורך שחזור.

כל סביבות העבודה נגזרות מאותו מפתח ראשי; פגיעה בו משפיעה על כל ההתקנה. התהליך הפועל יכול לפענח סודות. זהו אינו HSM או KDF של סיסמה. לא מתקבלות סיסמאות אנושיות שרירותיות כתחליף למפתח אקראי.

יש לשמור על המפתח הקיים עבור התקנות קיימות עד לביצוע ואישור של מעבר מכוון. מחיקת ה-`vault.key` או החלפת מפתח ראשי עלולה לשבש את הגישה למפתחות הפעלה/חתימה. יש לשמור גיבויים ומפתחות מוצפנים בנפרד ולבדוק את תהליך השחזור בסביבה מבודדת.
